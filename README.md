# Agent 工程化进阶

> 从"能把 Agent 跑起来"，到"能在线上跑住它"。

本书**从零开始**，循序渐进到 `Harness`：认识大模型 → 会用 LLM 做 RAG → 造出 Agent → 让循环可控 → 上下文与知识 → 敢上线并量化。

基础教程（ai-agents-from-zero）的内容已**完整整合进本书**（逐章映射见 [00-如何使用本书.md](00-如何使用本书.md) 的 0.9 节），不需要先读它。

---

## 这本书解决什么问题

从"能让模型回答问题"到"能在线上跑住它"，一路上你会遇到下面这些情况，而且**搜不到答案**：

| 现象 | 你缺的能力 | 对应章节 |
|---|---|---|
| 模型一本正经地说错话，你不知道为什么 | 大模型心智模型 | 第 1 章 |
| 不知道一次调用花了多少 token、多少钱 | 计量 | 第 2、37 章 |
| 改了 prompt，不知道变好还是变坏 | 评测 | 第 40、42、54 章 |
| Agent 报错，不知道错在哪一步 | 可观测 | 第 38 章 |
| 同一个问题问两遍，结果差很多 | 稳定性设计 | 第 1、42 章 |
| 用户关掉页面，任务丢了 | 状态持久化 | 第 22、23、41 章 |
| RAG 效果差，只会调 `top_k` | 检索工程 | 第 10、51 章 |
| 检索回来的东西"有原文但答不出来" | GraphRAG / 意图识别 | 第 25、28 章 |
| 用户说"我上次说的那个方案"它不记得 | 记忆分层 | 第 26、27 章 |
| Agent 怎么加载 skills / MCP / tools 说不清 | 装配 | 第 13、14、**55**、57 章 |
| 担心 Agent 执行 `DROP TABLE` | 护栏 | 第 31、33 章 |
| 一个请求烧掉 5 块钱，不知道贵在哪 | 成本工程 | 第 34 章 |
| 首字 30 秒才出来 | 延迟工程 | 第 35、41 章 |
| 知识库越加越乱，答案越来越飘 | LLMWiki | 第 29、30、39 章 |
| 拆了多 Agent，反而更慢更贵更差 | 多 Agent 判据 | 第 36 章 |
| 出故障后只能靠猜 | 复盘方法论 | 第 56 章 |
| 说不清"我这套东西到底工程化到什么程度" | Harness | 第 57 章 |

## 三条铁律

1. **能跑。** 每个代码块都是可以执行的完整代码，不是伪代码。所有示例都随仓库提供，并且经过实际运行验证。
2. **能失败。** 每章都有**失败实验**——故意让它错，观察错误形态。没故意让它失败过的人，不认为自己理解它。
3. **有数字。** 每章结束时，你必须能给出一个数字（召回率、成本、P95 延迟、拦截率）。给不出数字的"优化"都是玄学。

---

## 本书的组织方式

不是"一章一个 demo"，而是**每章解决上一章暴露的缺陷**：

- 写了第一个能跑的 Agent（第 11 章）→ 它开始无限循环（第 16 章）→ 加刹车后它还是答错（第 17 章）→ 简单任务其实不该用 Agent（第 18 章）→ 复杂任务要先规划（第 19 章）→ 规划错了要能改（第 21 章）→ 任务太长跑一半断了（第 22、23 章）→ 上下文爆了（第 24 章）……
- 代码是**阶梯**：`step1 → step2 → step3`，每级只加一个新概念，文件开头写着"上一级的痛点"。
- 公共底座 `code/common/` 逐章长大：第 37 章写 `meter.py`，第 38 章写 `trace.py`，第 57 章把全部能力编成自评表。

原因很简单：**组件是可以查文档的，能力只能在解决真实问题的过程中长出来。**

所以每章开头都是一个"你会遇到的坏事"，而不是"某个技术是什么"。
