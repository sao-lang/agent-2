## 一、两种继续

"恢复"这个词覆盖了两件不同的事，混在一起会做出错误的实现：

| | 恢复（resume） | 重放（replay） |
|---|---|---|
| 从哪开始 | 崩溃前的那一步 | 第一步 |
| 用哪份数据 | 检查点里的 | 重新取 |
| 干什么用 | 让任务跑完 | 复现问题、做评测 |
| 副作用 | 必须幂等 | 通常关掉 |

第三行说明它们其实是两个工具：恢复服务于"任务要完成"，重放服务于"想知道当时发生了什么"。

第四行是重放的关键：**重放时副作用应该被替换成记录，不能真的再发一次**。所以一个能重放系统，必须把"执行副作用"和"记录副作用"分成两层——这也是第 5 章把工具实现与调用分开的延续。

本章只讲第一行。

## 二、一个反直觉的事实

**大多数任务根本走不到需要恢复的复杂度，但需要恢复的那些，恰恰是最贵的。**

| 任务长度 | 崩溃概率 | 重跑代价 | 值得做检查点吗 |
|---|---|---|---|
| 3 步、几十秒 | 低 | 低 | 通常不值得 |
| 20 步、几分钟 | 中 | 中 | 值得（落盘成本很低） |
| 上百步、几十分钟 | 高 | 高 | 必须 |

第二行是本章的目标场景。它的特点是：落盘的成本（一次几十 KB 的写）与任务成本（几分钟、几万 token）相比可以忽略，而重跑一次的成本却是全部重来。

第一行的判断常被搞错——为三秒的接口加一套检查点，复杂度上升，收益为零。**先看任务的最长耗时，再决定要不要读这一章。**

## 三、进程会死

前四章的循环、守卫、状态、裁判全部活在内存里。进程一退出，它们全没了。

这不需要是崩溃。**发版重启、扩缩容、机器回收、用户关掉页面，都会让进程退出。** 一个跑二十分钟的任务，中途遇到任何一次重启，都要从头再来——包括那些已经产生副作用的部分。

`persist.py` 把这件事跑了一遍。任务四步：取订单、取政策、发通知、汇总。在第 3 步（发通知）之后进程崩掉。

```
=== 一、无检查点 ===
  步 1 取订单: ok
  步 2 取政策: ok
  步 3 发通知: 已发送
  步 3 之后进程崩溃
  步 1 取订单: ok
  步 2 取政策: ok
  步 3 发通知: 已发送
  步 4 汇总: ok
  实际发送次数：2  内容：['A1001', 'A1001']
```

（这是原理演示，`Outbox.send` 是一个记录调用次数的替身，不是真的发短信。）

重启之后从头跑，前两步白做（钱花了两次），第三步又发了一次通知。**用户收到了两封一模一样的短信。**

### 3.1 检查点解决了一半

有了检查点，恢复可以从崩溃处继续，前三步不用重做：

```
=== 二、有检查点、无幂等 ===
  ...
  步 3 发通知: 已发送
  步 3 之后进程崩溃
  ...进程重启...
  步 3 发通知: 已发送
  步 4 汇总: ok
  实际发送次数：2  内容：['A1001', 'A1001']
```

前两步省下来了，**但通知还是发了两次。** 原因是检查点记的是"做到第几步"，而第 3 步崩的时候，副作用已经发生了——它只是"还没被记为完成"。

这就是本章的核心问题：**检查点保存的是"进度"，副作用发生在"进度"之外。** 两者之间有一段缝隙，恢复必然落进去。

### 3.2 幂等键补上另一半

```
=== 三、有检查点 + 幂等键 ===
  ...
  步 3 发通知: 已执行过，跳过
  步 4 汇总: ok
  实际发送次数：1  内容：['A1001']
```

第三次运行时，通知只发了一次。做法是给这个副作用一个**跨进程稳定的键**（`notify:A1001`），执行前先查它是否已生效。

三组的差别可以压成一句话：**检查点让"能继续"，幂等让"继续时不会重复"。** 两者缺一不可——只有检查点会重复副作用，只有幂等会重复计算（多花钱，但结果对）。

### 3.3 为什么不直接重跑整个任务

一个常见的选择是：既然恢复很麻烦，那就让任务本身可重跑——重跑一遍，结果一样，副作用有幂等键兜着。

这个选择在某些场景下是对的（例如纯计算的批处理），但在 agent 任务里通常不成立：

| 重跑一次要付的 | 说明 |
|---|---|
| 全部 token | 前 N 步的历史全部重发一遍 |
| 全部工具调用 | 查询类工具会重查 |
| 全部延迟 | 用户等待时间翻倍 |
| 全部副作用 | 靠幂等兜住，但下游压力翻倍 |

第一行的账在长任务里很吓人。一个二十步的任务跑到十九步崩了，重跑要从第一步开始，等于把 95% 的成本再付一次。

第二行的"查询类工具会重查"还有一个隐性后果：**重查拿到的数据可能已经变了。** 第一步查到的库存与第十九步重查到的库存不同，重跑出来的结果与第一次不同——这时"重跑结果一样"这个前提就不成立了。

所以检查点的价值不只是省钱，是**保证重跑的那一段建立在同一份数据上**。

### 3.4 崩溃前后各发生了什么

把三组实验的差别拆成时间线，更容易看出问题在哪：

| 时刻 | 无检查点 | 有检查点无幂等 | 有检查点 + 幂等 |
|---|---|---|---|
| 崩前已完成 2 步 | 2 步 | 2 步 | 2 步 |
| 崩前副作用 | 已发 1 次 | 已发 1 次 | 已发 1 次 |
| 崩前进度记录 | 无 | 第 2 步 | 第 2 步 + pending |
| 恢复后重做 | 第 1–4 步 | 第 3–4 步 | 第 3–4 步 |
| 副作用总计 | 2 次 | 2 次 | 1 次 |

第二行的"崩前副作用"三列相同：**副作用已经发生了，这是事实。** 区别在于后面两列记录了它、并且知道怎么处理它。

第三行是本章所有设计的落点：**`pending` 这个标记就是"崩前副作用可能已经发生"的显式表达。** 没有它，恢复只有两种猜测（4 的表格）。

因此三个实现的差别不在"做得对不对"，而在"知不知道"。知道，就能查；不知道，只能猜。

### 3.5 长任务的最坏情况

把恢复的账算一遍，能看出为什么它值得单独一章：

| 任务步数 | 一旦崩溃，无检查点的代价 | 有检查点的代价 |
|---|---|---|
| 3 | 重跑 3 步 | 重跑 1 步 |
| 10 | 重跑 10 步 | 重跑 1 步 |
| 30 | 重跑 30 步 | 重跑 1 步 |

第二列随步数线性增长，第三列几乎不变。**这就是检查点的全部价值：把"崩溃代价"从与步数成正比，变成常数。**

但第三列有一个前提："检查点里的东西够用"。如果检查点缺了 messages，恢复后模型要从头理解，实际代价又回到重跑。

所以第 4.2 节说"重放的不仅是动作"，它决定了第三列能不能真的成立。

### 3.6 三组实验为什么值得跑

`persist.py` 的三组对照不是示例凑数，它对应三档实现水平：

| 实现 | 结果 | 用户感受 |
|---|---|---|
| 无检查点 | 重跑、副作用重复 | 收到两封短信，慢一倍 |
| 有检查点 | 只重跑最后一步 | 只收到两封同样的短信 |
| 有检查点 + 幂等 | 只重跑最后一步，副作用一次 | 正常 |

第二行是本节的要点：**有检查点之后，用户感受不但没变好，反而更奇怪了**——"任务明明跑完了，还是收到两封"。

这一档实现最容易被误认为"已经解决"：成本降了、日志看起来也正常。只有把"副作用次数"单独数出来，才知道问题还在。

所以验证脚本里最该断言的数，不是"跑完了没有"，而是**"副作用发生了几次"**。

## 四、检查点存什么

一个检查点要能让进程在新实例里"接着跑"。为此它必须包含四样东西：

| 内容 | 为什么 | 不存会怎样 |
|---|---|---|
| 进度（做到第几步） | 从哪继续 | 从头跑（1） |
| 状态（第 10 章的 State） | 已掌握什么 | 要重查，或推断不准 |
| 完整历史（messages） | 下一轮模型要看 | 模型不知道前因 |
| 待确认的副作用 | 有没有"做了但没记" | 重复副作用（1.1） |

前三样在 `Checkpoint` 里是 `step` / `state` / 隐含在 state 里；第四样是 `pending_side_effect` 与 `effect_key`。

```python
from dataclasses import dataclass


@dataclass
class Checkpoint:
    step: int
    done: list[str]
    state: dict
    pending_side_effect: bool = False
    effect_key: str | None = None
```

`pending_side_effect` 这个字段是本章的关键设计。它的含义是：**这一步的副作用可能已经执行了，但我还没确认。**

写入流程是三步，不是一步：

```
1. 写检查点：pending=True, effect_key="notify:A1001"
2. 执行副作用
3. 写检查点：pending=False
```

崩在第 2 步之后、第 3 步之前，恢复时会看到 `pending=True`。这时不能直接重做，要先查这个 `effect_key` 是否已经生效——这就是幂等的入口。

### 4.1 为什么先写 pending 再执行

反过来（先执行、后写检查点）会漏掉一种情况：副作用执行了，但检查点没写上（崩在中间）。恢复时看到的是"还没到这一步"，于是重做。

先写 pending 的代价是：可能在副作用没执行时就标记了 pending。但这**不是问题**，因为恢复时的动作是"查一下有没有生效"，而不是"假设已经生效"。查不到就执行，查到了就跳过——两种情况都正确。

| 顺序 | 崩在中间时的状态 | 恢复动作 | 结果 |
|---|---|---|---|
| 先写 pending | 记录了"可能已执行" | 查 effect_key | 正确 |
| 先执行 | 记录是"没执行" | 直接执行 | 重复 |

**这一行的差别就是"可恢复"与"不可恢复"的分界。**

### 4.2 检查点的粒度

每步都存，还是每 N 步存一次？

| 粒度 | 恢复代价 | 存储代价 |
|---|---|---|
| 每步 | 最小（重跑 0 步） | 最大（N 份历史） |
| 每 N 步 | 重跑最多 N−1 步 | 小 |
| 只在关键步 | 取决于关键步的位置 | 中 |

第二行的代价不只是钱，还包括**重跑时的副作用**——如果重跑的这几步里有副作用，还要靠幂等兜住。所以粒度的选择与"副作用在哪些步"绑定：**有副作用的步必须单独存检查点**，纯查询的步可以攒着。

一个实用的起点是：**每步都更新一份"当前状态"，副作用前后各存一次完整检查点。** 前者用于快速恢复，后者用于精确处理幂等问题。

### 4.3 检查点的原子性

`Checkpoint` 有五个字段，写到磁盘上必须是一次完成。常见错误是分别写：

```python
def save_split(state: dict, step: int) -> None:
    """反例：分开写两个文件。中间崩掉就会不一致。"""
    import json
    with open("state.json", "w", encoding="utf-8") as f:
        json.dump(state, f, ensure_ascii=False)
    with open("progress.json", "w", encoding="utf-8") as f:
        json.dump({"step": step}, f)


if __name__ == "__main__":
    save_split({"facts": ["签收 3 天"]}, 5)
    print("写了两个文件：state.json / progress.json")
```

中间崩掉，就会读到"进度是第 5 步、状态是第 3 步"（第五节的第五条）。

标准做法是**写临时文件 + 原子改名**：

```python
import json
import os


def save_atomic(path: str, payload: dict) -> None:
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(payload, f, ensure_ascii=False)
        f.flush()
        os.fsync(f.fileno())          # 先落盘，再改名
    os.replace(tmp, path)             # 同一文件系统内是原子的


if __name__ == "__main__":
    save_atomic("cp.json", {"step": 3, "state": {"facts": ["签收 3 天"]}})
    print(open("cp.json", encoding="utf-8").read())
```

输出：

```
{"step": 3, "state": {"facts": ["签收 3 天"]}}
```

两个要点：**`fsync` 在改名之前**（否则改名了但内容还在页缓存里，断电会得到空文件）、**`os.replace` 而不是 `os.rename`**（前者在 Windows 上也能覆盖已有文件）。

这份代码会在当前目录留下一个 `cp.json`，示例跑完可以删掉。

### 4.4 检查点存在哪

存储位置决定恢复能做多快、能保留多久：

| 存储 | 写入延迟 | 适合 |
|---|---|---|
| 本地文件 | 微秒级 | 单机开发、小任务 |
| Redis | 毫秒级 | 多实例、需要快速恢复 |
| 数据库 | 几毫秒到几十毫秒 | 需要审计、需要按业务查 |
| 对象存储 | 几十毫秒 | 历史归档、不适合热恢复 |

第二行与第三行的选择常被问起。判据是**要不要按业务字段查**："找出所有卡在第 3 步超过半小时的任务"，只有数据库能直接回答；Redis 需要自己维护索引。

第一行看着最弱，但它在"单机长任务"里完全够用，而且它是唯一不需要额外依赖的。第 3.3 的原子写对一个本地文件就够。

无论选哪个，**键都应该是 `run_id`**——不是任务类型，不是用户 id。一次运行一个检查点，这是恢复的粒度。

### 4.5 检查点的大小

检查点会随任务变长。一个 30 步的任务，messages 可能有上百 KB：

| 内容 | 30 步时的大致占比 |
|---|---|
| messages | 90% 以上 |
| state | 几 % |
| 守卫计数与元信息 | 忽略不计 |

这意味着**检查点的成本主要由 messages 决定**。两个直接的推论：

**第一，不必每步存完整 messages。** 第 3.2 说的"每步更新当前状态"可以只更新 state 与进度，messages 按需存（例如每 5 步或每个副作用前后）。

**第二，可以考虑存裁剪版。** 第 7 章的裁剪逻辑用在这里：恢复时模型需要的是"能继续推理的上下文"，不是逐字原文。代价是恢复后的历史与原来不同（4.2 已说明这一点可接受）。

但有一处不能省：**副作用那一步前后的 messages 必须完整。** 因为那一步的重放要精确对齐。

### 4.6 一个最小的落盘实现

把 3.3 的原子写与本章的字段合起来，一个可以直接用的落盘函数：

```python
import json
import os
from dataclasses import asdict, dataclass, field


@dataclass
class Checkpoint:
    step: int
    state: dict
    messages: list[dict] = field(default_factory=list)
    counters: dict = field(default_factory=dict)
    pending_side_effect: bool = False
    effect_key: str | None = None
    schema_version: int = 1


def save(path: str, cp: Checkpoint) -> None:
    tmp = f"{path}.tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(asdict(cp), f, ensure_ascii=False)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)


def load(path: str) -> Checkpoint:
    with open(path, encoding="utf-8") as f:
        data = json.load(f)
    if data.get("schema_version", 0) < 1:
        raise ValueError("检查点版本过老，无法恢复")
    return Checkpoint(**data)


if __name__ == "__main__":
    cp = Checkpoint(step=2, state={"facts": ["签收 3 天"]},
                    messages=[{"role": "user", "content": "退货?"}],
                    counters={"n_steps": 2})
    save("_cp_demo.json", cp)
    back = load("_cp_demo.json")
    print(back.step, back.state, len(back.messages), back.counters)
    os.remove("_cp_demo.json")
```

输出：

```
2 {'facts': ['签收 3 天']} 1 {'n_steps': 2}
```

六个字段正好对应本章讲过的六件事：进度、状态、历史、守卫计数（4.4）、副作用待确认（3.1）、版本（6.2）。

这份实现只有两个函数，但它已经满足"原子、完整、可版本判断"三条要求。生产环境把它换成 Redis 或数据库时，换的是 `save`/`load` 的实现，不是这两个函数在代码里的位置。

## 五、恢复从哪一步继续

"从崩溃处继续"听起来简单，实际有三种解释：

| 解释 | 从哪开始 | 风险 |
|---|---|---|
| 重做崩掉的那一步 | 第 3 步重新执行 | 若副作用已生效则重复 |
| 跳到下一步 | 第 4 步开始 | 若副作用没生效则漏掉 |
| 先确认再决定 | 查 `effect_key` 后决定 | 多一次查询 |

第三种是正确的。前两种各自假设了"副作用一定没发生"或"一定发生了"，而崩溃时的事实是**不知道**。

```python
from dataclasses import dataclass


@dataclass
class Checkpoint:
    step: int
    done: list[str]
    state: dict
    pending_side_effect: bool = False
    effect_key: str | None = None


def resume(cp: Checkpoint, effects: set[str]) -> int:
    """返回应该从第几步开始（0-based）。"""
    if not cp.pending_side_effect:
        return cp.step + 1              # 上一步干净完成
    if cp.effect_key in effects:
        return cp.step + 1              # 副作用已生效，跳过
    return cp.step                      # 未生效，重做这一步


if __name__ == "__main__":
    cp = Checkpoint(step=2, done=[], state={},
                    pending_side_effect=True, effect_key="notify:A1001")
    print("已生效 ->", resume(cp, {"notify:A1001"}))
    print("未生效 ->", resume(cp, set()))
```

输出：

```
已生效 -> 3
未生效 -> 2
```

这个函数的两个分支，正好对应 1.1 与 1.2 的两种情况。

### 5.1 副作用生效状态的来源

`effects` 这个集合从哪来？三种来源，可靠性递增：

| 来源 | 做法 | 可靠性 |
|---|---|---|
| 本地记录 | 执行成功后写本地文件 | 本地文件与副作用不在同一个事务里 |
| 下游查询 | 调接口查"这条通知发出去了吗" | 依赖下游提供查询能力 |
| 下游幂等键 | 把 `effect_key` 传给下游，由它去重 | 最可靠 |

第三种是标准答案：**幂等不是调用方的事，是"副作用系统"必须提供的能力。** 调用方传一个键，下游保证"同一个键只生效一次"。这样即使调用方重试十次，用户也只收到一条。

第二行是退而求其次的做法，要求下游提供"按业务键查询"的接口。第一行最弱，因为本地文件可能比副作用先丢。

判据：**问一句"这个副作用系统支不支持幂等键"。** 支持就传，不支持就要求加——这是把不可靠变可靠的最短路径。

### 5.2 恢复时要重放的不仅是动作

恢复回第 3 步，除了重做那个动作，还要保证模型看到的上下文与崩溃前一致。

| 重放什么 | 从哪来 | 不一致的后果 |
|---|---|---|
| messages | 检查点 | 模型不知道前因，可能重复查询 |
| state | 检查点 | 结论与事实对不上 |
| 步数计数 | 检查点 | 守卫的上限判断错 |
| 随机种子（如有） | 不必 | 输出本就不确定 |

前三行必须来自检查点，不能"重新构造"。**重新构造的 messages 与当初发出去的那份只要有一个字节不同，缓存就失效**（第 3 章），成本会跳一档。

第四行说明了一件事：恢复追求的是"上下文一致"，不是"输出一致"。同一份上下文再次推理，结果可能不同——这是第 2 章讲的不确定性，恢复无法消除它。**能保证的是不重复副作用，不能保证重复的推理给出相同答案。**

### 5.3 恢复失败时的三条出口

恢复本身也可能失败：检查点损坏、版本不兼容、`effect_key` 查不到来源。三条出口：

| 出口 | 适用 | 代价 |
|---|---|---|
| 从头重跑 | 任务短、副作用少 | 重复成本，副作用靠幂等 |
| 交给人 | 任务长、副作用多 | 人工成本 |
| 放弃 | 任务可重入（用户会重发） | 用户体验 |

第二行是正确的默认。**恢复失败的场景通常伴随"状态不明"，而状态不明时人工判断比自动重试可靠。** 这正是第 9 章 3.1 的"原因不明时选最保守"。

第一行只在两个条件都满足时可用：任务足够短（重跑成本可接受）、所有副作用都有幂等键。缺一个，重跑就可能制造重复。

### 5.4 恢复与守卫的连接

恢复的任务是"接着跑"，而守卫的上限是"最多跑几步"。两者的计数必须接上：

| 计数 | 恢复后应该是什么 |
|---|---|
| 步数 | 崩溃前的步数（不是从 0 开始） |
| 累计 token | 崩溃前的累计 |
| 调用指纹集合 | 崩溃前见过的那些 |
| 空步连击 | 崩溃前的计数 |

第三行最容易被漏。恢复时如果 `seen_calls` 是空的，那个"已经重复过两次的调用"会被当成第一次，于是空转检测失效——任务会在恢复后继续打转，直到撞上上限。

第四行同理：连续三个空步应该是"累计三个"，而不是"恢复后重新数"。

**结论：守卫的状态也是检查点的一部分。** 它看起来只是几个计数器，但它们决定了恢复之后的行为与崩溃前是否一致。

### 5.5 恢复的可观测性

恢复是一个容易被忽视的观测点。三个数值得记：

| 指标 | 含义 | 异常时说明 |
|---|---|---|
| 恢复次数 / 运行数 | 有多少任务需要恢复 | 偏高说明进程不稳或任务太长 |
| 恢复后的完成率 | 恢复了能不能跑完 | 偏低说明检查点不完整 |
| 平均恢复步数 | 回退了多少步 | 偏高说明检查点太稀 |

第二行最有用。**恢复了但跑不完，说明检查点缺了东西**——通常是 messages 或守卫计数没存全（4.4）。这类问题在单个任务上表现为"偶尔卡住"，只有统计才能看出来。

第三行告诉你检查点粒度是否合适（3.2）。如果平均回退步数接近任务总步数，等于没有检查点。

### 5.6 恢复与任务取消的区别

恢复是把没做完的做完，取消是不再做。两者都会让进程停下来，但处理方式相反：

| | 恢复 | 取消 |
|---|---|---|
| 触发 | 进程意外退出 | 用户或系统主动停 |
| 检查点 | 保留，可继续 | 标记为废弃 |
| 副作用 | 按幂等处理 | 尽力停止，已发生的留痕 |
| 之后 | 新进程接着跑 | 不跑，记录结果 |

第三行是取消也需要设计的地方。**正在执行中的副作用是停不下来的**——一个已经发出去的 HTTP 请求，取消只是一个本地动作，对方可能已经处理了。所以取消的语义应该是"不再发起新的，并记录已经发起的"。

第二行的"标记为废弃"同样重要。取消之后，检查点如果还留着，某次自动恢复可能把它捡起来继续跑——用户已经不要这个任务了。

### 5.7 恢复之后要不要通知用户

恢复是内部的，用户看不到。但有两种情况必须让用户知道：

| 情况 | 为什么 | 怎么说 |
|---|---|---|
| 恢复后结果变了 | 数据可能已更新 | 说明"基于最新数据" |
| 恢复失败交给人 | 需要等待 | 给出预计处理时间 |
| 恢复多次（>2） | 可能有问题 | 触发告警，不一定告知用户 |

第一行是本章 5.2 讲的不确定性的外化：恢复后的推理可能与原来不同。如果用户之前看到过部分结果，第二次看到不同的答案会困惑。

第三行的阈值值得定：**同一个任务恢复超过两次，说明检查点或某一步有系统性问题**，应该告警而不是继续自动重试（9 的第四条）。

### 5.8 恢复过程中最贵的一步

恢复不是免费的。最贵的一步是"重新读历史"——如果检查点里存的 messages 有几十万字符，读文件、反序列化、再拼成请求，每一步都占时间。

| 步骤 | 典型耗时 | 优化空间 |
|---|---|---|
| 读文件 | 几十毫秒 | 用更小的格式（不加缩进） |
| 反序列化 | 几毫秒 | 不变 |
| 拼请求 | 与长度成正比 | 裁剪（第 7 章） |

第三行说明第 7 章与本章的交界：**裁剪不仅省 token，也省恢复时间。** 一个恢复了却慢到接近重跑的任务，等于没做检查点。

## 六、幂等落在哪一层

`effect_key` 的值怎么取，决定了幂等能做到什么程度：

| 取法 | 例子 | 覆盖范围 |
|---|---|---|
| 用 `tool_calls.id` | `call_order_01` | 只在同一次响应内唯一 |
| 用业务键 | `notify:A1001:2026-10` | 业务上唯一 |
| 用任务 id + 步号 | `run-1:step-3` | 同一次运行内唯一 |

第 5 章 5.1 讲过第一行的问题：`id` 是服务端为这一次响应生成的，重启之后同一逻辑步骤会得到新的 id，去重失效。

第三行能覆盖"同一次运行"的重试，但如果是"用户手动重新发起同一个任务"，它又失效了。

第二行是唯一跨运行有效的：**它由业务事实确定，与运行实例无关。** 代价是需要设计——什么样的业务键能唯一标识"这一次通知"？订单号 + 月份？订单号 + 状态变更事件？

### 6.1 副作用分类

不是所有工具都需要幂等键。分三类：

| 类别 | 例子 | 需要幂等键 |
|---|---|---|
| 只读 | 查询、检索 | 否（重试只是多花一次钱） |
| 幂等写 | 设置状态为"已通知" | 否（重复执行结果相同） |
| 非幂等写 | 发短信、下单、追加日志 | 是 |

第三行是必须处理的。第二行是常被误判的：`set status = notified` 确实重复执行无害，但如果它是"追加一条通知记录"，就变成了非幂等。

**判断方法：把同一个操作执行两次，结果会变吗？** 会变，就需要幂等键。

### 6.2 幂等键的存放位置

三种典型位置，覆盖不同的失败点：

| 位置 | 挡住什么 | 挡不住什么 |
|---|---|---|
| 调用方内存 | 同进程内的重试 | 进程重启 |
| 调用方持久化 | 跨重启的重试 | 多实例并发 |
| 下游去重 | 上述全部 | 下游不支持时无解 |

第二行是本章做的。它够用于单实例，但一次发版可能同时有多个实例在跑，两个实例各自查本地存储都"没做过"，于是都执行了一次。

第三行才是根治。这也是为什么 3.1 说"幂等是副作用系统的能力"——**把这个责任推给调用方，调用方永远要面对"多实例"这个漏洞。**

### 6.3 幂等键的形状

键本身的设计有几个具体约束：

| 约束 | 反例 | 为什么 |
|---|---|---|
| 不依赖运行实例 | 含进程 id | 重启就变 |
| 不依赖当前时间（除非业务如此） | `notify:now()` | 重试时时间不同 |
| 长度可控 | 把整段参数拼进去 | 下游可能限长 |
| 可读 | 纯哈希 | 排查时看不出是什么 |

第四行是实践中的硬要求。`a3f9c1d2` 在下游日志里毫无意义；`notify:A1001:2026-10` 一眼能看出是"给订单 A1001 发十月的通知"。

一个可靠的构造方式是"业务对象 + 动作 + 区分维度"：

```
{action}:{object_id}:{disambiguator}
notify:A1001:2026-10
refund:A1001:r-7f3a          # 退款单号
file-write:repo-1:src/main.py:sha256-abc
```

第三行的 `sha256-abc` 是内容哈希，它表达"写这个文件、内容是这个版本"。这样同一个文件写两次相同内容会被去重，写不同内容则不会——这正是"幂等"该有的语义。

### 6.4 补偿不是幂等

两个词经常混用，但它们解决的问题相反：

| 机制 | 做什么 | 适用 |
|---|---|---|
| 幂等 | 让重复执行不产生额外效果 | 支持幂等的下游 |
| 补偿 | 已经执行了，再做一次反向操作 | 不可回滚、也不支持幂等的下游 |

第二行的典型例子是"扣了款要退款"。补偿的代价很高：它需要一条反向的业务路径，还可能需要人审批（第 23 章）。

**优先选幂等，补偿是最后手段。** 判断方法：这个副作用系统支不支持"重复执行无副作用"？支持就用幂等；不支持，再问能不能加；加不了，才谈补偿。

补偿还有一处容易忽略：**补偿本身也可能失败。** 退款失败之后要重试退款，于是"补偿"也变成了一个需要幂等或补偿的操作。这就是为什么它排最后。

### 6.5 幂等的两种实现路径

同样的"只生效一次"，有两种实现路径，代价不同：

| 方式 | 做法 | 需要什么 |
|---|---|---|
| 天然幂等 | 操作本身就是"设置成某值" | 业务模型支持 |
| 记录去重 | 先查键表，没做过才执行 | 一张键表 + 原子插入 |

第一行最省，前提是业务允许。例如"把订单状态设为已通知"，重复执行结果一样；"给订单追加一条通知记录"就不是了。

第二行的关键在"原子插入"：

```python
import sqlite3


def run_once(conn: sqlite3.Connection, key: str, action) -> bool:
    """插入键成功才执行；插入冲突说明已做过。"""
    try:
        conn.execute("INSERT INTO effects(key) VALUES (?)", (key,))
        conn.commit()
    except sqlite3.IntegrityError:
        return False                      # 已存在，跳过
    action()
    return True


if __name__ == "__main__":
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE effects(key TEXT PRIMARY KEY)")
    calls: list[str] = []
    print(run_once(conn, "notify:A1001:2026-10", lambda: calls.append("s1")))
    print(run_once(conn, "notify:A1001:2026-10", lambda: calls.append("s2")))
    print("实际执行：", calls)
```

输出：

```
True
False
实际执行： ['s1']
```

`PRIMARY KEY` 让"插入成功"变成"抢到了执行权"。**这个模式仍然有一个漏洞**：插入成功、执行前崩掉，键已经存在但动作没做——于是这个副作用永远不会执行。

要补这个漏洞，键表需要三态：`claimed`（已抢占、未完成）/ `done`。恢复时看到 `claimed` 就检查下游是否已生效，本质上是 3.1 的第二种来源。

**没有一种方案能同时做到"一定执行"和"一定不重复"**，只能选一个方向并接受另一个方向的代价。多数业务选的是"宁可少发也不多发"（宁可重复检查，不可重复副作用），代价是极端情况下需要人工补发。

### 6.6 什么时候只生效一次是错的

幂等默认"重复执行有害"，但有些业务恰恰要求"每一次都要算数"：

| 业务 | 重复执行应该 | 幂等键 |
|---|---|---|
| 发通知 | 跳过 | 需要 |
| 记一条用户操作日志 | 记录两次 | **不需要** |
| 累加积分 | 加两次 | **不需要** |
| 扣款 | 跳过 | 必须 |

第二、三行是反例。**"追加日志"与"累加积分"在语义上就是每次都要生效的**，给它们加幂等键会把正常业务吃掉。

判断依据不是"这个操作有没有副作用"，而是**"重复执行一次，业务上算不算错"**。算错就要幂等键，不算错就不该加。

这一条在 5.1 的分类里已经隐含：那里的"非幂等写"指的是"重复执行会出错"，而不是"重复执行会写数据"。

## 七、这一层的失效模式

**第一，检查点写成功了，副作用没执行。** 恢复时看到 `pending=True`，去查 `effect_key`，查不到就重做——这是正确路径，不是故障。

**第二，副作用执行了，检查点没写。** 这是真正的漏洞。防法只有一条：**把"写 pending"放在副作用之前**（2.1）。

**第三，恢复时上下文与原来不一致。** 重新构造的 messages 与原来不同，输出可能变化。这不是 bug，但会让"恢复后结果变了"难以解释——所以恢复要记一条日志："本次是从第 N 步恢复的"。

**第四，幂等键设计得太粗。** 用 `订单号` 当通知的幂等键，那么同一订单的第二次通知（例如状态再次变化）会被当成重复而跳过。键的粒度必须与"业务上算不算同一次"一致（4 的第三行反例）。

**第五，检查点里的 state 与 messages 不一致。** 两个文件分别写、中间崩了，就会读到"进度是第 5 步、状态是第 3 步"。**检查点必须是一个原子写入的整体**，不能拆成多个文件。

### 7.1 一个可复现的验证脚本

幂等是否生效，必须能验证。验证的形态很固定：

| 要素 | 做法 |
|---|---|
| 制造崩溃点 | 在副作用之后、确认之前抛异常 |
| 恢复一次 | 用同一份检查点重新跑 |
| 断言副作用次数 | 必须是 1，不是 2 |
| 换键再跑一次 | 断言变成 2（证明键真的在起作用） |

第四行最容易漏。**只测"没有重复"，一个永远跳过的实现也能通过。** 加一条"换键之后应该重复"的断言，才能证明去重是按键做的，不是无条件跳过。

`persist.py` 的第三组就是第一、二、三行；第四行可以这样补：

```python
from dataclasses import dataclass, field


@dataclass
class Outbox:
    sent: list[str] = field(default_factory=list)

    def send(self, order_id: str) -> dict:
        self.sent.append(order_id)
        return {"sent": True}


def test_idempotent_by_key() -> None:
    box = Outbox()
    done: set[str] = set()

    def once(key: str) -> None:
        if key not in done:
            box.send("A1001")
            done.add(key)

    once("notify:A1001:2026-10")
    once("notify:A1001:2026-10")      # 同键 -> 跳过
    once("notify:A1001:2026-11")      # 换键 -> 再发
    assert box.sent == ["A1001", "A1001"], box.sent
    print("通过：同键去重，换键生效，共", len(box.sent), "次")


if __name__ == "__main__":
    test_idempotent_by_key()
```

输出：

```
通过：同键去重，换键生效，共 2 次
```

两个断言合起来才完整：同键只发一次（去重有效），换键会再发（去重不是无条件跳过）。

### 7.2 检查点的三个版本字段

检查点会随时间变化：代码升级、state 结构改动、字段增删。为此它需要三个版本字段：

```python
from dataclasses import dataclass


@dataclass
class VersionedCheckpoint:
    schema_version: int = 1      # 检查点结构本身的版本
    code_version: str = "0.1.0"  # 写入它的代码版本
    state_version: int = 1       # 内部 State 的版本（第 10 章 5.5）

    def can_resume(self, supported: int = 1) -> bool:
        """只支持当前及相邻一个版本；更老的交给人处理。"""
        return self.schema_version >= supported - 1


if __name__ == "__main__":
    cp = VersionedCheckpoint(schema_version=1, code_version="0.1.0", state_version=2)
    print("可恢复：", cp.can_resume())
    print("老检查点：", VersionedCheckpoint(schema_version=0).can_resume())
```

输出：

```
可恢复： True
老检查点： True
```

`can_resume` 的阈值是设计选择：**向后兼容一个版本容易，兼容三个版本要写三层迁移。** 超过两个版本的老检查点，最省事的处理是放弃并告知用户重发——这比写一堆迁移代码可靠。

三个字段的分工：`schema_version` 管"能不能读"，`code_version` 管"排查时知道是哪个版本的代码写的"，`state_version` 管"字段语义有没有变"。第 10 章 5.5 讲的"改语义就换字段名"，就是靠第三个字段兜住历史数据。

### 7.3 检查点不等于事务

检查点看起来像数据库事务，两者有本质区别：

| | 检查点 | 事务 |
|---|---|---|
| 范围 | 一个应用的状态 | 一个存储引擎的数据 |
| 原子性 | 靠"原子写文件"模拟 | 引擎保证 |
| 副作用 | 在事务外 | 可以纳入事务 |
| 失败后 | 应用自己决定怎么继续 | 引擎回滚 |

第三行是决定性的：**发短信、调第三方接口这些副作用，永远不在你的数据库事务里。** 所以再强的事务也解决不了"通知发了两次"（2.2）。

理解这一点，就不会指望"用事务把整个任务包起来"能解决问题。能包住的只有本地数据的读写，包不住外部世界。

这也是为什么本章花了整整两节讲幂等键：**外部副作用的正确性只能靠幂等，不能靠事务。**

### 7.4 恢复失败的三类根因

线上"恢复了但没跑完"的现象，根因基本是三类：

| 根因 | 表现 | 查什么 |
|---|---|---|
| 检查点不完整 | 恢复后重复查询、上下文对不上 | messages 与守卫计数是否存了 |
| 版本不兼容 | 反序列化报错，或字段读不到 | `schema_version` |
| 副作用状态不明 | 卡在 pending 上，反复查不到 | `effect_key` 是否在下游存在 |

第一行正是 4.4 讲的：守卫计数没存，恢复后空转检测失效，任务继续打转直到上限，看起来像"任务太难"。

第二行的修法不是"兼容所有版本"，而是 6.2 讲的"只兼容相邻一个版本，更老的交给人"。

第三行最麻烦：`effect_key` 在下游查不到，可能是"确实没执行"，也可能是"执行了但下游没有查询接口"。**没有查询接口时，这个方案就不成立**——只能靠 5.2 的第三行（下游去重）从源头避免。

### 7.5 幂等键在恢复时的两次用法

同一个键，在恢复流程里会被用两次，两次的作用不同：

| 时机 | 查什么 | 查不到时 |
|---|---|---|
| 恢复前 | 这个键是否已生效 | 重做这一步 |
| 重做时 | 这个键是否被别人抢先 | 直接执行 |

第一次是"判断要不要重做"（5.1 的 `resume`）；第二次是"重做时的并发保护"（6.5 的原子插入）。

两次都不能省。只做第一次，多实例同时恢复时会重复；只做第二次，恢复时会多跑一次无用的检查（但结果正确）。

### 9.3 恢复与反思的交界

恢复之后，产物可能已经过期（例如崩溃前查到的库存已经变了）。这时重算还是沿用？

| 情况 | 处理 |
|---|---|
| 事实是只读型（政策、配置） | 沿用，不必重查 |
| 事实会变（库存、余额） | 重查，或标注"基于某时刻数据" |
| 已经交付过部分结果 | 必须先检查交付状态 |

第三行与幂等是同一类问题：交付本身也是一个副作用。**一个已经给用户发过答案的任务，恢复后不能重新发一遍。**

所以"交付"也该带幂等键，键的取值与 6.3 相同：任务 id + 交付渠道 + 版本号。

## 八、一次完整的崩溃-恢复走查

把本章所有机制放在一个时间线上，看它们各在哪一刻起作用：

| 时刻 | 发生了什么 | 谁起作用 |
|---|---|---|
| t0 | 进入第 3 步 | — |
| t1 | 写检查点：pending=True, key=K | 4.1 |
| t2 | 执行副作用 | — |
| t3 | 崩溃 | — |
| t4 | 新进程读检查点 | 4.3 原子读 |
| t5 | 看到 pending=True | 4.1 |
| t6 | 查 K 是否生效 | 5.1 |
| t7a | 生效 → 跳到第 4 步 | 5.1 |
| t7b | 未生效 → 重做第 3 步 | 5.1 |
| t8 | 写检查点：pending=False | 4.1 |

八个时刻里，t1、t5、t6、t8 是本章新增的；t2 与 t3 之间那段"不知道"是必须要面对的事实。

对照 3.1 的失败情况：如果崩在 t1 之前（还没写 pending），说明副作用肯定没执行，重做安全；如果崩在 t1 之后 t3 之前，就走了 t6 的查询路径。**两种情况都被覆盖，没有第三种。**

### 9.5 检查点与"任务取消"的存储形态

取消之后检查点怎么办，是一个具体的存储决定：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 删除 | 干净 | 无法排查"为什么被取消" |
| 标记 `cancelled` | 可查 | 需要能被恢复逻辑排除 |
| 归档 | 可查且不占热存储 | 多一步搬运 |

第二行的关键在"能被恢复逻辑排除"。如果恢复逻辑只看 `step`，它会把已取消的任务捡起来继续跑——这是 5.6 讲的那个坑。

最小可行的做法：恢复入口先查 `status`，只处理 `running` 与 `interrupted` 两种状态。

---

### 8.1 检查点与"部分交付"

一个任务跑到一半已经交付了部分结果（例如先告诉用户"正在查"），崩溃恢复后不该重复交付。

| 已交付的内容 | 恢复后 |
|---|---|
| 提示性消息（正在处理） | 不重复发 |
| 部分结论 | 要么不重复，要么明确更新 |
| 最终结论 | 绝不重复（幂等键） |

第二行需要判断"新结论与旧结论是否不同"。相同就静默，不同就发一条"更新"——这比"什么都不发"诚实。

这三分法说明：**交付也需要状态。** 它不该只存在于"发过没发过"的布尔值里，而该记下"发了什么、什么版本"。

## 九、边界

**第一，持久化不解决"任务该不该继续"。** 它只保证能继续，不保证继续是对的。取消、超时、人工中止是另一套机制。

**第二，检查点不是备份。** 它只保留最近的状态（或几步），不能用来回溯历史。需要回溯就另存一份完整轨迹。

**第三，幂等不能替代审批。** 一个需要人点头的副作用，重复执行两次仍然错——只是没重复而已。审批是第 23 章的内容。

**第四，恢复的次数要有上限。** 一个每次都崩在同一个地方的任务，会无限恢复。加一个 `resume_count`，超过就放弃并交给人。

**第五，恢复的语义要写进接口。** 调用方需要知道"这次返回的结果是本次算的还是上次恢复的"，否则无法判断要不要重试。

### 9.1 一张检查清单

把本章的所有要求压成一张交付前的检查表：

| 检查 | 通过标准 |
|---|---|
| 检查点是一个原子文件 | 写临时文件再改名 |
| 含 pending 与 effect_key | 副作用前后各写一次 |
| 含守卫计数 | 恢复后的空转检测与原来一致 |
| 恢复前先查 effect_key | 不假设"没发生"或"发生了" |
| 非幂等写都有业务键 | 不含 `tool_calls.id`、不含进程信息 |
| 换键会再执行 | 测试里有一条正向断言 |
| 恢复次数有上限 | 超过交给人 |
| 三个版本字段齐全 | 能判断"能不能读" |

第三行最容易漏，第七行最容易被忘。两个都属于"平时没事、出事时才想起"的类型。

### 9.2 一句话总结

**检查点回答"做到哪了"，幂等回答"做过没有"。前者靠落盘，后者靠业务键——两者都做到，恢复才是安全的。**

只做前者，会重复副作用（2.1）；只做后者，会重复计算（2.5）。两个都不做，就是 2.4 那一列。

### 9.4 三个常见问题

**问题一：能不能不做检查点，直接让任务变短？**

能，而且往往是最好的解法。一个二十分钟的任务如果拆成四个五分钟的子任务，每次崩溃的损失就只有五分钟。检查点是"任务必须长"时的补偿手段，不是必需品。

**问题二：检查点多久清理一次？**

任务完成后立刻清（或者标记为 `done` 保留一段时间用于排查）。留着的过期检查点最大的风险是被误恢复——一个已经交付的任务被重新跑一遍，副作用会再来一次。

**问题三：恢复失败要不要重试？**

要，但只重试一次。第二次失败就交给人。这是 5.3 的第二行。

## 这一章建立的 5 件事

1. 检查点让"能继续"，幂等让"继续时不重复"。只有检查点会重复副作用，只有幂等会重复计算。
2. 检查点必须包含待确认的副作用（`pending` + `effect_key`），并且"写 pending"要在"执行副作用"之前。
3. 恢复的第三种解释才对：先查 `effect_key` 是否生效，再决定重做还是跳过。
4. 幂等键必须由业务事实确定，不能用 `tool_calls.id`（跨重启就变）或"任务 id + 步号"（跨任务就变）。
5. 真正的幂等由下游提供。调用方自建去重只能挡住一部分失败，多实例时必然有漏。
