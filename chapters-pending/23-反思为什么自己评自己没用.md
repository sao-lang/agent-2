## 一、自评通过，不等于没错

循环跑到一定步数，很自然会有这个想法：让模型自己检查一下结果对不对。

`reflect.py` 里做了一次对照。同一个产物，三套裁判：

```python
BAD = {"order_id": "A1001", "days": 3, "reason": "签收不想要"}


def self_review(artifact: dict) -> tuple[bool, str]:
    """自评：只看产物本身，不看依据。脚本化：总是通过。"""
    return True, "看起来合理，字段齐全。"


def rule_review(artifact: dict) -> tuple[bool, str]:
    """规则裁判：业务代码能表达的判据。"""
    days = artifact.get("days")
    reason = artifact.get("reason", "")
    if not isinstance(days, int):
        return False, "days 不是整数"
    if days <= 7 and "超过" in reason:
        return False, "days<=7 却说超过窗口"
    if "签收不想要" in reason:
        return False, "reason 不是政策口径（应引用窗口天数）"
    return True, "通过"


if __name__ == "__main__":
    for label, a in [("问题产物", BAD), ("可用产物", {"order_id": "A1002", "days": 30,
                                                     "reason": "超过窗口"})]:
        ok, why = rule_review(a)
        print(f"{label}: {'通过' if ok else '驳回'}  {why}")
```

输出：

```
问题产物: 驳回  reason 不是政策口径（应引用窗口天数）
可用产物: 通过  通过
```

`reflect.py` 把三套裁判并排跑，输出：

```
=== 同一产物，三种裁判 ===
  自评       通过  看起来合理，字段齐全。
  规则裁判     驳回  reason 不是政策口径（应引用窗口天数）
  测试裁判     驳回  A1001 期望 days=30
```

自评放行了一个有问题的产物。它不是"判断错了"，是**没有可用的判断依据**：

```
=== 自评为什么会放行 ===
  产物字段： ['order_id', 'days', 'reason']
  自评能看到的：产物本身
  自评看不到的：政策窗口、订单真实天数、测试期望
  -> 它没有可用于否证的依据，只能凭'像不像'判断
```

### 1.1 为什么自评必然如此

一次自评调用拿到的输入，如果只有"产物本身"，那它和生成这一次调用看到的东西几乎一样。它在同样的信息上做第二次推理，能得到两种结果：

| 情况 | 后果 |
|---|---|
| 第二次推理得出同样的结论 | 白花一次调用，什么也没发现 |
| 第二次推理得出不同的结论 | 它不知道该信哪一个，通常信第二次 |

第二种更糟。**它换了一个答案，但没有增加任何依据。** 一个没有依据的判断，第二次和第一次同样不可靠。

这就是"自己评自己没用"的准确含义：不是模型的反思能力不行，是**反思缺少一个外部参照**。第 2 章讲过的三种依据强度在这里同样成立：自评处于"弱依据"——它只有产物，没有产生产物的那些事实。

### 1.2 让它"自我批评"有没有用

提示词里常见的写法是："请仔细检查你的回答，找出其中的错误。"这个写法在某些情况下确实能让输出变好，但它起作用的方式不是"发现了错误"，而是**改变了生成分布**——"检查一下"这句话让模型更倾向于保守、更倾向于重述、更倾向于补全。

| 现象 | 真实原因 |
|---|---|
| 加了自我批评之后准确率略升 | 措辞变化让输出更保守 |
| 偶尔能纠正明显错误 | 明显的错误在生成时就留下了内部矛盾 |
| 错误更隐蔽时完全无效 | 没有依据，看不出来 |

第三行是决定性的。**一个系统如果在明显错误上都表现良好，会让你误判它在隐蔽错误上也有效。** 而真正需要裁判的，恰恰是隐蔽错误。

### 1.3 自评还有第三种失效：它改了不该改的

除了"放行错误"，自评还有一种更隐蔽的失效：**它把一个本来正确的产物改错了。**

它的输入是产物本身，而产物里往往包含一些看起来可疑但其实正确的字段。例如 `days: 3` 与 `reason: "未拆封，3 天内"`——自评读到"3 天"，又看到政策写着"7 天"，可能觉得该写"7 天内可退"，于是改写了一段本来准确的表述。

| 失效 | 表现 | 危害 |
|---|---|---|
| 放行错误 | 有问题却说没问题 | 错误流到用户 |
| 改坏正确 | 没问题却说有问题，并改写 | 制造新错误 |
| 反复震荡 | 两次改写来回变 | 成本上升，最终结果不确定 |

第三行在多轮自评里最常见：第一轮"补充一下"，第二轮"精简一下"，第三轮又"补充"。每一轮看起来都在改进，合起来没有结论。**这就是为什么自评不该放在循环里反复执行**——它不是收敛的。

### 1.4 一次自评的实际开销

自评不只是"可能没用"，它还有确定的价格。把它加进循环，每次都要付：

| 项 | 内容 |
|---|---|
| 一次模型调用 | 输入是产物 + 检查指令 |
| 一段上下文 | 检查指令与产物都要进输入，在多步任务里还要带历史 |
| 一段延迟 | 串行执行时，它直接加在总时长上 |

第二项在多步任务里会放大：一个 10 步的任务，如果每步后都自评，历史里就多了 10 段"检查过"的记录，而它们对后续推理没有帮助。

第三项常被忽略。一次自评如果 2 秒，十步就是 20 秒的纯等待，用户感知到的是"慢"，而不是"稳"。

**这些成本换来的东西，在 1.1 已经说明是零依据。** 所以"要不要自评"不是一个权衡题——在缺少外部依据时，它既是无效的，也是有代价的。

真正值得权衡的是"用哪种外部裁判"（第二节），因为那三种都有确定的成本与确定的收益。

### 1.5 一个能说明问题的实验设计

要自己验证 1.1 的结论，不需要特殊工具，只要三步：

| 步 | 做法 | 看什么 |
|---|---|---|
| 1 | 收集 20 份有已知对错的产物 | 其中一半是有问题的 |
| 2 | 让模型自评这 20 份，记录通过与否 | 它拦下了几份有问题的 |
| 3 | 换成规则裁判，同样 20 份 | 对比两者的拦截数 |

关键在第一步：**样本里必须有确定是错的那些。** 如果随机抽样，可能一份错的都没有，两个裁判都是全过，结论就没有信息。

第二、三步的对比还要看一个数：**误杀数。** 一个把 20 份全驳回的裁判，拦截率 100%，但没有任何用。这就是第 4 章 3.1 与第 27 章要讲的"两个数必须一起报"——拦截率与误杀率。

这个实验的成本很低（20 份多跑两轮），而它能提前暴露一个很贵的问题：**如果自评的拦截率接近 0，那么基于自评搭起来的反思循环，收益就是 0。** 上线之前跑一次，比上线之后看通过率才知道要好。

### 1.6 一句话记住这一节

自评能拿到的输入，与生成时几乎相同；因此它能发现的错，只能是"生成过程自己暴露出来的矛盾"，而不能是"与外部事实不符"。

这条判断有一个直接用法：**写自评提示词之前，先问"我给它加了什么它原来没有的信息"。** 答不出来，这个自评就不会有用。

## 二、外部裁判的三种来源

"外部"的意思是：**判定依据来自产物之外。** 三种来源的可靠性、成本、覆盖面各不相同。

| 来源 | 依据从哪来 | 能发现什么 | 成本 |
|---|---|---|---|
| 规则 | 业务代码里的判据 | 违反硬性约束的 | 极低，确定 |
| 测试 | 已知答案的用例集 | 与预期不符的 | 中，需要维护用例 |
| 模型（另一个） | 另一份提示词 + 完整上下文 | 语义层面的问题 | 高，且不确定 |

三者不是替代关系，是覆盖不同层次。一个成熟系统的顺序是：规则先过（最便宜），再过测试（能定位），最后才用模型裁判（覆盖面广但不可靠）。

### 2.1 规则裁判

规则裁判就是业务代码。它只做一件事：判断产物是否违反了一条可以写成表达式的规则。

```python
def consistent(days: int, reason: str) -> bool:
    """说"超过窗口"，days 就必须大于窗口；窗口固定 7 天。"""
    says_over = "超过" in reason
    return not (says_over and days <= 7)


if __name__ == "__main__":
    print(consistent(3, "超过 7 天窗口"), consistent(30, "超过 7 天窗口"))
```

这一行的价值在于**它是确定的**。同样的输入永远同样的判定，失败可复现，不需要跑模型。第 4 章讲结构化输出时说过：schema 管形状，业务代码管语义。这里是把"语义"那一半写成断言。

规则裁判能覆盖的，是那些"如果错了就是个 bug"的东西：

| 类型 | 例子 |
|---|---|
| 类型与取值域 | `days` 必须是 0–365 的整数 |
| 内部一致性 | 说"超过窗口"，`days` 就必须大于窗口 |
| 引用完整性 | 提到的订单号必须在本次查询结果里出现过 |
| 格式 | 金额必须是两位小数的字符串 |

第三行值得单独提：**"引用完整性"是最容易漏的一类。** 模型会把一个不存在于任何工具结果里的订单号写进答案，而这个订单号看起来完全正常。

### 2.2 测试裁判

测试裁判拿一批已知答案比对。它的前提是"有一个正确答案"，这在工作流式的任务里通常成立（退货判定、价格计算），在开放任务里不一定成立（写一段总结）。

```python
def test_review(artifact: dict, cases: list[dict]) -> tuple[bool, str]:
    """测试裁判：拿一批已知答案比对。"""
    for case in cases:
        if case["order_id"] != artifact.get("order_id"):
            continue
        if case["expect_days"] != artifact.get("days"):
            return False, f"{case['order_id']} 期望 days={case['expect_days']}"
    return True, "与已知答案一致"
```

它的覆盖面受用例集限制——没写进去的情况发现不了（第 4 章 3.1）。这一点没有解法，只能靠持续积累用例。

### 2.3 另一个模型当裁判

第三种是让另一个模型来评，通常配上不同于生成时的提示词，并且**给它生成时没有的信息**（例如原始工具返回、政策原文）。

它的价值和风险都很明确：

| 维度 | 情况 |
|---|---|
| 能发现 | 语义不一致、答非所问、措辞与政策不符 |
| 不能发现 | 需要外部事实才能判断的对错（它也没有那个事实） |
| 风险 | 它自己会错，且错得和生成模型相关 |
| 关键 | 必须给它"生成时没有的信息"，否则又变成自评 |

第四行是判断"这到底算不算外部裁判"的唯一标准。**给它同样的输入，它就是在做自评。** 给它不同的输入——工具原文、政策条款、测试期望——它才有资格叫裁判。

第 30 章会讲怎么衡量这个裁判可不可信（与人工判定的一致性），本章只需要记住它不能单独使用。

### 2.4 三方不一致时信谁

当规则、测试与模型裁判的结论不一致时，优先级是固定的：

| 冲突 | 信谁 | 理由 |
|---|---|---|
| 规则 vs 测试 | 规则 | 规则是硬约束，测试用例可能过时 |
| 规则 vs 模型裁判 | 规则 | 规则确定，裁判不确定 |
| 测试 vs 模型裁判 | 测试（若用例可信） | 测试有已知答案 |

**规则永远优先。** 它是唯一一个"判定即事实"的裁判——一条规则说 `days` 必须是整数，产物里是字符串，那它就是错的，没有讨论空间。

这条优先级还有一个实用后果：**规则的误报要先修规则，不要先改产物。** 如果一条规则经常拦下正确的产物，说明规则写错了，而不是模型总在犯错。

### 2.5 裁判的输入怎么组织

同样是"给裁判更多信息"，给的方式差别很大：

| 给法 | 例子 | 效果 |
|---|---|---|
| 把依据塞进同一段话 | "政策是 7 天，答案是 30 天，请判断" | 差：裁判只能复核这一条 |
| 分成"事实 / 产物 / 判据"三段 | 见下 | 好：每条判据可单独核对 |
| 让裁判自己去找依据 | "请核实这个答案" | 差：它没有检索能力 |

第二段的写法值得照抄：

```text
# 事实（来自工具，不可修改）
order.signed_days_ago = 3
policy.window_days = 7

# 待评产物
{"order_id": "A1001", "days": 30, "reason": "超过退货窗口"}

# 判据
1. days 必须等于 order.signed_days_ago
2. days <= policy.window_days 时，reason 不得写"超过"
3. 只依据上面的事实判断，不引用外部知识

# 输出格式
只输出一个 JSON：{"pass": true|false, "violated": [判据编号], "why": "不超过 30 字"}
```

三个设计点：**事实段标明不可修改**（否则裁判可能"修正"事实来迁就产物）；**判据编号**（输出里能指出违反了哪一条，便于定位）；**输出结构化**（第 4 章的做法，让程序能直接读）。

第一点尤其重要。裁判拿到事实和产物之后，模型完全可能反过来把事实改掉以保持一致——这在"产物看起来更权威"时更容易发生。

### 2.6 裁判不能凭空创造依据

三种裁判有一个共同前提：**判据必须来自产物之外，且必须是机器或裁判能读到的东西。**

这一条排除了两种常见做法：

| 做法 | 问题 |
|---|---|
| "请检查答案是否符合公司政策" | 政策没给它，它只能猜政策 |
| "请确认这个数据是准确的" | 它没有数据源，只能确认格式 |

两者的共同点是**要求裁判做它做不到的事**。它们看起来像检查，实际是让模型再生成一次判断——又回到了自评。

正确的写法是把判据本身变成输入："政策原文如下（附），请判断答案是否与第 3 条一致。" 这句话里有两处关键：**原文在输入里**，**比对的是具体条款**而不是"符合政策"这个整体印象。

第二处尤其重要。要求判断"是否符合"给不出可执行的依据；要求判断"是否符合第 3 条"给出了一条可以逐字比对的判据。**判据越具体，裁判越接近规则，也就越可靠。**

由此可以给三种裁判排一条演进路线：**凡是能写成"第 N 条"的判据，都应该从模型裁判移到规则裁判。** 模型裁判只保留那些"说不清具体条款、但人能看出不对"的情形。

### 2.7 一个规则裁判的完整例子

把上面几条合起来，一个能直接用的规则裁判长这样：

```python
def check_against_facts(artifact: dict, facts: dict) -> list[str]:
    """对照事实检查产物，返回违规列表（空表示通过）。"""
    out: list[str] = []
    signed = facts.get("signed_days_ago")
    window = facts.get("window_days")

    if artifact.get("days") != signed:
        out.append(f"days={artifact.get('days')} 与事实 {signed} 不符")
    if isinstance(signed, int) and isinstance(window, int):
        over = signed > window
        says_over = "超过" in str(artifact.get("reason", ""))
        if over != says_over:
            out.append(f"超过窗口={over}，但 reason 说 {says_over}")
    for oid in facts.get("cited_orders", []):
        if oid not in str(artifact):
            out.append(f"事实里有 {oid}，产物没引用")
    return out


if __name__ == "__main__":
    facts = {"signed_days_ago": 3, "window_days": 7, "cited_orders": ["A1001"]}
    for name, art in [
        ("正确", {"order_id": "A1001", "days": 3, "reason": "3 天内，可退"}),
        ("天数抄错", {"order_id": "A1001", "days": 30, "reason": "超过窗口"}),
        ("漏引订单", {"days": 3, "reason": "可退"}),
    ]:
        problems = check_against_facts(art, facts)
        print(f"{name}: {problems or '通过'}")
```

输出：

```
正确: 通过
天数抄错: ['days=30 与事实 3 不符', '超过窗口=False，但 reason 说 True']
漏引订单: ['事实里有 A1001，产物没引用']
```

第二行的两条违规是同一次错误产生的两个症状——"天数抄错"导致"结论说反"。**这正是规则裁判比模型裁判有用的地方：它能把一次错误拆成两个可定位的断言，而不是一句"答案不对"。**

第三行的"漏引订单"是引用完整性检查（2.1 的第三类）。它和内容对不对无关，只关心"有没有引用应该引用的东西"，正因为简单，才不容易漏。

### 2.8 裁判读什么，决定了它能拦什么

把三种裁判按"能看到什么"排一下，覆盖关系就清楚了：

| 裁判 | 能看到 | 看不到 | 因此能拦 |
|---|---|---|---|
| 规则 | 产物 + 事实 + 判据代码 | 语义、措辞是否得体 | 违反硬约束 |
| 测试 | 产物 + 已知答案 | 没写进用例的情况 | 与预期不符 |
| 模型 | 产物 + 事实 + 判据描述 | 事实是否正确（它也只能信输入） | 语义不一致 |

第三行的"看不到"值得强调：**模型裁判无法验证事实本身的真假。** 如果工具返回了一个错的订单天数，规则、测试、模型裁判全部会通过——因为三者都以那个错的事实为依据。

这意味着裁判体系的最外层还有一个必须存在的东西：**工具的正确性检验**。它不在本章范围内，但它解释了一件事——裁判再全，也只是"产物与事实一致"，不是"产物与现实一致"。

### 2.9 裁判给出的"证据"要多具体

一份驳回报告的质量，取决于它能不能让人直接动手改。三种详细程度：

| 详细程度 | 报告内容 | 拿到之后要做什么 |
|---|---|---|
| 只有结论 | "答案不符合政策" | 自己去比对，等于重做一遍 |
| 指出位置 | "reason 与政策第 3 条不符" | 找到第 3 条，对照改 |
| 给出事实与期望 | "事实 signed_days_ago=3，产物 days=30" | 直接改 |

第三行是可以直接变成 patch 的形态（3.4 的第一种）。**能给出"期望值"的裁判，等于把修复也一并做了。**

规则裁判天然能给到第三层，因为它手里就有事实。模型裁判通常只能到第二层，因为它只有判据描述。这也是"能写成规则的就别用模型裁判"的另一个理由：**不只是更准，还更可修。**

### 2.10 判据的三种强度

不同的判据能给出的结论强度不同，这决定了它能不能作为"拦截"：

| 强度 | 判据 | 能给出 |
|---|---|---|
| 硬 | 类型、范围、字段一致 | 一定错 |
| 软 | 措辞与政策口径一致 | 大概率错 |
| 提示 | "读起来别扭" | 无法给出结论 |

第三行不能当判据，它只能当"要不要触发一次模型裁判"的依据。把它写成规则，会得到一堆误杀。

第一行与第二行的分工：硬判据直接驳回，软判据驳回之后要允许人工复核。这对应第 23 章的分级处理。

## 三、三种修复粒度

裁判只回答"对不对"。发现不对之后修到什么程度，是另一个决定。

`reflect.py` 的三个场景对应三种粒度：

```
=== 三种修复粒度 ===
  场景 A：规则裁判说 reason 口径不对 -> patch 后： {'order_id': 'A1001', 'days': 3, 'reason': '超过 7 天窗口'}
  场景 B：测试裁判说 days 错 -> retry：原样重跑一次
  场景 C：产物方向错（days=30 但订单只签收 3 天）-> replan_all：丢掉当前的中间结果，回到第 1 步重来
```

| 粒度 | 什么时候用 | 代价 | 风险 |
|---|---|---|---|
| patch | 错在一个字段，依据齐全 | 一次小调用 | 改错字段 |
| retry | 错得莫名其妙，看不出原因 | 一次完整重跑 | 可能重跑出同样的错 |
| replan_all | 方向错了，中间结果不可用 | 全部重来 | 最贵 |

### 3.1 怎么判断该用哪一种

判断依据是三件事：**错在哪一层、依据还在不在、重跑会不会不同。**

```python
def choose_repair(finding: dict) -> str:
    """根据裁判的发现选择修复粒度。"""
    if finding.get("scope") == "direction":
        return "replan_all"        # 方向错，中间结果全不成立
    if finding.get("patchable") and not finding.get("needs_new_data"):
        return "patch"             # 只差一个字段，依据齐备
    if finding.get("transient"):
        return "retry"             # 偶发（超时、空返回）
    return "replan_all"            # 兜底：不知道就别硬修


if __name__ == "__main__":
    cases = [
        {"scope": "field", "patchable": True, "needs_new_data": False},
        {"scope": "field", "patchable": False, "needs_new_data": True},
        {"scope": "direction"},
        {"scope": "unknown", "patchable": False, "transient": True},
    ]
    for c in cases:
        print(f"  {c} -> {choose_repair(c)}")
```

输出：

```
  {'scope': 'field', 'patchable': True, 'needs_new_data': False} -> patch
  {'scope': 'field', 'patchable': False, 'needs_new_data': True} -> replan_all
  {'scope': 'unknown', 'patchable': False, 'transient': True} -> retry
  {'scope': 'direction'} -> replan_all
```

第二行是容易被误判的：**字段错了，但修它需要新数据。** 这种情况下 patch 做不到——手里没有正确的值，只能回去取。它看起来像"改一个字段"，实际是"重跑一段"。

第四行的兜底很重要。**不知道原因时的默认动作应该是最保守的那个**，而不是最便宜的那个。选 retry 会在原因不明时反复重跑，把一次错误变成 N 次成本。

### 3.2 retry 的真实代价

retry 看起来最便宜，其实有一个隐藏成本：**它不保证结果不同。**

第 2 章讲过模型输出不稳定。一个因为"偶发超时"失败的调用，重跑大概率成功；一个因为"提示词本身有歧义"失败的调用，重跑会得到同样的错。后者是最坏的情况：你花了钱，得到同样的结果，而且不知道问题在哪。

判断方法很直接：**如果第一次失败的原因是确定的（输入有问题、规则不满足），retry 没用。** 只有原因是随机的（网络、限流、空返回），retry 才有意义。

### 3.3 replan_all 的边界

重规划最贵，也最容易被滥用。常见的滥用是"一发现不对就重来"，结果是任务反复从第一步开始，前面的成功全被丢掉。

合理的 replan_all 应该带一个条件：**重来之后的可用信息比第一次多。** 如果第一次是因为"没查到政策"，重来时还是查同样的地方，那重来只是重复。

| 重来前的状态 | 值得吗 |
|---|---|
| 换了更精确的查询、或换了数据源 | 值得 |
| 只是重跑一遍 | 不值得，多半同样失败 |
| 前面几步的结果仍然有效 | 不值得，应该 patch 或局部重跑 |

第三行提示了一个中间粒度：**不是全丢，是丢掉"方向错"之后的那几步。** 本章的代码没有实现这一层，它是第 11 章检查点的用途之一——存下每一步的快照，才能回到"出错之前那一步"。

### 3.4 patch 的两种形态

patch 不只是"改一个字段"，它有两种，代价差一个数量级：

| 形态 | 做法 | 代价 | 适用 |
|---|---|---|---|
| 直接改 | 用裁判给出的值替换 | 零模型调用 | 裁判已经知道正确值 |
| 定向重生成 | 只带出错的那一段 + 错误说明，重生成一次 | 一次小调用 | 裁判只知道"错了"，不知道"对的是什么" |

第一种最便宜，但要求裁判能给出正确值。规则裁判通常可以（"days 应该是 3，因为事实里写着 3"）；模型裁判通常不能（它只说"reason 与政策不符"）。

第二种是第 4 章"自愈重试"在答案层面的用法：**把错误说明和相关的局部上下文一起回灌，让模型只重写那一段。** 关键在于"只带出错的那一段"——带上全部历史会让它重新推理整件事，等于 retry。

第二种的失败模式是"改了还是错"。这时不该再 patch，因为同一段上下文已经失败过两次。判断条件是：**同一处 patch 超过两次就升级粒度。**

### 3.5 修复之后要再判一次

修复的闭环是"判 → 修 → 再判"。少了最后一环，修复就等于盲改。

| 情况 | 再判结果 | 处理 |
|---|---|---|
| 通过 | 正常交付 | 无 |
| 同样的问题仍在 | 修复无效 | 升级粒度 |
| 出现新问题 | 修出了新错 | 回滚到修复前，换粒度 |

第三行是最容易被忽略的：**一次 patch 可能修好一个字段、弄坏另一个。** 第 4 章讲提示词回归时说过"总数上升可以掩盖个别回归"，这里是同一件事在单次修复上的表现——所以再判要用与初判同一套判据，而不是只看"被指出的那一条是否通过"。

还有一条硬规则：**同一产物最多修两次。** 两次之后无论结果如何都停，把产物和两次修复记录一起交出来。允许无限次修复的循环，会变成一个"自评 + 改写"的无限循环（1.3 的第三种失效）。

### 3.6 重规划怎么不丢已有的成果

replan_all 的"全"是相对的。真正的重规划应该保留两类东西：

| 保留什么 | 为什么 | 怎么留 |
|---|---|---|
| 已经确认的事实 | 重新查一遍是浪费 | 事实与产物分开存 |
| 已经失败的尝试 | 避免重走同一条路 | 把失败原因写进新一轮的上下文 |

第一行是本节的要点。**产物是"结论"，事实是"材料"。** 重规划该丢的是结论，不该丢材料——材料是花钱查来的，而且大概率仍然有效。

第二行常被忽略。一个因为"查了 A 接口没拿到数据"而重规划的循环，如果不告诉它"A 接口查过了、是空的"，它会再查一次 A。这不是智能问题，是**重规划时上下文没有带上"试过什么"**。

这就是第 10 章要讲的状态：

| 存哪 | 放什么 | 谁维护 |
|---|---|---|
| messages | 对话过程 | 循环自动追加 |
| state.facts | 已确认的事实 | 工具结果写入 |
| state.attempts | 已试过的路径与结果 | 每步写入 |

三者的生命周期不同：messages 会被裁剪（第 7 章），facts 不该裁，attempts 只需要保留摘要。**把它们混在 messages 里，就等于让第 7 章的裁剪逻辑决定哪些事实还能用。**


### 3.7 三种粒度的成本对照

把三种修复放在同一个任务上，成本差得很清楚：

| 粒度 | 额外模型调用 | 额外工具调用 | 可能浪费的 |
|---|---|---|---|
| patch（直接改） | 0 | 0 | 无 |
| patch（定向重生成） | 1 次小调用 | 0 | 一次错误的改写 |
| retry | 1 次完整调用 | 0 | 之前的全部步数 |
| replan_all | 1 次计划 + N 次执行 | 重查全部数据 | 之前的全部步数与 token |

第四行的"重查全部数据"容易被忽略：重规划之后，那些已经查过的接口会再查一次。有幂等设计的系统不会出错，但会付两倍的钱；没有幂等设计的系统会出错。

由此得出选粒度的顺序：**先看能不能直接改（0 成本），再看能不能定位到一小段（1 次小调用），再看是不是偶发（retry），最后才重来。** 这个顺序与 3.1 的代码一致，区别只在于这里把它换算成了钱。

### 3.8 一条完整的修复流程

把三节的判断串起来，一个可用的修复流程是：

```python
def repair(artifact: dict, judges: list, facts: dict, budget: int = 2):
    """判 → 修 → 再判。最多修 budget 次，超过就带着证据交出来。"""
    history: list[str] = []
    for attempt in range(budget + 1):
        problems = []
        for judge in judges:
            problems.extend(judge(artifact, facts))
        if not problems:
            return artifact, history, "通过"
        history.append(f"第 {attempt + 1} 次判定：{problems}")
        if attempt == budget:
            break
        artifact = apply_patch(artifact, problems, facts)
    return artifact, history, "驳回"


def apply_patch(artifact: dict, problems: list[str], facts: dict) -> dict:
    """只改能被事实直接确定的字段，其余留给人工。"""
    out = dict(artifact)
    if any("days" in p for p in problems) and "signed_days_ago" in facts:
        out["days"] = facts["signed_days_ago"]
    return out


if __name__ == "__main__":
    from reflect import BAD, rule_review

    def judge(a, _facts):
        ok, why = rule_review(a)
        return [] if ok else [why]

    art, hist, status = repair(BAD, [judge], {"signed_days_ago": 3})
    print(status, art)
    for h in hist:
        print(" ", h)
```

输出：

```
驳回 {'order_id': 'A1001', 'days': 3, 'reason': '签收不想要'}
  第 1 次判定：['reason 不是政策口径（应引用窗口天数）']
  第 2 次判定：['reason 不是政策口径（应引用窗口天数）']
  第 3 次判定：['reason 不是政策口径（应引用窗口天数）']
```

这个结果说明了一件重要的事：**只有能直接映射到事实的违规才适合自动 patch。** `reason` 的措辞改法没有唯一答案，`apply_patch` 无从下手，于是两次修复都无效——流程正确地停下来交给了人工，而不是无限重试。

流程的三个要点：**每次都重跑全部判据**（3.5）、**失败记录留在 `history` 里**（5.3）、**次数用完就停**（8 的第三条）。

### 3.9 修复要不要留痕

patch 之后要不要记录"改了什么"，取决于这件事以后会不会被问起：

| 场景 | 留痕价值 |
|---|---|
| 只影响本次交付 | 低 |
| 会进入评测集 | 高：一次修复就是一条样本 |
| 涉及对外承诺（金额、时效） | 必须：需要审计 |

第三行不是技术选择，是合规要求。**一个改变了金额的 patch，必须能回答"改之前是什么、依据是什么、谁批准的"。** 这在第 20–23 章的护栏与审批里会展开。

第二行的价值容易被低估：每一次自动修复，都是一条"模型出这类错、规则能拦住"的证据。把它记下来，评测集的增长速度会快很多，而不是等人工去构造。

## 四、反思与评测的区别

这一章讲的是"判断这一次的结果对不对"。它和评测（第 27–31 章）看着像同一件事，其实不同：

| | 反思 | 评测 |
|---|---|---|
| 对象 | 这一次运行的产物 | 一批运行的统计 |
| 目的 | 决定要不要修 | 决定改动有没有效 |
| 结论 | 通过 / 驳回 | 通过率与置信区间 |
| 失败 | 修，或者交给人 | 记录，用于比较 |
| 成本 | 每次运行都要花 | 离线跑，可分批 |

两者共用同一套判据，但**不能互相替代**。反思的判据只要覆盖面够用来做单次判断；评测的判据必须稳定、可复现，否则两次比较之间会因为判据本身变化而失真。

一个实用推论：**反思用的规则裁判，可以直接拿来当评测的判据。** 这样"线上拦截的东西"和"离线打分的东西"是同一套，不会出现"离线 98% 通过、线上频繁驳回"的割裂。

### 4.1 为什么两者必须分开建

两者共用判据，但**运行方式完全不同**，混在一起会互相拖累：

| 维度 | 反思 | 评测 |
|---|---|---|
| 触发 | 每次运行 | 改动前后、定期 |
| 延迟预算 | 几百毫秒 | 分钟到小时 |
| 判据变更 | 随时可加（4 的第四条） | 变更需重跑基线 |
| 失败处理 | 阻断交付 | 只记录 |

第二行决定了反思不能用重的东西：一个要跑十秒的裁判放进每步，任务就会被拖慢一个数量级。所以**反思适合规则裁判**（毫秒级），**评测适合规则 + 测试的批量跑**（分钟级）。模型裁判两边都能用，但只适合抽样。

第三行是最容易出问题的一条：评测用的判据一旦改动，历史结果就不再可比（第 29 章会讲怎么处理）。而反思的判据本来就该持续演进。**同一个判据，在两种场景下的"可变性"要求是相反的。**

一个可操作的约定：**判据分为"稳定集"和"演进集"。** 稳定集两边都用、改动需评审；演进集只用于反思，随时可加。这样评测的可比性有了保障，反思也能持续变强。

## 五、反思放在循环的哪一步

反思不是一个步骤，是一个"在继续之前再确认一次"的动作。它的位置决定了它能看到什么：

| 位置 | 检查对象 | 能发现 |
|---|---|---|
| 每次工具调用后 | 单个工具结果 | 工具报错、返回明显不合理 |
| 每步回答后 | 当前答案 | 与已有信息矛盾 |
| 循环结束前 | 最终答案 | 整体不一致 |

第一行最便宜，收益也最确定：工具返回了 `{"error": ...}` 却继续往下走，是第 5 章讲的失败模式的直接后果，在这里拦一次就够了。

第三行最贵，也最值得：**最终答案要交给人，它是唯一必须正确的产物。** 一个在中间步骤放过了错误、但在最后拦住它的系统，比一个每个中间点都检查却漏掉最后的系统更可用。

```
一次典型的组合：
  每步   规则裁判（快，拦明显错误）
  循环末 规则 + 测试裁判（拦业务错误）
  交付前 模型裁判（拦语义问题，可选）
```

### 5.1 反思与第 7 章守卫的区别

守卫判断"要不要继续"，反思判断"结果对不对"。两者容易混：

| | 看什么 | 结论 | 停下之后 |
|---|---|---|---|
| 守卫 | 过程（指纹、token、空步） | 继续 / 停 | 任务未完成 |
| 反思 | 产物（内容、格式、一致性） | 通过 / 驳回 | 任务做错了 |

一个常见的错误是把反思写进守卫里。两者触发后的处理完全不同：守卫停下意味着"没走完"，反思驳回意味着"走完了但答案错"，前者要交付部分结果，后者要重做。

### 5.2 每步裁判的成本模型

"每一步都检查"听起来更安全，实际成本是：

| 位置 | 每次任务的裁判次数 | 相当于 |
|---|---|---|
| 每步 | 等于步数 | 调用次数翻倍 |
| 只在末步 | 1 | 增加 1 次 |
| 只在有副作用的步 | 取决于工具 | 可控 |

第一行的账容易被算错：它不只是多一倍调用，还因为裁判本身也带上下文（2.5 的三段结构），单次成本比工具调用高。

第二行的风险是"到最才发现错"。折中在第三行：**只对不可回滚的步骤做每步裁判。** 查日志错了可以再查，发短信错了撤不回——两者的检查必要性完全不同。这与第 5 章 5.1 的读写分类是同一条原则。

### 5.3 交给人之前该做什么

裁判驳回、修复两次仍未通过时，产物要交给人。交之前有三件事要整理好：

| 事 | 为什么 |
|---|---|
| 列出所有违规 | 人不想自己再找一遍 |
| 附上事实原文 | 人需要核对依据 |
| 附上两次修复记录 | 人需要知道已经试过什么 |

第二项最重要。一份"答案不对"的报告，人拿到之后第一步是去找依据；把依据一并附上，这一步就省了。第三项能避免人重复已经失败的尝试。

这与第 5 章 5.3（工具清单的承诺）、第 7 章 6.4（上限截断的残局）是同一条设计原则：**交接时必须把判断所需的信息一并交出，而不是只交出结论。**


### 5.4 反思失败之后循环算什么状态

反思驳回之后，任务处于一个没有名字的状态。它不在第 6 章的三态里：不是"答完"（答案没通过），不是"超步"（步数够），也不是"空转"（调用没重复）。

| 状态 | 触发 | 调用方该做什么 |
|---|---|---|
| 答完 | `finish_reason == stop` | 交付 |
| 超步 / 空转 | 守卫 | 告知未完成 |
| **驳回** | 反思两次未通过 | 交付带问题的产物 + 违规清单 |

第四行是本章新增的。它的处理方式与超步、空转都不同：**产物是完整的，只是不可信。** 这时的正确做法不是"报告失败"，而是"带着证据交出去"——4.3 讲的三件事就是为此。

给这个状态一个名字有实际好处：它让"答案错了"和"没答出来"在监控上分开。前者是质量问题，后者是能力问题，两条曲线该分别看。

### 5.5 反思放在子任务里还是整体外

多步任务有一个结构选择：**每步之后检查，还是整个任务之后再检查？** 它决定错误会不会被带进后续步骤。

| 放法 | 错误传播 | 成本 |
|---|---|---|
| 每步之后 | 被拦住，不进入下一步 | 高（步数倍） |
| 整体之后 | 会传染，最后一起发现 | 低（1 次） |
| 关键步之后 | 只在该拦的地方拦 | 中 |

第二行的问题在于**错误会被后续步骤引用**。一个错的订单天数，会被下一步的比对拿去用，再被再下一步的结论引用。到最后一起检查时，你只能看到"结论错了"，看不到"天数是错的"。

第一行的代价在 5.2 算过。折中在第三行，判据是：**这一步的输出会不会被别的步骤当成事实引用。** 会，就在这一步之后检查；只是自己的中间量，就放到最后。

### 5.6 反思结果要不要回灌给模型

发现错误之后，有两种处理：直接改（patch），或者把错误告诉模型让它自己改。

| 方式 | 谁改 | 上下文里留下什么 |
|---|---|---|
| 直接改 | 代码 | 什么都没留（干净） |
| 回灌 | 模型 | 一段"上次错了，因为……"的记录 |

第二种的好处是模型下一次可能不再犯同类错；坏处是那段记录会一直留在历史里，占上下文，还可能被后续步骤误当成事实。

判断标准与第 7 章 3.4 一致：**这条记录对后续步骤有没有用。** 如果它只影响当前这一处，直接改更省；如果它影响后续多个判断（例如"不要再用 aggregate 接口，它返回的是日粒度"），回灌更值。

第三种做法是回灌但不进 messages——写进系统消息或状态字段（第 10 章）。这样它一直生效，又不占历史。

### 5.7 一次驳回要留下什么

驳回不是终点，是下一轮迭代的输入。一份可用的驳回记录至少四项：

| 项 | 例子 | 用途 |
|---|---|---|
| 违规判据 | "days 与事实不符" | 定位到具体规则 |
| 事实与产物的差 | 事实 3，产物 30 | 直接可修 |
| 尝试过的修复 | "patch reason 无效" | 避免重复 |
| 最终的修复粒度建议 | "需要重新取数" | 给人工的下一步 |

第四项最难自动化，也最有价值。**它把"这次失败了"变成"下次该怎么做"。** 一个只有前三项的记录，人工拿到要自己想方案；有第四项的记录，人工只需要确认。

这一项可以由规则推导：如果违规里含"与事实不符"，且事实字段缺失，就是"需要重新取数"；如果违规全是措辞类，就是"需要人工润色"。推导表不需要很全，覆盖最常见的几类就有明显收益。

### 5.8 反思失败算不算事故

不是每一次驳回都值得复盘。区分方法是看**这一类错误有没有可能重复发生**：

| 情况 | 处理 |
|---|---|
| 单次数据异常（订单不存在） | 记录，不复盘 |
| 判据漏了一种情况 | 补判据，值得复盘 |
| 产物系统性错误（口径整体偏） | 补判据 + 补用例，必须复盘 |

第二行和第三行的区别在于"漏的是个例还是模式"。一个只漏了一笔订单的裁判，加一条用例就够；一个把所有"定制商品"都判错的裁判，说明判据里根本没有这一类。

判断方法很直接：**把这次驳回的产物，按同一判据批量回扫历史数据。** 如果只有这一例失败，是个例；如果一批都失败，是模式。回扫的成本远低于重新跑一批任务，因为它只需要读历史产物。

## 六、三个裁判同时跑的样子

`judges.py` 拿四份产物同时问三个裁判，结果值得逐行看：

```
订单      自评      规则      测试
A1001   通过      驳回      通过
A1002   通过      通过      通过
A1003   通过      驳回      通过
A1004   通过      驳回      驳回

通过数：自评 4/4   规则 1/4   测试 3/4
自评与规则的判定不一致处： ['A1001', 'A1003', 'A1004']
```

四行各有不同的含义：

| 订单 | 情况 | 谁对 |
|---|---|---|
| A1001 | reason 不是政策口径，但 days 对 | 规则对 |
| A1002 | 完全正确 | 三家一致 |
| A1003 | 天数与结论矛盾 | 规则对 |
| A1004 | days 是字符串 | 规则与测试都对 |

**自评在四行上全过，规则拦下三行。** 两者的不一致率是 3/4，而自评在这些不一致处全部判错。

第三行 A1003 是"内部矛盾"类的典型：`days=5` 却说"超过 7 天窗口"。产物本身没有任何语法问题，字段都在，格式都对——只有把它和事实放在一起看，矛盾才出现。这正是自评做不到的（1.1）。

第四行 A1004 展示了两类裁判的分工：规则说"days 不是整数"（格式），测试说"期望 3"（内容）。**两者都拦住了，但理由不同。** 只有规则的话，你知道"格式错了"；只有测试的话，你只知道"答案不对"。两个一起跑，定位才快。

### 6.2 裁判的判据从哪积累

裁判不是一次写全的。它的成长路径与第 4 章的用例集一样：

| 来源 | 得到什么判据 | 优先级 |
|---|---|---|
| 线上驳回 | 一条具体的违规 | 最高 |
| 人工复核 | 一条"看着不对但说不出"的 | 中 |
| 事故复盘 | 一条必须永久拦住的 | 最高 |
| 规则推导 | 字段间的一致性 | 低（可枚举） |

第二行最有意思：人工说"感觉不对"时，追问"哪一条不满足"往往能逼出一条判据。**问不出具体条款，说明这条判据还不存在**——那它就该被写出来。

第四行成本最低，收益也最确定：类型、范围、必填、字段间一致性，这四类几乎能自动生成。

## 七、这一层的失效模式

**第一，裁判本身会出错。** 规则写错会误杀正确产物；测试用例过时会拦住正确的改动；模型裁判会跟生成模型一起错。三者都要被度量——第 30 章讲怎么给裁判本身算准确率。

**第二，反射成本可能超过收益。** 每次工具调用后都跑一次裁判，等于把调用次数翻倍。判断标准是"这一步错了之后的下游代价"：一个查天气错了，代价小；一个扣款错了，代价大。

**第三，裁判通过的产物仍然可能是错的。** 规则只能表达能写成表达式的判据，测试只能覆盖用例集。**裁判通过的意思是"没有发现错误"，不是"正确"。** 这个区别在对外汇报时尤其重要。

**第四，自评与裁判混合使用会掩盖问题。** 常见写法是"先让模型自查，自查不通过再走裁判"。因为自评几乎总是通过（1.1），这条路等于把裁判跳过了。要么直接走裁判，要么把自评当成"改写"而不是"检查"。

**第五，修复粒度选错会放大成本。** 一次小错用了 replan_all，成本翻倍；一个方向错用了 retry，反复无效。判断依据是 3.1 那三条：错在哪层、依据还在不在、重跑会不会不同。

### 7.1 一个反例：看起来像裁判的自评

最常见的"伪裁判"长这样：

```text
你是质检员。请检查下面的回答是否准确、完整、符合要求。
如果发现问题，请指出并给出修改后的版本。
```

三个问题：**"准确"没有标准**（对照什么？）、**"符合要求"不知道指哪些要求**（要求在哪？）、**"发现问题就改"没有边界**（改坏了不算违约）。

把它的输入补上之后，同一个角色就变成了真裁判：

| 加什么 | 变成 |
|---|---|
| 事实原文（工具返回） | 能判断字段是否抄错 |
| 判据清单（编号） | 能指出违反了哪一条 |
| 输出格式（结构化） | 判定结果可被程序读 |

三行对应第 4 章六要素里的"背景""约束""输出格式"。**裁判本质上是一次带齐六要素的调用**，缺那三项时就退回到自评。

## 八、边界

**第一，反思不产生信息。** 它只判断已有信息够不够支撑产物。信息不够时，反思的结论只能是"不确定"，正确的动作是去取信息，不是让它多评几次。

**第二，裁判的覆盖永远小于全部错误。** 规则只覆盖能写成表达式的，测试只覆盖用例集里的，模型裁判只覆盖它能读懂的。三者的并集仍然漏，"通过"只等于"没发现问题"。

**第三，修复有次数上限。** 同一产物修两次仍不通过就该交出来（3.5）。无限修复会变成"自评 + 改写"的循环，既不收敛也不便宜。

**第四，裁判的判据要能演进。** 每次线上发现一个漏过去的错误，就该把它变成一条规则或一条用例。这不是额外工作，是裁判体系唯一的成长方式。

**第五，反思的成本要计入任务预算。** 每步都裁判的任务，实际成本接近原任务的两倍（5.2）。如果预算是按"不裁判"算出来的，加入裁判之后必然超。

**第六，事实本身的正确性不在裁判范围内。** 工具返回一个错的天数，三种裁判一致通过（2.8）。要发现这一类错误，只能靠工具侧的对账或抽样复核，不能靠裁判。

## 这一章建立的 5 件事

1. 自评无效的原因不是能力不足，是依据不足：它看到的信息和生成时几乎一样，没有可用来否证的东西。
2. 外部裁判的判据是"给它的信息是否多于生成时"。同样输入的"另一个模型"仍然是在自评。
3. 三种来源各有覆盖：规则拦硬约束（最便宜、最确定），测试拦已知答案，模型裁判拦语义问题（最贵、最不可靠）。冲突时规则优先。
4. 修复粒度看三件事：错在哪一层、依据还在不在、重跑会不会不同。原因不明时的默认动作应该最保守。
5. 反思与守卫是两件事：守卫判断"要不要继续"，反思判断"结果对不对"，两者的失败处理完全不同。
