## 一、先分开两件事

本章会出现两个容易混的词，先分开：

**编排（paradigm）** 决定"谁来说下一步做什么"。它有三档：代码说、模型每一步说、模型一次全说。

**执行（scheduling）** 决定"已知要做的事按什么顺序跑"。它也有三档：串行、并发、按依赖分层。

两者是正交的。一个固定工作流可以串行也可以并发，一个 P&E 计划也可以并发执行，ReAct 本身则天然串行（下一步依赖上一步的观察）。**本章把第一件放在前四节，第二件放在第五节，因为它们该分别决策。**

混在一起的后果很具体：想提速时把 ReAct 改成并发，但实际上 ReAct 的每一步都在等上一步的结果，并发无从下手；想省钱时把工作流改成 ReAct，结果每一步都在做本来不需要做的判断。

## 二、循环是最贵的默认选项

第 6、7 章的循环有一个隐含前提：**下一步做什么，只有走完这一步才知道。**

这个前提在任务真正需要探索时成立。但很多任务并不需要探索——"先查政策、再查订单、然后按规则比对"，这个顺序在写需求的时候就确定了，模型不需要在每一步重新发现它。

把一个已知顺序的任务交给 ReAct 循环，代价是每一步都要问一次模型，而每次问都带走全部历史：

```
固定工作流             步数=2  token≈230  产出字段=['docs', 'order']
ReAct                 步数=3  token≈84  产出字段=['docs', 'order']
Plan-and-Execute      步数=2  token≈250  产出字段=['search_docs', 'get_order']
```

（这是原理演示：`paradigms.py` 里模型调用是一个计数器，`token` 是字符数的粗略折算，不是实测。要看的是数量关系，不是绝对值。）

ReAct 的 token 反而比固定工作流少，因为本例的历史很短。**但步数多一步，而且这一步的代价随历史长度增长**——任务一旦有三五个观察结果，每一步都会带着它们重发。固定工作流则在执行阶段完全不花模型的钱。

### 2.1 三种范式的形状

| 范式 | 谁决定下一步 | 模型调用次数 | 适合什么 |
|---|---|---|---|
| 固定工作流 | 代码（写死） | 0 或固定几次 | 步骤已知、顺序确定的流程 |
| ReAct | 模型（每步一次） | 等于步数 | 需要探索、不知道要几步 |
| Plan-and-Execute | 模型（一次出全盘计划） | 计划 1 次 + 收尾 1 次 | 步骤可预先枚举、但要按结果调整 |

三者不是"先进与落后"的关系，是三种不同的信息分布：

**固定工作流**假设"做什么"在编码时就已知。它把判断从运行时挪到了开发时，代价是遇到没预料到的输入会失败。

**ReAct** 假设"做什么"必须在每一步看到中间结果后才能定。代价是每一步都花一次模型调用，历史还要全量重发。

**Plan-and-Execute** 假设"要做哪几件事"可以先想清楚，"每件事怎么做"可以按计划执行。代价是计划可能不准，执行到一半要重订。

### 2.2 判据：有几个必须看到结果才知道的步

三种范式的分界可以用一个问题切开：**这个任务里，有多少步的"下一步"必须先看到"上一步的结果"？**

| 依赖步数 | 建议 |
|---|---|
| 0 | 固定工作流 |
| 1–2 处 | Plan-and-Execute（计划里写清顺序，执行时按图走） |
| 大部分 | ReAct |

"0" 这一类最容易误判。它看起来像"简单任务"，其实是"顺序已知的任务"——复杂度可能很高（十个步骤、五个数据源），但只要顺序是确定的，就不需要每步问模型。

一个可以帮判断的例子：**退货判定**。查政策、查订单、比对天数——三步，顺序已知，依赖只有一处（比对需要前两步的结果）。这适合固定工作流。**故障排查**则相反：查完日志才知道该不该查指标，查完指标才知道该不该看部署记录，依赖链长且分支多，适合 ReAct。

### 2.3 一次范式选择的推演

拿到一个需求之后怎么选？这四步可以照着走：

**第一步，把流程写出来。** 不看代码，先用自然语言列出"要做哪几件事"。写不出来说明需求本身还不清楚，换范式也没用。

**第二步，标出哪一步依赖上一步的结果。** 依赖的意思是"这一步的输入里，包含上一步的输出"。不依赖的步骤之间可以任意换顺序。

**第三步，看依赖链的长度与分支。** 一条链、无分支，工作流就够；链上有分支（根据结果走不同路），要么在工作流里写 `if`，要么上 ReAct。

**第四步，估一下"未知"的比例。** 一个任务的步骤里，有多少比例是"现在写不出来，要跑了才知道"。比例越高，越该给模型决定权。

推演一个具体需求："用户问某订单能不能退，答完顺带告诉他预计退款到账时间。"

| 步 | 做什么 | 依赖 | 未知 |
|---|---|---|---|
| 1 | 取订单 | 无 | 无 |
| 2 | 取政策 | 无 | 无 |
| 3 | 比对天数与商品状态 | 1、2 | 无 |
| 4 | 取退款预计到账时间 | 3 判定为可退时 | 有：可退与否决定要不要查 |

四步，一处分支，一处未知。工作流写成"1、2 并发 → 3 → 可退则 4"完全可行，不需要 ReAct。**关键在于第 4 步的分支是"一个 `if` 能表达的"，不是"必须先看了结果才知道该做什么"。**

如果第 4 步的规则本身很复杂（比如"根据商品类目、支付方式、仓库位置综合决定"），那它就成了"未知"，此时给模型决定权更合适——但依然可以在工作流里调用一次模型，而不是退回 ReAct。

**这个推演的价值在于：多数"需要 agent"的需求，推完会发现只需要一个带一次模型调用的工作流。** 而工作流的成本、可测性、可预测性都优于循环。

### 2.4 混合形态才是常态

上面把三种范式当成三个选项，真实系统里最常见的是一条流水线：**入口路由 → 主体范式 → 出口渲染**。

| 段 | 通常用什么 | 理由 |
|---|---|---|
| 入口 | 规则 + 小模型路由 | 决定"这个问题值不值得走完整流程"（第 13 章） |
| 主体 | 工作流或 P&E | 大部分业务问题的步骤是已知的 |
| 局部 | ReAct | 只有那几处"必须先看结果"的地方 |
| 出口 | 一次模型调用 | 把结构化结果转成自然语言 |

这个形态的好处是**把不确定性限制在最小的范围内**：主体是确定的，只有局部需要探索。整条链的失败率是各段失败率的乘积，把大部分段变成确定性的，等于把它们那一段的失败率压到零。

代价是边界要多写一层：路由要判断"该走哪条"，局部 ReAct 要能交回结果继续往下走。这两处都比"一个循环跑到底"复杂。**判断标准是任务量：跑十次的东西，简单就好；跑十万次的东西，值得多写这两层边界。**

### 2.5 三种范式的失效不可互换

选范式时还要看一件事：**出问题之后能不能被定位。**

| 范式 | 失败长什么样 | 定位需要什么 |
|---|---|---|
| 工作流 | 某步异常，或走了错误分支 | 步骤日志 + 输入 |
| ReAct | 没答出来、空转、跑偏 | 完整轨迹（想法/动作/观察） |
| P&E | 计划不全、方向错、某步结果不符 | 计划原文 + 逐步结果 |

第二行需要的证据最多。ReAct 的失败往往不是"某个调用报错"，而是"一串正确的调用合起来跑偏了"——要定位它，必须看到每一步它当时"以为"在做什么（4.3 的想法字段）。

这也是一笔事前成本：**选 ReAct 之前就要决定轨迹记不记、记多细。** 事后再加日志，历史数据里没有，第一批问题只能靠猜。

## 三、固定工作流：把判断挪到开发时

固定工作流没有模型参与决策。它就是一串函数调用：

```python
def fixed_workflow(meter: Meter) -> dict:
    """固定工作流：顺序写死，不需要模型做任何选择。"""
    docs = search_docs("退货窗口")
    meter.call(200)
    order = get_order("A1001")
    meter.call(260)
    return {"docs": docs[0], "order": order}
```

`meter.call(...)` 在这里代表"这一步后面要接一次模型调用"，很多实现里它是零次的。如果整个流程是"取数 + 规则比对"，一次模型调用都不需要。

### 3.1 它在哪里失效

固定工作流的失效只有一个形态：**输入超出预设。**

| 输入情况 | 固定工作流的表现 | 该走哪条路 |
|---|---|---|
| 标准退货问题 | 正确 | 留在工作流 |
| 一次问三个订单 | 只处理了第一个 | 加分支，或者交给上游路由（第 13 章） |
| 问的是换货 | 按退货的流程答了 | 加意图判断，或路由到别的流程 |

第三种最危险，因为它不报错。**工作流的每一步都成功了，只是走的是另一条业务的流程。** 第 13 章的意图识别就是为这一步存在的：先判断"这是不是我的流程能处理的问题"，不能处理就转出去。

### 3.2 它仍然值得用的理由

固定工作流的三个好处是别的范式拿不到的：

| 好处 | 原因 |
|---|---|
| 可预测 | 步数与 token 是常数，成本可以精确预算 |
| 可单测 | 每一步是纯函数，能直接写断言 |
| 失败可定位 | 出错就是某一步出错，不需要看轨迹 |

第二条尤其重要。ReAct 的测试要跑真实模型，结果不稳定；固定工作流的测试是普通的单元测试。**当一件事用工作流能表达时，尽量不要用循环表达——省下的不只是 token，还有一整类不确定。**

### 3.3 工作流里的模型调用放在哪

固定工作流可以有模型调用，只是模型不做"选哪一步"的决定。它的位置通常在两类地方：

| 位置 | 作用 | 例子 |
|---|---|---|
| 入口 | 把自然语言转成结构化参数 | "我要退 A1001" → `{"order_id": "A1001"}` |
| 出口 | 把结构化结果转成自然语言 | `{"eligible": true}` → "可以退，3 天内寄回即可" |
| 中间 | 做一项规则写不出的判断 | 判断商品是否属于"定制类" |

第三种要谨慎。一旦工作流中间出现模型调用，它就带回了一部分不确定性：这一步的输出可能变化，下游的所有步骤都跟着不确定。**判断标准是：这一步的结果能不能被校验。** 能（比如输出必须是一个枚举值），放进工作流是安全的；不能（比如输出一段自由文本，下游直接引用），就该考虑是不是该换范式了。

入口与出口两处的模型调用最值得用，因为它们都在流程的边界上：**边界上的不确定性不会传染到流程内部。** 入口转错参数会立刻在第一步失败，出口措辞不好不影响判定结果。

### 3.4 固定工作流的测试

工作流最大的好处在测试上。它的每一步是纯函数，断言可以直接写在步骤之间：

| 测试层次 | 断言什么 | 需要模型吗 |
|---|---|---|
| 单步 | 输入 X 输出 Y | 不需要 |
| 串联 | 前一步输出能作为后一步输入 | 不需要 |
| 分支 | 每条分支都被走到 | 不需要 |

三行都不需要模型。这意味着工作流的回归测试是确定性的——同样的输入永远同样的结果，失败就是失败，不是波动。

对比 ReAct：它的测试必须跑模型，结果每次都不同，只能测通过率。第 29 章的评测体系要处理的就是这个问题，而工作流这边已经提前解决了。

**所以"能不能写成工作流"这个问题的一个等价答案是："这件事能不能用确定性测试覆盖。"** 能，就写成工作流；不能，再考虑把不确定的部分收窄到一个最小的模型调用里。

### 3.5 工作流里的条件分支

"工作流"不等于"没有分支"。它的分支由代码写死，判断条件来自数据，不来自模型：

| 分支依据 | 例子 | 代价 |
|---|---|---|
| 字段值 | `eligible == true` 才查退款时长 | 无 |
| 类型 | 定制商品走另一条流程 | 每个类型都要写一遍 |
| 置信度 | 意图识别低于阈值就转人工（第 13 章） | 需要一个阈值 |

第三行的分支值得单独说：**"转人工"也是工作流的一部分。** 一个只有"成功"和"报错"两条路的工作流，会把所有识别不了的情况都当成报错；加上"转人工"这条分支之后，识别不了的情况变成一个明确的交付结果。

判断分支该不该写进工作流，看一条：**这个分支的条件能不能用一个表达式算出来。** 能，写进工作流；不能（需要"理解"），它就是一个模型调用，该放到 3.3 说的那三类位置之一。

## 四、ReAct：每一步都问

ReAct 是第 6、7 章反复出现的那种循环。它的核心是"每步一次模型调用"，历史全量重发：

```python
def react(meter: Meter) -> dict:
    """ReAct：每一步都问模型下一步做什么，历史全量重发。"""
    history = BASE
    facts: dict = {}
    for _ in range(3):
        meter.call(len(history))          # 每次请求都带上全部历史
        if "docs" not in facts:
            facts["docs"] = search_docs("退货窗口")[0]
            history += f"\n观察：{facts['docs']}"
            continue
        ...
```

这里没有真实的模型调用，`if "docs" not in facts` 就是在扮演"模型决定下一步"。真实的实现里，判断由模型给出，见第 5、6 章。

### 4.1 它的成本来自哪

ReAct 的成本公式是 `步数 × 平均历史长度`（第 6 章 2.1）。这个公式有一个反直觉的推论：

**ReAct 在任务更长时变贵得更快，但它的价值也在任务更长时更高。** 短任务用它不划算（固定工作流更快更省）；长任务里它的优势才体现——因为它能在每一步重新判断，而工作流不能。

所以判断标准不是"ReAct 好不好"，而是"这个任务的不确定性值不值这个价"：

| 任务 | 不确定性 | 建议 |
|---|---|---|
| 步骤已知、输入标准 | 低 | 工作流 |
| 步骤已知、输入多样 | 中 | 工作流 + 路由 |
| 步骤未知、需要试 | 高 | ReAct |

### 4.2 ReAct 的失控风险最高

第 7 章讲的四种失控，在 ReAct 里全部可能发生；在工作流里一种都不会发生（它根本不循环）。这是选择范式时必须一起考虑的：**ReAct 换来的是适应性，付出的是所有循环层面的防护成本。**

这些防护不是可选项。一个没有步数上限的 ReAct，比一个写死的工作流危险得多——工作流最坏的情况是"答错"，ReAct 最坏的情况是"一直跑"。

### 4.3 ReAct 的轨迹是什么样

ReAct 的每一步在日志里应该留下三样东西：**想法、动作、观察。**

| 项 | 内容 | 为什么要有 |
|---|---|---|
| 想法 | 这一步打算做什么、为什么 | 出事时判断"它当时以为自己在干嘛" |
| 动作 | 调用了哪个工具、什么参数 | 第 7 章的指纹与去重依赖它 |
| 观察 | 工具返回了什么（或错误） | 判断下一步的输入是否可用 |

多数实现只保留动作与观察，省掉"想法"。省掉的代价在排查时才体现：一个卡住的循环，只看动作与观察能看出"它重复了"，看不出"它为什么以为重复是对的"。

不过"想法"也有代价：它是模型生成的自由文本，会占用上下文，还可能被后续步骤误当成事实引用。**折中的做法是把它记在轨迹里、但不回灌进 messages。** 也就是"给人和日志看的想法"与"给模型看的消息"分开存。

这一条与第 6 章 7（轨迹）的选择一致：轨迹用于归因，messages 用于推理，两者内容有交集但不该是同一份。

### 4.4 ReAct 与工具数量的关系

第 5 章 1.4 讲过工具越多选择越差。ReAct 把这个效应放大了一次：**每一步都要重新选一次，选错的概率按步数累乘。**

如果单步选对的概率是 0.95，五步全对的概率是 0.77。这不是说 ReAct 有 23% 的失败率——选错之后往往还能纠正。但它说明了为什么 ReAct 特别需要第 12 章的工具收窄：**减少可选工具，等于提高每一步的成功率，而它在每一步都被乘一遍。**

工作流没有这个问题，因为它不选。

### 4.5 ReAct 的一个变体：每一步都重排工具

ReAct 的一个实际问题是"第 5 章 1.4 的工具数效应"随步数累乘。一个可行的缓解是**按步收窄工具**：

| 步 | 可见工具 | 依据 |
|---|---|---|
| 1 | 全部查询类 | 还不知道要什么 |
| 2（已拿到订单） | 只留"查政策""查物流" | 订单已知，不需要再查 |
| 3（已拿到政策） | 只留"作答" | 数据齐了，不该再查 |

这个做法在本章只是提一句，它的实现细节（`allowed-tools`、按阶段切换）在第 12 章。**但它的前提在这一章就已经清楚：ReAct 的每步失败率会被乘起来，所以每一步都值得只暴露必要的工具。**

工作流不需要这个，因为它的工具是写死的。这也是选择范式时该算的一笔：ReAct 省下的是"写死流程"的维护成本，付出的是"每步都要做对选择"的可靠性成本。

### 4.6 ReAct 什么时候该结束探索

ReAct 的终止在第 6 章讲过三态。范式层面还有一层判断：**探索该不该继续。**

| 信号 | 说明 | 该做什么 |
|---|---|---|
| 连续两步没有新信息 | 探索在原地 | 停，交付已有信息 |
| 新信息与问题无关 | 走偏了 | 回到原始问题重问 |
| 已能回答但还在查 | 过度探索 | 明确告诉它"信息够了" |

第三行是 ReAct 特有的浪费：模型已经拿到足够的信息，但它不知道"够了"这件事（第 6 章第四节）。工作流不会这样，因为它的步数是写死的。

缓解手段是在系统消息里写清"够了的判据"，例如"只要拿到签收天数和政策窗口，就可以回答"。这与第 6 章 4.1 一致：提示词只能提高概率，真正的硬停在循环里。**但在这个场景里，提示词的收益特别高**——它把"该不该继续"从抽象判断变成了一个可数的条件。

## 五、Plan-and-Execute：先想清楚再动手

P&E 把"决定做什么"和"执行"分成两个阶段。计划阶段调一次模型，产出一份步骤清单；执行阶段按清单跑，不再问模型：

```python
def plan_and_execute(meter: Meter) -> dict:
    """P&E：先出计划（1 步），再按计划执行（不再问模型），最后汇总（1 步）。"""
    meter.call(180)                        # 计划
    plan = ["search_docs", "get_order"]
    facts: dict = {}
    for name, arg in zip(plan, ["退货窗口", "A1001"]):
        facts[name] = TOOLS[name](arg)     # 执行阶段不消耗模型调用
    meter.call(320)                        # 汇总
    return facts
```

它的成本结构是"两次固定开销 + 执行阶段零模型调用"，与 ReAct 的"每步一次"完全不同。

### 5.1 计划的价值在哪

既然计划可能不准，为什么要先写？有三个理由，每个都能对应到具体的问题：

**第一，计划可以被审查。** 一份"将执行以下三步"的清单，可以给人看，也可以在执行前被程序校验。第 23 章的分级审批正是靠这个——**没有计划就没有可以审批的对象。** ReAct 没有"动手之前"这个时刻，自然也没有审批点。

**第二，计划让成本可预估。** 计划里有几步，就大致知道花多少。ReAct 事前估不出来，只能给一个上限。

**第三，计划把并发结构暴露出来。** 计划里的步骤一旦写出来，哪些互不依赖就能一眼看出，这是第六节并发的前提。

### 5.2 它在哪里失效

P&E 的失效是"计划本身错了"，有两种典型：

| 情况 | 表现 | 处理 |
|---|---|---|
| 计划漏了一步 | 执行到一半发现缺数据 | 原地补一步（patch） |
| 计划方向错了 | 三步全做完还是答不出 | 重订计划（replan_all） |

这两种处理就是第 9 章的分级重规划。**P&E 不是"计划完就照做"，它需要执行阶段的检查点。** 一个不会检查执行结果的 P&E，等于把 ReAct 的适应性换成了工作流的僵硬，还多付了一次计划的钱。

### 5.3 计划写成什么样

计划的粒度决定它好不好用。太粗（"查一下订单"）等于没计划；太细（"用 get_order 传 A1001"）等于把 ReAct 的每一步预先写死，失去了 P&E 的意义。

好的粒度是"一步对应一个可验证的中间结果"：

| 粒度 | 例子 | 问题 |
|---|---|---|
| 太粗 | 调查这个订单 | 无法执行，无法校验 |
| 合适 | 取订单签收天数（需要 order_id） | 有输入、有输出、可校验 |
| 太细 | 调 get_order，参数 {"order_id":"A1001"} | 提前决定了实现细节 |

第二行有一个"需要什么"的标注，这是计划能被执行的前提：**每一步写清它依赖哪个前序结果。** 这个依赖关系就是下一节的 DAG。

### 5.4 执行阶段的检查点

P&E 最容易写错的地方是把执行阶段写成"照着跑完"。正确做法是每一步之后检查一次，检查内容有三项：

| 检查 | 不通过意味着 | 对应处理 |
|---|---|---|
| 结果是否符合这一步的预期 | 计划里的假设不成立 | 补一步（patch）或停 |
| 是否产生了计划里没预料的信息 | 计划不全 | 追加步骤 |
| 累计成本是否还在预算内 | 计划太长 | 截断并交付部分结果 |

第二项最有价值。**计划是猜出来的，执行会带来新信息。** 一个新出现的字段、一条意外的报错，都可能意味着计划漏了东西。能发现这一点的只有"把观察结果与计划对照"这一步，而它必须写在代码里。

第三项常被忽略：计划本身可能有二十步，跑到第十步预算就用完了。这时该停下来交付部分结果，而不是继续跑然后中途失败——后者连部分结果都拿不到。

### 5.5 计划本身值不值一次调用

计划要花一次模型调用，还要占一段上下文。什么时候这笔钱不值得花？

| 计划步数 | 值不值 | 理由 |
|---|---|---|
| 1–2 步 | 不值 | 直接执行比写计划还省 |
| 3–8 步 | 通常值 | 可审查、可预估、可并发 |
| 超过 15 步 | 要拆 | 计划本身会超窗口，且执行到一半必然偏离 |

第一行反直觉但有依据：**两步的任务写计划，等于用一次调用换一份两行的清单。** 执行阶段本来就要调两次模型（或者零次），计划的收益抵不上成本。

第三行是 P&E 的真实上限。一份十五步的计划，每步带说明，本身就要几千 token；执行到第十步时，前九步的结果又都在历史里，总量很快就顶到窗口。**P&E 适合的是"中等长度、结构清晰"的任务，不是"很长、很复杂"的任务。** 后者应该拆成几个子任务，每个用一个 P&E。

这三行也解释了一个常见困惑：为什么按 P&E 写出来的系统，任务一长就不好使。不是计划能力不行，是计划本身的成本随长度超线性增长，而执行阶段还要再付一次历史重发的钱。

### 5.6 计划要不要给人看

P&E 的一个隐藏优势是计划可以在执行前被人看到。这带来一个选择：看，还是不看？

| 场景 | 建议 | 原因 |
|---|---|---|
| 只读操作 | 不看 | 计划错的最坏结果是多查几次 |
| 有写操作 | 必看（或自动校验） | 计划里的写操作一旦执行就撤不回 |
| 成本敏感 | 看预算数字 | 步数一眼可见，等于预估 |

第二行与第 23 章的分级审批是同一件事的两个阶段：**这里是"计划可见"，那里是"计划需要批准"。** 前者是后者的前提——一份不存在的计划，没法被批准。

这也解释了为什么纯 ReAct 很难做审批：它没有"动手之前"的时刻。要做到审批，只能在每个工具调用前拦一次，而那时模型已经把整个意图拆散了，人看到的只是一个孤立的调用，无法判断它在整体上要做什么。

## 六、计划里的依赖决定谁并发

一个计划写成一串步骤，看上去只能顺序执行。实际上只要依赖关系允许，就可以并发。

```python
DAG = {
    "order": [],            # 不需要前置
    "user": [],             # 不需要前置
    "logistics": ["order"], # 需要订单号
    "policy": [],           # 不需要前置
}
```

四步里只有 `logistics` 依赖别人。串行执行与按层并发的对比：

```
串行：0.90s
  order     0.30s
  user      0.20s
  logistics 0.25s
  policy    0.15s

并发：0.55s
  层 1: ['order', 'user', 'policy']  最大耗时 0.30s
  层 2: ['logistics']  最大耗时 0.25s

加速比：1.63x
注：串行总耗时等于各步之和，并发总耗时等于各层最大值之和。
```

分层的代码很短：

```python
def layered(dag: dict[str, list[str]]) -> tuple[list[list[str]], float]:
    """按依赖分层，同层并发。"""
    remaining = dict(dag)
    layers: list[list[str]] = []
    done: dict[str, str] = {}
    t0 = time.perf_counter()
    while remaining:
        ready = [n for n, deps in remaining.items() if all(d in done for d in deps)]
        if not ready:
            raise RuntimeError(f"依赖成环：{list(remaining)}")
        layers.append(ready)
        with ThreadPoolExecutor(max_workers=len(ready)) as pool:
            for name, result in zip(ready, pool.map(lambda n: tool(n, COST[n]), ready)):
                done[name] = result
        for n in ready:
            del remaining[n]
    return layers, time.perf_counter() - t0
```

### 6.1 加速比由什么决定

上例的加速比是 1.63，不是理论上的 4 倍。原因是关键路径的长度：`order → logistics` 必须串行，耗时 0.55 秒，这就是加速比的极限。

**并发的上限由关键路径决定，不是由步数决定。** 这个结论在实际系统里有三个用法：

| 情况 | 判断 |
|---|---|
| 关键路径长、其余步多 | 并发收益有限，先缩短关键路径 |
| 关键路径短、其余步多 | 并发收益大 |
| 各步耗时悬殊 | 一层里最慢的那个决定这层耗时 |

第二行的"缩短关键路径"往往比"加并发"更有效。上例里如果 `order` 只要 0.05 秒，整个任务就能压到 0.30 秒。

### 6.2 依赖成环

`layered` 里那句 `if not ready: raise` 不是防御性代码，是真会发生的：计划由模型生成，模型完全可能写出 A 依赖 B、B 又依赖 A。不检查的话，`while` 会永远转下去。

这和第 6 章的"循环必须有上限"是同一类问题在另一层的表现：**只要结构由模型生成，就一定有生成不出合法结构的可能，必须有一个兜底。**

### 6.3 并发之后失败的归因

串行时"第 3 步失败"很好定位。并发时"第 1 层失败了"要麻烦一些：

| 情况 | 现象 | 处理 |
|---|---|---|
| 一个步失败、其余成功 | 层没完成，但部分结果可用 | 带上部分结果继续，或重试那一步 |
| 多个步失败 | 可能有共同原因（网络、鉴权） | 先查共同原因，别逐个重试 |
| 全部失败 | 大概率是整层的前置条件不满足 | 检查这一层的输入 |

第二行的判断很实用：**同一层里多个步骤同时失败，几乎总是一个共同原因。** 逐个重试只会让失败次数乘以步数，而修好共同原因一次就够。这也是 `ThreadPoolExecutor` 里应该收集全部结果再判断、而不是第一个异常就退出的原因。

### 6.4 并发与模型调用的关系

上面例子里的四步都是纯工具调用，并发只省时间。如果某几步是模型调用，情况会复杂一点，因为模型调用有**速率限制**：

| 情况 | 现象 | 处理 |
|---|---|---|
| 并发数小于配额 | 与串行一样快 | 无需处理 |
| 并发数大于配额 | 一部分请求被拒 | 限流 + 重试 |
| 长上下文 + 高并发 | 被拒的比例更高 | 按 token 配额而不是次数配额 |

第三行是最容易踩的：多数配额是按 token 计的，一次十万 token 的请求可能比十次一万 token 的请求更容易被拒。**并发调度器要知道每步的预期 token，而不是只数步数。**

这也解释了为什么"把并发放到最大"不是个好默认值。并发上限应该由两个约束里更紧的那个决定：线程/连接数，和模型的 token 速率。

### 6.5 DAG 从哪来

依赖表有两个来源，区别很大：

| 来源 | 可信度 | 风险 |
|---|---|---|
| 代码里写死 | 高，可以测 | 需求一变就要改代码 |
| 模型生成 | 只要能表达就能跑 | 可能漏依赖、可能成环、可能编出不存在的工具 |

第二行是 P&E 的真实形态。它带来三个必须做的校验，缺一个都会在运行时出事：

**校验一，工具名存在。** 计划里写了 `get_order_v2`，而它没注册，执行时才失败。这个检查在第 5 章 5.3 的 `audit_tools` 里已经实现了一半。

**校验二，参数能对上。** 计划里说"取订单天数（需要 order_id）"，那前序结果里必须真的有一个 order_id。检查方法是比对"这一步声明的输入"与"已有结果的字段集合"。

**校验三，无环且可达。** 就是 `layered` 里那句 `raise`。

三个校验都不需要模型，都是纯代码。**它们应该在计划被接受之前跑，而不是在执行中逐条发现。** 一次失败的校验比三步白跑便宜得多。

### 6.6 并发对上下文的影响

并发还有一个容易被忽略的副作用：**同一层的多个结果会一起回灌进 messages。**

串行时，一步的结果紧接着被下一步消费。并发时，三个结果同时回来，一起塞进历史。这意味着：

| 情况 | 串行的历史 | 并发的历史 |
|---|---|---|
| 三个查询各 1k token | 每步加 1k，逐步增长 | 一次加 3k |
| 下一步的 prompt | 只含前一步结果 | 含全部三个结果 |

并发让"单步历史增幅"从 1k 变成 3k。**时间省下来的同时，窗口压力变大了。** 步数少的任务无所谓；步数多、又并发度高的任务，需要把第 7 章的裁剪阈值按"层"而不是"步"来算。

另一个后果是顺序不可控：三个结果写回 messages 的先后顺序取决于谁先完成。这对模型通常没有影响（它读的是全部内容），但对"按顺序引用的答案"有影响——**如果答案强调"第一步……第二步……"，而结果顺序每次都不同，输出的顺序也会飘。** 需要固定顺序时，按层内的声明顺序写回，而不是按完成顺序。

## 七之前的对照：同一件事的三次实现

三种范式跑同一个退货任务，把三份代码并排看，差别只在"谁决定下一步"：

| | 决定者 | 模型调用 | 出错时 |
|---|---|---|---|
| 工作流 | 代码 | 0–2 次（入口/出口） | 某步报错，或走了错误分支 |
| ReAct | 模型，每步 | 等于步数 | 可能空转、可能选错工具 |
| P&E | 模型，一次 | 2 次（计划 + 汇总） | 计划漏步、方向错 |

三行的最后一列决定了防护成本：第一行需要的是"输入校验"，第二行需要的是第 7 章全部四种守卫，第三行需要的是计划校验（6.5）加执行检查点（5.4）。**防护成本也是选范式时要算的账**，不只是 token。

### 6.7 一个可以直接用的调度函数

上面 `layered` 用 `while` 逐层推进，够用但有两处可以更实用：失败的处理与并发的上限。

```python
import time
from concurrent.futures import ThreadPoolExecutor

# 依赖与耗时沿用 dag.py 的示例，便于与本节的输出对照
DAG = {"order": [], "user": [], "logistics": ["order"], "policy": []}
COST = {"order": 0.30, "user": 0.20, "logistics": 0.25, "policy": 0.15}


def tool(name: str, cost: float) -> str:
    time.sleep(cost)
    return name


def run_dag(dag: dict[str, list[str]], cost: dict[str, float],
            max_workers: int = 4) -> dict[str, object]:
    """按层执行，单步失败不中断整层；返回每步的结果或错误。"""
    done: dict[str, object] = {}
    remaining = dict(dag)
    while remaining:
        ready = [n for n, deps in remaining.items() if all(d in done for d in deps)]
        if not ready:
            for n in remaining:
                done[n] = RuntimeError(f"依赖成环，无法执行：{n}")
            break
        with ThreadPoolExecutor(max_workers=min(max_workers, len(ready))) as pool:
            futures = {n: pool.submit(tool, n, cost[n]) for n in ready}
            for n, fut in futures.items():
                try:
                    done[n] = fut.result()
                except Exception as e:      # 单步失败只记这一格
                    done[n] = e
        for n in ready:
            del remaining[n]
    return done


if __name__ == "__main__":
    out = run_dag(DAG, COST)
    for k, v in out.items():
        print(f"  {k}: {v!r}")
```

输出：

```
  order: 'order'
  user: 'user'
  policy: 'policy'
  logistics: 'logistics'
```

两个改动都在"失败"这一侧：

**单步失败记为值，不抛出。** 一层里三个步骤失败，`fut.result()` 都会抛异常；把它记成 `done[n] = e`，整层仍能跑完，下游能拿到"这一步失败了"这个事实。这对应 6.3 里"收集全部结果再判断"的做法。

**`max_workers` 有上限。** 一层里有十个步骤不等于该开十个线程；更不等于该同时发十个模型请求（6.4 的配额）。

### 6.8 并发与幂等冲突

并发有一个必须提前想到的后果：**同一层的两个步骤可能在做同一件事。**

计划里写"查订单"和"查订单详情"，看起来是两个任务，底层可能调的是同一个接口；两个并行的写操作更是直接冲突。后者是第 11 章幂等要解决的问题，前者属于计划本身的质量问题。

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 重复查询 | 两个步骤查同一份数据 | 计划校验时合并（6.5） |
| 写后读 | 一步写、另一步读同一对象 | 加依赖，串行执行 |
| 并发写 | 两步同时改同一对象 | 串行，或引入版本号（第 10 章） |

第二行最容易漏：计划里两步互不依赖，但执行时"写"和"读"是有先后的。**依赖表里看不到这个先后，因为它不是数据依赖，是时序依赖。** 修正方法是在 DAG 里显式加一条边，哪怕数据上不需要。

### 6.9 从示例到生产要补的三件事

`layered` 与 `run_dag` 加起来不到 40 行，能跑示例，离生产还差三件：

| 缺什么 | 症状 | 补法 |
|---|---|---|
| 超时 | 一个步骤卡住，整层永不完成 | 每步一个 deadline，超时记为失败 |
| 取消 | 上游失败后下游仍在跑 | 层间检查一个 `cancelled` 标记 |
| 重试 | 一次网络抖动让整步失败 | 只对可重试的错误重试，且要幂等（第 11 章） |

第一行最要紧。`pool.map` 会在最慢的那个任务上等到底，一个卡住的 HTTP 请求能让整层停在那里。加上超时之后，卡住的那一步变成一个失败值，其余步骤照常返回。

第二行在长任务里会变成成本问题：上层已经判定失败，下层还在花 token。**取消不是优化，是避免"失败之后还在付钱"。**

第三行是唯一需要业务知识的：哪些错误重试有意义，哪些重试也没用（第 5 章 5.1 的读写分类就是这个判断）。

### 6.10 为什么示例用 sleep 而不是真请求

`dag.py` 里每一步都是 `time.sleep(cost)`。换成真实请求，结论不变，但有两个数会变：

| 变化 | 原因 | 影响 |
|---|---|---|
| 串行耗时上升 | 多了网络往返 | 加速比的"分子"变大，并发收益看起来更高 |
| 并发耗时的方差变大 | 各请求的快慢不同，且不一定稳定 | 关键路径可能换人 |

第二行是真实系统里最容易误判的：示例里 `order` 固定 0.30 秒，永远是关键路径；真实环境里某次 `policy` 可能突然变成 1 秒，于是这一层的最慢者换了。**加速比不是常数，它随每次运行的耗时分布浮动。**

所以"并发能快多少"这个问题没有固定答案，只有分布。要给出可用的数字，得看一段时间的实际耗时（第 27 章的 span 树正好提供这个），取每层的 p50 与 p95。用单次测试得出的加速比去承诺 SLA，是这个环节最常见的错。

## 七、这一层的边界

**第一，范式可以嵌套。** 一个 ReAct 循环内部可以调用一个固定工作流（"查订单"本身可能是一串三个接口）。范式选择是分层的，不是整任务一刀切。

**第二，P&E 的计划不等于确定性。** 计划由模型生成，它可能漏步、可能方向错。P&E 的价值在于"计划可审查"，不是"计划一定对"。

**第三，并发不改变总 token。** 并发省的是时间，模型调用的次数与 token 总量不变。如果想省钱，要改的是范式（工作流替代 ReAct），不是并发。

**第四，DAG 只能表达"必须先做什么"，不能表达"只能做一次"。** 幂等与副作用控制是第 11 章的内容，与并发是两件事——并发会让"同一件事被做两次"更容易发生。

**第五，选错范式的表现是"跑得动但很贵"。** 它不会报错，只是每次都在做不必要的判断。判断方法是看轨迹：如果每一步的选择都是唯一的，那这些选择本来可以不问模型。

### 7.1 选错了会怎样

三个误判，各自的症状与修法：

| 误判 | 症状 | 修法 |
|---|---|---|
| 该用工作流却用了 ReAct | 每一步的选择都唯一，token 高但结果对 | 把循环压平成一串调用 |
| 该用 ReAct 却用了工作流 | 遇到没预设的输入就答错，且不报错 | 加路由，或把分支交给模型 |
| 该用 P&E 却用了 ReAct | 每次跑出来的步数都不一样，成本不可预估 | 先出计划，再执行 |

第一行是最常见也最容易被忽视的：**它不产生错误，只产生账单。** 识别方法是看轨迹——如果连续若干个任务里，每一步调用的工具都相同，这个"选择"就没有信息量。

第二行的危险在于它很安静。工作流遇到不认识的输入时，往往还能"处理"出一个结果，只是结果回答的是另一个问题。第 13 章的路由专门治它。

第三行只在需要预算控制时才是问题。如果成本无所谓，ReAct 更灵活。

### 7.2 一个决策清单

把全章压成六个问题，按顺序问，问完就能定范式：

| # | 问题 | 若答案是"是" |
|---|---|---|
| 1 | 步骤能不能事前完整写出？ | 固定工作流 |
| 2 | 步骤能写出，但分支多于两处？ | 工作流 + 路由 |
| 3 | 有几步必须先看到结果才知道下一步？ | 这几步单独用 ReAct |
| 4 | 整个任务都必须边看边定？ | 用 ReAct，并配齐第 7 章的守卫 |
| 5 | 步骤能枚举但顺序要看结果？ | Plan-and-Execute |
| 6 | 需要执行前审批？ | Plan-and-Execute（或至少"计划可见"） |

第 3 行是本章最实用的结论：**范式不必整任务统一。** 一个工作流里嵌一个 ReAct 子步骤，比整任务用 ReAct 便宜得多，也比整任务用工作流灵活得多。

第 6 行说明范式选择不只是技术问题。凡是"要让人点头才能执行"的流程，都需要一个"动手之前"的时刻，而那一刻只存在于 P&E 的计划阶段。第 23 章的分级审批建立在这一点上。

## 这一章建立的 5 件事

1. 循环是最贵的默认选项。判断依据是"有多少步必须先看到上一步结果才知道下一步"——0 步用工作流，大部分用 ReAct，介于两者用 P&E。
2. 固定工作流的失效形态是"输入超出预设"，且它不报错，只是走了另一条业务的路。上游需要路由。
3. ReAct 的成本是 `步数 × 平均历史长度`，它的适应性也随任务变长而变值。代价是第 7 章全部防护都必须到位。
4. P&E 的价值是"计划可审查、成本可预估、并发结构可见"，代价是计划可能不全或方向错，需要第 9 章的分级重规划。
5. 并发的上限由关键路径决定，不是步数。同层多步同时失败通常是一个共同原因。
