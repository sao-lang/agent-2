## 一、手写注册到不了两位数

前几章的工具都是手写的：一个 dict 描述，一个 Python 函数实现，第 5 章的 `audit_tools` 核一遍。

这套做法在 3–5 个工具时完全够用。到 20 个时会出现三个问题：

| 问题 | 表现 |
|---|---|
| 注册代码分散 | 每个服务一套写法，`audit_tools` 查不完 |
| 与外部服务的生命周期不同 | 服务重启、换地址，本地注册表要跟着改 |
| 权限与范围无法表达 | 所有工具对所有任务可见 |

第一行是维护成本，第二行是耦合，第三行是安全（第 20 章的问题）。

**MCP 解决的是前两个，Skill 解决的是"流程越来越长"。** 两者都建立在第 5 章的 `tools` 机制上——协议与目录只是换了一种方式生成那份清单。

### 1.1 三个问题的共同根源

三个问题的根源是同一个：**"有哪些能力"这件事被写死在代码里。**

| 谁维护能力 | 写死时 | 协议化之后 |
|---|---|---|
| 你 | 你写注册、你写实现 | 别人写 server，你只写配置 |
| 变化频率 | 跟着你的发版 | 跟着对方的发版 |
| 可见范围 | 全局 | Host 按需选 |

第二行是耦合的具体形态。一个外部服务的接口变了，写死时你要发一次版；协议化之后，对方更新 server，你只需要重新拉一次清单。

第三行是协议化带来的新能力，也是新风险：**范围由你自己决定，决定错了就是安全问题。**

### 1.2 三个问题的代价

把三个问题的代价摊开，能看出为什么值得引入两套新机制：

| 问题 | 每个工具/流程的边际成本 | 20 个之后的症状 |
|---|---|---|
| 注册分散 | 一次手工配置 | 配置漏了没人知道 |
| 生命周期耦合 | 一次发版 | 发版被外部服务拖住 |
| 权限无法表达 | — | 所有任务都能调所有工具 |

第二行是运维视角的痛：外部服务改了接口，你的 agent 要跟着发版。协议化之后，这只是"重新拉一次清单"。

第三行是安全视角的痛，也是第 20 章整章要解决的。它在本章只解决一半：**收窄把"不该给某阶段的工具"挡掉，但"谁有权进入这个阶段"要交给鉴权。**

## 二、MCP 与 Skill 各管什么

两个词常被并列提起，但它们的位置不同：

| | MCP | Skill |
|---|---|---|
| 解决什么 | 工具从哪来、谁维护 | 流程怎么组织、何时加载 |
| 粒度 | 一个工具 | 一套流程 |
| 常驻成本 | 每个工具一段说明 | 每套流程几十个字符（L1） |
| 失效方式 | 撞名、超时、越权 | 漏召、误召、加载失控 |

第三行是两者最实际的区别。**工具是"一直都在"的，流程是"按需出现"的。** 二十个工具就是二十段说明，跑不掉；二十套流程在 L1 只有一千多字符。

这也解释了为什么要有两套机制：把一个流程拆成工具，工具会爆炸；把工具写成流程说明，每次请求都得带着所有说明。

### 2.1 两者的交界面

MCP 提供工具，Skill 组织流程，两者交界在"Skill 正文里写的工具名"。

| 情景 | 结果 |
|---|---|
| Skill 要用的工具，Host 没接 | 4.2 的缺失校验会拦下 |
| Host 接了，但当前阶段被收窄掉了 | 运行时才发现，模型改硬凑 |
| 接了、也没被裁 | 正常工作 |

第二行是实践中最常见的坑：**校验发生在"接入时"，收窄发生在"每步拼清单时"**，两者不是同一个时刻。所以 5.2 的校验要跑在"这个 Skill 被激活且清单已收窄"之后，而不是启动时。

这条时序要求很容易漏，因为两处代码通常不在一个模块里。

## 三、能力的三种来源

在讲 MCP 之前，先把"能力从哪来"列全：

| 来源 | 例子 | 维护者 |
|---|---|---|
| 本地函数 | 第 5 章手写的 `get_order` | 你 |
| 外部进程（MCP） | 第三方订单系统 | 对方 |
| 本地脚本（Skill 的 scripts/） | 校验、格式转换 | 你 |

第三种常被忽略：**`scripts/` 里的脚本也是能力**，只是由流程触发而不是由模型直接选择。它适合"确定性很强、不需要模型参与"的动作，第 8 章 3.2 的"能写成表达式的判断放代码"在这里是同一个原则。

三者的可见性不同：第一种在 `tools` 里，第二种在 `tools` 里（加了前缀），第三种不在 `tools` 里——模型看不到它，只能通过流程被调用。

### 3.1 为什么第三种（本地脚本）不在 tools 里

一个自然的疑问是：既然 `scripts/` 里的脚本也是能力，为什么不也注册成工具？

| 原因 | 说明 |
|---|---|
| 它不需要"选" | 流程里写死第几步调用 |
| 它的参数由流程决定 | 不是模型临时判断 |
| 暴露出去会增加选择负担 | 第 5 章 1.4 |

第一行是关键：**能被工具化的前提是"有选择余地"**。一个只在固定位置被调用的脚本，交给模型去"选"只会增加犯错的机会。

第二行更具体：`scripts/check.py` 的输入是"上一步的结论与依据"，这个参数由流程提供，模型不需要也不应该决定它。

所以三种来源的划分标准是：**谁决定"要不要调用它"**。模型决定 → 工具；流程决定 → 脚本。

## 四、MCP：把工具放到进程外

MCP 是一个协议，让工具活在一个独立的进程（或服务）里，由客户端按标准方法访问。

`capability.py` 起了一个最小的 server，通过 stdin 喂一行 JSON-RPC：

```python
def mcp_roundtrip(method: str, params: dict | None = None, msg_id: int = 1) -> dict:
    """起一个 server 进程，写一行请求，读最后一行响应。"""
    req = {"jsonrpc": "2.0", "id": msg_id, "method": method, "params": params or {}}
    proc = subprocess.run(
        [sys.executable, SERVER],
        input=json.dumps(req, ensure_ascii=False) + "\n",
        capture_output=True,
        text=True,
        encoding="utf-8",
    )
    lines = (proc.stdout or "").strip().splitlines()
    return json.loads(lines[-1]) if lines else {"error": "no output", "stderr": proc.stderr}
```

第一次是 `initialize`：

```
=== 1. MCP 初始化 ===
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "serverInfo": {"name": "mini-order", "version": "0.1.0"},
    "capabilities": {"tools": {}}
  }
}
```

这段响应的三个字段各有用途：`protocolVersion` 决定后续能调哪些方法；`serverInfo` 是排查时的身份；`capabilities` 声明"我支持 tools"——一个只会读书面资源的 server 不会声明它。

### 4.1 三角色

协议里有三个角色，分清它们才能理解权限边界：

| 角色 | 是谁 | 干什么 |
|---|---|---|
| Host | 你的 agent 应用 | 决定把哪些 server 接进来 |
| Client | Host 内的连接器 | 与某个 server 一对一通信 |
| Server | 外部进程/服务 | 提供工具、资源、提示 |

**Host 是唯一的决策点。** 一个 server 能提供多少工具，不代表这个 agent 就该看到多少——是否接入、接哪些、给谁用，都是 Host 的决定。第 20 章的沙箱与第 12 章的收窄，都落在 Host 这一层。

### 4.2 清单与调用

```
=== 2. 列出工具（加前缀后进清单）===
  order__get_order  <- 查询订单。返回 JSON：status / signed_days_ago。
  order__get_policy  <- 查询退货政策。返回 JSON：window_days。

=== 3. 调用工具 ===
  {"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "{\"status\": \"已签收\", \"signed_days_ago\": 3}"}]}}
```

第 3 行的返回值结构与第 5 章的回灌不同：它是 MCP 的 `content` 数组（可以有多种内容块），需要客户端**转换成一条 `tool` 消息**再回灌。

```python
def namespaced(server: str, tool: str) -> str:
    """外部工具进模型可见清单时加前缀，避免与本地工具撞名。"""
    return f"{server}__{tool}"
```

前缀不是美观问题。**两个 server 都可能有一个叫 `search` 的工具**，混在同一个清单里，模型分不清，你回灌时也分不清该调哪个。加前缀之后，名字本身就带了来源。

### 4.3 默认拒绝

```
=== 4. 未声明的工具（默认拒绝）===
  {"jsonrpc": "2.0", "id": 4, "error": {"code": -32601, "message": "未声明的工具：drop_table"}}
```

这条是治理的核心。**server 只执行它声明过的工具，其余一律报错。** 后果是模型编造工具名时（第 5 章 5 项坏法之一）会拿到一个明确错误，而不是被某个"宽容"的实现执行了没想到的东西。

默认拒绝也要用在 Host 侧：一个 server 声明了 50 个工具，Host 只接入其中 8 个，其余在清单里就不出现（第三节）。**协议层的默认拒绝与 Host 层的收窄是两道闸。**

### 4.4 把 MCP 的返回转成 tool 消息

MCP 的 `content` 与第 5 章的 `tool` 消息不是同一种结构，中间要一次转换：

| MCP 返回 | tool 消息 |
|---|---|
| `result.content[]`（可能有多个块） | `content` 字符串 |
| `result.isError`（可选） | 用 `{"error": ...}` 表达 |
| `id`（JSON-RPC） | `tool_call_id` 用原来的 `call.id` |

第三行最容易搞错：**JSON-RPC 的 `id` 与 `tool_calls.id` 是两个编号。** 前者是协议层的请求序号，后者是本次模型请求的调用编号。回灌必须用后者，否则第 5 章 3.3 的配对校验会失败。

第二行的处理方式：`isError=true` 时，不要把内容原样回灌成成功结果——**把它包装成 `{"error": ...}`**，这样第 7 章的空步检测（连续空回灌）才能识别它。

第一行的多块情况：把文本块拼接，非文本块（图片等）转成一句描述。直接 `json.dumps` 整个数组会让模型读到一堆它们用不上的结构字段。

### 4.5 MCP server 的三条治理要求

接一个外部 server，不只是"连上就行"。三条硬要求：

| 要求 | 做法 | 不做的后果 |
|---|---|---|
| 白名单 | Host 配置里列出允许接入的 server | 任意 server 都能接进来 |
| 工具白名单 | 每个 server 只暴露一部分工具 | 一个 server 的 50 个工具全进清单 |
| 超时与隔离 | 每次调用有超时，故障 server 不影响其他 | 一个慢 server 拖慢整个循环 |

第三条在进程外架构里特别重要：**一个卡住的 server 会让你的循环停在那一步。** 第 8 章 6.9 讲的超时，在这里是必需品而不是优化。

第二行的做法是本章第三节的收窄在 server 维度上的应用：一个 server 可能同时提供"读"与"写"两类工具，Host 只接读的那一半。

### 4.6 一段最小的客户端代码

把 2.2 的三次往返接成一个客户端，是三十行以内的事：

```python
import json
import os
import subprocess
import sys


def call_server(method: str, params: dict | None = None,
                server: str = "mini_mcp_server.py") -> dict:
    """一次调用一个 server。真实客户端会保持连接，这里每次起一个新进程。"""
    req = {"jsonrpc": "2.0", "id": 1, "method": method, "params": params or {}}
    here = os.path.dirname(os.path.abspath(__file__))
    proc = subprocess.run(
        [sys.executable, os.path.join(here, server)],
        input=json.dumps(req, ensure_ascii=False) + "\n",
        capture_output=True, text=True, encoding="utf-8",
        cwd=here,            # server 与本模块同目录
    )
    lines = (proc.stdout or "").strip().splitlines()
    return json.loads(lines[-1]) if lines else {"error": {"message": proc.stderr[:200]}}


def as_tool_message(call_id: str, result: dict) -> dict:
    """MCP 返回 -> 第 5 章的 tool 消息。"""
    if "error" in result:
        payload = json.dumps({"error": result["error"]["message"]}, ensure_ascii=False)
    else:
        blocks = result["result"].get("content", [])
        text = "".join(b.get("text", "") for b in blocks if b.get("type") == "text")
        payload = text or "{}"
    return {"role": "tool", "tool_call_id": call_id, "content": payload}


if __name__ == "__main__":
    msg = as_tool_message("call_1", call_server("tools/call",
                          {"name": "get_order", "arguments": {"order_id": "A1001"}}))
    print(msg)
```

输出：

```
{'role': 'tool', 'tool_call_id': 'call_1', 'content': '{"status": "已签收", "signed_days_ago": 3}'}
```

两个函数各管一件事：`call_server` 负责协议，`as_tool_message` 负责转成第 5 章的形状。**分开写的好处是换传输方式（从 stdio 换成 HTTP）时只改前者。**

`as_tool_message` 里的 `or "{}"` 不是多余的：一个没有文本块的返回（例如只有图片块）如果不兜底，回灌进去就是空字符串，而空的 `tool` 内容会让模型以为工具什么都没返回。

### 4.7 传输方式的选择

MCP 支持多种传输方式，选哪个影响部署与延迟：

| 传输 | 进程关系 | 适合 |
|---|---|---|
| stdio | 子进程 | 本地工具、开发期 |
| HTTP（可流式） | 独立服务 | 远程服务、多 agent 共用 |
| 进程内 | 同进程 | 性能敏感、无需隔离 |

第一行是本节的示例方式：Host 起子进程，用 stdin/stdout 通信。它的优点是没有网络配置，缺点是**一个 server 一个进程**，工具多了进程数跟着涨。

第二行是生产常见方式。它带来一个额外问题：**认证**。stdio 靠"进程是你起的"来保证身份，HTTP 没有这个保证，需要 token 或 mTLS。第 20 章的鉴权在这一层落地。

第三行看似最省，但它放弃了隔离——一个 server 崩了会带走整个 agent。只有在工具逻辑极简单、可信度极高时才用。

### 4.8 失败调用的两层错误

MCP 的错误分两层，处理方式不同：

| 层 | 错误码示例 | 该谁处理 |
|---|---|---|
| 协议层 | `-32601` 方法不存在 | Host：配置错了 |
| 业务层 | `isError: true` | 回灌给模型，让它调整 |

第二行的判定依据是**"模型能不能改变结果"**。参数写错了，模型可以重发（第 5 章 3.1）；协议方法名写错，模型改不了，只有配置能改。

把两者混在一起会造成两种后果：协议错误回灌给模型，它会尝试"换个参数"（徒劳）；业务错误直接抛给上层，整个循环断掉。

一条实用的划分：**`-32xxx` 是协议层，`isError` 是业务层。** 本章的 server 里 `-32601` 就是前者：

```python
def reject(name: str, mid: int = 4) -> dict:
    """未声明的工具：协议层错误，不交给模型重试。"""
    return {"jsonrpc": "2.0", "id": mid,
            "error": {"code": -32601, "message": f"未声明的工具：{name}"}}


if __name__ == "__main__":
    print(reject("drop_table"))
```

而"订单不存在"应该是业务层——它是工具执行的结果，不是调用失败。

### 4.9 MCP 的三个能力面

协议里一个 server 除了 tools，还可以提供 resources 与 prompts：

| 能力 | 内容 | 本课用在哪 |
|---|---|---|
| tools | 可调用的动作 | 本章 |
| resources | 可按 URI 读的资料 | 类似 Skill 的 `references/` |
| prompts | 预置的提示词模板 | 类似 `templates/` |

后两者与 Skill 的 L3 有重叠。区别在"谁提供"：MCP 的 resources 由外部服务提供，Skill 的 `references/` 由你随 Skill 一起维护。

判断用哪个：**资料的更新频率跟着谁走。** 跟着外部服务更新，用 MCP resources；跟着你的流程更新，放 Skill 目录里。

### 4.10 一次调用的完整时序

跨进程调用比本地函数多几步，每一步都可能失败：

| 步 | 动作 | 失败形态 |
|---|---|---|
| 1 | 序列化请求 | 参数含不可序列化的值 |
| 2 | 写入 stdin | 管道断开（进程已退） |
| 3 | server 处理后写 stdout | 超时、崩溃 |
| 4 | 读一行并解析 | 输出不是 JSON、多于一行 |
| 5 | 转换成 tool 消息 | 结构不符（4.4） |

第四行的"多于一行"是实际会遇到的：一些 server 会往 stdout 打印日志。**协议规定 stdout 只放协议消息、日志走 stderr**，但实现会犯错。所以读的时候取"最后一行合法的 JSON"，并在解析失败时把 stderr 一起记下来。

第五行是本章新增的一步，也是最容易漏的：协议走通了、消息转错了，表现出来的仍然是"工具调用失败"。

### 4.11 一份 server 配置应该写什么

Host 侧的配置决定了"接入什么、暴露多少"。一份最小配置：

```python
import json


CONFIG = {
    "servers": {
        "order": {
            "transport": "stdio",
            "command": "python mini_mcp_server.py",
            "allow": ["get_order", "get_policy"],      # 工具白名单
            "timeout_ms": 3000,
        },
        "kb": {
            "transport": "http",
            "url": "https://kb.internal/mcp",
            "allow": ["search"],
            "timeout_ms": 5000,
        },
    }
}


if __name__ == "__main__":
    for name, s in CONFIG["servers"].items():
        print(f"{name}: {s['transport']} 允许 {len(s['allow'])} 个工具 超时 {s['timeout_ms']}ms")
```

输出：

```
order: stdio 允许 2 个工具 超时 3000ms
kb: http 允许 1 个工具 超时 5000ms
```

四个字段对应 4.5 的三条治理要求：`allow` 是工具白名单，`timeout_ms` 是隔离，`transport` 决定部署形态（4.7）。

**`allow` 必须是显式列表，不能是"除 X 之外全部允许"。** 后者在 server 新增工具时会自动放行，等于把安全边界交给了对方。

## 五、工具收窄

第 5 章 1.4 讲过工具越多选择越差。收窄就是把"这个阶段用不到的工具"从清单里拿掉。

| 收窄维度 | 依据 | 例子 |
|---|---|---|
| 阶段 | 当前在做什么 | 已拿到订单，只留"查政策" |
| Skill | 当前激活的流程 | 激活退货流程，只留退货相关 |
| 权限 | 谁在用 | 只读用户看不到写工具 |
| 数量上限 | 硬性阈值 | 每次最多 8 个 |

第三行是安全需求，第四行是效果需求。**两条都不做，工具一多必然出现"该调不调"。**

收窄的实现位置在 Host：清单是在发请求前拼出来的，所以"给哪些工具"本来就是一次计算。这比"在提示词里叮嘱模型只用某些工具"可靠——后者是软约束（第 6 章 4.1）。

### 5.1 收窄的一次实现

收窄不是"设计时决定"，而是"每次拼清单时算一遍"：

```python
def visible_tools(all_tools: list[dict], skill: str | None,
                  read_only: bool, limit: int = 8) -> list[dict]:
    """按阶段、Skill、权限裁剪工具清单。"""
    out = []
    for t in all_tools:
        name = t["name"]
        if read_only and name.split("__")[-1].startswith(("create", "delete", "update")):
            continue
        if skill and t.get("skill") and t["skill"] != skill:
            continue
        out.append(t)
    return out[:limit]


if __name__ == "__main__":
    tools = [
        {"name": "order__get_order"},
        {"name": "order__get_policy"},
        {"name": "kb__create_doc", "skill": "knowledge"},
        {"name": "kb__search", "skill": "knowledge"},
    ]
    print("只读：", [t["name"] for t in visible_tools(tools, None, True)])
    print("退货流程：", [t["name"] for t in visible_tools(tools, "refund", True)])
```

输出：

```
只读： ['order__get_order', 'order__get_policy', 'kb__search']
退货流程： ['order__get_order', 'order__get_policy']
```

第二个结果里 `kb__search` 被裁掉了，因为它的 `skill` 标着 `knowledge`，与当前的 `refund` 不符。第一组保留了它，因为它是"读"操作，只读模式不拦。**没有 `skill` 标注的工具（如 `order__*`）是通用工具，任何流程都可见。**

这一行的取舍值得说明：**通用工具全可见，专用工具按流程裁剪。** 反过来（全部按流程）会让每个流程都要重复声明通用工具；全可见则失去收窄的意义。

### 5.2 收窄了却调不动

收窄之后常见的失败是"模型说它没有这个能力"。两种原因，修法不同：

| 原因 | 表现 | 修法 |
|---|---|---|
| 收窄过头 | 当前步骤需要的工具也被裁掉 | 放宽该阶段的可见集 |
| Skill 没告知 | Skill 正文写了要调 X，但 X 不在清单里 | Skill 与清单的核对应自动化 |

第二种是配置错误，不是模型问题。**Skill 里提到的工具名，必须都在"激活这个 Skill 时的可见集"内。** 这条校验可以写成一行断言：

```python
import re


def check_skill_tools(skill_text: str, visible: list[dict]) -> list[str]:
    """Skill 正文里出现的工具名，是否都在可见清单里。"""
    mentioned = set(re.findall(r"[a-z]+__[a-z_]+", skill_text))
    names = {t["name"] for t in visible}
    return sorted(mentioned - names)


if __name__ == "__main__":
    skill = "1. 调 order__get_order 取天数\n2. 调 order__get_policy 取窗口\n3. 调 kb__search 查例外"
    visible = [{"name": "order__get_order"}, {"name": "order__get_policy"}]
    print("缺失的工具：", check_skill_tools(skill, visible))
```

输出：

```
缺失的工具： ['kb__search']
```

这个函数在第 5 章 5.3 的 `audit_tools` 之上补了一层：后者查"声明与实现是否一致"，这里查"Skill 声明要用的是否可见"。

### 5.3 收窄的两个极端

收窄有两个极端，都出过问题：

| 极端 | 表现 | 后果 |
|---|---|---|
| 全量暴露 | 50 个工具全给模型 | 该调不调、调错，prompt 巨长 |
| 极端收窄 | 每个阶段只留 1 个 | 模型没有选择余地，遇到分支就停 |

第二行的表现很隐蔽：**模型不会报"工具不够"，它会用现有工具硬凑。** 一个只有"查订单"的清单里被问到政策，模型可能拿订单字段去猜政策窗口——答案是编的，格式是对的。

合适的收窄是"当前阶段可能用到的全部，加上少量下一步可能用到的"。经验值是 5–10 个，低于 3 个就要检查是不是裁过头了。

这与第 5 章 1.4 的三条推论一致：工具越多越容易选错，工具太少又会让"不选工具"成为唯一出路。

### 5.4 收窄与缓存的相互影响

第 3 章讲过缓存只命中"从头开始的连续前缀"。工具清单通常拼在系统消息之后，所以**清单变了，缓存也会失效**。

| 收窄策略 | 清单稳定性 | 缓存影响 |
|---|---|---|
| 按 Skill 收窄 | 整个 Skill 期间不变 | 小 |
| 按阶段收窄 | 阶段切换时变 | 中 |
| 按每步的实际需要收窄 | 每步都变 | 大 |

第三行看起来最"精确"，实际上最贵：每一步的清单都不同，等于每一步都放弃缓存。

**推荐的折中是第二行**：阶段内的清单固定，阶段切换时重新拼一次。这样缓存能在阶段内命中，而阶段只有两三个。

这条与第 7 章 4.2 "裁剪与缓存的关系"是同一类权衡：**任何"按步变化"的上下文调整，都会消灭前缀缓存。**

### 5.5 收窄与 Skill 激活的先后

两者有先后关系，顺序反了会出问题：

| 顺序 | 结果 |
|---|---|
| 先激活 Skill，再按它收窄 | 正确 |
| 先按通用集合收窄，再激活 Skill | 可能缺少 Skill 需要的工具 |

第二行的症状就是 5.2 的"收窄了却调不动"。根因是**收窄的依据来自 Skill，所以 Skill 必须先确定。**

这条顺序在一轮对话里只影响第一次（激活那一刻）；后续轮次只要 Skill 不变，清单就不变（5.4 的第二行）。所以实现上可以做成"激活时才重算清单"，而不是每步重算。

## 六、Skill：流程不能只写成一段长提示词

有些能力不是"一个工具"，而是一套流程：先查什么、再核对什么、什么情况走分支。把这些写进系统提示词，会遇到两个硬限制。

**第一，撞窗口。** 第 3 章算过，一段两千字的流程说明每次请求都要带上。五套流程就是一万字，还没开始干活就花掉大半预算。

**第二，互相干扰。** 五套流程同时在场，模型要判断"这次该按哪套走"。第 5 章 1.4 的"名字互抢"在流程层面同样成立，而且更难分辨。

Skill 的思路是：**流程做成目录，按需加载。**

### 6.1 一个 Skill 的目录结构

`capability.py` 在临时目录里造了一棵最小的目录树：

```
refund-review/
├── SKILL.md              frontmatter（name/description）+ 步骤正文
├── references/
│   └── policy.md         详细资料，命中之后才读
├── scripts/
│   └── check.py          可执行脚本，需要时运行
└── templates/
    └── reply.md          输出模板
```

四个部分各管一件事：

| 部分 | 内容 | 什么时候用 |
|---|---|---|
| `SKILL.md` | 元数据 + 步骤 | 元数据常驻；正文命中才读 |
| `references/` | 详细规则、长文档 | 需要细节时按名读取 |
| `scripts/` | 可执行代码 | 需要计算/校验时运行 |
| `templates/` | 输出格式 | 生成最终结果时套用 |

**这就是"不是只有一个 md"的意思。** 只有 `SKILL.md` 时，所有细节都必须塞进一段正文；有了 `references/`，正文可以只写"细节见 policy.md"，需要时再读。

### 6.2 三级加载省的是什么

```
=== 5. Skill 三级加载的量 ===
  L1 只读元数据:   77 字符
  L2 加正文:       118 字符
  L3 含资源:       1786 字符
  L3 / L1 = 23 倍
```

（这是示例目录的量级，实际项目里 `references/` 通常是几十 KB，倍数更大。）

| 级别 | 加载什么 | 何时 |
|---|---|---|
| L1 | `name` + `description` | 常驻，永远在上下文里 |
| L2 | `SKILL.md` 正文 | 这个 Skill 被选中时 |
| L3 | `references/`、`scripts/`、`templates/` | 真正需要时按文件读 |

**L1 常驻的代价就是那 77 个字符，收益是模型知道"有这么一套流程"。** 十个 Skill 的元数据加起来不到一千字符，而十个 Skill 的正文可能是两万字——这就是省下来的东西。

第二行的"被选中"是触发判定（4.3）；第三行是"用的时候才读"。

### 6.3 触发判定

Skill 能不能用上，取决于 `description` 写得够不够准。它要回答三件事：

| 要素 | 例子 |
|---|---|
| 做什么 | "处理电商退货审查" |
| 什么时候用 | "用户询问订单能否退货" |
| 需要什么 | "需要订单号与签收时间" |

只写第一项是最常见的错。**"什么时候用"这一项决定了召回率**：模型在有多个 Skill 可选时，靠的就是这一段比较"这次像哪一个"。

触发判定有两个错误方向，都要量：

| 错误 | 表现 | 修法 |
|---|---|---|
| 该触发没触发（漏召） | 用户问退货，走了通用流程 | 补"什么时候用"里的关键词 |
| 不该触发却触发（误召） | 普通问答激活了流程 | 补边界：什么情况不属于它 |

量法是留出集：准备 20 条左右的真实问法，一半该触发一半不该，逐条看结果。这与第 4 章 3.1 的用例集同构——只是判定对象从"输出对不对"变成"触发得对不对"。

### 6.4 能力编排与冲突

一个系统里会同时存在四种能力来源：

| 来源 | 回答什么 | 第几章 |
|---|---|---|
| 工具 | 能做什么动作 | 5 |
| Skill | 按什么流程做 | 本章 |
| 知识检索 | 依据什么资料 | 14–19 |
| 记忆 | 以前发生过什么 | 18 |

冲突发生在"两个都能处理当前请求"时。裁定顺序建议是：

| 顺序 | 依据 | 理由 |
|---|---|---|
| 1 | 明确匹配的 Skill | 流程比临时拼凑可靠 |
| 2 | 工具直接调用 | 简单请求不必走流程 |
| 3 | 检索 | 只补事实，不决定流程 |
| 4 | 记忆 | 只提供背景 |

第一行优先，是因为 Skill 是**为人审过的流程**。让模型在"按流程走"和"自己想"之间自由选择，等于每次都重新赌一次。

### 6.5 L3 的读法

L3 的资源不是"全都读进来"，而是"按需读一个文件"。为此 `SKILL.md` 正文里要写清资源清单：

```text
# 退货审查

## 步骤
1. 取订单签收天数
2. 取政策窗口
3. 比对并给出结论

## 资料
- references/policy.md     退货政策的完整条款（判定前必读）
- references/exception.md  例外情形（遇到定制商品/预售时读）
- templates/reply.md       最终回复模板

## 脚本
- scripts/check.py         校验结论内部一致性
```

这份清单的价值在于**它把"读哪个"的决定交给了当前步骤**。模型看到"遇到定制商品时读 exception.md"，就能只在那种情况下加载它——而不是一开始就把三份都读进来。

对比一下只有正文、没有清单的写法：

| 写法 | 模型的行为 |
|---|---|
| 没有清单 | 不知道有哪些资料，只能凭正文硬答 |
| 有清单无触发条件 | 可能三份全读，L3 变 L1 |
| 有清单有触发条件 | 按情况读一份 |

第三行才是三级加载的本意。**"按需加载"的前提是"知道有什么、以及什么时候需要"。**

### 6.6 一个 Skill 的完整样子

把 4.1 与 4.5 合起来，一个能用的 `SKILL.md` 是：

```text
---
name: refund-review
description: 处理电商退货审查。当用户询问订单能否退货、需要核对政策与签收天数时使用。需要订单号。
---

# 退货审查

## 步骤
1. 调 order__get_order 取 signed_days_ago
2. 调 order__get_policy 取 window_days
3. 若 signed_days_ago <= window_days，结论为可退；否则不可退
4. 用 templates/reply.md 组织回复

## 资料
- references/policy.md     完整条款（第 3 步判定前必读）
- references/exception.md  例外情形（定制商品或预售时读）

## 脚本
- scripts/check.py         校验结论与依据是否一致

## 边界
- 只处理退货，换货/维修不属于本流程
- 缺订单号时先向用户索取，不要猜
```

六个段落各有用处：frontmatter 决定能不能被选中；步骤决定怎么做；资料决定细节从哪来；脚本提供可执行的校验；边界决定"不该做什么"。

**"边界"这一段最容易被省，也最影响误召。** 没有它，模型看到"电商客服"就会把换货问题也塞进来。

### 6.7 Skill 与工具的分工判据

一个能力该做成工具还是 Skill？三个问题：

| 问题 | 是 → | 否 → |
|---|---|---|
| 它有没有确定的输入输出？ | 工具 | 继续问 |
| 它需不需要"先看结果再决定下一步"？ | Skill | 工具 |
| 它有多种做法、需要看情形选？ | Skill | 工具 |

第一行是基础：能被调用、能给结果，就是工具的形态。Skill 里也调工具，它自己不直接"做"什么。

第二行是最常判错的一条。"查订单"是工具，"判断能不能退"更像 Skill——但如果不涉及分支、只要一次比对，它也可以是"一个工具 + 一段规则"。**Skill 的价值从"有分支"开始显现。**

第三行的典型是"按商品类型走不同流程"。这种条件判断写在工具里会变成一堆 `if`，而写成 Skill 可以让人读懂、也可以让人改。

### 6.8 一个反例：把 Skill 当知识库

常见的误用是往 `references/` 里塞一整个手册，然后指望 Skill 负责回答"手册里第 3.2 节说什么"。

这混淆了两件事：

| 需求 | 该用什么 |
|---|---|
| 按固定流程做事 | Skill |
| 从大量文档里找依据 | 检索（第 14 章起） |

第二行需要的是"索引 + 召回 + 排序"，而不是"按名读文件"。`references/` 里的文件适合"确定要读的那几份"，不适合"几百分之一要去哪找"。

判断方法：**这份资料会不会因为问题不同而读到不同部分？** 会，就是检索的活；不会（每次都要整份读完），才放 `references/`。

### 6.9 Skill 的版本与灰度

Skill 是要改的。改的时候要注意它与"评价"的关系：

| 改动 | 风险 | 缓解 |
|---|---|---|
| 改 `description` | 触发率变化 | 跑一次 7.2 的矩阵 |
| 改步骤 | 结果变化 | 用第 9 章的裁判批量回扫 |
| 加 `references/` | L3 加载变大 | 看 L1/L2 有没有引用它 |

第一行最容易被忽略，因为"只是改了一句话"。但 `description` 是触发判据，改它等于改"什么时候用这套流程"。

第二行的"批量回扫"是第 9 章 5.8 讲过的做法：拿历史产物按新判据重跑一遍判据，不动模型。成本低，能快速看出改动的影响面。

### 6.10 Skill 正文里写什么

L2 只在命中时才加载，所以它可以比 L1 长得多。但也不是越长越好：

| 内容 | 写进 L2 | 放进 L3 |
|---|---|---|
| 步骤顺序 | 是 | — |
| 判定规则（可判定的） | 是 | — |
| 完整条款原文 | 否 | `references/` |
| 长示例 | 否 | `references/` |
| 输出模板 | 否 | `templates/` |

第二行是判据：**能写成"若…则…"的规则属于 L2**，因为它直接指导行动；需要"读完再理解"的资料属于 L3。

第三、四行的划分与第 4 章讲的"示例放哪一层"同构：示例的 token 成本高，只在需要时加载。

第五行说明模板也不该进 L2。回复模板通常几百字，且只在最后一步要用——放进 L2 等于每次命中都付这笔钱。

### 6.11 一个 Skill 从写到上线

五个步骤，每步都有可检查的产物：

| 步 | 做什么 | 产物 |
|---|---|---|
| 1 | 写 L1 元数据 | 一段 name + description |
| 2 | 写步骤与资料清单 | `SKILL.md` 正文 |
| 3 | 补 `references/` 与 `templates/` | 若干文件 |
| 4 | 跑触发判定矩阵 | 漏召/误召两个数 |
| 5 | 跑一次端到端 | 一条真实请求的轨迹 |

第四步常被跳过。跳过它的后果在"两个 Skill 同时被激活"时才显现——那时已经上线了。

第五步的产物不是"能不能跑通"，而是"轨迹里调了哪些工具、读了哪些文件"。**它能反过来验证第 2 步写的清单是否被遵守。**

### 6.12 Skill 与卷二前面几章的对应

一个 Skill 落到代码上，会用到前几章的每一件东西：

| Skill 里的部分 | 落到哪一章 |
|---|---|
| 步骤顺序 | 第 8 章的编排序 |
| 判定规则 | 第 9 章的规则裁判 |
| 状态字段 | 第 10 章的 State |
| 脚本 | 第 5 章的工具实现 |
| 边界段 | 第 13 章的路由依据 |

第二行是最直接的复用：**Skill 里写的判定规则，就是裁判要用的判据**。写成同一份，就不会出现"流程说可退、裁判说不对"的割裂。

第五行说明 Skill 的边界段还有第二个用途——它是路由的输入。第 13 章的三级路由里，"这个请求是不是我的流程"这一判断，依据之一就是各 Skill 的边界段。

### 6.13 Skill 与多轮对话

一个 Skill 激活之后，会跨越多轮。两件事要注意：

| 事 | 处理 |
|---|---|
| 激活状态要不要带进下一轮 | 要，放进 State（第 10 章） |
| 中途用户换了话题怎么办 | 判定是否需要退出 Skill |

第二行容易被忽略。用户先说"A1001 能退吗"，中途改问"你们几点下班"——如果 Skill 还激活着，模型会硬把这个问题套进退货流程。

处理方式与第 13 章的路由一致：**每一轮都重新判一次"还在不在流程内"**，而不是激活一次管到底。代价是每轮多一次判定，收益是跨话题时不跑偏。

## 七、这一层的失效模式

**第一，工具撞名。** 没有前缀时，两个 server 的 `search` 会互相覆盖或让模型选错。加了前缀仍有隐患：**同一功能的两个 server 都声明了**，模型会在两者间摇摆。

**第二，Skill 元数据写得像广告。** "强大的数据分析能力"这类描述无法支撑判定，模型只能靠猜。判据是 4.3 的三要素能否填满。

**第三，L3 加载失控。** `references/` 里放了一百个文件，需要时读哪个？正文里必须写明"什么情况读哪个文件"，否则 L3 变成撞运气。

**第四，收窄过头。** 只留 2 个工具时，模型可能因为看不到必要工具而放弃调用，转而编答案。收窄的下限是"当前步骤真的够用"，不是"越少越好"。

**第五，MCP server 的延迟。** 每次工具调用都要跨进程，比本地函数慢一个数量级。第 8 章 6.4 的并发配额要按实际延迟算，不能按本地函数估算。

### 7.1 三级加载的真实边界

三级加载有一个前提常被忽略：**L1 里的元数据必须足以判断"该不该加载 L2"。**

| L1 写了什么 | 能不能判断 |
|---|---|
| 只有 name | 不能（名字太短） |
| name + 一句话功能 | 勉强 |
| name + 功能 + 触发条件 | 能 |

第三行就是 4.3 的三要素。**如果 L1 判断不了，三级加载就退化成"全部加载"**——因为模型只能靠试。

这个退化有一个具体表现：多套 Skill 同时被激活，正文全部进上下文，窗口被占满。它看起来像"任务复杂"，其实是元数据不合格。

一个可检查的判据：**把十个 Skill 的 L1 并排放，能不能只凭这些文字说出"第 7 个问题该用哪个"。** 说不出，就是元数据不够。

### 7.2 一次触发判定的矩阵

判定要能量。一张二十条的留出集，结论可以直接看：

| 用例数 | 该触发 | 实际触发 | 说明 |
|---|---|---|---|
| 8 | 是 | 是 | 正确召回 |
| 2 | 是 | 否 | 漏召 |
| 7 | 否 | 否 | 正确拒绝 |
| 3 | 否 | 是 | 误召 |

两个错误率分别是 `2/10` 与 `3/10`。**它们要分开报**，因为修法相反：漏召改 `description` 的触发条件（往里加），误召改边界段（往外划）。

这与第 4 章 3.1 的"拦截率与误杀率必须一起报"是同一个原则，只是换了对象。

一个实用的收敛路径：先只改 02 类错误对应的描述，再跑一遍看 04 类是否变多。**两个数一起动，才说明改动是有效的。**

### 7.3 加载失控的一个信号

一个可观测的信号：**单次请求的 prompt 里出现了两套以上 Skill 的正文。**

它意味着触发判定没有区分开，或者 `description` 互相覆盖。后果不只是多花 token：

| 后果 | 说明 |
|---|---|
| 步骤冲突 | 两套流程都说"先查 X"，先后不同 |
| 输出格式冲突 | 两套模板同时在场，格式飘 |
| 判定依据混淆 | 一套的规则被用到另一套的场景 |

第一行最难查——两套流程都合理，只是不能同时用。

信号阈值可以定得很具体：**同一请求里 L2 加载超过 1 份，就记一条**。数量不多时人工看，多了之后自然会推动改 `description`（6.3）。

### 7.4 一次能力冲突的裁决

5.4 给了顺序，这里给一次具体的裁决过程：

| 请求 | 命中 | 裁决 |
|---|---|---|
| "A1001 能退吗" | Skill: refund-review；工具: order__get_order | 走 Skill |
| "查一下 A1001 的状态" | 工具: order__get_order | 直接调工具 |
| "退货政策第几条说了 7 天" | 检索 | 走检索，不激活 Skill |

第一行与第二行的差别只在"用词"上——"能退吗"要求一个判断，"查状态"要求一个事实。**同一个数据源，走的路不同。**

第三行最容易误判：它提到了"退货"，但问的是政策条文，不是某笔订单。这时候激活 Skill 会去查订单，而用户并没有订单。

这个例子说明一件事：**路由不该靠关键词匹配"退货"两个字。** 第 13 章的意图识别就是为了解决这个——把"问什么"与"是不是我的流程"分开判断。

### 7.5 三处细节容易被误解

| 误解 | 实际 | 后果 |
|---|---|---|
| MCP 就是"远程工具" | 它也可以本地（stdio） | 误以为必须部署服务 |
| Skill 就是提示词仓库 | 它包含脚本与资料，可执行 | 只写一段文字，用不起来 |
| 收窄越精确越好 | 精确收窄会破坏缓存（5.4） | 省了 token，贵了缓存 |

第一条常见于第一次接触协议的人：以为要起一个 HTTP 服务才能"用 MCP"。stdio 方式在本章示例里就是几十行代码。

第二条的后果是"Skill 写了但不起作用"——没有 `references/`，模型只能凭正文硬答，与一段长提示词没有区别。

第三条与第 3 章的缓存是同一条权衡，容易被"精确控制"的直觉带偏。

## 八、边界

**第一，MCP 不是必须的。** 三五个工具时，本地注册更简单。它的价值在"外部服务由别人维护"和"多个 agent 共用同一批工具"。

**第二，Skill 不是提示词模板。** 模板是替换变量；Skill 是"什么情况做什么"的流程，包含资料与脚本。混为一谈会让 Skill 退化回一段长提示词。

**第三，三级加载依赖"知道有哪些文件"。** L1/L2 里的正文要写明资源清单，否则模型不知道 L3 有什么可读。

**第四，收窄是动态的。** 同一批工具，在第一阶段和第三阶段可见的集合不同。这意味着清单不能是常量。

**第五，能力冲突不能靠模型自觉。** 冲突裁决（4.4）必须写成规则，否则同一次任务里两次相同的输入可能走出不同的路。

### 8.2 一句话总结这一章

**工具回答"能做什么"，Skill 回答"按什么顺序做"。前者要收窄，后者要按需加载——两者的共同目的是：让模型在每一步只看见它这一步真正需要的东西。**

### 9.1 能力的四条上线检查

| 检查 | 通过标准 |
|---|---|
| 每个能力有明确的"不用它"的场景 | 边界段写了 |
| 每个能力有对应的失败处理 | 错误回灌或转人工 |
| 每个能力有成本估算 | 单次 token / 延迟 |
| 每个能力有负责人 | 出问题找谁 |

第三条是本课反复提到的"可预估"：一个说不清成本的能力，无法参与范式与路由的决策。

## 这一章建立的 5 件事

1. MCP 把工具放到进程外，解决"注册分散"与"生命周期耦合"；Host 是唯一的接入决策点。
2. 外部工具进清单必须加前缀，否则撞名时模型与回灌都无法分辨。
3. 默认拒绝要在两层都做：server 侧只执行声明过的工具，Host 侧只暴露当前阶段需要的。
4. Skill 是目录不是文档：`SKILL.md` + `references/` + `scripts/` + `templates/`，三级加载把常驻成本压到元数据那几十个字符。
5. 触发判定要量两个方向（漏召、误召）；能力冲突要有固定的裁定顺序，第一优先是"明确匹配的 Skill"。

### 8.1 一张能力清单的检查表

接入一批能力之前，逐条过：

| 检查 | 通过标准 |
|---|---|
| 每个工具都有前缀 | 名字里能看出 server |
| 每个 server 都有工具白名单 | 不是全量暴露 |
| Skill 引用的工具都可校验 | 5.2 的断言能跑通 |
| Skill 的 L1 能支撑判定 | 7.1 的"并排能不能判断" |
| 收窄规则在代码里 | 不是靠提示词叮嘱 |
| 有超时 | 每个调用都有上限 |
| 能力冲突有固定顺序 | 6.4 的表落在代码里 |

前三行是接入正确性，后四行是运行时行为。**接入时全对、运行时照样出问题的，通常是后四行没做。**
