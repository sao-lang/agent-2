## 一、状态在全书里的位置

本章讨论的状态，是任务在**运行期**记住的东西。它与前后几章的分工是：

| 章 | 管什么 | 存多久 |
|---|---|---|
| 第 7 章 | 历史怎么裁 | 单次运行 |
| 本章 | 任务状态怎么组织 | 单次运行 |
| 第 11 章 | 状态怎么落盘、怎么恢复 | 跨重启 |
| 第 18 章 | 跨任务的长期记忆 | 跨会话 |

四者的共同点是"要记住点东西"，区别在**存多久**和**给谁用**。混用它们的后果很具体：把长期记忆塞进状态，状态会大到无法投影；把状态当长期记忆，用户下次来了什么都记不住。

本章只回答第二行。判断方法：**这个东西在任务结束之后还有用吗？** 有用，它不属于 State。

## 二、状态与历史的三个区别

先把两个东西分开，后文的判断都建立在这上面：

| | messages（历史） | state（状态） |
|---|---|---|
| 内容 | 按时间排列的每一条消息 | 当前掌握的事实与结论 |
| 结构 | 线性、只追加 | 字段化、可按需更新 |
| 谁读 | 模型（作为输入） | 代码（做判断） |
| 会变少吗 | 会（裁剪） | 只增不减 |
| 恢复时需要吗 | 完整版需要 | 必需 |

第四行是关键的不对称：**历史可以变少，状态不能。** 这个不对称决定了两者不能合并存——合并之后，"裁剪历史"就变成了"删状态"。

第五行解释了为什么两者都要存：恢复时既要知道"做到哪了"（状态），也要知道"当时说了什么"（历史）。只存状态能继续做，但下一轮模型不知道前因；只存历史能重放，但要重新推断状态（1.1 的三次开销）。


第 6–9 章里，循环"记住"的东西全部在 `messages` 里。这个做法在十步以内没问题，超过之后会出现三类麻烦：

| 麻烦 | 表现 | 根源 |
|---|---|---|
| 会被裁掉 | 第 7 章的裁剪删掉某条消息后，状态就缺了一块 | 状态与历史共用一份存储 |
| 无法查询 | 想知道"已经查过哪些订单"，只能扫历史 | 状态没有结构 |
| 无法恢复 | 进程重启后，只有历史，没有"进行到哪" | 进度不是历史的一部分 |

第二条最能说明问题。**"已经查过哪些订单"是一个集合，而 `messages` 里它分散在若干条 `tool_calls` 的参数里。** 要回答这个问题，得把所有调用参数解析一遍再去重——这件事每次都要重做，而且结果不稳定（一旦裁剪，答案就变了）。

`state.py` 的第一版就是这个做法：

```python
from dataclasses import dataclass, field


@dataclass
class V1:
    """把整段对话当状态。放什么全靠 messages。"""
    messages: list[dict] = field(default_factory=list)
```

它的问题不是"不够好"，而是**它根本没有"状态"这个东西**。任务进行到哪、掌握了什么、还缺什么，都需要从历史里重新推断。

### 2.1 从历史推断的三次开销

每次需要状态时重新推断，成本落在三个地方：

**第一，每次都要扫全量。** 十步的历史扫一遍，百步就扫百遍（每一步都要重新算一次状态）。

**第二，结果依赖历史完整性。** 一旦裁剪（第 7 章），推算出的状态就变了。同一个任务，裁过与没裁过，状态不同。

**第三，推断逻辑散落在各处。** 一个地方算"查过哪些订单"，另一个地方算"还差哪些"，两处的口径可能不一致。

第二项是最隐蔽的：**它让"裁剪"从性能优化变成了语义变化。** 一个只该影响成本的开关，变成了影响正确性的开关。

### 2.2 第二版：把字段抽出来

```python
from dataclasses import dataclass, field


@dataclass
class V2:
    """把任务状态从 messages 里抽出来，字段固定。"""
    messages: list[dict] = field(default_factory=list)
    order_id: str | None = None
    eligible: bool | None = None
    reason: str | None = None
```

字段一旦明确，三件事立刻变好：可以查询（`state.order_id`）、可以裁剪（裁 `messages` 不影响字段）、可以恢复（存字段比存历史小得多）。

但它有一个新问题：**字段是固定的，而任务是变化的。** 换个任务要改类定义；一次任务里出现计划外的信息（比如"用户还有一笔待处理的退款"），没地方放。

### 2.3 第三版：字段按生命周期分类

```python
from dataclasses import dataclass, field


@dataclass
class V3:
    """字段分三类：输入（只写一次）、事实（只增）、结论（可覆盖）。"""
    messages: list[dict] = field(default_factory=list)

    user_intent: str = ""                  # 输入：本轮开始后不允许改
    facts: list[str] = field(default_factory=list)   # 事实：只增不减
    eligible: bool | None = None           # 结论：允许覆盖
    overwrites: int = 0
```

分类的依据是**这个字段会被写几次、被谁写**：

| 类别 | 写几次 | 谁写 | 例子 |
|---|---|---|---|
| 输入 | 1 次 | 调用方 | 用户意图、任务参数 |
| 事实 | N 次，只增 | 工具结果 | 查到的订单、政策、日志 |
| 结论 | N 次，覆盖 | 模型判断 | 是否可退、推荐的下一步 |
| 计数 | N 次，只增 | 循环 | 步数、覆盖次数 |

四类的并发安全性完全不同，这是第 11 章和第 10 章后半部分的内容。**先分清类别，再谈怎么存。**

### 2.4 三个版本的差异

同一句需求"订单 A1001 还能退吗"，在三个版本里"已查过什么"分别怎么表达：

| 版本 | "查过订单"这个事实在哪 | 要回答"查过吗"需要做什么 |
|---|---|---|
| V1 | 某条 `tool_calls` 的参数里 | 扫全部消息、解析参数、去重 |
| V2 | `order_id` 字段非空 | 一次判空 |
| V3 | `facts` 里有一条记录 | 查列表内容（能说出查的是哪一版数据） |

第二行看着最省，但它丢了一个信息：**查到的是什么。** `order_id` 非空只说明查过，不说明结果。V3 的 `facts` 保留了内容，同时保留了这个事实"是何时、由哪个工具写进来的"。

第三行的"哪一版数据"是 V3 特有的。如果订单状态在任务过程中变了（比如刚签收），旧的那条事实就不再准确。这正是5.1 的版本号要解决的问题。

### 2.5 判据：要不要进 State

四个问题，按顺序问，第一个答"否"就不用往下：

| # | 问题 | 否的结论 |
|---|---|---|
| 1 | 后续步骤会用到它吗？ | 不进 State（局部变量） |
| 2 | 它需要跨步骤保持一致吗？ | 不进 State（无需持久） |
| 3 | 它来自外部还是模型？ | 决定放"事实"还是"结论" |
| 4 | 它会被改几次？ | 决定 reducer |

第 3 问不只是分类问题。**同一个信息，来自不同来源时可靠性完全不同。** "订单签收 3 天"如果来自工具，是事实；如果来自模型的推断，是结论。混在一起存，下游无法区分该信谁。

第 4 问的答案决定并发策略（第三节）。一个只写一次的字段，根本不需要考虑并发；一个被反复写的字段，要考虑覆盖语义。

### 2.6 State 的读取成本

把状态从历史里抽出来，还有一个容易被忽略的收益：**读取变便宜了。**

| 操作 | V1（从历史推） | V3（读字段） |
|---|---|---|
| 判断"查过订单吗" | 扫全部消息，解析参数 | `bool(state.facts)` |
| 判断"还能再调几次" | 统计 tool_calls 条数 | 读计数器 |
| 判断"结论过期了吗" | 无法判断 | 比较两个版本号 |

第一行的时间复杂度差距在任务长时很明显。但真正重要的是第三行：**V1 根本没有这个能力。** 历史里没有"版本"这个概念，你无法从一个消息列表里推出"我的结论是基于哪一版事实算的"。

这正是"状态不是历史的子集"的准确含义：有些信息只在状态里存在，从历史推不出来。

### 2.7 状态里最容易多出来的字段

三处容易"顺手加"的字段，都该砍掉：

| 字段 | 为什么不该在 State 里 |
|---|---|
| `last_error` | 只在当前步骤有用，下一步就过期 |
| `current_prompt` | 拼出来的东西，是可再生的 |
| `debug_info` | 排查信息，属于 trace |

第一行的"过期"是关键：`last_error` 一旦被写进 State，它就成了一个"一直都在"的事实，后续步骤可能把它当成"这个工具坏了"来推理。

第二行是可再生原则：**能从其他字段推出来的，不要存。** 存了就有一致性问题（两处不同步）。

第三行是分类错误：调试信息属于 trace（3.1），进 State 只会让它被投影给模型。

## 三、放什么不放什么

一个字段该不该进 State，用三个问题筛：

**问题一：它会被后续步骤用到吗？** 不会，就不该进（一次性的中间量）。

**问题二：它需要跨步骤保持一致吗？** 需要，就该进。不需要的（比如某一步用来排序的临时列表）留在局部变量里。

**问题三：它的来源是外部事实还是模型判断？** 两者要分开存——这是第 9 章 3.6 讲的"事实与产物分开"。

| 该进 State | 不该进 State |
|---|---|
| 用户原始意图 | 本轮拼好的提示词 |
| 已确认的事实（订单、政策） | 模型生成的推理过程（除非要审计） |
| 关键结论与它的依据 | 临时的排序/格式化结果 |
| 已尝试过的路径 | 每个 token 的流式输出 |
| 步数、成本计数 | 复制的常量配置 |

第三行值得展开。**"结论"要带着"依据"一起存**：`eligible=True` 这个字段单独存在时，没人知道它是根据什么判的。加一个 `basis: list[str]`（引用哪几条事实），驳回时才能说清"哪条依据不支持这个结论"（第 9 章 2.9）。

### 3.1 与历史并列存的三份

**完整的历史不放进 State，而是与 State 并列。**

```python
from dataclasses import dataclass, field


@dataclass
class V3b:
    """结构化状态：只放需要跨步骤保持一致的内容。"""
    user_intent: str = ""
    facts: list[str] = field(default_factory=list)
    eligible: bool | None = None


@dataclass
class Run:
    state: V3b = field(default_factory=V3b)   # 结构化，几 KB
    messages: list[dict] = field(default_factory=list)   # 历史，可能几百 KB
    trace: list[str] = field(default_factory=list)       # 轨迹，用于归因


if __name__ == "__main__":
    r = Run()
    r.state.facts.append("签收 3 天")
    print(len(r.state.facts), "条事实，", len(r.messages), "条消息")
```

分成三份而不是一份，是因为它们的生命周期不同：`messages` 会被裁剪、`trace` 只在排查时用、`state` 必须完整。混在一起，裁剪就会碰到不该碰的东西。

| 存哪 | 会被裁 | 会被持久化 | 会被回灌给模型 |
|---|---|---|---|
| `state` | 否 | 是 | 部分（拼成摘要） |
| `messages` | 是 | 是（完整版） | 是 |
| `trace` | 否 | 可选 | 否 |

第四列是关键：**State 不是直接塞给模型的，它是拼成一段摘要之后才进去的。** 直接把 dataclass 序列化给模型，会带进一堆它不需要的结构（计数、时间戳）。

### 3.2 State 与提示词的关系

State 是内部结构，提示词是外部接口。两者之间要有一个"投影"：

| 层 | 内容 | 谁看 |
|---|---|---|
| State | 全部字段、版本号、计数 | 代码 |
| 投影 | 一部分字段拼成的一段文字 | 模型 |

投影的规则值得明确写出来，因为它决定了"模型知道什么"：

| 字段类 | 是否投影 | 形态 |
|---|---|---|
| 输入 | 是 | 原样 |
| 事实 | 是 | 摘要 + 必要的结构化字段 |
| 结论 | 视情况 | 若还要重算，就不投影（避免锚定） |
| 计数 | 否 | 只用于守卫与排查 |

第三行最值得琢磨。**把一个待验证的结论投影给模型，它会倾向于沿用。** 这与自评失效（第 9 章 1.1）是同一个机制：多给一条"看起来是结论"的内容，会压低它重新推理的意愿。

所以投影的原则是：**已经确定的给，正在判断的不给。** 上一轮得出的中间结论如果不打算重算，就投影；如果打算让模型重算，就不投影。

### 3.3 State 的序列化形态

State 最终要被持久化（第 11 章）和投影（2.3），所以它的序列化形态要先定下来：

| 形态 | 优点 | 缺点 |
|---|---|---|
| dataclass → dict | 代码里好用 | 字段一改，旧数据读不出 |
| 带 schema 的 JSON | 可校验、可跨版本 | 需要维护 schema |
| 直接存原文 | 无需转换 | 无法查询、无法部分读 |

第二行是生产环境的选择。它的关键在"跨版本"：任务可能跑几个小时，中间升级了代码，旧检查点还要能读。为此需要两条约定：

**只用可选字段。** 新增字段必须有默认值，删字段不能直接删（先标记废弃）。

**带一个 `schema_version`。** 读到旧版本的检查点时，先按旧版本解析，再升级到当前版本。

第三条（直接存原文）在小规模时可行，它的失败发生在第一件想查的事上——"这个任务的 facts 里有几条"，只能读出来自己数。

### 3.4 一个反例：把整份返回塞进 State

常见写法是把工具的完整返回直接存进 `state.data`：

```python
ORDERS = {"A1001": {"status": "已签收", "signed_days_ago": 3, "channel": "app"}}


def get_order(order_id: str) -> dict:
    return ORDERS[order_id]


def store_raw(state: dict, key: str, payload: dict) -> None:
    """反例：把整份工具返回塞进状态。"""
    state.setdefault("data", {})[key] = payload


if __name__ == "__main__":
    s: dict = {}
    store_raw(s, "order", get_order("A1001"))
    print(s["data"]["order"])
```

它的问题不在当下，在后续：

| 问题 | 后果 |
|---|---|
| 无法区分"事实"与"冗余字段" | 投影时全带上，浪费窗口 |
| 无法判断新鲜度 | 不知道它是何时取的 |
| 无法跨版本演进 | 上游接口加字段，下游行为跟着变 |

输出：

```
{'status': '已签收', 'signed_days_ago': 3, 'channel': 'app'}
```

`channel` 这个字段对判定没用，但被一起存下来了，投影时也会一起带上。

第三行值得展开。**把上游的原始结构存进状态，等于把上游的接口形状变成了自己的字段。** 上游加一个字段，你的状态就多一个字段；上游改一个字段名，你的旧检查点就读不出来了（5.5）。

正确做法是**提取需要的字段**，并把"提取自哪个工具的哪次调用"记下来。后者用于追溯，前者用于使用。

### 3.5 状态与工具结果的对账

State 里的事实来自工具。如果工具失败但状态仍被写入，后面所有的推理都建立在"查到了"这个假象上。

| 情况 | 状态里该留什么 |
|---|---|
| 工具成功 | 事实 + 来源 + 时间 |
| 工具报错 | 一条"失败记录"，不是空事实 |
| 工具超时 | 同报错，但标记为"可能已生效"（第 11 章） |

第二行最关键。**"查了但没查到"与"没查"是两种不同的状态。** 如果工具报错时状态什么都不写，下一步会以为还没查过，于是再查一次——这正是第 7 章"换参数打转"的成因之一。

把失败也记成一条事实，后续步骤就能看到"这条路试过了，是这条路不通"。这条记录在投影时也应该带上（3.2），因为模型需要知道它不该再试同一个地方。

### 3.5 State 的大小与投影长度

State 本身很小，但它的投影会变大。三个数需要分开看：

| 量 | 典型大小 | 谁关心 |
|---|---|---|
| State 序列化 | 几 KB | 存储（第 11 章） |
| 投影文本 | 几百字到一两千字 | 窗口预算（第 3 章） |
| 单条事实 | 几十字 | 裁剪（第 7 章） |

第二行是真正影响成本的。**一个 5 KB 的 State 可能投影成 2 千字**——因为投影时会把结构"讲清楚"（字段名、来源、时间）。

第三行的取舍在第 10 章 3 节 2.2 讲过：结构字段给机器，摘要给模型。投影只带摘要，State 里两份都留。

## 四、并发写为什么会丢

第 8 章的 DAG 允许多个分支同时跑。两个分支都要更新状态时，会出问题。

`state.py` 里做了对照：

```python
def overwrite_demo() -> tuple[int, int]:
    """读-改-写：两个分支各读一次旧值，再写回，结果丢一次。"""
    state = {"count": 0}
    barrier = threading.Barrier(2)

    def branch() -> None:
        barrier.wait()                     # 让两个分支同时读到旧值
        current = state["count"]
        time.sleep(0.01)
        state["count"] = current + 1       # 两边都写 1

    ...
```

```
覆盖写：期望 2 条，实际 1 条  丢了
追加写：期望 2 条，实际 2 条  没丢
```

第一行的机制是老问题：**两个分支都读了 0，都写了 1。** 中间那次 `sleep` 模拟了两次读写之间的间隔——在任何有网络调用的场景里，这个间隔是几十毫秒，而不是 0.01 秒。

第二行为什么没丢：`append` 不读旧值。它只做"在末尾加一个元素"，而这个操作在 CPython 里是原子的。

### 4.1 reducer 就是不读旧值

"reducer"这个词在状态管理里就是这个意思：**给出"旧状态 + 本次更新"，产出"新状态"，而不是"读旧状态、算一算、写回去"。**

| 写法 | 是否读旧值 | 并发安全 |
|---|---|---|
| `s.count = s.count + 1` | 是 | 不安全 |
| `s.facts.append(x)` | 否 | 安全（CPython） |
| `s.facts = s.facts + [x]` | 是（读引用） | 不安全 |
| `s = reduce(s, update)` | 否 | 取决于 reduce 实现 |

第三行是个陷阱：它看起来像追加，实际是"读出现有列表、拼一个新列表、把引用换掉"。两个分支同时做，后写的会覆盖前一个的整个列表。

### 4.2 覆盖与累加的选择

同一个字段，选择覆盖还是累加，取决于它的语义：

| 字段语义 | 正确做法 | 并发时的表现 |
|---|---|---|
| 计数（步数、覆盖次数） | 累加 | 需要原子操作或锁 |
| 集合（查过哪些订单） | 累加并去重 | append 安全，去重需在读取时做 |
| 结论（是否可退） | 覆盖 | 后写者赢，需记录覆盖次数 |
| 输入（用户意图） | 只写一次 | 不该有第二次写 |

第三行的"后写者赢"不是 bug，是语义——两个分支得出不同结论时，总得有一个生效。但**它必须被记录下来**，否则你不知道答案在本次任务里变过几次。这就是 `overwrites` 字段的用途。

### 4.3 跨进程的读-改-写

4.1 的三种写法只在单进程内成立。一旦状态存在外部（Redis、数据库），`append` 也不再安全：

| 存储 | 安全操作 | 不安全操作 |
|---|---|---|
| 进程内列表 | `append` | `x = x + [v]` |
| Redis List | `LPUSH` | 读出整个列表再写回 |
| 数据库 | `INSERT` | `SELECT` 后 `UPDATE` |

第二、三行的安全操作都是"由存储自己执行的那一条命令"。危险的是"先读出来、在程序里改、再整体写回去"——与单进程内的道理完全相同，只是慢得多，撞车概率高得多。

数据库里还有一个额外的选择：**用条件写入代替读-改-写。**

```sql
UPDATE runs SET eligible = 1, version = version + 1
WHERE run_id = :id AND version = :expected_version
```

`WHERE version = :expected_version` 这一句是乐观锁。两个分支同时写，只有一个成功，另一个影响 0 行，程序据此重读重试。这比加锁轻，也比"后写者赢"安全。

### 4.4 什么时候真的需要并发写

并发写不是必须解决的问题——它只在"多个分支同时改同一份状态"时才出现。先问一句：这个字段真的需要被两个分支写吗？

| 情况 | 处理 |
|---|---|
| 两个分支写不同字段 | 无需处理 |
| 两个分支写同一字段的"并集" | reduce（累加） |
| 两个分支写同一字段的"结论" | 串行化，或投票 |
| 一个分支读、一个分支写 | 加依赖（第 8 章 6.8） |

第三行值得展开。两个分支对同一件事得出了不同结论，该怎么办？三种做法：

| 做法 | 结果 | 适用 |
|---|---|---|
| 后写者赢 | 取决于完成顺序，不可复现 | 不推荐 |
| 先写者赢 | 忽略了后来者的信息 | 当后来者信息不可靠时 |
| 交给裁判 | 有依据地裁决 | 两个结论都有依据时 |

第三种是第 9 章的裁判在状态层的用法：把两个结论和它们的依据一起交给规则裁判，用判据裁定。这比"谁后写谁赢"可靠，因为它的结果可复现。

### 4.5 一个可并发的更新函数

把4.1 的三种写法落成代码，差别一目了然：

```python
import threading


def update_unsafe(state: dict, key: str, value: int) -> None:
    """读-改-写：并发时会丢。"""
    current = state.get(key, 0)
    state[key] = current + value


def update_safe(state: dict, key: str, value: int, lock: threading.Lock) -> None:
    """加锁：不丢，但串行化。"""
    with lock:
        state[key] = state.get(key, 0) + value


def update_reduce(state: dict, key: str, value: int) -> None:
    """累加式：交给容器自己完成，不读旧值。"""
    state.setdefault(key, []).append(value)


if __name__ == "__main__":
    s: dict = {}
    for _ in range(3):
        update_reduce(s, "hits", 1)
    print("记录：", s["hits"], "合计", sum(s["hits"]))
```

输出：

```
记录： [1, 1, 1] 合计 3
```

第三行的关键是：`update_reduce` 不计算合计，它只记录每一次发生。**合计在读取时才做**（`sum`），因此写的时候不需要知道旧值，也就没有并发问题。

这个取舍有一个代价：**存储会变大。** 记录每一次发生，比只存一个总数占空间。对计数类字段（步数、token），用加锁更省；对"发生过什么"类字段（查过哪些订单），累加式更合适。

一行判断：**这个字段将来需要被"数"还是需要被"看内容"。** 只需要数，就加锁 + 整数；需要看内容，就记录每次发生。

### 4.6 单线程也有覆盖问题

覆盖写不是并发才有的问题。异步任务里同样会发生：

| 场景 | 机制 | 后果 |
|---|---|---|
| 两个 `await` 之间 | 中间让出控制权，另一个协程改了状态 | 后写覆盖前写 |
| 回调链 | 回调触发顺序不定 | 结论取决于时序 |
| 定时刷新 | 定时器和主流程都写同一字段 | 随机覆盖 |

第一行最隐蔽：`await` 之前的读和之后的写，中间可能隔了几十毫秒的 IO。**这与线程里 `sleep` 的窗口完全一样**，只是没有线程这个词提醒你。

判断方法：**列出所有"读某个状态字段 → 等一个 IO → 写回该字段"的路径。** 每一条都是一个潜在覆盖点，无论它跑在线程、协程还是回调里。

修法与 4.1 的三条一样：能累加就累加，不能累加就加锁/串行化。

## 五、一个字段的完整生命周期

### 5.1 一个最小的状态更新器

把"字段分类 + 版本号 + 覆盖记录"合起来，一个可用的更新器是：

```python
from dataclasses import dataclass, field


@dataclass
class State:
    facts: list[str] = field(default_factory=list)
    facts_version: int = 0
    conclusions: dict[str, tuple[object, int]] = field(default_factory=dict)
    overwrites: dict[str, int] = field(default_factory=dict)

    def add_fact(self, fact: str) -> None:
        self.facts.append(fact)
        self.facts_version += 1          # 事实一变，所有结论都可能过期

    def set_conclusion(self, key: str, value: object) -> None:
        prev = self.conclusions.get(key)
        # 第一次写不算覆盖；之后每次"值改变"才算一次改主意
        if prev is not None:
            self.overwrites[key] = self.overwrites.get(key, 0) + 1
        self.conclusions[key] = (value, self.facts_version)

    def get_conclusion(self, key: str) -> object | None:
        entry = self.conclusions.get(key)
        if entry is None:
            return None
        value, version = entry
        if version < self.facts_version:
            return None                  # 过期，视同没有
        return value


if __name__ == "__main__":
    s = State()
    s.add_fact("签收 3 天")
    s.set_conclusion("eligible", True)
    print("刚写入：", s.get_conclusion("eligible"))

    s.add_fact("政策窗口从 7 天改为 2 天")
    print("事实更新后：", s.get_conclusion("eligible"))

    s.set_conclusion("eligible", False)
    s.set_conclusion("eligible", True)
    print("改了两次：", s.get_conclusion("eligible"), "覆盖次数", s.overwrites)
```

输出：

```
刚写入： True
事实更新后： None
改了两次： True 覆盖次数 2
```

三个要点：

**事实一变，结论全部失效。** `facts_version` 一加，所有 `version < facts_version` 的结论都读不到。这是粗糙但正确的做法——它假设任何新事实都可能影响任何结论。

**覆盖次数只统计"写过之后又写"的次数。** 第一次写不算。示例里先写 True、再写 False、再写 True，之后两次各算一次，所以是 2。这个数字的意义是"结论被重复设置的次数"——它偏高说明这一轮在反复下结论，对应第 9 章 1.3 讲的震荡。

**失效等于"没有"。** `get_conclusion` 返回 `None`，调用方必须重新计算。这比返回一个旧值安全得多。


把上面的内容合起来，一个字段从出生到使用有五个时刻，每个时刻要回答一个问题：

| 时刻 | 问题 | 谁负责 |
|---|---|---|
| 声明 | 它属于哪一类（输入/事实/结论/计数） | 设计时 |
| 首次写 | 谁写的、什么时候 | 调用方或工具 |
| 更新 | 覆盖还是累加、要不要去重 | reducer |
| 读取 | 谁读、读到的可能是哪个版本 | 消费方 |
| 失效 | 什么情况下它不再有效 | 设计时 |

第五行是最容易被漏掉的。**"结论"会失效**：查到一个新的订单状态之后，之前算出的"是否可退"就不再成立。没有失效机制的状态，会让后续步骤基于过期的结论继续推理。

最简单可行的失效方式是**版本号**：

```python
from dataclasses import dataclass


@dataclass
class Versioned:
    eligible: bool | None = None
    eligible_version: int = 0
    facts_version: int = 0        # 每次写 facts 时 +1

    def conclusion_is_stale(self) -> bool:
        """结论比事实旧，就该重算。"""
        return self.eligible_version < self.facts_version
```

推理"结论是否过期"只要一行比较。这比"记得手动清空结论"可靠得多——后者依赖每个写 facts 的地方都记得清空，而漏一处就是一个静默的错误。

### 5.2 字段命名约定

命名能提前暴露字段分类的错误。三条约定：

| 约定 | 例子 | 拦住的错误 |
|---|---|---|
| 事实用复数或前缀 | `facts`, `fetched_orders` | 不会写成单值覆盖 |
| 结论用判断句式 | `eligible`, `should_retry` | 一眼看出是"结论" |
| 计数用 `n_` 或 `_count` | `n_steps`, `overwrites` | 不会被当成内容字段 |

第二条特别有用：**一个叫 `status` 的字段，你无法从名字看出它是"查到的事实"还是"算出的结论"。** 前者只增，后者可覆盖，并发策略完全不同。改成 `fetched_status` 与 `derived_status`，分类就写在名字里了。

命名不能替代分类，但它能让分类错误在代码评审时被看见——而分类错误的后果往往在并发时才暴露，那时已经很难改。

### 5.3 状态迁移的状态图

一个任务的状态不是一堆字段的集合，它有"阶段"。把阶段画出来，很多边界问题会自动显现：

```
初始化 → 取数中 → 判定中 → 已判定 → (修复中 → 已判定)* → 交付
              ↑                          |
              └──────── 重规划 ───────────┘
```

图里有两处值得注意：

**第一，"修复中"是回边，必须带上限。** 这就是第 9 章 3.5 的"同一产物最多修两次"。没有上限的回边，就是第 9 章 1.3 讲的反复震荡。

**第二，重规划回到"取数中"而不是"初始化"。** 已经取到的数据仍然有效（第 9 章 3.6），所以不该回到最初。

阶段信息本身也该进 State，一个 `phase` 字段。它有两个用途：**决定投影什么**（不同阶段给模型的摘要不同）、**决定恢复从哪继续**（第 11 章）。

### 5.4 一次任务里的状态演进

把 V3 用在一个两步任务上，逐步看字段怎么变：

| 步 | 动作 | facts | facts_version | conclusions |
|---|---|---|---|---|
| 0 | 开始 | `[]` | 0 | `{}` |
| 1 | 查订单 | `["签收 3 天"]` | 1 | `{}` |
| 2 | 查政策 | `["签收 3 天", "窗口 7 天"]` | 2 | `{}` |
| 3 | 判定 | 同上 | 2 | `{"eligible": (True, 2)}` |
| 4 | 重新查订单（状态变了） | `[..., "签收 4 天"]` | 3 | `{"eligible": (True, 2)}` ← 过期 |

第四行的关键：`eligible` 的版本是 2，而 `facts_version` 已是 3，所以第 4 行之后 `get_conclusion("eligible")` 返回 `None`。**判定会自动失效，不需要任何人记得清空。**

这正是版本号的价值。相比之下，如果靠"写完事实后手动清空结论"，这张表里第 4 行就需要多一步操作，而漏掉那一步不会报错——只会让答案基于旧数据。

### 5.5 schema 演进

字段会变。变的时候有三件事必须同时做：

| 变更 | 必须做 |
|---|---|
| 新增字段 | 给默认值，不能是必填 |
| 删除字段 | 先标记废弃，读时忽略，写时不写 |
| 改语义 | 换字段名，而不是改现有字段的含义 |

第三条最重要。**"改语义但保留名字"是最危险的一种变更**：旧的检查点里那个字段是"签收天数"，新代码里它变成"距离窗口剩余天数"，读出来的值完全不是一回事，而且不会报错。

改名字的代价是所有读写处都要改；不改名字的代价是历史上所有数据的语义被悄悄改写。后者的问题在出事故那天才显现。

### 5.6 状态与并发的交叉检查

把第四、五两节的结论交叉一次，能得到一张"什么字段该用什么机制"的表：

| 字段类别 | 写频率 | 并发安全做法 | 失效判断 |
|---|---|---|---|
| 输入 | 1 | 无需处理 | 不失效 |
| 事实 | 多次、只增 | `append` 或存储层原子命令 | 只增，不失效 |
| 结论 | 多次、覆盖 | 串行化，或裁判裁定 | 版本号比较 |
| 计数 | 多次 | 锁，或存储层自增 | 不失效 |

四行的差异全部来自前三节：写频率决定要不要并发安全，是否只增决定要不要失效判断。

一张表能省掉很多讨论：**讨论"这个字段怎么存"之前，先把它归到这一行。** 归类错了，后面的方案再精细也没用。

### 5.7 为什么结论要单独存，不放在 messages 里

一个常见的省事做法是：结论直接写在回答里，不单独存字段。它失败在两个地方：

| 场景 | 结论在 messages 里 | 结论在字段里 |
|---|---|---|
| 需要重算 | 要重新解析上一轮的回答 | 直接覆盖 |
| 需要判断失效 | 无法判断 | 版本号比较 |
| 需要多个结论共存 | 散在各轮回答里 | 一个 dict |

第三行最能说明问题。一个任务里可能同时有"是否可退"和"是否需要补材料"两个结论，它们分别在不同轮次得出。**放在 messages 里，它们是两段自然语言；放在字段里，它们是两个可比较的值。**

这也是 3.2 投影原则的来源：结论要"能重算就别投影"。如果结论只存在于 messages 里，它总会被投影（因为历史总是全带上的），于是模型总在沿用旧结论。

### 5.8 一个完整的 State 定义

把本章所有要求合起来，一个可用的定义长这样：

```python
from dataclasses import dataclass, field
from typing import Any


@dataclass
class Facts:
    """一条事实：内容 + 来源 + 时间戳，便于追溯与判断新鲜度。"""
    key: str
    value: Any
    source: str          # 哪个工具、哪次调用
    at: float            # 单调时间或 ISO 字符串


@dataclass
class TaskState:
    # 输入（只写一次）
    intent: str
    run_id: str

    # 事实（只增）
    facts: list[Facts] = field(default_factory=list)

    # 结论（可覆盖，带版本）
    conclusions: dict[str, tuple[Any, int]] = field(default_factory=dict)

    # 计数（只增）
    n_steps: int = 0
    n_failures: int = 0

    def fact(self, key: str, default: Any = None) -> Any:
        """取最新一条同名事实。"""
        for f in reversed(self.facts):
            if f.key == key:
                return f.value
        return default

    def version(self) -> int:
        return len(self.facts)


if __name__ == "__main__":
    s = TaskState(intent="A1001 能退吗", run_id="r-1")
    s.facts.append(Facts("signed_days", 3, "get_order", 0.0))
    s.facts.append(Facts("window_days", 7, "get_policy", 0.0))
    s.conclusions["eligible"] = (True, s.version())
    print(s.fact("signed_days"), s.fact("window_days"), s.conclusions)
```

输出：

```
3 7 {'eligible': (True, 2)}
```

四个设计点：**事实带来源与时间**（可追溯，也可判断新鲜度）、**`fact()` 取最新一条**（同名事实可以多次写入，最新的赢）、**版本用 `len(facts)`**（省一个字段，写入时自增）、**结论存元组**（值 + 当时的版本）。

第三点是本章最省事的一个技巧：**事实只增不减，所以它的条数天然就是一个单调版本号。** 不需要单独维护 `facts_version`，也就不会出现"忘了自增"的 bug。

### 5.10 状态与幂等的交界

第 11 章讲幂等键。它的一个输入恰好来自 State：

| 幂等键的组成 | 从哪来 |
|---|---|
| 业务对象 id | `facts` / `intent` |
| 动作名 | 调用的工具 |
| 区分维度 | 版本或期间 |

第二、三行的组合在代码里体现为"用 State 的字段拼键"。这意味着**State 与检查点必须同时落盘**——否则恢复时拼不出同一个键，去重就失效。

这也解释了为什么第 11 章的检查点要存完整的 State：**它不是"顺便存的"，而是幂等的前提。**

## 六、这一层的失效模式

**第一，把 messages 当状态。** 第 1.1 讲的三种开销，在任务超过十几步之后都会显现。

**第二，字段过细。** 一个字段只被用过一次、只在一处读，它就是变量而不是状态。字段越细，并发写的机会越多，reducer 也越多。

**第三，用覆盖表达"累加"。** `s.facts = s.facts + [x]` 这种写法在多线程下会丢，在单线程下也不会暴露——它只在并发时才坏，所以测试要专门构造并发。

**第四，结论不带依据。** 被驳回时说不清为什么，也没法判断是哪条依据变了导致结论失效。

**第五，没有版本号。** 状态改过之后，之前的结论还在用。表现为"新数据进来了，答案没变"。

### 6.1 一个真实的丢数据场景

上面的 `overwrite_demo` 用线程模拟，看起来像玩具。换成真实的并发编排（第 8 章的 `run_dag`），同样的结构是：

| 代码 | 问题 |
|---|---|
| `state.summary = branch_a_result` | 覆盖，A 的结论丢了 |
| `state.summary = merge(state.summary, b_result)` | 仍是读-改-写，可能丢 |
| `state.merge("summary", b_result)` | reducer 内部完成，安全 |

第三行的 `merge` 必须是"把两个结果合成一个"的函数，而不是"把后一个赋给前一个"。合成函数是业务相关的：两段摘要怎么合并？两个结论怎么裁定？这需要写，不能自动生成。

**这也是并发写最容易被低估的地方：真正的难点不在加锁，而在"如何定义合并"。** 加锁只能保证不丢，保证不了合并得对。

### 6.2 一次并发写的检查清单

在把状态交给并发分支之前，逐条过一遍：

| 检查 | 通过标准 |
|---|---|
| 每个字段的写入者唯一吗？ | 唯一，或有 reducer |
| 有读-改-写的写法吗？ | 没有 |
| 结论有过期判断吗？ | 有版本号 |
| 合并语义定义了吗？ | 有明确的合成函数 |
| 丢数据能被发现吗？ | 计数或断言能证明 |

第五行最容易被忽略。`overwrite_demo` 之所以能发现问题，是因为它把"期望 2 条"写在了代码里。**没有这个期望值，丢一条数据是无声的。**

所以每个可并发的状态更新都该配一个"应该有几次"的断言，至少在测试里。

### 6.3 一个可复现的验证测试

状态问题最难的地方是"线上偶尔出现"。为此需要一个能稳定复现的测试：

| 要素 | 做法 |
|---|---|
| 构造并发 | 用 `threading.Barrier` 让两个分支同时起跑 |
| 放大窗口 | 在两个操作之间插入短暂延时 |
| 断言数量 | 断言"应该有几条"，而不是"有没有" |
| 重复多次 | 单次通过不代表安全 |

第三条是核心：**没有"应该几条"这个期望值，丢数据是无声的。** `state.py` 里 `overwrite_demo()` 返回 `(实际, 期望)`，就是为了让这个断言写在测试里。

第四行也不可省。并发问题往往不是每次都发生，跑一次通过说明不了什么；跑一百次通过才有说服力。

### 6.4 状态相关的三类线上问题

状态写错之后，症状往往不在状态本身，而在很远的地方。三类最常见：

| 症状 | 真实原因 | 排查线索 |
|---|---|---|
| "同一个问题两次答案不同" | 结论被覆盖，两次读到不同版本 | 看 `overwrites` 计数 |
| "改完还是旧的" | 结论过期未重算 | 比 `version` 与 `facts_version` |
| "数据丢了" | 读-改-写撞车 | 看期望条数与实际条数 |

第一行的排查线索是最有用的：`overwrites` 大于 0 且产物在两个版本之间反复，基本就是"两个分支给了不同结论，后写者赢"。

第二行的判断可以写成一行：`conclusion_version < facts_version` 就是过期。它应该是一个断言，而不是一个需要人去发现的疑点。

### 6.5 状态层的三个断言

生产代码里值得常驻的三个检查，都很便宜：

| 断言 | 检查什么 | 触发时的怀疑对象 |
|---|---|---|
| `len(facts) > 0` | 有数据才能判定 | 取数阶段失败了 |
| `conclusion_version == facts_version` | 结论是新算的 | 忘了重算 |
| `overwrites <= 1` | 结论没有反复改 | 两个分支在争 |

第三行的阈值不是绝对的：一个任务里改一次主意是正常的，改三次以上说明判据或数据在变。把它当告警而不是错误。

三个断言都写在"交付之前"那个位置最合适（第 9 章 5.5 的"关键步之后"）。放在每一步会太吵，放在交付之后就没用了。

### 6.6 状态与第 7 章守卫的关系

守卫（第 7 章）看的是过程信号，状态看的是内容。两者要共享一份计数，否则会出现"守卫停了但状态里看不出为什么"。

| 数据 | 谁产生 | 谁消费 |
|---|---|---|
| 步数 | 循环 | 守卫、状态（计数类字段） |
| 调用指纹 | 循环 | 守卫 |
| 事实条数 | 工具结果 | 状态、守卫（判断有没有新信息） |
| 覆盖次数 | 状态 | 交付前的断言（6.5） |

第三行是新增的：**守卫判断"有没有新信息"，最好的依据是状态里事实条数有没有增加**，而不是比对回灌字符串（第 7 章 3.3 讲的哈希失效问题）。状态在这儿成了守卫的一个更可靠的信号源。

第四行反过来：状态用守卫的数据做断言。两者不是两个独立模块，是同一份运行记录的两个视图。

### 6.7 State 与检查点的字段差异

第 11 章的检查点里有一部分不是 State：进度、pending、版本号。分清它们属于谁：

| 字段 | 属于 | 为什么 |
|---|---|---|
| `intent` / `facts` / `conclusions` | State | 任务内容 |
| `step` | 运行控制 | 与任务内容无关 |
| `pending_side_effect` | 运行控制 | 为了恢复，不是为了推理 |
| `schema_version` | 存储 | 为了读取，不是为了推理 |

**判断方法：这个字段会不会被投影给模型（第 10 章 3.2）。** 会，属于 State；不会，属于运行控制。

混在一起的后果是投影时把 `step`、`pending` 也带进去，模型看到"我在第 3 步"，可能因此改变行为——这类信息对推理没有帮助，只会干扰。

### 5.9 State 的初始化

任务开始时 State 长什么样，决定了很多后续行为。三件事要定：

| 事 | 做法 |
|---|---|
| 必填字段 | 没有默认值，缺了就报错 |
| 可选字段 | 给 `None`，与"有值但为空"区分 |
| 计数器 | 全从 0 开始，包括 `overwrites` |

第二行是 Python 里常见的坑：`None` 与 `""`、`[]` 语义不同。`facts=[]` 表示"还没查"，`facts=None` 表示"这个任务不做事实收集"。混用会让"查过但为空"与"没查"无法区分——第 11 章 3.5 讲的"工具报错也要记一条"依赖这个区分。

---

### 6.5 状态字段与提示词六要素的对应

第 4 章的六要素里，有三项天然属于状态：

| 六要素 | 是否进 State | 理由 |
|---|---|---|
| 角色 | 否 | 常量，放系统消息 |
| 任务 | 是（`intent`） | 每轮要引用 |
| 背景 | 部分（`facts`） | 查到的事实 |
| 输入数据 | 是（投影时拼） | 本轮数据 |
| 输出格式 | 否 | 常量 |
| 约束 | 部分（`phase` 决定启用哪些） | 随阶段变 |

第六行是一个容易忽略的用法：**约束是随阶段变的。** "取数阶段不要下结论"与"判定阶段必须给结论"是两条相反的约束，靠 `phase` 字段切换。

### 6.8 状态与评测的关系

第 9 章说过"反思用规则裁判可直接当评测判据"。State 让这件事更可行：

| 判据需要的 | State 提供 |
|---|---|
| 事实是否完整 | `len(facts)` |
| 结论是否过期 | 版本比较 |
| 是否有反复 | `overwrites` |
| 走了几步 | `n_steps` |

这四项都不需要读产物文本，只需要读状态。**它们让"轨迹评测"变成一次字段检查**，成本远低于重跑一遍。

第 31 章讲的轨迹判据（结果/轨迹/稳定/成本）里，"轨迹"那一层的主要输入就是这些字段。

## 七、边界

**第一，State 不解决持久化。** 它是内存里的结构，怎么存盘是第 11 章的内容。

**第二，State 不是数据库。** 不要把它做成一张表——放进去的字段应该都在本轮任务里被用到。需要长期保存的东西（用户偏好、历史记录）属于长期记忆，第 18 章。

**第三，并发安全在单进程内可以靠语言特性（第四节 4.1 的 `append`），跨进程不行。** 多进程共用状态时要外部存储，那时 reducer 要换成带条件的写入（第 11 章的幂等）。

**第四，字段分类不是一次定的。** 一个开始时当作"结论"的字段，后来发现它只增不减，就该改成"事实"。**分类错了的表现是：这个字段总是在被覆盖，而覆盖次数一直是 1。**

### 7.1 状态设计的检查清单

交付前逐条过：

| 检查 | 通过标准 |
|---|---|
| 每个字段能归到四类之一吗 | 能，且写频率与类别一致 |
| 有字段既存事实又存结论吗 | 没有 |
| 结论带依据吗 | 带，或能追到某条事实 |
| 结论有过期判断吗 | 有，且是自动的 |
| 可并发字段有 reducer 吗 | 有，且不读旧值 |
| 失败也会被记成一条记录吗 | 会 |
| 状态能独立于 messages 恢复吗 | 能 |

最后一行是终极检验：**把 messages 全部删掉，只用 state 能不能说清"任务做到哪了"。** 能，说明状态是完整的；不能，说明还有信息藏在历史里。

### 7.2 一句话总结这一章

**State 是"这一轮任务当前知道什么"的结构化快照。** 它要能被查询、能被裁剪（不影响它自己）、能被恢复、能被并发安全地更新——四条都满足，才配叫状态。

## 这一章建立的 5 件事

1. State 不等于聊天记录：从历史推断状态每次都要扫全量、结果依赖历史完整性、口径散落各处。
2. 字段按生命周期分四类：输入（1 次）、事实（只增）、结论（可覆盖）、计数（只增），四类的并发安全性不同。
3. 并发写丢数据只发生在"读-改-写"上。`append` 安全，`s.x = s.x + [v]` 不安全。
4. 结论要带依据（`basis`），并且要能判断过期（版本号比较），否则新数据进来后旧结论还在用。
5. State 与 messages、trace 并列存，不混存：它们的裁剪策略、持久化策略、回灌方式都不同。
