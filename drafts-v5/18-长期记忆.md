## 一、跨会话的东西放哪

第 17 章的记忆槽只解决一次会话：会话结束，槽就没了。下一通电话进来，系统不认识这个人。

需要跨会话的东西有三类，它们的共同点只是"要活过会话"，别的都不一样：

| 要记住的 | 一个例子 | 什么时候用得上 |
|---|---|---|
| 关于这个人/组织的稳定事实 | 偏好工作日 9–18 点联系 | 排期、发送通道选择 |
| 具体某一次发生过什么 | 上次因瑕疵全额退款并补了 10 元券 | 用户说"上次也是这样" |
| 我们自己怎么做事 | 瑕疵订单先要照片，再走质量问题通道 | 需要按流程走时 |

这三类不合并，因为它们**答案的寿命不同**：第一条能存一年，第二条只对类似情形有效，第三条是团队的规则、改一次影响所有人。

`memory.py` 里三层就是一个 `kind` 字段：

```python
@dataclass
class Record:
    kind: str                 # semantic / episodic / procedural
    tenant: str
    key: str
    text: str
    created_at: float
    deleted: bool = False
    source: str = ""          # 来源：哪次会话、哪份文档
```

`source` 不是可选项。**一条记不住来源的记忆，出问题时无法判断该不该改、改哪里。**

### 1.1 三层的召回触发条件不同

```
=== 2. 三条不同的问题，各自该召回哪一层 ===
  上班时间方便联系         -> semantic    用户偏好工作日 9-18 点联系
  上次这种情况是怎么处理的     -> episodic    上次退款因商品有瑕疵，全额退款并补了 10 元券
  瑕疵订单退款怎么走        -> procedural  瑕疵订单先要照片，再走质量问题通道，运费商家承担
```

三行对应三种触发：

| 层 | 触发词形态 | 召回几条 |
|---|---|---|
| 语义 | "一般""平时""方便""偏好" | 1–3 条 |
| 情景 | "上次""以前""也是这样""又来" | 3–5 条，按时间倒序 |
| 程序 | "怎么走""按什么流程""规定" | 1 条（当前版本） |

第三行的"1 条"是硬性要求，不是优化：**程序层同时召回两个版本的流程时，模型会把它们混起来执行。** 这与第 12 章 7.3 的"加载失控"是同一个故障，只是对象从 Skill 换成了记忆。

### 1.2 写入时机

三层里最容易写错的是语义层。程序层是人工维护的（等同于规则），情景层跟着会话结束写一条，语义层则要从对话里**抽取**。

抽取有一个绕不开的问题：同一个事实会在不同轮次被反复提到。`Deduper` 演示了后果：

```
=== 6. 同一批抽取结果，去重前后 ===
  4 条抽取结果，去重后留下 2 条：['用户偏好电话联系', '用户住杭州']
  不去重时，重复条目会占满召回前几名（与第 15 章 3.2 的近重复块同源）
```

不去重时，召回前 3 条可能全是"用户偏好电话联系"的三个变体，真正有用的那条排第 4。**这与第 15 章 3.2 的近重复块是同一个现象**，处理方法也一样：入库时去重，而不是在召回时想办法。

一个可用的键设计：语义记录的键由（实体, 属性）组成，例如 `user:123/preferred_contact_time`。同一键再写一次是**覆盖**，不是新增。这样"用户改了偏好"会被正确表达成一次更新，而不是两条互相矛盾的记录。

### 1.3 三层的物理形态

示例把三层放在一个 `dict` 里，用一个 `kind` 字段区分。生产里通常不是：

| 层 | 常见存储 | 检索方式 |
|---|---|---|
| 语义 | 关系库或 KV，按 (tenant, entity, attr) 索引 | 精确键查 |
| 情景 | 文档库或向量库，带时间与情形标签 | 过滤 + 相似度 |
| 程序 | 文件（`SKILL.md` 一类）或配置中心 | 按名字取当前版本 |

第二行与第一行差别最大：**语义层不需要向量检索**——你知道要查哪个实体的哪个属性，键查就够了。用向量检索去查"用户偏好"，只会引入"看起来相近的别的偏好"这类噪声。

第三行决定了程序层的更新流程与代码发版一样需要评审，这也是 5.1 里把它排在最后上线的理由。

**三层混用同一种存储与检索方式时，通常表现为"语义层召回不稳定"**：同一个用户问同一个问题，两次召回到不同的偏好——向量检索的近似性在语义层是纯负担。

## 二、一层一层看

### 2.1 语义层

存的是"关于实体的稳定属性"。三类内容要分开：

| 内容 | 例子 | 更新方式 |
|---|---|---|
| 用户说的 | "我一般上午方便" | 覆盖，带时间戳 |
| 系统观察到的 | "过去三次都在上午回复" | 累加，带计数 |
| 外部获得 | "CRM 里登记的偏好邮件" | 覆盖，带来源 |

三者的冲突处理方式不同：第一类用户说了算，第二类只是统计、不能压过用户自述，第三类要与前两类比对、不一致时提示人工确认。

**第二类不能直接当事实用**，原因与第 17 章 3.1 相同：它是推断。把"过去三次都在上午"渲染成"用户偏好上午"，就是一次未经确认的归纳。

### 2.2 情景层

存的是"某一次的经历"，与语义层最大的区别是**它带具体情形**：不只是"发生过退款"，而是"这次退款是因为瑕疵、金额全退、额外补了券"。

检索情景层时，关键不是"这个用户以前做过什么"，而是"类似的情形以前怎么处理过"。所以情景层的召回通常要两段：先按用户过滤，再按情形相似度排序。

一个实际的坑：情景层越用越大。一个老用户可能有几十条记录，全部召回既超预算又噪声大。可用的做法是只召回**最近 N 条 + 相似度最高的 M 条**，两者取并集。前一半保时间上的连续性，后一半保情形上的相关性。

### 2.3 程序层

存的是"怎么做"。它的值与第 12 章的 Skill 高度重叠——**流程就是 Skill 的正文**。两者的分工：

| | Skill | 程序记忆 |
|---|---|---|
| 谁写 | 团队 | 团队，但可从成功会话沉淀 |
| 加载 | 按需（三级） | 与 Skill 相同 |
| 版本 | 有 | 必须有 |

第三行是程序层与 Skill 唯一的实质区别，也是它必须被单独看的原因：**程序记忆会被系统自己写入时，版本就是安全的唯一保障。** 一个从三次成功会话里"学会"的流程如果直接覆盖旧版本，出问题时无法回退。

一个可用的约束：程序层的写入只允许"新增版本 + 标记生效"，不允许原地修改。这条约束在代码里就是"键里带版本号"，与第 11 章的 checkpoint 是同一个思路。

### 2.4 三层各自的写入成本

三层写入的时间点不同，成本也不同：

| 层 | 什么时候写 | 成本 |
|---|---|---|
| 语义 | 每一轮之后抽取一次 | 一次模型调用（抽取） |
| 情景 | 会话结束写一条 | 一次模型调用（摘要）+ 一次写 |
| 程序 | 人工维护，或成功会话后沉淀 | 人工或一次审核 |

第一行是长期记忆主要的成本来源。一个十轮的会话要抽十次，每次一次短调用——**这笔账在第 31 章的成本瀑布里属于"与业务无关的固定开销"，容易被漏掉。**

一个可行的压法：抽取从"每轮一次"改成"会话结束一次"，一次看完十轮，抽出所有事实。代价是会话中途无法用到刚抽出的事实——而这一点在多数场景里不影响，因为同一轮对话里的信息本来就在上下文里。

### 2.5 三层在一轮里的装配

三层召回之后都要进上下文，各自的进法与预算不同：

| 层 | 进上下文的形式 | 通常条数与长度 |
|---|---|---|
| 语义 | 一条短句，附来源与更新时间 | 1–2 条，几十字符 |
| 情景 | 一条摘要，附情形与结论 | 1–3 条，每条一两百字符 |
| 程序 | 当前版本的流程正文 | 1 条，长度由流程决定 |

第三行的长度是三层里最大的，也是为什么程序层要与 Skill 共用三级加载（第 12 章）：**它只在需要按流程走时才加载，不常驻。**

第二行的"附情形"是必须的：只给"上次全额退了"，模型会以为这次也能全额退；给出"上次因瑕疵全额退了"，模型才能判断这次的情形是否相同。

### 2.6 三层的检索方式不同，别用一个索引包打天下

三层的召回方式差别很大，用一个向量索引统一处理会在两个方向上出错：

| 层 | 召回方式 | 用向量索引的后果 |
|---|---|---|
| 语义 | 精确键查（实体 + 属性） | 召回"相近但不同"的属性，例如把"偏好渠道"当成"偏好时间" |
| 情景 | 过滤（用户、时间）+ 相似度 | 可用，噪声大 |
| 程序 | 按名字取当前版本 | 可能召回过期版本 |

第一行的后果最典型：用户问"什么时候方便联系"，向量检索召回到了"偏好邮件联系"——都是"偏好"，语义相近，但答非所问。**语义层需要的是精确，不是相似。**

第三行的后果最严重：召回两个版本的流程，模型会把它们混起来执行（1.1 的结论）。

一个例外情形值得记：**情景层与语义层可以共用一个向量索引**，只要用 `kind` 做过滤。它们的差别在"要不要情形的相似度"，而不在"要不要相似度"本身。真正不能混的是程序层——它的召回条件从来不是相似度，而是"叫什么名字、哪个版本"。

## 三、租户隔离

多租户系统里，记忆的键必须带租户。这一条听起来是常识，但它的失效方式是"不报错、结果看起来正常"：

```
=== 5. 一个容易做错的地方：键里不带租户 ===
  按 key 查（不带租户）-> ['A 用户偏好电话', 'B 用户偏好邮件']  <- 两个租户的数据混在一起
  按 (tenant, key) 查   -> ['A 用户偏好电话']
```

第一行的问题不是"查到了两条"，而是**其中一条本来不该被这个租户看到**。如果召回后会进入上下文，A 租户的模型就会读到 B 租户的偏好。

### 3.1 隔离要做在几层

| 层 | 做法 | 漏了会怎样 |
|---|---|---|
| 键/主键 | 键里带 tenant | 同名键互相覆盖 |
| 查询条件 | 每条查询强制带 tenant | 召回跨租户 |
| 向量索引 | 分区或过滤必须在检索前（第 15 章 3.4） | 候选被另一租户占满 |
| 缓存 | 缓存键带 tenant | 命中别人的结果 |
| 日志与导出 | 导出也按 tenant 分 | 排障时看到别人的数据 |

第二行是代码里最容易漏的：写代码时 `get(key)` 与 `get(tenant, key)` 只差一个参数，而两种写法都不会报错。

第四行最隐蔽：记忆的召回结果经常被缓存（第 31 章的语义缓存），**缓存键不带租户时，隔离在最外层被绕开**——所有内层的正确性都被浪费。

### 3.2 一条可执行的检查

不用等到出事，可以用一条断言在每个查询处兜底：

```python
def recall_checked(records: list[Record], tenant: str) -> list[Record]:
    """召回结果的最后一道检查。任何一条不属于本租户，直接报错而不是过滤。"""
    for r in records:
        if r.tenant != tenant:
            raise PermissionError(f"跨租户召回：期望 {tenant}，实际 {r.tenant}")
    return records
```

"报错而不是过滤"是刻意的：过滤会让系统继续正常工作，问题被掩盖到下一次；报错会在测试环境就暴露出来。**隔离类的问题必须让它吵，不能让它静。**

这条检查的成本是每条记录一次比较，在召回条数有限时可以接受。

### 3.3 隔离与检索的先后

第 15 章 3.4 讲过"过滤必须在检索前"，在多租户记忆里这条规则有一个更严重的版本：

| 做法 | 结果 |
|---|---|
| 全库取前 200，再按 tenant 过滤 | 大租户的结果占满前 200，小租户什么都拿不到 |
| 按 tenant 分区检索 | 每个租户在自己的分区里取前 k |

第一行的坏处不只是"小租户效果差"，而是**小租户的召回会被完全清空**：前 200 名里没有它的一条记录，过滤后剩零条，系统表现为"这个用户没有任何历史"，而他明明有。

这个现象在多租户系统上线初期经常被当成"冷启动问题"，实际是隔离做错了位置。判断方法很直接：**统计每个租户的召回条数分布。** 分布严重偏斜（有的租户恒为 0）时，就不是冷启动。

### 3.4 隔离失败之后怎么补救

隔离一旦漏过，补救的重点不是"改代码"，而是"判断影响面"。三步：

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 | 找出哪些请求读过跨租户数据 | 日志里租户字段与记录字段不一致的请求 |
| 2 | 判断有没有进到回答里 | 上下文快照里是否有别人的记录 |
| 3 | 修复 + 补检查 | 3.2 的断言，加在存储层 |

第一步依赖日志里有租户字段。**没有这个字段时，影响面无法确定**——只能假设全部受影响，而"全部"意味着要给所有租户发通知。

第二步依赖第 14 章 2.3 的"检索中间结果落盘"。没有它时，只能看最终回答里有没有出现别人的信息，而模型改写之后的文本很难判断来源。

这两条要求说明一件事：**隔离问题的事后取证能力，取决于平时记了什么。** 与性能优化不同，它不能临时加。

## 四、软删除

删除记忆有两种做法，选错了在合规检查时会卡住：

| 做法 | 存储里还剩什么 | 能审计吗 |
|---|---|---|
| 硬删除 | 什么都没了 | 不能 |
| 软删除 | 记录仍在，打一个标记 | 能 |

`memory.py` 的 `forget()` 做软删除，召回时过滤：

```python
def forget(self, tenant: str, kind: str, key: str) -> None:
    """软删除：标记而不是移除，保留审计痕迹。"""
    rid = f"{tenant}/{kind}/{key}"
    if rid in self.rows:
        self.rows[rid].deleted = True
```

```
=== 4. 软删除之后召回为空，记录仍在 ===
  t1 查'偏好联系' -> []
  存储里仍保留（用于审计）：
  t1/semantic/pref_contact           用户偏好工作日 9-18 点联系 (已删)
```

### 4.1 软删除的四个必需要求

| 要求 | 不做的后果 |
|---|---|
| 所有召回路径都过滤 `deleted` | 漏一条路径就"删了还在用" |
| 更新时检查 `deleted` | 用户删掉的偏好被下一轮又写回来 |
| 有实际的清理期限 | 存储无限增长，且与"删除"的承诺不符 |
| 清理时留摘要 | 审计只剩"已清理"，查不出曾有什么 |

第一条是最常见的漏洞：主召回路径过滤了，但缓存预热任务、导出任务、报表任务各有一份查询。**过滤条件要写在存储层，而不是写在每个调用方。**

第三条与"永久保留"的直觉相反，但它正是合规要求的形式：删除承诺通常有一个期限（例如 30 天内清除），超过期限仍在就是违规。软删除不是"不删"，是"先标记、后端再清"。

### 4.2 软删除与"用户改主意"

一个实际场景：用户说"以后别用邮件联系我"，系统软删了邮件偏好；下一轮用户说"还是邮件吧"，系统要能写回这条记录。

如果键不变（`user:123/preferred_channel`）、软删除后仍允许覆盖，这个回写是自然的。如果软删除时把键也改成带删除时间的形态，回写就成了新增，两条记录同时存在，召回又要靠时间戳判断哪条有效。

**键保持稳定、状态用字段表示**，是这处设计的基本要求，与第 10 章 State 的"字段生命周期"是同一个原则。

### 4.3 一次删除的完整路径

软删除看起来只是一个标记，实际要动的有四处：

| 处 | 做什么 | 漏了的后果 |
|---|---|---|
| 记录本身 | 打标记 | 召回里仍然出现 |
| 缓存 | 失效与租户键相关的条目 | 标记生效了，缓存还是旧的 |
| 向量索引 | 过滤或重建该条 | 检索仍能命中它 |
| 下游副本 | 导出、报表、分析库 | "已删除"的数据出现在报表里 |

第三行在向量库里最容易被忽略：多数向量库的删除是"标记 + 后续重建时清理"，这期间的检索结果仍然包含它。**要做到"删了就不再召回"，要么检索时按 ID 过滤，要么立即重建。** 前者便宜，后者彻底。

第四行是合规检查里最常见的失分点：主库删了，分析库还留着一份导出的副本。这条与本章的技术关系不大，但它是"软删除"这件事闭环的最后一环。

### 4.4 软删除与"重新写入"的冲突

用户删了某条偏好，而后台的一次批处理又把同样的偏好写了回来——这类问题在记忆系统里很常见，因为写入方不止一个：对话抽取、CRM 同步、运营后台。

一条可用的规则：**删除标记优先于任何后续写入，除非写入方明确声明"用户重新确认"。** 实现上就是写入时检查 `deleted` 并拒绝，只有带 `user_confirmed=true` 的写入才允许把它翻回来。

不这么做的后果是用户"删了又出现"，而这在用户一侧看起来是系统不听话，在系统一侧看起来"数据一直是对的"——两侧的判断长期不一致。

### 4.5 软删除之后写回的三方对账

删除与写入来自三个方向，彼此不知道对方的动作，于是需要一次对账：

| 写入方 | 它认为 | 实际可能 |
|---|---|---|
| 对话抽取 | 用户刚才又提到了偏好 | 用户已经明确说不要这个偏好 |
| CRM 同步 | 系统登记里这是最新值 | 这个值是登记前的旧数据 |
| 运营后台 | 人工更正过，一定对 | 人工更正的是另一个租户的记录（键错） |

第二行是最常见的"删了又回来"来源：CRM 的同步是定时的，它不知道用户在对话里删过什么。**时间戳不足以判断，因为同步的是旧数据、写入时间是新的。**

可用的做法是给每个字段记"最近一次用户明确表述"的时间与内容，**任何非用户来源的写入都不能覆盖它**，只能作为冲突提示交给人看。这与第 9 章的"外部裁判"逻辑一致：用户自己说的话是最高优先级的证据。

### 4.6 三层的清理节奏不同

| 层 | 典型保留期 | 为什么不同 |
|---|---|---|
| 语义 | 到用户撤回为止 | 撤回是明确动作，不需要自动过期 |
| 情景 | 6–12 个月 | 太久远的经历参考价值低 |
| 程序 | 永久（按版本） | 是团队的规则，需要历史版本 |

第二行需要一条"过期自动软删"的规则，否则老用户的情景层会无限增长，召回时占据大量候选（2.2 讲的"越用越大"）。

第三行的"永久"不等于"全部生效"：历史版本保留，但只有最新一版被召回（1.1 的要求）。

## 五、这一层的失效模式

**第一，三层混在一个集合里。** 表现为问"上次怎么处理的"召回到一条政策条文——因为两者都在同一个向量索引里，相似度算出来差不多。

**第二，语义层没有稳定键。** 表现为同一件事实有多条记录，召回结果互相矛盾（"偏好电话"与"偏好邮件"同时出现）。

**第三，程序层召回两条版本。** 表现为同一次任务里流程前后不一致。

**第四，隔离做在应用层但没做在缓存层。** 表现为极少数请求（缓存命中率高的那批）出现跨租户内容。

**第五，软删除只做了标记没做清理。** 表现为存储增长、合规检查时"已删除的数据还在"。

### 5.1 三个可以立刻算的数

长期记忆的质量不像检索那样有现成指标，但有三个数能算、且都能指向具体问题：

| 数 | 算法 | 低了说明 |
|---|---|---|
| 召回命中率 | 召回后答案被采纳的比例（用追问率或人工抽样） | 记了但没用上：键设计或触发词不对 |
| 重复率 | 同键记录数 / 语义层记录总数 | 去重没做，或键不稳定 |
| 陈旧率 | 超过 N 天未更新且被召回过的记录占比 | 更新机制缺失，记忆会越来越不反映现状 |

第三行是长期记忆独有的问题：**它不会自己过期。** 一条一年前的偏好，如果一直被召回、一直没被纠正，系统就会一直按它做事。第 19 章的文档生命周期处理的是同一类问题，只是对象从"用户的偏好"换成了"政策文档"。

### 5.2 与第 17 章记忆槽的分界

两章的边界容易混，用一句话分开：**第 17 章决定"这一轮看得见什么"，本章决定"下一次还记得什么"。**

| | 第 17 章（短期） | 本章（长期） |
|---|---|---|
| 生命周期 | 一次会话 | 跨会话 |
| 存储 | 会话状态 | 独立存储 |
| 丢失的后果 | 这一轮答得差 | 下次重新问一遍 |
| 主要风险 | 预算分配、压缩删掉关键事实 | 隔离、陈旧、重复 |

分界清楚之后，一个实际的问题就有了明确归属：**"用户抱怨每次都要重新说一遍"是本章的问题，"用户抱怨聊到后面忘了前面"是第 17 章的问题。** 两者的修法完全不同，混在一起排查会两头都改不对。

### 5.3 一次记忆写入的完整判断

把本章的规则收成一条写入前要问的清单，五问：

| 问 | 答案不对时 |
|---|---|
| 这条属于哪一层？ | 归属错时，召回方式也会错（2.6） |
| 键稳定吗（实体 + 属性）？ | 键不稳定就会产生重复（1.2） |
| 是用户说的、系统观测的、还是外部来的？ | 三类冲突处理方式不同（2.1） |
| 用户在别处删过同一个键吗？ | 删除标记优先（4.4） |
| 需要过期吗？ | 情景层必须有保留期（4.6） |

四个问题里没有一个是"这条是否重要"。**重要性不是判据**——一条不重要的偏好，写进状态也会被召回、也会占预算。判据要能落到具体动作上。

## 六、边界

**第一，不是所有系统都需要三层。** 单租户、任务短的系统，语义层加情景层就够；程序层实际上就是 Skill，不一定要单独存一份。

**第二，语义层不能替代用户设置。** 抽取出来的偏好是推断，不能覆盖用户在设置页里明确填过的值。两者冲突时以设置为准，抽取结果只作为提示。

**第三，情景层的价值在"相似"，不在"这个人"。** 只按用户过滤、不按情形相似度排序时，召回的是"这个用户最近做过的事"，而不是"类似情况怎么处理的"——后者才是用户问"上次也是这样"时想要的。

**第四，软删除的期限要写进承诺。** 说"随时可以删除"却在库里留了三年，与说"30 天内清除"是一致的，前者不一致。

**第五，记忆的写入要和评测共用一套定义。** 第 29 章的多轮评测会构造"用户提到上次""用户改主意"这类用例，评测集里的记忆数据与线上写入规则不一致时，评测结果无法解释。

**第六，记忆不是越多越好。** 每多一条被召回的记录，就多一段占预算的上下文（第 17 章的四槽位）。召回 1 条有用的偏好，胜过召回 5 条"可能相关"的往事——后者会把这一轮的注意力分散到与当前问题无关的事上。

### 6.1 上线顺序

三层不必同时上线。一个可行的顺序，每步都能独立验证：

| 步 | 上什么 | 验证方式 |
|---|---|---|
| 1 | 情景层（会话结束写摘要） | 用户说"上次也是这样"时能找回 |
| 2 | 语义层（稳定键 + 去重） | 同一事实不出现两条 |
| 3 | 程序层（带版本） | 同一次任务里只用到一个版本 |

第一步先上的理由很实际：情景层只写不抽（会话结束时总结一次），没有抽取质量的问题，也没有键设计的争议；它带来的体验改善最直接（"上次也是这样"能被接住）。

第二步最难，也最容易被跳过——因为它需要一个稳定的键设计，而键设计要等你见过真实的抽取结果才知道对不对。

第三步放在最后，是因为它涉及团队的流程定义，改动的影响面超出这个系统本身。

## 这一章建立的 5 件事

1. 跨会话记忆分三层：语义（稳定事实）、情景（某次经历）、程序（做法）。分层的依据是答案的寿命与更新方式，不是内容类型。
2. 语义层要用稳定键（实体 + 属性），同一键再写是覆盖；抽取结果必须去重，否则重复条目会占满召回前几名。
3. 程序层召回只能有一条当前版本，写入只允许"新增版本 + 标记生效"，不允许原地改。
4. 租户隔离要在键、查询、向量索引、缓存、导出五层都做；检查用"发现跨租户就报错"，而不是过滤掉算了。
5. 软删除要覆盖所有召回路径、更新时检查删除标记、有清理期限、清理时留摘要。键保持稳定，状态用字段表示。

## 下一章

记忆与索引都在回答"问题来了怎么办"。还有一件没处理的事：**文档本身会变。** 政策会改版、条款会删除、同一个主题会有新旧两份并存。第 19 章讲文档生命周期与知识治理：增量索引怎么做、两条互相矛盾的条目怎么被发现、可溯源率怎么算。
