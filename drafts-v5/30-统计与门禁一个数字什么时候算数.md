## 一、一个数字的三种骗法

评测跑完总有一个数：通过率 86%、准确率 0.83、P95 延迟 8.4 秒。这个数在三种情况下会骗人，而三种都很常见。

### 1.1 小样本

20 条里过 19 条，是 95%。这个 95% 与"一千条里过 950 条"的 95% 不是一件事：

```
  19/20 = 95%  区间 [76.4%, 99.1%]  宽 22.7 个点
  95/100 = 95%  区间 [88.8%, 97.8%]  宽 9.0 个点
  950/1000 = 95%  区间 [93.5%, 96.2%]  宽 2.7 个点
```

第一行的 95% 背后，真实水平可能只有 76%。**小样本的问题不是"不准"，是"我们不知道它准不准"**——而报告通常只写那个 95%。

### 1.2 只报点估计

第二种骗法与样本量无关：只报一个点，不报区间。

"这次从 86% 提升到 89%"听起来是 +3 个点。但如果两次都是 200 条，这个差值的区间是 `[-3.5, +9.5]`——它跨过 0，意味着"也有可能是降了 3.5 个点"。

| 说法 | 隐含的确定性 | 实际 |
|---|---|---|
| 提升 3 个点 | 一定提升了 | 可能下降 3.5 个点 |
| 提升 3 个点（±6.5） | 看不出方向 | 需要更多样本 |
| 提升 3 个点，200 条 | 无信息 | 同上 |

第二行的说法才诚实，但它不讨喜：它承认了这次评测什么也没证明。

### 1.3 分母被换过

第三种最隐蔽：两次数的分母不同，却被放在一张图上比。

| 变化 | 表现 |
|---|---|
| 评测集新增了 40 条难题 | 通过率从 86% 掉到 78%，"退步了" |
| 评测集删掉了一批简单题 | 通过率从 86% 涨到 91%，"进步了" |
| 采样策略改了 | 错误率突然上升，其实是错误样本终于被留下了 |

第一行与第二行都是"尺子变了"。它们的危险在于方向看起来都很合理——退步时有人会去找代码问题，而真正的原因是集合变了。

第 28 章 5.4 要求"只增不改"，就是为了挡住这两行。真要做到，还需要在报告里带集合版本号：**没有版本号的一次 86%，三个月后无法解释。**

### 1.4 三种骗法的共同点

三种骗法背后是同一个缺失：**报告只给了一个点，没给"这个点的不确定性"。**

| 缺失 | 补上什么 |
|---|---|
| 小样本 | 区间 |
| 只有点估计 | 区间 + 样本量 |
| 分母被换 | 集合版本号 |

补上之后，报告会变长一点，但结论会变短：很多"提升 3 个点"会变成"看不出方向"。这不是坏消息——**一个"看不出"的结论，比一个错的"提升了"便宜。**

这条判断有个前提：报告是给决策用的，不是给汇报用的。如果报告的用途是"让上级看到进展"，那区间会显得碍事；如果用途是"决定要不要发"，区间是唯一能让决定站得住的东西。

### 1.5 这点统计为什么必要

有人会说：业务变化动辄十几个点，纠结 3 个点显不显著是不是过度讲究？

不是。原因在于"评测样本"与"线上流量"是两个分布：

| | 评测样本 | 线上流量 |
|---|---|---|
| 规模 | 几百条 | 每天上万次 |
| 作用 | 决定要不要发 | 承受后果 |
| 噪声 | 大（样本小） | 小（大数定律） |

第一行的样本只有几百条，噪声本身就有几个点。**如果不扣掉噪声，一次"提升 3 个点"的判定可能只是在读噪声。** 而线上的问题在于：一次错误的发布会被放大上万倍。

所以统计在这里的作用不是"算得更准"，是**防止用噪声做决策**。它对业务变化大不大没有意见——它只说"这个差值是信号还是抖动"。

一个实际的折中：早期探索阶段（方向未定）用几十条样本看方向，不追求显著性；发布前用几百条样本做门禁，这时候显著性才有意义。

## 二、区间

`interval.py` 的四个数字，回答的是"这个比率能信到哪"。

### 2.1 为什么用 Wilson

比率的区间有好几种算法，最朴素的是 `p ± 1.96√(p(1-p)/n)`。它在小样本与极端比例上会失效——比如 20 条全过（p=1）时，它算出宽度为 0，等于说"确定是 100%"。

Wilson 区间在两端不会退化：

```python
def wilson(k: int, n: int) -> tuple[float, float]:
    """Wilson 区间：小样本与极端比例都适用。"""
    if n == 0:
        return 0.0, 1.0
    p = k / n
    denom = 1 + Z * Z / n
    center = (p + Z * Z / (2 * n)) / denom
    half = Z * math.sqrt(p * (1 - p) / n + Z * Z / (4 * n * n)) / denom
    return max(0.0, center - half), min(1.0, center + half)
```

它的代价是公式不好记、手算不了。但评测报告里这个数是由脚本算的，可读性不是问题。

### 2.2 要多少样本

```
=== 2. 要判多大的差异，需要多少条 ===
  半宽 ±10 个点 -> 约 35 条
  半宽 ±5 个点 -> 约 139 条
  半宽 ±3 个点 -> 约 385 条
  半宽 ±1 个点 -> 约 3458 条
```

这四行是第 28 章 5.3 那张表的来源。它说明的是一件反直觉的事：**样本量随"要判的差异"的平方增长。** 想把判据从 3 个点收紧到 1 个点，样本要涨近十倍。

第四行的 3458 条，多数团队不会去做。可用的判断是"1 个点的差异值多少钱"：如果它对应每年几百次错误回答，不值得为它维护三千条样本；如果对应一次合规风险，那就值得。

### 2.3 样本从哪来

样本量算出来是 385 条，接下来的问题是这 385 条从哪弄。三种来源的代价差很多：

| 来源 | 成本 | 偏置 |
|---|---|---|
| 线上日志抽样 | 低，但要脱敏与标注 | 贴近真实分布 |
| 从知识库构造 | 中，出题成本高 | 偏"可答"，漏掉负例 |
| 人工编写 | 高 | 容易写得比真实问题更完整 |

第一行是首选，代价在脱敏（第 27 章 5.2）与标注（第 28 章 5.2）。它的好处是分布真实：线上问题里那些"半句话""指代""错别字"都会自然出现。

第二行的偏置很实际：从文档构造出来的问题，天然是"文档里有答案"的，负例（该说不知道）几乎为零。要用它，必须单独补一批"文档里没有"的问题。

第三行的偏置最隐蔽：人写问题时会下意识把话说完整，于是评测集里的用户比真实用户更礼貌、更清楚。第 29 章 4.1 的指代用例就是这个坑。

可用的组合是"线上抽样为主（六成）+ 知识库构造（三成）+ 人工边界（一成）"，并按比例维护。任何一类的占比突然变化，指标的基线也要重算。

### 2.4 两版怎么比

两个版本比较时，要看的是"差异的区间"，而不是两个区间有没有重叠：

```
=== 3. 两个版本比较：差异与区间 ===
  基线 172/200 vs 候选 178/200
    差异 +3.0 个点，区间 [-3.5, +9.5] -> 不显著
  基线 172/200 vs 候选 186/200
    差异 +7.0 个点，区间 [+1.0, +13.0] -> 显著
  基线 172/200 vs 候选 173/200
    差异 +0.5 个点，区间 [-6.2, +7.2] -> 不显著
  小样本 17/20 vs 18/20
    差异 +5.0 个点，区间 [-15.4, +25.4] -> 不显著
```

第四行是最容易误判的一行：17/20 与 18/20 看起来"提升了 5 个点"，但区间宽 40 个点。任何基于 20 条样本的"提升 5 个点"的结论都不成立。

第一行与第二行的差别只有 8 条通过数，结论却从"不显著"变成"显著"。**这就是样本量 200 时能判的最小差异：大约 7 个点。** 要判更小的差异，只能加样本。

用"两个区间是否重叠"来判断是错误的：它比正确做法保守得多。两个 95% 区间即使重叠，差异仍可能显著——因为差值的标准误比各自的标准误小。

### 2.5 不同指标用不同区间

这一章的公式只适用于比率。其他指标要换方法：

| 指标类型 | 例子 | 区间怎么算 |
|---|---|---|
| 比率 | 通过率、拦截率、幻觉率 | Wilson |
| 均值 | 单次成本、平均步数 | t 区间（正态近似） |
| 分位数 | P95 延迟、P99 成本 | bootstrap 重采样 |
| 计数 | 每天的事故数 | 泊松区间 |

第三行是第 31 章要用的：P95 不是"某个样本的值"，它是分布的尾部位置，没有简单的解析式。bootstrap 的做法是从样本里有放回地抽 1000 次，每次算一个 P95，取这 1000 个值的 2.5% 与 97.5% 分位。

它慢，但对分布形状没有假设——而延迟分布恰恰是长尾的，正态近似会低估尾部的不确定性。

第二行的"均值"在长尾分布上也不可靠：单次成本里混着"一句话问答"与"跑了二十步"的两类样本，均值会被后者拉动。**成本类指标报到报告里时，最好同时给中位数与 P95。**

第四行的泊松区间常被忽略：一天 3 次事故与一天 0 次事故的差别很大，但"3"这个数字的区间是 [0.6, 8.8]——它意味着"可能只是运气"。事故计数做趋势判断时，至少要看一周的合计。

## 三、门禁

门禁是把"这次能不能发"变成一个可以自动判定的问题。`gate.py` 用两条规则：

```python
def regression(k1: int, n1: int, k2: int, n2: int) -> tuple[str, str]:
    d, lo, hi = diff_ci(k1, n1, k2, n2)
    if d <= -REGRESSION_PP:
        return "fail", f"绝对差 {d * 100:+.1f} 个点，超过 -2 的回归线"
    if d < 0:
        return "warn", f"绝对差 {d * 100:+.1f} 个点，小幅下降（区间 [{lo * 100:+.1f}, {hi * 100:+.1f}]）"
    return "pass", f"绝对差 {d * 100:+.1f} 个点，未触及回归线"


def ratio_verdict(name: str, base: float, cand: float) -> tuple[str, str]:
    rel = (cand - base) / base
    limit = RULE[name]
    if rel > limit:
        return "fail", f"{name} 涨 {rel:+.1%}，超过上限 {limit:.0%}"
    if rel > limit * 0.6:
        return "warn", f"{name} 涨 {rel:+.1%}，接近上限 {limit:.0%}"
    return "pass", f"{name} {rel:+.1%}，在 {limit:.0%} 之内"
```

```
=== 逐条判定 ===
  C1 提示词微调   PASS
    [回归] 绝对差 +3.0 个点，未触及回归线
    [改善] 看起来变好 +3.0 个点，但区间跨 0，不能算数
    [成本] cost +0.0%，在 5% 之内
    [延迟] p95 +0.0%，在 10% 之内
  C2 换模型       FAIL
    [回归] 绝对差 +7.0 个点，未触及回归线
    [改善] 显著改善 +7.0 个点（[+1.0, +13.0]）
    [成本] cost 涨 +11.7%，超过上限 5%
    [延迟] p95 +6.0%，在 10% 之内
  C4 加重排       FAIL
    [回归] 绝对差 +4.0 个点，未触及回归线
    [改善] 看起来变好 +4.0 个点，但区间跨 0，不能算数
    [成本] cost 涨 +30.0%，超过上限 5%
    [延迟] p95 涨 +14.3%，超过上限 10%
```

### 3.1 比率看绝对差

质量是比率类指标，它的阈值用**绝对差**，不用相对变化。

原因在分母：86% 的 5% 相对变化是 4.3 个点，而 60% 的 5% 相对变化是 3 个点。同一个相对阈值，在不同基线上对应的绝对变化不同——基线越低，同样的相对变化越不敏感。

| 基线 | "下降 5%" 的绝对差 | 感受 |
|---|---|---|
| 95% | 4.75 个点 | 严重 |
| 60% | 3.0 个点 | 一般 |

第一行的 4.75 个点在 95% 基线上几乎是灾难，而它在相对口径里只是一个"5%"。

所以质量阈值要写成绝对差：**下降超过 2 个点就拦。** 这个 2 是怎么来的？它是"业务能接受的年度退化量"除以年请求量之后反推出来的——不是统计量，是业务判断。

阈值定得对不对，可以用一条经验检验：**它拦下的改动里，有多少是团队事后认为"确实不该发"的。** 如果拦下的全是误拦，阈值太紧；如果一条都没拦过，阈值太松或者门禁没接上。

这条检验还暴露了另一件事：阈值需要定期回看。团队对"几个点的退化可接受"的判断会随业务变化——增长期容忍度高，稳定期低。阈值不跟着变，就会在某一天突然变成"所有人都要写豁免"。

### 3.2 非比率看相对变化

成本与延迟没有天然的绝对单位，它们的阈值用**相对变化**：

| 指标 | 上限 | 理由 |
|---|---|---|
| 单次成本 | +5% | 预算按比例分配，5% 是安全边际 |
| P95 延迟 | +10% | 用户能感知的阈值大约是这个量级 |
| 首字节 | +50ms | 绝对量，因为它是感知量 |

第三行是例外：TTFT（第 31 章）用绝对量，因为用户对"多久看到第一个字"的感知是绝对时间的，不是相对比例。

**同一次改动可能同时踩三条线。** C4 的成本涨 30%、延迟涨 14.3%，两条都超限，而它的质量提升还没被证实（区间跨 0）。门禁的结论是 FAIL，即便质量看起来涨了 4 个点。

### 3.3 门禁与"变好"是两件事

C1 与 C2 的对比是这一节的重点：

- C1 质量 +3 个点（不显著）、成本不变 → PASS
- C2 质量 +7 个点（显著）、成本 +11.7% → FAIL

门禁回答的是"能不能发"，不是"有没有变好"。C1 通过了，但它没有证明自己更好——它只证明了"没有变坏到不可接受"。C2 证明了变好，但它太贵。

**把这两件事混起来的代价**：如果门禁同时要求"显著改善"，那所有中性改动（重构、依赖升级、日志补充）都会被拦，而它们中的大多数根本不该改变质量。

所以门禁的设计是双向不对称的：回归判定用绝对差（保守，宁可误拦），改善判定用显著性（严格，宁可漏认）。这个不对称是刻意的——**误拦一次可以重跑，放过一次回归会进生产。**

### 3.4 容差与冻结期

门禁还有两个不写在公式里的参数：

| 参数 | 作用 | 典型值 |
|---|---|---|
| 容差 | 同一版本重复跑的正常波动 | 由重复跑量出来 |
| 冻结期 | 基线多久更新一次 | 每次发布后更新 |

第一行是"同一份代码两次跑出来的差异"。它来自生成采样与裁判判定的随机性（第 28 章 2.4）。**容差不设，门禁会把噪声当回归**，团队会开始忽略告警。

第二行决定了"回归"是与谁比。基线一直不更新，门禁就在跟一个越来越旧的版本比；基线每发布更新，就变成"与上一个版本比"，累积的退化会被掩盖。可用的折中是**双基线**：与上一版比（抓单次回归）+ 与三个月前的版本比（抓累积漂移）。

### 3.5 门禁的落地形态

规则写成代码之后，还有三个落地问题：

| 问题 | 做法 | 不做的后果 |
|---|---|---|
| 在哪跑 | 提交时跑轻量门禁，发布时跑全量 | 每次提交等十分钟，开发者绕过 |
| 失败怎么办 | 阻止合并，但允许显式豁免并记录 | 有人手改数字，或本地不跑 |
| 阈值改哪里 | 与代码同一仓库，走评审 | 阈值被临时放宽，没人知道 |

第一行的关键在于时间预算：提交级门禁必须在几分钟内跑完，所以它只能跑几十条样本的一层评测；轨迹层与稳定层留给发布前的全量。

第二行的"显式豁免"是必须的：总有改动会合理地让某个指标下降（比如为了延迟牺牲一点召回）。没有豁免通道，团队会用两种方式绕过——本地不跑，或直接改数。

第三行的成本最低、效果最大：阈值一旦在代码库里，改动就有历史、有评审；阈值在某个后台页面里，改动就没人知道。第 31 章的复盘经常落在"某个阈值被谁在什么时候放宽了"上。

### 3.6 门禁与人的分工

| 判定 | 谁做 | 理由 |
|---|---|---|
| 有没有回归 | 机器 | 规则明确、可重复 |
| 回归是否可接受 | 人 | 要权衡业务影响 |
| 要不要发 | 人（+ 灰度） | 要承担后果 |

第二行不能交给机器：一个 -3 个点的召回下降，在"这个月要冲量"与"这个月要保证准确"两种背景下结论不同。机器只能把它标成 warn 并列出证据。

第三行意味着门禁是"建议 + 闸门"的组合：它拦住的是明确的回归，放过的是有争议的。**一道门禁如果连有争议的都要拦，团队会把它变成形式。**

### 3.7 门禁上线之后

门禁本身也会退化。三种退化方式，各有信号：

| 退化 | 表现 | 应对 |
|---|---|---|
| 绕过 | 豁免越来越多 | 统计豁免率，超过两成就要复盘阈值 |
| 失真 | 基线版本过旧 | 每次发布更新基线，并保留上一个 |
| 失效 | 指标不再变化 | 检查跑批是否真的在跑 |

第一行是渐进式的：先是"这次特殊"，再是"最近都在特殊"。它的终点是所有人都学会写豁免理由，而门禁的通过率与豁免率一起失去意义。

第二行的"基线过旧"最隐蔽：门禁一直在与三个月前的版本比，中间累积的退化被当成"新的正常"。双基线能挡住这一种。

第三行的"指标不再变化"通常来自跑批失败但被忽略：CI 里那一步红了很久没人看，指标一直停在旧值。可用的做法是让跑批本身有一个心跳——连续 N 天没有新的跑批记录就告警。

**门禁的可靠性要由门禁之外的东西来保证。** 一个"通过率 100%"的门禁，可能意味着它根本没在跑。

## 四、跑批

`code/eval/run_eval.py` 把前面的东西串起来：40 条用例、三个配置、区间、门禁、样本量提示。

```
=== 1. 三个配置各跑 40 条 ===
  baseline  33/40 = 82%  区间 [68.0%, 91.3%]
    正例：17/22 = 77%
    负例：8/9 = 89%
    边界：8/9 = 89%
  candidate 36/40 = 90%  区间 [76.9%, 96.0%]
  risky     28/40 = 70%  区间 [54.6%, 81.9%]

=== 2. 与基线的差异 ===
  candidate 差异 +7.5 个点，区间 [-7.5, +22.5]  不显著
  risky     差异 -12.5 个点，区间 [-30.9, +5.9]  不显著

=== 3. 门禁判定 ===
  [candidate] pass:质量未回归（+7.5 个点）；pass:成本 +0.0% -> PASS
    改善未证实：+7.5 个点，区间下界 -7.5
  [risky] fail:质量回归 -12.5 个点；pass:成本 +0.0% -> FAIL
```

### 4.1 三段产物

一次跑批要产出三段，缺一段就无法复查：

| 段 | 内容 |
|---|---|
| 逐条结果 | `case_id`、通过与否、耗时、token |
| 汇总 | 分组的通过率 + 区间 |
| 判定 | 门禁结论 + 理由 + 基线版本 |

第一段是数据，第二段是指标，第三段是决策。三段的粒度不同，用途也不同：出了问题先看第一段找样本，向上沟通看第二段，发不发布看第三段。

第二段按 kind 分组（正例、负例、边界）比只看总数有用：candidate 的 90% 里，正例 91%、负例 89%、边界 89%，分布比 baseline 均匀——这比一个总分更能说明"它全面地好了一点"。

### 4.2 判定的两难

看 `risky`：-12.5 个点，但区间 `[-30.9, +5.9]` 跨 0，统计上"不显著"。门禁却判 FAIL。

这不是矛盾，是两条规则的分工：**回归判定不看显著性，只看绝对差。** 理由是风险不对称——一个可能是 -30 个点的改动，不能因为"样本不够所以看不出来"就放行。

代价是误拦：一个真实的 -3 个点退化，在 40 条样本上会被判 FAIL，而它可能只是噪声。这个代价是故意选的：**误拦的代价是重跑一次评测，放过的代价是一次生产回归。**

如果团队受不了误拦，正确的做法是加样本（本节第 2 段），而不是放宽回归线。

### 4.3 跑批的工程细节

一次跑批的耗时主要由三件事决定，三件都有便宜的优化：

| 环节 | 耗时来源 | 优化 |
|---|---|---|
| 模型调用 | 每条一次或多次 | 并发、缓存相同输入 |
| 判分 | 裁判调用、字面比对 | 规则先行，裁判只判边界 |
| 汇总 | 通常可忽略 | — |

第一行的并发要小心：并发太高会撞下游的速率上限（第 26 章的限流），表现出来是"跑批变慢且错误率上升"。可用的做法是按下游配额反推并发度，并把 429 当作可重试而不是失败。

第二行的"规则先行"来自第 29 章 3.6：字面不一致的样本才送裁判，裁判调用量能降一个数量级。

还有一个常被忽略的工程细节：**跑批要能断点续跑。** 一次 500 条的跑批跑到 300 条时进程挂了，重跑全部会浪费时间与钱。按 `case_id` 记录已完成的结果、重启时跳过，是第 23 章断点续跑在评测上的同一个做法。

最后是结果的可比性：跑批要固定模型版本、温度、提示词版本、检索索引版本。少记一个，下次就说不清差异来自哪里（第 27 章 1.4 的第三种用法）。

### 4.4 一次跑批的时序

从提交到拿到结论，中间有五步，每步都可能卡住：

| 步 | 耗时来源 | 卡住的样子 |
|---|---|---|
| 排队 | 并发度与配额 | 提交后十几分钟没开始 |
| 执行 | 模型调用 | 单条超时被反复重试 |
| 判分 | 裁判调用 | 裁判把整批拖慢 |
| 汇总 | 通常可忽略 | — |
| 判定 | 门禁规则 | 差一个基线版本号，判不了 |

第二步的"反复重试"是隐形的时间杀手：一条样本超时后重试三次，跑批时间就多三倍。可用的做法是给单条设一个硬上限，超了就记为失败——**评测里的一条超时，本身就是它该被记录的结果。**

第五步的"判不了"最常见：门禁需要基线，而基线是上一次跑批的产物。第一次跑没有基线，只能"记录不判定"。这个状态要显式表示，否则会有人拿第一次的结果当基线，而那次可能正好跑在异常环境上。

第五步之后还有一步常被漏掉：**把结果写回可查的地方**。一次跑批的产物如果只留在 CI 日志里，三个月后复盘时找不到——而第 31 章的事故复盘恰恰需要"当时那次评测的数字"。

## 五、会怎么坏

**第一，20 条结论。** 用 20 条样本的通过率做发布决策。信号是报告里没有区间。

**第二，点估计比较。** "从 86% 到 89%"写进周报，不看区间。信号是周报里只有数字没有范围。

**第三，分母换了不说。** 集合新增或删除样本后照常比。信号是评测集有改动、报告无版本号。

**第四，用"区间是否重叠"判断差异。** 把显著的改动判成不显著，错失改进。信号是判定逻辑里写的是两个区间相交。

**第五，质量用相对阈值。** "通过率下降 5%"这种写法，在 95% 基线上是灾难，在 60% 基线上是噪声。信号是阈值写成百分比。

**第六，门禁要求"显著变好"。** 所有中性改动被拦，团队开始批量绕门禁。信号是门禁的通过率异常低。

**第七，容差没量过。** 把采样噪声当回归，告警越来越频繁，最后被静音。信号是同一版本的重复跑差异没人知道。

**第八，评测样本与线上分布脱节。** 评测里 90 分，线上投诉不断。信号是评测集的问题写得比真实问题完整。

**第九，跑批不可复现。** 同一版本的两次跑分不同，且没人能说清为什么。信号是跑批记录里缺模型版本或温度。

**第十，豁免没有记录。** 每次都能"临时通过"，三个月后没人知道基线是怎么来的。信号是门禁的豁免列表在某个人的聊天记录里。

## 六、边界

**第一，区间假设独立同分布。** 评测样本如果彼此相关（同一个文档的多个问题），真实区间比算出来的宽。可用的做法是按文档分组抽样，或直接用 bootstrap。

**第二，统计显著不等于业务重要。** 一千条样本能测出 1 个点的显著提升，而这 1 个点可能不值得一次发布。反过来，样本不足时一个真实的 10 个点提升可能"不显著"。**显著性回答"能不能看见"，重要性回答"值不值得"，两个都要人判。**

**第三，门禁的阈值是业务参数，不是统计参数。** 2 个点的回归线、5% 的成本上限，都来自业务容忍度。统计只告诉你"这个差是不是噪声"，不告诉你"多大的差可以接受"。

**第四，多次比较会放大假阳性。** 一次发布同时看 10 个指标，每个都用 95% 的区间，至少一个"显著"的概率接近 40%。可用的做法是预先指定主指标，其余作为参考。

**第五，本章只处理比率与相对变化。** 分布类指标（P95、P99）的区间要用 bootstrap，不能用本节的正态近似。第 31 章的延迟瀑布会碰到这个。

**第六，门禁不能替代灰度。** 离线评测通过只说明"在评测集上没退步"，线上还有分布漂移与长尾。发布仍然要灰度，只是门禁把风险压低了一层。

**第七，统计方法的选择会影响结论，而它通常不在评审范围内。** 同一个差异，用正态近似、Wilson、bootstrap 算出来的区间宽度可能差 20%。团队应当在评测脚本里固定一种方法并写明，而不是每次临时选。

**第八，本章的数字都建立在"样本独立"这个假设上。** 同一份文档衍生的十个问题不是十个独立样本，它们会一起对或一起错。真实区间比算出来的宽，这一点只能靠按文档分组抽样来缓解。

## 这一章建立的 5 件事

1. 一个比率不带样本量就没有意义：19/20 的 95% 区间是 [76%, 99%]，950/1000 的 95% 是 [93.5%, 96.2%]。小样本的问题是我们不知道它准不准。
2. 样本量随"要判的差异"的平方增长：±5 个点约 139 条，±3 约 385 条，±1 约 3458 条。
3. 两个版本比较要看"差异的区间"，不是两个区间是否重叠；200 条样本能判的最小差异约 7 个点。
4. 门禁的两条规则方向相反：质量（比率）看绝对差、不看显著性；成本与延迟（非比率）看相对变化。回归判定保守，改善判定严格。
5. 门禁回答"能不能发"，不回答"有没有变好"。把两者混起来，所有中性改动都会被拦。
