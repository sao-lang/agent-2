> **知识点**：E11 成本归因与三级预算；E12 延迟瀑布；E13 故障复盘；E14 事故到回归用例

## 一、钱花在哪

一次任务的总成本是一个数，但它由六个阶段的成本相加而成。不拆开，所有优化都只能"试试看"。

`cost_waterfall.py` 把一次 12 步任务按阶段拆开：

```
=== 1. 一次任务的成本瀑布 ===
  阶段                    输入     输出     缓存      成本(元)      占比
  路由                   900     80      0   0.001220    2.2%
  检索改写                2400    120      0   0.002880    5.1%
  生成（主回答）            16000   900   6000   0.020200   35.8%
  子 agent 汇总         18000   520      0   0.020080   35.6%
  自审                  9000    300   4000   0.010600   18.8%
  格式化输出               1200     60      0   0.001440    2.6%
  合计                 47500   1980  10000   0.056420  100.0%
```

### 1.1 瀑布读法

第一眼看的是"哪一段最大"：生成（35.8%）与子 agent 汇总（35.6%）几乎相同，自审 18.8%。

第二眼看的是"哪一段可以省"：三段的省法完全不同。

| 阶段 | 为什么贵 | 能怎么省 |
|---|---|---|
| 生成（主回答） | 上下文 16000 是全部检索结果 | 裁剪上下文、提高缓存命中 |
| 子 agent 汇总 | 它读了 18000 的原文 | 减少交给它的材料、缩小任务 |
| 自审 | 它把回答与依据又读了一遍 | 只在关键步自审，或用规则裁判 |

第三行是这一章最值得注意的一处：自审占 18.8%，而它的收益是"少一次返工"。**如果返工率只有 5%，自审的成本可能超过它省下的钱。** 这就是第 9 章"每步裁判的成本模型"要算的账。

第一行的"缓存 6000"也是一个信号：缓存只覆盖了 16000 输入里的 6000，说明前缀复用得不够。第 3 章的缓存命中是输入侧的定价差，命中率从 37% 提到 80%，这一阶段的成本能降三成。

### 1.2 三级预算

成本要在三个尺度上各有一个上限，缺一个就会出现"单次很便宜、月度爆掉"：

```
=== 2. 三级预算 ===
  单任务       已用     0.06 / 0.08    （ 70.5%）
  单租户/日     已用     4.92 / 6.00    （ 82.0%）
  平台/月      已用    88.80 / 120.00  （ 74.0%）
  <- 单任务只占日预算的 0.94%，但日预算已用 82%：真正该管的是租户级
```

| 级 | 管什么 | 超了怎么办 |
|---|---|---|
| 单任务 | 一次运行的失控 | 中止该任务（第 7 章） |
| 单租户/日 | 一个客户的用量 | 降级到便宜路径，或 429 |
| 平台/月 | 整体预算 | 换模型、关缓存、限流 |

第一级的阈值通常比平均值高几倍：正常任务 0.056 元，预算 0.08——它有 40% 的余量给异常长的任务。

第二级是实际最常触发的。示例里租户已用 82%，意味着再有一次大任务就会触发降级。

第三级是"事故级"：它触发时，所有租户都受影响，处理方式只能是全局降本（换小模型、缩小 top-k、关掉自审）。

**三级的阈值要能互相推导**：如果租户日预算 6 元、单任务 0.08 元，那么一个租户一天理论上限是 75 次任务——超出这个数就不是"用量大"，而是"有人在刷"。这个推导能提前发现配额设计的不合理。

三级之外还有一个"第四级"常被忽略：**按功能的预算**。一个 agent 平台上，问答、审批、批处理三类负载的成本结构完全不同，混在一个月度预算里，某一类暴涨会被另一类的节省掩盖。可用的做法是给每类一个子预算，总和不超过月度总额。

子预算的粒度要按"能被谁负责"来定：问答由算法团队负责、审批由业务团队负责，那么预算也按这个切。**没有人负责的预算，超了也不会有人处理。**

### 1.3 语义缓存的三条红线

缓存是最直接的降本手段，示例里命中率 30% 省 28%、60% 省 57%。但它的三条红线每一条都能把省下的钱变成事故：

| 红线 | 形态 | 后果 |
|---|---|---|
| 键不含租户 | A 问"我的订单"，命中 B 的答案 | 数据串户 |
| 不随文档失效 | 政策改了，命中旧答案 | 答了过期政策 |
| 命中仍计全额 | 报表算 0 省，账单没降 | 归因失真 |

第一条是安全事件，第二条是正确性事件，第三条只是账目问题——但第三条会让前两条更难被发现，因为成本曲线"看起来很健康"。

正确的键是 `hash(question, tenant, index_version)`。三个分量各有理由：问题决定语义、租户决定数据边界、索引版本决定内容时效。

**索引版本这一项最容易被忘。** 第 19 章的文档更新如果没让缓存失效，一次政策修改对缓存命中的流量完全无效——表面上"新政策已上线"，实际一半的请求还在拿旧答案。

### 1.4 成本归因的三个口径

同一笔钱，按三种口径拆，回答三个不同的问题：

| 口径 | 拆法 | 回答 |
|---|---|---|
| 按阶段 | 路由/检索/生成/自审 | 该优化哪一段 |
| 按租户 | 每个客户用了多少 | 该向谁收费 |
| 按功能 | 问答/审批/批处理 | 这条产品线值不值 |

第一种是技术视角，第二种是商业视角，第三种是产品视角。**三者不能互相替代**：按阶段拆不出"哪个客户在烧钱"，按租户拆不出"哪段代码贵"。

实际系统里三者用同一份数据、不同的分组维度。这就要求 span 上同时带阶段（`kind`）、租户（`tenant_id`）与功能（`feature`）三个标签——第 27 章 4.3 的扩展字段就是为这个准备的。

第三行的"值不值"最容易吵：一个功能成本占比 30%、使用率 2%，是否该下线？这已经不是成本问题，而是产品判断。但**没有按功能拆的成本，这个判断连讨论的起点都没有。**

## 二、慢在哪

延迟有两条曲线：一条是用户感知的（多快看到第一个字），一条是计费的（一次请求占多久）。两者的优化手段不同。

`latency_breakdown.py` 把一次 4.4 秒的请求拆成五段：

```
=== 1. 一次请求的延迟分解 ===
  段               耗时(ms)    累计(ms)     占总量
  排队                 120       120    2.7%
  检索                 400       520    9.0%
  模型首字节              900      1420   20.4%
  生成                2400      3820   54.3%
  工具调用               600      4420   13.6%
  TTFT = 排队 + 检索 + 首字节 = 1420ms
  总延迟 = 4420ms，TTFT 占 32.1%
```

### 2.1 TTFT 与总延迟

TTFT（首字节时间）是"用户从点击到看到第一个字"的时长，它包含排队、检索与模型的首字节，不含生成。

| 指标 | 优化手段 | 用户体验 |
|---|---|---|
| TTFT | 减少前置步骤、并行、流式 | 感觉快 |
| 总延迟 | 减少生成长度、换快模型 | 等待结束得早 |

第二行的优化对第一行没有帮助：把生成从 2400ms 降到 1200ms，TTFT 仍然是 1420ms。**用户"觉得快不快"主要由 TTFT 决定**，因为第一个字出现之后，后续内容在陆续到达。

反过来，把检索从 400ms 降到 40ms，TTFT 直接降 360ms——这是流式之外最有效的一类优化。

生成占 54.3%，看起来最大，但它是最不该优先优化的：减少生成长度会牺牲完整性，而它在用户感知上已经被流式掩盖了。

这两条曲线还对应两种不同的验收方式：**首字节用"用户可感知的等待"验收（通常 1 秒以内），总延迟用"任务总时长"验收（第 25 章的同步超时、异步轮询）。** 把两者混成一个"延迟"指标，会导致为了首字牺牲完整性，或者反过来。

### 2.2 并行化的真实收益

```
=== 2. 三种优化各省多少 ===
  检索与工具并行                           4020ms  （省  400ms， 9.0%）
  流式输出（首字节不变）                       4420ms  （省    0ms， 0.0%）
  模型换小一档（首字节 900 -> 500）            4020ms  （省  400ms， 9.0%）
  检索加缓存（400 -> 40）                  4060ms  （省  360ms， 8.1%）
```

四项优化，每一项都只省 9% 左右。**这就是"优化了一圈只快了 10%"的数学原因**：总延迟是五段之和，任何一段的优化上限就是它自己的占比。

并行化的上限由"两段里较短的那一段"决定：检索 400ms 与工具 600ms 并行，能省 400ms，不是 1000ms。

第二行是流式：总延迟一分不省，但用户感知从 4420ms 变成 1420ms。**它不改变瀑布，改变的是瀑布什么时候被看见。**

### 2.3 降级链

```
=== 3. 降级链：主模型超时时 ===
  单次等待预算 2000ms
  主模型         2800ms  质量：正常        超预算，降下一级
  备用模型        5200ms  质量：正常但慢      超预算，降下一级
  语义缓存          80ms  质量：可能过期      采用，链在此停止
  <- 降级不是'换一个更快的'，是'按预算逐级降质量'
```

降级链的每一级都是"质量换时间"，而不是"换一个更快的模型"。链的顺序按质量从高到低，预算按单次等待时间。

三个设计要点：

| 要点 | 做法 | 不做的后果 |
|---|---|---|
| 每级标注质量 | "可能过期""只给原文" | 用户不知道答案降级了 |
| 预算在链外 | 一次请求的总预算 | 逐级重试把预算用光 |
| 命中即停 | 不继续往下试 | 白白多等一次 |

第一行的"标注质量"要传到用户界面：一个"可能过期"的答案与一个正常答案，应当有不同的提示。这是第 22 章"引用要能溯源"的延伸。

第二行是常见错误：每一级各有一个超时，加起来远超总预算。正确做法是先定总预算，再按剩余时间逐级试。

第三行看起来显然，但实现里常出错——降级逻辑写成"依次调用，取最后一个成功的"，结果每次都跑完全链。

### 2.4 分位数视角

平均值会骗人。一次请求 4.4 秒，但如果 5% 的请求要 12 秒，用户感受到的是那 5%。

| 指标 | 含义 | 用途 |
|---|---|---|
| P50 | 一半请求快于它 | 看"典型体验" |
| P95 | 5% 的请求慢于它 | 看"坏体验" |
| P99 | 1% 的请求慢于它 | 看"极端情况" |
| 平均 | 总量除以次数 | 算容量与成本 |

第四行是唯一适合做容量规划的：它对应总时长。**但用它来描述体验是错的**：一个 4.4 秒的平均值，可能来自 90% 的 2 秒与 10% 的 26 秒。

分位数的区间要用 bootstrap（第 30 章 2.5）：从样本里有放回抽样一千次，每次算一个 P95，取 2.5% 与 97.5% 分位。它比正态近似可靠，因为延迟分布是长尾的。

一个实用的判读方式：**P50 与 P95 的差，就是"抖"的程度。** 差 2 倍说明偶发慢；差 5 倍说明系统里有排队或重试——而这两样通常来自下游限流或锁竞争，不是模型本身。

### 2.5 成本与延迟的联合优化

大多数优化同时改变两个数，只报一个就会把交换说成改进：

| 优化 | 成本 | TTFT | 总延迟 |
|---|---|---|---|
| 检索结果缓存 | 略降 | 降 | 降 |
| 加一轮自审 | 涨 | 涨 | 涨 |
| 换小一档模型 | 降 | 降 | 降 |
| 加长上下文 | 涨 | 涨 | 涨 |

第一行是真正"双赢"的那一类，也最少：缓存命中省了一次检索的钱与时间。

第二行与第四行是"用成本换质量"，必须同时报质量指标（第 28 章的四个数），否则看起来就是"变慢了、变贵了"。

**一个团队的优化清单里如果全是双赢项，说明它没在做真正的取舍。** 真实的系统里，取舍才是主要工作：多一轮自审值不值那 18.8% 的成本、加长上下文值不值那 35% 的输入，这些都要用质量差异去换。

## 三、事故之后

前两节是常规优化。这一节处理非常规：一次事故已经发生，怎么从它走到"不再发生"。

`postmortem_to_case.py` 用一次真实形态的事故走完整条链路：

```
=== 1. 事故记录 ===
  id      INC-0314
  start   2026-03-14 10:20
  end     2026-03-14 11:05
  symptom 生鲜退货咨询回答'可以退'，实际政策不支持
  impact  37 次会话给出错误承诺
```

### 3.1 五问法

```
=== 2. 五问法 ===
  问 1：为什么答错？——回答依据的块写着'7 天内可退'，没有生鲜例外
  问 2：为什么依据了那一块？——检索把 15 天版本的旧块排在了第一条
  问 3：为什么旧块还在？——文档更新时新块插入了，旧块只标了 inactive，没有过滤
  问 4：为什么没有过滤？——检索实现里没写 active 条件，靠调用方自觉
  问 5：为什么靠调用方自觉？——入库与检索是两个模块，'失效'语义没有统一在一处
```

五问的目标不是问满五层，而是问到一个"可以改结构"的位置。

问 2、3 都还是症状：一个是排序，一个是过滤。问到问 5，答案从"某处忘了写条件"变成了"两个模块各自定义失效"，这才是一个能改的地方——把失效语义收到存储层（第 19 章 1.3）。

**停在"忘了加条件"的复盘，修复方式是"加一个 if"。** 下一次新增一条检索路径，同样的 if 还会漏。停在"语义没有统一"，修复方式是把过滤写进 `search()` 内部，新路径自动继承。

### 3.2 失败分类

```
=== 3. 失败分类 ===
  归到「数据与版本」：旧版本块未过滤、条目过期
  修复方向：检索层加版本过滤，而不是改提示词
```

| 类 | 典型根因 | 修复落点 |
|---|---|---|
| 数据与版本 | 旧块未过滤、条目过期 | 检索与入库 |
| 检索质量 | 召回缺失、排序不当 | 索引、改写、重排 |
| 生成 | 编造、漏要点 | 提示词、引用约束 |
| 编排 | 步数、终止条件 | 循环 |
| 权限 | 越权、审批绕过 | 边界与审批 |
| 基础设施 | 超时、限流、依赖故障 | 部署与容量 |

分类的作用是**决定改哪里，以及该找谁**。归错类的代价很大：一个"数据与版本"问题被归成"生成"，团队会去改提示词，改一周之后指标没动，再回头查检索。

分类的判据来自第 28 章的分层指标：检索层不合格就是前三类，生成层不合格才是第四类。

### 3.3 MTTD 与 MTTR

两个数字衡量"出事之后多久能恢复"，它们各自指向不同的改进：

| 指标 | 从哪到哪 | 优化手段 |
|---|---|---|
| MTTD（发现时间） | 出错到有人知道 | 告警、监控、用户反馈通道 |
| MTTR（恢复时间） | 知道到恢复 | 回滚、降级、值班流程 |

示例里 10:20 出事、11:05 恢复，45 分钟。如果 MTTD 占了 40 分钟，说明问题在"没人发现"——再快的修复流程也没用。

**这两个数要分开报。** 一个团队把 MTTR 从 20 分钟压到 5 分钟，但如果 MTTD 是 40 分钟，用户感知的故障时长仍然是 45 分钟。

MTTD 的改进通常比 MTTR 便宜：一条基于"错误率突增"的告警，可能就能把 40 分钟压到 5 分钟。而 MTTR 的改进依赖回滚能力、灰度、值班——都是重投入。

### 3.4 复盘会怎么开

一次复盘会要产出四样东西，缺一样它就变成"追责会"或"漫谈会"：

| 产出 | 内容 | 不产出的后果 |
|---|---|---|
| 时间线 | 什么时候发生了什么 | 讨论变成回忆 |
| 根因 | 五问走到的那一层 | 修复停在表面 |
| 行动项 | 谁、做什么、什么时候 | 会后没人动 |
| 用例 | 旧配置失败、新配置通过 | 半年后原样复发 |

第一行要在会前准备好，用第 27 章的 trace 与日志拼出来。会上现拼时间线，时间都花在"当时是谁点的"这种问题上。

第二行是会议的核心，也是最容易滑向追责的地方。**一个可用的规矩是"对事不对人"写成具体的问法**：不问"你为什么没加过滤"，问"检索路径为什么可以不带过滤条件"。

第三行的"谁、什么时候"要具体到人能认领。行动项写"改进检索"等于没有行动项；写"把 active 过滤写进 search()，周五前"才有。

第四行是这一章第四节的落点。**没有用例的复盘，等于给同一次事故留了回访日期。**

复盘会的时长也有讲究：超过一小时，讨论通常会滑向"要不要重构"。可用的做法是限时四十分钟，把那类大问题另开专题——**事故复盘解决"这一次"，架构讨论解决"这一类"，混在一起两个都做不完。**

### 3.5 复盘样例的读法

一份复盘文档要被后来的人读懂，四个字段不能省：

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| 时间线 | 什么时候发生了什么 | 后人只能猜 |
| 影响 | 多少用户、多少成本 | 无法排优先级 |
| 根因 | 问到了哪一层 | 修的是症状 |
| 用例 | 哪条测试挡住了复发 | 半年后复发 |

第二行决定了这次复盘值多少钱花：37 次会话与 3.7 万次会话，处理力度完全不同。

第四行是这一章的核心：**没有用例的复盘，在文档系统里看起来完整，在系统里什么也没留下。** 一次复盘产出的真正资产只有两样——一条结构化根因（下次同类问题能快速归类）与一条用例（这次输入不再回归）。

其余部分（时间线、影响、讨论记录）是证据，不是资产。

## 四、事故变用例

事故复盘的最后一步不是写报告，是**把这次输入固化成一条用例**。

### 4.1 用例的四要素

```
  {
    "case_id": "reg-0314-01",
    "question": "生鲜订单可以无理由退货吗？",
    "must_contain": "不支持",
    "must_not_contain": "可以退",
    "source": "INC-0314"
  }
```

四样缺一不可：

| 要素 | 作用 |
|---|---|
| 输入 | 能复现那次调用 |
| 必须包含 | 正确答案的关键结论 |
| 必须不包含 | 当时的错误说法 |
| 来源 | 指回事故编号，便于复查 |

第三条是它区别于普通用例的地方：普通用例只验"对不对"，事故用例还要验"那个错法不再出现"。两个判据一起用，才能挡住"改对了结论但换了个错法"。

第四条让用例集可追溯：三个月后有人问"这条用例为什么在"，答案是一个事故编号，而不是"某个人加的"。

### 4.2 旧配置跑一遍

```
=== 5. 旧配置与新配置各跑一遍 ===
  [old] 召回 policy#4@v1  回答：根据policy#4@v1：生鲜商品签收后 7 天内可退。
         判定：失败（缺少关键结论'不支持'）
  [new] 召回 policy#4@v2  回答：根据policy#4@v2：生鲜类商品不支持无理由退货。
         判定：通过（结论正确）
```

这一步是整条链路里最容易被跳过、也最重要的：**用例必须在旧配置上失败。** 如果它在旧配置上也通过，说明这条用例没有复现那次事故——它抓的是别的东西，或者事故的根因还没找到。

三种组合的结论：

| 旧配置 | 新配置 | 结论 |
|---|---|---|
| 失败 | 通过 | 修复有效，用例进回归集 |
| 通过 | 通过 | 没复现，用例要重写 |
| 失败 | 失败 | 根因还在，别急着写复盘 |

第一种是唯一可以宣布"修好了"的组合。第二种最危险，因为它看起来一切正常，而事故随时会回来。

### 4.3 用例集的增长方式

事故用例应当只增不改，与第 28 章 5.4 的评测集规则一致。它的规模增长缓慢——一年几十条——但每一条都是"真发生过"的。

| 来源 | 数量级 | 价值 |
|---|---|---|
| 事故复盘 | 每年几十条 | 最高：真实、有判据、有来源 |
| 误杀投诉 | 每年上百条 | 高：直接改善体验 |
| 主动构造 | 每季度一批 | 中：覆盖未发生的场景 |

第一行的价值最高，因为它的判据是"已经被违反过的"，不需要论证。**一个团队的回归集里如果一条事故用例都没有，说明复盘没有落到用例上。**

### 4.4 回归集怎么跑

事故用例写进回归集之后，要能被自动执行，否则它会和文档一样腐烂。

| 位置 | 何时跑 | 耗时预算 |
|---|---|---|
| 提交级 | 每次提交 | 分钟级 |
| 发布级 | 每次发布 | 十分钟级 |
| 夜间 | 每天一次 | 小时级 |

第一行只能放"快且确定"的用例：事故用例大多是单次问答，几十条跑完在几分钟内，适合放这里。

第二行放多轮、审批、需要重复跑的用例（第 29 章四层评测里的稳定层）。

第三行放需要重复多次或依赖外部服务的用例。它跑得慢，但能在第二天早上给出"昨晚有没有新的退化"。

**事故用例应该优先放在第一行**：它的目的是"不让同一次事故复发"，而越早发现越便宜。一个在夜间才发现的回归，可能已经在灰度里跑了几个小时。

失败的处理也要定：第一行失败应当阻止合并（第 30 章 3.5），第三行失败应当开一条工单并在第二天处理。两者都用"失败即通知"，不区分的话，团队会把所有失败都当噪声。

## 五、会怎么坏

**第一，只报总成本。** "一次 0.056 元"无法回答该省哪一段。信号是成本报表只有一列。

**第二，只有单任务预算。** 单次都合规，月度总额翻倍。信号是预算只在一个地方定义。

**第三，缓存键不含租户。** 跨租户命中，答案串户。信号是缓存键的构成本里没有问题文本以外的分量。

**第四，缓存不随索引失效。** 政策改了，一半流量还在答旧版本。信号是缓存键里没有索引版本。

**第五，只优化总延迟。** 用户仍觉得慢，因为 TTFT 没变。信号是延迟报表里没有首字节这一个指标。

**第六，降级链没有总预算。** 逐级重试，一次请求等了三倍时间。信号是每级各有超时、没有全局上限。

**第七，复盘停在"忘了加条件"。** 修了这一处，下一处照旧。信号是复盘的结论是一句操作说明，而不是一个结构问题。

**第八，事故用例在旧配置上也通过。** 以为修好了，其实没复现。信号是用例没有在修复前跑过。

**第九，降级没有被统计。** 降级率上升没人知道，只看到"延迟变好了"。信号是报表里没有"降级次数"这个字段。

**第十，复盘的行动项没有复查。** 会后写了五条，下次复盘发现三条没做。信号是行动项没有跟踪单号。

## 六、边界

**第一，成本瀑布依赖 span 的分阶段归因。** 第 27 章没记 `kind` 与 token，这一章的瀑布就做不出来。**可观测的字段设计是成本优化的前置条件。**

**第二，三级预算的阈值要随业务调整。** 增长期与稳定期的容忍度不同，阈值不动就会出现"所有任务都被限流"。

**第三，语义缓存的收益在高频重复提问上才明显。** 一个长尾问题的集合，命中率可能只有 5%，而它引入的失效与串户风险不变。**先量命中率，再决定要不要上缓存。**

**第四，延迟优化的上限由瀑布的占比决定。** 一个生成占 80% 的系统，把检索优化到 0 也只能省 20%。想大幅降低延迟，必须改生成方式（流式、更短的输出）。

**第五，降级链的每一级都要有质量标注。** 没有标注，用户无法判断答案的可信度，团队也无法统计"降级率"。

**第六，MTTD 与 MTTR 依赖观测与流程，不是本章的代码能解决的。** 这一章只给出两个数字的定义与它们的分工。

**第七，事故用例不能覆盖"没发生过"的问题。** 它是回归网，不是探索网。探索靠第 28、29 章的评测集与红队（第 22 章）。

**第八，成本与延迟的优化常常互相冲突。** 加缓存降成本但可能提高首字节（多一次查询）；并行化降延迟但提高并发与成本。一次改动要同时报两个数，否则会把一次交换说成一次改进。

**第九，本章的复盘样例是"单点事故"。** 还有一类是缓慢退化：三个月里错误率从 2% 涨到 6%，没有单次事故可复盘。它靠第 30 章的双基线（与三个月前比）发现，而不是靠复盘。

### 6.1 卷五的收束

卷五到这里完整了。五章回答的是同一个问题：**怎么用一个数字证明改动变好或变坏。**

| 章 | 回答 | 产物 |
|---|---|---|
| 27 | 能不能看见 | span 树、字段口径 |
| 28 | 答得对不对、坏在哪 | 分层指标、四个数 |
| 29 | 过程对不对、裁判可信吗 | 四条判据、kappa |
| 30 | 这个差异算不算数 | 区间、门禁 |
| 31 | 钱与时间花在哪、怎么不再犯 | 瀑布、复盘、事故用例 |

五章的依赖是单向的：没有 span 就做不出分层归因，没有分层就没有可比的指标，没有区间就不知道指标的变化算不算数，没有复盘就不知道下一个指标该测什么。

一个贯穿全卷的判据：**任何一次"我们变好了"的结论，都应该能追到三样东西——一个指标、一个区间、一次回归验证。** 缺任何一样，那句结论就只是印象。

## 这一章建立的 5 件事

1. 成本要按阶段拆开：示例里生成 35.8%、子 agent 汇总 35.6%、自审 18.8%；三段各自的省法不同，只看总成本无法行动。
2. 预算要三级：单任务防失控、租户日防刷量、平台月防整体超支。三级阈值要能互相推导，否则配额设计有问题也看不出来。
3. 语义缓存的三条红线是跨租户、不随文档失效、命中仍计全额；正确的键是 `hash(问题, 租户, 索引版本)`。
4. TTFT 与总延迟要分开看：流式不改总延迟，只改 TTFT；并行化的上限是较短那一段的占比，所以一轮优化常常只快 10%。
5. 复盘要问到"能改结构"的位置，并固化成一条"旧配置失败、新配置通过"的用例；停在一句操作说明的复盘，下一次还会犯。
