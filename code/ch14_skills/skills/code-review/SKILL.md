# 代码审查

## 什么时候用

用户说「review 一下」「看看这个改动有没有问题」「检查下 diff」时。

**不要用于**：写新功能（那是另一件事）、跑测试（那是工具的事）。

## 步骤

1. 先读完整 diff，不要只看文件名就下判断
2. 确认改动意图：新功能 / 修 bug / 重构。意图不明就先问
3. 按风险排序，从高到低：
   - 数据丢失（删表、覆盖写、丢字段）
   - 权限越界（谁能调到、鉴权有没有漏）
   - 逻辑错误（边界、空值、并发）
   - 可维护性（命名、重复、缺注释）
4. 每个问题必须给出 `文件:行号`，不要泛泛而谈
5. 没发现问题就明说「没发现高风险问题」，不要为了凑数提风格问题

## 输出格式

```
## 结论
<一句话：可以合 / 需要改 / 必须拦>

## 问题（按风险排序）
1. [高] 文件:行号 —— 什么问题、为什么危险
2. [中] ...

## 未覆盖
<哪些地方你没看，为什么>
```

## 常见错误

- ❌ 只报「建议加注释」这类低价值问题
- ❌ 没读全 diff 就下结论
- ❌ 说「可能有并发问题」但不说具体在哪一行
