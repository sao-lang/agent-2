# 定位与学习路径

> 分册：《Agent 工程》大纲 · 交付物、主线/副线、七条能力
> 全局约定、章号与「写哪章读哪册」见 [docs/OUTLINE.md](../docs/OUTLINE.md)。

## 一、这本书交付什么

**读完能独立设计、实现、交付一个 agent 系统，并能解释每一个设计决定的取舍。**

| # | 交付物 | 怎么证明 |
|---|---|---|
| 1 | 说得清 agent 是什么 | 能回答"它和一次模型调用差在哪"，并指出差别带来的全部新问题 |
| 2 | 讲得清机器 | 说得出"它为什么编 / 为什么忘 / 为什么停不下来" |
| 3 | 写得出一个能跑的 agent | 不用框架，从一次调用的 HTTP 请求写到多步循环 |
| 4 | 判断得出该不该上 agent | 拿到需求能说出走哪条路、为什么、成本上界 |
| 5 | 交付得出工程化系统 | 可部署、可观测、可评测，出过事故能复盘 |
| 6 | 拆得开一个 harness | 能说出"哪些能力被做成了可替换的部件"，以及为什么这么切 |

第 1、3 项是这本书的位置：市面上不缺"用框架搭一个 demo"的资料，缺的是**从一次调用开始，把每一步为什么必须有它讲清楚**的资料。

## 二、主线与副线

### 2.1 主线：三层认知

```
第三层  工程化    从"能跑"到"敢上线"：约束、持久、度量、交付
                    ↑ 为什么需要：系统会被人用错、会被断电、会被要求证明
第二层  agent     从"一次调用"到"一个循环"：工具、终止、状态、编排
                    ↑ 为什么需要：一次调用解决不了需要多步的任务
第一层  模型      一次调用到底发生了什么：messages、usage、finish_reason、token
                    ↑ 为什么需要：所有上层的坏法最终都能追到这一层
```

**学习顺序必须由内向外**，因为外层的每个设计决定都在补偿内层的某个事实：

| 外层的东西 | 补偿的是内层的哪个事实 |
|---|---|
| 循环与终止条件 | 模型只输出 token，不会"停下来" |
| 工具调用 | 模型不能执行任何东西，只会生成文本 |
| 上下文裁剪 | 窗口是硬上限，超了就丢 |
| 状态与检查点 | 进程会死，模型没有记忆 |
| 护栏与审批 | 模型的输出可以被说服，代码不会 |
| 评测 | "感觉变好了"不是证据 |

### 2.2 副线：harness 组件封装（卷 12）

主线讲完，读者手上有二十几个各自讲透的原理，以及一堆互不相干的一次性脚本。副线回答的是另一个问题：

> **如果要把这些原理组织成可替换、可单测、可组合的部件，该沿哪条线切、怎么定契约？**

副线与主线的关系是"回头看"，不是"边学边造"：

| | 主线（卷 1–11） | 副线（卷 12） |
|---|---|---|
| 目的 | 说清每个设计为什么必须有 | 说清为什么能单独换掉一个 |
| 代码形态 | 每章独立、可直接运行的小程序 | 一个包，组件之间只通过契约通信 |
| 读者要拿到的 | "我知道它为什么存在" | "我知道它为什么能替换" |
| 能不能跳过 | 不能 | 能（只读卷 1–5、7 也成立） |

**硬规定**：主线正文不出现 harness 的封装代码、类名、模块名；不出现"本章给 Harness 装上 X 组件"。副线的任何概念（契约、插点、依赖规则）在主线中不得预先使用。

## 三、七条主线能力

| # | 主线 | 学完的标志 |
|---|---|---|
| S1 | **模型心智** | 能预判一段提示词会怎么被带偏 |
| S2 | **上下文经济学** | 能对任意一次调用报出 token / 成本 / 延迟三个数并解释来源 |
| S3 | **循环与终止** | 能写出一个不会跑飞的循环 |
| S4 | **知识供给** | 能设计从文档到回答的完整链路，并对坏回答做归因 |
| S5 | **编排与范式** | 能对需求给出范式判断并说明代价 |
| S6 | **边界与耐久** | 能设计出"撞得住"的系统 |
| S7 | **度量与交付** | 能用一个数字证明某次改动变好或变坏 |

七条全部落在主线上。副线不新增能力，只增加**把能力组织起来的方法**；框架卷（3、8、9）同样不新增能力，它给出的是**同一套能力的另一种装法**——用现成部件、接现成平台。
