## 第 59 章素材 · LLM Wiki（G6）

> **它是什么**：把语料**离线编译**成一套持久化的 Markdown wiki（条目 + 交叉链接 + 来源回指），查询时读取条目、而不是每次重新检索块。语料编译一次、之后增量维护。它是 2026 年 Karpathy 提出的设计，社区把它当作"编译出来的语义记忆"，而不是 RAG 的替代品。
>
> **放在深水区的理由**：它不是主线的一环，而是一条**不同的设计点**——主线 13–21 讲"每次查询怎么找到并拼装依据"，这一篇讲"如果把依据提前编译成一篇篇文章会怎样"。两者会长期并存，选哪条取决于语料的更新频率与规模。
>
> **与第 21 章的分界**：21 章（C12）讲**条目的治理**（要点/例外/来源、矛盾检测、可溯源率）；这一篇讲**整库编译成 wiki 的架构选择**（要不要编译、怎么编译、编译坏了怎么修）。

### 1. 缺什么：RAG 每次都在重建同一份知识

RAG 的四环节（检索→拼装→生成→引用）里，前三步每次查询都要重做一遍：同一份政策文档，今天为问题 A 被切成块、拼进上下文，明天为问题 B 再切一次、再拼一次。这带来四个结构性代价：

| 代价 | 表现 |
|---|---|
| 块边界破坏语义 | 一段结论被切成两半，检索命中前半段，答案缺后半段 |
| 检索失败 ≠ 知识不存在 | 问题答不出，但答案就在库里，只是块没被召回 |
| 同一知识重复推理 | 同一份材料每天被重新理解一遍，成本按查询次数乘 |
| 中间产物不可审阅 | 用户看到的是答案，看不到"系统认为的知识是什么" |

LLM Wiki 的出发点是：**把"理解"这一步提前到编译期，只做一次**。

### 2. 怎么做：编译流水线

| 步 | 做什么 | 失败长什么样 |
|---|---|---|
| ① 主题抽取 | 从语料里聚出条目（topic），而不是切块 | 主题过细→条目碎；过粗→一条塞十件事 |
| ② 大纲 | 先产出目录与条目清单，供人审 | 大纲偏→整库偏（后面全白做） |
| ③ 逐条撰写 | 每条一篇：要点、例外、来源、交叉链接 | 模型把"例外条款"写丢（编译缺口） |
| ④ 交叉链接 | 条目之间建图（`[[...]]`），形成导航 | 链接名实不符，点进去不是那件事 |
| ⑤ 来源回指 | 每段结论标回原文位置 | 无法核对，出错只能整条重写 |
| ⑥ 校验 | 诊断探针：拿一批问题问 wiki，看哪些事实丢了 | 只测"能不能答"，不测"丢了什么" |
| ⑦ 发布与增量 | 版本化；语料变了只重编译受影响的条目 | 全量重编译，成本随语料线性增长 |
| ⑧ 服务 | 全文/向量辅助导航 + 条目整篇进上下文；或整库走 KV cache | 条目太长，整篇塞不进窗口 |

**关键认识：编译会丢事实。** 有研究报告（WiCER，2026）测过：盲目编译的失败率高达 53–60%，质量从 3.46 掉到 2.14–2.32（5 分制）。所以第 ⑥ 步不是可选项——它要做的是**诊断**（哪些事实被丢了）而不是**打分**（整体好不好）。补齐的方式是编译—评估—精修的迭代：1–2 轮能把 80% 的损失找回来，灾难性失败减少约 55%。

### 3. 与 RAG 的六项差异

| 维度 | RAG | LLM Wiki |
|---|---|---|
| 时间 | 每次查询现做 | 编译一次，增量维护 |
| 单位 | 块（几百 token） | 条目（一篇完整主题） |
| 读取方式 | 向量/关键词召回 Top-k | 导航（目录、链接、全文）+ 整篇进上下文 |
| 失败形态 | 召回不到、拼装稀释 | 编译丢事实、大纲偏、条目陈旧 |
| 可审阅性 | 差（只看到答案） | 好（中间产物就是一份可读的 wiki） |
| 更新成本 | 低（重切块即可） | 高（要重编译受影响条目） |
| 规模上限 | 大（百万级块） | 中（个人/团队级知识库） |
| 延迟 | 检索 + 拼装 | 更低（条目现成；整库 KV cache 可到亚秒级） |

**它不是 RAG 的替代。** 有实测显示：在"语料受控"的场景下，整库直接进上下文（或 KV cache）优于 RAG（4.38 vs 4.08，首 token 快 7.3 倍）；但规模一大就因注意力稀释而退化，公开研究里也有两个领域没有跑赢 RAG。**分界是语料规模与更新频率，不是"新旧"**。

### 4. 什么时候选它

| 适合 | 不适合 |
|---|---|
| 语料稳定、篇数有限（个人或团队知识库） | 每天都在变的语料 |
| 需要长文档的整体理解（政策、手册、代码库） | 长尾事实型查询（问一个具体数字） |
| 需要可审阅的中间产物（合规、教学） | 百万级块的公共知识库 |
| 同一个问题会被反复问 | 一次性、临时性的语料 |

### 5. 失效与度量

| 失效 | 信号 | 度量 |
|---|---|---|
| 编译丢事实 | 答案缺例外条款 | 诊断探针的"丢失事实率" |
| 大纲偏 | 条目覆盖不到问题 | 覆盖矩阵：问题集 × 条目 |
| 条目陈旧 | 政策改了，wiki 没改 | 陈旧率 = 未随语料更新的条目 / 总条目 |
| 链接名实不符 | 点进去不是那件事 | 链接抽样核对 |
| 来源丢失 | 出错无法回溯 | 可溯源率（沿用第 21 章） |
| 成本失控 | 每次更新都全量重编译 | 单条更新成本、全量重编译频率 |

### 6. 与主线的关系

- **读起来像第 21 章的下游**：21 章定条目结构与治理规则，这一篇把它推到"整库编译"。
- **和第 19 章互补**：wiki 条目是"装配时的一类素材"，占的是检索槽位（或记忆槽位），仍要过预算与抢占。
- **和第 20 章互补**：编译产物本身可以充当 agent 的**程序记忆**（这类事怎么办），只是它由语料编译而来，不是由对话抽取而来。
- **不写进主线的理由**：它需要一整套新的工程（编译流水线、诊断探针、增量重编译），且规模上限明确；放进主线会打断"每次查询怎么做对"这条因果链。

### 7. 必给示例（第 59 章）

- 一份 20 篇文档的语料，编译出 8 条条目（含交叉链接与来源）——贴出目录与其中一条的全文。
- 同一个问题，RAG 的 Top-3 块与 wiki 的对应条目并排，标出"块缺了哪句、条目补上了哪句"。
- 一次诊断探针：5 个问题里有 2 个答案缺事实 → 修编译提示 → 再编译 → 复测。
- 一次增量：改一篇源文档 → 只重编译 1 条条目 → 贴出 diff。
