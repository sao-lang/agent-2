## 二、共用的写法

- 沿用主线骨架：缺什么 → 成因 → 怎么补 → 做法对比 → 会怎么坏 → 边界。
- 每节第一句是判据或失效，不是定义；名字第一次出现要写明"决定权/成本放在哪"。
- 代码示例必须"代码 + 说明 + 真实输出"三件齐全；数字来自脚本，不手填。
- 两章的示例都用**脚本化替身**（规则抽取、模板编译），必须在章首与对应小节标注"原理演示，不是真实 LLM 抽取/长文生成"；接真实模型时替换哪一行，要写清。
- 每章至少一处"失败输出"：58 章是实体消歧错误导致的错误答案；59 章是诊断探针发现的缺事实条目。

## 三、第 58 章 · GraphRAG（节级）

| 节 | 讲什么 | 必给的东西 |
|---|---|---|
| 58.1 三类问题 | 多跳、聚合、关系型问题；每类给一个向量 Top-k 必然答不对的例子 | 三类问题 × 向量检索失败原因表 |
| 58.2 实体与关系 | 从文档抽实体、关系、属性；实体消歧与关系方向；抽取的调用成本 | 抽取结果表（实体/关系/来源）与一次消歧错误 |
| 58.3 二部图与 PPR | 查询节点、块节点、实体节点怎么连；二部图上的 Personalized PageRank；重启概率与迭代次数 | PPR 迭代公式 + 完整函数 |
| 58.4 一次多跳查询 | 同一问题分别走 Top-k 与 PPR，比较证据链；回答差在哪 | 两种证据的并排输出与差异标注 |
| 58.5 成本账 | 离线抽取、图存储、查询迭代三段成本；5–20 倍的构成；规模阈值 | 成本表：索引 token/调用、图规模、查询 token；与普通 RAG 的倍数 |
| 58.6 混合检索 | 先用向量找实体、再图上扩展；GraphRAG 与 hybrid 的取舍 | 一张判据表：普通 RAG / hybrid / GraphRAG |
| 58.7 会怎么坏 | 实体消歧错、关系方向错、图陈旧、过度抽取、PPR 走到噪声 | 每条给信号与第一个检查点 |
| 58.8 边界 | 语料规模、更新频率、问题类型；什么时候不值得 | 边界清单 |

**必给示例**（`code/knowledge/ch58_graphrag/`）：

1. `build_graph.py`：12 篇小文档 → 实体/关系表 → 二部图；打印节点数、边数、抽取调用次数。
2. `ppr_compare.py`：同一多跳问题，向量 Top-k 的证据 vs PPR 的证据；打印两边命中的块、缺失的关键一跳、最终答案差异。
3. `cost.py`：普通 RAG 与 GraphRAG 的索引/查询成本对照；把 5–20 倍拆成"抽取 + 图存储 + 迭代"三块。
4. `entity_resolution.py`：两家同名公司被合并成一个实体，导致答案错；打印错误实体、错误关系、错误结论。

**与第 18 章的分工**：18 章讲"已召回的怎么排得更准"（混合、重排、MMR、改写）；58 章讲"召回之前先走图"，不重复 BM25/向量/重排的实现。

**与第 14 章的分工**：14 章是 RAG 四环节的总图；58 章只补"检索这一环换成图"的增量，不重讲拼装与引用。

## 四、第 59 章 · LLM Wiki（节级）

| 节 | 讲什么 | 必给的东西 |
|---|---|---|
| 59.1 重复重建 | 同一份知识每次查询都被重新切块、拼装、理解；四个结构性代价 | 四代价表 + 一次重复付费的账 |
| 59.2 编译流水线 | 主题抽取、大纲、逐条撰写、交叉链接、来源回指、校验、发布与增量、服务 | 八步表：每步做什么、失败长什么样 |
| 59.3 编译会丢事实 | 编译不是无损压缩；缺例外条款、丢来源、条目过粗 | 一次"编译后答案少一句"的失败输出 |
| 59.4 诊断探针 | 不问"整体好不好"，问"哪些事实丢了"；compile-evaluate-refine | 5 个问题的探针表、2 个缺事实、修编译提示、复测 |
| 59.5 与 RAG 的差异 | 时间、单位、读取、失败、可审阅、更新成本、规模上限；不是替代 | 六项差异表 + 一段"哪个场景选哪个" |
| 59.6 增量编译 | 语料变了只重编译受影响条目；版本与 diff；陈旧率 | 改一篇源文档 → 只重编译 1 条 → diff |
| 59.7 选型与边界 | 语料稳定/有限、需要整体理解、需要可审阅产物时选它；规模与更新频率的阈值 | 适合/不适合表 + 规模边界 |
| 59.8 会怎么坏 | 大纲偏、编译缺口、条目陈旧、链接名实不符、全量重编译 | 每条给信号与度量 |
| 59.9 边界 | 不是 RAG 替代；不是实时知识；不是百万级公共库 | 边界清单 |

**必给示例**（`code/knowledge/ch59_llm_wiki/`）：

1. `compile.py`：20 篇小文档 → 8 条条目（含交叉链接、来源）；打印目录与其中一条全文。
2. `compare_rag.py`：同一问题，RAG Top-3 块 vs wiki 条目；标出块缺了哪句、条目补上了哪句。
3. `probe.py`：5 个诊断问题，2 个答案缺事实；改编译模板后重编译，再复测；打印前后对照。
4. `incremental.py`：改一篇源文档，只重编译 1 条，打印 diff 与未受影响条目数。

**与第 21 章的分工**：21 章讲"单条目的结构、矛盾检测、可溯源率"；59 章讲"整库要不要编译成 wiki、怎么编译、编译坏了怎么修"，不重讲条目字段与治理规则。

**与第 19、20 章的分工**：19 章讲装配预算，20 章讲长期记忆；59 章只说明 wiki 条目会占用哪个槽位、编译产物如何充当程序记忆，不重讲槽位算法。

## 五、代码与运行约定

- 两章都**不联网**、只用标准库（图算法手写 PPR，不依赖 graphrag/networkx）。
- 58 章的抽取是规则替身：按句式匹配"X 是 Y 的供应商""Y 的 CEO 是 Z"；正文标注"换成真实 LLM 抽取时，只替换 `extract()` 一行"。
- 59 章的编译是模板替身：按文档标题生成条目骨架；正文标注"换成真实 LLM 长文生成时，只替换 `write_entry()` 一行"。
- 每个入口脚本单独可跑；输出逐字进正文。
- 运行前设 `PYTHONIOENCODING=utf-8`；不需要 API key。

## 六、验收

### 6.1 通用

- [ ] 章首四行齐全，知识点为 G4 / G6。
- [ ] 中文字符 ≥ 9000（目标 10000）。
- [ ] 每节第一句是判据或失效。
- [ ] 每个做法有代码 + 输出 + 一句"说明了什么"。
- [ ] 至少一处失败输出。
- [ ] `这一章建立的 N 件事` 与 `下一章` 都在。
- [ ] 标题 ≤ 12 字，句式不全部相同。

### 6.2 内容边界

- [ ] 58 章不重讲 BM25/向量/重排/MMR 的实现（18 章），只讲"图这一层加在哪"。
- [ ] 58 章给出 5–20 倍成本的构成，不只给一个倍数。
- [ ] 59 章不重讲条目字段与矛盾检测（21 章），只讲整库编译。
- [ ] 59 章明确"编译会丢事实"，诊断探针不是可选项。
- [ ] 两章都明确"不是替代 RAG"，并给出选型判据。
- [ ] 两章的替身示例都标注"原理演示"，不冒充真实模型实测。

## 七、施工顺序

```text
58 章（GraphRAG：先写 build_graph + ppr_compare，再补成本与失效）
  → 59 章（LLM Wiki：先写 compile + compare_rag，再补诊断与增量）
    → 章首/目录/章末与 INDEX（gen_book.py build）
      → check_nav.py + check_chapters.py
```

先 58 后 59 的理由：58 的输出是"同一问题的两种证据"，读者先看到图检索补了哪一跳；59 再讲"如果把整库提前编译，连这一跳都不用走"，两章形成对照。

## 八、不写什么

- 不写微调（G1–G3）：训练基础设施与本书主线不同，留在附录。
