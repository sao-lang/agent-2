## 五、组件封装：副线的推导依据

**本节只在写卷 12 时使用。卷 1–11 的正文不得引用本节任何概念。**

### 5.0 推导起点：Agent 的四个结构事实

| # | 事实 | 推出什么 |
|---|---|---|
| **①** | Agent 的本质是**一个循环**：模型输出 →（可能）调用工具 → 结果回灌 → 再问模型 | 循环是最小骨架，没有它就是一次性的单次调用 |
| **②** | 循环的每一步都在**做决定**（要不要调工具、调哪个、算不算完成） | 需要「决策」类部件 |
| **③** | 决定需要**素材**（工具清单、检索结果、历史、记忆） | 需要「供给」类部件 |
| **④** | 循环里每件事都**可能出错且不可逆** | 需要「治理」类部件 |

组件清单 = **循环骨架 + 三类插件**。下面自下而上验证：**每个组件必须挂到一次 loop 的一个具体位置。**

### 5.1 一次 loop 的九个插点

```
   请求进来 ──▶ ① 入口：这是什么请求？走哪条路？
                   ▼
               ② 装配：这一轮让模型看见什么
                   ▼
   ┌────────────── Loop（反复执行）──────────────┐
   │  ③ 判断：要不要先拆成计划？                  │
   │        ▼                                     │
   │  ④ 决策：下一步做什么？                      │
   │        ▼                                     │
   │  ⑤ 准入：这个动作允许吗？要人点头吗？        │
   │        ▼                                     │
   │  ⑥ 执行：真的去调工具 / 真的去问模型          │
   │     （超时→重试→限流→熔断→降级 包住这一次调用）│
   │        ▼                                     │
   │  ⑦ 校验：这一步做对了吗？整体达标了吗？       │
   │        ▼                                     │
   │  ⑧ 记账：花了多少？第几步？存档了吗？         │
   │        ▼                                     │
   │  回到 ②（下一轮）或退出                       │
   └──────────────────────────────────────────────┘
                   ▼
               ⑨ 出口：整理结果、留痕、交回
```

### 5.2 九个插点 → 十五个组件

| 插点 | 要回答的问题 | 组件 | 为什么必须独立 |
|---|---|---|---|
| ① 入口 | 这是什么请求？ | **Router** | 分流决策与执行分离，才能对简单请求跳过高成本路径 |
| ② 装配 | 让模型看见什么？ | **Context** | 窗口预算与召回质量是两件事，混在一起无法归因；它决定"放几条"，不决定"取哪几条" |
| ③ 判断 | 要不要先拆计划？ | **Planner** | 计划是「可审查、可修改的数据」；塞进决策里就无法 HITL |
| ④ 决策 | 下一步做什么？ | **Actor** | 唯一必需的组件；它只做执行，不做评估 |
| ⑤ 准入 | 允许吗？ | **Guard** | 必须独立于决策：模型被说服了，Guard 不被说服 |
| ⑥ 执行 | 怎么调？ | **Tools** | 能力注册与调用分离；执行后端（本地/沙箱/MCP）可替换 |
| ⑥ 执行 | 挂一次怎么办？ | **Resilience** | 五种机制共享同一份失败计数；拆开要跨组件共享状态 |
| ⑦ 校验 | 做对了吗？ | **Reflector** | 必须能拿到**外部**证据；判定与修复共用一个 `Verdict` |
| ⑧ 记账 | 还能继续吗？ | **Budget** | 被三处读取，任一处持有都会造成反向依赖 |
| ⑧ 记账 | 发生过什么？ | **Tracer** | 跨全部插点，且必须能离线工作 |
| ⑧ 记账 | 崩了怎么续？ | **Durability** | 恢复是"重放结论"不是"重新推理" |
| ⑨ 出口 | 交回什么、以什么状态交回？ | **Delivery** | 终止态（答完/降级/拒答）、输出过滤、引用编号与格式是**决策**不是渲染；分散在各 agent 里，护栏的最后一公里就失守 |
| 循环外 | 记得住什么？ | **Memory** | 跨会话；与单次 loop 的 State 生命周期不同。它决定"取哪几条"，不决定"放几条" |
| 循环外 | 凭什么知道？ | **Knowledge** | 召回质量独立于窗口预算 |
| 循环外 | 正确流程是什么？ | **Skills** | 给流程；Tools 给能力。数量级与加载时机都不同 |

**State 不是第 16 个组件**，它是"随 loop 变化且需要持久化"那一列的容器。**Prompt 不是组件**，它是插点 ② 的产物。**Provider 与 Executor 是部件**。**Cache 归入 Budget 的实现策略**。**Session 与 State 同类**——它是持久化与隔离的单位（一个键），横跨多次 loop、挂不到任何插点上，所以也不是组件；它落在 `SessionRef` 这个数据类型里，由 `Durability` 消费（会话的开始/过期/清理由 `Durability.open/close/expire` 承担，会话级累计配额由 `Budget(scope="session")` 承担）。**拓扑（supervisor / handoff / blackboard / 流水线）同样不是组件**——它不改变一次 loop 的内部，只决定有几个 loop、谁拥有控制权，属于"组件的组合方式"，写法见 5.7 与卷 12 第 57 章。

### 5.3 五种装配形态（副线的验收方式）

**这一节是纵向：一个 agent 装多少部件。** 横向（几个 agent 怎么连）是 5.7 的四种拓扑；两者交叉成一张矩阵，副线的验收是"在矩阵里取点"，见 5.7。

| 形态 | 装哪些组件 | 获得的能力 | 验收 |
|---|---|---|---|
| 最小 | Actor + Tools | 能调一次工具并回答 | 能跑通一次工具调用 |
| 循环 | + Context + Budget + Tracer | 多步、不跑飞、可排查 | 四种失控各被拦一次 |
| 知识 | + Router + Knowledge + Memory | 会分流、会查资料、会记 | 对坏回答能归因到具体组件 |
| 生产 | 全部 15 个 | 生产形态 | 一次越权被拦 + 一次中断恢复 |
| 框架 | 用现成框架装同一套 | 对照 | 两版行为一致 |

**验收不是"能跑"，是"换掉一个组件不影响其他组件"**：

| 替换实验 | 应当只有一件事消失 |
|---|---|
| `Reflector` → `NullReflector` | 自我纠错消失 |
| `Router` → `AlwaysRoute` | 分流消失 |
| `Knowledge` → `NullKnowledge` | 查资料消失，退化成纯对话 |
| `Planner` → `ImplicitPlanner` | 从 P&E 退化成 ReAct |

**任何一次替换导致别的组件报错，就是耦合。** 这条判据对 5.7 的拓扑同样成立：换一种拓扑，只应改变"控制权归谁"，结论不变。

### 5.4 依赖规则（"不耦合"的可操作定义）

| 规则 | 表述 | 违反的样子 |
|---|---|---|
| **R1 按插点分层** | 位置靠后的组件不 import 位置靠前的组件 | Guard import Actor 来判断"它要干什么" |
| **R2 只依赖契约** | 组件之间只依赖 Protocol / dataclass | `isinstance(x, LLMJudgeReflector)` |
| **R3 数据只走 State** | 跨组件传数据走 State，不做参数层层透传 | `actor.run(plan, ctx, mem, kb, budget, tracer)` |
| **R4 构造只在装配层** | 所有实例化集中在一个 `build(config)` | 组件内部 `Planner()` |
| **R5 治理不可选** | 一旦装配，任何路径都不能跳过 Guard/Budget/Tracer | "内部调用"绕过 Guard |
| **R6 每个组件可离线测** | 无模型、无网络能单测 | 测不了 = 耦合了 |
| **R7 拓扑不实现能力** | `Supervisor` 只分派与汇总，不自己调模型做事；`Blackboard` 的触发是声明式规则，不能由某个 agent 自荐 | `Supervisor` 里长出"实在不行我自己答"的分支；`Blackboard.trigger` 读的是 agent 的意愿 |

### 5.5 组件契约（卷 12 写代码前必须先定）

**十二个数据类型**

| 类型 | 字段 |
|---|---|
| `Goal` | `text: str`、`user_id: str`、`session_id: str` |
| `Step` | `index: int`、`plan_id: str`、`instruction: str`、`tool_name: str \| None`、`args: dict`、`idem_key: str` |
| `ToolCall` | `name: str`、`args: dict`（`args` 已是解析后的对象） |
| `ActionResult` | `step: Step`、`ok: bool`、`output: str`、`error: str \| None`、`tokens: int` |
| `Verdict` | `passed: bool`、`reason: str`、`action: Literal["accept","retry","patch","replan_all"]` |
| `Plan` | `id: str`、`steps: list[Step]`、`rev: int` |
| `Recalled` | `text: str`、`layer: Literal["semantic","episodic","procedural"]`、`score: float`、`source: str`、`age_days: int` |
| `Pack` | `messages: list[dict]`、`usage: dict[str, int]`、`dropped: list[str]` |
| `SessionRef` | `session_id: str`、`tenant: str`、`started_at: str` |
| `Brief` | `goal: Goal`、`context_refs: list[str]`、`done: list[str]`、`forbidden: list[str]`、`deadline: float \| None` |
| `Board` | `state: State`、`rev: int`、`owner: str \| None` |
| `Route` | `name: str`、`accepts: list[str]`、`fallback: bool` |

**十一个接口（Python `Protocol`）**

| 接口 | 签名 |
|---|---|
| `Actor` | `step(step: Step, state: State) -> ActionResult` |
| `Tool` | `name: str`、`schema() -> dict`、`invoke(args: dict) -> str` |
| `Planner` | `plan(goal: Goal, state: State) -> Plan` |
| `Reflector` | `review(result: ActionResult, plan: Plan) -> Verdict` |
| `Context` | `assemble(state: State, budget: int) -> Pack` |
| `Memory` | `recall(query: str, scope: str, layers: list[str], k: int) -> list[Recalled]`、`write(items: list[Recalled]) -> int` |
| `Budget` | `remaining() -> int`、`spend(tokens: int) -> None` |
| `Durability` | `save(state: State, key: SessionRef) -> None`、`load(key: SessionRef) -> State \| None` |
| `Tracer` | `span(name: str, **fields) -> None`、`on_event(name: str, payload: dict) -> None`。唯一的外部事件出口：事件名固定为 `run.start` / `step.end` / `run.end` / `run.error`，无返回值，处理异常只记日志、不影响请求 |
| `Agent` | `name: str`、`run(goal: Goal, state: State) -> State`、`run_once(goal: Goal, state: State) -> tuple[State, str \| None]`（第二项是交接给谁，`None` 表示自己做完） |
| `Topology` | `run(goal: Goal) -> State`、`name: str` |

**六条约束**：

1. **`State` 是唯一可变载体。** 组件之间不传 State 的字段，只传 State 本身。
2. **接口只依赖上面的数据类型。**
3. **数据类型只增不改。** 新增字段必须有默认值。
4. **`State` 字段只增不改。** 初始形态：`goal`、`session`、`step_index`、`messages`、`plan`、`verdicts`、`budget_used`。
5. **记忆与装配的分工固定。** `Memory.recall` 只按分数返回候选，条数 `k` 由 `Context` 给；`Memory` 不感知预算，`Context` 不感知评分。装配的产物是 `Pack`，账（各槽位占用与丢弃项）随它一起返回，否则装配不可观测。
6. **拓扑只依赖 `Agent` 与 `State`/`Board`。** 拓扑不 import 任何组件，也不持有 `Actor`/`Planner` 的具体实现；它拿到的是已经 `build()` 好的 `Agent`。这条把"换一种拓扑"限制在组合层，组件一行不改。

**主线的 `code/knowledge/` 与副线的 `code/harness/` 不共享代码。** 主线示例追求"一段就能读完、直接能跑"；副线追求"组件之间只通过契约通信"。两者混在一起会让主线正文被迫解释封装。

**框架卷（3、8、9）的 `code/framework/` 与卷 12 的 `code/harness/` 也不共享代码。** 框架示例要能对着卷 1–11 的写法看（"框架替掉了哪一段"），卷 12 的示例要能单独单测（"换掉一个部件只消失一件事"）。两者的验收方式不同。

### 5.7 拓扑：组件的组合方式（不是组件）

**判据的边界。** 5.0 那条"每个组件必须挂到一次 loop 的一个具体位置"只能表达**一个** loop。而"几个 loop 怎么连、控制权归谁、上下文怎么过去"回答的是另一个问题，它挂不到任何插点上——所以它是组合，不是部件，写法放在卷 12 第 57 章。

**四种拓扑与它们的失效**：

| 拓扑 | 决定权 | 上下文怎么过去 | 坏了的样子 |
|---|---|---|---|
| supervisor-worker | 一个中心 | 复制（交给 worker 的 `Brief`） | 上下文二次丢失，转述失真 |
| handoff | 当前持有者 | 转移（连同 State 一起交接） | 责任漂移，两个 agent 互相推回 |
| blackboard | 板上的状态（声明式触发） | 共享（读写同一块 `Board`） | 无主垃圾场，并发写冲突 |
| 流水线 | 代码（阶段顺序） | 阶段产物契约 | 阶段间契约漂移 |

三者的差别一句话：**supervisor 是"调用"，handoff 是"转移"，blackboard 是"读写"。**

**四种拓扑只依赖 `Agent`、`State`、`Board`、`Brief`**，不 import 任何组件（约束 6 + R7）。所以：

| 替换实验 | 应当只有一件事消失 |
|---|---|
| `Supervisor` → `Handoff` | "中心拥有控制权"消失，结论应一致 |
| `Blackboard` → `Pipeline` | "动态触发"消失，产物应一致 |
| `Supervisor` → 单 `Agent` | 只有"上下文隔离"消失 |

**纵向 × 横向的验收矩阵**（5.3 的五种形态 × 这里的四种拓扑）：

```
              单 agent   supervisor   handoff   blackboard   流水线
最小             ✓
循环             ✓            ✓
知识             ✓
生产             ✓                         ✓
框架             ✓            ✓            ✓          ✓
```

副线的验收不再是"五种形态各跑一次"，而是**在矩阵里取 3 个点，每点跑一次替换实验**。G5 的 L1–L5 自评据此变成可指认的坐标。

**同一个任务的四种拓扑**（以"PDF 分析"为例，卷 12 第 57 章逐个搭一遍）。

前提：四个参与者都是 `build(cfg)` 出来的**完整 agent**（各自有 Context/Guard/Reflector），拓扑只决定"谁指挥、上下文怎么过去"。

| 拓扑 | 怎么分 | 上下文怎么过去 | 成本记号 | 失效 |
|---|---|---|---|---|
| 流水线 | 解析 → 切块 → 逐节摘要 → 汇总，阶段即 agent（或阶段即函数） | 阶段产物（结构化契约） | 阶段数 × 一次调用，最便宜 | 阶段契约漂移（上一段偷改了字段） |
| supervisor | 1 个中心 + 3 个 worker（extract / analyze / write），中心只分派与汇总 | `Brief`：doc_refs、已有结论、禁止项 | agent 数 × 各自上下文 + 汇总一次 | 转述失真（原始页码在转述里丢了） |
| handoff | 通用问答 agent 遇到"文档内条款"→ 交接给文档专家，专家处理完可交回 | 转移：State + doc_id + 已确认结论 | 每次交接复制一次 State | 责任漂移（两边都以为对方在做） |
| blackboard | N 个分节 agent 并行读同一份文档，结论写到共享板，规则触发汇总 | 共享 `Board` + reducer | 写入次数 + 冲突重试 | 无主垃圾场（没人收敛）、写冲突 |

选择依据：

| 场景 | 拓扑 | 理由 |
|---|---|---|
| 单文档、步骤固定、要能续跑 | 流水线 | 步骤写死最便宜，且每阶段可单独重试 |
| 需要三种专长、且专家要复用 | supervisor | 中心只做分派与汇总，worker 各自独立 |
| 请求类型混合，专业分支偶发 | handoff | 平时只有通用 agent，遇到才转 |
| 多文档并行、结论互相参照 | blackboard | 没有中心，靠板上的状态推进 |

supervisor 版的骨架（第 57 章的主例）：

```python
workers = {name: build(cfg[name]) for name in ("extract", "analyze", "write")}

pdf_supervisor = Supervisor(
    planner=LLMPlanner(llm, checks=[max_steps(3), tool_whitelist(WORKER_TOOLS)]),
    workers=workers,
    brief=lambda goal, step: Brief(
        goal=goal,
        context_refs=[goal.text],          # 交接单带"原始依据"，不是只带结论
        done=state.done,
        forbidden=["改写原文"],
    ),
    synth=merge_reports,                    # 只汇总，不做事（R7）
)
```

blackboard 版的骨架：

```python
board = Board(state=State(goal=goal), rev=0)
for section in sections:                    # 每节一个 agent，可并行
    agent = build(cfg["section"])
    board = board.commit(agent.run_once(goal, board.state), reducer=append_findings)
report = build(cfg["aggregate"]).run(goal, board.state)   # 汇总由规则触发
```

**两个必须写进 57 章的对照点**：同一个 PDF 任务，流水线版本没有"中心"，supervisor 版本有；把 `Supervisor` 换成 `Handoff`，结论应一致，只少了"中心拥有控制权"——这正是 5.7 替换实验的落地。

**讨论式为什么不单列**：成本乘人数、越讨论越趋同，且没有明确收敛条件；在 PDF 场景里它等价于"多个 agent 各写一版再投票"，属于集成策略而不是编排，放在边界处一句带过。

**边界**：卷 12 只做进程内拓扑。跨进程、跨框架的交接是 A2A（多 Agent 一章），消息总线与重投是交付一章；`Board` 是内存对象，不是消息队列。

### 5.8 四层与装配：同一副骨架，六种搭法

**为什么要有这一节。** 5.1–5.7 是按插点、契约、拓扑切的，读者拿着 15 个部件仍然不知道从哪开始装。这一节把主线讨论的**四层**（分派 / 主体 / 校验 / 拓扑）收成一张**装配表**：层的选择落到具体槽位，槽位决定装哪些部件。它是 56 章的主产物，57 章的第一个例子。

**四层在副线的三种落法**（注意：四种层，三种可替换性）：

| 层 | 副线里是什么 | 契约 | 替换实验 |
|---|---|---|---|
| 分派 | **部件 + 数据**（唯一两者都有的层） | `Router` + `Route{name, accepts, fallback}` | `Router → AlwaysRoute` |
| 主体 | **loop 的配置**，不是部件 | `Actor`、`Planner`、`config.mode ∈ {workflow, react, pe}` | `Planner → ImplicitPlanner`（P&E 退化成 ReAct） |
| 校验 | **部件 + 预算** | `Reflector` + `Verdict` + `Budget` 的重试计数 | `Reflector → NullReflector` |
| 拓扑 | **组合**，不是部件 | `Agent`、`Brief`、`Board`；R7 | `Supervisor ↔ Handoff ↔ Pipeline` |

一句话：**分派是"换一个部件"，主体与校验是"换一个配置"，拓扑是"换一层组合"。**

**骨架**（56 章按这段写，六个例子都从它出发）：

```python
def build(cfg) -> Agent:                      # 所有实例化集中在装配层（R4）
    return Agent(
        router     = cfg.router or AlwaysRoute("default"),
        context    = cfg.context or BudgetedContext(ratios=cfg.ratios),
        actor      = Actor(llm=cfg.llm, tools={t.name: t for t in cfg.tools}),
        planner    = cfg.planner,             # workflow 模式为 None
        reflector  = cfg.reflector,           # 无校验为 None
        guard      = cfg.guard or DenyAllGuard(),
        budget     = cfg.budget or Budget(tokens=60_000, calls=40),
        tracer     = cfg.tracer or JsonlTracer(cfg.trace_path),
        durability = cfg.durability or NullDurability(),
        workflow   = cfg.workflow,            # 固定步骤时才填
        knowledge  = cfg.knowledge, memory = cfg.memory, skills = cfg.skills,
    )


def run(agent, goal, state) -> State:
    route = agent.router.route(goal)                         # ① 分派
    if route.fallback: return fallback(goal, route.name)
    return BRANCH[route.name](agent, goal, state)


def run_workflow(agent, goal, state) -> State:                # ② 主体：固定步骤
    for step in agent.workflow.steps:
        if not agent.guard.allow(step): return blocked(step)  # ⑤ 准入
        pack = agent.context.assemble(state, agent.budget.remaining())   # ② 装配 → Pack
        result = agent.actor.step(step, state.with_pack(pack))           # ⑥ 执行
        agent.budget.spend(result.tokens)
        if agent.reflector:                                   # ③ 校验
            v = agent.reflector.review(result, agent.workflow)
            if v.action == "retry": result = agent.actor.step(step, state)
        state = state.apply(result)
        agent.durability.save(state, agent.session)           # ⑧ 记账/存档
        agent.tracer.span(step, result)
    return state
```

`run_react` 与 `run_pe` 只改这一段循环：前者每步先 `actor.propose()` 决定下一步，后者先 `planner.plan()` 再执行。**其余组件一行不改，这是副线要证明的事。**

**装配表：五个问题的答案决定填哪些槽位。**

| 问题 | 落到槽位 | 不填会怎样 |
|---|---|---|
| 这条请求归谁？ | `Router` + `Route` | 所有请求走同一条最贵的路 |
| 步骤能提前写死吗？ | `mode`、`Planner`、`Workflow` | 写死不可预知的步骤 → 静默走错；不写死能写死的 → 白花钱 |
| 错了代价多大？ | `Reflector`、`Guard` | 错误直接流到用户或外部系统 |
| 活多久、会不会死？ | `Durability`、`idem_key`、`Topology` | 崩一次重来；恢复重复副作用；一个上下文装不下就互相打架 |
| 怎么交回？ | `Delivery` | 终止态不清、输出不脱敏、引用编号对不上 |

**六个装配例**（56 章各给一份完整代码 + 一次运行；只换装配表，不换组件）：

| 例 | 主体 | 校验 | 关键槽位 | 一句话 |
|---|---|---|---|---|
| PDF 分析（固定步骤） | workflow，5 步 | 规则（要点/页码/schema） | 路径 Guard、每步 checkpoint、长文档按节并发 | 步骤能写死，就不要用循环 |
| 日志排障 | react，8 步 | 无（人判） | 只读工具白名单、轨迹全记 | 下一步依赖上一步观察 |
| 退款执行 | pe | 规则（金额/政策/权限） | 审批 L4、`idem_key` | 有"动手之前"的时刻才谈审批 |
| RAG 问答 | workflow，单步 | 引用回指 | 三级路由、四槽位装配 | 大多数请求不值得检索 |
| 编码 agent | pe | 测试裁判 | 沙箱、补丁幂等 | 有天然裁判才敢让它改代码 |
| 研究报告 | 3×agent + supervisor | 各 worker 自带 | `Brief` 交接单 | 拓扑只做分派与汇总（R7） |

**共同点要写进 56 章**：六个例子的 `contracts.py` 与组件实现完全相同，差异只在 `build(cfg)` 的参数。**如果换一个例子需要改组件代码，就是耦合**（R2/R6 的验收方式）。

**第 7 个例子留给 57 章**：同一个 PDF 任务换成四种拓扑（流水线 / supervisor / handoff / blackboard）。56 章证明「换配置不改组件」，57 章证明「换组合也不改组件」——两章合起来，才是副线的完整验收。

**边界**：六个例子都在进程内。跨进程的第六个变体（远端 worker）属于 A2A，不在副线；`Board` 是内存对象，不是消息总线。

### 5.9 生命周期的四个归属

一次完整生命周期有两头：请求进来之前（谁在调、还能用几次）与交回之后（会话怎么收尾、版本对不上怎么办、反馈去哪）。这四件事都不新增组件，各有归属：

| 阶段 | 归属 | 怎么实现 | 为什么不新增组件 |
|---|---|---|---|
| 接入（鉴权/租户/配额） | `Guard` 的 pre 阶段 | `guard.check_identity(ctx)` | 与准入共享"不通过就拦"的语义，单独拆会把同一条拒绝逻辑写两遍 |
| 会话（开始/过期/并发/清理） | `Durability` + `Budget` | `durability.open/close/expire(session)`；`budget(scope="session")` | `SessionRef` 已经是数据类型；生命周期只是存档的扩展 |
| 配置与版本（prompt/模型/工具/Skill） | 装配层的输入 | `build(registry.snapshot(version))`，版本号进 trace | 它不改变决策，只改变装哪个实现 |
| 反馈（点踩/纠正） | `Memory.write` 的一条来源 + `Tracer` 事件 | 请求结束后写一条 `source="feedback"` 的记忆 | 它是记忆的写入路径，不是新的决策点 |

判断口诀：**"一次请求一次的事"归壳（`Guard.pre`/`Delivery`），"跨请求的事"归存储（`Durability`/`Budget`/`Memory`），两者都不是组件。**

**边界**：队列与调度属于交付层（第 32 章），不进副线；`Provider`/`Cache` 是部件不是组件；跨进程交接（A2A）在卷 7，副线只做进程内。
