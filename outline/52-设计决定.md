# 已确认的设计决定

> 分册：《Agent 工程》大纲 · 40 条设计决定
> 全局约定、章号与「写哪章读哪册」见 [docs/OUTLINE.md](../docs/OUTLINE.md)。

## 九、已确认的设计决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **主线是"从 0 讲明白三层认知"，不是"装 14 个组件"** | 读者要的是知识，不是某个仓库的说明书 |
| 2 | **harness 封装整体移到卷 12（副线，全书最后）** | 切分部件的依据是失效边界，只有见过它们各自怎么坏之后才看得见；卷 11 的四章补齐了这份失效清单，副线才有完整依据 |
| 3 | **主线正文不出现 harness 的任何封装概念** | 出现即跑偏；用检查脚本强制 |
| 4 | **主线示例与副线代码物理分离** | 混在一起会让主线正文被迫解释封装 |
| 5 | 组件是 **15 个**，按 loop 插点划分（14 个 + `Delivery`） | 挂不到具体插点的就不是组件；原先 ⑨ 出口没有归属，补 `Delivery` 后九个插点一一对应 |
| 6 | `Tools` 与 `Skills` 分开 | 能力清单 vs 流程说明书；数量级与加载时机都不同 |
| 7 | `Knowledge` 与 `Context` 分开 | 召回质量 vs 窗口预算；合并后无法归因"答错" |
| 8 | `Resilience` 独立成一个部件 | 五种机制共享同一份失败计数 |
| 9 | `Replanner` 合回 `Reflector` | 两者只隔一个 `Verdict` |
| 10 | `Provider`/`Executor`/`Cache` 是部件不是组件 | 不改变任何决策 |
| 11 | **第 6 章只讲工具调用的往返，不落代码封装** | 正文要讲清楚这一步为什么必须有，不是讲本仓库怎么组织它 |
| 12 | **路由（13 章）排在 RAG（14 章）之前** | 路由是请求进来后的第一个决策，决定要不要花检索这笔钱 |
| 13 | **框架分散成卷 3、8、9，排在副线之前** | 手写过一遍，再读框架才看得懂它在替掉什么；而框架本身就是一次做完的切分，正好给副线当对照物 |
| 14 | 主项目 Coding Agent，另两个作对照实验 | 有天然裁判、天然副作用、天然长任务 |
| 15 | 知识点保持 108 条全覆盖 | 丢一条就是丢一块知识；`PLAN-v11` 草案的 111 条（C13/C14/D16/H14）不采纳——新增内容并入 C6、C7 与既有章，不新开点，避免同一概念两处定义 |
| 16 | **每章正文目标 11000 字符以上，不许凑字数** | 篇幅服务于讲透；撑不到就写短，但复述、扩背景、编故事一律返工。细则见 `docs/WRITING-SPEC.md` |
| 17 | **大纲只记结构与内容边界，不记写法与流程** | 思路与进度类内容会让结构被流程淹没 |
| 18 | **正文必须有代码块，且代码与它的输出成对出现** | 只贴输出不贴代码，等于让读者相信一个没有依据的结论。细则见 `docs/WRITING-SPEC.md` 第 1.1 节 |
| 19 | **标题是这一节讨论的对象的名字，不是摘要，也不是自造代号** | 摘要在正文里看不出问题，代号则要求读者先读过正文。取法见 `docs/WRITING-SPEC.md` 第四节 |
| 20 | **卷 10 把可观测（LangFuse）与评测（评测集、RAGAS、Agent 评测框架）接到手写能力之后** | 42–46 章手写的能力在工程里都落在现成平台上；不接这一段，能力读得懂但落不了地 |
| 21 | **评测集不单独成章，并在 RAG 评测（43）里讲** | RAG 与 Agent 共用的数据模型只有一套规则；单开一章会把"怎么来、怎么标、怎么版本化"讲两遍 |
| 22 | **H 组知识点只描述"框架侧怎么接"，不重复主线原理** | 主线已经把原理讲透，框架卷只回答"这个平台把哪一步接走了、边界在哪" |
| 23 | **示例技术栈按章分层：卷 1–2 可手写，卷 4 起"库即主题"的章节必须用真实库** | 手写近似讲得清原理，却让读者落不了地；逐章缺口见 `docs/AUDIT-CODE-GAPS.md` |
| 24 | **A2A 独立成章（34），卷 8 第 38 章只讲框架侧编排** | 协议是"拆开之后怎么说话"，属于多智能体本身；编排属于框架 |
| 25 | **架构按"决定权在哪"分层，不按名字平铺** | 系统 = 拓扑 + N 个 agent；agent = 分派 + 主体 + 校验。层间可叠加、层内互斥；变体不新开层（ReWOO 属 P&E，Reflexion 属"校验 + 记忆"） |
| 26 | **拓扑不是组件：副线新增第 53 章（48–53，总 58 章）** | 拓扑挂不到 loop 的插点上，它是组合；它与第 48 章互为镜像（为什么切 / 切完怎么拼） |
| 27 | **同一个词两个意思必须分开：转人工（`handoff=True`）≠ agent 间交接** | 13 章的 handoff 指转人工，33 章指控制权转移；术语表分开定义 |
| 28 | **"编排架构"的落点是六处：22、23、33、38、51、57** | 主体与分派在 22，校验成本在 22.7 + 23，拓扑选型与手写在 33/35，框架对照在 38，选型收口在 51，组件组合在 57；节级计划见「六之二」 |
| 29 | **向量化与向量库不新开知识点** | 嵌入原理并进 C7、向量库运维并进 C6；111 条是 v11 早期的估算，未定义内容的不计入 |
| 30 | **LLM Wiki 放深水区（G6），不进主线**（后由第 39 条改为正文第 59 章） | 它是一条不同的设计点（编译一次 vs 每次重建），但需要独立的编译流水线、诊断探针与增量重编译，且规模上限明确；放进主线会打断 13–21 章的因果链。升为卷 13 的可选章，是为了让读者拿到可复现的判据，同时不挤进主线 |
| 31 | **Computer Use 与 Coding Agent 从附录升为正文（第 49、50 章）** | 两个形态都够一章：发展脉络、动作空间、作用判据、MVP 各有独立内容，附录容不下；且附录读者会整段跳过，而这两种形态是 2026 年最主要的落地方向。与结业项目的分工不变：这两章写"形态本身"，`51-结业项目.md` 写"用全书能力组装完整版" |
| 32 | **Loop / Graph Engineering 升为正文（第 47、48 章），放在副线之前** | 它们是同一层结构（单循环 / 多循环组合），必须在副线之前讲完——副线切分部件的依据是失效边界，这两章正好给出失效清单。作为收口章，它们与 7、8、22、33、36–38 章部分重叠，因此设硬门槛：每节至少一条主线没有的判断，不满足就删掉那一节 |
| 33 | **卷 11 = 形态与结构（47–51），副线为卷 12（52–57）；五章不新增知识点，总 58 章、108 条不变** | 四章是收口与应用，不是新知识：47、48 收口 B6/B7/B10–B13/D10，49、50 应用既有点，51 收口 13/22/23/31/32/33/42–46。新开点会造成两处定义（不变量 5）。放在度量（42–46）之后，是因为这五章都要用评测、成本与轨迹的结论；放在副线之前，是因为副线需要它们的失效清单。副线"放最后"的理由不变 |
| 34 | **四层在副线落成三种可替换性；"装配表"是 56 章的主产物** | 分派是换部件（`Router`+`Route`）、主体与校验是换配置（`mode`/`Reflector`）、拓扑是换组合（`topology.py`）；56 章给骨架与六个装配例（PDF 分析、排障、退款、RAG、编码、研究报告），验收是"换例只改 `build(cfg)`，组件一行不改"；57 章开头先回收四层再讲拓扑 |
| 35 | **生命周期的四件事不新增组件** | 接入归 `Guard.pre`、会话归 `Durability`+`Budget(scope=session)`、配置版本归 `build(registry.snapshot)`、反馈归 `Memory.write` 的来源；判断口诀：一次请求一次的事归壳，跨请求的事归存储 |
| 36 | **失败处理并入第 32 章，D13 扩词，知识点仍 108 条** | 超时/重试/熔断/降级/隔离五件套共享同一份失败计数（`Resilience`）；熔断按目标（provider/endpoint/tenant）而非全局；降级三档（换模型/换路径/兜底），每档要回答"降级后还对不对"；不新增知识点，避免为一条能力改全线计数 |
| 37 | **新增第 47 章「架构选型：从一个项目到一套架构」，卷 11 收口为 47、副线为 48–53；不新增知识点，总 58 章、108 条不变** | 22 章只解决"单 agent 内部三层怎么配"，明确不碰多 agent、框架、状态、部署；读者手里有零件却没有"项目事实 → 五层配置"的映射。这一章不新开点，收口 13/22/23/31/32/33/42–46；放在卷 11 末尾、副线之前，是因为它要用前四章的失效清单与卷 10 的量法，同时它的配置表正是 52 章装配表的输入。硬门槛：每个决定必须附落选方案的失效证据 |
| 38 | **导航与目录由 `book.json` 生成，章首改为六行元信息** | 原章首四行只有知识点编号，读者无法解码；33 章几乎没有内部链接，读完无法进入下一章；文件名与标题漂移无人发现。改为：`book.json` 是唯一事实源（卷、章、知识点、状态），`docs/gen_book.py` 生成 `INDEX.md` 与各章章首/章末导航，`docs/check_nav.py` 校验五条不变量（章号连续、标题与文件名一致、章首六行、章末链接有效、INDEX 同步）。文件名 = 章号 + 标题，因此"文件名对不上章名"变成一条机器报错，而不是靠人记 |
| 39 | **G4 GraphRAG 与 G6 LLM Wiki 从附录条目升为正文第 58–59 章（卷 13），总章数 58 → 60** | 两条路线都够一章：GraphRAG 要讲图的建法、PPR、5–20 倍成本与三类问题判据；LLM Wiki 要讲编译流水线、编译缺口、诊断探针与增量重编译。留在附录时，第 18、21 章只有一句"见附录"，读者拿不到可复现的判据。放末尾而不插入卷 4，是为了不改 22–57 的章号与全部交叉引用；卷 13 标为"附录式（可选）"，不读不影响主线。G1–G3、G5 仍留在附录。此条取代第 30 条中"LLM Wiki 只放深水区"的落点，章数不再以第 33、37 条的 58 为准 |
| 40 | **47–50 移入卷 13「深水区」，51 前移为第 47 章，52–57 前移为 48–53，深水区扩为 54–59** | 47–50（循环工程、图工程、编码 agent、计算机操作 agent）都是深水路线，不应单独占一个正文卷；51（架构选型）才是主线的收口，必须放在它们之前。为了保持章号连续、不改 0–46，采用整体前移：47=架构选型，48–53=组件封装副线，54–59=深水区六章（54 循环、55 图、56 编码、57 计算机操作、58 GraphRAG、59 LLM Wiki）。总章数 60、知识点 108 不变；主线在 47 结束，卷 12 仍可跳过，卷 13 仍可选读 |
