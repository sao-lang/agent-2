# 架构选型：章节计划（第 51 章）

> 分册：《Agent 工程》大纲 · 第 51 章的节级计划
> 全局约定、章号与「写哪章读哪册」见 [docs/OUTLINE.md](../docs/OUTLINE.md)；卷表见 [vol11-形态与结构.md](vol11-形态与结构.md)。

## 六之四 · 为什么加这一章

卷 11 的前四章把零件装成了两类结构（循环、图）和两种形态（编码、计算机操作），但它们各自回答"这种结构怎么搭"，没有回答**"我这个项目该搭哪一种"**。

第 22 章已经把"单 agent 内部怎么选"讲完了（分派、主体、校验），但它明确不管四件事：多 agent 拆分、框架与技术栈、状态与持久化、部署与上线。读者读完 22 章，手里有一张三层表，却没有一张**从项目事实到整套架构**的映射表。这一章补的就是这张表，并把它落成三个可交付物：**输入清单、决策记录、迁移阶梯**。

**四条纪律**（与 47–50 共用，本章另加两条）：

1. **不新开知识点**。章首列引用编号，正文不重新定义（108 条不变）。
2. **不复述机制**。每个机制第一次出现给一句引用 + 章号。
3. **每章必须有一件主线没有的判断**（见「门槛」）。
4. **每章一个可跑的最小实现**，代码在 `code/selection/`，不 import `harness/`。
5. **不写"最佳实践清单"**。只写"在什么项目事实下成立、失效信号是什么"。
6. **不许给伪量化**。打分表只保留能算出数来的项（调用次数、token、首次通过率、延迟），其余一律写成判断题。

## 第 51 章 · 架构选型：从一个项目到一套架构

**定位**：把全书前十卷的选型依据收成一张表，让读者拿到一个真实项目时，能从"项目事实"推到"五层配置"，并写下"为什么不选另一种"。本章不教新机制，它教**怎么在信息不全的情况下做决定，以及怎么在信息变多之后改决定**。

| 节 | 内容 | 边界（不写什么） |
|---|---|---|
| 51.1 | **选型的输入是五类项目事实**：任务形状（依赖步数）、请求分布（简单/复杂占比）、错误代价与动作可逆性、预算（token 与延迟）、团队与存量（人、栈、合规）。每类给出"怎么在两天内量到"的最小方法 | 不写需求文档模板；不写访谈技巧 |
| 51.2 | **五层决策**：形态（一次调用/循环/图/多 agent）、编排（22 章三层）、供给（RAG/工具/Skill）、可靠性（卷 6）、交付（31、32 章）。层间不可替代，一层选错不会因为另一层加码而变对 | 不重讲各层机制；不出现"架构评分卡"这类合成指标 |
| 51.3 | **把"复杂"换成三个可数的量**：依赖步数（22 章）、首次通过率 `p`（23 章）、请求分布（13 章）。三个数各自怎么量、量错会选错成什么样 | 不给"复杂度 7.2 分"这类评分 |
| 51.4 | **用预算反算架构**：给定月度 token 预算与 P95 延迟，反算可用步数、能否带裁判、要不要缓存。给出一张"预算 → 形态"的反算表 | 不预测厂商降价；不写容量规划 |
| 51.5 | **架构决策记录（ADR）五段式**：背景事实、决定、落选方案与它的失效证据、代价、回滚点。**"为什么不选"比"选了什么"更重要**；没有失效证据的取舍只是偏好 | 不给文档模板下载；不写组织流程 |
| 51.6 | **迁移阶梯（五级）**：一次调用 → 单循环 → 工作流加路由 → P&E 加外部裁判 → 多 agent。每级的**升级触发条件**（哪个数连续多久变坏）与**迁移代价**（代码、评测集、运维各动多少） | 不写重构步骤；不承诺"平滑迁移" |
| 51.7 | **两个反例**：过度架构（三步任务画成图、再加一个 agent，成本上升而成功率不动）与欠架构（该分派不分派，兜底率被写成"尽量答"）。两个反例都从 51.1 的同一份项目事实出发，只改一个决定 | 反例必须来自实测或可复算，不编数字 |
| 51.8 | **框架与自研的判据**：什么情况下框架是净收益（可观测、评测、生态），什么情况下是负债（锁定、隐形状态、版本漂移）。给出"两者都对"的三种情形 | 不做框架排名；不预测版本 |
| 51.9 | **验收：三个数加一个回滚点**。三个数是单任务成本、P95 延迟、外部裁判通过率；回滚点写进 ADR。选对了不等于不用改，选错了要能在一天内退回上一级 | 不写 SLO 文档 |
| 51.10 | **三个项目画像的完整推演**：客服（资金动作、需审批）、内部知识问答（只读、答错代价低）、研究报告（长任务、多源）。同一张表推三遍，产出三套架构 + 三份 ADR + 三行成本估算 | 不写行业方案；案例只保留推演必需的事实 |

**必给示例**：

1. 三个项目画像（`code/selection/cases/`）→ 五层配置表 → 调用次数与 token 估算（脚本可复算）。
2. 同一项目在两套架构下的对照：省下的钱与多出的失败点各是什么。
3. 一份完整 ADR：五段齐全，且"落选方案"一栏有失效证据。
4. 迁移触发条件命中：某分支兜底率连续两周上升 → 加分派 → 成本与失败率的变化。

**门槛（主线没有的那一句）**：**每一个架构决定都必须附一条落选方案的失效证据。** 说不出"另一种会在什么条件下坏、坏在哪一层"，这个决定就还只是偏好——而偏好无法在三个月后复盘，也无法在半年后迁移。

**与第 22 章的分工**：22 章回答"一个 agent 内部三层怎么配"，本章回答"这个项目要不要走到 agent、走到第几级、五层各配成什么"。22 章的决策清单是本章 51.2 的输入之一，不是替代。

**与卷 12 的分工**：本章产出的是**决定**（选哪套、为什么、何时改），卷 12 产出的是**可替换性**（这套决定怎么落成能单独换掉的部件）。所以本章在前，副线在后；本章的方案表正好是 56 章装配表的输入。
