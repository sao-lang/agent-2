## 一、提示词的六项

先看坏的样子。同一段提示词只删掉"只输出一个 JSON 对象，不要任何其他文字"这一句，输出照样有内容、读起来也通顺，区别只有一处：程序解析不了：模型给了一段表格，人看没问题，`json.loads` 直接抛异常。

这类失效的共同点是：输出看起来是正常的。没有报错、没有空回复、没有明显的错。写提示词时最容易只盯着"任务说清楚了没有"，而它只是六项里的一项。

代价落在下游。解析失败那一行抛异常，上层记一条日志、返回一个笼统的 500，从用户看到的信息里已经看不出问题在哪。提示词缺项的代价不是"模型答得差"，而是"出错了归因不到提示词"。结构化的目的是让失败能被定位到一个具体的地方。六项分别是：

| 要素 | 回答什么 | 缺了之后的表现 |
|---|---|---|
| 角色 | 用什么身份和口吻说话 | 语气漂移，同一问题在两种立场间摆动 |
| 任务 | 具体要完成什么 | 答了相关的东西，但没答被问的那件事 |
| 背景 | 依据什么判断 | 没有判断依据，立场可能整体反了 |
| 输入数据 | 本次处理哪一段内容 | 编造输入，用看起来合理的内容填空 |
| 输出格式 | 结果长什么样 | 形状随机，下游解析失败 |
| 质量与约束 | 哪些事不能做、什么情况下不该答 | 越界照答，不拒答也不标注不确定 |

### 1.1 一份完整的提示词

六项齐全时，一份提示词长这样：

```text
# 角色
你是电商客服，只处理退货相关问题。

# 任务
判断这笔订单是否符合退货条件，给出结论。

# 背景
当前退货政策：
- 签收后 7 天内可申请退货
- 商品需未拆封
- 定制商品不支持退货

# 输入数据
<<<
订单号：A1001
签收时间：3 天前
商品状态：未拆封
商品类型：普通商品
>>>

# 输出格式
只输出一个 JSON 对象，不要任何其他文字：
{"eligible": true | false | null, "reason": "不超过 40 字"}
不要用 markdown 代码块包裹。

# 质量与约束
- 只依据上面的政策判断，不引用外部知识
- 商品类型如果是定制商品，eligible 直接为 false
- 信息不足时 eligible 为 null，并在 reason 里说明缺什么
- 不要推测，不要补充政策里没有的规则
```

这份提示词有四个结构特征，每一个都有具体的作用：

| 特征 | 作用 |
|---|---|
| 六段用 `# 标题` 分隔 | 每段作用没有歧义，也方便逐项检查是否漏了 |
| 输入数据用 `<<< >>>` 包住 | 数据和指令分开，数据里的内容不会被当成指令 |
| 格式要求写明"不要 markdown 包裹" | 少掉一类最常见的解析失败 |
| 约束里有"信息不足时填 null" | 明确允许拒答，否则它倾向于硬答 |

第二条单独值得说。输入里如果出现类似指令的文字，比如合同里有一句"忽略以上要求"，没有边界标记时它和调用方的指令在同一层级，模型无法区分哪句该听；加上 `<<< >>>` 之后，边界变成输入里一个可见标记。它不是绝对安全的隔离，但是零成本的一层。

第三条与格式的关系最直接："不要 markdown 包裹"挡掉的是最高频的一类解析失败。它的写法值得借鉴：明确否掉一个具体的形态，而不是要求"输出要干净"。约束写得越具体，能挡掉的失败越确定；写成"注意格式"，挡掉的是零。

`code/knowledge/ch04_prompt/six_elements.py` 把六项做成一个结构，逐项删掉一个，列出预计的失效形态：

```python
@dataclass
class Prompt:
    role: str | None = None
    task: str | None = None
    context: str | None = None
    data: str | None = None
    fmt: str | None = None
    constraints: str | None = None

    def present(self) -> set[str]:
        keys = ["role", "task", "context", "data", "fmt", "constraints"]
        return {k for k in keys if getattr(self, k)}


def simulate(p: Prompt) -> list[str]:
    """按缺失项返回预计的失效形态。"""
    have = p.present()
    return [MISSING_EFFECT[k] for k in ("role", "task", "context", "data", "fmt", "constraints")
            if k not in have]
```

运行输出（节选前六组）：

```
=== 完整六项 ===
  六项齐全：输出可复现、可解析、边界明确

=== 缺 role ===
  语气与视角不稳定：同一问题在'客服'和'法务'口吻间摆动

=== 缺 task ===
  输出跑题：回答了相关但没有回答被问的那件事

=== 缺 context ===
  缺少判断依据：不知道你现在是哪一方，立场可能反了

=== 缺 data ===
  编造输入：没有真实数据时，用看起来合理的内容填充

=== 缺 fmt ===
  格式随机：有时表格、有时列表、有时整段文字，下游无法解析

=== 缺 constraints ===
  越界：超出范围也照答，不拒答也不标注不确定
```

（这是原理演示：`simulate` 把"缺哪一项会坏在哪"显式列出来，方便逐项自查，不是模型实测。）六种失效里，三种在测试时很难发现，因为它们的输出"有内容"。缺 `fmt`。输出一定通顺，只是这次是表格、下次是列表，接下游时才坏，而那时改动已过去很久。缺 `constraints`。该拒答的时候照答：没有约束时它不会主动标注"我不确定"，因为标注不确定和给出结论在生成过程中是两条路。缺 `data`。会编造输入：没有真实数据时，最省力的续写是给一个看起来合理的值。它与上一条的区别是"根据什么说话"与"什么时候闭嘴"。

缺 `role` 与缺 `context` 的表现相反。缺角色时语气漂移，但漂移不影响事实；缺背景时立场可能整体反了，而输出看起来很确定，也越不容易被怀疑。缺 `task` 反而最容易发现，因为答的内容明显不是被问的。最最容易发现的问题往往最不重要，要自查的是那三个看不出来的。

### 1.2 六项都要写吗

不需要。判断标准只有一条：这一项的缺失会不会导致看不出来的失效。

| 场景 | 可以省 | 不能省 |
|---|---|---|
| 一次性问答，结果给人读 | `role`、`fmt` | `task` |
| 结果要程序解析 | `role` | `fmt`、`constraints` |
| 高风险判断（金额、资格、合规） | `role` | 全部，尤其 `constraints` |

省掉 `role` 通常没关系，多数任务不需要特定口吻；省掉 `fmt` 只在人读时安全；省掉 `constraints` 在任何场景都有风险，它决定的是"什么时候不该答"，而这恰恰是模型不会主动选的选项。

### 1.3 六项放在哪一层

六项不是全写在同一段话里。请求的结构是分层的，每层作用不同，见 `code/knowledge/ch04_prompt/six_elements.py`：

```text
系统消息    角色、全局约束、输出格式要求   ← 每轮都发，内容不变
示例消息    少样本示例                    ← 每轮都发，内容不变
用户消息    本次任务、本次输入数据         ← 每轮变化
```

分层影响两件事。第一，作用范围。系统消息里的规则每轮都生效，用户消息里的要求只作用于本轮：把必须输出 JSON 写在用户消息里，下一轮一换这条要求就没了。第二，成本。缓存只命中从头开始的连续前缀，系统消息与示例消息不变，正好构成稳定前缀；反过来放，缓存全部失效。放错层的四种后果：

| 放错 | 后果 |
|---|---|
| 长期规则放进用户消息 | 换一轮就失效，输出格式开始飘 |
| 本次数据放进系统消息 | 每轮都变，缓存失效，成本上升 |
| 示例放进用户消息 | 示例被当成本轮输入的一部分，取值可能被照抄 |
| 约束写进示例里 | 它被理解成"示例中的一句话"，不是规则 |

最后一行最隐蔽。示例里出现 `{"days": 7}`，约束写的是"天数必须是 1 到 30 的整数"。这条约束放在示例之后且没有单独成段时，模型可能把 7 当成默认值反复输出：示例里的具体值比抽象规则更容易被复制。

### 1.4 拼接顺序的影响

长提示词还有一处与顺序有关的事实：开头和结尾的内容比中间的内容更容易被遵守。它是注意力分布的后果：生成每个 token 时，上下文各位置的影响并不均匀，这决定了拼接顺序，见 `code/knowledge/ch04_prompt/six_elements.py`：

```text
[系统消息]
  最关键的约束        ← 开头，最稳
  角色
  详细说明            ← 中间，最容易被稀释
  输出格式            ← 结尾前，次稳
[示例]
[用户消息]
  本次任务
  本次输入数据        ← 位置靠后，且长度不可控
```

实际影响最大的是长提示词：两千字的说明里，中间那句金额必须用整数分表示很容易被稀释，挪到最前面或系统消息最后一行，遵守率会明显不同。长提示词的检查方法因此很具体：把所有「必须」和「禁止」挑出来，看它们是否都在前三分之一或后三分之一内。落在中间的，挪位置比改措辞有效，不需要跑模型。

### 1.5 否定式约束的弱点

约束里最常见的写法是"不要做 X"，它有一个结构性问题：没有给出替代动作。缺 `constraints` 的表现是"越界照答"，根因不只是少一条规则：输入超范围时，模型面前只有给答案或承认给不出来两条路，"不要超范围回答"只否掉了前者的一半，却没指定后者该输出什么。生成过程于是只能在"看起来合理的内容"里继续挑。对照两种写法：

| 写法 | 模型能做什么 | 结果 |
|---|---|---|
| 不要回答政策以外的问题 | 只能判断"这算不算政策以外" | 边界依然模糊，照答居多 |
| 问题超出政策范围时，`eligible` 填 null，`reason` 写"超出政策范围" | 有一条明确的可执行路径 | 越界时能稳定输出约定值 |

第二种给的是一个动作，输出结构化、可判定。判定标准很简单：把这条约束交给一个只会照做的人，他能不能确定该输出什么。答案是"看他怎么理解"，这条约束就还没写完。同样的改写可以用在所有"不要"上：

| 原写法 | 改成 |
|---|---|
| 不要编造 | 资料里没有的信息，填 null 并说明缺哪一项 |
| 不要输出多余文字 | 只输出一行 JSON，第一个字符是 `{` |
| 不要用中文引号 | 所有键与值使用双引号，不得使用 `“”` |
| 不要太长 | `reason` 不超过 40 个字，超出则截断到最后一个句号 |

前三行把"不要"变成"要"，而且是可检测的；第四行还多给了一个处理方式，因为只说"不超过 40 字"没回答"超过时怎么截"。依据与生成机制有关：禁令和行动在生成过程中不是同一类东西。禁令要在每一步判断"这样做算不算违反"，边界模糊；行动只是一个候选输出，可以直接生成。

## 二、让输出能被程序使用

输出要进程序，必须过两道关，而这两道关是独立的：

| 关 | 检查什么 | 失败的样子 |
|---|---|---|
| 语法关 | 这段文本能不能解析成结构 | `json.loads` 抛异常，一个对象都拿不到 |
| 字段关 | 结构里的字段名、类型、取值对不对 | 解析成功，但 `order_id` 缺失，或者 `days` 是字符串 |

五种做法沿着这两道关依次加强。它们的代码都在 `code/knowledge/ch04_prompt/structured_output.py` 里，逐条给出调用代码与真实输出。

### 2.1 做法一：纯文本与正则

最省事的做法：提示词里要求输出 JSON，拿到回复后用正则抽。强项是零依赖、零配置，弱项是任何一处写法偏差都会失败，见 `code/knowledge/ch04_prompt/structured_output.py` 的 `plain_extract`：

```python
def plain_text(client, msgs: list[dict]) -> str:
    """纯文本调用：不带任何格式约束，返回原始回复。"""
    return client.chat.completions.create(
        model="demo-model", messages=msgs).choices[0].message.content or ""


def plain_extract(text: str) -> tuple[dict | None, str | None]:
    """做法一的解析：用正则把 JSON 片段捞出来。"""
    m = re.search(r"\{.*\}", text, re.S)
    if not m:
        return None, "没有找到 JSON 片段"
    try:
        return json.loads(m.group(0)), None
    except json.JSONDecodeError as e:
        return None, f"JSON 解析失败：{e}"
```

第一次调用与回灌错误后的重试：

```
第一次尝试：
  原始回复：'{“order_id”: “A1001”, “days”: 7, “reason”: “签收不想要”}'
  抽取结果：JSON 解析失败：Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
回灌错误后第 1 次重试：
  原始回复：'{"order_id": "A1001", "days": 7, "reason": "签收不想要"}'
  抽取结果：{'order_id': 'A1001', 'days': 7, 'reason': '签收不想要'}
  校验：通过
```

输出说明了什么：正则成功捞出了 `{...}`，但 `json.loads` 不认中文引号。正则能定位，不能校验。它只保证"这里有一对花括号"。

还有两处同类失败：遇到嵌套对象时 `.*` 只抽到第一个 `}`，抽出来是残缺片段；回复里既有说明又有 JSON 时，说明部分若出现花括号，正则从那里就开始匹配。两种报错都像"JSON 格式错误"。

适用场景因此比想象中窄：一次性脚本、离线清洗、以及对结果只需要大致可用的场合。判据是「这个输出坏了，代价是什么」：人工过一遍就能发现并重跑，正则够用；输出直接进下游、坏了没人看，正则不能用。中间地带的做法是缩小失败面，要求模型把 JSON 放在 `<<<JSON>>>` 与 `<<<END>>>` 之间。

### 2.2 做法二：JSON mode

请求时声明 `response_format={"type": "json_object"}`，服务端在生成时保证输出是一段合法 JSON，语法关由服务端负责，本地不再需要正则，见 `code/knowledge/ch04_prompt/structured_output.py` 的 `json_text`：

```python
def json_text(client, msgs: list[dict]) -> str:
    """JSON mode 的原始回复：服务端保证语法合法，字段名不保证。"""
    return client.chat.completions.create(
        model="demo-model", messages=msgs,
        response_format={"type": "json_object"}).choices[0].message.content or ""


def json_obj(client, msgs: list[dict]) -> dict:
    """JSON mode + 本地解析：语法已经被服务端保证了。"""
    return json.loads(json_text(client, msgs))
```

三次尝试的输出：

```
第一次尝试：
  原始回复：'{"orderId": "A1001", "days": 7, "reason": "签收不想要"}'
  语法：合法，json_object 的承诺兑现了
  校验：缺字段 ['order_id']
第 1 次重试：
  原始回复：'{"orderId": "A1001", "days": 7, "reason": "签收不想要"}'
  校验：缺字段 ['order_id']
第 2 次重试：
  原始回复：'{"orderId": "A1001", "days": 7, "reason": "签收不想要"}'
  校验：缺字段 ['order_id']
```

输出说明了什么：语法关过了，字段关没过，而且重试无效。三次回复一字不差，因为模型对"这个字段该叫什么"没有新的判断：回灌一句"缺 order_id"不改变它认为 `orderId` 就是正确写法，除非提示词或 schema 写明字段名。

JSON mode 最容易踩的一条：它承诺的是"合法 JSON"，而非调用方要的那份 JSON，把它当成结构化输出的都会遇到字段名不对、字段缺失、多出字段这三类问题。

还有一处使用条件写得隐蔽：JSON mode 要求提示词里出现"JSON"这个字样，否则请求被拒。两处约束是叠加的：参数保证语法合法，提示词里的字样与字段说明影响内容。由此得出分工：参数负责语法，提示词负责字段名与取值含义。

### 2.3 做法三：强制调用工具

把输出结构声明成一个工具的参数，用 `tool_choice` 强制调用。字段名由 schema 决定，不是由模型的理解决定，见 `code/knowledge/ch04_prompt/structured_output.py` 的 `tool_submit`：

```python
def tool_submit(client) -> tuple[str, str]:
    """function calling：强制调用 submit_result，返回 (arguments, finish_reason)。"""
    reply = client.chat.completions.create(
        model="demo-model", messages=messages(), tools=[TOOL],
        tool_choice={"type": "function", "function": {"name": "submit_result"}})
    choice = reply.choices[0]
    return choice.message.tool_calls[0].function.arguments, choice.finish_reason
```

两种情形的输出：

```
正常形状：
  finish_reason=tool_calls
  arguments='{"order_id": "A1001", "days": 7, "reason": "签收不想要"}'
  解析结果：{'order_id': 'A1001', 'days': 7, 'reason': '签收不想要'}
  校验：通过
arguments 坏掉：
  finish_reason=tool_calls
  arguments='{"order_id": "A1001", days: 7}'
  解析结果：JSON 解析失败：Expecting property name enclosed in double quotes: line 1 column 23 (char 22)
  校验：无法进行
```

输出说明了什么：字段名这一关过了，但多出一道解析。`arguments` 里放的是一个字符串，里面才是 JSON，所以要解析两次：先取 `tool_calls[0].function.arguments`，再 `json.loads` 它，这条路径上任何一次 `json.loads` 都可能抛异常，而它必须被捕获，否则整段对话中断。

另一个代价并非所有模型都支持把 `tool_choice` 钉死到某一个函数；不支持时请求被拒，或被降级成"允许自由选择"，模型可能返回正文而不是调用。这是这种做法在跨厂商时最脆的地方。`tool_choice` 还有三种取值：

| 取值 | 约束 | 适用 |
|---|---|---|
| 强制调用某个函数 | 这一步必须调它，不能返回正文 | 当作结构化输出用 |
| 允许调用（默认） | 可以调任意一个，也可以不调 | 当作"可选动作"用，讲工具调用时会用到 |
| 禁止调用 | 这一步不许调任何工具 | 收尾轮，只需要正文 |

三种取值是三种不同的东西。当作结构化输出时要的是第一种：不仅要字段名正确，还要保证"一定有输出"，不能让模型选择"只说一句人话"。允许自由选择就会出现一种极难处理的失败——`finish_reason` 是 `stop`、`content` 是一段自然语言、`tool_calls` 为空，而下游只认 `tool_calls`。另一条分工与 schema 有关：`description` 管"什么时候用"，`parameters` 管"调它的时候填什么"。

### 2.4 做法四：严格模式

给出完整的 JSON Schema，并声明 `strict: True`。约束发生的时机变了：不是在生成完再检查，而是在生成过程中限制下一个 token 的候选范围，见 `code/knowledge/ch04_prompt/structured_output.py` 的 `strict_text`。

```python
STRICT_FORMAT = {
    "type": "json_schema",
    "json_schema": {"name": "refund_check", "strict": True, "schema": SCHEMA},
}


def strict_text(client) -> str:
    """严格模式：服务端按 schema 约束采样，返回原始回复。"""
    return client.chat.completions.create(
        model="demo-model", messages=messages(),
        response_format=STRICT_FORMAT).choices[0].message.content or ""
```

两种情形的输出：

```
字段齐、类型对：
  原始回复：'{"order_id": "A1001", "days": 7, "reason": "签收不想要"}'
  语法：合法
  校验：通过
可选字段被逼成 null：
  原始回复：'{"order_id": "A1001", "days": null, "reason": "签收时间未知"}'
  语法：合法
  校验：类型不对 ['days']
```

输出说明了什么：严格模式确实解决了字段名和缺字段的问题，但它带了一个结构性副作用：所有字段都要在 `required` 里，可选字段只能靠"允许 null"来表达。于是"这个值我不知道"从"字段不出现"变成"字段明确为 null"：下游只判断字段存在，就会把 `null` 当有效值；按类型校验，又把它判成类型错误。处理方式是在 schema 里显式表达可空，把 `null` 与"缺失"分开，写成一行声明：

```python
days: int | None = Field(default=None, ge=1, le=90)
```

这属于下一章（用 pydantic 定义输出结构）的内容。这里只需要知道：严格模式保证的是形状，不是语义，而且它会把"缺失"改写成"null"，这是一个必须提前决定的表示法问题。严格模式还有一份硬性要求清单：

| 要求 | 漏了会怎样 |
|---|---|
| 所有属性都出现在 `required` 里 | 请求被拒，或 schema 被判定为不支持 |
| `additionalProperties: false` | 约束不生效，多出的字段照常返回 |
| 可选字段用"允许 null"表达 | 想表达"可以没有"，实际只能表达"可以是 null" |
| 不用未支持的组合关键字 | 请求被拒；有些实现是静默降级 |

怎么确认某一家支持到什么程度？只有读文档，或者发一个探测请求：拿一份用到全部关键字的 schema 发一次，看它是报错、成功、还是成功但字段没被约束（第三种最危险，它与"支持"长得一样）。这也是手写 schema 不划算的原因：这些要求全靠人记，而下一章的 pydantic 模型能从类型自动生成 schema，写错在开发期就报。

### 2.5 做法五：本地校验与自愈重试

前四种都可以配这一层，区别在于回灌什么：具体的错误，不是一句"重来"。这一层的 `Result` 与 `heal` 也在 `code/knowledge/ch04_prompt/structured_output.py`。它不替代前面任何一种，而是压在最下面：做法一到四决定形状，做法五决定内容不对时怎么办。两者都要：即使服务端按 schema 约束了采样，取值范围、跨字段一致性、以及"这个订单号是不是真的存在"仍然只能本地判断。

```python
class Result(BaseModel):
    """做法五用的模型：三层校验写进类型与约束里。"""

    order_id: str = Field(min_length=1)
    days: int = Field(ge=1, le=90)
    reason: str = Field(max_length=40)


def pydantic_error(text: str) -> str | None:
    """pydantic 校验：通过返回 None，不通过返回错误原文。"""
    try:
        Result.model_validate_json(text)
        return None
    except ValidationError as e:
        return str(e)


def heal(client, msgs: list[dict]) -> tuple[Result | None, int]:
    """自愈重试：把 pydantic 的错误原文当成下一条消息回灌。"""
    history = list(msgs)
    for attempt in range(3):
        text = json_text(client, history)
        error = pydantic_error(text)
        print(f"第 {attempt + 1} 次尝试：\n  原始回复：{text!r}")
        if error is None:
            print(f"  校验：通过 {Result.model_validate_json(text)}")
            return Result.model_validate_json(text), attempt
        print(f"  pydantic：{error.splitlines()[0]}")
        for line in error.splitlines()[1:]:
            print(f"  {line}")
        history = history + [
            {"role": "assistant", "content": text},
            {"role": "user", "content": f"上面的输出有问题：{error}。请修正后重新输出，只给 JSON。"},
        ]
    return None, 3
```

一次失败、一次成功的完整过程：

```
第 1 次尝试：
  原始回复：'{"order_id": "A1001", "days": "三天", "reason": "签收三天"}'
  pydantic：1 validation error for Result
  days
    Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='三天', input_type=str]
      For further information visit https://errors.pydantic.dev/2.13/v/int_parsing
第 2 次尝试：
  原始回复：'{"order_id": "A1001", "days": 7, "reason": "签收不想要"}'
  校验：通过 order_id='A1001' days=7 reason='签收不想要'
```

输出说明了什么：第一次的失败是"语法合法、类型不对"，`days` 是中文数字。JSON mode 拦不住它，因为那串东西合法；严格模式也拦不住，除非 schema 声明了 `integer` 且服务端真按 schema 采样。回灌的是 pydantic 原文，带着字段名、期望类型、实际值，第二次能改对靠的就是这三样；回灌"格式错了"，模型只能猜是哪一项错。

这里有一条界限：重试只能修"信息已经在上下文里、只是表达错了"的问题。`days` 写成中文数字属于这一类；JSON mode 那种字段名理解错误不属于，它的原因是"不知道调用方要哪个名字"，回灌再多次也不会知道。

回灌有三条规则：

第一条，回灌错误原文，不回灌结论。`str(e)` 里有字段名、期望类型、实际值，模型才知道改哪里。

第二条，不把整段坏输出重复一遍。`heal` 里把坏输出放进 `assistant` 消息是必要的，它给了模型"上一条说了什么"的参照；顺序不能反，否则修正要求会被当成对原始问题的新要求。

第三条，不写评价，只给事实。"理解错了"这类话没有信息，还可能让模型过度修正，把本来对的其他字段也改掉。

还有一条工程约定：重试次数要有上限，而且应该很小。`range(3)` 已经足够区分"能修"与"修不了"；超过三次仍失败，问题就不在表达层，该走失败分支并上报。

### 2.6 五种做法的对比

同一份输入，五种做法跑完了汇总，见 `code/knowledge/ch04_prompt/structured_output.py`：

```
做法                    语法      字段        结论                  重试
------------------------------------------------------------------------------
纯文本+正则             不合法    未通过      重试后通过            1
JSON mode               合法      不通过      字段名靠理解          2
function calling        合法      通过        字段由 schema 定      0
JSON Schema 严格模式    合法      通过        结构有保证，值要另查  0
本地校验+自愈重试       合法      通过        一次失败一次成功      1
```

（服务端是脚本化的，回答的内容由脚本按典型失败给出。它演示的是失败形态，不是模型实测。）把这一份结果摊成一张对比表：

| 做法 | 语法可靠性 | 字段可靠性 | 成本 | 需要重试 |
|---|---|---|---|---|
| 纯文本 + 正则 | 低：引号、包裹、嵌套、截断都能坏 | 低 | 最低：一次调用 | 经常，且不保证成功 |
| JSON mode | 高：服务端保证合法 | 中：字段名靠理解 | 低：一次调用 | 字段名错时重试无效 |
| function calling | 高：schema 约束 | 高：由 schema 定名 | 中：多一层解析，`arguments` 是字符串 | 少，但有第二道解析 |
| JSON Schema 严格模式 | 高：采样期约束 | 高，但可选字段变 null | 中：请求体变大 | 极少 |
| 本地校验 + 自愈 | 取决于基础做法 | 取决于校验写得多严 | 高：失败就多一次调用 | 本身含重试，需设上限 |

「需要重试」这一列最值得注意。重试的代价不是又一次调用：延迟翻倍、成本翻倍，有副作用的动作还可能重复执行。选择顺序因此是确定的：能上严格模式就上；服务端不支持时用 function calling；两者都不支持才用 JSON mode 加严格校验；纯文本加正则只在一次性脚本里用。

本地校验这一层无论选哪种都要有。它检查的是「这个值合理吗」：`days` 是整数、格式完全合法、值等于 0，业务上不成立，签收 0 天意味着还没签收。成本还能再具体一点，同一份 messages 的四种请求体（脚本末段的输出）：

```
==============================================================================
  纯文本               97 token   相对纯文本 +0
  JSON mode           108 token   相对纯文本 +11
  function calling    211 token   相对纯文本 +114
  严格模式            185 token   相对纯文本 +88
  （messages 本身 97 token，差出来的部分是格式声明）
```

（按请求体序列化后的 token 数计，是成本的近似；真实计费由服务端决定，但差值的方向与量级可以看清。）三行差值说明三件事。

格式声明不是免费的。JSON mode 只多 11 个 token，它的声明就是一句 `{"type": "json_object"}`；function calling 多 114，因为工具定义里带着名字、说明、参数树和必填列表——上一章量过，一个工具的开销可能是正文的两倍。这是每次请求都要付的钱。一个任务跑五步，这 114 就被付五次。

严格模式并不比 function calling 贵，甚至略便宜。差别只在包装层：工具那边多一个 `description` 与 `tool_choice`。可靠性与成本都相当时，选择就落在服务端支持哪一种、要不要顺带拿到强制调用。

### 2.7 校验的三层

到这里可以把校验拆开看：

| 层级 | 检查什么 | 谁能做 |
|---|---|---|
| 语法 | 能不能解析成结构 | 服务端（严格模式）或本地解析 |
| 结构 | 字段齐不齐、类型对不对 | schema 或 pydantic |
| 语义 | 值合不合理 | 只有业务代码 |

第三层没法交给 schema。schema 能声明"是整数"，不能声明「这个订单号属于当前用户」。所以第三层必须写成能给出具体原因的函数，见 `code/knowledge/ch04_prompt/structured_output.py` 的 `semantic_check`：

```python
def semantic_check(obj: dict) -> str | None:
    """返回 None 表示通过，否则返回具体的失败原因。"""
    days = obj.get("days")
    if not isinstance(days, int):
        return None      # 交给上一层类型校验

    if days < 0:
        return f"days 为负数（{days}），签收后经过的天数不可能为负"
    if days > 365:
        return f"days 为 {days}，超出一年，请确认日期是否正确"
    return None
```

每一条返回信息都要能让模型据此修正。`"days 不合法"` 这样的描述没有信息量，模型只能重新猜。第三层失败最难处理：格式全对、类型全对、只有值是错的，重试往往无效，模型认为它答对了。出路是把"值为什么错"写成一句它无法反驳的证据，比如把真实的签收日期贴回去。

还有一类容易漏掉的检查：值与来源是否对得上。`reason` 里写"未拆封"，而输入里商品状态是"已拆封"，两个字段各自合法却互相矛盾。单字段校验发现不了，只能拿输出与输入做交叉检查，对不上就报一条具体的错误。它把"模型抄错了一个字段"变成一条可以回灌的具体错误，也解释了一件事：校验函数不该只接收输出，它需要知道这次输出的依据。

## 三、改动效果的判断

提示词是要反复改的。改完怎么判断有没有变差？最自然的做法是"跑几个例子看看"，它有两个漏洞：例子是挑过的，比较的是总数。正确做法是维护一份用例集，每次改动跑同一批，并逐例比较。用例与判定函数都在 `code/knowledge/ch04_prompt/regression.py`：

```python
@dataclass
class Case:
    name: str
    category: str
    text: str
    check: Callable[[dict], bool]


CASES = [
    Case("常规退货", "常规", "订单 A1001：签收 3 天，未拆封，普通商品", eligible_is(True)),
    Case("超期退货", "边界", "订单 A1002：签收 30 天，未拆封，普通商品", eligible_is(False)),
    Case("定制商品", "边界", "订单 A1003：签收 3 天，未拆封，定制商品", eligible_is(False)),
    Case("已拆封", "边界", "订单 A1004：签收 3 天，已拆封，普通商品", eligible_is(False)),
    Case("空输入", "异常", "", is_refusal),
]
```

判定不靠人看。`check` 是一个函数，输入是解析后的对象，输出是真假：

```python
def eligible_is(value: bool) -> Callable[[dict], bool]:
    return lambda obj: obj.get("eligible") is value


def is_refusal(obj: dict) -> bool:
    """拒答：eligible 为 null，且 reason 里说了缺什么。"""
    return obj.get("eligible") is None and bool(obj.get("reason"))
```

两个版本的提示词差别只有三处：B 版补了"定制商品不支持退货"，把"商品需未拆封"改成了"商品需完好"，又补了"信息不足时 eligible 填 null"。判定函数自己也要有测试：

```python
def self_test() -> None:
    """判定函数自己也要有测试：它错了，整个回归集都会失真。"""
    assert eligible_is(True)({"eligible": True})
    assert not eligible_is(True)({"eligible": False})
    assert not eligible_is(True)({"eligible": None})
    assert is_refusal({"eligible": None, "reason": "缺少订单信息"})
    assert not is_refusal({"eligible": None, "reason": ""})
    print("判定函数自测通过")
```

五行断言值得解释。第三条断言确认 `None` 不等于 `True`，写错成 `== value` 时它就会漏；第五条断言确认 null 但没有给原因不算合格拒答。两者都是判定函数最容易写松的地方，而写松的方向恰好是让失败的用例看起来通过，失真永远偏向乐观。

判定还有一条设计原则：判定落在解析后的对象上，不落在文本上。`"可以退" in content` 看起来更像人判断，实际会把"不能退，若未拆封则可以退"判成通过。

`code/knowledge/ch04_prompt/regression.py` 跑出来的逐例结果：

```
判定函数自测通过

========================================================================
版本 A
========================================================================
  常规退货    常规   eligible=True  通过   签收 3 天，未拆封，可以退
  超期退货    边界   eligible=False 通过   签收 30 天，超过 7 天
  定制商品    边界   eligible=True  失败   签收 3 天，未拆封，可以退
  已拆封     边界   eligible=False 通过   商品已拆封，不符合条件
  空输入     异常   eligible=True  失败   签收 3 天，未拆封，可以退

========================================================================
版本 B
========================================================================
  常规退货    常规   eligible=True  通过   签收 3 天，未拆封，可以退
  超期退货    边界   eligible=False 通过   签收 30 天，超过 7 天
  定制商品    边界   eligible=False 通过   定制商品不支持退货
  已拆封     边界   eligible=True  失败   商品完好，可以退
  空输入     异常   eligible=None  通过   缺少订单信息，无法判断
```

（服务端是脚本化的，五个回答由脚本按"版本 × 用例"回放；判定由上面那两个函数对解析后的对象做。真实使用时这一段换成模型的真实回答，判定代码不变。）

### 3.1 总数掩盖了什么

同一批结果按类别合并后是这样，见 `code/knowledge/ch04_prompt/regression.py`：

```
  总数：3/5 → 4/5（+1）
  常规  1/1 → 1/1
  边界  2/3 → 2/3
  异常  0/1 → 1/1   <- 0→1

  修好的：['定制商品', '空输入']
  弄坏的：['已拆封']
```

三行数字连起来看，是这个示例最要紧的部分。总数从 3 涨到 4，只看这一个数，结论是"改得更好"。逐例比较：修好两条，弄坏一条。弄坏的是"已拆封"：B 版把"商品需未拆封"改成"商品需完好"，"已拆封但完好"的商品在这条措辞下变成可以退。分类统计看不出来。边界类两版都是 2/3，修好的和弄坏的都在这一类比里，正好抵消；异常类从 0/1 变成 1/1 是真实提升。

三层聚合的结果依次是：总数 +1、分类无变化、逐例一好一坏。聚合的层级越低，能看见的东西越多，而报告通常只给最高层。任何通过率都是标量，丢掉了「哪条对哪条错」：修好的部分决定这次改动值不值得留，弄坏的部分决定它能不能上线。能用的回归报告应当固定包含四段：

| 段 | 内容 | 回答的问题 |
|---|---|---|
| 总数 | 通过数 / 总数，两版并列 | 整体有没有变 |
| 分类 | 每类的通过数，两版并列 | 变化集中在哪一类 |
| 逐例差异 | 修好的清单、弄坏的清单 | 具体动了哪几条 |
| 未覆盖 | 这次改动涉及、但用例集里没有的输入 | 结论的适用范围到哪 |

第四段几乎总被省略，而它决定了报告的可信范围：这次改的是"定制商品"相关逻辑，而用例集里没有定制商品的边界用例，"总数没变"就什么也说明不了，只说明没撞上已有用例。把没覆盖到什么写进报告即可。

### 3.2 用例集的四条要求

| 要求 | 原因 | 违反的后果 |
|---|---|---|
| 覆盖类别，不只覆盖常见输入 | 模型在异常输入上的行为与常规输入无关 | 改常规用例时弄坏异常处理，测不出来 |
| 保留历史失败 | 修好一次不代表永远好 | 后续改动悄悄回退 |
| 逐例比较，不只看总数 | 总数上升可以掩盖个别回归 | 把变差判断成变好 |
| 每次改动跑同一批 | 换用例集就不可比 | 两版结果无法对照 |

第一条在这个示例里体现得很直接：五个用例分成常规、边界、异常三类，边界占三个。边界用例多不是浪费，因为提示词的改动绝大多数发生在规则措辞上，而规则措辞影响最大的是边界；常规用例几乎不会因为措辞翻转。

用例的取舍还有一个判据：测同一条规则、同一方向、只是数字不同的，留一个就够；测的是不同方向（未拆封是"可以退"、已拆封是"不可以退"），两条都必须留，因为措辞改动往往只翻转其中一个方向。

第二条是这份用例集的长期价值："定制商品"和"空输入"曾经失败，修好之后必须一直留在里面，它们从失败样本变成了回归防线。

### 3.3 单次结果与通过率

上面每个用例只跑了一次，这在真实系统里不够：输出本来就不稳定，同一输入两次结果可能不同。所以每一例要跑多次，看的是通过率：

| 层级 | 比什么 | 什么时候用 | 代价 |
|---|---|---|---|
| 逐例单次 | 哪几条从通过变成失败 | 每次改动 | 一次跑批 |
| 逐例多次 | 每条的通过率变化 | 判断改动是否有效 | N 倍调用 |

第一层能发现明确的回归，第二层才能判断"有没有变好"。第二层还要过统计这一关：五条用例、每条跑三次，通过率从 60% 到 80% 在样本量这么小时不足以支撑任何结论，判断差异需要的是置信区间，这部分留给讲统计与门禁的那一章。

一个常见错误是拿两次改动各跑一遍、比通过率、留下高的一次：两次跑批的输入不完全相同，差的可能只是噪声。正确做法是在同一次跑批里比较两个版本：对照必须在同一次测量里完成。

### 3.4 用例从哪里来

理想来源是真实请求。可行做法是按价值排序积累：

| 来源 | 得到什么 | 成本 |
|---|---|---|
| 线上失败样本 | 最有价值：已经被真实输入触发过 | 零，但要主动收集 |
| 边界构造 | 覆盖措辞改动最容易翻转的位置 | 低 |
| 常规构造 | 保证基础功能不退化 | 低 |
| 随机采样 | 发现意料之外的问题 | 中，需要标注 |

线上失败样本的优先级最高，因为它不是猜的。收到一个坏结果时，正确动作是当场把它变成一条用例：输入原文、期望输出、判定函数。这个动作只有几分钟，挡住的是同一类问题以后的回归。这也解释了为什么「保留历史失败」不可省：每条用例背后通常都有一次真实事故。

### 3.5 提示词的版本管理

用例集解决"改完能不能判断"，版本管理解决"改坏了怎么回到上一版"。这件事在提示词上必需，因为提示词是最容易被当场修改的东西，它看起来只是一段文字。需要三样东西：

| 要素 | 内容 | 为什么必要 |
|---|---|---|
| 版本标识 | 每次改动一个新标识，随请求一起记录 | 出了坏结果时能确定当时用的是哪一版 |
| 变更记录 | 改了什么、为什么改、跑完用例集的结果 | 三个月后回看，只看 diff 已经看不懂意图 |
| 并行而非原地改 | 新版与旧版同时存在，按标识分流 | 原地改没有回退路径，也没有对照数据 |

第一条在排查时最有用：请求记录里没有提示词版本时，能做的只有"现在这版看起来没问题"，而当时那版可能已经被改过三次；把版本标识写进日志，成本只有一行代码。

第二条更实际：提示词改动通常是挪一句位置或换个说法，diff 微不足道，对输出分布的影响却可能很大；记录里写清改动意图，比留一段 diff 有用。

第三条与缓存规则直接相关：原地改提示词会让所有在途会话的前缀失效一次。并行两个版本各自前缀稳定；原地改每次都是全量失效，还丢掉回退路径。

## 四、这套做法的边界

**第一，六要素是检查清单，不是模板。** 每一项写多少取决于任务：把六项都写成三句话，不代表提示词就好。**第二，结构化输出解决形状，不解决内容。** 字段全对、值全错完全可能发生：`order_id` 指向一个不存在的订单，没有任何一层 schema 能拦住。

**第三，回归测试的覆盖面受用例集限制。** 用例集没覆盖的情况发现不了，而"这次没跑出回归"只说明没撞上已有用例。

**第四，提示词工程的收益有上限。** 资料里没有的内容，提示词写得再清楚也变不出来；这一章适用于"信息已经在输入里，只是表达和格式不可控"，超出这个范围需要检索（讲 RAG 四环节的那一章）。

**第五，约束越严，拒答越多。** 严格 schema 下模型可能因为无法满足约束而返回错误或空，这需要有对应的失败分支。**第六，提示词是代码，不是配置。** 它要 review、要版本、要测试；放进数据库、靠后台界面随时改，看起来更灵活，实际取消的正是这三件事。

**第七，改了提示词并不等于改了行为。** 同一份提示词配上不同的模型、温度、工具清单，输出分布可能差很远，所以回归用例集必须连同「用哪个模型、哪些参数」一起固定。

## 这一章建立的 6 件事

1. 提示词有六项：角色、任务、背景、输入、格式、约束。缺格式、约束、输入时输出照样有内容，只是不可用，这三种最难自查。
2. 六项不必写满，判断标准是"缺失会不会导致看不出来的失效"；长期规则放系统消息，本次数据放用户消息。
3. 结构化输出有两道独立的关：语法与字段。纯文本正则败在第一道，JSON mode 败在第二道，function calling 与严格模式靠 schema 约束结构。
4. 严格模式会把"缺失"改写成"null"，这是一个必须提前决定的表示法问题；它保证形状，不保证语义。
5. 校验分三层：语法、结构、语义。第三层只有业务代码能做，失败时要回灌具体原因，回灌"格式错了"等于让模型重猜。
6. 总数上升可以掩盖个别回归，分类聚合也可能互相抵消；必须逐例比较，并把"修好哪条、弄坏哪条"当成改动的必备输出。
