## 一、同一任务的四种拓扑

第 33 章给了选型判据，这一章给实现。四种拓扑都在 `code/knowledge/ch35_topology/` 下，跑的是同一个任务，输入输出完全相同，差别只在控制权放在谁手里：supervisor、handoff、blackboard 分别把决定权放在中心、当前持有者与板上的条件里，流水线作为对照基线一并实现，它的决定权在设计时就写死了。

```text
任务：读三份日志，定位错误，写一份事故初报
输入：三份日志（每份约 60 字符）
输出：一段初报，包含三条发现与依据
```

四种实现的差别可以压成三个问题：

| 问题 | supervisor | handoff | blackboard | 流水线 |
|---|---|---|---|---|
| 谁决定下一步 | 中心节点 | 当前持有者 | 触发条件 | 设计时的代码 |
| 上下文怎么过去 | 复制任务、回收交接单 | 转移，交出后退出 | 共享工作区 | 上一阶段输出 |
| 什么时候结束 | 中心判断收齐 | 最后一棒交给写者 | 写者读完板 | 最后一个阶段返回 |

共用件也在同一目录的 `actors.py` 里：一个脚本化 actor、一个虚拟时钟、一张交接单。actor 的每次调用记录 agent、动作、输入字符、输出字符与起止时间：

```python
@dataclass
class Actor:
    name: str
    world: World
    trace_id: str = "run-1"
    last_span_id: str = ""

    def run(self, prompt: str, purpose: str, reply: str,
            parent: str | None = None) -> str:
        start = self.world.now_ms
        end = self.world.tick()
        tokens = int(len(prompt) * TOKENS_PER_CHAR) + 20
        self.world.calls += 1
        self.world.tokens += tokens
        span = Span(
            span_id=f"s{next(self.world._ids)}",
            parent=parent,
            agent=self.name,
            purpose=purpose,
            prompt_chars=len(prompt),
            reply_chars=len(reply),
            start_ms=start,
            end_ms=end,
        )
        self.world.spans.append(span)
        self.last_span_id = span.span_id
        return reply
```

关键行是 `self.last_span_id = span.span_id`：下一次调用能把父 span 传进来，trace 才能连成树。没有这一行，所有 span 都是根，成本归因无从谈起。

### 1.1 固定任务与共用件

比较四种拓扑，最容易犯的错误是每种用一个“适合它”的任务：supervisor 用三层审批，handoff 用客服转接，差异里混进了任务本身的复杂度。所以四种实现跑同一个任务：三份日志、三条发现、一份报告，三条发现是否都进报告一眼可判。代价是任务太小，规模效应看不出来，结论只能说差异的方向。

`World` 是虚拟时钟加账本，记录每次调用、推进时间、累计 token。时间按固定步长推进，一次调用 1 秒、一次交接 0.2 秒，不调用 `sleep`。这样做是为了可复现：真实 `sleep` 会让输出随机器负载变化，固定步长让耗时变成调用次数的线性函数。

| 共用件 | 记什么 | 不记什么 |
|---|---|---|
| `World` | 调用次数、消息数、token 估算、起止时间 | 模型真实延迟、网络抖动 |
| `Span` | agent、动作、输入/输出字符、父子关系 | 提示词内容、模型版本 |
| `Brief` | 任务、结论、依据、置信、待决项、用量 | 子 agent 的完整推理过程 |

第三列同样重要。`Span` 不记提示词，提示词可能含敏感数据；`Brief` 不记完整推理，交接单要小到能进上下文。记录边界就是隐私边界与成本边界。`Actor` 每次返回固定剧本的文本，不判断质量，所以四种拓扑只能比成本、延迟与丢失，比不了准确率；判断质量要靠评测集与裁判，那是卷 10 的内容。

### 1.2 四种实现的骨架

四种拓扑的代码长度不同，骨架是同一套，`code/knowledge/ch35_topology/` 下每个脚本都按它写：

```text
准备任务数据 -> 决定下一步 -> 调用一个 actor -> 收下交接单 -> 判断是否结束
```

差别只在决定下一步与收下之后放哪：

| 拓扑 | 决定下一步 | 收下之后 |
|---|---|---|
| supervisor | 中心按已有结论选 | 放进中心的列表，再决定下一个 |
| handoff | 当前棒按阶段计数选 | 拼进上下文，交给下一棒 |
| blackboard | 触发器按板上条件选 | 合并进板 |
| 流水线 | 代码里的下一行 | 作为下一阶段的输入 |

把这张表与四个脚本对照，能看出哪些行是拓扑特有的。输入裁剪、交接单校验、失败处理、trace 记录四件事与拓扑无关，第 38 章的框架版仍然要写它们。

## 二、supervisor 的中心循环

supervisor 是一个循环：中心每轮看已有结论，决定下一个派给谁；worker 只拿到自己那一份输入，交回一张交接单。`code/knowledge/ch35_topology/supervisor.py` 里的循环是：

```python
def run() -> tuple[World, str, list[Brief]]:
    world = World()
    supervisor = Actor("supervisor", world)
    workers = [Actor(f"worker{i}", world) for i in (1, 2, 3)]

    briefs: list[Brief] = []
    for i in (1, 2, 3):
        # 中心节点每派一次活，自己也要花一次调用：看已有结论、决定下一个是谁
        prompt = (
            f"任务：{TASK}\n"
            f"已有结论：{[b.result for b in briefs]}\n"
            f"下一个派给谁？只剩 worker{i}，回 worker{i}"
        )
        supervisor.run(prompt, f"决定派发 {i}", f"worker{i}")
        world.handoffs += 1
        world.now_ms += 200
        briefs.append(read_log(workers[i - 1], i, parent=supervisor.last_span_id))

    world.handoffs += 1
    world.now_ms += 200
    report = write_report(supervisor, briefs, parent=supervisor.last_span_id)
    return world, report, briefs
```

这段循环里有三笔成本，都记在账上：

- `supervisor.run(...)`：每次派发前的决策调用，三份日志三次，收尾写报告再一次。
- `read_log(...)`：每个 worker 一次，三次。
- `world.handoffs += 1`：每条消息 200ms，四次。

输出：

```text
=== 1. supervisor 的调用顺序 ===
  span  父    agent        动作              输入   输出
  s1   -    supervisor   决定派发 1        57    7
  s2   s1   worker1      读日志 1          339   23
  s3   -    supervisor   决定派发 2        82    7
  s4   s3   worker2      读日志 2          334   31
  s5   -    supervisor   决定派发 3        117   7
  s6   s5   worker3      读日志 3          347   33
  s7   s6   supervisor   写报告            396   92
```

`s1`、`s3`、`s5` 是三次中心决策，`s2`、`s4`、`s6` 是三次 worker 调用，`s7` 是收尾。中心节点一共四次调用，比三个 worker 加起来还多：它不是多一个协调者，而是每个 worker 前面都多一次模型调用。`s1` 的输入只有 57 字符，因为决策只看任务和已有结论、不看日志原文；这既是 supervisor 省 token 的方式，也是它失真的原因，中心永远看不到 worker 看到的细节。

### 2.1 中心的三种决策方式

中心每一轮要回答下一个是谁。三种实现方式的成本与可控性不同：

| 方式 | 怎么决定 | 成本 | 风险 |
|---|---|---|---|
| 代码写死 | `for i in (1,2,3)` | 无额外调用 | 不能根据中间结果改派 |
| 规则判断 | 按 `len(briefs)`、字段值分支 | 无额外调用 | 规则覆盖不到的情况会走错 |
| 模型决策 | 中心一次调用，返回下一个 worker | 每次多一次调用 | 决策本身也会错，且难复现 |

示例用规则决定下一个，但每次派发仍记为一次中心调用，因为真实系统里中心通常要让模型判断。如果连这次调用也不记，成本表里 supervisor 会少三次调用，看起来比 handoff 还便宜；那样比较的是写死的分派与模型的交接，不是两种拓扑。三种方式可以混用：先用规则挡掉大部分，规则不确定时才让模型决定；边界要写清楚，否则 trace 里看不出某一步为什么走规则。

### 2.2 退化与消息协议

第一处退化是中心读了全文。中心把 worker 的完整输入也读了一遍，它的上下文与单 agent 一样大，隔离收益归零；可用的检查是中心的输入长度应该接近交接单。

第二处退化是 worker 之间互相可见。交接单全放进每个 worker 的输入，worker 于是能看到别人的结论，这不再是 supervisor，而是一个没有发言顺序的讨论组。判断方法是看每次调用的输入里有没有本不该看到的东西。

supervisor 只有两种消息：派发与回收。两种消息的字段要分开设计，混在一起中心就分不清这是任务还是结果：

| 消息 | 必填字段 | 谁填 |
|---|---|---|
| 派发 | 任务说明、输入、期望输出、截止条件 | 中心 |
| 回收 | 交接单六个字段、状态（完成/失败/需补充） | worker |

第二行的状态最容易被省。worker 失败时如果只交回一个空 `result`，中心无法区分没找到与没做完；可用的做法是回收消息带一个枚举，取值是 done、failed、need_input。派发消息里的截止条件同样常被省：没有它，worker 不知道什么时候该停。

一个 worker 自己可以是一个 supervisor，`code/knowledge/ch35_topology/` 下的脚本都能这样组合。嵌套之后，有几个 agent 取决于在哪一层计数：

```text
顶层 supervisor
├── worker1（内部是流水线：读 -> 找 -> 写）
├── worker2（单 agent）
└── worker3（内部是 supervisor：分成两段扫描）
```

按节点数这里有七个执行者，按上下文边界只有四个：worker1 内部三个阶段共享一个上下文，worker3 内部两个子 worker 各自独立。成本表要按上下文边界计数，否则嵌套会让 agent 数虚高。嵌套的收益来自隔离，代价是每次跨层交接都多一条消息。可用的规则是嵌套不超过两层，再深，trace 会变成一张难读的图。

## 三、handoff 的交接

handoff 没有中心循环。每一棒处理完自己的日志，把上下文交给下一棒，自己退出；控制权通过 `Command`（第 36 章）或一个显式的 `next` 变量传递。`code/knowledge/ch35_topology/handoff.py` 用显式循环展示语义：

```python
def run() -> tuple[World, str, list[Brief]]:
    world = World()
    agents = [Actor(f"agent{i}", world) for i in (1, 2, 3)]
    writer = Actor("writer", world)
    briefs: list[Brief] = []

    context = f"{TASK}\n已知结论：无\n"
    prev: str | None = None
    for i in (1, 2, 3):
        if i > 1:
            world.handoffs += 1
            world.now_ms += 200
        prompt = (
            f"{'x' * SYSTEM}\n"
            f"# 任务\n{TASK}\n"
            f"# 交接上下文\n{context}\n"
            f"# 你这一棒\n读日志 {i}，补一条发现，然后把上下文交给下一棒。\n"
            f"# 日志\n<<<\n{LOGS[i]}\n>>>"
        )
        reply = f"{FINDINGS[i]}（{EVIDENCE[i]}）"
        agents[i - 1].run(prompt, f"第 {i} 棒", reply, parent=prev)
        prev = agents[i - 1].last_span_id
        briefs.append(Brief(task=f"第 {i} 棒", result=FINDINGS[i],
                            evidence=EVIDENCE[i]))
        context += f"- {reply}\n"

    world.handoffs += 1
    world.now_ms += 200
    report = write_report(writer, briefs, parent=prev)
    return world, report, briefs
```

输出：

```text
=== 1. handoff 的调用顺序 ===
  span  父    agent        动作              输入   输出
  s1   -    agent1       第 1 棒           346   33
  s2   s1   agent2       第 2 棒           377   45
  s3   s2   agent3       第 3 棒           438   47
  s4   s3   writer       写报告            396   92

=== 2. 每一棒接手时看到的上下文 ===
  agent1   输入 346 字符，交给下一棒 33 字符
  agent2   输入 377 字符，交给下一棒 45 字符
  agent3   输入 438 字符，交给下一棒 47 字符
  <- 上下文逐棒变大；最后一棒看到的是前三棒的链，不是三份日志
```

三个数字要连起来看。调用从 7 次降到 4 次，因为没有中心决策；消息从 4 条降到 3 条，因为每一棒只交给下一棒；输入逐棒从 346 涨到 438，因为后一棒看到前面所有结论。supervisor 的每个 worker 输入都在 3200 左右且彼此独立，handoff 的输入逐棒增长，累积到第几棒会超过窗口，取决于结论的长度。

### 3.1 退出条件

handoff 没有中心，谁来宣布结束是一个必须显式回答的问题。三种写法：

| 写法 | 谁决定结束 | 风险 |
|---|---|---|
| 最后一棒知道自己是最后一棒 | 代码里的阶段计数 | 阶段数变化时要改代码 |
| 下一棒由当前棒指定 | 当前棒的判断 | 判断错会把控制权传给不该接的人 |
| 条件满足即结束 | 一个显式的终止条件 | 条件写错会提前结束或永不结束 |

示例用第一种：循环跑完三棒之后交给 writer。它最无聊，也最可控，终止条件在代码里，不在模型输出里。第二种是 handoff 与 agent 自治最容易混淆的地方：当前棒决定下一棒，看起来灵活，实际是把一个全局的终止问题交给了局部判断，每一棒都以为后面还有人，最后一棒以为总有人会收尾。责任漂移不是实现 bug，是让每一棒自己决定是否结束的必然结果。

### 3.2 替换实验与压缩

把同一个任务从 supervisor 换成 handoff，只有一件事应该改变：控制权归属。结论也变了、产物格式也变了，说明两种实现共享了不该共享的东西。

可用的检查是三项：三条发现是否都出现在报告里，每个 worker 的输入是否只含自己那份日志，交接次数是否等于棒数减一。第三项在 supervisor 里不成立，它的消息数是 worker 数加一。替换实验要证明的是差异只在设计允许的那一处。

handoff 的输入逐棒增长，长链必然撞窗口。压缩的时机有三种：

| 时机 | 做法 | 风险 |
|---|---|---|
| 每棒都压 | 交给下一棒之前摘要一次 | 每次摘要都丢细节，且多一次调用 |
| 超过阈值才压 | 字符数到上限时摘要 | 阈值附近的行为不稳定 |
| 最后一棒前压 | 收尾时把全部结论合成一段 | 中间棒仍然可能爆 |

第一种最均匀也最贵，N 棒多 N 次摘要调用。第二种省调用，但阈值本身是要调的超参：太高会撞窗口，太低会频繁压。第三种把压缩推迟到收尾，只适合中间棒只需要累积的任务。三种的共同问题是摘要的标准由谁定：每棒自己决定，链尾会收到一份每棒都认为重要的混合体；由写者决定，它又看不到被丢掉的细节。可用的折中是给每一棒一个固定模板，只填结论、依据、置信、待决项，把保留什么从模型判断变成了字段约束。

## 四、blackboard 的写回

blackboard 没有交给下一棒这个动作。每个 worker 读当前板、写自己的发现，写者最后读板，难点在写回：并行写同一份列表，怎么写不丢。`code/knowledge/ch35_topology/blackboard.py` 里的板有三个方法：

```python
@dataclass
class Board:
    findings: list[str] = field(default_factory=list)
    writes: int = 0

    def snapshot(self) -> list[str]:
        return list(self.findings)

    def merge(self, items: list[str]) -> None:
        for item in items:
            if item not in self.findings:
                self.findings.append(item)
        self.writes += 1

    def overwrite(self, snapshot: list[str]) -> None:
        """整份写回：拿的是旧快照，写回时把中间发生的一切盖掉。"""
        self.findings = list(snapshot)
        self.writes += 1
```

`run()` 里每个 worker 的顺序是读快照、生成发现、`merge`，写者最后读 `board.findings`。它的输出：

```text
=== 1. blackboard 的调用顺序 ===
  span  父    agent        动作              输入   输出
  s1   -    worker1      读日志 1          290   23
  s2   s1   worker2      读日志 2          320   31
  s3   s2   worker3      读日志 3          382   33
  s4   s3   writer       读板写报告        330   130

  板上的发现（3 条）：
    - 连接池在 db.py:42 耗尽，重试没有上限（db.py:42）
    - client.py:88 的重试没有 max_attempts（client.py:88）
    - config.py:17 把 timeout 设成 0，等于不超时（config.py:17）
```

输入从 290 涨到 382，因为每个 worker 都看到板上已有的条目。这是共享的代价：板越大，每个 worker 的输入越大，而它们可能只需要其中一两条。第 36 章的 reducer 会把这类合并写进状态定义，真实的 blackboard 要给 worker 一个只看相关条目的过滤。

### 4.1 触发、写者与过滤

示例按固定顺序触发 worker，这其实是流水线的形状。真正的 blackboard 要回答什么时候有人被触发：

| 触发方式 | 怎么工作 | 成本 |
|---|---|---|
| 有新任务就全触发 | 每个 worker 都跑一遍 | 扇出数固定，可能做无用功 |
| 板上的条件满足才触发 | 监听字段变化 | 需要一个触发器与去重 |
| 人手动触发 | 运营点"开始" | 响应慢，但可控 |

第一种最像批处理，第二种才是 blackboard 的本意。它的关键不在共享内存，在板上的状态决定工作：板上出现了一个未处理的错误，负责该类错误的 worker 才被唤醒。第二种的工程代价经常被低估：触发器本身要持久化，否则进程重启后谁该被唤醒就丢了；触发还要去重，否则同一个条目会唤醒同一个 worker 多次。

板上可以有很多写者，但最终报告只能有一个写者。示例把 writer 做成单独一个 actor，读板一次、写报告一次。这条规则消掉一整类冲突：多个 worker 都写报告，后写的覆盖前写的，报告内容取决于调度顺序。

每个字段一个写者，比给板加一把锁便宜。锁能防并发写，防不了两个写者都认为自己在写同一件事；后者是设计问题，锁只会把它变成排队或死锁。

板越大，worker 的输入越大。可用的过滤有三种：

| 过滤 | 怎么选条目 | 适用 |
|---|---|---|
| 按标签 | 只读与本次任务同标签的条目 | 条目有明确分类 |
| 按时间 | 只读最近 N 条 | 条目会过期 |
| 按相关性 | 用检索选 top-k | 条目是自然语言、数量大 |

第三种最像 RAG，也最容易引入新问题：检索选错，worker 会漏掉关键条目；优点是板可以无限增长而输入不涨，代价是多一次检索与一个阈值。第一种最便宜，前提是条目在写入时就打了标签，标签要事先定，写完再补就会出现同一类发现三种标签。过滤规则要写在板的读取接口里，不能留给每个 worker 自己实现，否则写者收到的报告前后不一致。

## 五、写冲突与 reducer

`code/knowledge/ch35_topology/blackboard.py` 里的 `conflict()` 用一段确定的交错复现丢更新。两个 worker 同时读到空板，各自追加，再整份写回：

```python
def conflict() -> None:
    print("=== 2. 同一段交错，两种写回方式 ===")
    print("  步骤：A 读板 -> B 读板 -> A 写回 -> B 写回")
    lost = Board()
    a = lost.snapshot()
    b = lost.snapshot()
    a.append("A 的发现")
    lost.overwrite(a)
    b.append("B 的发现")
    lost.overwrite(b)
    print(f"  整份写回之后：{lost.findings}")
    print(f"  <- A 的发现被 B 的旧快照盖掉，板只涨了 {len(lost.findings)} 条")

    merged = Board()
    a = merged.snapshot()
    b = merged.snapshot()
    a.append("A 的发现")
    merged.merge(a)
    b.append("B 的发现")
    merged.merge(b)
    print(f"  按增量合并之后：{merged.findings}")
    print("  <- 两次写都保留；reducer 写回的是'我新增的部分'，不是'我看到的全部'")
```

```text
=== 2. 同一段交错，两种写回方式 ===
  步骤：A 读板 -> B 读板 -> A 写回 -> B 写回
  整份写回之后：['B 的发现']
  <- A 的发现被 B 的旧快照盖掉，板只涨了 1 条
  按增量合并之后：['A 的发现', 'B 的发现']
  <- 两次写都保留；reducer 写回的是'我新增的部分'，不是'我看到的全部'
```

两种写回方式的结果差一条，原因在写回的语义不同，不在并发控制：`overwrite` 写回整份列表，B 的快照里没有 A 的发现，于是 A 的被覆盖；`merge` 只把新条目追加到当前列表。

reducer 的正确性问题可以在单线程里用一段确定的交错复现。这比偶发失败的并发测试可靠：交错顺序是显式的，失败是必现的。

### 5.1 reducer 的取舍与性质

| reducer | 写回什么 | 适用 | 风险 |
|---|---|---|---|
| 覆盖 | 整份新值 | 唯一写者、状态整体替换 | 有第二个写者就丢数据 |
| 追加 | 新元素 | 列表型发现、日志 | 重复元素要自己去重 |
| 合并 + 计数 | 新元素 + 出现次数 | 多分支独立观察 | 计数需要额外的字段与合并函数 |

第三种是第 33 章那个带计数的 reducer 里的 `votes`：两个分支都看到连接池用到上限，计数为 2。它保住的信息是这是两个独立来源，而不只是有一条发现。下游要按证据强度排序时计数是必需的，只做展示时列表去重就够。

一个 reducer 要能安全地用于并行写，至少满足两条：交换律要求先 A 后 B 与先 B 后 A 结果相同，幂等要求同一个增量合并两次与合并一次相同。列表追加不满足交换律，但发现列表在语义上是集合，它满足的是按内容去重后的交换律。计数 reducer 满足交换律，不满足幂等：同一个分支重放两次，计数变成 2。

这就是第 25 章强调幂等键的原因：reducer 能保证合并结果正确，不能保证同一个增量只来一次，后者要在写回之前用去重键挡掉。

`votes` 记录几个分支独立报到同一条发现，它常被误用成投票：三个分支里两个说回滚，就按多数回滚。这个用法在两种情况下失效。分支不独立时，三个分支共享同一份上下文或同一个模型，两个同意其实是一个。判断与观察混淆时，发现连接池耗尽是观察，判断应该回滚是决策。观察可以计数，判断要标来源：一条发现带 `source` 字段，写明来自哪个分支、哪份输入。

## 六、流水线

流水线把阶段写死在代码里。每个阶段是一个函数，阶段之间靠字段契约连接，上一阶段的输出就是下一阶段的全部输入。`code/knowledge/ch35_topology/pipeline.py` 的三个阶段：

```python
def run() -> tuple[World, dict]:
    world = World()
    reader = Actor("reader", world)
    finder = Actor("finder", world)
    writer = Actor("writer", world)

    merged = "\n".join(LOGS.values())
    reader.run(f"{'x' * SYSTEM}\n# 阶段：合并日志\n{merged}", "合并日志", merged[:40])
    world.handoffs += 1
    world.now_ms += 200

    findings = [FINDINGS[i] for i in (1, 2, 3)]
    evidence = [EVIDENCE[i] for i in (1, 2, 3)]
    finder.run(
        f"{'x' * SYSTEM}\n# 阶段：找错误\n{merged}",
        "找错误",
        "；".join(findings),
        parent=reader.last_span_id,
    )
    world.handoffs += 1
    world.now_ms += 200

    payload = {"findings": findings, "evidence": evidence}
    check(payload, {"findings", "evidence"}, "finder")
    report = "初报：" + "；".join(
        f"{f}（{e}）" for f, e in zip(payload["findings"], payload["evidence"])
    )
    writer.run(f"{'x' * SYSTEM}\n# 阶段：写报告\n{payload}", "写报告", report,
               parent=finder.last_span_id)
    return world, {"report": report, **payload}
```

输出：

```text
=== 1. 流水线的三个阶段 ===
  span  父    agent        动作              输入   输出
  s1   -    reader       合并日志          379   40
  s2   s1   finder       找错误            378   89
  s3   s2   writer       写报告            361   130

=== 2. 阶段之间传的是什么 ===
  reader -> finder：合并后的日志 186 字符
  finder -> writer：findings 3 条 + evidence 3 条
  最终报告：初报：连接池在 db.py:42 耗尽，重试没有上限（db.py:42）；client.py:88 的重试没有 max_attempts（client.py:88）；config.py:17 把 timeout 设成 0，等于不超时（config.py:17）

=== 4. 成本 ===
  agent 数=3 模型调用=3 消息=2 token 估=729 耗时=3400ms
  串行下界    三个阶段的耗时相加，没有并行空间
```

三个阶段、3 次调用、2 条消息，是四种拓扑里最便宜的。代价是第一个阶段要合并全部日志，输入 379 字符里绝大部分是日志原文；日志若有三千字符，这个阶段就是新的上下文瓶颈。第 37 章会把阶段输入存成检查点，恢复才能从中间开始。

### 6.1 阶段契约

`code/knowledge/ch35_topology/pipeline.py` 里的 `check()` 在阶段入口校验字段，它抛出的 `ContractError` 表示阶段契约被破坏：

```python
class ContractError(Exception):
    pass


def check(payload: dict, required: set[str], stage: str) -> None:
    missing = required - set(payload)
    if missing:
        raise ContractError(f"{stage} 的输出缺字段 {sorted(missing)}")
```

坏阶段只交结论、不交依据，它的输出：

```text
=== 3. 一个丢字段的坏阶段 ===
  拦住：finder 的输出缺字段 ['evidence']
  <- 阶段契约把'少一个字段'变成一次显式失败，而不是下游的静默猜测
```

图的边不检查字段，契约要自己写在节点入口。第 38 章用 LangGraph 再写一遍流水线，那里同样需要在节点入口放 `check()`，框架给的是调度，不是字段校验。

### 6.2 并行与恢复

纯流水线是串行的：阶段一完成才进阶段二。但阶段不等于不可并行，要看阶段内部：

| 位置 | 能不能并行 | 说明 |
|---|---|---|
| 阶段之间 | 通常不能 | 后一阶段依赖前一阶段的输出 |
| 阶段内部按条目 | 可以 | 三条发现各自评分，互不依赖 |
| 多个独立流水线 | 可以 | 三份文档各走一条流水线 |
| 合并阶段 | 不可以 | 它是汇合点，必须等全部输入 |

第二行是最容易被忽略的并行机会。阶段函数如果处理一个列表，可以按元素扇出，这不改变阶段顺序，只是把阶段内部的时间压掉，第 36 章的 `Send` 就是做这件事的。第三行的代价是合并：多条流水线各自产出后要有一个步骤合并，而这一步通常是串行的，与第 33 章的加速比公式一致。

阶段失败时，流水线有三种恢复方式，代价差别很大：

| 方式 | 从哪继续 | 代价 |
|---|---|---|
| 整条重跑 | 第一个阶段 | 前面已完成的阶段全部重做 |
| 从失败阶段重跑 | 失败阶段 | 需要保存每个阶段的输入快照 |
| 从失败阶段的下一个继续 | 下一阶段 | 需要确认失败阶段真的完成了 |

第二种是大多数流水线的默认做法，前提是每个阶段的输入被持久化了。没有快照只能整条重跑，而整条重跑会重复执行有副作用的阶段，比如发通知，除非每个阶段都幂等。第三种只适合失败阶段是只读的，或失败发生在返回之后。恢复能力由快照粒度决定：每个阶段存一份输入，恢复就能从任意阶段开始。第 37 章的检查点是同一套思路，粒度从阶段细到超步。

## 七、交接单、降级与成本归因

四种拓扑都需要一个交回什么的约定。`Brief` 是共同约定，定义在 `code/knowledge/ch35_topology/actors.py`，第 38 章沿用同一份字段做对照：

```python
@dataclass
class Brief:
    """交接单：子 agent 交回的东西不是一段话，而是一张可判定的表。"""

    task: str
    result: str
    evidence: str
    confidence: str = "high"
    open_items: list[str] = field(default_factory=list)
    usage_tokens: int = 0
```

六个字段各有用途，`validate()` 只检查前四个。它的输出：

```text
=== 1. 交接单校验 ===
  完整    接收
  缺依据  打回，缺 ['evidence', 'confidence']
  <- 缺 evidence 的结论不能进上下文；否则主 agent 只能选择相信或重读
```

`open_items` 不参与校验，但它是 handoff 与 supervisor 的分水岭。supervisor 的中心可以当场决定这件事我来处理；handoff 的下一棒没有这个权力，它只能把待决项写进 `open_items`，让最后一棒的写者或人来处理。没有 `open_items` 的 handoff，遇到需要上级决定的事只能猜。`usage_tokens` 是成本归因的落点，第 38 章的 trace 会把每个 agent 的调用次数与 token 分开记账。

### 7.1 交接单的字段

交接单不是越全越好。字段每多一个，子 agent 就要多填一段、主 agent 就要多读一段，而其中大部分可能没人用。判断一个字段该不该留，看三个问题：

| 问题 | 该留 | 该删 |
|---|---|---|
| 下游会按它走分支吗 | `result`、`evidence` | 只用于展示的 `summary` |
| 没有它会不会重复劳动 | `open_items`、`usage_tokens` | 可以重算的 `elapsed_ms` |
| 它能不能被机器校验 | `confidence` 的枚举值 | 自由文本的 `notes` |

第一行的字段决定控制流，必须结构化；第二行的字段决定预算与是否追问，必须有；第三行如果只能填自然语言，就不能作为判断依据。`Brief` 只有六个字段，因为任务只有三条发现。真实系统里交接单要按任务类型分几种：审查类要多填严重度字段 `severity`，检索类要多填来源字段 `sources`。

子 agent 与主 agent 可能不是同一天上线的。子 agent 升级后多写一个字段，主 agent 还在按旧字段读；反过来，主 agent 要一个新字段，子 agent 还没更新。三种处理方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| 只加不改 | 新字段可选，旧字段保留 | 字段会越来越多，最终没人知道哪些是必需的 |
| 版本号 | 交接单带 `schema_version`，主 agent 按版本分支 | 要维护多个版本的读取逻辑 |
| 校验加默认 | 缺字段用默认值 | 默认值会掩盖契约破坏 |

第三种最危险，也最常见。`confidence` 缺失时默认 `"high"`，看起来兼容，实际把没交当成了很确定；可用的默认值只有一种：缺失即失败。第二种多写一点代码，但把版本差异显式化了，主 agent 看到 `schema_version=2` 知道要读新字段。版本号不必与软件版本一致，只标识交接单的形状。

---

并行拆开之后，失败的单位从整轮变成某个分支。`code/knowledge/ch35_topology/failure.py` 用两种策略跑同一个超时：

```python
def run(policy: str) -> str:
    findings = ["连接池在 db.py:42 耗尽", "client.py:88 的重试没有 max_attempts"]
    missing: list[int] = []
    for i in (1, 2, 3):
        try:
            if i == 2:
                raise Timeout(f"worker{i} 超时")
            findings.append(f"日志 {i}：已定位")
        except Timeout:
            if policy == "fail_all":
                raise
            missing.append(i)
    tail = f"；缺第 {'、'.join(map(str, missing))} 份" if missing else ""
    return "初报：" + "；".join(findings) + tail
```

```text
=== 2. 一个分支超时，两种策略 ===
  fail_all  整轮失败：worker2 超时
  degrade   继续：初报：连接池在 db.py:42 耗尽；client.py:88 的重试没有 max_attempts；日志 1：已定位；日志 3：已定位；缺第 2 份
  <- 缺的那一项不是后续步骤的前提时，降级比整轮重来便宜
```

选择哪一种，看后面有没有步骤依赖那份缺失的结论。没有依赖就降级并在报告里标注，有依赖就整轮失败或重试该分支。降级要求产物里显式写出缺了什么，否则读报告的人会把没查到当成没问题。第 13 章的兜底是同一套判断：能降级就降级，不能降级转人工，都不行才失败。

### 7.2 降级、超时与成本

降级很容易变成悄悄少做一点，三条纪律能把它挡回来。缺失要可见：报告里写明缺了哪一份、为什么缺。降级要有上界：最多允许缺几项，缺三项还继续，等于用一份残报告冒充完整结论。降级要能追溯：缺的那一项在 trace 里要有一个失败的 span。

第三条最容易被省。报告里写了缺第 2 份，trace 里没有 worker2 的失败记录，复盘时无法判断是超时、格式错，还是根本没派发。上界的取法取决于任务：缺一份还能出初报，缺两份只剩猜测，缺失比例超过三分之一就该改为整轮失败。

分支失败里最常见的是超时。超时不是一种失败，它是一类失败，可能是对方慢、可能是网络断、可能是对方已经做完但响应丢了。三种情况的处理不同：

| 情况 | 怎么判断 | 处理 |
|---|---|---|
| 对方慢 | 超时前有进度事件 | 延长等待或换更快的分支 |
| 连接断 | 没有进度事件，连接被重置 | 用同一任务 id 重连，不重发任务 |
| 响应丢 | 对方可能已完成 | 先查任务状态，再决定 |

第三行是跨进程特有的，第 34 章的 `task_id` 就是为它准备的。本地函数调用没有响应丢，因为返回值与执行在同一个栈上；跨进程时，超时与没执行是两件事。重试要只发生在幂等操作上：worker 读日志是幂等的；worker 发通知不是，重试会发两次。拆分时按子任务有没有副作用给每个分支标一个可重试标志。

---

`supervisor.py` 的 span 表已经是一棵调用树：`s2` 的父是 `s1`，`s4` 的父是 `s3`。把它与 `code/knowledge/ch35_topology/compare.py` 的数字放在一起，就是一张成本归因表：

```text
=== 1. 四种拓扑跑同一任务 ===
  拓扑        agent  调用  消息  token   耗时ms  峰值上下文
  supervisor  4      7     4     1141    7800    396
  handoff     4      4     3     1012    4600    438
  blackboard  4      4     4     873     4800    382
  pipeline    3      3     2     729     3400    379
```

四个数字的读法：调用次数上 supervisor 比 handoff 和 blackboard 多三次，全部花在中心决策上，流水线最少，因为它没有分派；消息数就是交接次数；token 上 supervisor 最高，中心的四次调用输入虽短但次数多，blackboard 最低，worker 之间不经过中心；峰值输入 handoff 最高，达 438，supervisor 最低，396。这张表里没有哪个更好，只有哪一笔账在哪种拓扑下更贵。

| 问题 | 数据从哪来 | 没有它会怎样 |
|---|---|---|
| 这次运行经过了哪些 agent | span 的 agent 字段 | 出问题只能看日志文本 |
| 每个 agent 花了多少 | span 的输入/输出字符 + token 估算 | 成本只能按总数摊 |
| 哪一步是串行瓶颈 | span 的 start/end | 优化错对象，改了不慢的那一段 |

第三行是 trace 与日志的区别。日志记录发生了什么，span 记录发生了多久、在谁的下面。没有父子关系的日志，无法回答这 800ms 是模型慢还是交接慢。

同一张成本表，换一个口径就能得出相反结论。三个口径必须先定：

| 口径 | 算进去什么 | 什么时候用 |
|---|---|---|
| 模型调用 | 只算 LLM 请求的 token | 比较提示词与上下文设计 |
| 端到端 | 模型 + 工具 + 交接 + 排队 | 比较拓扑与部署方案 |
| 单任务全包 | 端到端 + 失败重试 + 人工处理 | 做预算与定价 |

成本表用第二个：虚拟时钟把交接也算进去，但不算失败重试。第一个口径会得出 supervisor 只贵 10%，因为它忽略了三次中心调用的交接时间；第三个口径把降级与人工都算进来，数字更大但更接近真实账单。口径不同不是错，不声明口径才是错。一张表如果不写算不算交接、算不算重试，两个团队的成本下降 20% 可能不是同一件事。

总成本突然上涨时，按 agent 维度拆开，通常落在三种形态之一：

| 形态 | 表现 | 原因 |
|---|---|---|
| 单点放大 | 某一个 agent 的 token 占比超过一半 | 它的输入里混进了完整上下文 |
| 次数放大 | 某个 agent 的调用次数是其他 agent 的数倍 | 循环没有终止，或每次都被重新派发 |
| 长尾 | 平均成本正常，P99 很高 | 个别任务触发了重试或长上下文 |

第一种先查输入：那个 agent 的 prompt 里有没有本不该出现的字段；第二种先查循环：派发条件是不是依赖一个永远不满足的字段；第三种先查重试：一次失败的重试会把 token 翻倍，而平均值看不出来。成本异常不是某个 agent 贵，是某段代码让某个 agent 拿到了不该拿的输入。

## 八、对照、失效与边界

第 38 章会用 LangGraph 把四种拓扑各写一遍。两版的对应关系如下，读到第 38 章时可以逐行对照：

| 手写版 | 框架版 | 框架替掉了什么 | 没替掉什么 |
|---|---|---|---|
| `for` 循环 + 字典分派 | 节点 + 条件边 | 控制流的调度 | 分派判据、交接单校验 |
| 显式 `next` 变量 | `Command(goto=...)` | 控制权转移的表达 | 责任归属、失败降级 |
| `Board.merge` + 锁 | `Annotated[list, add]` | 并发写的合并 | 写者所有权、读取过滤 |
| 阶段函数顺序调用 | 节点 + 边 | 顺序与依赖 | 阶段契约、字段校验 |
| `Actor.run` 手记 span | `astream_events` | span 的采集 | 成本口径、归因规则 |

框架替掉的是调度，没替掉的是判断。一个 supervisor 用 LangGraph 写，仍然要自己决定下一个派给谁；一个 blackboard 用 reducer，仍然要自己决定哪些条目该被读。

### 8.1 与框架版对照

与第 38 章做一次逐项对照，判据不是代码像不像，是同一次输入下行为是否一致：

| 对照项 | 手写版 | 框架版 | 期望 |
|---|---|---|---|
| 调用次数 | 7 / 4 / 4 / 3 | 7 / 4 / 4 / 3 | 完全一致 |
| 产物内容 | 三条发现 + 依据 | 三条发现 + 依据 | 完全一致 |
| 控制流 | 循环/显式 next/merge/顺序 | 条件边/Command/reducer/边 | 结构不同，路径一致 |
| trace | 手记 span | `astream_events` | 层级一致，字段名不同 |

第一行完全一致是刻意设计的：两版都用同一套脚本化 actor，token 与耗时按同样规则计算。调用次数不同，说明框架版多做或少做了一次决策。

第三行是允许不同的地方。控制流的表达方式不同，走过的路径必须相同；路径不同就是两个不同的拓扑。

第四行的差异最大：手写版的 span 是自定义的，框架版用事件流，但父子关系、起止时间、节点名要能对齐。

---

### 8.2 会怎么坏

失效可以按落点分三类。控制权两端：中心的输入长度与 worker 接近，说明中心读了全文，隔离收益归零；输入逐棒线性增长而没有摘要，handoff 会在第几棒撞上窗口；reducer 里出现 `state.field = new_list`，说明写回退成了整份覆盖。

契约与记录上：下游读到默认值而日志里没有报错，说明阶段契约没校验；`Brief` 只有一个 `text` 字段，交接单退化成了自由文本；`parent` 全是 `None`，所有 span 都是根；计量表里没有 agent 维度，成本只有一个总数；span 数与调用次数对不上，说明只记了成功的调用。

设计与产物上：并行分支的异常没有被单独捕获，一个 worker 超时把其余两个的结果丢掉；板只增不删，而写者只读最近几条；第一个阶段的输入等于全部输入之和，阶段化没有带来隔离；派发条件依赖自由文本，节点名匹配就会出错；全部阶段跑完却没有产物，最后一棒没有写者职责。

---

### 8.3 边界

四种拓扑都在一个进程内，交接是函数调用、共享是同一块内存；跨进程要换成第 34 章的 A2A 对象，延迟、失败、鉴权都要重算。脚本化 actor 不是模型：输出是固定剧本，token 按字符估，耗时是虚拟时钟，这些数字能比较结构，不能预测真实模型的成本。

手写版适合控制流简单、需要精确控制的场景；任务再复杂，比如嵌套拓扑、动态图、检查点，手写的维护成本会超过框架。框架版适合需要持久化、流式、可视化的场景，第 38 章的 LangGraph 版会多出检查点与事件流。

blackboard 的 reducer 只解决写不丢，不解决写得对不对：两个分支都写错同一条发现，合并之后仍然错，正确性要靠裁判（第 23 章）或外部验证。supervisor 的中心是单点，挂了整轮就停；handoff 没有全局视角，最后一棒看不到被丢掉的原始输入。

降级只覆盖分支超时，没有覆盖分支交回格式不对的交接单，前者靠 `validate()`，后者要靠裁判或人工。可测试性是手写编排最大的优势：四种拓扑都能用脚本化 actor 做离线测试，无模型、无网络、结果确定；框架版里测试要覆盖框架的行为。跨机器的 trace 合并没有覆盖，trace 上下文须随请求头传播，第 42 章会讲。token 与耗时不能直接搬去估算，要按真实输入长度重算。

## 这一章建立的 7 件事

1. 四种拓扑的差别可以压成三个问题：谁决定下一步、上下文怎么过去、什么时候结束；代码结构由这三问决定。
2. supervisor 的成本是"每个 worker 前面多一次中心决策"，它的收益是中心始终只看交接单；中心读全文就退化成单 agent。
3. handoff 省掉中心调用，代价是上下文逐棒累积；它适合结论短、链路长的任务，不适合每棒都要看全部历史的任务。
4. blackboard 的核心是写回语义：整份覆盖会丢更新，增量合并才保留；写冲突可以用一段确定的交错在单线程里复现。
5. 流水线最便宜也最脆，阶段契约要写在节点入口；第一个阶段如果必须合并全部输入，它就会成为新的上下文瓶颈。
6. 交接单要可校验：`task`、`result`、`evidence`、`confidence` 缺一就打回；`open_items` 决定 handoff 遇到待决项时是猜还是上报。
7. 成本归因要同时有 span 与 agent 维度：调用次数、token、起止时间分开记，才能回答"钱花在谁身上、慢在哪一段"。
