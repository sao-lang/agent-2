## 一、能力的三种形态

第 6 章把工具讲成三样东西：一份 dict 声明、一个函数实现、一次拼进请求的清单。三五个工具时这套写法没有破绽；到二十个外部服务加五套业务流程，三处同时出问题。一是注册分散，每个服务一套写法，声明和实现对不上时没有统一的核对点。

二是与外部服务的生命周期不同步，对方换地址、改接口，本地注册表要跟着改并发一次版；三是范围无法表达，清单里有什么模型就能调什么，这个任务不该看到写操作这件事没有地方写，第 8 章的守卫也管不到它。三个问题的根源是同一个：有哪些能力被写死在代码里，维护者是自己、变化跟着发版走、可见范围是全局。

协议化改的正是这三样，代价与收益都落在可见范围上：

| 谁维护能力 | 写死在代码里 | 协议化之后 |
|---|---|---|
| 维护者 | 你写声明、你写实现 | 对方写 server，你只写配置 |
| 变化频率 | 跟着你的发版 | 跟着对方的发版 |
| 可见范围 | 全局 | Host 按需选 |

外挂能力因此有三种形态，判断标准是谁决定要不要调用它：

| 形态 | 谁维护 | 谁决定调用 | 在模型可见清单里 |
|---|---|---|---|
| 本地函数 | 你 | 模型 | 是 |
| MCP server 的工具 | 对方 | 模型 | 是，带服务器前缀 |
| Skill 的 `scripts/` | 你 | 流程 | 否 |

第三行最容易漏。`scripts/` 里的脚本也是能力，它执行的动作和第 6 章的工具没有区别，区别在触发者：工具的触发者是模型，脚本的触发者是流程。可见性也由此分出三层，本地函数与 MCP 工具都在 `tools` 数组里、靠前缀区分来源，脚本不在数组里、流程走到那一步才可见。

代价要说清：协议化把维护成本转给了对方，换来一个新的失败面，对方的进程可能不响应、可能改方法名、可能升级后行为变化。演进的顺序因此有迹可循，三五个工具、全自己维护，用本地函数；工具数过十、维护者变成外部团队、第二个 agent 要共用，才值得上 MCP。这一层与第 34 章的 A2A 是两条不同的边，A2A 管 agent 之间交接任务。

## 二、进程外的工具

MCP 是让工具活在独立进程里的协议，全称是模型上下文协议：Host 起一个子进程或连一个服务，用 JSON-RPC 按标准方法问答。JSON-RPC 是一种请求与响应都带 `id` 的远程调用格式，两端靠这个编号配对。

本章示例在 `code/knowledge/ch26_mcp/` 里用标准库手写了一个最小服务端，本机没有装官方 `mcp` 包，示例要说明的是协议形状，与第 6 章的最小 client 对照着看，服务端只做三件事：读一行、分发、写一行。

```python
def dispatch(req: dict) -> dict:
    """一条请求进来，一条响应出去。"""
    mid = req.get("id")
    method = req.get("method")
    params = req.get("params") or {}
    if method == "initialize":
        result = {
            "protocolVersion": "2024-11-05",
            "serverInfo": SERVER_INFO,
            "capabilities": {"tools": {}},
        }
    elif method == "tools/list":
        result = {"tools": [{"name": n, "description": t["description"]}
                            for n, t in TOOLS.items()]}
    elif method == "tools/call":
        name = params.get("name")
        if name not in TOOLS:
            return {"jsonrpc": "2.0", "id": mid,
                    "error": {"code": -32601, "message": f"未声明的工具：{name}"}}
        data = TOOLS[name]["handler"](params.get("arguments") or {})
        result = {"content": [{"type": "text", "text": json.dumps(data, ensure_ascii=False)}]}
    else:
        return {"jsonrpc": "2.0", "id": mid,
                "error": {"code": -32601, "message": f"未声明的方法：{method}"}}
    return {"jsonrpc": "2.0", "id": mid, "result": result}
```

三个分支对应协议里最常用的三个方法，`initialize` 交换版本与能力，`tools/list` 列清单，`tools/call` 执行。跑一遍完整往返，`code/knowledge/ch26_mcp/` 的输出是四次请求、四条响应：

```
=== 1. initialize（Host 起一个 Client，连一个 stdio server）===
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "serverInfo": {
      "name": "mini-order",
      "version": "0.1.0"
    },
    "capabilities": {
      "tools": {}
    }
  }
}

=== 2. tools/list：Host 先按白名单过滤，再加前缀进清单 ===
  order__get_order     <- 查询订单。返回 JSON：status / signed_days_ago。
  order__get_policy    <- 查询退货政策。返回 JSON：window_days。
  （refund_apply 已声明，但不在 Host 白名单里，不进清单）

=== 3. tools/call -> tool 消息 ===
  {"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "{\"status\": \"已签收\", \"signed_days_ago\": 3}"}]}}
  {'role': 'tool', 'tool_call_id': 'call_3', 'content': '{"status": "已签收", "signed_days_ago": 3}'}

=== 4. 未声明的工具（server 侧默认拒绝）===
  {"jsonrpc": "2.0", "id": 4, "error": {"code": -32601, "message": "未声明的工具：drop_table"}}

=== 5. Host 侧默认拒绝（声明过，但本阶段不给）===
  {"error": {"code": -32000, "message": "工具不在本阶段的可见集：refund_apply"}}
```

第 2 段里 server 声明了三个工具，进清单的只有两个，第三个 `refund_apply` 是写操作，Host 侧按白名单没有接进来，这就是后面两道闸的第一道。

### 2.1 三个角色

协议里有三个角色，分清它们才能确定权限边界写在哪：

| 角色 | 是谁 | 决定什么 |
|---|---|---|
| Host | 你的 agent 应用 | 接哪些 server、每个 server 露哪些工具、给哪个阶段用 |
| Client | Host 内的连接器 | 与某个 server 一对一通信，管超时与重连 |
| Server | 外部进程或服务 | 提供工具、资源、提示 |

Host 是那个跑着模型的应用，Client 是 Host 内部的连接件，Server 是能力提供方；一个 Host 可以挂多个 Client，Server 不知道自己被谁用，也不知道别的 Server 存在。Host 是唯一的决策点：是否接入、这个阶段接哪几个工具、要不要审批，都在它这一侧，第 8 章的预算与守卫也挂在它这里。

### 2.2 前缀与两个编号

外部工具进模型可见清单时要加前缀，前缀写成 `server__tool` 的形式，实现在 `code/knowledge/ch26_mcp/` 里：

```python
def namespaced(server: str, tool: str) -> str:
    """外部工具进模型可见清单时加前缀，避免与本地工具撞名。"""
    return f"{server}__{tool}"
```

前缀不是美观问题。两个 server 都可能提供一个叫 `search` 的工具，混在同一份清单里模型分不清该调哪个，加了前缀，来源与权限就能按前缀区分。

调用返回值的形状与第 6 章的 `tool` 消息不同，MCP 返回的是 `content` 数组，可以有多个内容块，转成 `tool` 消息要自己做：

```python
def as_tool_message(call_id: str, resp: dict) -> dict:
    """MCP 的 content 数组 -> 第 6 章那条 tool 消息。"""
    if "error" in resp:
        payload = json.dumps({"error": resp["error"]["message"]}, ensure_ascii=False)
    else:
        blocks = resp["result"].get("content", [])
        payload = "".join(b.get("text", "") for b in blocks if b.get("type") == "text") or "{}"
    return {"role": "tool", "tool_call_id": call_id, "content": payload}
```

转换函数里有两处容易写错。第一处是 `tool_call_id` 用哪个编号，JSON-RPC 的 `id` 与 `tool_calls.id` 是两套编号，混用会让下一轮回灌找不到对应调用，第 6 章的回灌三条要求在这里第一次跨进程。第二处是空文本兜底，只有图片块、没有文本块的返回，不兜底回灌进去就是空字符串，模型会把它当成工具什么都没返回。

### 2.3 两道默认拒绝

示例的第 4、5 段是两道不同的闸，都在 `code/knowledge/ch26_mcp/` 里，两个字都在拒绝，拒绝的位置不同。第一道在 server 侧，只执行声明过的工具，没声明过的名字返回 `-32601`，即协议里方法不存在的错误码。第二道在 Host 侧，声明过、也在白名单外，请求根本不发出去，这层白名单与第 22 章的编排决定谁能调谁同源：

```python
def host_call(client: Client, allow: list[str], name: str,
              args: dict, mid: int) -> dict:
    """Host 是唯一决策点：不在本阶段白名单里的调用，不发给 server。"""
    if name not in allow:
        return {"error": {"code": -32000,
                          "message": f"工具不在本阶段的可见集：{name}"}}
    return client.request("tools/call", {"name": name, "arguments": args}, mid)
```

两道闸缺一不可。只有 server 侧，这个阶段不该用的工具仍然在清单里，模型会调它、会成功；只有 Host 侧，server 自己实现错了也没有人挡。默认拒绝的意思是清单只列这个阶段需要的，其余一律不接，而这条要靠两处都写才成立。

### 2.4 治理的三条硬要求

接一个外部 server 不只是连上，三条要求在配置里都要有位置：

| 要求 | 做法 | 不做的后果 |
|---|---|---|
| server 白名单 | Host 配置列出允许接入的 server | 任意 server 都能接进来 |
| 工具白名单 | 每个 server 只暴露一部分工具 | 一个 server 的五十个工具全进清单 |
| 超时与隔离 | 每次调用有上限，一个 server 故障不拖住其他 | 卡住的 server 让循环停在那一步 |

第二条是本章第八节的收窄在 server 维度上的应用，一个 server 常同时提供读与写两类工具，Host 只接读的那几个。第三条在进程外架构里是必需品，本地函数失败会立刻抛异常，跨进程失败可能表现为一直没返回，第 7 章的步数上限在这里拦不住卡住的调用。

传输方式影响这三条怎么落。stdio 的进程由本地起，身份由进程是本地的这件事保证，适合本地工具与开发期；HTTP 与 SSE 要额外做认证与鉴权，适合跨机器的服务。

### 2.5 一次调用的五个步骤

跨进程调用比本地函数多几步，每一步都可能失败，失败的样子各不相同：

| 步 | 动作 | 失败形态 |
|---|---|---|
| 1 | 序列化请求 | 参数里有不可序列化的值 |
| 2 | 写入管道 | 管道断开（进程已经退出） |
| 3 | server 处理并写回 | 超时、崩溃、卡在等锁 |
| 4 | 读一行并解析 | 输出不是 JSON、或不止一行 |
| 5 | 转成 `tool` 消息 | 结构不符，字段名对不上 |

第四步在实际部署里会遇到，一些 server 顺手把日志打到标准输出，而协议规定标准输出只放协议消息，多一行日志就破一次解析。第五步最容易漏，协议走通了、消息转错了，表现出来的仍然是工具调用失败，而回灌的三样东西，角色、`tool_call_id`、内容，少一样模型就接不上，第 19 章的装配在这里第一次吃到结构错误的代价。

### 2.6 三个能力面

协议里一个 server 除了 tools，还可以提供 resources 与 prompts。resources 是按 URI 读的资料，prompts 是预置的模板；工具进清单、占上下文，资源不进清单、按名读取，这条差别是按需加载的地基，与第 14 章的检索是两套东西。

判断用哪个，看资料的更新频率跟着谁走。退货政策由法务每季度改一次、改完要同步给所有 agent，用 resources；一次任务里拼出来的临时上下文，留在本地，不必做成对外能力。

## 三、流程写进提示词

有些能力不是一个动作，而是一套流程：先查什么、再核对什么、什么情况走哪条分支、结论怎么组织。把这套东西写进系统提示词，在工具少的时候还行；十套流程同时在场时，两个问题一起出现。一是撞窗口，系统提示词每次请求都要带上，示例里一份 `SKILL.md` 正文是 570 token，十套就是 5700，第 19 章讲的常驻部分就是它。

被挤掉的第一样东西是依据，第 3 章讲过窗口挤满的一种形态是裁剪把检索到的原文裁掉、只留结论，模型因此失去了核对的材料。二是互相干扰，十套流程同时在场，模型要先判断这次该按哪套走、再在选中的那套里执行，任何一步判错都走错路径。

这两个限制指向同一个不对称：工具一直都在，流程一次会话只用一套。把账摊开看：

| 供给方式 | 常驻部分 | 十套流程的常驻量 |
|---|---|---|
| 全部写进系统提示词 | 十套正文全部 | 5700 token |
| 三级加载，没有命中 | 十套的元数据 | 820 token |
| 三级加载，命中一套 | 十套元数据 + 一套正文 | 1390 token |

这两个数来自本章的示例目录，用 cl100k_base 实算，差七倍。还有第三笔账不在 token 上：写在系统提示词里，改一句话要发一次版；写成目录里的文件，改完下次读取就生效。

### 3.1 三种供给方式

流程的供给有三种方式，差别在于什么时候付钱：

| 方式 | 常驻成本 | 命中成本 | 主要代价 |
|---|---|---|---|
| 全部写进系统提示词 | 全部正文 | 无 | 撞窗口、互相干扰、改不动 |
| 全部按需 | 无 | 一次判断 + 正文 | 判断没有依据，输入里没有"有哪些流程"这条信息 |
| 三级加载 | 元数据 | 正文 + 用到的资源 | 元数据要写准，否则退化成全量 |

第二行看起来最省，实际不成立：输入里没有有哪些流程这条信息，模型就不会去读任何一套。按需加载的前提是这条信息在场，代价因此落在元数据的质量上，目录页写得含糊，模型要么不读，要么把几套都读一遍，后者的判据见第六节，与第 44 章的评测口径一致。

## 四、按需加载的三级

Skill 是流程的文件系统形状，一个目录装一套流程。它的思路是把流程从提示词里挪出来，脚本在 `code/knowledge/ch26_skills/` 里，按需加载，它和第 20 章的记忆不是一层：记忆存事实，Skill 存流程。加载分三级，每一级回答一个不同的问题：

| 级别 | 加载什么 | 什么时候 | 回答的问题 |
|---|---|---|---|
| L1 | `name` + `description` | 常驻，永远在输入里 | 有没有一套流程可能相关 |
| L2 | `SKILL.md` 正文 | 这套流程被选中时 | 这套流程具体怎么做 |
| L3 | `references/`、`scripts/`、`templates/`、`tests/` | 某一步真的需要时 | 这一步的细节与工具在哪 |

三级里只有 L1 是每个请求都付的，它回答的问题很窄：这次请求像不像这套流程管的事。L2 回答怎么做，只在选中之后付；L3 是执行到那一步才读的资料与脚本。把三级量出来：

```python
def measure(root: str) -> dict:
    skill_md = read(os.path.join(root, "SKILL.md"))
    l1 = tokens(frontmatter(skill_md))
    l2 = tokens(skill_md)
    total = 0
    files = 0
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames if d not in SKIP]
        for f in filenames:
            total += tokens(read(os.path.join(dirpath, f)))
            files += 1
    return {"L1": l1, "L2": l2, "L3": total, "files": files}
```

`frontmatter` 取的是 `SKILL.md` 开头两个 `---` 之间的部分，也就是 `name` 与 `description`，它是 L1 的全部内容。三级量出来的比例写在下面：

```
=== 2. 三级加载的 token 占用（cl100k_base）===
  L1 元数据常驻（frontmatter）         82 token
  L2 命中后加载（SKILL.md 全文）      570 token
  L3 资源全读（6 个文件）           2974 token
  L3 / L1 = 36.3 倍；L3 / L2 = 5.2 倍
  命中一套时 = 十套 L1 + 一套 L2 + 这次真正读到的 L3
```

L3 是 L1 的 36 倍，这个比例说明三级加载的意义不在总共少读了多少，在读的时机：一次退货审单只读一套流程的正文，其余九套只付元数据。它有一个前提，漏了就退化：L1 的信息必须足以判断该不该加载 L2，只写 `name` 和一句做什么不够，第 3 章的窗口预算在这里表现为 L1 的常驻开销。

### 4.1 命中两套的信号

三级加载有一个可观测的失效：单次请求里出现了两套以上的 `SKILL.md` 正文。它意味着触发判定没有把两套分开，后果不只是多花 token，步骤冲突、输出格式冲突、边界冲突会同时出现，第 19 章的装配会被两套正文同时占满。

信号阈值可以定得很具体：同一次请求里 L2 加载超过一份就记一条。数量少时人工看，多了之后自然会推动改描述，因为它把判定质量变成了一个可以统计的数。

## 五、目录的五个部分

一个能用的 Skill 不是一份 markdown，是一棵目录，它的单位是流程而不是文档，与第 14 章的文档库不同。本章示例的目录在 `code/knowledge/ch26_skills/` 下，每一项后面是字符数：

```
=== 1. 一个完整 Skill 的目录树 ===
refund-review/
├── references/
│   ├── exception.md       335 字符
│   └── policy.md         1180 字符
├── scripts/
│   └── check.py          1292 字符
├── templates/
│   └── reply.md           195 字符
├── tests/
│   └── test_check.py     1262 字符
└── SKILL.md               799 字符
```

五个部分各管一件事：

| 部分 | 内容 | 什么时候用 |
|---|---|---|
| `SKILL.md` | 元数据 + 步骤 + 判定规则 + 资源清单 + 边界 | 元数据常驻；正文命中才读 |
| `references/` | 长条款、例外情形 | 某一步需要细节时按名读一份 |
| `scripts/` | 可执行代码，确定性动作 | 流程走到那一步时执行 |
| `templates/` | 输出格式 | 生成最终结果时套用 |
| `tests/` | 上面那些脚本的离线单测 | 改脚本之后、上线之前 |

前三项在多数介绍里都会出现，后两项最容易被省。`scripts/` 被省掉，结果是该用代码算的东西让模型算；`tests/` 被省掉，后果更隐蔽：脚本改坏了，流程仍然跑得通，只是校验那一步失效。跑一遍脚本与单测：

```
=== 4. L3 的脚本被执行一次 ===
  tests/test_check.py -> OK
  一致的结论 -> exit=0  PASS 结论与数字一致
  矛盾的结论 -> exit=1  FAIL 结论与数字矛盾：9 与 7 应为不可退，写的是 可退
```

第一行是单测；第二、三行是同一个 `check.py` 跑在两条结论上，矛盾的那条以退出码 1 结束，流程据此可以要求重算。这类信号必须来自脚本，模型自己说这条不对不算数。

L2 的正文要写四段东西，缺一段就有一种失效：

```text
---
name: refund-review
description: 处理电商退货审查，判断某笔订单是否符合退货条件。当用户询问订单能否退货、需要核对签收天数与政策窗口、或要求给出退货结论时使用。需要订单号；缺订单号时先索取。
---

# 退货审查

## 步骤
1. 取订单签收天数：调 `order__get_order`，读 `signed_days_ago`。
2. 取政策窗口：调 `order__get_policy`，读 `window_days`。
3. 判定：`signed_days_ago <= window_days` 则可退，否则不可退。
4. 组织回复：用 `templates/reply.md`，结论在前、依据在后。
5. 交付前校验：跑 `scripts/check.py`，确认结论与两个数字一致。

## 判定规则
- 签收天数按自然日算，签收当天记为第 0 天。
- 窗口以政策返回的 `window_days` 为准，不在正文里写死 7 天。
- 两者相等算可退（第 7 天当天仍可退）。

## 资料
- `references/policy.md`：退货政策完整条款（第 3 步判定前必读）。
- `references/exception.md`：例外情形（定制商品、预售、生鲜时读）。

## 边界
- 只处理退货。换货、维修、发票重开、物流查询不属于本流程。
- 只回答"某笔订单能不能退"。政策条文本身怎么规定，走检索，不激活本流程。
```

上面是摘录。五段的分工是：frontmatter 决定能不能被选中，步骤决定怎么做，判定规则决定分支怎么走，资料清单决定细节从哪来，边界决定什么情况不属于它。只有清单、没有触发条件的写法会退化，模型看到三份资料无法判断哪份此刻需要，倾向全读，L3 就变成了 L1。

### 5.1 一个反例

常见的误用是往 `references/` 里塞一整个手册，然后指望 Skill 负责回答手册第 3.2 节说什么。这混淆了两件事：按固定流程做事，与从大量文档里找依据，前者是 Skill，后者是检索，第 14 章讲的四个环节就是后者。放错之后的表现是可识别的，`references/` 里的文件越来越多，L3 的加载量持续上涨，而答案质量没有跟着涨。

### 5.2 版本与灰度

Skill 是要改的，改动有四类，风险与验证方式各不相同：

| 改动 | 风险 | 怎么验 |
|---|---|---|
| 改 `description` | 触发率变化 | 跑第六节的矩阵，看两个错误率 |
| 改步骤或判定规则 | 结论变化 | 用第 23 章的裁判批量回扫历史产物 |
| 加 `references/` 文件 | L3 变大 | 看正文里有没有引用它、引用得对不对 |
| 改 `scripts/` | 校验静默失效 | 跑 `tests/`，再看一次矛盾样本 |

第一行最容易被当成只是改了一句话，但 `description` 就是触发判据，改它等于改什么时候用这套流程。第四行风险最隐蔽，脚本改坏了流程仍然跑得通，只是校验那一步不再拦，所以每次改脚本都要跑单测，并保留一条应当失败的样本。第二行的批量回扫成本最低，拿历史产物按新规则重跑判据，不动模型，几秒钟能看出改动的影响面，改判据时可以直接复用第 23 章的裁判输入。

## 六、触发判定

Skill 能不能用上，取决于 `description` 写得够不够准，第 8 章的守卫看过程信号，这里看的是元数据，它要回答三个问题，少一个问题就少一类判断依据：

| 要素 | 回答什么 | 示例 |
|---|---|---|
| 做什么 | 这套流程处理哪类事 | 处理电商退货审查，判断订单是否符合退货条件 |
| 什么时候用 | 什么信号出现时该用它 | 用户询问订单能否退货、要求给出退货结论时 |
| 需要什么 | 用之前要有什么 | 需要订单号；缺订单号时先索取 |

只写第一项是最常见的错。什么时候用这一项决定召回，模型在多个 Skill 之间比较时，比的就是这一段与当前请求的接近程度；需要什么决定流程能不能开始。还有第四段，通常写在正文的边界里：什么情况不属于它，这一项决定误触。

两个错误方向要分开量：

| 错误 | 表现 | 修法 |
|---|---|---|
| 该触发没触发（漏召） | 用户问退货，走了通用回答 | 往"什么时候用"里补词 |
| 不该触发却触发（误召） | 换货、发票问题激活了退货流程 | 往边界里划出去 |

修法相反，所以两个数必须分开报。只报一个准确率会把两个方向的改动混在一起，补了触发词，漏召降了、误召可能升，一个加一个减，总数看不出来。量法是留出集：准备二十条真实形状的问法，一半该触发一半不该，逐条看判定结果，这份留出集与第 44 章的评测集同构。

下面的脚本把四版 `description` 跑在同一批用例上，`code/knowledge/ch26_skills/` 里的判定器是词面重合的替身：

```python
def decide(case: str, desc: dict) -> int:
    """1 = 触发。边界段优先；没有触发条件段时，域词命中即触发。"""
    if any(w in case for w in desc["exclude"]):
        return 0
    if not desc["when"]:
        return 1 if any(w in case for w in desc["what"]) else 0
    hit = any(w in case for w in desc["what"]) and any(w in case for w in desc["when"])
    return 1 if hit else 0
```

A 到 B 误触发从 5 降到 2，代价是漏掉一条：A 只有做什么，任何带退字的请求都会触发。B 到 C 把误触发压到零，C 到 D 补回漏掉的那一条，退货运费谁出是流程内的问题，问法里却没有能不能退。四步说明漏召与误召是两个可以分别降的数，但它们会互相牵动。

矩阵本身也有边界，二十条用例只覆盖二十种问法，判定器换成模型之后，同一条用例的判定可能随上下文变化，所以这份账要定期重跑。

### 6.1 留出集怎么建

留出集的质量决定这份账能不能用，四件事按顺序做。正负各半，全是该触发的用例就只量得出召回；按线上分布抽，写用例的人容易写出标准问法，而线上问法是带指代、缺主语的句子。

标注要写依据，一条用例标该触发，要写清依据 `description` 的哪一句或哪条边界。判定记录要留档，每条请求记请求原文、候选流程集合、最终选中、判定器版本，少一样就无法复算。用例还会过期，线上问法变了、政策换了，同一批用例的结论就不再代表当前，第 13 章讲分流时提过同一条。

### 6.2 多套之间的比较

上面的矩阵是单套判定，一条请求要么进要么不进。系统里通常有十套流程，判定因此不是十次独立的二分类，而是一次比较。差别会改变错误的样子：单套视角下换货那句是一次误触发，多套视角下它是两套都命中、被谁判走。

处理方式有两层：各自写清边界，让重叠区尽量小；给重叠区一个固定顺序，和第七节的裁决顺序一样，写进代码而不是交给模型。单套用例只覆盖第一层，第二层要另建一份多套用例，跑出来看的是混淆矩阵。

## 七、能力冲突的裁决

一个系统里同时存在四类能力来源，它们回答的问题不同，前两类来自第 6 章的工具层，后两类来自第 14 章的检索与第 20 章的记忆，裁定的实现在 `code/knowledge/ch26_skills/` 里：

| 来源 | 回答什么 | 在哪一章 |
|---|---|---|
| 工具 | 能做什么动作 | 第 6 章 |
| Skill | 按什么流程做 | 本章 |
| 检索 | 依据什么资料 | 第 14–19 章 |
| 记忆 | 以前发生过什么 | 第 20 章 |

四类的边界在正常情况下是清楚的，动作、流程、依据、背景各管一段。冲突发生在两个都能处理当前请求时，典型的是这句话既像一个工具调用，又像一套流程的第一步。裁定顺序必须固定，不能交给模型临时判断：

```python
def rule(req: dict) -> tuple[str, str]:
    """返回 (裁决, 理由)。顺序即优先级。"""
    if req["skill"]:
        return "Skill", f"命中流程 {req['skill']}，流程是审过的，优先于临时拼凑"
    if req["tool"] and not req["rule_text"] and not req["past"]:
        return "工具", f"只要一个事实，{req['tool']} 直接给，不必走流程"
    if req["rule_text"]:
        return "检索", "问的是条文本身，要的是依据，不是某笔订单的结论"
    if req["past"]:
        return "记忆", "指代过去发生的事，只有记忆里有"
    return "直接回答", "四类都没有可用依据，交回模型作答"
```

四条请求跑一遍：

```
=== 2. 四条请求的裁决 ===
  A1001 能退吗？
    命中：skill=refund-review tool=order__get_order 条文=False 过去=False
    裁决：Skill —— 命中流程 refund-review，流程是审过的，优先于临时拼凑
  查一下 A1001 的状态
    命中：skill=None tool=order__get_order 条文=False 过去=False
    裁决：工具 —— 只要一个事实，order__get_order 直接给，不必走流程
  退货政策第几条说了七天
    命中：skill=None tool=None 条文=True 过去=False
    裁决：检索 —— 问的是条文本身，要的是依据，不是某笔订单的结论
  我上次那笔退货最后怎么判的
    命中：skill=None tool=None 条文=False 过去=True
    裁决：记忆 —— 指代过去发生的事，只有记忆里有
```

前两条请求的差别只在用词，能退吗要一个判断，查状态要一个事实，同一个数据源走的路不同。第三行最容易误判，它含退字，但也含查，顺序对了才会先走工具，顺序反了就会绕一圈：

```
=== 3. 同一条请求按不同顺序裁，会走到哪 ===
  请求：A1001 能退吗？
  顺序 A ['Skill', '工具', '检索', '记忆'] -> Skill
  顺序 B ['工具', '检索', '记忆', 'Skill'] -> 工具
```

同一句话，两个顺序，两条路径。顺序写死在代码里，才有同一次任务的两次运行走同一条路这回事。Skill 优先的理由不是流程更高级，是流程是人审过的：步骤、判定规则、边界都在文件里，改一次要过评审。检索与记忆排在后面，理由不同，它们只提供材料、不决定流程。

### 7.1 记忆与政策冲突

四类能力里，记忆最容易与其他三类冲突，因为它存的是过去，另外三类给的是现在。一个具体的冲突：记忆里存着用户上次问的那单结论是可退，这次政策窗口从七天改成五天，同一单按新政策不可退，听谁的。

规则是事实以工具与检索为准，记忆只提供背景与偏好。记忆里的结论是当时的判定结果，有效期与当时的政策绑定；处理方式是降权并标注来源，不删除那条记忆，把它当作用户之前问过这单的背景，而不是这单可退的依据。

记忆与 Skill 的冲突不同：记忆里写着这个用户偏好简短回复，Skill 的模板要求结论在前、依据在后、附条款，两者不矛盾，靠 Skill 的格式加记忆的篇幅控制可以共存。

## 八、工具收窄

第 6 章 1.5 讲过工具越多选择越差。收窄就是把这个阶段用不到的工具从清单里拿掉，实现位置在 Host，清单本来就是它拼的。写进提示词的只用这几个工具是软约束，模型可以被说服；`allowed-tools` 是硬约束，不在清单里的名字调不动。

收窄有四个维度：

| 维度 | 依据 | 例子 |
|---|---|---|
| 阶段 | 当前在做什么 | 已拿到订单，只留查政策与提交 |
| Skill | 当前激活的流程 | 激活退货流程，只留它引用的工具 |
| 权限 | 谁在用 | 只读用户看不到写工具 |
| 数量上限 | 硬性阈值 | 每次最多八个 |

前两行是效果需求，第三行是安全需求，第四行是兜底。四条都不做，工具一多必然出现该调不调与调错。收窄的实现是每次拼清单时算一遍，代码在 `code/knowledge/ch26_skills/` 里：

```python
def pick(task: str, tools: list[dict]) -> str:
    """字符二元组重合最多者胜；同分取清单里靠前的。"""
    t = grams(task)
    scored = [(-len(t & grams(x["name"].replace("__", " ") + " " + x["desc"])), i, x["name"])
              for i, x in enumerate(tools)]
    return sorted(scored)[0][2]
```

选择器是示例里的脚本化替身，用词面重合代替模型判断，只用来比较同一批任务在两份清单上的结果。

收窄过头的代价也可测，把每个阶段都只留一个工具会怎样：

```
=== 3. 收窄过头：每个阶段只留一个工具 ===
  查订单    只留 1 个 -> 本阶段 2/3 个任务的必需工具不在清单里
  退货判定  只留 1 个 -> 本阶段 1/1 个任务的必需工具不在清单里
  写知识    只留 1 个 -> 本阶段 2/3 个任务的必需工具不在清单里
  客户沟通  只留 1 个 -> 本阶段 3/4 个任务的必需工具不在清单里
  数据      只留 1 个 -> 本阶段 1/2 个任务的必需工具不在清单里
```

必需工具不在清单里时，模型不会报工具不够，它会用现有工具硬凑，产出一份格式正确、数字编造的答案。合适的位置是当前阶段可能用到的全部，再加少量下一步可能用到的，经验区间是五到十个。

### 8.1 收窄与顺序

收窄与 Skill 激活有先后，顺序反了会出现收窄了却调不动，这一对在 `code/knowledge/ch26_skills/` 里都有示例：

| 顺序 | 结果 |
|---|---|
| 先激活 Skill，再按它收窄 | 正确 |
| 先按通用集合收窄，再激活 Skill | Skill 需要的工具可能不在清单里 |

根因是收窄的依据来自 Skill，可见集是这套流程引用的工具，所以流程必须先确定。这类配置错误可以写成一行断言，在激活时校验：

```python
def check_skill_tools(skill_text: str, visible: list[str]) -> list[str]:
    """SKILL.md 正文里提到的工具名，是否都在激活时的可见集里。"""
    mentioned = set(re.findall(r"[a-z]+__[a-z_]+", skill_text))
    return sorted(mentioned - set(visible))
```

两个阶段的可见集跑一遍：

```
=== 5. Skill 引用的工具是否都可见 ===
  退货判定  缺：无
  查订单    缺：['order__get_policy']
```

第二个阶段缺了 `order__get_policy`，而 `SKILL.md` 的第 2 步就要调它，这类缺失在启动时就要拦，不能等到调用失败才发现流程跑不动。

### 8.2 收窄与缓存

第 3 章 4.2 讲过缓存只命中从头开始的连续前缀，工具清单通常紧跟在系统消息之后，所以清单变了缓存就失效。三种收窄频率的代价如下：

| 收窄策略 | 清单稳定性 | 缓存影响 |
|---|---|---|
| 按 Skill 收窄 | 整个 Skill 期间不变 | 小 |
| 按阶段收窄 | 阶段切换时变 | 中 |
| 按每步的实际需要收窄 | 每步都变 | 大 |

每步都换清单看起来最精确，实际最贵，等于每步都放弃缓存。推荐的折中是阶段内清单固定，阶段切换时重算一次，清单的变化次数就从步数降到阶段数。

### 8.3 权限维度与审批

收窄的四个维度里，权限是唯一与安全直接相关的一条，也最容易做成半截。只读用户看不到写工具要落在清单上，不能落在一句提示词上：提示词里写不要调用写工具，模型可以被上下文说服；清单里没有这个名字，它就调不动。

但收窄只是第一层。一个写工具留在清单里、也确实该由这个阶段用，还需要第二层：审批，第 30 章讲哪些动作必须人点头。两层的记录要分开，收窄的效果看清单，每个阶段可见几个、命中率多少；审批的效果看放行率与拒绝理由。

## 九、这一层的失效

失效有六种。一是工具撞名，没有前缀时两个 server 的 `search` 会互相覆盖或让模型选错。二是描述写得像广告，强大的数据分析能力这类描述无法支撑判定。三是 L3 加载失控，`references/` 里放一百个文件而正文没写什么情况读哪个。

四是收窄过头，只留两三个工具时模型会用现有工具硬凑。五是跨进程的延迟，每次调用都要过一次序列化与进程边界，比本地函数慢一个数量级，第 7 章的步数上限与第 3 章的 token 预算都要按这个延迟重算。六是脚本改坏没有信号，校验失效后流程照常跑完，只是不再拦矛盾结论。

## 十、边界

MCP 不是必须的，三五个工具、全自己维护、没有第二个 agent 共用，本地注册更简单，第 6 章的最小写法就够。Skill 不是提示词模板，模板是替换变量，Skill 是什么情况做什么的流程，带资料、脚本与测试。三级加载依赖资源清单，L2 里不写有哪些文件、什么时候读哪个，L3 就不会发生。

收窄是动态的，同一批工具在不同阶段可见的集合不同，清单不能是常量，这条与缓存冲突，折中在阶段边界。冲突不能靠模型自觉，裁决顺序必须写成规则，否则同一次任务的两次运行可能走出不同的路。这一层不解决能力做坏事，收窄挡住不该给这个阶段的工具，挡不住给了的工具被用错，第 27 章接着讲这一层的边界。

## 这一章建立的 6 件事

1. 外挂能力有三种形态，判据是谁决定调用它：模型决定的是工具，流程决定的是 `scripts/` 里的脚本；可见范围由 Host 决定，不由 server 决定。
2. MCP 的三个角色里 Host 是唯一决策点；工具进清单要加前缀，JSON-RPC 的 `id` 与 `tool_calls.id` 是两套编号，不能混用。
3. 两道默认拒绝缺一不可：server 只执行声明过的工具，Host 按阶段白名单决定发不发请求。
4. 流程不能只写成提示词：十套正文会挤掉依据并互相干扰；写成目录后按三级加载，元数据常驻、正文命中才读、资料执行时才读。
5. 触发判定要分开报漏召与误召，用留出集量；四类能力的裁决顺序写进代码，事实以工具与检索为准，记忆只提供背景。
6. 收窄是 Host 拼清单时做的硬约束，先激活 Skill 再按它收窄；阶段内清单固定以保住缓存，权限与审批是两层，不能互相替代。
