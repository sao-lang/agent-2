## 一、嵌入是什么

检索要在问题与文档之间做匹配。最直接的做法是字符串匹配：问题里出现过的词，在文档里也出现，就算相关。第 14 章的 `pipeline.py` 用的就是这个思路的变体，它有一个无法绕过的边界：换个说法就匹配不上。东西坏了能退吗与质量问题退货怎么处理，两句话没有一个相同的字，字面匹配给出接近 0 的分数。

嵌入模型做的事是把这个一眼能看出变成可计算的东西：把一段文本映射成一个固定长度的实数向量，让语义相近的文本在空间里靠得近。这个映射由模型学出来，不是规则。

```python
from langchain_huggingface import HuggingFaceEmbeddings

emb = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    encode_kwargs={"normalize_embeddings": True},
)
v = emb.embed_query("退货运费由谁承担")
print(len(v), round(sum(x * x for x in v) ** 0.5, 3))
```

```
512 1.0
```

512 是维度，1.0 是向量的长度。两个数都不是质量指标：维度大不代表更准，长度为 1 是归一化的结果。要防止两个误解。第一，嵌入不是理解：它是把文本投影到一组坐标上，每个轴没有名字，问第 37 维代表什么没有答案。第二，相似度不是概率：0.89 只是两个单位向量夹角的余弦，同一个 0.89 在不同语料、不同模型上对应的判断可以完全不同。

### 1.1 这个映射是怎么学出来的

嵌入模型通常用对比学习训练：给一批同义句对与无关句对，让同义对的向量靠近、无关对的向量推开。训练目标里没有理解语义这一项，只有在这个语料上把该近的推近、该远的推远。这解释了三件事。脚本见 `code/knowledge/ch15_vectorize/`

第一是语料决定能力边界。一个在通用语料上训练的模型，遇到行业术语会把它们投影到相近的位置，因为训练时没人为这些词提供区分信号。第二，长尾词的表现差。罕见词、新词、内部代号在训练语料里出现次数少，向量基本由上下文猜出来。第三，模型换代必然改变坐标。重新训练一次，所有向量都变，旧的校准表与阈值一起作废。嵌入模型是有版本的依赖，与数据库 schema 同级，升级要按升级依赖的流程走：评估、双写、灰度、回滚预案。所以换个小模型试试在生产里不便宜，这不是换一行配置，是数据迁移。

### 1.2 向量里没有"字面"这个维度

一个常见的设计错误是：以为向量检索可以替代关键词检索，把编号、订单号、型号全交给稠密检索。向量里没有为精确匹配留出位置。模型把 A1001 与 A1002 编码成几乎相同的向量，因为它们在语料中出现的上下文几乎一样。脚本见 `code/knowledge/ch15_vectorize/`

这不是模型的缺陷，是表示方式的选择：稠密向量丢掉了字面信息，换来了语义泛化。需要字面精确的场景，要用保留字面信息的表示，或者两者一起用。第 18 章的混合检索就是这件事的标准做法。

### 1.3 什么时候值得换嵌入模型

换模型是全库重算加双索引加阈值重建，值得先看三个信号，脚本见 `code/knowledge/ch15_vectorize/`：

| 信号 | 说明 | 换模型有用吗 |
|---|---|---|
| 近义对与无关对的分数分不开 | 2.1 那三行里的第二、三种 | 有用，这是模型能力问题 |
| 召回差但重排能救 | 前 20 条里有对的，只是排得靠后 | 用处小，先上重排 |
| 术语、型号匹配不上 | 字面精确查询失败 | 没用，该上稀疏检索 |

第二行是最常见的误判：检索没找到与检索找到但排得靠后是两种病，前者要换模型或改切块，后者加一层重排就能解决，而重排便宜一个数量级。在换模型之前，先看候选集里有没有正确答案，有就不是模型的问题。

## 二、相似度矩阵

把六句话两两算余弦，得到一张对称的矩阵，这是观察嵌入行为最直接的方式，脚本见 `code/knowledge/ch15_vectorize/`：

```python
SENTENCES = [
    "退货运费由谁承担",
    "退货的运费谁出",
    "质量问题退货运费商家出",
    "发票多久能开",
    "签收后几天可以退货",
    "今天天气不错",
]

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0

vecs = emb.embed_documents(SENTENCES)
for i, vi in enumerate(vecs):
    print(f"  {i:<3}" + "".join(f"{cosine(vi, vj):>7.2f}" for vj in vecs))
```

```
=== 1. 相似度矩阵（bge-small，归一化后）===
          0      1      2      3      4      5
  0     1.00   0.89   0.69   0.43   0.54   0.23
  1     0.89   1.00   0.73   0.41   0.57   0.24
  2     0.69   0.73   1.00   0.40   0.55   0.38
  3     0.43   0.41   0.40   1.00   0.60   0.40
  4     0.54   0.57   0.55   0.60   1.00   0.39
  5     0.23   0.24   0.38   0.40   0.39   1.00
```

矩阵有三处值得读：

| 位置 | 值 | 说明 |
|---|---|---|
| 0 与 1 | 0.89 | 同义、换词序、换说法 |
| 0 与 3 | 0.43 | 只共享"退货""运费"这类词，主题不同 |
| 5 与其余 | 0.23–0.40 | 完全无关的句子，仍然不是 0 |

第三行是嵌入与字符串匹配最大的差别：无关文本的相似度不是零。在 512 维空间里任何两句话都有方向重合，中文短句的底噪通常在 0.2 到 0.4，所以分数低是相对概念，要不要判为不相关取决于同一批候选里的分差。

### 2.1 判断模型适配

同一张矩阵也是 C7 那个一个数的来源：取一批自有语料里的近义对与无关对，分别算余弦，看两组分布有没有分开。脚本见 `code/knowledge/ch15_vectorize/`

| 情况 | 近义对均值 | 无关对均值 | 判断 |
|---|---|---|---|
| 分得开 | 0.85 以上 | 0.35 以下 | 适配，阈值容易定 |
| 挨得近 | 0.75 | 0.55 | 阈值会很难调，考虑换模型或加领域语料 |
| 反过来 | 0.5 | 0.7 | 模型与语料不匹配，换模型 |

判据是两组之间有没有一条能放下的线：一个模型即使把近义对都算到 0.95，如果无关对也在 0.9，它就不能用来做区分。

### 2.2 矩阵还能看出什么

同一张矩阵，换几个角度看能回答别的问题，脚本见 `code/knowledge/ch15_vectorize/`：

| 看什么 | 说明什么 |
|---|---|
| 非对角的最小值 | 底噪有多高；底噪高则阈值难定 |
| 同义对与无关对的差 | 模型的区分力 |
| 某个块的"邻居" | 这条内容在库里有没有重复或近似重复 |
| 跨语言对 | 多语言模型的能力边界 |

一个块有一堆 0.95 以上的邻居，说明库里存在大量近似重复，检索会把它们全召回来占预算。这种语义重复用字符串去重查不出来。第四行只在多语言场景用：中文问题对英文文档的余弦如果普遍低于同语言，说明模型不支持跨语言检索，得换多语言模型或先翻译。

### 2.3 矩阵的规模是有上限的

六句话的矩阵是教学用的。真实库有几十万块，两两算一遍是 `n²` 次比较，不可行。实际做法是抽样：随机取几百块算矩阵；或者取一批已知近义的块对，只看这些对的分数。判断模型的区分力不需要全量矩阵。需要全量相似度时，用的是近邻索引，不是矩阵。脚本见 `code/knowledge/ch15_vectorize/`

## 三、归一化与距离

余弦只看夹角，不看长度；L2 距离两者都看。这就是归一化存在的理由：把向量长度压成 1，L2 与余弦就变成单调对应的关系，选哪个排序都一致。先看 bge-small 的实际输出，脚本见 `code/knowledge/ch15_vectorize/`：

```
=== 2. 归一化与距离度量 ===
  bge-small 未归一化输出：|a|=1.000  |b|=1.000
  bge-small 归一化输出：  |a|=1.000  |b|=1.000
  这个模型内部已经做了归一化，encode_kwargs 对它是个空操作——换模型时不能假定如此
```

两行完全一样，因为 bge 的输出层自带归一化。这个结果本身是个提醒：`normalize_embeddings=True` 不是开了才归一化，而是要求归一化，模型可能本来就归一化了。为了看清归一化到底改变什么，构造两个方向相同、长度不同的向量：

```
  为什么归一化必须与距离度量成对选（构造两个长度不同的向量）：
    短向量 |b|=1      余弦 0.900   L2 0.446
    长向量 |b|=3      余弦 0.900   L2 2.143
    两组的余弦完全相同，L2 差 1.70：用 L2 排序时，向量长度会冒充相关性
```

同一方向、不同长度，余弦一模一样，L2 差了三倍多。库里混着长度差异大的向量时，用 L2 排序等于按向量长度排序，而长度与相关性无关。三种距离策略与它们的适用条件：

| 策略 | 计算 | 什么时候对 |
|---|---|---|
| 余弦 | `1 - cos(a,b)` | 已归一化，或长度不代表信息 |
| 内积 | `-a·b` | 向量已归一化时与余弦等价；未归一化时长度会加权 |
| 欧氏 | `‖a-b‖` | 向量已归一化时与余弦单调对应；未归一化时会被长度带偏 |

结论可以压成一句：归一化加余弦，或者归一化加内积，是唯一不需要额外假设的组合。用欧氏时必须在写入前统一归一化，否则排序结果无法解释。第 17 章讲向量数据库时会再碰到 `distance_strategy` 这个参数，它就是在选这张表里的一行。

### 3.1 混合库是怎么出现的

同一个索引里出现两种口径的向量，通常是三种操作叠出来的，脚本见 `code/knowledge/ch15_vectorize/`：

| 操作 | 为什么会产生未归一化向量 |
|---|---|
| 换模型重建索引 | 新模型输出层没有内置归一化，而建库脚本沿用了旧参数 |
| 手工写入 | 有人用 `model.encode()` 直接写库，绕过了封装 |
| 部分重建 | 只重算了新增文档，旧文档的向量还是上一版的 |

第一种最隐蔽：`encode_kwargs` 是建库脚本里的一个参数，换模型时脚本其他部分都不用改，只有它的语义变了。第二种在多人协作时会反复发生，判断方式是抽样：随机取 100 条向量，看长度的标准差。第三种只在增量更新时出现，也最难发现：新写入的那批是好的，只有查询命中旧文档时排序会略偏。这类部分正确的故障只能靠全库统计发现。

### 3.2 距离策略写进索引

距离策略通常在建集合时确定，改策略意味着重建索引。三个后果要提前想到。一是策略与模型一起选：选定了归一化加余弦，模型就必须一直是归一化的，换一个不自带归一化的模型，要么在写入前补一次归一化，要么整体换策略。二是不同策略的分数不可比，跨集合拼结果时必须先统一换算。三是回滚要连索引一起回滚：切回旧模型时旧索引必须还在。脚本见 `code/knowledge/ch15_vectorize/`

### 3.3 归一化与零向量

归一化要除以长度，长度为零时除不了。零向量几乎不会出现，但在空文本与整块都是空白字符时会遇到。余弦的分母为 0，多数实现返回 0 或 NaN：前者让这块永远检索不到，后者污染整批排序。写入前做一次检查，长度为 0 的块直接跳过并记一条日志。脚本见 `code/knowledge/ch15_vectorize/`

## 四、读数与阈值

同一个意思的相似度，换个模型读数就变，脚本见 `code/knowledge/ch15_vectorize/`：

```
=== 3. 同一个问题，两个模型的读数 ===
  bge-small 维度 512，bge-base 维度 768
  句子对                              small    base
  退货运费由谁承担 / 退货的运费谁出               0.886   0.941
  退货运费由谁承担 / 质量问题退货运费商家            0.694   0.750
  退货运费由谁承担 / 发票多久能开                0.428   0.327
  退货运费由谁承担 / 今天天气不错                0.228   0.227
```

近义对从 0.886 变成 0.941，无关对从 0.428 掉到 0.327，差距变大了，这是更大模型容量带来的。但要注意：同一个 0.5 的阈值，在 small 上恰好卡在相关与无关之间，在 base 上会把一条 0.428 的相关文本判成无关。这带来一条工程约束：阈值是模型与语料的联合属性，不能跟着模型一起迁移。换嵌入模型时必须重建阈值，依据是第 13 章那套分桶校准。

嵌入升级的代价也在这里：换模型意味着全库重算向量，第 17 章讲索引重建时还会碰到它。重算期间新旧两套向量不能混用，可行做法是双写、双索引、按流量灰度切换。

### 4.1 阈值校准的最小做法

阈值重建不一定要一套完整的评测系统。最小的做法是三步：从线上抓 50 到 100 条真实查询，人工标出每条应该被哪一块回答；用新模型算每条查询与它对应块的余弦，得到一组正样本分数；再用同一批查询与随机块的余弦，得到一组负样本分数。脚本见 `code/knowledge/ch15_vectorize/`

两组分数一画，阈值就是两条分布之间的位置。如果两组几乎重叠，说明新模型在这个语料上分不开，换阈值没用，所以这一步的价值往往在提前发现模型不可用。样本量不用大，但要求分布对。

### 4.2 读数随语料漂移

同一句查询与同一块文档，在库扩充之后余弦会变，原因不是模型变了，是新文档改变了归一化的空间。这类漂移幅度小，单看一条看不出，但会累积到阈值上：三个月前定的 0.5，今天的通过率可能已经变了十几个百分点。对策不是阻止漂移，是定期重跑 4.1 那三步，并把每次的阈值与日期一起记下来。脚本见 `code/knowledge/ch15_vectorize/`

### 4.3 阈值与两个率的关系

一个阈值同时决定两个数：通过率是分数高于阈值的比例，错误率是通过部分里答错的比例。它们的关系与第 13 章路由的那张表同构，脚本见 `code/knowledge/ch15_vectorize/`：

| 阈值 | 通过率 | 通过部分的错误率 |
|---|---|---|
| 调低 | 上升 | 上升 |
| 调高 | 下降 | 下降 |

所以把阈值调到 0.7 这句话没有意义，除非同时说清它换来多少通过率、多少错误率。工程上更可操作的做法是固定一个错误率上限，在这个约束下求最高的阈值，这与第 13 章按答错代价与升级代价之比选阈值是同一件事。还有一个常被忽略的第三个数：阈值之下被丢弃的候选里，有多少本来是该用的。

## 五、维度与成本

维度决定存储、计算与不确定的质量。先算存储，一个 float32 向量占维度乘 4 字节，脚本见 `code/knowledge/ch15_vectorize/`：

| 规模 | 512 维 | 768 维 | 1024 维 |
|---|---|---|---|
| 10 万块 | 205 MB | 307 MB | 410 MB |
| 100 万块 | 2.0 GB | 3.1 GB | 4.1 GB |
| 1000 万块 | 20 GB | 31 GB | 41 GB |

再算计算量：暴力检索下比较次数与库大小成正比，每次比较是维度次乘加，1000 万块的 768 维一次全量比较是 76.8 亿次乘加，这就是大库必须上 ANN 索引的原因。量化能把存储压下来：float16 减半，int8 再减半，代价是精度损失，int8 量化后召回率通常下降 1 到 3 个百分点。

维度高不代表更好。 512 维的 bge-small 在中文短句上常与 768 维的 base 打平；把维度从 512 提到 1024，收益往往小于重排或混合检索带来的收益，而成本是线性的。榜单上的分数差距换算成业务指标经常小到看不见，而存储与延迟的差距立刻能感觉到。

### 5.1 重算一次要多久

换模型时最容易被低估的是重算时间，它由块数、单块编码耗时、并行度决定。按本机实测，bge-small 在批次 32 下的吞吐约 420 条每秒，100 万块的重算时间约 40 分钟；换成 bge-base，吞吐大约降到三分之一。脚本见 `code/knowledge/ch15_vectorize/`

| 块数 | small（约 420 条/秒） | base（约 140 条/秒） |
|---|---|---|
| 10 万 | 4 分钟 | 12 分钟 |
| 100 万 | 40 分钟 | 2 小时 |
| 1000 万 | 6.6 小时 | 20 小时 |

第二列与第三列的差距来自模型参数量，不是维度本身。选型时要把这张表与质量收益放在一起看：如果 base 只带来两个百分点的召回提升，而重算从 40 分钟变成 2 小时、存储从 2 GB 变成 3 GB，这笔账未必划算。重算期间系统不能停，还要一份新旧并存的方案：双索引、按文档 id 对比新旧结果、达标后切流量。

### 5.2 量化的空间与精度

float32 存 100 万块 512 维要 2 GB，改成 float16 是 1 GB，int8 是 0.5 GB。省下来的不只是磁盘：检索时要在内存里装下整个索引，内存装不下就要分片或落盘，延迟会翻倍。精度损失要用实测定：同一批查询用 float32 与 int8 各检索一次，比前 k 的召回差异。脚本见 `code/knowledge/ch15_vectorize/`

是否值得，取决于瓶颈在哪。如果瓶颈是内存容量，量化是唯一解；如果瓶颈是召回率，量化只会让它更差。

## 六、截断

嵌入模型有一个最大输入长度，bge 系列是 512 token。超过的部分不会被压缩，而是被直接丢掉，脚本见 `code/knowledge/ch15_vectorize/`：

```
=== 4. 截断：超出 max_seq_length 的部分不进入计算 ===
  bge 的 max_seq_length = 512 token
  原文              37 字     39 token  与查询余弦 0.769
  重复 2 遍          74 字     76 token  与查询余弦 0.768
  重复 12 遍        444 字    446 token  与查询余弦 0.767
  重复 40 遍       1480 字   1482 token  与查询余弦 0.771
```

第四行的 token 数是 1482，远超 512，但它与 39 token 的原文余弦几乎相同：进入模型计算的只有前 512 个 token，后面 970 个 token 里的内容一个都没参与。如果后半段写着真正的答案，这个答案对向量毫无贡献。截断有三种后果，按严重程度排：

| 后果 | 形态 | 发现难度 |
|---|---|---|
| 长块的后半段无关 | 向量由开头决定，检索命中率下降 | 中，召回率会掉但不明显 |
| 答案在块的后半段 | 检索不到这一块，答不出来 | 高，看起来像"知识库没有" |
| 截断发生在句子中间 | 向量来自半句话，语义偏移 | 高，且难以复现 |

第三种最隐蔽。切块时如果按字符数切，一个块可能在句子中间被切断，嵌入看到的是半个句子；而人看这个块时看不出它缺了一半。工程上有两个检查。第一，写入前检查 token 数，超过的块要么切小、要么在元数据里记一个 `truncated` 标记。第二，把块大小设在窗口的 60% 以内：512 token 的窗口对应约 500 字，块大小取 300 字左右，余量留给标题与元数据。

### 6.1 写入前的那次检查

检查的写法本身很轻：拿模型自己的 tokenizer 数一遍 token 数，与 `max_seq_length` 比，脚本见 `code/knowledge/ch15_vectorize/`：

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("BAAI/bge-small-zh-v1.5")
limit = tok.model_max_length

def check(chunks: list[str]) -> list[tuple[int, int, bool]]:
    out = []
    for i, text in enumerate(chunks):
        n = len(tok(text, truncation=False, add_special_tokens=True)["input_ids"])
        out.append((i, n, n > limit))
    return out
```

三个细节容易写错。第一，`truncation=False` 不能省，否则 tokenizer 会先截断再返回长度，检查永远通过。第二，`add_special_tokens=True`，特殊标记也占位置。第三，用模型自己的 tokenizer，不是别家的，同一个词在不同 tokenizer 下的 token 数可以差 30%。

超过上限的块分两种情况处理：内容确实长，切小；内容是表格或代码，切开就没意义，那就接受截断但把 `truncated` 写进元数据。

### 6.2 截断与切块

截断发生在嵌入之前，切块发生在更早。切块决定块有多长，截断决定这个长度有没有被浪费。切块偏大时，嵌入只看到前半段，后半段对检索没有贡献，但仍会进入上下文占预算。脚本见 `code/knowledge/ch15_vectorize/`

反过来，切块偏小时，一块只装半句话，嵌入看到的是一个不完整的语义单元，向量会偏向这个字出现了，而不是这段在说什么。两种偏差的方向相反，中间那个合适的区间由模型的窗口与文档的句子结构共同决定，这正好是第 16 章的主题。

## 七、稀疏与稠密

到目前为止讲的都是稠密向量：每个维度都有值，语义相近的靠得近。另一半是稀疏表示：维度等于词表大小，绝大多数位置是 0。两个都跑一遍，在同一批文档上对比，脚本见 `code/knowledge/ch15_vectorize/`：

```python
def tfidf_rank(query: str, ids: list[str], texts: list[str], k: int = 2):
    vec = TfidfVectorizer(analyzer="char", ngram_range=(1, 2))
    matrix = vec.fit_transform(texts + [query])
    scores = cosine_similarity(matrix[-1], matrix[:-1])[0]
    order = scores.argsort()[::-1][:k]
    return [(ids[i], round(float(scores[i]), 3)) for i in order]
```

```
  查询 'A1001 到哪了'
    TF-IDF d6=0.405  d4=0.062
    稠密   d6=0.648  d1=0.427
    前二重合 1 条

  查询 '东西坏了能退吗'
    TF-IDF d2=0.019  d1=0.018
    稠密   d1=0.583  d3=0.575
    前二重合 1 条

  查询 '多久能开发票'
    TF-IDF d4=0.164  d6=0.024
    稠密   d4=0.755  d3=0.514
    前二重合 1 条
```

第二组最能说明差别：查询里没有一个字出现在文档里，TF-IDF 给出的分数几乎全是噪声，而稠密给出了 0.583 与 0.575，两个都是相关文档。但稀疏也不是劣势。第一组里查询带编号 A1001，TF-IDF 把 d6 排第一，稠密也排第一，但它同时把退货运费那条文档拉到 0.427：编号这种精确标识，稠密模型没有可靠的处理机制。

| 维度 | 稀疏（TF-IDF / BM25） | 稠密（嵌入） |
|---|---|---|
| 换说法 | 失效 | 有效 |
| 精确词、编号、型号 | 强 | 弱 |
| 存储 | 与词表大小相关，通常比稠密小 | 每块固定 2–4 KB |
| 增量更新 | 加文档即可，无需重算旧向量 | 新模型要全库重算 |
| 可解释性 | 命中哪些词一目了然 | 无法解释某个维度 |

两者互补是第 18 章混合检索的全部理由。这里只需要记住一件事：用向量检索不等于向量能解决所有匹配。编号、型号、精确数字这类内容，稀疏或结构化过滤往往更可靠。

### 7.1 稀疏侧的实现细节

上面用的是 TF-IDF，生产里更常见的是 BM25。两者都在词频乘逆文档频率这条思路上，差别在饱和与长度归一化：TF-IDF 的词频是线性的，BM25 有饱和。结果上，BM25 更不容易被长文档刷分。脚本见 `code/knowledge/ch15_vectorize/`

中文还有一步分词。TF-IDF 与 BM25 都按词统计，而中文没有空格，所以要么先分词，要么用字符 n-gram。示例里用的是字符 1 到 2 gram，它不需要词典、不会切错词，代价是词表大、语义粒度粗。两种切法各有失效：分词切错会让这个词彻底匹配不上；字符 n-gram 则会把退货与货退当成不同的东西。分词错误在中文检索里是最常见的静默失败。

### 7.2 什么时候干脆不用向量

有一类需求看起来是检索，实际上不该用相似度：给一个订单号，取回它的状态。它的答案唯一确定，字面精确匹配就够，向量反而引入不确定性。判断标准是这个问题有没有唯一正确答案，而不是数据是不是文本。有，就用结构化查询或精确匹配；没有，才需要相似度。脚本见 `code/knowledge/ch15_vectorize/`

### 7.3 更新成本也不一样

稀疏索引在增量更新上是便宜的：新文档进来，算它的词频、加进倒排表，旧文档不动。稠密索引则要看情况，同一模型下加一条新文档也只需编码它自己，但如果换模型，全库都要重算。这个差别在多租户或高频更新的场景里会放大。脚本见 `code/knowledge/ch15_vectorize/`

两种索引可以共存：稀疏负责新文档立刻可查与精确匹配，稠密负责语义召回，查询时合并两路结果。这就是混合检索的雏形，第 18 章会给出融合公式与实测对比。

## 八、批量与缓存

编码是一个可以批处理的运算，但批次大小要自己设，脚本见 `code/knowledge/ch15_vectorize/`：

```
=== 1. 批次大小（encode_kwargs['batch_size']）===
  batch_size    耗时(ms)       条/秒
           1       608      98.7
           8       180     333.4
          32       142     422.1
          64       135     443.2
```

从 1 到 8 吞吐翻了 3.4 倍，从 32 到 64 只多 5%。原因是单条编码时并行度用不满，批次到一定大小后计算成为瓶颈。这条曲线的形状决定了两个工程选择。建索引时用大批次，一次编码几万块。在线查询时批次永远是 1，因为一次只来一个问题：

```
=== 2. 单条查询的固定开销 ===
  同一句查询连续两次：9.3 ms / 10.3 ms
  编码本身的成本远小于一次模型调用的网络往返，所以在线查询阶段的瓶颈通常不在编码
```

9 毫秒的编码，与一次模型调用动辄几百毫秒到几秒相比可以忽略。缓存能省下的也是建索引那一侧：

```
=== 3. 重复编码的浪费 ===
  20 条算两遍：106 ms
  20 条算一遍 + 查缓存：50 ms
  只查缓存：0.00 ms
```

文档向量在库里只该算一次。重复编码发生在三个地方：重建索引时必须重算、多实例各自预热、以及把同一批文档写进两个库。前两个靠共享缓存或流水线设计解决，第三个只能靠算一次、写两处。

### 8.1 建索引的流水线

一次完整的建索引有五个阶段，失败的代价各不相同，脚本见 `code/knowledge/ch15_vectorize/`：

| 阶段 | 做什么 | 失败后的处理 |
|---|---|---|
| 读取 | 从源拉文档、解析格式 | 重试，单文档跳过并记录 |
| 切块 | 切成可检索的块 | 纯函数，失败说明有异常输入 |
| 编码 | 块 → 向量 | 最贵的一步，要断点续跑 |
| 写入 | 向量 + 元数据进库 | 按批提交，记录成功批次 |
| 校验 | 抽查召回与长度分布 | 只读，失败则整体回滚 |

第三行的断点续跑是重点：编码 100 万块要几十分钟，中途失败从头再来就是几十分钟。可行的做法是按批记录进度，重启时从最后一个成功批次继续。第五行的校验常被省略，但它是唯一能发现索引建好了内容不对的环节：随机取十块查询看能否召回、统计块长度分布、统计向量长度分布。

### 8.2 一次重建的预算

把 5.1 的耗时表、8.1 的流水线、存储放在一起，一次全量重建的成本可以估出来，脚本见 `code/knowledge/ch15_vectorize/`：

| 项 | 100 万块、512 维 | 说明 |
|---|---|---|
| 读取与切块 | 十几分钟 | 取决于源文档格式 |
| 编码 | 约 40 分钟 | 批次 32，约 420 条/秒 |
| 写入 | 十几分钟 | 取决于库的写入吞吐 |
| 校验 | 几分钟 | 抽样查询与分布统计 |
| 存储 | 约 2 GB | float32；量化后减半 |

加起来一个多小时。这个数字的意义在于：它决定了换模型这类改动的上线节奏。一个小时的窗口可以放在夜间；二十个小时的窗口就必须分批、双写、灰度，不能一次性做。预算里没有列回滚，回滚的成本是双份存储与双份写入，通常按 2 倍估。

灰度期间两套索引同时在线，查询走哪一套由流量比例决定。这时需要一个开关而不是改代码：索引版本要么是查询参数的一部分，要么是服务配置的一部分，不能硬编码在检索函数里。

## 九、LangChain 侧的三个参数

框架侧只有三个参数要认，其他都是这三个的组合，脚本见 `code/knowledge/ch15_vectorize/`：

| 参数 | 管什么 | 本章的实测依据 |
|---|---|---|
| `model_name` | 用哪个模型、多少维 | 512 vs 768，读数差 0.05–0.10 |
| `encode_kwargs={"normalize_embeddings": True}` | 是否归一化，以及批次 | 归一化决定 L2 与余弦是否一致 |
| `distance_strategy`（在向量库里） | 用哪种距离 | 与归一化必须成对选 |

```python
emb = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    encode_kwargs={"normalize_embeddings": True, "batch_size": 32},
)
```

### 9.1 两个方法不是同义词

`embed_query` 与 `embed_documents` 看着只是一个对一个、一个对多个，实际可能走不同的预处理。bge 1.0 系列要求给查询加一段指令前缀，文档不加；从 1.5 起不再强制。实测这个差别有多大，脚本见 `code/knowledge/ch15_vectorize/`：

```
doc 无前缀 1.0
doc 有前缀 0.898
另一句无前缀 0.428
另一句有前缀 0.377
```

同一句文本，加不加前缀的余弦从 1.000 掉到 0.898：这不是相似度下降，是同一句话被编码成了两个向量。如果建库时给文档加了前缀、查询时没加，全库的相似度会整体偏移。所以有一条硬规定：建库与查询必须用同一套预处理，且这条规定要写进建库脚本里。

### 9.2 三类典型写错

| 写错的地方 | 表现 | 怎么发现 |
|---|---|---|
| 建库用 `embed_documents`，查询用别的模型 | 全库相似度整体偏低 | 换回同一模型后指标跳变 |
| 一边加了指令前缀、一边没加 | 同义句的余弦掉到 0.9 以下 | 取同一句话分别用两个方法编码，比对余弦 |
| 建库时归一化、查询时归一化 | 两种组合的一致性 | 用余弦与内积各查一次，看排序是否相同 |

第三行的检查值得单独说：同一批数据用余弦与内积各查一次，如果排序不一致，说明向量没有归一化，因为归一化之后两者是单调等价的。这是一个不用看代码就能判断的实现级检查。

这类检查只用系统自己产出的东西做交叉验证。嵌入系统里最容易出的错都在这一层：模型、归一化、距离三者不一致，指标缓慢下滑，日志里没有异常。三个交叉检查不到二十行代码，却能把这类问题挡在索引建立之前。

### 9.3 为什么接口要分成两个方法

如果只是一个对一个、一个对多个，一个方法加个分支就够。分成两个的真实原因是非对称检索：有些模型要求查询与文档走不同的预处理路径，这个差异必须由调用方通过用哪个方法来表达，而不是由模型猜。这也是为什么把 `embed_query` 写成 `embed_documents([q])[0]` 是个隐患：此刻恰好等价，换一个需要指令前缀的模型就不等价了，而错误不会报出来。脚本见 `code/knowledge/ch15_vectorize/`

### 9.4 一份可直接抄的配置

把本章的结论收成一份配置，注释写清每条对应哪条结论，脚本见 `code/knowledge/ch15_vectorize/`：

```python
emb = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",       # 512 维，中文短文本够用
    encode_kwargs={
        "normalize_embeddings": True,          # 与 distance_strategy="cosine" 成对
        "batch_size": 32,                      # 只影响建索引吞吐
    },
)
```

配置写完后还要记下这份配置的版本：模型名、归一化开关改变结果，批次大小不影响，把三者都记进去是为了让下次对比有的放矢。

### 6.3 长文档的两种处理

超过窗口的文档不只有切小一条路。另一条是先摘要再嵌入：用模型把长文压成一段摘要，嵌入摘要，检索命中后把原文放进上下文。两种做法的取舍很明确，脚本见 `code/knowledge/ch15_vectorize/`：

| 做法 | 优点 | 代价 |
|---|---|---|
| 切小块 | 保留原文，引用精确 | 一块信息量小，同一文档块数多 |
| 摘要后嵌入 | 块少、语义完整 | 摘要可能丢关键细节，引用只能指到文档级 |

摘要那条路的风险在丢了什么：它可能把退货期限 7 天、生鲜除外压成 7 天无理由退货。所以摘要不能替代原文进入上下文，只能替代入索引的向量。

### 9.5 结论落到参数

| 主线结论 | 落到的参数 |
|---|---|
| 归一化与距离必须成对选 | `encode_kwargs={"normalize_embeddings": True}` + 向量库的 `distance_strategy="cosine"` |
| 阈值不能跨模型迁移 | 换 `model_name` 时必须重建校准表 |
| 批次只影响建索引 | `encode_kwargs={"batch_size": 32}`，在线路径不用管 |

## 十、边界

第 13 章讲过阈值怎么定，第 14 章讲过四环的分工，第 16 章讲切块。边界有八条。

嵌入不解决精确匹配。编号、型号、日期这类内容，稀疏检索或结构化过滤更可靠。模型不是越大越好，512 维与 768 维在很多任务上差距小于一次重排带来的收益，而成本是线性的。归一化不是可选项，除非确定库里的向量长度都一致且长度有语义，否则统一归一化，混着用往往在换模型那天才爆发。截断是静默的，没有任何报错。

嵌入的质量与适配是两件事。榜单上很强的模型，可能在这批语料上把无关文本算得很近，判断依据是第二节那张矩阵。距离策略与归一化是一对约束，只改一边排序就会静默地变差。不要用嵌入取代精确查询：订单状态、库存数量这类问题，结构化查询更准更快。

索引的新鲜度要能查。一个块从源文档更新到能被检索到，中间隔着读取、切块、编码、写入四步，任意一步卡住就会返回旧内容。给每条记录带上 `indexed_at` 与源文档的 `updated_at`，就能查出有多少块的索引落后于源文档。

## 这一章建立的 6 件事

1. 嵌入把文本映射成固定维度的坐标，相似度是几何量不是概率；无关文本的底噪在 0.2–0.4，阈值要靠分差或校准而不是绝对值。
2. 归一化把 L2 与余弦对齐；未归一化时用 L2 排序等于按向量长度排序。归一化加余弦（或内积）是唯一不需要额外假设的组合。
3. 同一个意思的相似度在不同模型上差 0.05–0.10，所以阈值不能跨模型沿用；换模型要全库重算并重建校准表。
4. 维度决定存储与计算成本，与质量不严格正相关：100 万块 512 维约 2 GB，768 维约 3 GB。
5. 截断是静默的：超出 `max_seq_length` 的内容不参与计算，写入前检查 token 数是唯一低成本防线。
6. 稀疏与稠密互补；批次大小只影响建索引吞吐，在线查询的单条编码在毫秒级，通常不是瓶颈。
