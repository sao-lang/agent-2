## 一、三种依据强度

第 1 章说过，一次调用产出的是文本。这一章问的是这段文本从哪来。有三种情况，输出看起来没有区别，运行 `code/knowledge/ch02_generation/evidence_strength.py`：

看不出区别的原因在接口形状上：响应里只有文本，没有任何字段说明来源。模型收到的只是前文里的文字，输出的也只是文字，中间没有这条来自哪份资料的标注。要判断依据，只能在请求里安排来源，或者在响应之后补上核对。

```python
def answer_with_docs(question: str, docs: dict[str, str]) -> Answer:
    """有直接依据：资料里就有答案。"""
    if "退货期限" in docs:
        return Answer(docs["退货期限"], "strong", "退货期限")
    return answer_without_docs(question)


def answer_with_partial(question: str, docs: dict[str, str]) -> Answer:
    """弱依据：资料相关，但没写具体数值。"""
    related = [v for k, v in docs.items() if "退" in k or "退" in v]
    if related:
        return Answer(f"{related[0]}（具体天数需要确认）", "weak", "部分相关")
    return answer_without_docs(question)


def answer_without_docs(question: str) -> Answer:
    """无依据：资料里没有，只能靠训练时见过的东西拼。"""
    return Answer("商品签收后 7 天内可申请退货，通常需保持商品完好并保留发票。", "none", None)
```

它的输出：

```
问题：退货期限是多久？
可信资料：商品签收后 7 天内可申请退货，需保持商品完好。

=== 有依据 ===
  回答：商品签收后 7 天内可申请退货，需保持商品完好。
  依据强度：strong
  来源：退货期限

=== 弱依据 ===
  回答：本店支持退货（具体天数需要确认）
  依据强度：weak
  来源：部分相关

=== 无依据 ===
  回答：商品签收后 7 天内可申请退货，通常需保持商品完好并保留发票。
  依据强度：none
  来源：None

三种情况下的差别：
  有依据：答案的字面来自资料，可以逐字核对。
  弱依据：资料只说了存在性，数值是补上去的，无法核对。
  无依据：没有任何来源，但输出形式和有依据时完全一样。

关键：三种情况的输出格式没有区别，
      只能靠调用方记录来源，事后才分得清。
```

原理演示，不是模型实测。三种情况的关键差别：

| 情况 | 答案内容 | 能否核对 |
|---|---|---|
| 有依据 | 逐字来自资料 | 能，拿资料比对 |
| 弱依据 | 资料给了框架，数值是补的 | 不能，资料里没这个数 |
| 无依据 | 全部来自训练时见过的东西 | 不能，没有可比对的来源 |

最需要注意的不是无依据那一种，是弱依据。无依据时输出往往泛泛而谈，容易看出不对；弱依据时输出格式正确、语气确定、细节具体，只是那个具体数值没有任何来源。第三段输出就是个例子：`7 天内` 这四个字资料里根本没有，它出现在那里，是因为这个数字在训练语料里出现过太多次。

依据强度说的是能不能核对，不是对不对。资料本身也可能过期、写错、与另一份资料冲突：有依据的输出照样可能是错的，只是错能定位到某一句话；无依据的输出错了，连定位的入口都没有。三种强度往往同时存在，一段回答里退货期限来自资料、运费规则是补的、行业常识来自语料，所以判断依据得按句子里的事实点逐个过。

### 1.1 为什么不会说不知道

要让"我不知道"成为能给出的答案，需要它在那个位置上的概率足够高，而生成过程里没有"先判断自己知不知道"这一步。位置一旦出现就必须填一个 token，前文里没有相关信息时，概率最高的往往不是一个不确定的说法，是一个语义通顺、形式上合理的填充。原因在训练数据：真实文本里"退货期限是 X 天"这种完整陈述的出现次数，远多于"关于退货期限，我无法确定"。

所以沉默和拒答是训练数据里的少数派，模型不是倾向于编，是倾向于填满。推论是：想让输出拒答，必须在提示词里明确允许，并给出拒答的表达方式。光写不确定就说不知道通常不够，因为那个说法的具体形式不由调用方决定，第 4 章会给出可用的写法。表达方式还决定了它好不好用：直接说资料里没有这条信息最干净，给出最接近的信息并标注范围信息量大，转给人工要看有没有通道。

### 1.2 三种依据强度的判断方法

不做任何处理时，三种情况在输出里分不出来，要做到能分只有三条路。第一条是要求引用原文：每个结论后面附上资料里的原句，能附上的是可以核对的。它只能发现无依据，发现不了弱依据，因为模型能找到一句相关原文附上，而那个具体数字仍然不是从这句原文里来的。

第二条是代码比对：输出里的关键值逐个在输入资料里查找。它只对可精确匹配的内容有效，同义改写的句子比对不上，会产生误报。第三条是外部判据，用测试、规则或另一个模型来判定，反思与外部裁判一章会展开。三条路各有代价，共同点是不能只靠声明：输出里说自己有依据，这件事本身也需要验证。

还有一件比三条路都靠前的事：资料与问题不匹配时，补资料不等于有依据。问题问的是退货期限，资料里给的是运费规则，模型会挑一句最像的资料贴上来，输出有引用有出处，结论却与问题无关。判断方法在检索那一侧：看召回的文档与问题是否真相关，检索质量一章讲怎么评。

## 二、文本的产生过程

要理解为什么会产生没有来源的细节，需要知道生成过程。生成是一个循环，每一步做同一件事：根据已有的全部内容算下一个 token 的概率分布，取一个放进去，再算下一步（示意）：

```
已有的内容  ──▶ 算下一个 token 的分布 ──▶ 取一个 ──▶ 追加
     ▲                                                    │
     └────────────────────────────────────────────────────┘
```

这个过程中有三个事实，直接决定了输出的性质。

### 2.1 每一步只看概率

每一步的输出是"给定前文，下一个位置最可能出现什么"。这里没有"这条信息我有没有"这个概念，也没有"该不该说"这个判断，前文里没有的信息，位置上照样需要填一个 token，于是填一个出现频率高的。这是无依据内容的第一层原因：位置必须填满，输出里没有办法表达"这条我没有"，除非提示词给了表达方式（1.1 节），或者外部判据拦住（1.2 节第三条）。

顺带把一个数量关系说清：一次回答有多少个 token，就有多少次采样。第 1 章那份响应里 `completion_tokens` 是 9，那段话就经过了 9 次取候选，一段两百字的回答就是两百多次。所以结果不稳定不是一次抽签的结果，是几百次抽签连起来的结果，这也是 3.5 节那个连乘关系的由来：短回答的稳定性很高，长回答几乎不可能完全一致。

### 2.2 前文对后文的影响

一旦生成了"7 天内"这个片段，它就进入了前文，下一步的分布更容易延续与它一致的内容。这解释了为什么错误往往成片出现：第一个错的地方落定之后，后面会顺着它继续往下写，而且越写越具体。这也是排查的信号：一段输出里只有一个孤立的可疑数字时，位置通常靠前；整段都在围绕一个错误前提展开时，错误的位置在那段开头。

顺着这个信号排查，顺序是反的：先从这段输出的第一个具体值查起，确认它有没有依据。它如果是编的，后面整段都不必逐个核对；它如果有据，再往后一句一句看。在有依据的输入上加逐句核对，收益远小于先定位第一个分叉点。

### 2.3 依据强度的来源

同一句话，给不给资料，产出的可靠性完全不同，而"给不给资料"是调用方决定的。

| 输入里有什么 | 输出的依据强度 |
|---|---|
| 资料中直接写明 | 强：可以逐字核对 |
| 资料相关但缺关键信息 | 弱：框架来自资料，细节是补的 |
| 没有任何资料 | 无：全靠训练语料 |

怎么让它少编，第一层答案不在提示词里，在输入里：把该给的资料给进去。给不进去时，第二层答案才是允许它说不知道。对照表里的三种强度，在代码里对应的正是三种处理：直接使用、标注待确认、拒答。第三种必须有对应的分支，因为它的输出格式和前两种完全一样，这正是第 1 章说过的那类问题：不同情况被压成同一个返回值。

### 2.3.1 多轮里的依据衰减

单轮里依据强度由"给没给资料"决定，多轮里还有第二层：上一轮给的资料，这一轮还在不在。历史会随轮数增长，而窗口有上限（第 3 章讲），常见处理是把早期消息裁掉，或者只保留摘要，两件事都会让"资料还在、但已经不在这次请求里"发生，症状和"模型忘了"完全一样：上一轮明确说过的退货期限，这一轮变成了"通常七天左右"。判断方法还是下一节那条，区别在于多轮时看的是放进去的资料有没有被裁掉，问题在于依据强度降级了而回答的语气没有降级。

### 2.4 四种被当成忘的情形

章节标题里有"忘"，需要先澄清这个词。模型不会忘：它没有状态、没有记忆、没有上一次请求的任何痕迹。所谓"忘"，是调用方没有把内容放进这次请求。这个区别不是措辞问题，它决定了修复方向。

| 如果理解成"忘" | 如果理解成"内容没传进去" |
|---|---|
| 想办法增强记忆 | 检查这次请求里带了什么 |
| 换更长的窗口 | 检查窗口里放的是不是该放的 |
| 在提示词里说"记住前面说过的" | 把前面说过的内容重新放进去 |

第三列那种做法是无效的：让输出记住它从未收到的内容，和让它编造没有区别。真正会发生的情形是这几种：历史被裁剪掉了，为了省 token 前几轮被删；检索结果没有命中，这次没检索出来，检索质量一章讲怎么定位；任务在另一个会话里，之前的状态不在这次请求里，持久化一章会处理；同一轮里前面的工具结果没有回灌，第 1 章说过 `tool_calls` 返回的是动作。

四种情形里只有第一种和"忘"有点像，其余三种都是代码问题。把它们都归成记性不好，会导致去调提示词，而真实原因在别处。第一种还有一个变体：历史没有被删，而是被换成了摘要。把前几轮压缩成一句概述，看起来内容还在，实际上具体数值、限定条件、例外条款都在压缩时丢了。这种失效比直接裁剪更难发现，因为 `messages` 里确实有一条看起来相关的记录，前面那条排查线索不会响。判断方法不是数条数，是把这一轮要用的期限、条件、例外逐个在 `messages` 里搜一遍。

把这次请求的完整 `messages` 打印出来，内容在里面说明问题在生成，不在里面说明问题在装配。`code/knowledge/ch02_generation/dump_messages.py` 就是这一步：

```python
def dump_messages(messages: list[dict]) -> None:
    """排查"忘"的第一步：这次请求里到底有什么。"""
    print(f"共 {len(messages)} 条消息")
    for i, m in enumerate(messages):
        content = m.get("content") or ""
        role = m.get("role")
        print(f"[{i}] {role:<9} {len(content):>6} 字  {content[:40]!r}...")

        if m.get("tool_calls"):
            print(f"      tool_calls: {[t['function']['name'] for t in m['tool_calls']]}")
        if role == "tool":
            print(f"      tool_call_id: {m.get('tool_call_id')}")
```

```

[0] system        19 字  '你是退货客服，只回答与退货相关的问题。'...

      tool_calls: ['get_order']

      tool_call_id: call_abc

=== 工具结果没回灌 ===

```

两组的差别只有一条消息，后果很具体：第二组的请求里，最后一次工具调用的结果根本不存在。这段输出把"忘"从一句感觉变成了一个可数的差别。四条排查线索，各对应一种情形：

| 看到什么 | 说明 |
|---|---|
| 消息条数比预期少 | 历史被裁剪，属于情形一 |
| 只有 user 和 assistant，没有 tool | 工具结果没有回灌，属于情形四 |
| 检索文档条数为 0 | 召回失败，属于情形二 |
| 整段历史都在，但还是答错 | 才轮到怀疑生成 |

最后一行是重点：只有排除掉前三种情形，才值得去调提示词，否则改的是提示词，坏的是装配。

## 三、同一输入的结果差异

第 1 章的 `finish_reason` 处理的是这段文本能不能直接用，这一节处理另一个问题：为什么同样的输入跑两次，文本不一样。

原因是采样，但在讲采样之前，要先说清被采样的那个东西从哪来。分布由模型的权重决定：给定前文，模型算出词表里每个 token 的分数，归一化成概率，这一步没有随机性；随机性只出现在下一步，从这组数字里取哪一个。分清这两步决定了改什么能改掉什么：温度、`top_p` 影响取样那一步，资料、提示词、历史影响算分那一步。所以调温度改不了内容有没有依据，3.7 节会把这一点讲透。

下面按取样那一步展开，代码在 `code/knowledge/ch02_generation/temperature.py`。每一步算出一个分布，比如某个位置有五个候选：

```python
CANDIDATES = ["7天", "7日", "一周", "七天", "3天"]
PROBS = [0.50, 0.22, 0.15, 0.10, 0.03]


def apply_temperature(probs: list[float], temperature: float) -> list[float]:
    """温度 <1 时分布更尖，>1 时更平。返回归一化后的概率。"""
    if temperature <= 0:
        # 温度 0 等价于取最大概率的那一个（贪心）
        idx = max(range(len(probs)), key=lambda i: probs[i])
        return [1.0 if i == idx else 0.0 for i in range(len(probs))]

    scaled = [p ** (1.0 / temperature) for p in probs]
    total = sum(scaled)
    return [s / total for s in scaled]


def sample(probs: list[float], rng: random.Random) -> int:
    """按累积概率取一个下标。"""
    r = rng.random()
    acc = 0.0
    for i, p in enumerate(probs):
        acc += p
        if r < acc:
            return i
    return len(probs) - 1
```

`temperature=0` 那一支直接把最大值设为 1、其余设为 0，所以每次取到同一个候选；其余三支先按 $p^{1/T}$ 缩放再归一化，这就是温度改的是分布形状这句话的实现。用这个分布，四种温度各取样 200 次：

```
原始分布：
  7天     0.50
  7日     0.22
  一周     0.15
  七天     0.10
  3天     0.03

=== temperature = 0.0 ===
  调整后分布  7天:1.00  7日:0.00  一周:0.00  七天:0.00  3天:0.00
  200 次取样  {'7天': 200}
  最高频结果  7天 出现 200/200 次

=== temperature = 0.7 ===
  调整后分布  7天:0.62  7日:0.19  一周:0.11  七天:0.06  3天:0.01
  200 次取样  {'7日': 35, '7天': 128, '一周': 22, '七天': 10, '3天': 5}
  最高频结果  7天 出现 128/200 次

=== temperature = 1.0 ===
  调整后分布  7天:0.50  7日:0.22  一周:0.15  七天:0.10  3天:0.03
  200 次取样  {'7日': 43, '7天': 103, '一周': 27, '七天': 19, '3天': 8}
  最高频结果  7天 出现 103/200 次

=== temperature = 1.5 ===
  调整后分布  7天:0.40  7日:0.23  一周:0.18  七天:0.14  3天:0.06
  200 次取样  {'一周': 31, '7天': 85, '七天': 29, '7日': 43, '3天': 12}
  最高频结果  7天 出现 85/200 次

同一输入、同一分布，温度不同，结果的分散程度不同：
  温度 0    最高频结果占 200/200
  温度 1.5  最高频结果占 85/200

温度 0 时每次结果相同，温度的升高让低概率候选出现的机会变大。
对需要解析字段的输出，这是不稳定来源之一。
```

原理演示，不是模型实测。四段对照说明三件事。温度 0 时结果完全确定，200 次取样全是同一个候选，这是取概率最高的那个，不是取消随机性。温度升高，低概率候选出现的机会变大：`3天` 只占 3%，200 次里出现了 12 次，足以让一部分请求得到完全不同的答案。最高频结果的占比持续下降，200 → 128 → 103 → 85，直接对应同一输入多跑几次结果不同的程度。

### 3.1 温度改的是分布形状

温度不是"随机性开关"，它改变的是分布的形状：

| 温度 | 分布形状 | 效果 |
|---|---|---|
| 0 | 只有一个候选概率为 1 | 每次相同 |
| < 1 | 更尖，高概率的更高 | 更稳定，但仍有变化 |
| = 1 | 保持原始分布 | 按模型本来的倾向 |
| > 1 | 更平，低概率的被抬高 | 更多样，也更容易跑偏 |

`top_p` 是另一种方式：不改变分布形状，是把累积概率超过 `top_p` 之后的候选直接排除。两者都能控制多样性，作用点不同：温度改相对高低，`top_p` 改候选数量。区别在候选分布不均匀时才明显，假设某个位置的分布是：

```python
CANDIDATES = ["A", "B", "C", "D", "E"]
PROBS = [0.60, 0.25, 0.08, 0.05, 0.02]


def apply_top_p(probs: list[float], p: float) -> list[float]:
    """按概率从高到低保留，直到累积超过 p，其余置零后重新归一化。"""
    order = sorted(range(len(probs)), key=lambda k: -probs[k])
    kept, acc = [], 0.0
    for i in order:
        kept.append(i)
        acc += probs[i]
        if acc >= p:
            break
    out = [0.0] * len(probs)
    for i in kept:
        out[i] = probs[i]
    tot = sum(out)
    return [x / tot if tot else 0.0 for x in out]
```

关键在 `break`：累积概率一旦超过 `p` 就停止保留，剩下的候选被直接置零，不是降低概率。温度会对所有候选做幂运算，一个都不会丢。`code/knowledge/ch02_generation/top_p.py` 把两个函数作用于同一分布：

```
原始分布： A:0.60  B:0.25  C:0.08  D:0.05  E:0.02

温度改变相对高低（所有候选都保留）：
  temperature=0.5
    分布  A:0.83  B:0.14  C:0.01  D:0.01  E:0.00
    300 次 {'A': 251, 'B': 42, 'C': 7}

  temperature=1.5
    分布  A:0.47  B:0.26  C:0.12  D:0.09  E:0.05
    300 次 {'A': 146, 'B': 75, 'C': 36, 'D': 29, 'E': 14}

top_p 改变候选集合（低概率直接消失）：
  top_p=0.90
    分布  A:0.65  B:0.27  C:0.09  D:0.00  E:0.00
    300 次 {'A': 198, 'B': 78, 'C': 24}

  top_p=0.95
    分布  A:0.61  B:0.26  C:0.08  D:0.05  E:0.00
    300 次 {'A': 191, 'B': 68, 'C': 26, 'D': 15}

差别：
  温度 1.5：E 的概率从 0.02 变成 0.05（还在）
  top_p=0.90：E 的概率变成 0.00（被排除）

温度做的是缩放，top_p 做的是裁剪。
要保留多样性但不想出现冷门候选，用 top_p；
要整体降低或提高随机程度，用温度。
```

| | 温度 | top_p |
|---|---|---|
| 作用对象 | 所有候选的相对高低 | 参与取样的候选集合 |
| 低概率候选 | 概率上升，仍可能出现 | 超过累积阈值直接排除 |
| 结果 | 分布更平或更尖 | 候选更少 |
| 极端取值 | 0 = 只取最高；很大 = 接近均匀 | 0 = 只取最高；1 = 不裁剪 |

温度做的是缩放，`top_p` 做的是裁剪：温度允许冷门候选出现，只是概率变了；`top_p` 让冷门候选彻底没有机会。选择依据：

| 想达到的效果 | 用哪个 |
|---|---|
| 整体上更稳或更随机 | 温度 |
| 保证某些低概率输出永不出现 | `top_p` |
| 输出需要解析，不容许同义替换 | 两者都收紧 |

常见组合是低温配高 `top_p`，或者干脆用 `temperature=0`。

还有一点与成本有关：温度和 `top_p` 不改变 token 数量，所以调低温度省不了钱；反过来，调低温度会减少输出不合格要重跑的次数。把采样参数当成成本手段是找错了地方，成本在窗口与输出长度上（第 3 章）。

### 3.2 参数进了请求体

上面两节算的是分布在取样阶段怎么变，还有一个更前置的问题值得确认：这些参数是不是真的被发出去了。`code/knowledge/ch02_generation/sampling_params.py` 用真实的 `openai` 客户端在三种温度下各发一次请求，把脚本化后端收到的请求体交回来对照：

```python

    return client.chat.completions.create(

        messages=[{"role": "user", "content": QUESTION}],
        temperature=temperature,
        top_p=0.9,

```

这段输出要读准它的边界：它证明的是参数原样进了请求体，不是参数改变了输出。三档的响应内容完全相同，因为脚本化后端不采样，只回放固定文本。

它仍然有价值，因为参数是不是真的发出去了是另一类常见的失效：拼错名字、被封装层丢掉、被服务商忽略，都不会报错，症状都是调了没反应。判断方法是看请求体：请求体里有、效果没变，问题在服务端或模型；请求体里没有，问题在调用方。参数被丢掉的常见场景有三种：

| 场景 | 症状 | 判据 |
|---|---|---|
| 中间封装层只暴露部分参数 | 代码里传了，请求体里没有 | 抓请求体，字段缺席 |
| 配置文件覆盖了代码里的默认值 | 改代码没生效，改配置才生效 | 请求体里的值与代码里的不一样 |
| 网关或代理裁剪不认识的字段 | 直连正常，走网关失效 | 绕开网关发一次对比 |

三种的共同点是都没有报错。参数是可选的，服务端不会因为少一个 `temperature` 就拒绝请求，它会用默认值。所以发现方式只有一种：把请求体打出来，逐字段对一次。顺带说明 `stop` 与 `logprobs`：它们和采样参数在同一层，都改变请求的行为，`stop` 让生成在命中指定字符串时停下（第 1 章讲过它会带来一个 `stop` 取值），`logprobs` 要求服务端把候选分布带回来。

### 3.3 候选分布的形状

前面所有的分布都是本地常数。真实调用里，那个分布由服务端算出来，默认不返回，要看它得在请求里要 `logprobs`。`code/knowledge/ch02_generation/logprobs_shape.py` 请求一次带 `logprobs=True`、`top_logprobs=5` 的响应：

```python
def logprob_node(token: str, candidates: list[tuple[str, float]]) -> dict:
    """一个位置的 logprobs 节点：选中项 + 候选列表。"""
    chosen = dict(candidates)[token]
    return {
        "token": token,
        "logprob": math.log(chosen),
        "bytes": None,
        "top_logprobs": [
            {"token": t, "logprob": math.log(p), "bytes": None} for t, p in candidates
        ],
    }
```

`openai` 客户端把它解析成对象，输出是这样的：

```
要了 logprobs：ChoiceLogprobs，共 3 个位置
没要 logprobs：None

  位置    选中      p       该位置的候选（top_logprobs=5）                          候选合计
  0     7天      0.50    7天:0.50  7日:0.22  一周:0.15  七天:0.10  3天:0.03     1.00
  1     内       0.88    内:0.88  之:0.07  以:0.03  后:0.02                  1.00
  2     可退      0.71    可退:0.71  可以退:0.12  能退:0.08  可退货:0.03  可退款:0.01  0.95

第三个位置的候选合计 0.95，剩下 0.05 的尾部没有出现在 top_logprobs 里。
这 0.05 里有若干更冷的候选，它们各自概率很低，合起来才够补满 1。
```

概率值是给定的演示常数，形状是真的，`openai` 客户端把它解析成 `ChoiceLogprobs` 对象。

这段输出说明四件事。`logprob` 是对数概率，表格里的 0.50、0.88 都是做 `exp` 之后的值，响应里存的是 `-0.69` 这样的负数，把对数概率当概率比较，阈值会全错。`top_logprobs=5` 只给前 5 个候选，第三个位置的候选合计只有 0.95，尾部被截掉，所以某个候选没出现在里面不等于它的概率是 0。被选中的 token 一定在候选列表里，但概率可能不高。不要求就没有：没带 `logprobs` 的请求，`choices[0].logprobs` 是 `None`。

四件事合起来，解释了 3.1 节那几组演示分布为什么只能当原理演示：真实分布要靠 `logprobs` 取，取到的还是截断过的前 N 名。

拿 `logprobs` 做判定还有两个陷阱。不同长度的输出不能直接比对数概率：20 个 token 的连乘必然比 5 个的更小，要比就得看每个 token 的平均值，而标点、虚词的候选更集中，长输出里这类 token 多，平均值会被人为压低。分词不同也不可比：`7天` 可能是一个 token，也可能是两个。共同点是 `logprobs` 给的是模型内部视角的数值，适合比较相似输入上的相对变化，不适合当绝对阈值。

能用的场景有一个很具体：看选中的 token 与第二名差多少，用来标记"这一处是在猜"。上面那张表里，位置 2 的 `可退` 是 0.71、第二名 0.12，差距大；位置 0 的 `7天` 是 0.50、第二名 0.22，差距小。差距小的地方换一次采样就可能换成别的候选。它给的是定位线索，不是结论：差距大也可能错得一致。

### 3.4 温度 0 的确定性边界

温度 0 的做法是每一步取概率最高的 token，这个动作本身是确定的，但有三处不确定；这一点在第 1 章提过，这里说明原因。

浮点累加的次序算一个：不同硬件、不同批大小下算出的概率可能有极小差异，当最高和第二高的概率非常接近时，这个差异足以改变取哪一个。批处理算一个：服务端把多个请求打包成一批并行计算，同一批里的其他请求会影响浮点运算的分组方式。模型版本算一个：服务端更新模型时即便名字没变权重也可能变，第 1 章那份响应里的 `system_fingerprint` 是事后确认这件事的唯一线索。

三处的共同点是它们都不在调用方的代码里，所以温度 0 等于可复现这个假设在跨请求、跨时间时并不成立。有的服务端还提供一个 `seed` 参数固定随机数的起点，它减少的是同一进程内的波动。正确的理解是：温度 0 让同一个进程、同一台机器、同一版本下的重复调用结果一致，跨这些边界时只能大致一致。

### 3.5 单步稳定与整段稳定

比温度 0 不确定更值得注意的一条是单步稳定与整段稳定。`code/knowledge/ch02_generation/length_compounding.py` 用同一个分布，分别按三种温度、四种长度生成，统计两次生成的序列完全相同的比例：

```python
def same_rate(probs: list[float], length: int, trials: int = 200) -> float:
    """跑 trials 次，统计与第一次完全相同的有几次。"""
    rng = random.Random(11)
    first = one_sequence(probs, length, rng)
    same = sum(1 for _ in range(trials - 1) if one_sequence(probs, length, rng) == first)
    return same / (trials - 1)
```

输出：

```
每步分布： A:0.70  B:0.15  C:0.10  D:0.05
（最高频候选占 70%，单看一步很稳）

 temperature      步数        两次完全相同
------------------------------------
         0.3       1        98.0%
         0.3       5        96.0%
         0.3      20        86.9%
         0.3      50         0.0%

         0.7       1        80.4%
         0.7       5         2.5%
         0.7      20         0.0%
         0.7      50         0.0%

         1.0       1        67.8%
         1.0       5         1.0%
         1.0      20         0.0%
         1.0      50         0.0%

读法：
  温度 0.3，单步最高频占 99%，
  但 50 步全对的概率是它连乘 50 次，几乎没有。

结论：
  '单步稳定'不等于'整段稳定'。
  输出越长，两次完全相同的概率越低。
  要判断改动是否有效，必须比较多次运行，不能各跑一次。
```

温度 0.3 那一组最能说明问题：单步最高频候选占 99%，看起来非常稳；5 步时还有 96% 两次相同，20 步降到 86.9%，50 步时降到 0。原因是整段相同要求每一步都取到同一个候选，单步概率 $p$ 时，$n$ 步全同的概率是 $p^n$，$0.99^{50} \approx 0.61$，再乘上低概率候选的干扰，实际更低。

实践上有三条结论。短输出的稳定性不能外推到长输出：一段 20 字的分类结果可能每次都一样，一段 500 字的总结几乎不可能两次相同。比较两个版本时必须多次运行，各跑一次就下结论等于在比较两个随机样本。每次都不同不一定是 bug，长文本本来就不可能逐字相同，需要判断的是语义是否一致。

这也解释了为什么把输出写短能同时改善三件事：采样次数少，两次相同的概率高；token 少，成本低；要核对的句子少，依据更容易标。语义一致怎么判是评测问题，这里能确定的只有一条：字符串相等只能当必要条件，不能当充分条件。

### 3.6 结构化输出的温度

如果要从中解析字段，需要的是"同一输入给出同一形状的输出"。温度升高会让同义词、同义格式、不同的表达方式交替出现（示意）：

```
7天 / 7日 / 一周 / 七天
```

这四种写法指的是同一件事，但解析代码必须全部覆盖；温度 0 时稳定输出其中一种，解析只需要处理一种。温度 0 并不等于完全确定（3.4 节），所以正确做法是两层：调低温度减少变异，同时让解析器容忍同义写法与少量格式噪声。只做前一层，等于把正确性押在服务端不会变这个假设上。

两层里第二层更重要，原因是采样参数管不到语法。温度 0 只让最可能的那个 token 每次相同，它不保证这个 token 拼出来的 JSON 是合法的，引号、逗号、括号都可能出错。要拦住这类错误靠的是解析与校验，不是温度，第 4 章讲结构化输出的几条路径，本质上都是在把语法从采样里拿出来交给别的机制保证。

### 3.7 采样参数解决不了依据

需要说清楚一件事：调低温度不会让没有依据的内容变得有依据。温度 0 时仍然会输出那个出现频率最高的 `7天`，只不过每次都输出它。稳定性提高了，正确性没有提高，一个稳定的错误答案比一个不稳定的错误答案更难发现。两个问题要分开处理：

| 问题 | 解决办法 | 在哪一章 |
|---|---|---|
| 内容没有依据 | 补资料，或允许拒答，或外部校验 | 本章第二节、第 4 章、反思与外部裁判一章 |
| 同一输入结果不同 | 降低温度，固定参数 | 本章第三节 |

## 四、几种失效的表现

前面几节各讲了一个侧面，合起来会漏掉一类问题：这些参数和判据用错时，症状不是出错，而是一切都正常、结论是错的。四种形态值得单独列。

弱依据通过了引用检查：代码检查有没有引用，弱依据照样能附上一句相关原文，信号是对照引用的那一句，结论里的数字在原文里找不到。稳定性被当成正确性：把温度调到 0，输出可复现被读成输出可信，信号是换一批输入错误率没变、重复跑结果也不变。把对数概率当概率：3.3 节的两个陷阱之一，阈值怎么设都不对，信号是调整阈值时被拦与放行的样本没有明显区别。参数没生效但没人发现：3.2 节那张表里的三种场景，信号是所有调参实验都得出影响不大的结论。

四种失效的共同点是都没有异常。能拦住它们的不是更严的日志级别，是四种具体的核对动作：比对引用原文、看换输入的差异、确认量纲、打请求体。这四种动作里只有最后一个能机械化，前三个更像是排查时的顺序。真要系统化，得把判据变成用例：一组带期望答案的输入，每条同时校验内容与依据，载体是评测集，不是日志。

## 五、这套做法的边界

补资料只能解决"资料里有的"。资料里没有的，补多少资料都不会出现正确答案，只会让输出换个方式编。判断方法是：同一个问题换三种问法都得到相同错误答案，多半不是提示词问题，是资料问题。

允许拒答会降低回答率。明确让它说不知道，会有相当一部分本来能答对的问题变成拒答，这是有意的取舍：宁可拒答，不要编造。在高风险场景这是正确的，在低风险场景可能过度保守。

温度不是越低越好，需要多样性的时候，温度 0 会导致每次都给同一个答案。温度也控制不了整条链路：一次任务里可能有多处采样点，多步任务里每一轮都有各自的采样，整体结果的分散程度是累积的，这一点在第 8 章讲循环失控时会具体展开。

`logprobs` 不是所有服务端都给，有的服务商不返回它，或者在流式响应里不返回，这决定了 3.3 节那种分析能不能做：拿不到候选分布时只能退回多跑几次看结果分布这种间接办法。

补资料与窗口预算冲突。资料进 `messages` 就占 token，占得多了留给输出的额度就少，占满了请求会被拒，第 1 章 12.2 节算过这笔账。所以补资料的可行范围由窗口决定，窗口之外的部分要靠检索先筛一遍。这一章只能说清一件事：资料放不进去时，依据强度就自动降级，这时必须让它表达出来，而不是让它填满。

多跑几次不等于评测。3.5 节说比较两个版本必须多次运行，这句话只解决随机波动：跑十次得到十次相同的结果，只能说明稳定，不能说明正确。

七条边界合起来，给出这一章做法的代价上界：依据靠资料，资料靠窗口，窗口靠钱；拒答靠提示词，提示词降低回答率；稳定性靠低温，低温降低多样性。三对取舍都是真的取舍。所以这一章的结论不是把这些都做到，是先判断场景更怕哪一种错：怕编造就允许拒答，怕不一致就压低温度，怕不可核对就要求引用。

## 这一章建立的 5 件事

1. 输出分三种依据强度：强（可逐字核对）、弱（框架有源、细节无源）、无（全靠训练语料）。三种的输出格式相同。
2. 弱依据最难发现：格式正确、语气确定、细节具体，只是那个细节没有任何来源。
3. 生成是逐 token 采样，每一步只算概率不看事实；位置必须填满，所以拒答需要提示词或外部判据来兜。
4. 温度改变分布形状：0 时取最高概率（不是取消随机），升高让低概率候选有机会出现；`top_p` 改的是候选集合，不是相对高低。
5. 调低温度只解决稳定性，不解决依据问题。一个稳定的错误答案更难发现。
