## 一、块是检索的最小单位

第 15 章讲向量化时有一个前提没展开：向量由"一段文本"算出来，这段文本多大由切块决定。检索返回的不是文档，是块，检索的最小命中单位、引用的最小单位、预算的最小扣除单位都是块。块的粒度就是系统的粒度，取舍由此而来：块大能装完整论述，却可能混着三个主题，向量被平均掉；块小向量更聚焦，一句完整的话又可能被切成两半。

### 1.1 一份文档变成很多块之后

切块的直接后果是 id 体系变化。`doc_id` 是文档编号，一条文档进来时就有；切完变成十几个块，每块加一个 `chunk_id` 并保留 `doc_id` 作为回溯。影响落在三处：引用按块定位，块要带偏移量；删除按 `doc_id` 过滤全部块；重新切块会改变块的划分，第 21 章讲治理时展开。

### 1.2 切块发生在嵌入之前

切块发生在嵌入之前，顺序决定了切块的错误无法被后续环节纠正：块切错了，嵌入只是把错的文本编码成向量，检索、拼装、生成都忠实执行，输出仍然错。所以切块的验收要在建索引之前做，一旦写进库，改切法意味着全量重算，与第 15 章换模型是同一种成本。

### 1.3 块大小与问题粒度

块该多大，取决于用户问的问题有多大。"生鲜能在几小时内拍照"的答案是一句话；"生鲜为什么不能无理由退"要先讲前提再给结论，块要装下一整段。两类问题并存时，单一 chunk_size 必然有一类不合适，处理方式不是找折中值，而是让块同时支持两种粒度：小块索引、大块生成，或者按问题类型分两个索引。

### 1.4 块是索引的原子

块与文档的从属关系在治理上很重要：文档下线时删除的单位是"这个 `doc_id` 的所有块"，更新时替换的单位也是块。块没有 `doc_id`，删除只能靠全文匹配或逐个 id 记录，前者不准，后者要额外维护一张映射表。新块与旧块不会一一对应，按位置对齐会错位，可行做法是整篇重切、按 `doc_id` 全量替换。

## 二、切错的三类后果

切块出问题，表现都不在切块本身，而在下游。三类后果按发现难度排：

| 后果 | 表现 | 发现难度 |
|---|---|---|
| 一句话被切成两半 | 检索命中半句，答案缺主语或缺条件 | 低，看输出能发现 |
| 一块混了几个主题 | 向量偏向其中一个，另外几个查不到 | 中，召回率下降但不报错 |
| 标题与正文分家 | 块里没有上下文，模型不知道这条在讲什么 | 高，答案看起来答非所问 |

第一类最容易看到。下面这个块来自 40 字切法的一次切分（示意）：

```
  生鲜坏了要在多久内拍照        命中块  39 字：'小时内拍照并联系客服，逾期不再受理。生鲜订单的退款按坏果比例计算，不'
```

它从"小时内"开始，前面的"24"被切到了上一个块里，这个块单独看仍然通顺，只是没有主语也没有时限，模型拿到它只能答"签收后拍照"，答不出"24 小时内"；而它被检索到，是因为包含"拍照""客服"这些词。

第二类要跑评测才看得出：一个 300 字的块前半讲退货、后半讲发票，向量被两段平均，两个主题的查询都能命中它，但都不够准，它却占掉了两个位置。第三类最隐蔽：按长度切的块丢掉标题，模型不知道这段文字是政策条款还是客服话术。

### 2.1 三类后果各自怎么测

三类后果都需要可测的量，否则改切法只能靠感觉：

| 后果 | 可测的量 | 怎么算 |
|---|---|---|
| 句子被切断 | 命中率 | 带答案关键词的问题，top-1 里有没有那句话 |
| 一块混多个主题 | 块内主题分散度 | 块的相邻句余弦方差，或人工标注 |
| 标题丢失 | 带元数据的块占比 | 统计 `metadata` 里有标题字段的块 |

第一行是第四节那个扫描实验，最便宜也最有效；第三行只需要数一下，Markdown 切法 100%，递归切法 0%。第二行没有便宜的量，可行的近似是算块内相邻句的余弦方差，它只能排序、不能当阈值，先找出混得最厉害的那批块人工看一眼更快。

### 2.2 混杂度是可以设计掉的

"一块混几个主题"听着是切法问题，实际有一半是文档结构问题：每一节都有小标题的政策文档，按标题切天然不会混；没有小标题的会议纪要，按长度切必然把两三个议题塞进一块。混杂度可以在写文档时被消除，这也是治理里"条目结构"（要点、例外、来源）的来源。

文档本身没有结构时，切块只能猜：要么接受混杂，要么先让模型把文档改写成有结构的条目，后者是治理动作，成本与风险都在另一个量级。

### 2.3 混杂度的量化做法

"一块混了几个主题"可以算。做法是把块按句号切开，算相邻句的余弦，取均值或方差，下面是示意代码：

```python
def diversity(emb, text: str) -> float:
    """块内相邻句的平均余弦距离；越大说明主题跳变越频繁。"""
    sents = [s for s in text.split("。") if s.strip()]
    if len(sents) < 2:
        return 0.0
    vecs = emb.embed_documents(sents)
    sims = [sum(a * b for a, b in zip(vecs[i], vecs[i + 1]))
            for i in range(len(vecs) - 1)]
    return 1 - sum(sims) / len(sims)
```

这个数无法定阈值，但可以排序：把库里所有块算一遍，取前 50 个混得最厉害的，人工看它们是不是真把两三个主题塞在了一起。还有一个更省的做法，不用嵌入，直接看块内是否出现两个小标题，标题是最强的主题信号。

## 三、五种切法

同一份文档，运行 `code/knowledge/ch16_chunk/splitters.py` 后五种切法的输出：

```
  [CharacterTextSplitter（按段落分隔）] 5 块，长度 [15, 78, 57, 43, 96]
    '# 售后政策\n\n## 退货条件'
    '质量问题退货，运费由商家承担，买家需在签收后 7 天内提交凭证。\n非质量问题'...

  [RecursiveCharacterTextSplitter（递归分隔符）] 6 块，长度 [15, 78, 65, 50, 72, 23]
    '# 售后政策\n\n## 退货条件'
    '质量问题退货，运费由商家承担，买家需在签收后 7 天内提交凭证。\n非质量问题'...

  [MarkdownHeaderTextSplitter（按标题）] 4 块，长度 [70, 50, 33, 96]
    '质量问题退货，运费由商家承担，买家需在签收后 7 天内提交凭证。\n非质量问题'... {'h1': '售后政策', 'h2': '退货条件'}
    '生鲜类商品不支持无理由退货。若存在质量问题，请在签收后 24 小时内\n拍照并'... {'h1': '售后政策', 'h2': '生鲜类'}

  [from_tiktoken_encoder（按 token 数）] 7 块，长度 [15, 32, 37, 58, 50, 51, 44]
    '# 售后政策\n\n## 退货条件'
    '质量问题退货，运费由商家承担，买家需在签收后 7 天内提交凭证。'

  [SemanticChunker（默认英文断句）] 1 块，长度 [298]
  [SemanticChunker（中文断句正则）] 7 块，长度 [18, 76, 9, 56, 8, 37, 116]
```

六组结果，四个地方值得说。第一，CharacterTextSplitter 只在分隔符处切，段落 96 字、chunk_size 80，它给出 96 字的块，chunk_size 在这类切法里是目标值而不是上限。第二，RecursiveCharacterTextSplitter 的块更贴合语义边界，代价是块数变多、长度更不齐。第三，MarkdownHeaderTextSplitter 保住了标题元数据，但它只按标题切，长度不受控。第四，SemanticChunker 也就是语义切块，在中文上默认失效：默认断句正则是 `(?<=[.?!])\s+`，只认英文标点且要求标点后有空格，中文句号不匹配，整篇被当成一句话，等于不切块。

```
  [SemanticChunker（默认英文断句）] 1 块，长度 [298]
  [SemanticChunker（中文断句正则）] 7 块，长度 [18, 76, 9, 56, 8, 37, 116]
```

第一行是最危险的失败形态：没有报错，块看起来也正常，只是"语义切块"退化成了"不切块"。换成正则后切成 7 块，但标题单独成块、正文与标题分家，正是第二节的第三类后果。

语义切块不是更聪明所以更好，它在句子边界上做聚类，而标题这种短行与正文的语义距离天然很远；要用它，得先把标题行合并进正文，或者切完再把过短的块与相邻块合并。

### 3.1 separators 的顺序就是优先级

递归切法的全部智能都在 `separators` 这个列表里。它按顺序尝试：先用第一个分隔符切，切出的块还超过 chunk_size，就对超长的块用第二个分隔符，下面这段是示意代码：

```python
splitter = RecursiveCharacterTextSplitter(
    separators=["\n## ", "\n\n", "\n", "。", "，", ""],
    chunk_size=80,
    chunk_overlap=10,
)
```

列表的设计原则是从语义最强的边界往最弱的边界排：`\n## ` 是标题，`\n\n` 是段落，`\n` 是行，`。` 是句子，空字符串是最后兜底，按字符硬切。两个常见错误：把空字符串放在最前面，等于放弃所有语义边界；忘记中文标点，默认列表是英文的，最后一档会频繁触发硬切。

### 3.2 中文切块的三个特殊之处

中文在切块上比英文麻烦。中文没有空格作为天然边界：英文按空格切，最坏切在词中间；中文按字符切，切在哪里都不像词。中文的句子边界只有句号可靠，分号通常表示并列，切在分号上得到的常常是半句，所以分隔符里应当放句号而不放逗号。

### 3.3 切法要跟着索引版本一起记

切法变了，块就变了，块 id 也变了，这在增量更新时会立刻出问题：库里一半是旧切法的块、一半是新切法的块，同一段内容有两份不同的块，检索会同时召回。所以切法必须与索引版本绑定，`index_version` 是索引版本号，里面记录切法名称、`chunk_size`、`overlap`、分隔符列表；换切法等于换版本。

### 3.4 切块对在线延迟没有影响

切块对在线延迟的影响容易误解：切块只发生在建索引阶段，查询时块已经存在。在线路径上真正与块有关的成本有两处：块的数量决定检索的候选集大小，影响延迟；块的长度决定拼装时能放几块，影响上下文质量。

| 块大小 | 块数 | 检索延迟 | 上下文质量 |
|---|---|---|---|
| 小 | 多 | 高（候选多） | 低（信息碎片） |
| 大 | 少 | 低 | 高（但可能超预算） |

切块因此是在检索成本与上下文成本之间做分配。把它当成纯离线的事会漏掉前一半：块切得太碎，检索会变慢，这个慢随文档量增长而放大。块的大小还决定了 k 怎么取：先定块大小再定 k，因为块小、k 小召回不够，k 大了候选多、延迟涨；块适中时 k=3 就能覆盖大部分问题，参数之间是乘法关系，单独调一个往往只是把成本挪了个位置。

## 四、块大小怎么定

块大小不是拍出来的，是扫出来的。运行 `code/knowledge/ch16_chunk/chunk_retrieval.py` 得到的四种 chunk_size 命中率：

```
=== 1. chunk_size 与命中率（top-1 里有没有那句话）===
  chunk_size    块数      平均块长     命中率
          40    12        27     40%
          80     5        63    100%
         160     5        63    100%
         320     5        63    100%
```

40 字时命中率掉到 40%，80 字以上全是 100%。原因不在模型，在块：

```
=== 2. 固定小块的上下文长度 ===
  生鲜坏了要在多久内拍照        命中块  39 字：'小时内拍照并联系客服，逾期不再受理。...'
  发票最晚什么时候可以开        命中块  24 字：'发票。发票可在订单页申请，开票时限为下单后 30'
  买完降价了能补差价吗          命中块  39 字：'天内出现降价，可申请补差价，每人每单限一次。...'
```

三行里有两行被切掉了关键信息："24 小时"的"24"、"15 天"的"15"都留在了上一个块。命中率下降不是检索变差，是答案本身被切走了。判据不是块长是否合理，而是拿一批带答案关键词的问题，看 top-1 里有没有那句话。chunk_size 定下来之后，还有两个参数要一起定：

| 参数 | 作用 | 定法 |
|---|---|---|
| `chunk_size` | 目标块长 | 扫描到命中率不再上升的那个点 |
| `chunk_overlap` | 相邻块的重叠字数 | 通常是 size 的 10%–20%，用来救被切断的句子 |
| `separators` | 递归切分的分隔符顺序 | 按文档的实际结构排，段落 → 行 → 句号 |

`chunk_overlap` 常被当成万能补丁：它确实能救一部分切断句，代价是同一段文字在多个块里重复出现，检索时被一起召回，占掉多个位置而内容几乎一样。overlap 是补偿不是修复，40 字的块需要 30 字重叠才能用，答案就是别用 40 字。

### 4.1 overlap 的代价是可以算的

重叠的字数直接变成重复的向量与重复的预算。设块长 `s`、重叠 `o`，一份总长 `L` 的文档切出的块数约是 `(L - o) / (s - o)`，`o` 加到 `s/2` 时块数接近翻倍。

| 块长 | 重叠 | 块数（相对无重叠） | 重复内容占比 |
|---|---|---|---|
| 100 | 0 | 1.0 | 0% |
| 100 | 10 | 1.1 | 10% |
| 100 | 30 | 1.4 | 30% |
| 100 | 50 | 2.0 | 50% |

第三行之后收益小于成本：重叠 30 字时，库里三成内容是重复的，检索会把同一段文字的不同片段一起召回，去重成了必须做的事。更麻烦的是隐性预算代价，第 14 章讲过拼装预算：一块 100 字里有 30 字与上一块重复，有效信息只有 70 字。折中是 `o = s × 0.15` 左右，只在句子确实被切断时才保留重叠。

### 4.2 扫描实验要做在业务文档上

扫描只用了五条短文档，结论只对这一批文档成立。搬到生产的做法是：从每个文档类型抽十份，每份标三到五个问题，得到 50 到 100 条的小评测集；问题要来自真实提问，答案关键词要唯一。还有一个反直觉的结果：更大的 chunk_size 命中率不一定更高，块太大时答案那句被稀释，最优点在中间某处。

### 4.3 扫描集与评测集

4.2 那份小评测集就是 RAG 评测一章要建的东西，区别只在用法：这里用它选 chunk_size，那时用它验收整条链路。早点建有三层收益：切块选型有依据；每次改动有同一套问题做基准，换切法、换模型、换重排都能比；线上答错的那条补进去就成了回归用例。文档更新后问题引用的答案可能变，所以要带版本、与索引版本一起记。

## 五、父子块

两节的矛盾很清楚：小块召回准，大块上下文完整。父子块把这个矛盾拆开，用小块检索，用大块生成，下面这段输出来自 `code/knowledge/ch16_chunk/chunk_retrieval.py`：

```
=== 3. 父子块：检索用小块，交给模型用大块 ===
  父块数 5，子块数 12
  生鲜坏了要在多久内拍照        返回  70 字，含关键词 True：'生鲜类商品不支持无理由退货。若存在质量问题，请在签收后 24 小时内拍照...'
  发票最晚什么时候可以开        返回  61 字，含关键词 True：'发票。发票可在订单页申请，开票时限为下单后 30 天，超过时限不再补开。'
  买完降价了能补差价吗          返回  53 字，含关键词 True：'价保。商品签收后 15 天内出现降价，可申请补差价，每人每单限一次。...'
```

5 个父块、12 个子块，每个父块被切成两到三个子块，检索时比的是子块，返回的是它所属的父块。同一条问题，两种返回的差别：

```
  小块  39 字：'小时内拍照并联系客服，逾期不再受理。生鲜订单的退款按坏果比例计算，不需要寄回。'
  父块  70 字：'生鲜类商品不支持无理由退货。若存在质量问题，请在签收后 24 小时内拍照并联系客服，逾期不再受理。生鲜订单的退款按坏果比例计算，不需要寄回。'
```

小块从"小时内"开始，父块从"生鲜类商品不支持"开始，主语回来了，"24 小时"也回来了。父子块同时改善了两件事：检索精度用小块比，上下文质量用大块给。

| 代价 | 说明 |
|---|---|
| 存储翻倍 | 子块要存向量，父块要存原文，两套都要 |
| 一次查找变两次 | 先查子块，再按父 id 取原文，多一次读 |
| 父块可能过大 | 父块超过预算时还要再裁，裁法与拼装一致 |

第三条代价最容易被忽略：父块按语义完整切出来，长度没有上限，塞进 200 字预算时要么截断（回到第 14 章那个问题），要么二次切分。可行的做法是给父块也设上限，超过上限时退回取子块加相邻子块。

### 5.1 父子块与拼装

父子块改变的是检索返回什么，而拼装需要的是带编号的块，两者之间要做一次转换：

| 步骤 | 拿到什么 | 要做什么 |
|---|---|---|
| 检索 | 子块向量命中的父块 id | 按 id 取父块原文 |
| 去重 | 同一个父块可能被多个子块命中 | 按父 id 合并，只保留一次 |
| 截断 | 父块可能超预算 | 超长时按句切，保留包含答案的那一段 |
| 编号 | 父块没有编号体系 | 给每个进入上下文的父块分配 `[dN]` |

第二步最容易漏：三条子块命中同一个父块时，如果不去重，上下文里会出现三段几乎相同的文字，占掉三个编号，人去核对时发现三份一样的来源。第四步说明父子块与第 14 章的引用体系要一起设计：编号分配给父块，校验时也只校验父块的 id。

### 5.2 什么时候不该用父子块

父子块不是默认选项，三个场景下它会帮倒忙。块本来就大时，chunk_size 已是 300 字而预算能放 400 字，再拆一层只是多一层间接。答案依赖精确位置时，合同条款、法条编号要求引用精确到句，父块把范围放大到整段，精度反而下降。写入频繁时，两套存储与两套 id 的维护成本会超过收益。

### 5.3 父子块的引用代价

父块进上下文之后，引用只能标到父块，用户点开看到的是 200 字的一段，而他问的那句只是其中一句。三个应对方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| 标记答案句 | 生成时要求指出答案在父块中的第几句 | 模型不一定可靠，需要二次校验 |
| 高亮范围 | 用子块的位置反推答案范围 | 子块偏移要存进元数据 |
| 接受粗粒度 | 引用只到父块 | 核对成本由用户承担 |

第二种在工程上最划算：子块本来就是按答案位置命中的，它的偏移量能精确指出答案落在父块的第几到第几字，存储上多两个整数，展示时可以把这一段高亮出来。精度藏在检索的中间结果里，只是多数实现没把它传下去。

### 5.4 父子块的更新成本

父块与子块是两份数据，更新时要么同时改，要么接受一段时间的不一致。

| 更新方式 | 一致性 | 代价 |
|---|---|---|
| 同时写两份 | 强一致 | 写入放大一倍，失败要回滚 |
| 先写父块再写子块 | 最终一致 | 中间时刻可能查到新父块配旧子块 |
| 整篇重切重写 | 强一致 | 每次更新都全量重算这一篇 |

第二种不一致的窗口很短，后果却很具体：用户拿到一段父块，而检索命中的是旧子块的向量，内容对得上但位置偏了，引用高亮会错位；多数系统接受这个窗口，因为它只存在于更新的一瞬间。

## 六、表格与代码块

表格和代码块是切块最容易破坏的结构，它们的语义依赖行与行之间的对齐，而按字符或按行切会把这个对齐破坏掉。下面是一份运费对照表被切断的样子（示意）：

```
=== 表格被切断的样子 ===
    '| 场景 | 谁承担 | 时限 |\n|---|---|---|'
    '| 质量问题 | 商家 | 7 天 |'
    '| 非质量问题 | 买家 | 7 天 |'
    '| 生鲜质量问题 | 商家 | 24 小时 |'
```

上面这一组切法把表头与数据行分开了：单独一块 `| 质量问题 | 商家 | 7 天 |` 看着还能读，但模型不知道三列分别是什么。三种处理方式：

| 方式 | 做法 | 适用 |
|---|---|---|
| 整表保留 | 检测到表格边界，整块不切 | 表格小于预算时 |
| 行内补表头 | 每行前面拼上列名 | 表格大、必须切时 |
| 转写成句子 | 把每行写成"质量问题由商家承担，时限 7 天" | 表格用于问答而非展示时 |

第三种效果最好，它同时解决了表头丢失与向量不理解表格结构两个问题，代价是转写要花一次模板或模型调用，且原文表格与转写文本要分开存。代码块的问题不同，它没有行对齐，但有缩进与作用域：按固定字符切一个函数，前半段有签名、后半段有实现，可用的做法是按语法结构切，退一步按空行切。

### 6.1 表格转写的一种写法

转写不需要模型，用模板就能覆盖多数"场景—结论"型表格，下面是示意代码：

```python
def table_to_sentences(rows: list[list[str]], header: list[str]) -> list[str]:
    """把表格行转成“列名 值、列名 值、……”的句子。"""
    out = []
    for row in rows:
        parts = [f"{h} {v}" for h, v in zip(header, row) if v.strip()]
        out.append("，".join(parts) + "。")
    return out

header = ["场景", "谁承担", "时限"]
rows = [
    ["质量问题", "商家", "7 天"],
    ["非质量问题", "买家", "7 天"],
    ["生鲜质量问题", "商家", "24 小时"],
]
for s in table_to_sentences(rows, header):
    print(s)
```

```
场景 质量问题，谁承担 商家，时限 7 天。
场景 非质量问题，谁承担 买家，时限 7 天。
场景 生鲜质量问题，谁承担 商家，时限 24 小时。
```

转写出来的句子自带列名，切到哪一块都不会丢上下文，语义也与用户提问更接近：用户问"生鲜坏了谁出运费"时，匹配的正是"场景 生鲜质量问题，谁承担 商家"这样一句。代价是原文被改写，政策里"逾期不再受理"这类措辞可能被简化，而它恰恰有法律含义，这也是第 14 章引用要能回指原文的另一处应用。

### 6.2 代码块按空行切

代码没有通用解析器的场景下，按空行切比按字符切好得多：

| 切法 | 结果 |
|---|---|
| 按 40 字符 | 函数签名与实现分家，缩进错乱 |
| 按空行 | 一个函数、一个代码段各自成块，缩进完整 |
| 按语法树 | 完整语义单元，需语言解析器 |

按空行的前提是代码有良好的空行习惯，压缩过的代码会退化成按字符切。另一条约束与嵌入有关：代码的向量表示与自然语言不同，同一个嵌入模型在代码上的表现通常弱于自然语言，所以代码类知识库常见做法是文档与代码分开索引，用自然语言描述查文档，用标识符查代码。

### 6.3 表格的可检索性

即使表格没被切断，它作为检索对象也有问题：表格里的信息是行列关系，而检索靠的是字面与语义相似。用户问"生鲜坏了谁出运费"，表里那一行字面上没有"运费"两个字，语义上也不构成一个句子，嵌入模型很难把它与问题对应起来。三种补救，成本递增：

| 补救 | 做法 | 效果 |
|---|---|---|
| 补表头 | 每行拼上列名 | 解决"不知道列是什么" |
| 转写成句 | 见 6.1 | 解决"不成句" |
| 双份存储 | 原文 + 转写都入库 | 展示与检索各取所需 |

第三行是生产里的常见做法，代价是存储翻倍、更新时要同时改两份，好处是保住了两边的优点：检索用转写文本，展示与引用用原文。表格还有一类问题来自合并单元格：Markdown 无法表达合并，转成 Markdown 时常见的做法是重复填充，同一列值出现多次，向量被这些重复值主导。

### 6.4 混合文档要分开切

真实文档经常是混排的：一段说明、一张表、一段代码、再一段说明，只用一个切法，必然有一类内容被切坏。可行的做法是先分段再分别切：按 Markdown 标题切出章节，章节内部判断这一节主要是文字、表格还是代码，用对应的切法；判断不需要模型，正则足够。块的元数据里还要加一个 `type` 字段。

## 七、五个类与一个组合

副线要认的组件只有六个：五个切分器加一个父子检索器。

| 切法 | 类 | 关键参数 |
|---|---|---|
| 定长 | `CharacterTextSplitter` | `separator`、`chunk_size`、`chunk_overlap` |
| 递归 | `RecursiveCharacterTextSplitter` | `separators`、`chunk_size`、`chunk_overlap` |
| 按标题 | `MarkdownHeaderTextSplitter` | `headers_to_split_on` |
| 按 token | `RecursiveCharacterTextSplitter.from_tiktoken_encoder` | `encoding_name`、`chunk_size` |
| 语义 | `SemanticChunker` | `breakpoint_threshold_type`、`breakpoint_threshold_amount`、`sentence_split_regex` |
| 父子 | `ParentDocumentRetriever` | `child_splitter`、`parent_splitter`、`search_kwargs` |

按 token 切那一条最容易被忽略，它解决的是字符数与 token 数不是线性关系的问题：中文一个字大致一个 token，但英文、数字、标点混排时差异很大，400 字的混排文本可能是 300 token，也可能是 600 token。按字符切，块可能超出模型窗口；按 token 切，块长度不可预测但绝不会超，写法只有一行（见 `code/knowledge/ch16_chunk/splitters.py`）：

```python
tok = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    encoding_name="cl100k_base", chunk_size=60, chunk_overlap=10)
```

`encoding_name` 要与模型匹配，用错编码算出的 token 数与模型实际不符，切块就白算了，这类错误不报错，只让块长分布与预期略有差异。五个切法的差别可以压成一张对照：

| 输出 | 块数 | 保留标题 | 尊重语义边界 | 中文可用 |
|---|---|---|---|---|
| Character | 5 | 否 | 否（只按段落） | 是 |
| Recursive | 6 | 否 | 部分 | 是 |
| Markdown | 4 | **是** | **是**（按标题） | 是 |
| tiktoken | 7 | 否 | 部分 | 是 |
| Semantic | 1 / 7 | 否 | **是** | 需改正则 |

最后一列是我在这个环境里跑出来的结果，不是文档上的说法：SemanticChunker 在中文上默认不可用。

### 7.1 ParentDocumentRetriever 的两个存储

ParentDocumentRetriever 把两次存储写在了构造函数里（见 `code/knowledge/ch16_chunk/chunk_retrieval.py`），看懂它需要分清两个参数：

```python
retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,   # 存子块向量，负责“找得到”
    docstore=docstore,         # 存父块原文，负责“给得全”
    child_splitter=child,
    parent_splitter=parent,
    search_kwargs={"k": 1},
)
retriever.add_documents(DOCS)
```

`add_documents` 先用 `parent_splitter` 切出父块，给每个父块分配 id 存进 `docstore`，再用 `child_splitter` 切每个父块，子块的元数据里记下父 id，存进向量库。两个存储的职责不能互换：`docstore` 是键值存储，按 id 取原文，不参与相似度计算；`vectorstore` 只存向量与元数据。`search_kwargs` 里的 `k` 是子块的返回数而不是父块，k=3 时三个子块可能指向同一个父块，去重后只返回一个。

### 7.2 该选哪一种

五种切法不是并列关系，选法有先后：

| 文档特征 | 先试 | 不行再换 |
|---|---|---|
| 有 Markdown 标题 | `MarkdownHeaderTextSplitter` | 标题切完块太大时，套一层 `RecursiveCharacterTextSplitter` |
| 有明确段落、无标题 | `RecursiveCharacterTextSplitter` | 块仍混杂时考虑语义切块 |
| 纯长文本、主题跳跃 | `SemanticChunker` | 中文先修正则，再合并过短块 |
| 混排、含表格代码 | 按类型分别切 | 表格转写、代码按空行 |
| 需要精确引用 | 小 `chunk_size` + 父子块 | 接受引用粒度变粗 |

第一行是实践中最常见的组合：先用标题切出语义完整的节，再对超长的节用递归切分。先按结构切，再按长度切，这个顺序几乎适用于所有格式化文档。

### 7.3 两层切的写法

把 7.2 第一行落成代码（`code/knowledge/ch16_chunk/splitters.py`），只有十来行：

```python
def split_markdown(text: str, size: int = 120, overlap: int = 20):
    md = MarkdownHeaderTextSplitter(
        headers_to_split_on=[("#", "h1"), ("##", "h2")])
    sections = md.split_text(text)
    small = RecursiveCharacterTextSplitter(
        chunk_size=size, chunk_overlap=overlap,
        separators=["\n\n", "。", "\n", ""])
    out = []
    for sec in sections:
        for piece in small.split_text(sec.page_content):
            out.append(Document(page_content=piece, metadata=dict(sec.metadata)))
    return out
```

关键在最后三行：每一块都继承它所属章节的 metadata，检索命中之后仍然知道自己在哪一节，拼装时可以把标题一并带上。如果没有最后三行，标题元数据只留在原始 sections 上，切碎之后全丢。

## 八、边界

没有通用的 chunk_size：政策条款 200 字合适，代码示例 40 行合适，问答对一句话合适。块大小要与嵌入窗口对齐，第 15 章讲过截断：块大于模型窗口时后半段不进向量，切块的上限应该小于窗口。

overlap 不是修复切断的工具，它只降低损失。语义切块成本最高、收益最不确定，它要对每句编码、算相邻距离，先用标题切加递归切解决大部分场景。

切块是不可逆的：块写完进库，改成另一种切法意味着重建索引，这与第 15 章换模型的结论是同一条。块的元数据与块本身一样重要：没有标题模型不知道上下文，没有来源引用点不回原文，没有偏移父块里定位不到答案，没有版本旧引用在重切后失效。

切块的效果还会随文档变化漂移：一份 PDF 转出来的文本没有空行也没有标题，两层结构全部失效，退化到按字符切；这类漂移不报警，只会让新文档的召回率低于老文档，按文档类型分开统计命中率是发现它的办法。

切块上线前有一份五分钟能过完的清单：块边界是否落在句号或段落上；块开头有没有半个词；每块的元数据是否带 `doc_id`、标题、偏移；最长块是否小于嵌入窗口；表格与代码块是否完整；过短的块占比多少。

## 这一章建立的 5 件事

1. 块是检索、引用、预算三者的共同最小单位；切法在向量化之前就决定了召回的上限。
2. 切错的三类后果：句子被切断（答案缺条件）、一块混多个主题（向量被平均）、标题与正文分家（模型不知道上下文）。
3. 五种切法各有约束：Character 忽略 chunk_size 上限、Recursive 尊重语义边界、Markdown 保住标题元数据、tiktoken 按 token 计数、Semantic 在中文上要自己给断句正则。
4. chunk_size 要用命中率扫描来定，判据是"top-1 里有没有答案关键词"；40 字与 80 字之间的差别可以是 40% 对 100%。
5. 父子块用小块检索、大块生成，同时改善召回与上下文；代价是双份存储、两次查找、以及父块可能超出预算。
