## 一、只取 content 的写法

第一版代码几乎都长这样：

```python
from openai import OpenAI


def ask(client: OpenAI, question: str) -> str:
    response = client.chat.completions.create(
        model="demo-model",
        messages=[{"role": "user", "content": question}],
    )
    return response.choices[0].message.content or ""
```

在一个顺利的演示里它能跑通，因为演示时总是问一句话、答一句话。它的失效方式很具体：五种不同的结果，被压成了同一个返回值。下面这段是 `code/knowledge/ch01_call/why_branch.py` 的输出，五次请求都走真实的 `openai` 客户端往返，响应内容由脚本化后端回放：

```
  正常     -> '签收后7天内可退。'
  截断     -> '签收后7天内可退，条件是商品'
  要调工具   -> （空字符串）
  被过滤    -> （空字符串）
  新取值    -> '签收后7天内可退。'
```

五行里只有第一行能直接交出去，其余四行各有各的失效方式。第二行语法通顺，句号也在该在的位置，只是停在逗号后面：拿去展示，读者读到"条件是商品"就没有了；拿去解析字段，解析失败。

空字符串出现两次，原因正好相反：模型要求先做一件事，下一步该执行动作；生成被拦截，重试没有意义。代码只看到空字符串，这两条路径就被当成同一件事处理。最后一行最隐蔽，厂商新增了一个取值，代码没有对应分支，它和第一行走同一条路径，被当成正常答案。

问题不在模型，在于响应体里有一个字段说明这次生成是怎么结束的，而这段代码没读它。那个字段是 `finish_reason`，它不在 `content` 里，也不在消息对象里，而在 `choices[0]` 这一层。它常被当成元数据，实际是关于结果的判断依据。

函数签名也把信息丢了：`-> str`。返回类型宣告只要文本，关于这次生成为什么结束的信息在函数边界上被截断。

## 二、一次调用的往返

要理解 `finish_reason` 为什么能起这个作用，先把一次调用拆成"谁决定什么"。`code/knowledge/ch01_call/lifecycle.py` 用真实的 `openai` 客户端发一次请求，把请求体和响应对象都打出来：

```python
from fake_server import chat_completion, client_for, scripted_server

QUESTION = "能退吗？"


def field_owner(body: dict, response) -> list[tuple[str, str, str]]:
    """把一次调用里真正出现的字段列出来，标注它由谁产生。"""
    choice = response.choices[0]
    usage = response.usage
    return [
        ("messages", f"{len(body['messages'])} 条", "调用方"),
        ("temperature", repr(body.get("temperature")), "调用方"),
        ("max_tokens", repr(body.get("max_tokens")), "调用方"),
        ("finish_reason", choice.finish_reason, "服务端"),
        ("usage", f"{usage.prompt_tokens}+{usage.completion_tokens}={usage.total_tokens}", "服务端"),
    ]


def main() -> None:
    sent: list[dict] = []

    def respond(index: int, body: dict) -> dict:
        sent.append(body)
        return chat_completion("签收后 7 天内可退。", usage=(24, 9))

    with scripted_server(respond) as base_url:
        client = client_for(base_url)
        response = client.chat.completions.create(
            model="demo-model",
            messages=[
                {"role": "system", "content": "你是退货政策助手，只回答与退货相关的政策。"},
                {"role": "user", "content": QUESTION},
            ],
            temperature=0.0,
            max_tokens=64,
            extra_body={"case": "normal"},
        )
```

这段输出说明的第一件事是：请求里只有四类东西，全部由调用方决定。一次调用涉及三方，调用方代码、SDK、服务端，分清三方各管什么，后面每一条排错方向才有依据：

| 角色     | 负责                                                 | 出问题时先看                 |
| -------- | ---------------------------------------------------- | ---------------------------- |
| 你的代码 | 决定 `messages` 的内容与顺序、参数取值、对响应的分支 | 请求体里的字段是不是你想发的 |
| SDK      | 把参数编码成 HTTP 请求、解析响应体、按默认值重试     | 请求次数、异常类型、超时     |
| 服务端   | 生成、统计 `usage`、给出 `finish_reason`             | 响应体原文                   |

表里最实用的地方是第三列：遇到问题先确定它属于哪一行，再动手。把服务端返回的 `length` 当成 SDK 的问题去升级依赖，或者把自己的参数错误当成服务端问题去换服务商，都是这一步跳过的后果。

| 请求字段                | 谁决定 | 决定什么                       |
| ----------------------- | ------ | ------------------------------ |
| `messages`              | 调用方 | 模型收到的文本，按什么顺序排列 |
| `temperature` / `top_p` | 调用方 | 从概率分布里怎么取样           |
| `max_tokens`            | 调用方 | 最多允许生成多少个 token       |
| `tools`（本例未用）     | 调用方 | 模型可以请求哪些动作           |

响应里同样只有四类东西，全部由服务端产生：

| 响应字段             | 谁产生 | 说明什么                                        |
| -------------------- | ------ | ----------------------------------------------- |
| `message.content`    | 服务端 | 这次生成的文本。可能为空字符串，也可能是 `null` |
| `message.tool_calls` | 服务端 | 模型请求执行的动作。没有时是 `null`             |
| `finish_reason`      | 服务端 | **这次生成为什么结束**                          |
| `usage`              | 服务端 | 本次实际消耗的 token 数                         |

`messages` 是数组而不是单个字符串。`role` 决定一段文本在生成时的位置：`system` 提供背景约束，`user` 是本次输入；数组顺序就是模型收到内容的顺序，改顺序会改变结果。工具结果与历史回复也放进这个数组，对服务端来说它们都只是前文，这也是第 2 章说模型不会忘的原因。

这份输出的来历决定了哪些数字能当证据：请求体和响应都经过真实的 HTTP 与真实的 SDK 解析；但响应内容是脚本化后端按固定脚本回放的，不是模型输出。请求体里多出来的 `"case": "normal"` 给脚本化后端分流用，换真实服务时把 `extra_body` 去掉即可：

```python
from openai import OpenAI

client = OpenAI(base_url="https://你的服务地址/v1", api_key="sk-你自己的key")
```

其余代码一行不动：`messages`、`max_tokens`、`temperature` 的写法和线上一致，换掉客户端就能对着真模型跑。

输出的末尾两行最容易被忽略。`max_retries` 和 `timeout` 不在请求体里，却决定一次调用实际发生了几次 HTTP 往返：默认重试两次意味着一回 `create` 最坏发出三次请求，失败的每一次也可能被计费，而调用方只看到成功那次的 `usage`。账单上的请求数多于 `create` 调用次数时，先看这两行。

四个字段的分工经常被混用。`content` 是这次生成的文本，不是答案：被截断时照样有内容，被拦截时是空字符串，模型要求调用工具时是 `null`。`usage` 是实际值，由服务端统计，也是第 3 章校准 token 估算的唯一依据。`finish_reason` 是过程记录，不是质量评价。`tool_calls` 与 `content` 互斥，产物要么是文本，要么是动作。

`model_dump()` 里其余字段本次全为 `null`，是这次生成没用到它们。其中 `system_fingerprint` 标识后端配置版本，这正是第 2 章要讲的温度 0 不等于可复现：后端换了配置，同样的请求会给出不同结果。

因此判断一份响应能不能用，不能只看 `content` 是否为空，还要看这几个配套字段。

## 三、协议层的对照

`client.chat.completions.create(...)` 这一行背后是什么，决定了排错时能从哪里下手。`code/knowledge/ch01_call/protocol_layer.py` 不用 SDK，用标准库的 `http.client` 手发同一条请求：

```python
import http.client
import json


def build_request(case: str, max_tokens: int = 64) -> dict:
    """客户端发出的请求体。SDK 的每个参数都落在这里。"""
    return {
        "messages": [
            {"role": "system", "content": "你是退货政策助手，只回答与退货相关的政策。"},
            {"role": "user", "content": "能退吗？"},
        ],
        "temperature": 0.0,
        "top_p": 1.0,
        "max_tokens": max_tokens,
        "metadata": {"case": case},
    }


def call(port: int, request: dict) -> dict:
    conn = http.client.HTTPConnection("127.0.0.1", port, timeout=5)
    payload = json.dumps(request, ensure_ascii=False).encode()
    conn.request("POST", "/v1/chat/completions", payload,
                 {"Content-Type": "application/json"})
    data = json.loads(conn.getresponse().read())
    conn.close()
    return data
```

它打出来的三段分别是请求体、响应体、四个取值的对照：

```
请求体（http.client 手发，未经 SDK）
{
  "messages": [
    {
      "role": "system",
      "content": "你是退货政策助手，只回答与退货相关的政策。"
    },
    {
      "role": "user",
      "content": "能退吗？"
    }
  ],
  "temperature": 0.0,
  "top_p": 1.0,
  "max_tokens": 64,
  "metadata": {
    "case": "normal"
  }
}

响应体（HTTP 响应的原始字节）
{
  "id": "chatcmpl-demo",
  "object": "chat.completion",
  "created": 1730000000,
  "model": "demo-model-2024",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "签收后 7 天内可退。"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 24,
    "completion_tokens": 9,
    "total_tokens": 33
  }
}

四个取值的原始 JSON 里各有什么：
  normal    stop            usage=24+9   content='签收后 7 天内可退。'
  truncated length          usage=24+16  content='签收后 7 天内可退，条件是商品'
  tool      tool_calls      usage=58+19  content=None
  filtered  content_filter  usage=24+0   content=''
```

对照的结论只有一句：SDK 没有做别的事，它把上面那二十行参数化成一个方法调用，再把响应包装成对象。一次调用在网络上就是一条 HTTP POST，请求体是一段 JSON，响应体也是一段 JSON。

有两个直接用处。排错：SDK 的异常类型只覆盖它认识的错误形状，遇到畸形响应体时真实内容在 HTTP 响应体里，绕过 SDK 打一次能看到原文。对账：代理或网关改写响应体时 `usage` 会跟着变。

不主张手写 HTTP 的理由是手写版没有连接复用、重试与流式分帧解析。它的价值是在出问题时能把 SDK 剥掉，自己发一遍确认协议形状。

## 四、四个取值

`finish_reason` 的四个常见取值，对应四种不同的中止原因。`code/knowledge/ch01_call/four_finish.py` 把四种都跑了一遍，每次都是一次真实的 SDK 往返：

```python
TOOL_CALLS = [
    {
        "id": "call_abc",
        "type": "function",
        "function": {"name": "get_order", "arguments": '{"order_id": "A1001"}'},
    }
]

SCRIPTS = {
    "stop": chat_completion("签收后 7 天内可退。", finish_reason="stop", usage=(24, 9)),
    "length": chat_completion("签收后 7 天内可退，条件是商品", finish_reason="length", usage=(24, 16)),
    "tool_calls": chat_completion(None, tool_calls=TOOL_CALLS, finish_reason="tool_calls", usage=(58, 19)),
    "content_filter": chat_completion("", finish_reason="content_filter", usage=(24, 0)),
}


def ask(client, case: str):
    """一次完整的往返：请求进、响应对象出。"""
    return client.chat.completions.create(
        model="demo-model",
        messages=[{"role": "user", "content": QUESTION}],
        temperature=0.0,
        max_tokens=64,
        extra_body={"case": case},
    )
```

输出里每个值都是从响应对象上读出来的：

```
=== case=stop ===
  finish_reason   'stop'
  content         '签收后 7 天内可退。'
  tool_calls      None
  usage           prompt=24 completion=9

=== case=length ===
  finish_reason   'length'
  content         '签收后 7 天内可退，条件是商品'
  tool_calls      None
  usage           prompt=24 completion=16

=== case=tool_calls ===
  finish_reason   'tool_calls'
  content         None
  tool_calls      [ChatCompletionMessageFunctionToolCall(id='call_abc', function=Function(arguments='{"order_id": "A1001"}', name='get_order'), type='function')]
  usage           prompt=58 completion=19

=== case=content_filter ===
  finish_reason   'content_filter'
  content         ''
  tool_calls      None
  usage           prompt=24 completion=0
```

四个取值放在一起，各自的产物一目了然：

| 取值             | 谁中止了生成            | `content` | 产物             |
| ---------------- | ----------------------- | --------- | ---------------- |
| `stop`           | 模型输出了结束标记      | 文本      | 完整文本         |
| `length`         | 服务端数到 `max_tokens` | 文本      | 不完整文本       |
| `tool_calls`     | 模型决定先要外部数据    | `None`    | 一个待执行的动作 |
| `content_filter` | 服务端的内容过滤        | `''`      | 无               |

输出里还有一个容易看漏的细节，它是实测的：`tool_calls` 情况下 `content` 是 `None`，`content_filter` 情况下是空字符串 `''`。两者打印出来都像没内容，在 SDK 对象里却是两个类型：`None` 表示没有产出文本，`''` 表示产出了文本、长度为零。客户端通常用 `content or ""` 抹平这个区别，抹平之后，去执行动作和该中止这两条路径就只剩一条。

### 4.1 流式里的收尾

`stream=True` 时，一次调用被拆成多个 chunk 依次返回。正文散在 `delta.content` 里，`finish_reason` 不在正文那一块。`code/knowledge/ch01_call/stream_finish.py` 走一次真实的流式往返：

```python
def respond(index: int, body: dict) -> dict:
    """拼一份 SSE 响应体：三个正文块 + 一个只带收尾原因的块。"""
    sse = [
        {"id": "chatcmpl-demo", "object": "chat.completion.chunk", "created": 0,
         "model": "demo-model",
         "choices": [{"index": 0, "delta": piece, "finish_reason": None}]}
        for piece in PIECES
    ]
    sse.append({
        "id": "chatcmpl-demo", "object": "chat.completion.chunk", "created": 0,
        "model": "demo-model",
        "choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}],
        "usage": {"prompt_tokens": 24, "completion_tokens": 6, "total_tokens": 30},
    })
    return {"_sse": sse}


def main() -> None:
    with scripted_server(respond) as base_url:
        client = client_for(base_url)
        stream = client.chat.completions.create(
            model="demo-model",
            messages=[{"role": "user", "content": QUESTION}],
            temperature=0.0,
            max_tokens=64,
            stream=True,
            stream_options={"include_usage": True},
        )
```

它输出四行，前三个 chunk 有正文，第四个没有：

```
  chunk 0: delta='签收后'       finish_reason=None    usage=None
  chunk 1: delta=' 7 天内'     finish_reason=None    usage=None
  chunk 2: delta='可退。'       finish_reason=None    usage=None
  chunk 3: delta=None        finish_reason='stop'  usage=有

拼接后的文本：'签收后 7 天内可退。'
收尾原因：'stop'
正文分在三块里，第四块的 delta 是空的，只带收尾原因与用量。
```

这段输出说明三件事。`finish_reason` 是流式响应里的最后一个事件，判断流有没有正常读完要看最后一个 chunk 的取值，中途断连时它不出现。`usage` 默认不随流返回，要它必须显式传 `stream_options={"include_usage": True}`，不传的话 `usage` 全是 `None`，计量在第 3 章就断了依据。正文要自己拼，流式里 `content` 是一串增量，拼错不会有异常，只会少字。

## 五、取值的来历

四个取值不是随意定的，它们对应生成过程里三个可以中止的位置，加上一条不生成正文的分支。

生成是一个循环：每一步算出一个 token 的概率分布，取一个追加到输出，再算下一步。中止只能发生在三个地方：模型算出结束标记的概率最高、已经生成了 `max_tokens` 个、服务端检测到违规内容。`code/knowledge/ch01_call/generation_loop.py` 把这段过程写成可运行的循环：一段完整回答被切成片段，逐片生成，遇到停止条件就收尾。

```python
# 一段完整的回答，被切成若干片段
FULL_ANSWER = ["签收后", "7", "天内", "可退", "，", "条件", "是", "商品", "未", "拆封", "。"]

# 内容过滤的触发词
FILTER_WORDS = {"拆封"}


def generate(max_tokens: int, want_tool: bool = False, filter_on: bool = False) -> Reply:
    """从片段序列逐片生成，遇到停止条件就收尾。"""
    if want_tool:
        # 模型判断需要外部数据，于是不生成正文
        return Reply(content="", finish_reason="tool_calls", tool_calls=["get_order"])

    out: list[str] = []
    for i, piece in enumerate(FULL_ANSWER):
        # 条件一：达到输出上限，立刻截断
        if i >= max_tokens:
            return Reply("".join(out), "length", produced=i, limit=max_tokens)

        # 条件二：服务端在生成过程中做内容过滤
        if filter_on and piece in FILTER_WORDS:
            return Reply("".join(out), "content_filter", produced=i, limit=max_tokens)

        out.append(piece)

    # 条件三：模型生成完并输出结束标记（本例里就是片段走完）
    return Reply("".join(out), "stop", produced=len(out), limit=max_tokens)
```

同一段回答，只改输出上限，收尾原因就变了：

```
同一段回答，只改输出上限：
  上限 64  content='签收后7天内可退，条件是商品未拆封。'  (stop, produced=11)
  上限 5   content='签收后7天内可退，'  (length, produced=5)
  上限 6   content='签收后7天内可退，条件'  (length, produced=6)

另外两条路径：
  要调工具  content=''  (tool_calls, tool_calls=['get_order'])
  被过滤    content='签收后7天内可退，条件是商品未'  (content_filter, produced=9)

收尾发生的位置：
  上限      收尾原因            已生成片段       内容
  64      stop            11          '签收后7天内可退，条件是商品未拆封。'
  5       length          5           '签收后7天内可退，'
  6       length          6           '签收后7天内可退，条件'
  None    tool_calls      0           ''
  64      content_filter  9           '签收后7天内可退，条件是商品未'

上限 5 与上限 6 都是 length，但截断的位置不同：一个停在逗号后，一个停在词中间。
服务端不判断内容是否完整，它只数到上限就停。
```

（这一段是过程模拟，不是模型实测。）上限 5 和上限 6 都是 `length`，截断位置不同：一个停在逗号后，一个停在词中间。`length` 是正常的中止原因，它只说明还有话没说完，至于说到哪里算完整，服务端不判断。三个中止位置的触发者不同，这一点决定了排错方向：

- `stop` 由模型的结束标记触发。模型给出的标记可能不符合调用方的预期，但它仍然是模型侧的判断。
- `length` 由服务端的计数触发。服务端不判断内容是否完整，它只数到上限就停。
- `content_filter` 由服务端介入。它可能发生在生成过程中，也可能发生在生成之后。

结束标记本身也是一个 token：它占用输出额度，上限刚好时模型说完内容却放不下结束标记，于是得到 `length` 而不是 `stop`；它是模型算出来的，不是服务端代填的。文本看起来完整与收尾原因是 `stop` 不是等价条件，原因就在这里。

循环里还有一个细节：三个条件的检查顺序有讲究。上限检查放在过滤检查之前，因为前者在每一步开头，一旦达到就结束本次生成。真实服务端里这个顺序由厂商决定，能观察到的只是结果：同一份输入有时得到 `length`，有时得到 `content_filter`。所以这两个取值不能用输入去推断，只能按响应里的实际值分支。

`tool_calls` 是第四条路径，但它不是中止，是换了个产物类型。请求里带了工具清单时，模型可以输出一个动作请求来替代正文，这时没有正文可读。

理解这三处的分工，就能明白 `length` 为什么不能靠看文本结尾有没有句号来判断要不要续写。`code/knowledge/ch01_call/completeness_heuristic.py` 拿了七种真实会出现的结尾，逐个比对标点法和收尾原因：

```

--------------------------------------------------------------------------------------------
'签收后 7 天内可退。'                     stop           完整      正常完整
'签收后 7 天内可退。'                     length         完整      刚好在句号处被掐断
'签收后 7 天内'                        length         不完整     半句话
'签收后 7 天内可退，条件是商品'                length         不完整     半句话
'可以。'                             length         完整      短答案，被掐在完整句之后

标点法与 finish_reason 不一致的：3 / 7

  '①'                                finish_reason=stop            模型输出结束标记，但内容是列表符号
```

前几行说明问题所在：头两行文本完全相同，收尾原因不同，一个能直接交出去，另一个必须补全，只看文本区分不了。标点法在七行里错了三行：两行是标点看起来完整、实际被掐断，一行是标点看起来不完整、生成其实正常结束。最后一行是另一种情况，收尾原因是 `stop` 而内容只有一个列表符号，生成正常结束与内容有用是两件事。

## 六、stop 的含义

`stop` 只是说模型输出了结束标记。模型完全可能输出一个完整的、语法通顺的、但内容错误的句子，然后正常结束。一份这样的响应长这样（示意，不是某次运行的结果）：

```
问：订单 A1001 什么时候到？
答：预计 3 天后到。（stop）
```

回答的 `finish_reason` 是 `stop`，格式正常，但答案可能是错的，比如订单实际已经签收。`finish_reason` 判断的是生成过程，不是内容正确性，后者要靠外部判据。

`stop` 还有一个容易忽略的来源：调用方自己传的 `stop` 参数。请求里带 `stop=["\n\n"]` 时，模型生成到这个字符串就停，收尾原因同样是 `stop`。同一个取值下有两种情况，模型算出了结束标记，或者文本命中了调用方给的停止词，响应里没有字段区分，只能自己记录这次请求带没带 `stop`。

误判的后果是：代码把 `stop` 当成自然说完时，带 `stop` 参数的调用会把在停止词处被切误当成说完了。停止词通常用来切段，切出来的文本往往不完整。给请求加了 `stop` 参数，就不能再用这个取值证明内容完整。

## 七、四种取值的处理

四个取值对应四种处理，没有一种可以省略。`code/knowledge/ch01_call/branches.py` 拿同一批响应对象，按收尾原因分支：

```python
def decide(response) -> tuple[str, str]:
    """拿到响应，返回（下一步动作，理由）。最后一支是兜底。"""
    choice = response.choices[0]
    reason = choice.finish_reason

    if reason == "stop":
        return "接受", "文本已完整，直接使用"
    if reason == "length":
        return "续写或重来", "文本被截断，需要续写或放宽上限"
    if reason == "tool_calls":
        names = [c.function.name for c in choice.message.tool_calls or []]
        return "执行工具", f"需要执行 {names}，再回灌结果"
    if reason == "content_filter":
        return "中止", "被内容过滤拦截，重试无效"
    return "未知", f"未处理的取值：{reason}"
```

输出里第五行是兜底分支的实测结果，服务端返回了一个不在这四个里的取值：

```
  情况    finish_reason    动作        理由
  正常    stop             接受        文本已完整，直接使用
  截断    length           续写或重来     文本被截断，需要续写或放宽上限
  要调工具  tool_calls       执行工具      需要执行 ['get_order']，再回灌结果
  被过滤   content_filter   中止        被内容过滤拦截，重试无效
  新取值   unknown_value    未知        未处理的取值：unknown_value
```

为什么恰好是这四种动作：动作由产物类型决定，不由措辞决定。产物是完整文本时只有一件事要做，用；不完整文本要补；动作类型要执行；无产物只能中止。

分支必须有一个兜底，而且兜底要默认拒绝。没有兜底时，新取值会走进某个意外的分支，通常是被当成成功处理，因为所有 `if` 都不成立时代码继续往下走。升级 SDK 或换服务商都不在调用方控制之内，这类失效只是时间问题。兜底返回未知而不是接受，代价是偶尔要人工看一眼日志，换来的是新取值立刻暴露。

还有一层：未知取值要不要透传给上层。透传让上层看到细节，但调用方就得知道所有厂商的取值集合；不透传、统一归成未知失败，排查时得回到这一层看日志。建议是不透传，但在日志里留下原始取值。

## 八、length 的三种补法

`length` 是四个取值里唯一有救的：内容不完整，但可以补。补的方式有三种，代价不同。`code/knowledge/ch01_call/handle_length.py` 三种都实现了，全部走真实 SDK 往返：

```python
def cut_at_sentence(text: str) -> str:
    """本地找最后一个句号，丢掉之后的部分。不产生新调用。"""
    for i in range(len(text) - 1, -1, -1):
        if text[i] in END_MARKS:
            return text[: i + 1]
    return ""


def seam_overlap(prefix: str, tail: str, window: int = 6) -> int:
    """续写的接缝检查：尾巴开头有多少字与正文结尾重复。"""
    for k in range(min(window, len(tail), len(prefix)), 0, -1):
        if prefix.endswith(tail[:k]):
            return k
    return 0
```

三种方案的完整结果：

```
原始：'签收后7天内可退，条件' (length, 上限=6)
  completion_tokens=6  prompt_tokens=24

方案一 直接截到最后一个完整句：
  ''  丢弃 11 个字  调用次数 1

方案二 放宽上限重来：
  '签收后7天内可退，条件是商品未拆封。'  (stop)  调用次数 2
  新增 7 字，但重算了前面 11 字的生成
  两次 prompt_tokens 合计 48，输入全文各计一次

方案三 续写：
  '签收后7天内可退，条件是商品未拆封。'  (stop)  调用次数 2
  只补了 7 字，接缝重叠 0 字
  两次 prompt_tokens 合计 54，第二次只多带了已生成的部分

对照：
  方案        调用次数      产出字符      输入 token 合计   备注
  一 截断      1         0         24            丢失后半句
  二 重来      2         18        48            整段重算
  三 续写      2         18        54            需处理接缝
```

方案一的结果是空字符串。截断的文本里没有任何句号，按截到最后一个完整句的规则，一个字都留不下。这条规则只在长文本且有多处句号时有效。

代价差异在最后两列上：调用次数决定请求次数，输入 token 合计决定钱。两者都调了两次，但方案二每次都把整段提示词重发一遍（24+24=48），方案三第二次带上了已生成的 11 字（24+30=54）。方案三反倒更贵一点，它的优势是只让服务端生成缺的那部分：输出越长、输入越短，差距越大。

| 方案         | 做法                                   | 代价                                   | 什么时候用                     |
| ------------ | -------------------------------------- | -------------------------------------- | ------------------------------ |
| 截到完整句   | 本地找一个句号，丢弃之后的部分         | 零调用，但丢失信息                     | 只需要大意，且丢失部分无关紧要 |
| 放宽上限重来 | 提高 `max_tokens` 重新请求             | 重算整段，输入与已生成部分都要重新计费 | 输出长度不可预测，且必须完整   |
| 续写         | 把已生成文本作为助手消息追加，请求继续 | 只补缺少的部分，但要处理接缝           | 长输出，重算成本高             |

三个方案各有一个陷阱。截断发生在任意位置：一个句号都没有就只能整段丢弃，有多个句号时截到哪一个取决于要多少，不保证留下的是核心内容。重来意味着前面生成的 token 全部作废，但又已经付过费。续写要求模型接着上文写，而它可能重复上文，`seam_overlap` 就是为接缝准备的：比较新生成的开头与已有结尾有没有重叠。

三种都不是标准答案，选择取决于两件事：这段文本是要展示还是要解析，以及输出长度的可预测程度。更根本的一条是，这三种补法都不该被当成常规路径。同一个提示词反复触发 `length`，说明上限或输出结构本身不合适，把上限调到覆盖真实长度分布的上沿，比在调用方反复补救便宜得多。真实长度分布要靠采样统计：记下每次的 `completion_tokens`，取足够高的分位点作为上限。上限是可测的，不该是猜的。

## 九、过滤的两个来源

`content_filter` 看起来是一个取值，实际有两种来源，处理方式相反。来源一是输入端被拦：请求里的内容触发了策略，服务端直接拒绝处理，`completion_tokens` 为 0，没有生成。来源二是输出端被拦：生成到一半或生成完成后输出触发策略，`completion_tokens` 大于 0。`code/knowledge/ch01_call/four_finish.py` 的输出里，两行正好各是一个例子：

```
=== case=content_filter ===
  usage           prompt=24 completion=0

=== case=stop ===
  usage           prompt=24 completion=9
```

`completion_tokens` 为 0 说明模型没有产出任何 token，这是输入端被拦的可靠信号。两者的区别决定了一件事：输入端被拦时改写提示词可能有效，输出端被拦时改写提示词通常无效，因为触发内容是模型生成的。这条区分不属于 `finish_reason` 的语义，它靠 `usage` 补出来：收尾原因说明怎么结束的，`usage` 说明结束之前干了多少活，两件事拼起来才能判断该不该重试。

落到代码里，过滤这一支要做的事只有三件：记下 `usage` 的两个数字判断来源、记下收尾原因判断分支、不要进重试循环。第三件最容易被写错，因为内容为空就重试是一条很自然的直觉，在这里是纯粹的浪费。

输入端被拦的判定依赖 `completion_tokens == 0`，但有些服务端仍会返回一个很小的非零值，或者在响应体里省掉 `usage`。这时判定不能只看数字，还要看响应里有没有 `content` 之外的解释字段，这条只能按服务商文档逐个确认。

## 十、参数的字符串形式

前四个取值处理的是文本够不够用。`tool_calls` 不是，它意味着这次调用的产物不是文本。`code/knowledge/ch01_call/four_finish.py` 输出里那条 `tool_calls` 原文：

```
[ChatCompletionMessageFunctionToolCall(id='call_abc', function=Function(arguments='{"order_id": "A1001"}', name='get_order'), type='function')]
```

三个细节决定了后续代码怎么写。`content` 是 `None` 而不是空字符串，含义是没有为这次生成产出文本。`arguments` 是字符串而不是对象，它的值是 `'{"order_id": "A1001"}'`，一段 JSON 编码后的文本，要拿到 `order_id` 必须再解析一次，这是下一级解析失败的主要来源：字符串可能不是合法 JSON，可能缺字段，可能类型不对。`id` 用于配对，执行完动作要把它放进一条 `role="tool"` 的消息里并标明对应哪一次请求；少这个字段多轮里就无法配对，配错时不会报错，只会让模型拿着别人的内容继续推理。

### 10.1 为什么是字符串

字符串参数是接口设计的结果，不是实现缺陷。参数的形状由调用方在 `tools` 里声明，服务端不解析它的语义，用字符串传递，它就不需要理解调用方定义的结构。字符串可以容纳任意结构而对象不行，参数里可能嵌套数组与特殊字符，序列化成字符串是唯一与 schema 无关的传递方式。

代价落在客户端：每一次拿到参数都要解析，而解析可能失败。所以在 `tool_calls` 分支里，正确顺序是这样（示意）：

```
1. 校验 finish_reason == "tool_calls"
2. 遍历 tool_calls，逐个解析 arguments
3. 解析失败 -> 把错误信息作为工具结果回灌，让模型重试
4. 解析成功 -> 执行，按 id 与请求配对
```

第 3 步是关键：解析失败不抛异常终止，是把失败原因告诉模型，让它重新给出参数。`arguments` 是模型生成的文本，模型可能生成不合法的 JSON，这和第 2 章讲的输出是采样结果是同一件事。

## 十一、四种误判

分支写错不会立刻报错。四种取值配上错误的分支，表现各不相同，其中两种几乎无法通过测试发现。

### 11.1 截断被当成完整

代码只判断 `content` 非空，`length` 就会走进成功路径。界面上显示的是这样一句（示意）：

```
签收后 7 天内可退，条件是商品
```

截断的文本语法完整，只是少了半句。它不会抛异常，日志里没有错误，监控指标一切正常，唯一能发现它的方式是比对收尾原因和实际使用的分支是否一致。代价取决于下游怎么用这段文本：只展示时回答显得简略，要解析字段时会随机出现解析失败，且只在长回答时出现。

### 11.2 待执行动作被当成空回答

`tool_calls` 情况下 `content` 是 `None`，经过 `content or ""` 之后变成空字符串，被当成模型没生成内容返回。用户看到的是一个空白回答，这时如果有重试逻辑就会重试，重试得到同样的结果，因为模型每次都会要求调用工具。重试次数耗尽后报模型无响应，而真实原因是没有执行工具并把结果送回去。

这个错误的特征是日志里有一串相同的请求，每次响应都是空的，没有异常，这时该去查收尾原因的取值分布。

### 11.3 被拦截当成长度问题

拦截返回空字符串，如果分支写成了内容为空就重试，会反复重试一个不会成功的结果。更糟的是把 `content_filter` 归类成生成失败，然后切到降级模型：降级模型面对同样的内容通常也会被拦，拦的是内容，不是模型。

判据是：某个请求的重试次数总是恰好等于上限，且每次结果都为空，先确认是不是 `content_filter`。它与模型能力不足的区别在于，前者对任何模型都一致，后者换模型可能缓解。

### 11.4 新取值落进成功路径

分支用 `if/elif` 写四种取值，没有 `else`。厂商新增一个取值时，代码走完所有判断后继续向下执行，落到正常处理。这一种和截断被当成完整表现相同：一切看起来正常，只是行为不对。唯一可靠的做法是让分支默认拒绝，未知取值应当走进一个显式的错误路径。

`branches.py` 的兜底分支返回的是未知和未处理的取值。新增取值的正确反应是让人看到它，而不是猜它。

### 11.5 为什么测试发现不了

四条误判有两个共同点，它们正好绕开了常规测试。输入与输出都合法：没有异常、没有超时、没有空指针，而测试通常断言返回不为空，截断的输出恰恰不为空。触发条件是概率性的：截断只在回答够长时发生，`tool_calls` 只在请求带工具清单时发生。

能拦住它们的不是更多用例，而是把收尾原因写进断言：任何一条用例都同时校验文本对不对和收尾原因是不是预期的那个，后者可以机械地全量覆盖。构造用例的办法也很直接：把 `max_tokens` 设成一个必然不够用的值，就得到稳定的 `length` 用例；把 `tools` 传进去但不执行任何工具，就得到稳定的 `tool_calls` 用例。这两种情况手工点测最不容易遇到，却恰好是线上最常出问题的地方。

### 11.6 四种误判的区分

把它们放在一起，是因为它们的信号完全不同，排查方向也不该相同：

| 失效                    | 表面现象               | 日志特征                              | 该查什么             |
| ----------------------- | ---------------------- | ------------------------------------- | -------------------- |
| `length` 当 `stop`      | 回答偏短，解析偶发失败 | 无异常，`completion_tokens` 接近上限  | 分支代码与实际取值   |
| `tool_calls` 当答案     | 空白回答，重试无效     | 多次相同请求，响应为空                | 是否漏了工具执行     |
| `content_filter` 当长度 | 重试打满，每次为空     | `completion_tokens` 为 0 或远小于预期 | 输入还是输出被拦     |
| 无兜底                  | 新场景下行为异常       | 无不寻常记录                          | 响应里有未处理的取值 |

## 十二、这套分支的边界

`finish_reason` 能回答这次生成是怎么结束的，四类问题它回答不了。内容对不对：`stop` 配上错误内容是正常组合，正确性要靠外部判据。生成质量如何：它只记录被谁停下的，不记录离完整还差多少。该不该重试：取值能提示方向，策略还要看一次重试要花多少钱、会不会带来重复副作用。多厂商一致性：各家取值集合不同，有的厂商把命中停止词和自然结束都归到 `stop`，直接透传会在换厂商时出现未处理分支，这一层要靠显式的取值映射表。

### 12.1 单次生成与整轮任务

`finish_reason` 是单次生成的记录，不是整轮任务的记录。加了循环之后，每一步都有各自的取值，需要汇总成这个任务是否完成。两者不能混为一谈，因为同一个取值在两个层面含义不同：

| `finish_reason` | 在单次生成里               | 在整轮任务里                                 |
| --------------- | -------------------------- | -------------------------------------------- |
| `tool_calls`    | 这次没生成正文，要执行动作 | 正常推进，任务还在进行                       |
| `length`        | 这次被截断                 | 可能只是某一步说得太长，任务本身没问题       |
| `stop`          | 这次生成完整结束           | 可能是任务的终点，也可能只是中间某一步的终点 |

把单次的 `stop` 当成任务完成，会导致循环提前退出；把单次的 `tool_calls` 当成失败，会导致循环无法进行。这两个错误在第 7 章会具体展开。

结论只有一条：这一章建立的分支处理的是"一次生成"，不是"一次任务"。`decide` 这类函数的返回值不能直接当循环的退出条件：`tool_calls` 在一次生成里是没产出正文，在循环里却是继续执行；`stop` 在一次生成里是完成，在循环里可能只是这一轮答完了。两层判断必须分开写，内层判一次生成能不能用，外层判整个任务该不该停。

### 12.2 两个上限

`max_tokens` 和上下文窗口是两个不同的限制，混淆它们会导致一类特定的失败：请求在生成开始之前就被拒绝，而代码把它当成生成失败去重试。`code/knowledge/ch01_call/two_limits.py` 用一组固定数值演示这个区别（数值是演示用常量）：

```
上下文窗口 = 8192，输出上限是预留值，不是实际产出。

    输入 token      上限        两者之和  结果          说明
------------------------------------------------------------------------------------------------
         100     256         356  正常          输入与上限之和在窗口内
        4000     256        4256  正常          输入与上限之和在窗口内
        8000     256        8256  请求被拒        输入 8000 + 上限 256 = 8256 > 窗口 8192
        4000    2048        6048  正常          输入与上限之和在窗口内
        4000   12000       16000  请求被拒        输入 4000 + 上限 12000 = 16000 > 窗口 8192
         200      16         216  length 风险高  上限太小，长答案会被截断

两件事要分开：
  1. max_tokens 是本次生成的允许上限，实际产出通常更少。
  2. 但它会连同输入一起占用窗口。设得太大，长输入会被直接拒绝。

第三种情况（输入 8000）：
  输入 8000 已占掉窗口的 97.7%，
  只剩 192 个 token 可给输出，
  默认上限 256 会超出 64，请求在生成开始前就被拒。

这不是 length：length 是生成中途被掐断，这里根本没有开始生成。
```

两件事必须分开。`max_tokens` 是预留量，不是产出量：请求时说最多允许生成 256 个，实际可能只生成 9 个，但窗口按预留算，服务端要在生成开始前确认输入加上限放得下。第三行为什么被拒就是这个原因：8000 加上 256 等于 8256，超出窗口 8192。这个区别在排查时很重要：

| 现象                                   | 属于哪种 | 处理                           |
| -------------------------------------- | -------- | ------------------------------ |
| 生成到一半停了，`finish_reason=length` | 输出上限 | 放宽上限或续写                 |
| 请求直接报错，没有响应体               | 窗口溢出 | 缩短输入，或调小上限           |
| 上限设得过大，长输入全被拒             | 窗口溢出 | 上限应当按"窗口减输入"动态计算 |

实践中最多见的一种是：上限用一个固定的大值，输入短时正常，输入一长就全部被拒。正确做法是上限跟着输入走。

`length` 是生成中途被掐断，窗口溢出是生成没有开始。前者能拿到部分文本，后者拿不到任何文本，代码里这两种情况应当走不同分支。

### 12.3 一次调用与一次计费

最后要说清一个容易被混淆的对应关系：响应对象只有一个，但产生它的 HTTP 往返可能不止一个。第二节那两行客户端默认值说明这件事：重试是客户端行为，服务端不会因为重试而合并计费，所以一次 `create` 花多少钱取决于重试了几次。

流式的情况反过来：`create` 只有一次，`usage` 默认不返回，日志里就没有这次的花费记录。

两种偏差合起来，说明这一章真正的边界：`finish_reason` 与 `usage` 描述的是一次 HTTP 往返，而代码里看到的是一次函数调用。

对账的判据可以现在给出：把一段时间内的请求次数、`create` 调用次数、`usage.total_tokens` 三项放在一起看。三者相等，说明没有重试、没有流式、没有中间层改写；请求次数多于调用次数，先查 `max_retries`；`usage` 全为空，先查流式有没有要 `include_usage`。

## 这一章建立的 6 件事

1. 一次调用分四部分：请求里是消息、采样参数、输出上限、工具清单，全由调用方决定；响应里是内容、动作、收尾原因、用量，全由服务端产生。
2. 一次调用在网络上就是一条 HTTP POST，SDK 只负责编码请求体、解析响应体；`model_dump()` 打出来的字段就是响应体的字段。
3. `finish_reason` 记录生成是怎么结束的，四个常见取值对应四种不同的产物类型：完整文本、不完整文本、待执行动作、无产物。
4. `stop` 只说明输出了结束标记，不说明内容正确；内容正确性需要外部判据。
5. 只看 `content` 的写法会把"截断""被拦截""要调工具""新取值"压成正常返回值，其中截断最难发现，因为不报错。
6. `max_tokens` 与上下文窗口是两个限制：前者决定生成能否完成，后者决定生成能否开始；窗口按"输入 + 预留输出"计算。
