## 一、钱花在哪

一次任务的总成本是一个数，但不拆开，所有优化都只能试试看。`cost_waterfall.py` 是一个把任务成本按阶段拆开的脚本，一次十二步任务的瀑布长这样：

```python
@dataclass
class Stage:
    name: str
    input_tokens: int
    output_tokens: int
    cache_tokens: int = 0

    @property
    def cost(self) -> float:
        return (self.input_tokens * PRICE["input"]
                + self.output_tokens * PRICE["output"]
                + self.cache_tokens * PRICE["cache"]) / 1_000_000
```

```
=== 1. 一次任务的成本瀑布 ===
  阶段                    输入     输出     缓存      成本(元)      占比
  路由                   900     80      0   0.001220    2.2%
  检索改写                2400    120      0   0.002880    5.1%
  生成（主回答）            16000   900   6000   0.020200   35.8%
  子 agent 汇总         18000   520      0   0.020080   35.6%
  自审                  9000    300   4000   0.010600   18.8%
  格式化输出               1200     60      0   0.001440    2.6%
  合计                 47500   1980  10000   0.056420  100.0%
```

这段说明了什么：总额零点零五六元，分布极不均匀：生成与子 agent 汇总各占三成六，自审占一成九，其余三段加起来不到一成。只看总额，无法知道该动哪一段。

### 1.1 瀑布怎么读

第一眼看哪一段最大：生成与子 agent 汇总几乎相同，自审第三。第二眼看哪一段可以省：三段的省法不同。

| 阶段 | 为什么贵 | 能怎么省 |
|---|---|---|
| 生成（主回答） | 上下文 16000 是全部检索结果 | 裁剪上下文、提高缓存命中 |
| 子 agent 汇总 | 它读了 18000 的原文 | 减少交给它的材料、缩小任务 |
| 自审 | 它把回答与依据又读了一遍 | 只在关键步自审，或用规则裁判 |

第三行是这一章最值得注意的一处：自审占一成九，而它的收益是少一次返工，如果返工率只有百分之五，自审的成本可能超过它省下的钱。第一行的缓存六千也是一个信号：缓存只覆盖了一万六输入里的六千，说明前缀复用得不够，命中率提上去，这一阶段的成本能降一截。

**三级预算。** `cost_waterfall.py` 的第二段输出把三个尺度排开：

成本要在三个尺度上各有一个上限，缺一个就会出现单次花费很低、月度总额翻倍：

```python
checks = [("单任务", total, TASK_BUDGET),
          ("单租户/日", TENANT_DAILY * 0.82, TENANT_DAILY),
          ("平台/月", MONTHLY * 0.74, MONTHLY)]
for name, used, limit in checks:
    print(f"  {name:<10}已用 {used:>8.2f} / {limit:<8.2f}"
          f"（{used / limit:>6.1%}）{' 超限' if used > limit else ''}")
```

```
=== 2. 三级预算 ===
  单任务       已用     0.06 / 0.08    （ 70.5%）
  单租户/日     已用     4.92 / 6.00    （ 82.0%）
  平台/月      已用    88.80 / 120.00  （ 74.0%）
  <- 单任务只占日预算的 0.94%，但日预算已用 82%：真正该管的是租户级
```

| 级 | 管什么 | 超了怎么办 |
|---|---|---|
| 单任务 | 一次运行的失控 | 中止该任务 |
| 单租户/日 | 一个客户的用量 | 降级到便宜路径，或拒绝 |
| 平台/月 | 整体预算 | 换模型、缩上下文、限流 |

第一级是单任务，阈值通常比平均值高几倍：正常任务零点零五六元，预算零点零八，四成余量给异常长的任务。余量太小会把正常的长任务误杀，太大则失去防失控的意义。第二级是租户日预算，实际最常触发：示例里租户已用八成二，再有一次大任务就会触发。它的处理不该是直接拒绝，而是降级到便宜路径，对客户来说一个稍慢的答案好过一次报错。

第三级是事故级：它触发时所有租户都受影响，处理方式只能是全局降本，换小模型、缩小 top-k、关掉自审，这一级应当有预案。三级的阈值要能互相推导：租户日预算六元、单任务零点零八元，一个租户一天理论上限是七十五次任务，超出这个数就不是用量大。

三级之外还有一个第四级常被忽略：按功能的预算。问答、审批、批处理三类负载的成本结构完全不同，混在一个月度预算里，某一类暴涨会被另一类的节省掩盖。子预算的粒度要按能被谁负责来定：问答由算法团队负责、审批由业务团队负责，预算也按这个切。

### 1.2 语义缓存的三条红线

缓存是最直接的降本手段，`cost_waterfall.py` 的第三段输出里，命中率三成省两成八、六成省五成七。它的三条红线每一条都能把省下的钱变成事故：

```
=== 3. 语义缓存：命中率与红线 ===
  命中率 0% -> 成本 0.056420 元（省 0%）
  命中率 30% -> 成本 0.040340 元（省 28%）
  命中率 60% -> 成本 0.024261 元（省 57%）

  三条红线，各一条具体形态：
  1 缓存键不含租户：A 租户问'我的订单'，命中 B 租户的答案 -> 数据串了
  2 缓存不随文档失效：政策从 15 天改成 7 天，命中旧答案 -> 答了过期政策
  3 命中仍计全额：成本报表按 0 省，实际账单没降 -> 归因失真
```

命中率与节省不是线性的，命中省下的主要是输入侧，收益在高频重复提问上才明显。第一条红线是安全事件，第二条是正确性事件，第三条只是账目问题，但第三条会让前两条更难被发现，因为成本曲线看起来很健康。

正确的键是 `hash(question, tenant, index_version)`：问题决定语义、租户决定数据边界、索引版本决定内容时效。索引版本这一项最容易被忘，文档更新如果没让缓存失效，一次政策修改对命中的流量完全无效，表面上新政策已上线，实际一半请求还在拿旧答案。

### 1.3 成本归因的三个口径

同一笔钱按三种口径拆，回答三个不同的问题：

| 口径 | 拆法 | 回答 |
|---|---|---|
| 按阶段 | 路由、检索、生成、自审 | 该优化哪一段 |
| 按租户 | 每个客户用了多少 | 该向谁收费 |
| 按功能 | 问答、审批、批处理 | 这条产品线值不值 |

第一种是技术视角，第二种是商业视角，第三种是产品视角，三者不能互相替代：按阶段拆不出哪个客户花得多，按租户拆不出哪段代码贵。实际系统里三者用同一份数据、不同的分组维度，这要求 span 上同时带阶段、租户与功能三个标签，第 42 章的扩展字段就是为这个准备的。第三行的值不值最容易吵：一个功能成本占比三成、使用率百分之二，是否该下线？这已经不是成本问题，是产品判断，但没有按功能拆的成本，这个判断连数字都拿不出来。

### 1.4 降本的顺序与易错项

降本不是哪个手段先进用哪个，而是按单位收益与风险排序：

| 顺序 | 手段 | 收益 | 风险 |
|---|---|---|---|
| 1 | 提高缓存命中 | 输入侧直接降 | 失效与串户 |
| 2 | 裁剪上下文 | 按比例降 | 召回下降 |
| 3 | 换小模型 | 单价降 | 质量下降 |
| 4 | 减少自审 | 省一段 | 返工率上升 |
| 5 | 缩 top-k | 输入降 | 召回下降 |

第一行的风险最高但收益最直接，它要求最严的键设计；第二、五行与质量直接冲突，必须同时看第 43 章的召回与精度；第三行的质量损失最难察觉。第四行最容易被误判为纯收益：去掉自审短期指标可能不变，因为返工是概率事件，要积累一段时间才显现，凡是减少一道检查的降本措施，都要设观察窗口。

成本表看起来是加法，但有三项经常算错。第一项是重试，按成功调用记账会把重试的输入 token 全漏掉，一次超时重试的输入可能占这次任务的两成，正确做法是任务成本按成功调用报、预算与账单按全部调用算。第二项是缓存，命中 token 的单价与正常输入不同，把缓存并进输入按原价算，会让缓存上线看起来没有任何收益。第三项是被中断的流，用户关掉页面时模型可能已经生成了一部分，长回答场景下这个差会累积成可见金额。三项的共同点是计费边界与记录边界不一致，对账要做的是把两个边界都写清楚。

### 1.5 按租户与按功能

按阶段拆是技术视角，落地还要租户与功能两个维度。租户维度要求每次调用都带上租户标识，且这个标识要能穿过子 agent 与异步任务，漏传一次的后果是那部分成本落到未知租户里，。功能维度要求入口处打标，它比租户更难，因为一次运行可能跨功能，这时要按谁发起归因。两个维度都要求标签在链路起点注入，中途补的标签只能覆盖一部分 span，聚合时会得到部分归因的结果。

### 1.6 一次降本的完整账

降本方案不能只报省了多少，要同时报四列：省下的钱、掉的质量、增加的风险、回滚的代价。

| 手段 | 省 | 质量 | 风险 | 回滚 |
|---|---|---|---|---|
| 提高缓存命中 | 输入侧 20%–30% | 无（键正确时） | 串户、过期 | 改键即可 |
| 缩 top-k | 按比例 | 召回下降 | 答不完整 | 改配置 |
| 换小模型 | 单价 50%+ | 中等题开始错 | 难以察觉 | 改配置 |
| 减自审 | 一段 | 返工率上升 | 延迟显现 | 加回来 |

第三行的难以察觉是它最危险的地方：换小模型后简单题仍然全对，总分可能只掉两三个点，而那两三个点集中在最难的样本上，要发现它必须按难度分组看指标。第四行的延迟显现指返工是概率事件：去掉自审的当天指标可能完全不变，两周后返工累积，成本反而上升。四列合起来才是完整的账，只报第一列，团队会一路把质量换成成本。

## 二、慢在哪

延迟有两条曲线：用户感知的多快看到第一个字，与任务总时长，两者优化手段不同，混在一起看就会得出优化了一圈只快了一成的结论。`latency_breakdown.py` 是一个延迟分解脚本，把一次四点四秒的请求拆成五段：

```
=== 1. 一次请求的延迟分解 ===
  段               耗时(ms)    累计(ms)     占总量
  排队                 120       120    2.7%
  检索                 400       520    9.0%
  模型首字节              900      1420   20.4%
  生成                2400      3820   54.3%
  工具调用               600      4420   13.6%
  合计                4420      4420  100.0%
  TTFT = 排队 + 检索 + 首字节 = 1420ms
  总延迟 = 4420ms，TTFT 占 32.1%
```

这段说明了什么：生成占五成四，是最大的一段；但用户觉得快不快由 TTFT 决定，而 TTFT 只包含排队、检索与首字节，两个视角看到的是两个瓶颈。

### 2.1 TTFT 与总延迟

| 指标 | 优化手段 | 用户体验 |
|---|---|---|
| TTFT | 减少前置步骤、并行、流式 | 感觉快 |
| 总延迟 | 减少生成长度、换快模型 | 等待结束得早 |

第二行的优化对第一行没有帮助：把生成从两千四百毫秒降到一千二百毫秒，TTFT 仍然是一千四百二十毫秒。反过来，把检索从四百毫秒降到四十毫秒，TTFT 直接降三百六十毫秒，这是流式之外最有效的一类优化。生成占五成四看起来最大，却最不该优先优化：减少生成长度会牺牲完整性，而它在用户感知上已经被流式掩盖了。两条曲线还对应两种验收方式：首字节用用户的感受验收，总时长用任务完成率验收。

**并行化与流式。** `latency_breakdown.py` 的第二段输出把四项优化各算一遍：

```
=== 2. 三种优化各省多少 ===
  检索与工具并行                           4020ms  （省  400ms， 9.0%）
  流式输出（首字节不变）                       4420ms  （省    0ms， 0.0%）
  模型换小一档（首字节 900 -> 500）            4020ms  （省  400ms， 9.0%）
  检索加缓存（400 -> 40）                  4060ms  （省  360ms， 8.1%）
```

这段说明了什么：四项优化每一项都只省百分之九左右，这就是优化一圈只快百分之十的数学原因，总延迟是五段之和，任何一段的优化上限就是它自己的占比。并行化的上限由两段里较短的那一段决定：检索四百毫秒与工具六百毫秒并行能省四百，不是一千，而且它要求两段之间没有数据依赖。流式则一分不省总延迟，改变的是瀑布什么时候被看见。

**降级链。** `latency_breakdown.py` 的第三段输出把主模型超时后的链路走一遍：

```
=== 3. 降级链：主模型超时时 ===
  单次等待预算 2000ms
  主模型         2800ms  质量：正常        超预算，降下一级
  备用模型        5200ms  质量：正常但慢      超预算，降下一级
  语义缓存          80ms  质量：可能过期      采用，链在此停止
  <- 降级不是'换一个更快的'，是'按预算逐级降质量'
```

这段说明了什么：链的顺序按质量从高到低，预算按单次等待时间。主模型两千八百毫秒超了预算，备用模型也超，最后落到缓存，一个可能过期但八十毫秒能给出的答案。三个设计要点：

| 要点 | 做法 | 不做的后果 |
|---|---|---|
| 每级标注质量 | "可能过期""只给原文" | 用户不知道答案降级了 |
| 预算在链外 | 一次请求的总预算 | 逐级重试把预算用光 |
| 命中即停 | 不继续往下试 | 白白多等一次 |

第一行的标注质量要传到界面：可能过期的答案与正常答案应当有不同的提示。第二行是常见错误：每一级各有一个超时，加起来远超总预算，正确做法是先定总预算，再按剩余时间逐级试。第三行看起来显然，实现里却常出错，降级逻辑写成依次调用取最后一个成功的，结果每次都跑完全链。

### 2.2 分位数与联合优化

平均值会骗人：一次请求四点四秒，但如果百分之五的请求要十二秒，用户感受到的是那百分之五。

| 指标 | 含义 | 用途 |
|---|---|---|
| P50 | 一半请求快于它 | 看"典型体验" |
| P95 | 5% 的请求慢于它 | 看"坏体验" |
| P99 | 1% 的请求慢于它 | 看"极端情况" |
| 平均 | 总量除以次数 | 算容量与成本 |

第四行是唯一适合做容量规划的，它对应总时长，但用它描述体验是错的：一个四点四秒的平均值可能来自九成的两秒与一成的二十六秒。分位数的区间要用第 45 章的 bootstrap，它比正态近似可靠。一个实用的判读方式是看 P50 与 P95 的差：差两倍说明偶发慢，差五倍说明系统里有排队或重试。

大多数优化同时改变两个数，只报一个就会把交换说成改进：

| 优化 | 成本 | TTFT | 总延迟 |
|---|---|---|---|
| 检索结果缓存 | 略降 | 降 | 降 |
| 加一轮自审 | 涨 | 涨 | 涨 |
| 换小一档模型 | 降 | 降 | 降 |
| 加长上下文 | 涨 | 涨 | 涨 |

第一行是真正双赢的那一类，也最少：缓存命中省了一次检索的钱与时间。第二行与第四行是用成本换质量，必须同时报第 43 章的四个数，否则看起来就是变慢了、变贵了；换小一档模型看起来双赢，但它掉的是最难样本上的正确率。优化清单里如果全是双赢项，说明没在做真正的取舍。

### 2.3 延迟预算怎么分

给一次请求定总预算之后，预算要往下分到段，否则优化会变成谁嗓门大谁先改。

| 段 | 典型占比 | 预算分配的依据 |
|---|---|---|
| 排队 | 少量 | 超出说明并发打满，是容量问题 |
| 检索 | 一成 | 检索超时要有兜底（走缓存或降 top-k） |
| 首字节 | 两成 | 与模型档位直接相关 |
| 生成 | 五成 | 与输出长度直接相关 |
| 工具 | 一成 | 与下游依赖相关 |

分预算的依据是这一段超了能做什么，不是占比：排队的预算该给容量，检索的预算该给降级，生成的预算该给长度限制；一段超了却没有任何手段，预算是没有意义的。常见的错误是把总预算平均分给五段，平均分忽略了各段波动不同、可控程度不同。预算还要与降级链对齐，两条东西写在两个地方，就会出现降级链以为还有两秒、实际只剩两百毫秒。

### 2.4 串行链路上的头阻塞

一次请求里如果有一段必须等前一段完成，整条链的延迟就是各段之和，这段必须等的位置叫头阻塞，它决定了并行化能省多少。三个模型调用串行各八百毫秒，总延迟两千四；把它们并行理论上限是八百，前提是三次调用互不依赖，而检索与生成之间有依赖。判断能不能并行只问一个问题：后一段的输入里有没有前一段的输出。头阻塞还有一种隐形形态：流式输出里的工具调用，用户在读到一半时流会暂停，这段暂停在总延迟里算一次工具调用，在感知上却是一次卡住。

## 三、事故之后

前两节是常规优化，这一节处理非常规：一次事故已经发生，怎么从它走到不再发生。`postmortem_to_case.py` 是一条从事故记录到回归用例的链路脚本：

```
=== 1. 事故记录 ===
  id      INC-0314
  start   2026-03-14 10:20
  end     2026-03-14 11:05
  symptom 生鲜退货咨询回答'可以退'，实际政策不支持
  impact  37 次会话给出错误承诺
```

**五问法。** `postmortem_to_case.py` 的第二段输出用五问走一遍这次事故：

```
=== 2. 五问法 ===
  问 1：为什么答错？——回答依据的块写着'7 天内可退'，没有生鲜例外
  问 2：为什么依据了那一块？——检索把 15 天版本的旧块排在了第一条
  问 3：为什么旧块还在？——文档更新时新块插入了，旧块只标了 inactive，没有过滤
  问 4：为什么没有过滤？——检索实现里没写 active 条件，靠调用方自觉
  问 5：为什么靠调用方自觉？——入库与检索是两个模块，'失效'语义没有统一在一处
```

五问的目标不是问满五层，而是问到一个可以改结构的位置。问二、问三都还是症状，一个是排序，一个是过滤；问到问五，答案从某处忘了写条件变成两个模块各自定义失效，这才是一个能改的地方。停在忘了加条件的复盘，修复方式是加一个 if，下一次新增一条检索路径，同样的 if 还会漏。

**失败分类。** 同一脚本的第三段输出把它归进四个分类：

```
=== 3. 失败分类 ===
  归到「数据与版本」：旧版本块未过滤、条目过期
  修复方向：检索层加版本过滤，而不是改提示词
```

| 类 | 典型根因 | 修复落点 |
|---|---|---|
| 数据与版本 | 旧块未过滤、条目过期 | 检索与入库 |
| 检索质量 | 召回缺失、排序不当 | 索引、改写、重排 |
| 生成 | 编造、漏要点 | 提示词、引用约束 |
| 编排 | 步数、终止条件 | 循环 |
| 权限 | 越权、审批绕过 | 边界与审批 |
| 基础设施 | 超时、限流、依赖故障 | 部署与容量 |

分类的作用是决定改哪里，以及该找谁。归错类的代价很大：一个数据与版本问题被归成生成，团队会去改提示词，改一周之后指标没动，再回头查检索。分类的判据来自第 43 章的分层指标：检索层不合格就是前三类，生成层不合格才是第四类。没有分层指标，分类只能靠感觉，而感觉倾向于把问题归到自己熟悉的模块。

### 3.1 MTTD 与 MTTR

两个数字衡量出事之后多久能恢复，它们各自指向不同的改进：

| 指标 | 从哪到哪 | 优化手段 |
|---|---|---|
| MTTD（发现时间） | 出错到有人知道 | 告警、监控、用户反馈通道 |
| MTTR（恢复时间） | 知道到恢复 | 回滚、降级、值班流程 |

示例里十点二十出事、十一点零五恢复，四十五分钟，如果 MTTD 占了四十分钟，说明问题在没人发现，再快的修复流程也没用。两个数要分开报：一个团队把 MTTR 从二十分钟压到五分钟，但 MTTD 是四十分钟，用户感知的故障时长仍然是四十五分钟。MTTD 的改进通常比 MTTR 便宜，一条基于错误率突增的告警可能就能把四十分钟压到五分钟；MTTR 的改进依赖回滚能力与值班。

### 3.2 复盘会与复盘文档

一次复盘会要产出四样东西，缺一样它就变成追责会或漫谈会：

| 产出 | 内容 | 不产出的后果 |
|---|---|---|
| 时间线 | 什么时候发生了什么 | 讨论变成回忆 |
| 根因 | 五问走到的那一层 | 修复停在表面 |
| 行动项 | 谁、做什么、什么时候 | 会后没人动 |
| 用例 | 旧配置失败、新配置通过 | 半年后原样复发 |

第一行要在会前准备好，用第 42 章的 trace 与日志拼出来，会上现拼时间线，时间都花在追谁点的。第二行是会议的核心，也是最容易滑向追责的地方，一个可用的规矩是把对事不对人写成具体的问法：不问为什么没加过滤，问检索路径为什么可以不带过滤条件。第三行的谁、什么时候要具体到人能认领，写改进检索等于没有行动项。第四行是下一节的落点，没有用例的复盘等于给同一次事故留了回访日期。复盘会超过一小时，讨论通常会滑向要不要重构。

一份复盘文档要被后来的人读懂，四个字段不能省：

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| 时间线 | 什么时候发生了什么 | 后人只能猜 |
| 影响 | 多少用户、多少成本 | 无法排优先级 |
| 根因 | 问到了哪一层 | 修的是症状 |
| 用例 | 哪条测试挡住了复发 | 半年后复发 |

第二行决定了这次复盘值多少钱花：三十七次会话与三万七千次会话，处理力度完全不同。第四行是这一章的核心：没有用例的复盘，在文档系统里看起来完整，在系统里什么也没留下。一次复盘产出的真正资产只有两样，一条结构化根因与一条可执行的用例。

### 3.3 复盘的三个反模式

第一种是人的问题：结论写成值班同学没有按流程操作，修复动作是加强培训，这类结论并不不真实，只是不可执行，下一个人在同一压力下还会做同样的选择。第二种是工具的问题：结论写成检索效果不好，修复动作是换一个向量库，它跳过了一步，哪一类查询效果不好、坏在召回还是排序。第三种是没有结论：会议记录写满两小时讨论，最后一栏是继续观察，它的信号是行动项为零，可用的补救是当场只定一条，这条事故对应的用例怎么写。三个反模式的共同点是都让复盘停在描述现象这一层。

### 3.4 事故的账怎么算

一次事故的代价要算四笔，只算一笔会低估：

| 一笔 | 怎么算 | 容易漏的地方 |
|---|---|---|
| 直接成本 | 出错期间的模型与调用费用 | 重试与补偿调用 |
| 人工成本 | 排查、修复、客服的人力 | 跨团队的时间 |
| 信任成本 | 受影响的会话数 × 挽回成本 | 沉默流失的用户 |
| 机会成本 | 同一批人本可以做的事 | 排期推迟的连带影响 |

第三笔最难算，也最容易被忽略：三十七次错误承诺里可能只有几次被投诉，其余用户直接不再使用，用投诉数当影响面会系统性低估。四笔不需要精确到元，但需要同一套口径。可用的做法是只算前两笔的精确值，后两笔给区间。

## 四、事故变用例

事故复盘的最后一步不是写报告，是把这次输入固化成一条用例；没有这一步，复盘只是一份文档。

**用例的四要素。** `postmortem_to_case.py` 的第四段输出把这次事故固化成用例：

```
  {
    "case_id": "reg-0314-01",
    "question": "生鲜订单可以无理由退货吗？",
    "must_contain": "不支持",
    "must_not_contain": "可以退",
    "source": "INC-0314"
  }
```

| 要素 | 作用 |
|---|---|
| 输入 | 能复现那次调用 |
| 必须包含 | 正确答案的关键结论 |
| 必须不包含 | 当时的错误说法 |
| 来源 | 指回事故编号，便于复查 |

第三条是它区别于普通用例的地方：普通用例只验对不对，事故用例还要验那个错法不再出现，两个判据一起用才能挡住改对了结论但换了个错法。第四条让用例集可追溯：三个月后有人问这条用例为什么在，答案是一个事故编号。

**旧配置跑一遍。** 同一脚本的第五段输出把新旧配置各跑一次：

```
=== 5. 旧配置与新配置各跑一遍 ===
  [old] 召回 policy#4@v1  回答：根据policy#4@v1：生鲜商品签收后 7 天内可退。
         判定：失败（缺少关键结论'不支持'）
  [new] 召回 policy#4@v2  回答：根据policy#4@v2：生鲜类商品不支持无理由退货。
         判定：通过（结论正确）
```

这一步最容易被跳过，也最重要：用例必须在旧配置上失败，如果它在旧配置上也通过，说明它没有复现那次事故，抓的是别的东西，或者根因还没找到。三种组合的结论是：

| 旧配置 | 新配置 | 结论 |
|---|---|---|
| 失败 | 通过 | 修复有效，用例进回归集 |
| 通过 | 通过 | 没复现，用例要重写 |
| 失败 | 失败 | 根因还在，别急着写复盘 |

第一种是唯一可以宣布修好了的组合。第二种最危险，因为它看起来一切正常，而事故随时会回来。第三种说明修复没生效，这时写复盘只会把错误结论固化下来。

### 4.1 用例集的增长方式

事故用例应当只增不改，与第 43 章的评测集规则一致。它的规模增长缓慢，但每一条都是真发生过的。

| 来源 | 数量级 | 价值 |
|---|---|---|
| 事故复盘 | 每年几十条 | 最高：真实、有判据、有来源 |
| 误杀投诉 | 每年上百条 | 高：直接改善体验 |
| 主动构造 | 每季度一批 | 中：覆盖未发生的场景 |

第一行的价值最高，因为它的判据已经被违反过，不需要论证。一个团队的回归集里如果一条事故用例都没有，说明复盘没有落到用例上。

### 4.2 回归集与用例的寿命

事故用例写进回归集之后，要能被自动执行，否则它会和文档一样腐烂。

| 位置 | 何时跑 | 耗时预算 |
|---|---|---|
| 提交级 | 每次提交 | 分钟级 |
| 发布级 | 每次发布 | 十分钟级 |
| 夜间 | 每天一次 | 小时级 |

第一行只能放快且确定的用例：事故用例大多是单次问答，几十条跑完在几分钟内，适合放这里。第二行放多轮、审批、需要重复跑的用例，也就是第 44 章四层评测里的稳定层；第三行放依赖外部服务的用例，它跑得慢，但能在第二天早上给出昨晚有没有新的回归。事故用例应该优先放在第一行，因为越早发现越便宜。失败的处理也要定：第一行失败阻止合并，第三行失败开一条工单，不区分的话团队会把所有失败都当噪声。

用例也会过期。文档改版后，旧用例的必须包含可能不再正确；模型升级后，某条用例的判定可能从失败变通过，这未必是修好了，可能是判定条件太宽。

| 变化 | 处理 |
|---|---|
| 政策文本改了 | 更新"必须包含"，并在用例里记来源版本 |
| 用例连续通过一年 | 检查它是否还有区分力 |
| 用例开始随机通过 | 说明有采样或外部依赖，要固定条件 |
| 同一事故复发 | 用例没覆盖根因，要补一条而不是改旧的 |

第二行的连续通过不是坏事，但它意味着这条用例不再产生信息；保留成本很低，但一个集合里九成用例都这样就说明该扩了。第四行最值得注意：同一事故复发，第一反应往往是把用例改严一点，正确做法是补一条覆盖新路径的用例，因为复发说明根因在别处。

### 4.3 从用例到看板

用例写出来之后，还要能被看见，三种可见性各解决一个问题：

| 看哪里 | 看什么 | 解决什么 |
|---|---|---|
| CI 失败列表 | 哪条用例挂了 | 当次改动有没有碰坏 |
| 回归集趋势 | 通过率随时间 | 缓慢退化 |
| 事故台账 | 每条事故对应哪条用例 | 复盘是否闭环 |

第二行最容易被忽略：单次 CI 只看这次挂没挂，看不到这个月通过率从九成八掉到九成三，趋势要单独存，且要按用例分组。第三行是管理视角：一次事故如果没有对应用例编号，台账上就是空的，这个空位比任何指标都更能说明复盘的执行情况。看板的价值不在好看，在让遗漏可见：一条事故记进台账但没写用例，等于没复盘。

## 五、会怎么坏

**第一，只报总成本。** 一次零点零五六元无法回答该省哪一段，信号是成本报表只有一列。第二，只有单任务预算。 单次都合规，月度总额翻倍。第三，缓存键不含租户。 跨租户命中，答案串户。第四，缓存不随索引失效。 政策改了，一半流量还在答旧版本。

**第五，只优化总延迟。** 用户仍觉得慢，因为 TTFT 没变。第六，降级链没有总预算。 逐级重试，一次请求等了三倍时间。第七，复盘停在忘了加条件。 修了这一处，下一处照旧。第八，事故用例在旧配置上也通过。 以为修好了，其实没复现。

**第九，降级没有被统计。** 降级率上升没人知道，只看到延迟变好了。第十，复盘的行动项没有复查。 会后写了五条，下次复盘发现三条没做。

## 六、边界

**第一，成本瀑布依赖 span 的分阶段归因。** 第 42 章没记 `kind` 与 token，这一章的瀑布就做不出来，可观测的字段设计是成本优化的前置条件。第二，三级预算的阈值要随业务调整。 增长期与稳定期的容忍度不同，阈值不动就会出现所有任务都被限流。第三，语义缓存的收益在高频重复提问上才明显。 一个长尾问题的集合，命中率可能只有百分之五，而它引入的失效与串户风险不变。

**第四，延迟优化的上限由瀑布的占比决定。** 一个生成占八成的系统，把检索优化到零也只能省两成，想大幅降低延迟必须改生成方式。第五，降级链的每一级都要有质量标注。 没有标注，用户无法判断答案的可信度，团队也无法统计降级率。第六，MTTD 与 MTTR 依赖观测与流程，不是这一章的代码能解决的。 这一章只给出两个数字的定义与分工。

**第七，事故用例不能覆盖没发生过的问题。** 它是回归网，不是探索网，探索靠第 43、44 章的评测集与主动构造的对抗样本。第八，成本与延迟的优化常常互相冲突。 加缓存降成本但可能提高首字节，并行化降延迟但提高并发与成本。第九，这一章的复盘样例是单点事故。 还有一类是缓慢退化：三个月里错误率从百分之二涨到百分之六，没有单次事故可复盘，它靠第 45 章的双基线。

**第十，这一章的成本与延迟数字都来自固定单价与固定阶段。** 它们不能当成任何厂商的报价。第十一，三级预算与门禁都假设流量可预测。 一次营销活动会把日预算瞬间打满，这时预算的作用是提前暴露，不是拦住。

卷十到这里完整了。五章回答的是同一个问题：怎么用一个数字证明改动变好或变坏。

| 章 | 回答 | 产物 |
|---|---|---|
| 42 | 能不能看见 | span 树、字段口径、平台对象 |
| 43 | 答得对不对、坏在哪 | 分层指标、评测集、四个数 |
| 44 | 过程对不对、裁判可信吗 | 四条判据、kappa、多轮用例 |
| 45 | 这个差异算不算数 | 区间、门禁 |
| 46 | 钱与时间花在哪、怎么不再犯 | 瀑布、复盘、事故用例 |

五章的依赖是单向的：没有 span 就做不出分层归因，没有分层就没有可比的指标，没有区间就不知道指标的变化算不算数，没有复盘就不知道下一个指标该测什么。一个贯穿全卷的判据：任何一次我们变好了的结论，都应该能追到一个指标、一个区间、一次回归验证。

## 这一章建立的 6 件事

1. 成本要按阶段拆开：生成三成六、子 agent 汇总三成六、自审一成九；三段各自的省法不同，只看总成本无法行动。
2. 预算要三级：单任务防失控、租户日防刷量、平台月防整体超支；三级阈值要能互相推导，否则配额设计有问题也看不出来。
3. 语义缓存的三条红线是跨租户、不随文档失效、命中仍计全额；正确的键是"问题 + 租户 + 索引版本"三者的哈希。
4. TTFT 与总延迟要分开看：流式不改总延迟，只改 TTFT；并行化的上限是较短那一段的占比，所以一轮优化常常只快一成。
5. 复盘要问到"能改结构"的位置，并固化成一条"旧配置失败、新配置通过"的用例；停在一句操作说明的复盘，下一次还会犯。
6. 本卷的因果是单向的：看见（42）→ 判对错（43、44）→ 判差异（45）→ 归因与不再犯（46）；任何"变好了"的结论都要能追到指标、区间与回归验证三样东西。
