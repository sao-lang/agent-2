## 一、一条链的尽头

一条封装好的查询链会把一次无关的检索也送去合成，钱已经花掉，而调用方拿到的是一个看不出依据的回答。`as_query_engine()` 就是这条链：检索、取前 k 个块、拼进提示词、调用模型，中间没有可以插入判断的位置。`retrieval_three_ways.py` 第一节对两个问题各查一次：

```python
engine = index.as_query_engine(similarity_top_k=3)
for q in (Q_ANSWERABLE, Q_MISSING):
    resp = engine.query(q)
```

```text
=== 1. QueryEngine：一条链，合成前无法判断 ===
  问：退货邮费谁付
    回答：根据资料，质量问题的退货运费由商家承担。
    首位来源：invoice.md，词面覆盖率 0.00
    LLM 调用：1 次（合成已经发生，覆盖率再低也拦不住）
  问：如何申请专利
    回答：根据资料，质量问题的退货运费由商家承担。
    首位来源：logistics.md，词面覆盖率 0.00
    LLM 调用：1 次（合成已经发生，覆盖率再低也拦不住）
```

第一个问题问的是退货，首位来源却是发票文档；第二个问题问的是专利，资料里一个字都没有，系统照样调用了一次模型。两句回答一模一样，因为 LLM 是固定回答的脚本：回答文本不携带"有没有依据"的信息，能携带这个信息的是来源与覆盖率。这段输出说明了什么：`QueryEngine` 的接口只返回答案加来源，判断只能发生在拿到返回之后，而在那之前合成那次调用已经花掉了。

### 1.1 覆盖率是个代用品

示例里的判据是"问题里的字有多大比例出现在首位块里"，下面是原理演示，不是语义相关性：

```python
def coverage(query: str, text: str) -> float:
    """问题里的字有多大比例出现在这个块里。原理演示，不是语义相关性。"""
    chars = set(query)
    return sum(1 for c in chars if c in text) / len(chars)
```

这个判据只看字面，不看语义：它对"退货邮费谁付"有效，对"客户很生气，钱能退吗"这类口语化问题基本无效。用它是因为它确定、可复现、不需要第二个模型，生产里替换它的是交叉编码器打分（第 18 章）、一次 LLM 判定，或者一个业务规则。判据换了结构不变：检索之后、合成之前，有一个能返回布尔值的判断点。

## 二、固定链为什么不可改

查询引擎把"取哪些块"和"怎么合成"写成一个对象，改动只能通过构造参数，不能通过控制流，它的参数里没有"如果不够就重查"这一项。`QueryEngine` 由 `retriever` 与 `response_synthesizer` 组成，两者都可替换，但连接方式是固定的，检索一次，合成一次。

| 层 | 覆盖 | 不覆盖 |
|---|---|---|
| `Retriever` | 相似度检索、过滤、top_k | 检索结果够不够 |
| `ResponseSynthesizer` | 多块合成、引用、模式 | 块从哪来、够不够 |
| `QueryEngine` | 上面两者串起来 | 串的过程中间加分支 |

第 14 章把 RAG 拆成四个环节，第 18 章讲"查得准不准"，第 19 章讲"装进上下文"，这三件事在 `QueryEngine` 里被压成一次调用，压缩掉的是"判断"这个环节。第 7 章的最小循环给过同一个判据：循环要有终止条件，而终止条件必须由调用方定义。"再查一次"还是"就用这些"，是一个判断，不是一个配置。

### 2.1 判断点该放在哪

判断只有三个可能的位置，各有代价：

| 位置 | 做法 | 代价 | 失效 |
|---|---|---|---|
| 合成前 | 看分数或覆盖率，不够就重查 | 一次额外判断 | 判据不准时白重查 |
| 合成中 | 提示词里要求"资料不足就说不知道" | 零额外调用 | 模型不一定照做（第 23 章） |
| 合成后 | 拿回答再判一次是否有依据 | 一次额外调用 | 已经花掉了合成那次 |

第一行是这里的做法，第二行是提示词层的兜底，第三行是反思。三者可以叠加，但第一行最便宜，它在花钱之前拦；"资料不足就说不知道"这类约束在压力下最不可靠。第三行的问题是判断的对象已经是一次生成的结果，模型可能编得很像有依据，第 23 章讲过"自己评自己没用"，同一个模型既生成又判定，倾向是给自己通过。

### 2.2 可换的组件与不可换的顺序

检索器可以换：向量检索、关键词检索、摘要检索，第 39 章那三种索引各有一个检索器。合成器也可以换：`compact`、`refine`、`tree_summarize`，其中 `tree_summarize` 是一种分层合并的模式。换这两样都不改变"检索一次、合成一次"这个顺序。

| 换什么 | 换来什么 | 不变的 |
|---|---|---|
| 检索器 | 召回的口径（语义 / 词面 / 全量） | 判断点仍然不存在 |
| 合成器 | 调用次数与上下文压力 | 判断点仍然不存在 |
| 索引类型 | 查询时取多少块 | 判断点仍然不存在 |

## 三、手写循环的形状

一个 `while` 就能把判断插进去，代价是循环、状态、退出条件都要自己管。`retrieval_three_ways.py` 第二节把这件事写成二十来行：

```python
def answer(q: str) -> tuple[str, list[str]]:
    retriever = index.as_retriever(similarity_top_k=3)
    trace: list[str] = []
    query = q
    for rnd in range(MAX_ROUNDS):
        hits, top = top_hit(retriever, query)
        cov = coverage(query, top.node.text)
        trace.append(f"第 {rnd} 轮 {query!r} 首位={top.node.ref_doc_id} 覆盖={cov:.2f}")
        if cov >= THRESHOLD:
            synth = get_response_synthesizer(response_mode="compact")
            resp = synth.synthesize(q, nodes=hits)
            trace.append(f"合成：{len(hits)} 个节点")
            return str(resp), trace
        nxt = REWRITE_MAP.get(query)
        if nxt is None:
            trace.append("没有可用的改写，放弃（0 次合成调用）")
            return "资料里没有依据，无法回答。", trace
        query = nxt
    return "两轮都不够，放弃。", trace
```

```text
=== 2. 手写循环：先判覆盖率，再决定要不要合成 ===
  问：退货邮费谁付
    第 0 轮 '退货邮费谁付' 首位=invoice.md 覆盖=0.00
    第 1 轮 '质量问题导致退货时退货运费由谁承担' 首位=policy.md 覆盖=0.87
    合成：3 个节点
    回答：根据资料，质量问题的退货运费由商家承担。
    LLM 调用：1 次
  问：如何申请专利
    第 0 轮 '如何申请专利' 首位=logistics.md 覆盖=0.00
    没有可用的改写，放弃（0 次合成调用）
    回答：资料里没有依据，无法回答。
    LLM 调用：0 次
```

第一个问题两轮：第一轮首位是发票，覆盖率零，改写后第二轮首位变成退货政策，覆盖率 0.87，合成；第二个问题一轮就放弃，零次合成调用。两次查询的差别是一整次模型调用，这个差额就是判断点的价格：它在检索与合成之间，把"没有依据"挡在花钱之前。

改写之所以有效，是因为它把口语换成资料里的用词：第一轮问"邮费"，资料里写"运费"，改写后两个词都在，命中率从零跳到 0.87。第 4 章讲的"把用户的话翻译成检索词"，在检索层就是这个样子。

### 3.1 循环的三个出口

这个 `while` 有三个出口，缺一个就会变成死循环或错误回答：

| 出口 | 条件 | 缺了它 |
|---|---|---|
| 够了 | 覆盖率达标 | 一直重查，直到轮数上限 |
| 改不动了 | 改写表里没有这条 | 用同一个问题重查两遍，白花两次检索 |
| 轮数到顶 | `rnd == MAX_ROUNDS` | 无限循环 |

第二个出口最容易被漏：很多实现只判"够不够"，不够就改写，而改写函数对任何输入都返回一个新问题，于是"改写—再查—还不够—再改写"一直转到轮数上限。轮数上限是兜底，不是出口。第三个出口的取值取决于成本，一轮检索加一次合成，两轮是两倍。

### 3.2 改写本身的成本

示例里的改写是一张两行的表，真实系统里它通常是一次 LLM 调用：把原问题、检索到的块、判断结果一起给模型，让它给出更好的检索词，这一步的成本要算进循环，两轮就是两次改写调用。

改写还有一个失败模式：模型把问题改得更具体，反而离语料更远，信号是第二轮覆盖率比第一轮更低。可用的做法是保留每轮的覆盖率，只在覆盖上升时采用新问题；`while` 里加一个变量就行，Workflow 里要放进 `ctx.store`。

### 3.3 判据的三种实现

"够不够"有三种实现，代价与可靠性的排序正好相反：

| 判据 | 实现 | 成本 | 失效形态 |
|---|---|---|---|
| 分数阈值 | 比检索分数 | 零 | 不同索引的分数不可比 |
| 词面覆盖 | 数问题里的字命中多少 | 零 | 同义改写漏判 |
| 模型判定 | 把问题与块给模型判 | 一次调用 | 自己给自己放行 |

第一行最省，问题是分数只在同一个索引、同一个嵌入模型下可比，换了嵌入模型、换了 `top_k`，0.5 这个阈值的含义就变了。第二行稳但粗。第三行最准，却要在检索与合成之间再插一次调用，而且它与合成用的是同一个模型时倾向是"够"，第 23 章讲的那种偏差会再现。

可行的组合是"词面覆盖做硬拦，模型判定做兜底"：覆盖率为零直接拒绝，不必再花一次调用；处在中间区间时再问模型。两级判据的成本是一级的，代价是两条路径要分别测。

## 四、事件驱动的同一件事

同一套判断写成 `Workflow` 后，控制流从"循环体"变成"事件类型"，每一步是一个独立函数，下一步由返回类型决定。`retrieval_three_ways.py` 第三节是同一道题的事件版：

```python
class RagFlow(Workflow):
    @step
    async def start(self, ctx: Context, ev: StartEvent) -> Retrieved:
        return Retrieved(query=ev.get("query"), round=0)

    @step
    async def retrieve(self, ctx: Context, ev: Retrieved) -> Judged:
        hits = self.index.as_retriever(similarity_top_k=3).retrieve(ev.query)
        await ctx.store.set("hits", hits)
        return Judged(query=ev.query, round=ev.round, covered=coverage(ev.query, hits[0].node.text))

    @step
    async def judge(self, ctx: Context, ev: Judged) -> Rewritten | StopEvent:
        ...
```

```text
=== 3. Workflow：同样的判断，写成带类型的事件 ===
  问：退货邮费谁付
    句柄 0: 检索 '退货邮费谁付' → invoice.md 覆盖 0.00
    改写：'质量问题导致退货时退货运费由谁承担' → 下一轮
    句柄 1: 检索 '质量问题导致退货时退货运费由谁承担' → policy.md 覆盖 0.87
    句柄 1: 合成 3 个节点
    结果：'根据资料，质量问题的退货运费由商家承担。'，状态 answered，用了 2 轮
    LLM 调用：1 次
  问：如何申请专利
    句柄 0: 检索 '如何申请专利' → logistics.md 覆盖 0.00
    句柄 0: 无改写可用，放弃
    结果：'资料里没有依据，无法回答。'，状态 refused，用了 1 轮
    LLM 调用：0 次
```

行数和调用次数与手写版一样，差别在结构：`retrieve` 只负责检索，`judge` 只负责判断，`rewrite` 只负责改写，三个函数各自可测，事件类型就是它们之间的接口。`judge` 的返回类型是 `Rewritten | StopEvent`，一个联合类型，两个分支。Workflow 的路由不靠条件边，靠返回值的类型：返回 `Rewritten` 走到 `rewrite`，返回 `StopEvent` 就结束。第 36 章的 LangGraph 把条件写在边上，这里写在步骤里。

### 4.1 状态放在 `ctx.store`

`retrieve` 把检索结果放进 `ctx.store`，`judge` 再取出来。这个 store 是这次运行私有的，跨步骤共享；事件里只放下一跳需要的最小信息：查询词、轮数、覆盖率。这个分工有实际好处：事件可以被序列化、被日志记录、被重放，检索结果里有节点对象，不适合塞进事件。事件是控制流的载体，`ctx.store` 是数据的载体。

`ctx.store` 里的东西在运行结束后不保留，要跨运行保留得自己写出去，Workflow 没有检查点，这是它与图框架最大的差别（第 37 章那套）。

### 4.2 超时是一个构造参数

`RagFlow(index=index, timeout=5)` 里那个 `timeout` 管整个运行，从第一个事件到 `StopEvent`。超时到了抛 `WorkflowTimeoutError`，消息里带当前还在跑的步骤名，第七节有真实输出。手写版要自己算 deadline 并在每次循环开头检查，Workflow 版交给框架。这是选 Workflow 的一条实际理由：它把整次运行的截止时间做成了参数，而不是靠代码纪律。

### 4.3 一次运行的时序

`run()` 之后，框架做的是"把事件放进队列、按类型找步骤、执行、再放回队列"的重复。示例里那次两轮运行，事件按 StartEvent、Retrieved、Judged、Rewritten 一棒棒传下去。每一步都是异步函数，但默认不并行：队列里只有一个事件时，步骤一个接一个跑。这个默认值对检索流程是对的，检索、判断、改写之间是严格的前后依赖，强行并行只会让判断读到还没写完的状态。

时序在两种情况下不直观：一个事件被多个步骤消费时，两个步骤各自独立执行，谁先完成不确定；返回类型是联合类型时，只有实际返回的那个分支被触发。读一个 Workflow 的执行顺序，不能只看代码顺序，要看谁的返回类型指向谁。

### 4.4 步骤的粒度

粒度由"会不会独立变化"决定，不由行数决定。示例里检索、判断、改写各一步，因为这三件事的变化来源不同：检索随索引变，判断随阈值变，改写随语料用词变；合成被放进 `judge`，因为它与判断共用同一批 `hits`。

粒度过细的代价是事件类型爆炸，读代码要先在脑子里建一张图；粒度过粗的代价回到起点，一个步骤里塞了检索与判断，换判据就要动检索。一个可用的判据是"这个步骤会不会被单独测试"，会被单独测就独立成步。

## 五、三种写法的对照

三种写法的调用次数一样，差别在"能不能插判断"与"出错时能定位到哪一步"。对照如下：

| | QueryEngine | 手写循环 | Workflow |
|---|---|---|---|
| 代码行数 | 1 行构造 + 1 行查询 | 约 25 行（含 trace） | 约 60 行（含事件类） |
| 插判断的位置 | 无 | 循环体里 | 步骤之间 |
| 检索与合成调用数 | 各 1 次，固定 | 1–2 次检索，0–1 次合成 | 同左 |
| 分支表达 | 无 | `if` / `for` | 返回类型 |
| 超时 | 无（要外层包） | 自己算 deadline | `Workflow(timeout=)` |
| 出错定位 | 堆栈在库里 | 堆栈 + 自己打的 trace | 异常 + 活跃步骤名 |
| 跨运行恢复 | 无 | 自己存 | 无 |

第二行是本质差别：`QueryEngine` 没有位置插判断，另两种有。第三行是收益：同样两个问题，`QueryEngine` 花两次合成，另外两种只花一次。第四行是代价：手写版的 trace 要自己打，Workflow 版的 trace 由事件流给出（第 42 章）。第六行讲定位：手写循环出错时，堆栈指向 `answer()` 内部某一行，看不出是第几轮；Workflow 出错时异常消息里带活跃步骤名，定位成本低得多。

换掉实现时，测试也要跟着换：手写版通常只测 `answer()` 的最终返回，事件版可以分别测检索是否命中、判断是否给出正确布尔值、改写是否产出新问题。调用数也能这样断言，给一个假检索器，数它被调用几次；真正需要模型的只有判据准不准那一步（第 43 章）。

### 5.1 行数不是选型依据

六十行比二十五行多，但多出来的三十五行走的是声明式代码：五个事件类、五个步骤方法，每个方法十来行。这类代码的好处不在短，在于每一段都能单独替换：换判据只改 `judge`，换检索器只改 `retrieve`。手写版的二十五行里，判断、检索、改写、合成挤在一个函数里。代码行数是表象，可替换的边界数才是结构。

### 5.2 什么时候仍然用手写循环

单轮、无分支、无并发的场景，`while` 更直接：一次检索、一次判断、一次合成，三行写完，Workflow 的五个事件类在这时是负担。判断依据是"这个流程会不会长出第二个分支"。会长，就从 Workflow 开始；不会，`while` 更省，不必为了统一把三行的流程写成六十行。

### 5.3 步骤怎么测

写 Workflow 的一个实际收益是每一步可以单独调用：`retrieve` 的输入是一个 `Retrieved` 事件，输出是一个 `Judged` 事件，给一个查询词就能验证它返回的 `covered` 是不是预期值。

### 5.4 判据换了，代码不动

示例的判据是覆盖率，换成"交叉编码器打分"时，只需要改 `judge` 里那一行，把 `coverage(...)` 换成 `reranker.score(query, node.text)`，阈值重新标定，`retrieve`、`rewrite`、`start` 都不用动。反过来，如果判断写在 `retrieve` 内部，换判据就要动检索、换检索又会影响判断，两件事被绑在一个函数里。

## 六、事件类型与路由

路由由返回类型决定，类型写错时流程不会走错分支，而是直接不满足校验。一个步骤的签名是 `async def name(self, ctx: Context, ev: 某事件) -> 返回事件`，三处都在表达契约：

| 位置 | 含义 | 写错的后果 |
|---|---|---|
| 参数类型 | 这个步骤消费哪种事件 | 该事件无人消费，校验报错 |
| 返回类型 | 这个步骤产出哪种事件 | 下游步骤永远等不到输入 |
| 联合返回类型 | 二选一的分支 | 少写一支，那个分支不可达 |

第三行是本章用到的写法：`-> Rewritten | StopEvent`，两个分支各自对应一个步骤或终止。如果把 `StopEvent` 写成另一个自定义事件，流程会停在"没人消费这个事件"上，校验期就会报出来。`ctx.store` 与事件的边界也要划清：事件里放能序列化的小值，store 里放这次运行要复用的大对象。示例把 `hits` 放进 store，把 `covered` 放进事件。

### 6.1 并发与 `send_event`

`ctx.send_event` 可以在一个步骤里发出多个事件，让下游并行执行，再用 `ctx.collect_events` 等齐。这是 Workflow 相对手写循环多出来的一项能力：两路检索同时跑，等两路都回来再合并。

它也有静态约束：发出的事件必须在某个步骤的返回类型里声明过，否则校验期报"被消费但从未产出"。这条约束保证每个事件都有明确的产出者，流程不会在运行时停在"等一个永远不会来的事件"上。示例没有用并发，因为两路检索的对照需要另建一个关键词索引。

### 6.2 `Context` 管的是什么

`Context` 是这次运行的句柄，示例用到它三件事：`ctx.store.set/get` 存检索结果，`ctx.send_event` 发事件，`ctx.collect_events` 等齐多路结果。它与 LangGraph 的 `Runtime` 位置相当，后者是那边表示单次运行上下文对象；区别在职责：`Runtime` 还带状态的持久化，`Context` 只有内存里的 store 与事件通道。并行分支共享它，所以两路检索同时写 store 是"最后写入者赢"，走事件才能合并。数据走 store 会互相覆盖，走事件才能合并。

## 七、五种坏法

五种坏法里有四种在 `run()` 之前就被拦下，只有一种会真的跑起来然后失败。它们报的错不一样，定位成本也不一样。`workflow_errors.py` 是一个脚本，逐个触发：

```python
try:
    await MissingStop(timeout=1).run()
except Exception as e:
    print(f"  {type(e).__name__}: {e}")
```

```text
=== 1. 没有任何步骤返回 StopEvent ===
  WorkflowConfigurationError: At least one Event of type StopEvent must be returned by any step. (Workflow 'MissingStop' has no @step that returns StopEvent.)
=== 2. 步骤比超时慢 ===
  WorkflowTimeoutError: Operation timed out after 0.5 seconds. Currently active steps: slow
=== 3. 事件产出后没人消费 ===
  WorkflowValidationError: The following events are produced but never consumed: Orphan
=== 4. send_event 发了，但没有步骤声明返回它 ===
  WorkflowValidationError: The following events are consumed but never produced: StartVec
=== 5. 步骤里抛异常 ===
  ValueError: 切块器收到空文档
```

第一种是"没有终点"。少了 `StopEvent`，`run()` 会永远等下去，框架选择在启动时拒绝，消息里带类名与原因。第二种是"太慢"：0.5 秒超时，一个 `Slow` 步骤要睡 2 秒，它是一个故意慢的函数，消息里带 `Currently active steps: slow`，直接指出卡在哪一步；没有这一行，只能知道超时，不知道超时在哪。

第三种是"产出了没人要"。`OrphanFlow` 里 `first` 返回 `Orphan`，没有任何步骤消费它，校验期报错，这类错在重构后很常见。第四种是"要的没人产"：`start` 用 `send_event` 发了 `StartVec`，但没有任何步骤声明返回它。

第五种是唯一会跑起来才失败的：步骤里抛的异常原样冒泡，没有包装、没有步骤名。`ValueError: 切块器收到空文档` 这样的消息，得自己带上上下文，否则看不出是哪个步骤、第几轮。

| 坏法 | 何时发现 | 消息里有什么 | 该补什么 |
|---|---|---|---|
| 缺 `StopEvent` | `run()` 时校验 | Workflow 类名 | 加终止步骤 |
| 超时 | 运行中 | 超时秒数 + 活跃步骤 | 调大超时或拆步骤 |
| 孤儿产出 | `run()` 时校验 | 事件名 | 删产出或加消费 |
| 无主消费 | `run()` 时校验 | 事件名 | 补返回类型声明 |
| 步骤异常 | 运行中 | 原始异常 | 异常里带步骤与轮次 |

### 7.1 校验期与运行期

五种坏法分两批：前四种在 `run()` 的事件图校验里报，最后一种要跑到那一步才报。校验期的四种不需要模型、不需要网络，实例化再 `run()` 就能触发，可以写成一个离线单测，每次改事件类都跑一遍；超时那条用 `asyncio.sleep` 就能稳定复现。运行期的异常只能靠覆盖到那条路径的用例。

| 坏法 | 需要模型吗 | 单测能覆盖吗 |
|---|---|---|
| 缺 `StopEvent` | 否 | 能 |
| 孤儿产出 | 否 | 能 |
| 无主消费 | 否 | 能 |
| 超时 | 否（用 sleep 模拟） | 能 |
| 步骤异常 | 视步骤而定 | 要构造输入 |

## 八、与图框架的对照

`Workflow` 与第 36–38 章的 LangGraph 解决同一类问题，但把"状态"和"持久化"留在了框架之外。逐项对照：

| 关心的事 | LangGraph | LlamaIndex Workflow |
|---|---|---|
| 节点 | `add_node` 注册的函数 | `@step` 装饰的方法 |
| 边 | `add_edge` / 条件边 | 返回类型 |
| 共享状态 | `State` + reducer | `ctx.store`（无 reducer） |
| 并行扇出 | `Send` | `ctx.send_event` + `collect_events` |
| 检查点 | `Checkpointer` | 无 |
| 中断与人审 | `interrupt()` | 无内建，要自己发事件等外部输入 |
| 流式 | 多种 `stream_mode` | 事件流 |

第四行的差别在写冲突：LangGraph 的 reducer 决定两个节点同时写同一个键怎么合并，`ctx.store` 是最后写入者覆盖，两路检索同时往 store 里写 `hits`，后写的赢，先写的那一路白跑。第五行是最大的差别。Workflow 跑完就没了，进程重启后无法从中间恢复；要审批后继续，得把状态写到外面，再用一个新的事件接回来。第 37 章那套时间旅行，在 Workflow 里没有对应物。

第六行是第二的直接后果：人在环里的等待没有上界，而 `timeout` 是整次运行的上界，两者放在一起，要么把超时设得很长，要么把等人的环节拆成两次运行。

### 8.1 事件流就是 trace

一次运行里每个事件的产出与消费，天然构成一棵树：根是 `StartEvent`，叶子是 `StopEvent`。把每个步骤的开始、结束、输入事件类型打印出来，就得到一份不依赖观测平台的 trace。示例里 `self.trace` 是手写的字符串列表。真实项目里这份记录应当结构化：步骤名、事件类型、耗时、轮数、检索命中数。

第 42 章讲的 span 与这里是一回事：一个步骤一个 span，父子关系就是事件的因果链。事件流已经能给出这棵树，上报层要做的只是把它翻译成自己的格式。

## 九、检索这一层的取舍

把所有判断都压在检索之后，会让检索承担它承担不了的责任；判断太严，会把能答的问题也拒掉。这一节的三个数字决定收益边界。第一个数字是阈值。示例用 0.5 的词面覆盖率，第一轮 0.00、第二轮 0.87，区间很宽，所以判断不敏感；真实语料里覆盖率分布在 0.3–0.6 之间时，阈值取 0.4 还是 0.5 会改变答与不答的比例，只能靠评测集定（第 43 章）。

第二个数字是轮数。两轮意味着最坏多一次检索加一次合成，三轮是两次；收益递减很快，第一轮解决大部分问题，第二轮解决用词不对的问题，第三轮之后通常是在同一个语义空间里打转，所以轮数上限取 2 是常态。

第三个数字是改写成本。示例里改写是查表，零成本；真实系统里改写是一次 LLM 调用，于是两轮的实际成本是两次检索加一次改写加一次合成。改写本身也判断够不够时还要再加一次，调用次数不是 2，是 3 到 4。

### 9.1 拒答也是一种输出

示例第二个问题返回"资料里没有依据，无法回答"，零次合成调用。这条路径在很多系统里被写成返回空，调用方拿到空字符串后不知道是没查到还是出错了。

拒答要带三样东西：为什么拒、试过什么、下一步能做什么。拒答与报错是两件事：拒答是查过了没有，报错是没查成。第三样在知识库场景里很实际，用户问的可能是语料里没有的新政策，正确的行为是告诉他这个主题没有资料，而不是让模型用旧政策编一个答案；第 28 章的护栏在这里体现为一条硬规则，没有来源就不生成。

### 9.2 检索词从哪里来

示例里的改写是一张两行的表，它回答了一个真实问题：检索失败的多数原因不是索引不好，是问法与语料用词不一致。资料里写"运费"，用户说"邮费"。三种做法，成本递增：

| 做法 | 例子 | 成本 | 覆盖 |
|---|---|---|---|
| 固定同义词表 | 邮费 → 运费 | 零 | 只能覆盖写下来的那些 |
| 查询扩展 | 生成三个同义问法，各查一次后合并 | 检索次数翻倍 | 覆盖改写没写到的说法 |
| 模型改写 | 把问题、首轮结果、判断一起给模型 | 一次 LLM 调用 | 能利用上下文 |

固定同义词表在垂直领域里够用：售后、物流、发票这几个词各自只有几种说法查询扩展适合召回优先的场景，代价是每次查询多几次检索。模型改写最灵活，也最贵，而且改写质量本身要评测。

三行可以叠加：先查同义词表，命中就换词；没命中再让模型改写。改写表的价值在可审计，每条改写都能被人工检查，而模型改写只能靠评测集发现它改错了。同义词表还有一个维护问题：它随语料演化而腐化。新政策用了"寄回运费"这个说法，表里没有，这条改写就失效；可用的做法是把"改写后仍然覆盖率很低"的查询记下来，定期人工看，把高频的新说法补进表。

### 9.3 拒答要带什么

拒答的返回体应当结构化。第二项常被忽略：用户看到"没有找到相关资料"时，下一步动作取决于系统试过什么，只查了一个说法，他可以换个说法再试；已经试过三个，他应当去找文档管理员。

第三项要写成明确的标记，不要用空字符串：在调用方看来，空可能是没有结果，可能是模型返回了空，也可能是服务出错但被吞了。

拒答还应当分两级：语料里确实没有，与有但这次没查到。前者要补文档，后者要调检索；两种用不同的标记，否则运营侧会把拒答都当成缺内容，标记取值不超过三个。

## 十、会怎么坏

**判断点放错位置。** 放在合成之后，已经花掉合成调用，再判有没有依据，信号是拒答率上去、成本没降。把覆盖率当语义相关性，同义改写全部漏判，信号是口语化提问的拒答率远高于书面提问。**判据与阈值不合格。** 判据与合成用同一个模型时，倾向是说够，信号是拒答率异常低、编造率异常高；阈值定得太高，能答的问题也被拒，定得太低，无关块也送去合成。

**循环出不去。** 改写函数对任何输入都返回新问题，循环永远不触发"改不动"出口，信号是每轮覆盖率都在 0.1 上下波动。**事件写错。** `StopEvent` 与自定义事件混用，流程停在没人消费的事件上，校验期报错，校验被关掉就挂住，信号是 `run()` 不返回。步骤里抛异常没带上下文，只看到 `ValueError`，不知道第几轮。

**并发与状态。** 并行两路写同一个 store 键，后写的覆盖先写的；把 `ctx.store` 当成持久化，重启后重复执行已经完成的步骤；事件里塞大对象，日志几十 MB。**超时与流程形状。** 把 `timeout` 当成单步超时，长流程里先跑的步骤会吃掉后面步骤的时间，信号是同样的步骤单独跑很快、串起来就超时。用 Workflow 表达等人审批时，审批慢会让查询报超时，这一类要拆成两次运行（第 30 章）。

**排障信息缺失。** 改写后的查询没有回写日志，用户说不对时复现不出来；两轮之间的检索器被重建，第二轮比第一轮慢一倍。

## 十一、边界

**Workflow 不提供持久化。** 它把一次运行内的事件调度做好，跨运行的状态要自己存。需要断点续跑、时间旅行、审批恢复的场景，用第 37 章那套检查点更省事。**事件图是静态校验的，动态生成的流程不适合。** 步骤集合在类定义时就固定，要按配置决定跑哪几步，只能在步骤内部判断，或用子类组合。

**判据是词面覆盖率，不是相关性模型。** 它只用来演示判断点存在与否的差别；换成真实判据后，0.00 与 0.87 这样的干净对比不会出现，阈值要重新标定。阈值还会随语料漂移：语料扩一倍，原来 0.5 的阈值可能一夜之间把一半问题拒掉。

**拒答的边界由语料决定。** 语料里没有的内容，再好的检索也拿不出依据；判据的作用是承认没有，不是找到有；补充语料是另一件事（第 21 章）。**Workflow 的价值在流程会长分支时成立。** 单轮问答写成 Workflow 是过度设计；三行 `while` 能解决的，不要上事件。

**多路检索的合并没有覆盖。** 向量与关键词各返回一批节点，怎么去重、怎么归一化分数、怎么合并排序，是第 18 章的检索排序问题：单路检索的分数可以直接比阈值，两路必须先归一化再比，归一化做法那里有。**`ctx.store` 的键没有命名空间。** 多个步骤写同一个键会互相覆盖，且无编译期检查；规模上去以后，键名要按步骤前缀区分。

**检索循环只处理单跳问题。** 先查政策、再按政策查订单这类问题要把查询结果当输入再查一次，结构不变，但每轮查询词由上一轮结果生成，轮数上限要更小；多跳的检索策略与排序在第 18 章。**阈值与轮数应当进评测集，不进代码注释。** 这两个数字直接决定拒答率与成本，改了就要重跑一批用例；写在注释里的数字三个月后没人敢动。

**流程跑通与流程稳定是两件事。** 示例里两条路径都是确定的；真实语料上，同一句话换个标点就可能改变覆盖率。上线前要用一批问题跑一遍，统计走一轮、走两轮、拒答的比例。

## 这一章建立的 6 件事

1. `as_query_engine()` 是一条固定链：检索一次、合成一次。它在合成前没有判断点，所以检索结果再差也会花掉一次调用。
2. 判断点有三个位置——合成前、提示词里、合成后。合成前最便宜，提示词兜底最不可靠，合成后已经花掉了钱。
3. 手写循环要有三个出口：够了、改不动、轮数到顶。只判"够不够"会在改写函数总能返回新问题时退化成长循环。
4. `Workflow` 用返回类型做路由，用 `ctx.store` 传数据，用 `timeout` 管整次运行；它的 60 行比手写 25 行多出来的是可替换边界，不是复杂度。
5. 五类坏法里四类在校验期就报（缺 `StopEvent`、孤儿产出、无主消费、步骤异常只有运行期），异常消息里的"活跃步骤名"是定位超时的关键信息。
6. 它与 LangGraph 的差别集中在持久化与人审：没有检查点、没有 `interrupt()`，所以"等人"的流程要拆成两次运行。
