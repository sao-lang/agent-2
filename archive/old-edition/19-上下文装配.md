## 一、装配是预算入口

前六章都在解决哪些内容值得进窗口，这一章解决窗口装不下时怎么办。窗口是有限的，第 14 章讲过拼装的预算，第 16 章讲过块的大小，但那些都是局部决定，真正把这些内容放在一起权衡的只有装配这一步。四个槽位，其中记忆这一槽内部再分两份：

| 槽位 | 内容 | 谁决定 | 会增长吗 |
|---|---|---|---|
| 系统 | 角色、约束、工具清单 | 开发者，基本固定 | 否 |
| 任务 | 目标、已确认的事实、下一步 | 状态层抽取（见状态一章） | 否 |
| 记忆 · 会话历史 | 本次会话说过的话、工具返回 | 运行时 | 是，随轮次 |
| 记忆 · 跨会话记忆 | 召回的事实、经历、流程 | 记忆层召回，装配定额 | 否，条数由预算定 |
| 检索 | 召回的块 + 编号 | 检索层的产物 | 是，随问题 |
| 输出 | 留给回答的空间 | 由 `max_tokens` 决定 | 否 |

四个槽位抢同一个池子，池子的大小由模型决定，装配的全部工作就是在这个池子里做一次有依据的分配。没有依据的分配是：系统提示写满、历史全留、检索取前 5、剩下的给输出。它在测试时能跑，因为对话都很短；上线之后历史变长、输出被挤压，回答开始被截断。记忆槽内部再分两份，是因为寿命不同：会话历史在会话结束时就没，跨会话记忆活到被遗忘为止。它们的共同点只是都占记忆这一槽，而更新方式与抢占规则全不一样，合在一个预算里、分开算，正是后面两条规则的来源：历史先丢，记忆按层丢。

### 1.1 一次调用的总账

把一次调用的输入摊开，它是六份东西的拼接：系统提示、工具清单、历史、记忆召回、检索块，以及一个不可见的输出预留。前五份占据输入窗口，第六份占的是输入加输出的总上限，所以要满足的约束是这一条（示意）：

```
系统 + 工具 + 历史 + 记忆 + 检索 + 输出预留 ≤ 模型上限
```

式子看起来简单，落地时有三个容易出错的地方。token 数与字符数不是一回事：中文大致一字一 token，混排数字、英文、标点时会跳变。每轮都要重算：历史在长，检索块数在变。工具返回也占位置：一次调用返回 200 字的 JSON，它进的是下一轮的消息列表，属于历史。

第三处最容易漏。一条 `query_order` 的返回可能比问题长十倍，且每轮都会被重新带上，所以多轮工具调用时，历史增长的主要来源不是对话，是工具结果。

### 1.2 裁剪提示词不够

把系统提示写短一点确实有效，但它解决的是固定成本，而超预算通常由可变成本造成：系统提示从 200 token 压到 120 省下 80，历史从 300 涨到 900 涨了 600，前者一次性，后者随使用增长。超预算的根因几乎总在增长项上，只优化固定项，等于在漏水的桶里舀水。可行的顺序是先把固定项压到合理，再给增长项定策略：前者一次做完，后者要持续运营。

### 1.3 换大窗口不够

窗口不够就换大窗口模型是最常见的反应，它解决一部分问题，也带来新问题。窗口从 8k 变成 128k，装配不紧张了，但另两个问题会浮出来。第一个是大海捞针：窗口越大，同一段关键信息的占比越小，第 14 章讲拼装的稀释时说过这件事。第二个是成本：窗口填得越满，单次调用越贵，128k 全填满是 8k 窗口的十几倍。

所以正确的用法是用大窗口换更少的分段，大窗口的价值在于减少被迫丢弃，不在于增加塞进去的量，

## 二、四个槽位各占多少

先量，再谈分配。运行 `code/knowledge/ch19_context/assembly.py` 得到的一次装配：

```
=== 1. 四个槽位各占多少 ===
  系统提示        65 token      7%
  工具清单        29 token      3%
  对话历史       295 token     30%
  检索上下文      302 token     30%
  输出预留       300 token     30%
  合计         991 token
```

三成三成三成，系统与工具占一成。这个分布说明一个事实：历史与检索是仅有的两个会增长的槽位。示例只装了四块，工具清单单独列一行，任务与跨会话记忆两行为零。

分布会随使用变化：十轮之后历史可能占到 50%，把检索挤掉一半。装配不是启动时算一次，是每次调用前算一次，这也是它要写在请求路径上而不是配置里的原因。

### 2.1 输出预留不能省

四行里最容易省掉的是输出预留，省掉它的表现是回答被截断：`finish_reason` 是 `length`，而多数调用方不检查这个字段。预留多少取决于答案的分布，取 300 遇到长答案问题会截断，取 1000 则挤掉检索，可行做法是按查询类型给不同预留，并用第 13 章的分流决定走哪条。

预留是一个业务决定，不是技术参数：它决定了这个系统能给出多长的答案。

### 2.2 工具清单可以按需给

工具清单是最容易被忽略的一块，因为看起来很小。示例里 29 token 是因为只有三个工具；真实系统有二十个工具时，清单能到 800 token。三种处理方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| 全量给 | 每次调用都带完整清单 | 800 token 的固定成本 |
| 按意图筛 | 第 13 章分流时决定走哪组工具 | 需要维护意图到工具的映射 |
| 分层加载 | 先给"工具目录"，模型要哪个再展开 | 多一轮调用 |

第二种最常见：分流已经知道这是一条退货请求，就只给退货相关的五个工具，收益不只是 token，还有准确率——工具越多，模型选错的概率越高。第三种在工具极多时才有必要，它把清单本身变成检索问题，代价是多一轮往返。

工具清单的预算问题，本质是给了用不上的工具。把清单按场景收窄，比压缩描述文字更有效。

### 2.3 系统提示决定预算

系统提示是唯一一个写多少就占多少的槽位，它也最容易被写成散文：一段"专业、友好、耐心"的客服描述占了八十 token，对行为的影响接近于零。把系统提示压到必要的部分，一般只要四块：角色与范围、不能做的事、输出格式、拒绝的方式。

判断一段话该不该留：删掉它之后系统的行为会不会变，不会变就删。另一个浪费是把例子塞进系统提示。

### 2.4 任务槽位更可靠

最容易被低估的是任务。它指的不是用户的话，而是当前这件事进展到哪了：目标、确认了的事实、还差什么。它与历史的区别是结构：历史是一串消息，任务是一组字段，不随对话变长而变长，也不受裁剪影响。一个具体的例子：用户说我上周买的耳机 A1001 还没到，历史里这句话会随会话滚远，任务槽位里固定写着订单 A1001、已发货。代价是要有人写抽取逻辑，这属于第 24 章的任务状态设计，但它把会增长的内容变成了大小固定的内容，所以优先级高于历史：历史可以被裁，任务不行。

### 2.5 记忆槽位：条数由预算定

记忆槽里放的是召回结果，不是记忆库的全部。这个槽位的预算通常是几十到几百 token，一条记忆二十到四十 token，所以能放进来的只有三到十条。第一个决定因此不是取哪几条，是放几条：

| 方式 | 做法 | 偏差 |
|---|---|---|
| 固定条数 | 取前 5 条 | 5 条里有 3 条讲同一件事时浪费；只有 2 条相关时硬凑 |
| 分数阈值 | 取高于阈值的 | 阈值难定：记忆的分数分布跨用户、跨时间都会漂 |
| 分层配额 | 语义 2 条、情景 2 条、程序 1 条 | 某一层不相关时仍然占位 |

实践里用后两种合起来：先按层给上限，层内再按分数取，既保证三层都有代表，又不会硬凑。条数还要随请求变：简单请求一条语义记忆就够，复合请求需要语义、情景、程序各一条，判断依据是分流给出的请求类型。记忆槽还有一条要求：召回结果必须带来源。一句"根据以往偏好，该用户免运费"如果错了，用户要能指出是哪条记忆。这里的边界要划清：取哪几条由记忆层的分数决定，放几条、放在哪、挤掉谁由装配决定；`recall` 收到的 `k` 是这里算出来的。

## 三、预算与抢占

超预算时，必须丢东西。丢什么、按什么顺序丢，是装配的核心决定。运行 `code/knowledge/ch19_context/assembly.py` 的抢占输出：

```
=== 2. 预算 600 token 时的抢占 ===
  完整装配 721 token，超预算 121
  抢占后 588 token，历史剩 5 轮，块剩 8 条
  丢弃顺序 ['最旧的一轮对话', '最旧的一轮对话', '最旧的一轮对话']
```

这次丢的是三轮最旧的对话，检索一块没丢。顺序不是随意的，每一行都有自己的判据：

| 先丢 | 理由 | 例外 |
|---|---|---|
| 最旧的对话 | 越久的信息越可能已经过时 | 用户在最开始给的关键约束 |
| 情景记忆 | 它的价值随时间衰减，丢了影响"贴不贴切" | 用户刚说过、与本轮直接相关的 |
| 语义与程序记忆 | 它们属于依据的一部分，丢了会改变正确性 | 本轮明显用不上时（比如闲聊） |
| 排名最低的块 | 相关性最低，去掉损失最小 | 全部块都低分时，问题在检索 |
| 工具清单 | 只保留本轮可能用到的 | 模型会依赖完整清单 |
| 系统提示 | 永不丢 | — |

第一行的例外值得单独处理：用户在第一轮说的"我有三张订单"，到第十轮仍然有效，最旧不等于最不重要，可行的做法是把关键事实抽出来放进任务状态（第 24 章）。第四行的例外说明抢占只能解决内容太多，不能解决内容不对：八块全是低分时，丢到只剩两块也不会让答案变好。

### 3.1 抢占顺序为什么不能反

如果先丢检索、后丢历史，历史保留完整而检索被裁到一两块：追问在历史里都能找到上下文，但答案的依据没了，模型开始凭记忆答，而第 14 章讲过，没有依据的答案就是编。反过来先丢历史，模型少了一些对话上下文，但仍能基于检索到的政策回答。依据比对话连续性更重要：依据决定答得对不对，对话连续性决定答得顺不顺。这条顺序也有例外：多轮任务里历史本身就是依据，这时该把历史里的关键事实提炼成结构化状态。

### 3.2 记忆槽的抢占顺序

记忆的抢占与历史不同：历史是一轮一轮地涨，记忆是一条一条地减，所以它的规则不是从旧到新，而是按层。按层的依据与下一章的衰减规则相同：衰减只作用于情景层，抢占也只先动情景层。情景记忆说的是一次经历，丢掉它，答案从记得上次退货原因退到按政策办，变粗但不变错；语义与程序记忆丢掉会让答案变错。

一个可操作的规则是给记忆槽设下限：至少留一条语义与一条程序，低于下限就转裁历史。理由是一笔账：记忆总共才几十到几百 token，而历史动辄上千。最后一点与观测有关：检索块被裁光就开始编，记忆被裁光只是答得不够贴切，用户只会觉得这次不如上次好用，所以记忆槽的占用要单独记一个数。

### 3.3 换三档预算看结果

同一份内容，预算给 600、800、1200，结果差别很大：预算 600 时丢掉三轮历史，检索八块全留；800 时只丢一轮；1200 时什么都不丢。它能回答一个问题：多数请求是刚好够还是差很多。九成请求在 800 以下，1200 就是浪费；三成超过 1200，说明策略整体偏紧。

做法很简单：每次调用前记录按最宽松的分配需要多少 token，再与预算比，这个数就是预算压力。它还随会话轮次增长，第一轮几乎不超，第十轮开始频繁超，而用户感受到的是聊得越久越容易答错。

### 3.4 抢占要留余量

抢占的触发条件是超过预算。如果每次都恰好压到上限，任何波动都会触发一次抢占，而这些波动本身没有意义：多一条工具返回、多一轮寒暄。留出 10% 的余量是常见解法，代价是可用空间少一成，好处是抢占从每轮发生变成偶尔发生。

余量还能应对 token 估算误差：不同 tokenizer 对同一段文本的计数可能差几个百分点，尤其在中英混排时。把预算当作目标而不是上限，是这个环节最实用的一条经验。

### 3.5 用户能感知到的抢占

抢占发生在服务端，后果用户能看到。第一种是忘了刚才说的：刚聊过的内容下一轮就不认了。第二种是答得越来越短：检索块被历史挤掉，模型只能用常识答。第三种是引用消失：块被裁到零条时，答案里不再有编号。四种里第一种最容易被缓存或状态掩盖，第四种最难排查，共同点是从单轮看都正常，只有多轮放在一起才看得出规律。所以要靠会话级日志发现：看每轮槽位分布在会话内的走势。

## 四、裁剪历史：trim_messages

框架提供了裁剪历史的工具，它只动消息列表，不动系统提示，用法见 `code/knowledge/ch19_context/assembly.py`：

```python
trimmed = trim_messages(
    messages,
    max_tokens=150,
    strategy="last",
    token_counter=count_messages,
    include_system=True,
    allow_partial=False,
)
```

四个参数各管一件事：

| 参数 | 作用 |
|---|---|
| `max_tokens` | 裁到多少 token 以内 |
| `strategy="last"` | 从最新往回保留 |
| `token_counter` | 用哪个函数数 token |
| `include_system=True` | 系统提示不计入裁剪、且始终保留 |

跑一遍：

```
=== 3. trim_messages 只裁历史，不动系统提示 ===
  消息 33 条 360 token -> 13 条 148 token
  保留的第一条 '用户'…
  系统提示在最前 True
```

33 条裁到 13 条，系统提示仍在最前。`allow_partial=False` 保证不会把一条消息从中间切开，切开的消息会让模型看到半句话，比丢掉更糟。`token_counter` 是这里最容易写错的地方：它收到的是一个消息列表，不是字符串，写成 `len(enc.encode(text))` 会在 `SystemMessage` 上报 `TypeError: a bytes-like object is required`，正确写法是按消息逐条取 `content`：

```python
def count_messages(messages) -> int:
    """trim_messages 的 token_counter 收到的是消息列表。"""
    total = 0
    for m in messages:
        content = m.content if hasattr(m, "content") else m
        if isinstance(content, str):
            total += ntok(content)
    return total
```

报错信息完全指向别处，看起来像 tiktoken 的问题，实际是接口签名不匹配。

### 4.1 裁剪之后历史会"断层"

从最新往回保留，切掉的是开头。如果第 1 轮用户说了"我有三张订单"，第 12 轮开始裁剪时这句就没了，而第 13 轮的"帮我查一下第二张"仍然需要它。两种处理方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| 摘要 | 把被裁掉的历史压成一段摘要，放在最前 | 一次模型调用，可能丢细节 |
| 抽事实 | 把关键信息抽成结构化状态 | 需要定义"哪些算关键" |

第一种最通用：把被裁掉的历史压成一段摘要放在最前，风险与第 16 章的摘要相同，它可能丢掉例外条款，所以只用于对话的连续性，不用于事实依据。第二种更可靠但更难：先定义状态字段再写抽取逻辑，这基本就是第 24 章的任务状态设计。

### 4.2 摘要怎么做才不丢关键信息

摘要的写法有三种，代价与风险递增。滚动摘要是每裁掉一段就与上一版合并，问题是误差累积。分段摘要保留每段摘要按需拼接，避免误差累积，代价是数量增长。三种做法有一个共同问题：摘要本身也占预算，一段 200 token 的摘要可能省下 600 token 的历史，但摘要会随对话变长、最后也要裁剪，它只是把增长换成了缓慢增长。历史超过预算的三倍时，摘要才开始划算。

### 4.3 裁剪的两种语义

裁剪有两种语义，混淆会出问题：一种是丢内容，被裁掉的历史真的消失；另一种是移出窗口但保留可检索，历史仍存在存储里，需要时取回。第二种更安全：历史全文存进一个可检索的存储，或者干脆用第 20 章的长期记忆，装配时只放最近几轮，被裁掉的部分由模型调用一个回忆工具取回。

代价是要维护存储、检索接口与回忆判断；收益是长度不再随会话线性增长。从裁剪即丢失到裁剪即可检索，是上下文管理从被动转向主动的分界线。

## 五、拼接顺序与编号

装配的产物是消息列表，不是一段字符串。用模板把它固定下来，写法见 `code/knowledge/ch19_context/assembly.py`：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", SYSTEM + "\n" + TOOLS),
    ("human", "对话历史：\n{history}\n\n<资料>\n{context}\n</资料>\n\n问题：{question}"),
])
```

```
=== 4. 带编号的模板 ===
  渲染后 2 条消息，共 598 token
  编号出现 8 处
```

三个细节。第一，资料用边界标记包住：`<资料>` 与 `</资料>` 让模型知道哪一段是外部内容、哪一段是指令，这是第 14 章 3.4 讲过的隔离。第二，编号在块前面：`[1] 内容` 而不是 `内容 [1]`，前置编号让引用检查用正则就能抽出来。

第三个细节是历史与资料分开：历史是说过的话，资料是依据的文本，混在一起会让模型把用户的自述当成政策依据，第 13 章那个用户称商品有瑕疵与政策规定质量问题的混淆就是这样产生的。

### 5.1 顺序影响注意力

同样的内容放在不同位置，模型的使用率不同：开头的系统提示最稳，中间的检索内容最容易被忽略，末尾的问题最能被响应。所以常见的顺序是系统、历史、资料、问题：问题紧挨生成位置，资料是回答前最后看到的依据。这个顺序不是绝对的。长资料时把资料放在末尾会让模型读到哪答到哪，这时可以改成系统、资料、历史、问题，让资料前后都有指令包裹。顺序要按模型在哪一步需要什么排，不是按人类阅读习惯排。

### 5.2 顺序与前缀缓存的关系

前缀缓存按从开头起最长的相同部分计费，装配顺序直接决定它能不能命中。如果系统提示在最前且内容固定，每次调用都能命中这一段；如果顺序是历史在前，历史每轮都变，系统提示就永远不在前缀里。

所以顺序不只是注意力问题，也是成本问题，原则是越稳定的内容越往前放：系统提示最稳定，放最前；工具清单次稳定；历史与检索每轮变，放后面。这条原则还有一个副作用：把当前时间、用户昵称这类每次都变的内容拼进系统提示，会让前缀缓存彻底失效，第 13 章说过这一点。

### 5.3 编号与引用要保持一致

编号决定了引用能不能被校验。第一，编号在装配时分配，不在检索时分配：如果检索时就编号，被裁掉的块会留下空号。第二，编号要在会话里保持稳定：同一个块在第二轮被再次召回时编号变了，用户看到的引用就指向了别的内容，可行的做法是编号与块 id 绑定。第三，编号要能回指原文：`[1]` 必须能映射到一个块 id，块 id 必须能映射到原文位置，这条链断在任何一环，用户点开引用都会落空，第 14 章讲引用时强调过可回指。

### 5.4 工具清单放最后

有一种优化看着合理，实际会破坏两件事：把工具清单从系统提示里拿出来，放到用户问题后面，理由是模型在生成前最后看到的是工具。它破坏的第一件事是缓存：工具清单被移出后，命中范围缩小，成本反而可能上升。它破坏的第二件事是约束关系：工具说明属于指令，用户问题属于数据，把指令放到数据后面会让隔离问题重新出现，只是这次错位的是工具，第 14 章 3.4 讲过。顺序每调整一次，都要同时检查缓存与隔离。

## 六、压缩

预算不够时，除了丢内容，还可以压内容。压缩的极端形式是摘要，温和形式是只留与问题相关的句子，下面这段输出来自 `code/knowledge/ch19_context/assembly.py`：

```
=== 5. 压缩：把块压成与问题相关的一句 ===
  3 块 123 token -> 3 块 59 token
    '质量问题导致的退货，往返运费由商家承担。'
    '非质量问题退货，运费由买家承担。'
    '生鲜类商品不支持无理由退货。'
```

三块从 123 token 压到 59，每一块只剩与退货运费相关的那句，`LLMChainExtractor` 是这样一个抽取器，它把每块丢给模型并抽出与问题相关的片段。压缩有三个代价：

| 代价 | 说明 |
|---|---|
| 一次模型调用 | 每块一次，5 块就是 5 次，延迟与成本都上去 |
| 可能抽错 | 模型可能抽掉关键限定（"生鲜除外"） |
| 引用对不上 | 抽出来的句子在原文里可能不连续，引用回指会错位 |

第三条最容易被忽略：压缩后的文本不是原文的连续片段，用户按引用去核对时会在原文里找不到一样的句子，所以压缩只适合给模型看，上下文用压缩版，引用仍指向原文。收益边界也很清楚：块数少、每块不长时，压缩的成本超过收益，只有长块加多块同时成立时才划算。

### 6.1 更便宜的压缩：按句筛

不做模型调用，用查询与句子的字面重合筛一遍，也能压掉一半：

| 方式 | 成本 | 质量 |
|---|---|---|
| LLMChainExtractor | 每块一次调用 | 高，能理解语义 |
| 句子级关键词打分 | 微秒级 | 中，只能处理字面重合 |
| 只取前 N 句 | 零 | 低，经常丢掉结论句 |

第二种在本章的语料上够用，因为政策条款的措辞与问题高度重合；第一种适合问题与原文用词差异大的场景；第三种基本不可取，因为政策文档的结论常常在最后一句。

### 6.2 压缩什么时候才划算

压缩的收益是省下的 token 乘单价，成本是一次调用。省下的 token 要足够多：一块 100 字的文本抽成一句 20 字，省 80 token，所以小块的压缩几乎总是亏的。块数要足够少：压缩是每块一次调用，如果一次调用能压掉 300 token、成本相当于 2000 token，至少要七块才回本。粗略判据是：块长超过 200 字、块数超过 5 块，才值得压。还有一个隐蔽成本：压缩后的句子在原文里可能不连续，用户核对时会觉得引用对不上，所以装配时要同时保留两份。

### 6.3 压缩与裁剪的分工

压缩与裁剪解决的是同一个问题的两面：内容太多。裁剪删掉整个单元，成本为零，但信息全失；压缩保留部分信息，成本是一次调用。先裁剪还是先压缩，取决于丢掉的那部分信息有没有用：被裁的块排名很低就直接删掉，只有排名高但太长的块才值得压。

换句话说：裁剪按相关性做，压缩按长度做。

### 6.4 一个常见的浪费：重复的块

装配时经常出现重复内容：同一份政策的不同块因为切块重叠被同时召回，占了两份预算，提供的信息只有一份。去重是零成本的压缩：按内容指纹或高相似度合并，只留一条，不需要模型调用。

判断重复的方法很简单：块之间的余弦相似度超过 0.95 基本可以认为是同一内容，成本是几十次向量比较，可以忽略。

## 七、装配要能被观测

装配错了外部看不到：回答变短、开始编造、引用对不上，每一种都可能是别的原因，所以要记录装配的结果，而不只是它的输入。至少要记五个数：

| 记什么 | 用来回答 |
|---|---|
| 各槽位与记忆子项各占多少 token | 预算花在哪了 |
| 被丢弃的条数与类型 | 抢占是否频繁 |
| 输出预留 | 截断是不是预留不足 |
| 最终消息总 token | 有没有超窗口 |
| 是否触发压缩 | 压缩的代价值不值 |

第一个数最有诊断价值：历史长期占 50% 以上，说明该做摘要或状态抽取了；检索长期不到 10%，说明预算配得不对。第五个数常被忽略：压缩触发的频率高，说明预算长期紧张，而不是压缩很好用。

### 7.1 装配应该有单测

装配是纯函数：给定系统提示、历史、块、预算，输出一段消息，这意味着它可以被单测覆盖，而且不需要模型。三个用例分别覆盖：刚好超一点（断言丢掉最旧的一轮）、系统提示加历史就超了（断言系统提示完整保留）、一块都留不下（断言仍返回合法结果），而不是抛异常。三个用例加起来不到五十行。装配的错误无法从输出倒推：一段被裁掉的历史，在最终回答里看不出痕迹。

### 7.2 装配的四种失败模式

线上出问题时，装配的问题经常被误判成别的原因。第一种是回答变短，原因是输出预留不够，看 `finish_reason` 是不是 `length`。第二种是回答开始编，原因是检索块被裁光了，看装配记录里检索槽位的 token 数。第三种是答非所问的连续性，原因是历史被裁掉了开头，判断方法是看被裁掉的轮次里有没有关键约束。第四种是引用对不上，原因是编号在裁剪之后重新分配。四种里有三种的根因都是裁掉了不该裁的，这也是为什么抢占顺序要写死。

### 7.3 观测数据怎么用

记下来的五个数，用法是回答三个具体问题。问题一是预算配得对不对：检索长期低于 15% 说明预算给少了，第 18 章那些检索手段的效果进不了上下文；历史长期超过 40% 说明该做摘要或状态抽取。问题二是抢占是否频繁：发生抢占的请求数除以总请求数，低于 5% 属于正常波动，高于 20% 说明预算整体偏紧。问题三是压缩值不值：比较压缩省下的 token 与调用成本。三个问题都能用装配自己的记录回答。

## 八、边界

**装配不是越紧越好。** 算到最后一 token，任何波动都会触发抢占，留一成余量能让系统稳定。

**抢占只能解决容量问题。** 内容不对、检索不到，丢多少都救不回来。

**输出预留是产品决定。** 被截断的回答在用户看来是模型没写完。

**压缩要区分给模型看与给用户看。** 引用必须指向原文，压缩只影响上下文。

**裁剪历史要处理断层。** 从最新往回保留会丢掉开头的关键约束，要用摘要或状态补上。

**装配的改动要能被回滚。** 抢占顺序、预算值、压缩开关都应该是配置。

**装配不该感知业务细节。** 它只应该知道各类内容的 token 数与优先级，一旦开始写业务判断，它就变成了藏起来的业务规则库。

**装配只管放几条，不管取哪几条。** 记忆的取舍是打分问题，归记忆层；混在一处就无法判断是没召回还是没放进去。

## 这一章建立的 7 件事

装配是本章唯一一处"看得见全部输入"的地方，因此它也是唯一一处能做预算权衡的地方；其余环节都只看到自己那一段。

1. 装配是唯一把四个槽位放在一起权衡的地方，且必须每次调用前算一次，因为历史与检索都在增长；记忆槽内部还要分出会话历史与跨会话记忆两份。
2. 预算按"系统、任务、记忆、检索、输出"分，输出预留是业务决定，不能省。
3. 抢占顺序先历史后检索：依据比对话连续性更重要；例外是多轮任务，这时该把关键事实抽成状态。
4. 记忆按层抢占：情景层先丢，语义与程序层后丢，并给记忆槽留一个下限——它总共才几十到几百 token，裁历史更划算。
5. 记忆的"取哪几条"归记忆层打分，"放几条、放哪里"归装配；`recall` 的 `k` 是装配算出来的。
6. `trim_messages` 只裁历史、保住系统提示；`token_counter` 收到的是消息列表，写成字符串计数会报一个指向别处的错。
7. 拼接顺序按"模型在哪一步需要什么"排，资料用边界标记包住并前置编号；压缩只给模型看，引用仍回指原文。
