## 一、十步之后的三种症状

同一个任务跑两遍，第一遍答可以退，第二遍答不能退；把历史裁剪到最近几条，同一个问题答还没查过订单；进程重启，查到的政策窗口不见了。三种症状出现在三个位置，成因是同一个：循环把跨步骤要保持一致的东西全放在了消息列表里，见第 8 章。

第 7 章的循环只有两个变量，`messages` 和步数。步数不在消息里，它在代码里被累加、被比较、被用来终止，它已经是一个状态字段，只是没有人为它定义结构。任务长起来之后，重试次数、查过的单号集合、当前阶段都会排进同一类，其中步数用于终止，动作指纹集合用于查重，失败次数用于降级。

这些变量留在函数局部变量里的后果很具体：换一个函数就看不见，恢复时存不下来，两个分支各写一份时互相覆盖，守卫读到的步数与状态里记录的步数也可能不是同一个数。

把这些变量收进一个对象，就是 State。第一版最省事的收法是“不收”，代码在 `code/knowledge/ch24_state/state.py` 里：

```python
from dataclasses import dataclass, field


@dataclass
class V1:
    """把整段对话当状态，放什么全靠 messages。"""
    messages: list[dict] = field(default_factory=list)
```

它的字段只有一个：

```
  V1 等于聊天记录
    messages     list[dict]
```

这一版的问题不是字段少，是它根本没有状态这个东西。任务进行到哪一步、已确认哪些事实、下一步该做什么，全部要在需要时从历史里重新推断：遍历消息、挑出 `tool_calls`、解析 JSON 参数、按业务口径去重。判断一个 agent 有没有状态，看一个操作：把消息列表清空，还能不能说出任务做到哪了。

## 二、历史与状态的分界

两者的差别不在内容多寡，在四个属性：

| | messages（历史） | state（状态） |
|---|---|---|
| 内容 | 按时间排列的每条消息 | 当前掌握的事实与结论 |
| 结构 | 线性、只追加 | 字段化、按需更新 |
| 谁读 | 模型，作为输入 | 代码，用来做判断 |
| 会变少吗 | 会，按窗口预算裁剪 | 不能，裁了就丢事实 |
| 恢复时需要吗 | 完整版需要 | 必需 |

第四行是决定性的不对称：历史可以变少，状态不能。一旦把两者合成一份存储，裁剪历史这个纯成本动作就变成了删状态这个语义动作，第一种症状里的裁剪问题就在这里，不是裁剪写错了，是裁剪的对象里混进了不该被裁的东西。

### 2.1 裁剪改动了答案

下面这段代码是 V1 回答“查过订单 A1001 吗”的唯一办法，在 `code/knowledge/ch24_state/state.py` 里：

```python
def sample_messages() -> list[dict]:
    """一段六条消息的历史：两次调用 get_order，参数完全相同。"""
    call = {"id": "c1", "type": "function",
            "function": {"name": "get_order", "arguments": '{"order_id": "A1001"}'}}
    call2 = {"id": "c2", "type": "function",
             "function": {"name": "get_order", "arguments": '{"order_id": "A1001"}'}}
    return [
        {"role": "user", "content": "订单 A1001 还能退吗"},
        {"role": "assistant", "content": None, "tool_calls": [call]},
        {"role": "tool", "tool_call_id": "c1", "content": '{"status": "已签收", "signed_days_ago": 3}'},
        {"role": "assistant", "content": None, "tool_calls": [call2]},
        {"role": "tool", "tool_call_id": "c2", "content": '{"status": "已签收", "signed_days_ago": 3}'},
        {"role": "assistant", "content": "可以退"},
    ]


def scanned_order_ids(messages: list[dict]) -> tuple[list[str], int]:
    """V1 的做法：扫全量历史，解析每个工具调用的参数，再去重。"""
    seen: list[str] = []
    parsed = 0
    for m in messages:
        for call in m.get("tool_calls") or []:
            if call["function"]["name"] != "get_order":
                continue
            args = json.loads(call["function"]["arguments"])
            parsed += 1
            if args["order_id"] not in seen:
                seen.append(args["order_id"])
    return seen, parsed
```

同一份历史，裁到只剩最后一条回答，再问一次：

```
=== 2. 从历史推断状态：全量与裁剪后 ===
  全量：扫 6 条消息，解析 2 次工具调用，去重后 ['A1001']
  裁剪到最近 1 条：扫 1 条消息，解析 0 次工具调用，得到 []
  同一个任务，历史一裁，答案就变了
```

两行输入只差裁过与没裁过，答案从 `['A1001']` 变成 `[]`。第 8 章讲循环内的单条消息裁剪，第 19 章讲上下文装配里的预算与压缩，两处都把裁剪当成成本手段；在 V1 里这个成本手段同时是语义开关，一个只想省钱的动作改变了后续所有判断的依据。

### 2.2 从历史推断的三次开销

把状态当成历史的函数，代价落在三个地方。第一是每次读都要扫全量，十步的任务每次判断扫十条，一百步扫一百条。第二是结果依赖历史的完整性，历史一被裁剪或压缩，推断结果就变，而系统不记录这个差异。第三是推断口径会散落，一个函数算查过哪些单号，另一个算还差哪些，改一处就三处不一致，第 19 章的装配也依赖这份口径。

三条里第二条最隐蔽，它把性能优化和正确性绑在了一起：性能优化可以随时回滚，正确性变化不能。把历史压成一段摘要当状态也不行，摘要能省窗口，但它是不可逆的有损压缩，被压掉的字段再也查不回来。

摘要能回答任务做到哪了，回答不了一共查过哪些单号，后者需要一个精确的集合。摘要属于历史那一侧，见第 19 章。

### 2.3 状态不是历史的子集

有人会问，既然状态都能从历史推出来，把历史留着，需要时推一次不就行了。不行，因为有些信息在历史里根本不存在，四个例子：

- 版本。要知道这个结论是基于哪一版事实算的，历史里没有版本这个概念，消息只有先后顺序，没有第几版事实的标记。
- 来源。同一条签收 3 天，是工具返回的还是模型自己写的，在历史里都表现为一段文本；状态可以把来源单独存成字段，历史不能。
- 写入次数。这个结论被改过几次只能由写入方统计，历史里两个不同的结论只是两条消息，看不出它们是同一个字段的两次覆盖。
- 时间。历史有顺序，没有可信的时间戳，一条工具返回是什么时候取的，只能由写入方在写的时候记下来。

所以状态不是历史的投影，是另一份数据：历史记录过程，状态记录当前值。两份都要存，第 25 章会看到，恢复时既需要状态做到哪了，也需要历史当时说了什么。

## 三、字段从历史里抽出来

第二版把任务字段从历史里拿出来，固定成几个字段，实现在 `code/knowledge/ch24_state/state.py` 的 V2 里：

```python
from dataclasses import dataclass, field


@dataclass
class V2:
    """把任务状态从 messages 里抽出来，字段固定。"""
    messages: list[dict] = field(default_factory=list)
    order_id: str | None = None
    eligible: bool | None = None
    reason: str | None = None
```

字段清单变成四个：

```
  V2 抽出任务字段
    messages     list[dict]
    order_id     str | None
    eligible     bool | None
    reason       str | None
```

三件事立刻变好：可以查询，`state.order_id` 一次判空；可以裁剪，裁 `messages` 不影响字段；可以恢复，存字段比存历史小得多。代价是字段固定、任务变化，换一个任务要改类定义，一次任务里出现计划外的信息没有地方放。

### 3.1 第三版：按生命周期分类

第二版按这个任务需要什么设字段，第三版按这个字段会被写几次、被谁写设字段，V3 在同一份 `state.py` 里：

```python
@dataclass
class V3:
    """输入只写一次，事实只增，结论可覆盖，计数只增。"""
    messages: list[dict] = field(default_factory=list)
    user_intent: str = ""                       # 输入
    facts: list[tuple[str, Any, str]] = field(default_factory=list)   # 事实：内容 + 来源
    eligible: bool | None = None                # 结论
    overwrites: int = 0                         # 计数

    def add_fact(self, key: str, value: Any, source: str) -> None:
        self.facts.append((key, value, source))

    def fact(self, key: str, default: Any = None) -> Any:
        """同名事实取最新一条。"""
        for k, v, _ in reversed(self.facts):
            if k == key:
                return v
        return default

    def set_conclusion(self, value: bool) -> None:
        if self.eligible is not None and value != self.eligible:
            self.overwrites += 1
        self.eligible = value

    def version(self) -> int:
        """事实只增，条数天然是一个单调版本号。"""
        return len(self.facts)
```

字段清单与类别：

```
  V3 按生命周期分类
    messages     list[dict]                 历史
    user_intent  str                        输入
    facts        list[tuple[str, Any, str]] 事实
    eligible     bool | None                结论
    overwrites   int                        计数
```

四类的区别不是命名习惯，是写入规则不同：

| 类别 | 写几次 | 谁写 | 例子 | 并发后果 |
|---|---|---|---|---|
| 输入 | 1 次 | 调用方 | 用户意图、任务参数 | 不需要处理 |
| 事实 | N 次，只增 | 工具结果 | 查到的订单、政策、日志 | 可累加 |
| 结论 | N 次，覆盖 | 模型判断 | 是否可退、下一步 | 后写者赢，需记录 |
| 计数 | N 次，只增 | 循环 | 步数、覆盖次数 | 需原子或锁 |

分好类，后面两节的结论才有落点：事实与计数的并发做法是累加，结论的并发做法是串行化或裁决。一开始就把订单状态和是否可退放进同一个字段，这两套做法会打架，一个要保留每次结果，一个要只保留最后一次。

### 3.2 三个版本的回答

同一个问题查过订单 A1001 吗，跑 `code/knowledge/ch24_state/state.py` 第三段看三个版本各自要做什么：

```
=== 3. 三个版本回答「查过订单 A1001 吗」 ===
  V1: 扫 6 条消息，解析 2 次工具调用，去重后 ['A1001']
  V2: 判空一次，order_id='A1001'
  V3: 读 facts，得到 [('signed_days', 3, 'get_order'), ('window_days', 7, 'get_policy')]
      fact('signed_days')=3，版本=2
```

V2 那行看着最省，但丢了一个信息：查到的是什么，`order_id` 非空只说明查过，不说明结果。V3 的 `facts` 保留内容，也保留来源和条数：来源用于追溯，结论被驳回时能指出它算自哪次工具返回；条数用于判定新鲜度，新事实进来一条，用旧事实算出的结论自动过期。

三个版本的分工是：V1 说明没有状态也能跑，代价是每次现算；V2 说明抽出字段能解决查询与裁剪；V3 说明分类才能解决失效与并发。V3 的代价是 `facts` 只增，同一单号查两次会留两条记录，第 25 章恢复时要按 key 取最新。

## 四、放什么不放什么

字段一旦可以随手加，State 会变成杂物间。筛选按顺序问四个问题，第一个答否就不用往下问。问题一是后续步骤会用到它吗，不会就是局部变量；问题二是它需要跨步骤保持一致吗，某一步用来排序的临时列表不需要。

问题三是它来自外部还是模型，这决定它进事实还是结论：签收 3 天来自工具是事实，来自模型推断是结论，混在一个字段里就无法区分该信谁。问题四是它会被改几次，这决定 reducer。第三问和第四问的顺序不能换，反过来会得出只写一次所以不用管来源的错误结论。

### 4.1 该进与不该进

两列的判据同一条：这个字段进状态之后，后续步骤读它会不会读到变质的内容。

| 该进 State | 不该进 State |
|---|---|
| 用户原始意图 | 本轮拼好的提示词 |
| 已确认的事实（订单、政策） | 模型生成的推理过程（除非要审计） |
| 判定结论与它的依据 | 临时的排序、格式化结果 |
| 已尝试过的路径 | 每个 token 的流式片段 |
| 步数、失败次数、成本计数 | 复制的常量配置 |

右边第一行是可再生，提示词由意图、事实、模板拼出来，存了就有两份可能不同步的副本；第二行是归属错误，推理过程属于轨迹 trace，混进状态会被投影给模型；第三行是寿命太短；第四行是粒度太细，流式片段是输出过程，不是任务事实。

左边那一行值得展开：结论要带着依据一起存。`eligible` 单独存在时没人知道它是根据什么判的，加一个 `basis` 字段引用哪几条事实，驳回时才能说清哪条依据不支持它。混合字段的典型是 `status`，工具返回已签收和模型判断这笔可以退都被写成同一个字段，下游无法判断它是原始事实还是加工结论，第 23 章讲过裁判要能给出理由。

### 4.2 三处容易多出来的字段

还有三处字段经常被顺手加进来：

| 字段 | 为什么不该在 State 里 |
|---|---|
| `last_error` | 只在当前步骤有效，下一步就过期 |
| `current_prompt` | 拼出来的东西，可再生产 |
| `debug_info` | 排查信息，属于 trace |

第一行的过期是实质问题。`last_error` 写进状态就成了一个一直存在的事实，后续步骤可能把它当成这个工具坏了来推理，错误应该记成一条带来源的事实。中间那行是可再生原则，能从其他字段推出来的不要存。最后一行是分类错误，调试信息属于 trace，混进状态后会跟着投影进窗口。

### 4.3 三份并列存

结构化状态不替代历史，两者并列存，都要落盘，代码见 `code/knowledge/ch24_state/state.py`：

```python
@dataclass
class V3b:
    """结构化状态：只放需要跨步骤保持一致的内容。"""
    user_intent: str = ""
    facts: list[str] = field(default_factory=list)
    eligible: bool | None = None


@dataclass
class Run:
    state: V3b = field(default_factory=V3b)              # 结构化，几 KB
    messages: list[dict] = field(default_factory=list)   # 历史，可能几百 KB
    trace: list[str] = field(default_factory=list)       # 轨迹，用于归因
```

运行结果：

```
=== 4. State、messages、trace 三份并列 ===
  state 字段 ['user_intent', 'facts', 'eligible']
  state 事实 1 条，messages 6 条，trace 2 条
  序列化后 state 79 字节，messages 651 字节
```

三份而不是一份，因为三者的生命周期不同：

| 存哪 | 会被裁 | 会被持久化 | 会被投影给模型 |
|---|---|---|---|
| `state` | 否 | 是 | 部分，拼成摘要 |
| `messages` | 是 | 是（完整版） | 是 |
| `trace` | 否 | 可选 | 否 |

第三列最容易忽略：State 不是直接塞给模型的。把一个 dataclass 序列化后整段贴进提示词，会带进计数器、时间戳、来源字段名，这些内容占窗口，还会把注意力引到与任务无关的信息上，见第 25 章。

### 4.4 投影给模型的部分

State 是内部结构，提示词是外部接口，两者之间要有一个投影规则：

| 字段类 | 是否投影 | 形态 |
|---|---|---|
| 输入 | 是 | 原样 |
| 事实 | 是 | 摘要加必要的结构字段 |
| 结论 | 视情况 | 还要重算就不投影 |
| 计数 | 否 | 只用于守卫与排查 |

表的第三行是本章与第 23 章的交界。把一个待验证的结论投影给模型，它会倾向于沿用，这与自评失效是同一个成因：提示词里多一条看起来是结论的内容，会压低重新推理的意愿。状态层的做法是已经确定的给，正在判断的不给，判据是下一步要不要重算，这一点第 23 章讲过。

投影还有长度问题。State 序列化后很小，投影文本却会明显变长：为了让模型读懂，投影要把字段名、来源、时间讲成句子，一条事实可能从二十个字变成六十字，窗口预算要按投影后的长度留。

### 4.5 整份返回塞进状态

常见写法是把工具的完整返回整段存进状态的一个 data 字段，反例见 `code/knowledge/ch24_state/state.py`：

```python
ORDERS = {"A1001": {"status": "已签收", "signed_days_ago": 3, "channel": "app"}}


def store_raw(state: dict, key: str, payload: dict) -> None:
    """反例：把整份工具返回塞进状态。"""
    state.setdefault("data", {})[key] = payload
```

输出：

```
=== 5. 反例：整份工具返回塞进状态 ===
  存进去的键: ['channel', 'signed_days_ago', 'status']
  投影时会带上: status=已签收, signed_days_ago=3, channel=app
  channel 对判定没用，但它已经成了状态的一个字段
```

三个后果都出现在后续步骤，而不是当下：

| 问题 | 后果 |
|---|---|
| 无法区分事实与冗余字段 | 投影时全带上，浪费窗口 |
| 无法判断新鲜度 | 不知道它是何时、由哪次调用取的 |
| 无法跨版本演进 | 上游接口加字段，状态跟着变 |

最后一行最贵：把上游的原始结构存进状态，等于把上游的接口形状变成了自己的字段。上游加一个字段，状态多一个字段；上游改一个字段名，旧的检查点读不出来，见第 25 章。正确做法是提取需要的字段，并记下来自哪个工具的哪次调用。

### 4.6 失败也要记一条

状态里的事实来自工具。如果工具失败而状态什么都不写，后续所有推理都建立在还没查过这个假象上：

| 情况 | 状态里该留什么 |
|---|---|
| 工具成功 | 事实 + 来源 + 时间 |
| 工具报错 | 一条失败记录，不是空事实 |
| 工具超时 | 同报错，但标记为"可能已生效"（第 25 章） |

最容易漏掉的是报错那一行：查了但没查到与没查是两种不同的状态。工具报错时状态保持空白，下一步会以为还没查过，于是换个参数再查一次，这正是第 8 章讲过的换参数打转。把失败记成一条带来源的事实并投影给模型，否则它会重复同一个调用。

## 五、字段的生命周期

一个字段从声明到失效有五个时刻，每个时刻要回答一个问题：

| 时刻 | 问题 | 谁负责 |
|---|---|---|
| 声明 | 属于哪一类（输入/事实/结论/计数） | 设计时 |
| 首次写 | 谁写、什么时候 | 调用方或工具 |
| 更新 | 覆盖还是累加、要不要去重 | reducer |
| 读取 | 谁读、读到的是哪一版 | 消费方 |
| 失效 | 什么情况下不再有效 | 设计时 |

最后一行最容易被漏掉：结论会失效，查到新的订单状态之后，之前算出的是否可退就不成立了。没有失效规则的状态会让后续步骤基于过期结论继续推理，而症状出现在很远的地方。最省事的失效办法是版本号，事实只增不减，条数天然单调。

### 5.1 版本号让结论自动失效

带版本的结论实现在 `code/knowledge/ch24_state/state.py` 里：

```python
@dataclass
class TaskState:
    """带版本的结论：事实条数一变，旧结论自动读不到。"""
    intent: str
    facts: list[tuple[str, Any, str]] = field(default_factory=list)
    conclusions: dict[str, tuple[Any, int]] = field(default_factory=dict)
    overwrites: dict[str, int] = field(default_factory=dict)

    def add_fact(self, key: str, value: Any, source: str) -> None:
        self.facts.append((key, value, source))

    def version(self) -> int:
        return len(self.facts)

    def set_conclusion(self, key: str, value: Any) -> None:
        if key in self.conclusions:
            self.overwrites[key] = self.overwrites.get(key, 0) + 1
        self.conclusions[key] = (value, self.version())

    def get_conclusion(self, key: str) -> Any:
        entry = self.conclusions.get(key)
        if entry is None:
            return None
        value, version = entry
        if version < self.version():
            return None                     # 过期视同没有，调用方必须重算
        return value
```

一次两步任务里的演进：

```
=== 6. 结论的生命周期：事实一变，旧结论失效 ===
  步骤 0  版本 0  eligible=None
  步骤 1  版本 1  eligible=None
  步骤 2  版本 2  eligible=True
  步骤 3  版本 2  eligible=True，改主意 2 次
  步骤 4  版本 3  eligible=None（过期）
```

第一件事，事实一变结论全部失效：步骤 4 加了一条签收 4 天的事实，版本从 2 变 3，`eligible` 的版本还停在 2，读出来是 `None`。这个做法假设任何新事实都可能影响任何结论，但宁可多算一次。第二件事，失效等于没有，`get_conclusion` 返回 `None`，调用方必须重新计算，忘记检查就直接拿不到值。

第三件事，覆盖次数只统计改写：步骤 2 首次写 True 不算，步骤 3 改两次所以是 2。失效有三种触发方式：版本号最便宜，写事实时自动推进；显式标记依赖每个写入方都调用 `invalidate()`，漏一处就是静默错误；TTL 按时间过期，只适合缓存类结论。

### 5.2 阶段也是字段

字段之外，状态还有一个容易漏掉的维度：任务处在哪个阶段。阶段不是某一类字段的附属，它自己就是一个字段，取值是一个有限集合，形状见 `code/knowledge/ch24_state/state.py`：

```
初始化 → 取数中 → 判定中 → 已判定 → (修复中 → 已判定)* → 交付
              ↑                          |
              └──────── 重规划 ───────────┘
```

图里有两处值得注意。修复中是回边，必须带上限，同一产物最多修两次，见第 23 章，没有上限的回边就是反复震荡。重规划回到取数中而不是初始化，已经取到的事实仍然有效。阶段字段还决定投影什么、恢复从哪继续，第 25 章的检查点按阶段决定重放哪些步骤。

### 5.3 命名能暴露分类错误

命名约定能拦住三类分类错误：

| 约定 | 例子 | 拦住的错误 |
|---|---|---|
| 事实用复数或来源前缀 | `facts`、`fetched_orders` | 不会被写成单值覆盖 |
| 结论用判断句式 | `eligible`、`should_retry` | 一眼看出是结论 |
| 计数用 `n_` 或 `_count` | `n_steps`、`overwrites` | 不会被当成内容字段 |

最典型的是 `status`。一个叫 `status` 的字段，从名字看不出它是查到的事实还是算出的结论，前者只增，后者可覆盖，并发做法完全相反。改成 `fetched_status` 与 `derived_status`，分类就写在名字里了；命名不能替代分类，但它能让分类错误在评审时暴露，第 25 章的检查点读到的就是这些字段。

### 5.4 schema 演进

字段会变，任务可能跑几个小时，中间升级了代码，旧检查点还要能读。三条规则：

| 变更 | 必须做 |
|---|---|
| 新增字段 | 给默认值，不能是必填 |
| 删除字段 | 先标记废弃，读时忽略，写时不写 |
| 改语义 | 换字段名，而不是改现有字段的含义 |

最后一条最重要，改语义但保留名字是最危险的一种变更。旧检查点里那个字段是签收天数，新代码里它变成距离窗口剩余天数，读出来的值完全不是一回事，而且不会报错，类型一样，范围也重叠。读取旧数据需要一个显式的迁移函数，而不是靠 `getattr` 兜底，迁移函数在 `code/knowledge/ch24_state/state.py` 里：

```python
SCHEMA_V1 = {"intent": "A1001 能退吗", "facts": ["签收 3 天"], "schema_version": 1}


def migrate(raw: dict) -> dict:
    """读旧检查点：补默认值、换名字，不猜语义。"""
    if raw.get("schema_version") == 1:
        raw = dict(raw)
        raw["facts"] = [{"key": f"fact_{i}", "value": v, "source": "v1"}
                        for i, v in enumerate(raw["facts"])]
        raw["conclusions"] = {}
        raw["schema_version"] = 2
    return raw
```

```
=== 7. schema 演进：旧检查点用新代码读 ===
  旧检查点: {"intent": "A1001 能退吗", "facts": ["签收 3 天"], "schema_version": 1}
  升级之后: {"intent": "A1001 能退吗", "facts": [{"key": "fact_0", "value": "签收 3 天", "source": "v1"}], "schema_version": 2, "conclusions": {}}
  旧值仍在: facts[0]['value']='签收 3 天'，schema_version=2
```

迁移函数不猜语义：`facts` 从字符串列表变成对象列表，`migrate` 给它补上 `key` 与 `source`，`source` 填 v1 表示来路不明。补默认值可以，猜原意不行。`schema_version` 属于存储层，不属于 State，它为了读取而存在。

### 5.5 初始化的三个取值

任务开始时状态长什么样，决定了很多后续判断，三件事要定：

| 事 | 做法 |
|---|---|
| 必填字段 | 没有默认值，缺了就报错 |
| 可选字段 | 给 `None`，与"有值但为空"区分 |
| 计数器 | 全从 0 开始，包括 `overwrites` |

可选字段给 `None` 而不是空值，因为 `None`、空串、空列表语义不同：`facts=[]` 表示还没查，`facts=None` 表示这个任务不做事实收集；混用之后，查过但结果为空与没有查无法区分。必填字段用 dataclass 的无默认值参数，缺了在构造时就报错。

## 六、并发写为什么丢

第 22 章的 DAG 允许多个分支同跑。两个分支都要更新同一份状态时，覆盖写会丢数据。这不是理论风险，是三个字节码之间的空隙造成的。

### 6.1 两个分支同时写

示例把窗口固定下来：两个线程在同一道 barrier 上起跑，都先读旧值再写回。这里不调用模型，演示的是读-改-写的时序，属于原理演示而非模型实测，真实的工具调用窗口只会更长：

```python
def run_two(branch) -> None:
    """两个线程在同一道 barrier 上同时起跑。"""
    barrier = threading.Barrier(2)
    ts = [threading.Thread(target=branch, args=(barrier, i)) for i in range(2)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()


def overwrite_trial() -> tuple[int, int]:
    """读-改-写：两个分支各读一次旧值，再写回，必然丢一次。"""
    state = {"count": 0}

    def branch(barrier: threading.Barrier, i: int) -> None:
        barrier.wait()                      # 两个分支都先读到 0
        current = state["count"]
        time.sleep(0.005)                   # 放大读写之间的窗口
        state["count"] = current + 1

    run_two(branch)
    return state["count"], 2


def concat_trial() -> tuple[int, int]:
    """拼接后重新赋值：看着像追加，实际是整体换掉引用。"""
    state: dict[str, list[str]] = {"facts": []}

    def branch(barrier: threading.Barrier, i: int) -> None:
        barrier.wait()
        current = state["facts"]            # 读出整个列表
        time.sleep(0.005)
        state["facts"] = current + [f"fact_{i}"]   # 写回整个列表

    run_two(branch)
    return len(state["facts"]), 2


def locked_trial() -> tuple[int, int]:
    """加锁的读-改-写：不丢，但两个分支被串行化。"""
    state = {"count": 0}
    lock = threading.Lock()

    def branch(barrier: threading.Barrier, i: int) -> None:
        barrier.wait()
        with lock:
            current = state["count"]
            time.sleep(0.005)
            state["count"] = current + 1

    run_two(branch)
    return state["count"], 2


def append_trial() -> tuple[int, int]:
    """累加（reducer）：不读旧值，只把新元素并进去。"""
    state: dict[str, list[str]] = {"facts": []}

    def branch(barrier: threading.Barrier, i: int) -> None:
        barrier.wait()
        time.sleep(0.005)
        state["facts"].append(f"fact_{i}")

    run_two(branch)
    return len(state["facts"]), 2
```

四种写法各跑二十轮：

```
=== 8. 两个并行分支写同一字段：丢与不丢 ===
  覆盖写（读-改-写） 20 次里 20 次丢  期望 2 实际 1  [丢]
  拼接后整体赋值     20 次里 20 次丢  期望 2 实际 1  [丢]
  加锁的读-改-写     20 次里  0 次丢  期望 2 实际 2  [不丢]
  累加写 append      20 次里  0 次丢  期望 2 实际 2  [不丢]
```

第一行二十轮全丢，因为 barrier 保证两个分支都读到 0 之后才有一个写回。拼接后整体赋值同样全丢，虽然写法像追加，实际是读出整个列表、拼一个新列表、把引用换掉。加锁那行不丢，代价是两个分支被串行化；累加那行不读旧值，两个分支各加各的。

`time.sleep(0.005)` 是放大窗口用的，真实场景里这个窗口来自网络往返。GIL 常被误认为能保证这类操作安全，它只保证同一时刻只有一个线程执行字节码，不保证读、算、写三步不被打断；`list.append` 不同，整个调用期间不释放 GIL，单进程内的并发追加是安全的。

### 6.2 reducer 是不读旧值

reducer 在状态管理里就一个意思：给出旧状态加本次更新，产出新状态，而不是读旧状态、算一算、写回去。四种写法的对照如下：

| 写法 | 是否读旧值 | 并发安全 |
|---|---|---|
| `s.count = s.count + 1` | 是 | 不安全 |
| `s.facts.append(x)` | 否 | 安全（CPython） |
| `s.facts = s.facts + [x]` | 是（读引用） | 不安全 |
| `s = reduce(s, update)` | 否 | 取决于 reduce 实现 |

第三行是最容易写错的一种，看起来在追加，实际是整体替换。判断方法不是看有没有 `append`，而是看等号右边有没有出现旧值。框架里把这个合并函数叫 reducer，声明在字段上而不是写在更新代码里，写在字段声明上合并规则只定义一次。

### 6.3 覆盖与累加的取舍

同一个字段用覆盖还是累加，由语义决定，不由并发决定：

| 字段语义 | 正确做法 | 并发时的表现 |
|---|---|---|
| 计数（步数、覆盖次数） | 累加 | 需要原子操作或锁 |
| 集合（查过哪些订单） | 累加并去重 | append 安全，去重读取时做 |
| 结论（是否可退） | 覆盖 | 后写者赢，需记录次数 |
| 输入（用户意图） | 只写一次 | 不该有第二次写 |

表里结论那一行的后写者赢不是缺陷，是语义：两个分支得出不同结论时总得有一个生效，但它必须被记录下来，`overwrites` 就是干这个的。合并形式只有三类，都不读旧值：追加把新元素并进列表，求和在计数器上加，取并集按 key 合并。

结论类字段不属于这三类，它需要的是裁决而不是合并，合并函数必须知道哪个结论更可信，这个信息只能由业务提供，见第 23 章。累加有一个代价，存储会变大，计数类字段加锁更省，发生过什么类字段累加更合适。

### 6.4 写者唯一

比 reducer 更省事的做法是让每个字段只有一个写者。一个字段只有一个分支能写，其他分支想改它，就把结果交回给那个写者，四种情况的处理如下：

| 情况 | 处理 |
|---|---|
| 两个分支写不同字段 | 无需处理 |
| 两个分支写同一字段的并集 | reducer 累加 |
| 两个分支写同一字段的结论 | 串行化，或交给裁决 |
| 一个分支读、一个分支写 | 加依赖（第 22 章） |

第四行的顺序问题在状态层无解：读的分支如果先跑，读到的是旧值，后面再怎么合并也补不回来，这类问题只能回到编排层，用依赖边把读写分开，见第 22 章。写者唯一的好处是把并发问题变成拓扑问题；代价是这个分支成为串行点。

### 6.5 跨进程的读-改-写

前面三种写法只在单进程内成立。状态一旦存在外部存储，`append` 也不再自动安全，下面给出示意：

| 存储 | 安全操作 | 不安全操作 |
|---|---|---|
| 进程内列表 | `append` | `x = x + [v]` |
| Redis List | `LPUSH` | 读出整个列表再写回 |
| 数据库 | `INSERT`、`UPDATE v = v + 1` | `SELECT` 后在程序里改再 `UPDATE` |

Redis 与数据库那两行的安全操作都是存储自己执行的那一条命令。危险的是先读出来、在程序里改、再整体写回去，与单进程内的道理相同，只是慢得多，撞车概率高得多。数据库里还有一个额外选择，用条件写入代替读-改-写：

```sql
UPDATE runs SET eligible = 1, version = version + 1
WHERE run_id = :id AND version = :expected_version
```

`WHERE version = :expected_version` 是乐观锁。两个分支同时写，只有一个成功，另一个影响 0 行，程序据此重读、重算、重试。它比加锁轻，也比后写者赢安全，不会静默丢掉一个结论；前提是每次写都带版本，而版本号从读的时候就要拿到。

### 6.6 合并语义比加锁难

加锁能保证不丢，保证不了合得对。两个分支各产出一段摘要，合并后应该包含两者：

| 代码 | 问题 |
|---|---|
| `state.summary = branch_a_result` | 覆盖，B 的结论丢了 |
| `state.summary = merge(state.summary, b_result)` | 仍是读-改-写，可能丢 |
| `state.reduce("summary", b_result)` | 合并函数内部完成，安全 |

第三种写法里的 `merge` 必须真的把两个结果合成一个，而不是把后一个赋给前一个。合成规则是业务相关的：两段摘要怎么合，两个结论冲突时听谁，这些需要写，不能自动生成。两个分支对同一件事得出不同结论时，有三种处理：

| 做法 | 结果 | 适用 |
|---|---|---|
| 后写者赢 | 取决于完成顺序，不可复现 | 不推荐 |
| 先写者赢 | 忽略了后来者的信息 | 后来者信息不可靠时 |
| 交给裁判 | 有依据地裁决 | 两个结论都有依据时 |

交给裁判是第 23 章的裁判在状态层的用法，把两个结论和它们的依据一起交给规则裁判，用判据裁定。它比谁后写谁赢可靠，因为结果可复现，代价是要为每种结论写判据，判据怎么积累见第 23 章。

### 6.7 单线程也会覆盖

覆盖不是线程的专利，异步任务里同样发生：

| 场景 | 成因 | 后果 |
|---|---|---|
| 两个 `await` 之间 | 中间让出控制权，另一个协程改了状态 | 后写覆盖前写 |
| 回调链 | 回调触发顺序不定 | 结论取决于时序 |
| 定时刷新 | 定时器和主流程都写同一字段 | 随机覆盖 |

第一行最隐蔽，`await` 之前的读和之后的写中间可能隔了几十毫秒的 IO，这与线程里 sleep 的窗口完全一样。判断方法是机械的：列出所有读某个状态字段、等一个 IO、写回该字段的路径，每一条都是覆盖点；修法与前面一样，能累加就累加。

## 七、状态层的失效模式

状态层的失效模式有五种。一是把 `messages` 当状态，症状是任务超过十几步之后答案开始与事实对不上；二是字段过细，一个只用一次的字段是变量不是状态；三是用覆盖表达累加，`s.facts = s.facts + [x]` 单线程下不会暴露，只在并发时坏；四是结论不带依据；五是没有版本号，表现为新数据进来了、答案没变。

五种里最难发现的是第三、第五种，它们不报错，只是让结果慢慢偏离。三类线上症状各有对应线索：

### 7.1 三类线上症状

| 症状 | 真实原因 | 排查线索 |
|---|---|---|
| 同一个问题两次答案不同 | 结论被覆盖，两次读到不同版本 | 看 `overwrites` 计数 |
| 改完还是旧的 | 结论过期未重算 | 比较结论版本与事实版本 |
| 数据丢了 | 读-改-写撞车 | 看期望条数与实际条数 |

第一行最有用，`overwrites` 大于 0 且产物在两个版本之间反复，就是两个分支给了不同结论、后写者赢。第二行可以写成一行断言，结论版本小于事实版本就是过期。第三行需要期望条数才能发现，期望值必须来自业务。

事实去重会影响这个数。同一单号被查两次，`facts` 里留两条记录，条数从 1 变 2，但信息没有增加；守卫判断有没有新信息，用的应该是去重后的 key 数。去重放在读取时做，写入时保留原始记录。

### 7.2 交付前的断言

交付前有三个便宜的检查，值得常驻：

| 断言 | 检查什么 | 触发时的怀疑对象 |
|---|---|---|
| `len(facts) > 0` | 有数据才能判定 | 取数阶段失败了 |
| `conclusion_version == facts_version` | 结论是新算的 | 忘了重算 |
| `overwrites <= 1` | 结论没有反复改 | 两个分支在争 |

第三个的阈值不是绝对的，一轮里改一次主意正常，改三次以上说明判据或数据在变，把它当告警而不是错误。三个断言放在交付之前最合适，对应第 23 章的交付前校验；并发测试还要多两条：构造同时起跑，重复多轮。

### 7.3 与守卫共享计数

第 8 章的守卫看过程信号，步数、调用指纹、重复率，状态看内容，事实、结论、版本，两者要共享同一份计数，否则会出现守卫停了但状态里看不出为什么：

| 数据 | 谁产生 | 谁消费 |
|---|---|---|
| 步数 | 循环 | 守卫、状态（计数类字段） |
| 调用指纹 | 循环 | 守卫 |
| 事实条数 | 工具结果 | 状态、守卫 |
| 覆盖次数 | 状态 | 交付前的断言 |

事实条数那一行是新增的用法：守卫判断有没有新信息，最好的依据是事实条数有没有增加，而不是比对回灌字符串的哈希，后者在文本轻微变化时失效。覆盖次数那一行反过来，状态用守卫的数据做断言，两者是同一份运行记录的两个视图。

## 八、边界

State 不解决持久化。它是内存里的结构，怎么落盘、怎么恢复、恢复后怎么防重复副作用，都是第 25 章的内容；它也不是数据库，放进去的字段应该都在本轮任务里被用到，需要跨任务保存的东西属于长期记忆，见第 20 章。

单进程内的并发安全靠语言特性，跨进程不行，`append` 的原子性只在 CPython 单进程内成立。字段分类也不是一次定的，一个开始时当作结论的字段后来发现只增不减，就该改成事实，分类错了的表现是：这个字段总是在被覆盖，而覆盖次数一直是 1。

State 不负责跨 agent 共享，多 agent 之间传的是消息或任务对象，不是同一个 dataclass，见第 33 章。五条边界的共同点是 State 只处理一次运行内的当前值，落盘、跨会话、跨进程、跨 agent 都不是把字段加多能解决的；反过来，那几层也解决不了字段分类错误，一个把事实写成覆盖的字段，落到任何存储里都还是丢。

### 8.1 哪些字段不属于 State

检查点里有一部分字段不是状态，分清它们属于谁：

| 字段 | 属于 | 为什么 |
|---|---|---|
| `intent`、`facts`、`conclusions` | State | 任务内容 |
| `step` | 运行控制 | 与任务内容无关 |
| `pending_side_effect` | 运行控制 | 为了恢复，不是为了推理 |
| `schema_version` | 存储 | 为了读取，不是为了推理 |

判断方法是这个字段会不会被投影给模型，会就属于 State，不会就属于运行控制。混在一起的后果是投影时把步数与待执行的副作用也带进去，投影里出现我在第 3 步这类内容，模型可能因此改变行为，只占窗口不帮忙推理，第 25 章会把这类字段单独列出来。

### 8.2 状态设计的检查清单

状态设计有一份检查清单，顺序不能颠倒：先归类，再看来源，再看写入规则，最后看失效。

| 检查 | 通过标准 |
|---|---|
| 每个字段能归到四类之一吗 | 能，且写频率与类别一致 |
| 有字段既存事实又存结论吗 | 没有 |
| 结论带依据吗 | 带，或能追到某条事实 |
| 结论有过期判断吗 | 有，且是自动的 |
| 可并发字段有 reducer 吗 | 有，且不读旧值 |
| 失败也会被记成一条记录吗 | 会 |
| 状态能独立于 messages 恢复吗 | 能 |

反过来先想用什么存，会掉进存储选型，而选型解决不了分类错误：一个被写成覆盖的累加字段，换成任何数据库都还是丢。查完还应该反向验一次：列出每个字段的写入方，看有没有字段被两个分支写却没有 reducer。

最后一行是终极检验：把 `messages` 全部删掉，只用 state 能不能说清任务做到哪了。能，说明状态是完整的；不能，说明还有信息藏在历史里。这张表也是评测的输入，第 44 章的轨迹判据里，事实是否完整、结论是否过期、是否有反复、走了几步都可以直接读状态。

## 这一章建立的 6 件事

1. State 不等于聊天记录：从历史推断状态要扫全量、结果依赖历史完整性、口径会散落；裁剪本来是成本开关，在 V1 里变成了语义开关。
2. 字段按生命周期分四类：输入写一次、事实只增、结论可覆盖、计数只增。分类先于存储，也先于并发方案。
3. 放什么不放什么：后续步骤要用、来源要能区分、写入次数要能定；可再生的、寿命太短的、属于 trace 的都不进。
4. 结论要带依据，并且要能自动失效：事实条数当版本号，版本落后就返回 `None`，把忘记清空变成拿不到值。
5. 并发丢数据只发生在读-改-写：`append` 安全，`s.facts = s.facts + [x]` 不安全。reducer 是旧状态加更新产出新状态，不读旧值。
6. State、messages、trace 三份并列存：裁剪策略、持久化策略、投影方式都不同；合在一起，裁历史就会删状态。

## 下一章

状态在内存里已经清楚了。但进程会死，重启之后那个 dataclass 什么都没有了；更麻烦的是，从中断点继续时，之前已经发出去的那封邮件会被再发一次。第 25 章讲检查点里到底存什么、两种继续方式有什么区别，以及为什么恢复会重复副作用、幂等键要由哪些字段拼出来。
