## 一、四层坏法

一条坏回答有四种坏法，上层看起来都是“答错了”。第 14 章把 RAG 拆成检索、拼装、生成、引用四段，评测要做的第一件事是把“答错”拆回这四段：

| 坏法 | 现象 | 修法 |
|---|---|---|
| 知识库里没有 | 任何检索都找不到依据 | 补文档、补条目 |
| 召回了但排得靠后 | top-3 里没有，top-10 里有 | 调 top-k、重排 |
| 上下文里有，回答没用 | 依据就在眼前，答成了别的 | 改提示词、改拼装 |
| 上下文里没有，回答编了 | 依据缺失，话却说得完整 | 加引用约束、加"信息不足"出口 |

四行的修法分别落在知识库、检索、提示词、生成约束上。不分层时，“准确率 62%”无法指向任何一处修改，评测就从给方向退化成给分数。第三行与第四行尤其容易混：前者上下文里有正确依据而回答绕开它，后者上下文里根本没有支撑而回答照样完整。两者现象都是回答里没有依据，修法却分别在拼装与检索。

### 1.1 两次比较与三类样本

一条样本的评分要做两次比较：

| 比较 | 比什么 | 得到 |
|---|---|---|
| 检索 vs 标准答案的出处 | 该出现的块出现了吗、排第几 | 检索层指标 |
| 回答 vs 检索到的块 | 每句话有没有依据 | 生成层指标 |

第一次比较回答材料够不够，第二次回答材料用没用对，两次都通过才算好样本。只做第二次的系统会把检索没召回记成生成幻觉，优化方向指向提示词，而缺口在知识库。这个误判还会自我强化：改提示词之后忠实度可能略升，团队以为方向对了，召回仍然是零。

评测集要三类都有，否则指标会系统性偏高：

| 类型 | 构造方式 | 通过标准 |
|---|---|---|
| 正例 | 知识库里明确有答案 | 答对且引用正确 |
| 负例 | 知识库里明确没有 | 说"没有"而不是编 |
| 边界 | 有答案但需要两条以上拼接、或有过期版本 | 拼对、选对版本 |

第二类最容易被漏掉。只测正例的集合，准确率会随模型更敢回答而上升，同时线上编造率也在上升，而评测看不见。负例的作用是给说不知道留出得分空间。第三类对应第 19 章的文档版本问题：知识库里同时存在旧版本时，系统要选当前版本，而只测有没有答案的集合抓不到答了旧版本，那种回答字面正确、依据已经失效。三类的通过标准不同，正例看对不对，负例看敢不敢说不知道，边界看拼得全不全，平均成一个数等于把三种能力混成一种。

### 1.2 分层的代价与三种用途

分层评分比整体打分贵，贵在三处：

| 成本 | 表现 |
|---|---|
| 标注 | 每条样本要标"哪几块是相关的"，而这是人给的判断 |
| 标准答案 | 负例要写"正确回答是不知道"，边界要写清拼哪两条 |
| 维护 | 文档更新后，相关性标注会过期 |

主要成本在标注：相关性不能由被评测的系统自己给，那等于自己出题自己打分，第 23 章讲过纯自评会失效。模型可以预标，但必须有人抽检，否则标注偏差与系统偏差同向叠加。省钱的标法是只标命中位置，即标准答案出自哪一块、它在检索结果里排第几。这一个数字就能区分前两种坏法：位置为空说明知识库里没有，位置大于 top-k 说明排序把答案压下去了。

同一套指标在三个场合的读法不同：

| 用途 | 看什么 | 判据 |
|---|---|---|
| 验收 | 一次改动的方向对不对 | 目标指标涨，其余不跌 |
| 回归 | 有没有碰坏别的 | 所有指标不跌超阈值 |
| 对比 | 两个方案谁更好 | 同一批样本上的差异与区间 |

验收只看改的那一处有没有效果，容忍其他指标的小波动；回归反过来，不看谁涨只看谁跌；对比要求最严，同一批样本、同一个脚本、同一套参数。冲突在于一次改动通常同时动多个指标：把 top-k 调大，召回涨、精度跌、成本涨。验收看目标指标，回归看全部指标的下界，对比看区间，三份输出由第 45 章的门禁统一判定。

## 二、分层打分

分层打分的第一步不是算分，是给每条样本标出哪一块能支撑标准答案。`layered_score.py` 是本章的分层打分脚本，用三个样本演示：每个样本带问题、带相关性标注的检索块、回答与标准答案。

```python
def retrieval_metrics(s: Sample, top_k: int = 3) -> dict:
    top = s.chunks[:top_k]
    relevant = [c for c in s.chunks if c.rel == 1]
    hit = [c.cid for c in top if c.rel == 1]
    rank = next((i + 1 for i, c in enumerate(top) if c.rel == 1), None)
    rank_all = next((i + 1 for i, c in enumerate(s.chunks) if c.rel == 1), None)
    return {
        "relevant_total": len(relevant),
        "hit_in_topk": len(hit),
        "recall": len(hit) / len(relevant) if relevant else 0.0,
        "first_hit_rank": rank,
        "rank_all": rank_all,
        "precision": len(hit) / len(top) if top else 0.0,
    }
```

```
=== 1. 三个样本的分层打分 ===
  [A 检索漏召回] 生鲜订单可以无理由退货吗？
    检索层：召回 0%（0/0）  首命中位置 None  精度 0%
    生成层：忠实度 0%（0/2 条断言有依据）  要点覆盖 0%（0/2）
    归因：检索层：知识库里没有能支撑正确答案的块

  [B 排序把答案压到第 4] 定制商品能退吗？
    检索层：召回 0%（0/1）  首命中位置 None  精度 0%
    生成层：忠实度 0%（0/2 条断言有依据）  要点覆盖 100%（1/1）
    归因：检索层：答案排在第 4 位，被 top-3 截断

  [C 生成加了一条] 退款多久到账？
    检索层：召回 100%（1/1）  首命中位置 1  精度 50%
    生成层：忠实度 50%（1/2 条断言有依据）  要点覆盖 100%（1/1）
    归因：生成层：答案里有上下文不支持的断言
```

它的输出把三条样本的错归到三处：A 是知识缺失，B 是排序被截断，C 是生成多写了一句。只报总分时三条都是失败，修法却分别是补文档、调 top-k、改提示词。

### 2.1 检索层的三个数

召回回答该出来的出来了吗。A 的 `0/0` 不是算错：它表示检索结果里标了相关的块数为零，知识库里根本没有能支撑答案的那一块。这个零本身就是结论，补检索策略没用，要补知识；把它当成召回率为零去报警，会得到一个永远为真的告警。

首命中位置回答排第几。B 的答案在 `rank_all=4`，被 `top_k=3` 截断。它与 A 的召回都是零，修法完全不同：A 要补文档，B 只要把 top-k 从三调到五。这也说明单看召回不够，B 在 top-10 上的召回是百分之百，只有位置能暴露问题。

精度回答 top-k 里有多少是有用的。C 的精度是百分之五十，检索结果里混了噪声。三者合起来才能定位环节：召回高精度低是东西都在、排得乱，召回低精度高是排得干净、缺内容。

### 2.2 生成层的两个数

忠实度看回答里每一句能不能在相关块里找到依据。C 的两句里“需要支付 5% 手续费”在上下文里不存在，这是第 19 章“引用必须能指回原文”的量化版本。要点覆盖看标准答案里每一句有没有被回答覆盖：B 的覆盖是百分之百而回答是错的，因为它确实回答了“定制商品可以退”，只是与标准答案矛盾。覆盖率只测说到没说到，不测说的是不是同一个意思，把十五天说成三百六十五天的回答覆盖率仍然很高。它必须与一致性判断一起看。

### 2.3 归因与波动

`layered_score.py` 里的 `attribute()` 按顺序判四种：

```python
def attribute(s: Sample, r: dict, g: dict) -> str:
    """按两个层的指标给出归因。"""
    if r["rank_all"] is None:
        return "检索层：知识库里没有能支撑正确答案的块"
    if r["recall"] == 0 and r["rank_all"] > 3:
        return f"检索层：答案排在第 {r['rank_all']} 位，被 top-3 截断"
    if g["coverage"] < 1.0:
        return "生成层：答案漏了标准答案里的要点"
    if g["faithfulness"] < 1.0:
        return "生成层：答案里有上下文不支持的断言"
    return "两层都通过"
```

判据的顺序不是随意的：先判检索再判生成。检索失败时生成层指标没有意义，上下文里本来就没有依据，模型要么编、要么说不知道，两种都不该算生成能力差。这也解释了归因为什么要先有标注：不知道答案应该来自哪一块，就分不开检索失败与生成失败。最后一行“两层都通过”还隐含一个条件，回答与标准答案一致，那属于结果层评测。

同一批样本跑两次，指标不会完全一样，因为生成有采样。波动有多大，决定多小的差异可以当成信号：

| 指标 | 波动来源 | 典型波动 |
|---|---|---|
| 召回、精度 | 只由检索决定，检索是确定的 | 接近 0 |
| 忠实度 | 生成采样 + 判据阈值 | 几个百分点 |
| 要点覆盖 | 生成采样 | 几个百分点 |
| answer relevancy | 生成采样 + 代理公式 | 更大 |

召回与精度的波动接近零，示例的检索是固定列表，真实系统里向量检索也不打散，所以它们最适合做门禁。忠实度与覆盖的波动取决于温度，没固定温度时两次得分差三个点，分不清是改动还是采样噪声。answer relevancy 最大，它是生成乘代理公式的复合量，只适合看趋势。可用的做法是给每个指标单独定最小可判差异：确定性指标一个点，生成类三到五个点，代理类不单独做门禁，数字从重复跑里量出来，第 45 章的重复与区间是同一个问题。

### 2.4 报告的三段

一份能用的分层报告有三段，缺一段就落不了地：

| 段 | 内容 | 读者 |
|---|---|---|
| 结论 | 按归因分组的计数：知识缺 12 条、排序 5 条、生成 3 条 | 决定优先级的人 |
| 明细 | 每条样本的四个数 + 归因 + 出处 | 改代码的人 |
| 对比 | 与上一版的差异，按归因分组 | 决定要不要发的人 |

第一段决定先修哪个：十二比五比三直接说明该补知识库还是调 top-k，因为补十二条文档是几天的标注，调 top-k 是一次配置改动。第二段要能下钻到样本，点开一条“生成幻觉”要看到原始回答、检索到的块与标准答案，否则报告只能被相信，不能被核对。第三段是对比的落点：同一归因分组里上一版十二条、这一版八条说明改动有效，而组别变了说明副作用在别处。三段更新频率不同。

## 三、锚点映射

`layered_score.py` 还会把每条断言映射到最接近的块。指不回去的那句就是幻觉的候选，而“指不回去”本身可以计数：

```
=== 3. 锚点映射：每条断言能指回哪一块 ===
  '3 个工作日内到账'                  -> ['faq#5']
  '且需要支付 5% 手续费'               -> 无锚点（幻觉）
```

### 3.1 锚点怎么算

锚点的定义是这条断言能在某一块原文里找到依据。`layered_score.py` 用字面重合度做代理：

```python
def overlap(a: str, b: str) -> float:
    """字面重合度：交集 / 较短一方。"""
    ba, bb = bigrams(a), bigrams(b)
    if not ba or not bb:
        return 0.0
    return len(ba & bb) / min(len(ba), len(bb))
```

阈值取零点五：低于它只是词汇偶合，高于它这句话的意思基本来自那一块。这个代理有两个失效方向：改写会让重合度掉到阈值以下，被误判为无锚点；套话在任何块里都有词，会被误判为有锚点。两种误差方向相反，所以它适合做统计意义上的忠实度，不适合逐条判对错。

同一个标签在评测里有三种用法：

| 用法 | 含义 | 后续动作 |
|---|---|---|
| 计数 | 一次运行的幻觉句数 | 汇总成幻觉率 |
| 定位 | 哪一句没有依据 | 回看它为什么被生成出来 |
| 拦截 | 输出前检查 | 交给护栏与引用校验 |

第三种是产品动作，前两种是评测动作。评测里不该直接拦截，拦截会把问题盖住，让幻觉率看起来是零。第二种最有价值：一条无锚点断言往往来自把上一轮的常识带进来，或把相邻块的数字抄错，定位到它才知道改哪里。

### 3.2 阈值的标定

零点五这个阈值不是天上掉的。标定方法是拿一批人工标过的有依据与无依据句子，看不同阈值下的判对率与误判率：

| 阈值 | 表现 |
|---|---|
| 0.3 | 改写也能匹配上，但套话会被误判为有依据 |
| 0.5 | 折中：改写漏一部分，套话挡一部分 |
| 0.8 | 只有近乎原句才算有依据，判得严 |

低阈值让忠实度偏高，高阈值让它偏低；同一个系统换一个阈值，分数可以差十几个点，所以报告里必须写阈值，跨版本比较时阈值不能改。中文语料还有一层问题：短句的二元组太少，一句“可以退货”只有三个二元组，交集一个就过三分之一。短断言的判分天然更抖，可用的做法是把断言合并到一定长度再判，或对短断言单独定阈值。

## 四、四个指标

四个指标各自只测一件事，任何一个单独上升都不等于系统变好。`ragas_four.py` 是四个指标的离线复算脚本，在一个样本上逐项算开；它用的全是字面重合，目的是让每一步都可核对。

```
=== 1. 四个指标的逐项计算 ===
  faithfulness = 0.500
    '退款会在 3 个工作日内到账'               最高重合 0.80（faq#5） -> 有依据
    '且需要支付 5% 手续费'                 最高重合 0.00（faq#5） -> 无依据
    有依据 1 / 2 = 0.500

  answer_relevancy = 0.174
    问题二元组 5 个，答案二元组 18 个，交集 2 个
    精确率 2/18 = 0.111，召回率 2/5 = 0.400
    F1 = 0.174（代理指标，绝对值不可解释，只看版本间方向）

  context_precision = 0.500
    k=1 faq#6 rel=0  precision@1=0.00  贡献 0.00
    k=2 faq#5 rel=1  precision@2=0.50  贡献 0.50
    加权和 0.50 / 相关条数 1 = 0.500

  context_recall = 0.500
    标准答案句 '退款 3 个工作日内到账'         最高重合 0.88 -> 覆盖
    标准答案句 '退款原路返回'               最高重合 0.20 -> 未覆盖
    覆盖 1 / 2 = 0.500
```

这段说明了什么：三个零点五含义完全不同。忠实度的零点五是两句断言一句有依据；上下文精度的零点五是相关块排在第二位、前面有一条噪声；上下文召回的零点五是标准答案两句覆盖了一句。同一个数字背后是三种失败，修法也不同。

### 4.1 忠实度

忠实度的算法分三步：把回答切成断言、每条断言去相关块里找最高重合、有依据的条数除以总数。分母是断言数不是字数：三条短断言错一条得三分之二，一条长断言错一个数字得零，它因此偏向话少的回答。这个偏置是设计取舍：忠实度衡量有没有编，敢不敢说由覆盖率衡量。

### 4.2 精度、召回与相关度

上下文精度的口径是按位置加权的平均精度。`ragas_four.py` 里就是这几行：

```python
for k, (cid, _, rel) in enumerate(CONTEXTS, start=1):
    pk = sum(r for _, _, r in CONTEXTS[:k]) / k
    total += pk * rel
```

示例里相关块在第二位，`precision@1` 为零、`precision@2` 为半点五，加权和零点五除以一个相关块得零点五。这个指标对相关块在前极其敏感，挪到第一位分数就变一点零。所以它测的是排序质量，有没有召回到是上下文召回的事。

上下文召回把标准答案拆成句子，逐句看有没有块覆盖：示例两句覆盖一句得零点五。第二句“退款原路返回”没覆盖，原因是检索到的两条块都在讲时间、没讲路径。这就是知识缺一块的量化形态：它的表现是答不完整，而非答错。召回高精度低是东西都在、排得乱，精度高召回低是排得干净、缺内容。

答案相关度的标准做法是让模型根据回答反推问题再算相似度。`ragas_four.py` 用的是更便宜的代理，直接算问答字面 F1：

```
    精确率 2/18 = 0.111，召回率 2/5 = 0.400
    F1 = 0.174
```

零点一七四没有绝对值意义：它低，是因为回答里塞了“手续费”这种问题没问的内容。代理指标唯一可靠的用法是比较方向，同一批样本上从零点一七四变零点三一说明更贴题，不说明相关度百分之三十一。一旦把零点八二当成“准确率百分之八十二”去承诺，指标就开始骗人。

### 4.3 各自能证明什么

| 指标 | 变好意味着 | 不能证明 |
|---|---|---|
| faithfulness | 少编了 | 答得全（可能只是话说少了） |
| answer relevancy | 更贴题 | 答得对（贴题的错答也高分） |
| context precision | 排序更准 | 知识够（内容缺了照样靠前没用） |
| context recall | 内容更全 | 答得好（给了没用上也白搭） |

四行合起来才是完整判断：前两个测生成，后两个测检索。任何一个单独上升都不等于系统变好，这也是第 45 章门禁要按指标分别设阈值的原因，四个方向合成一个总分就丢掉了方向。

四个指标还会一起动，同一个改动常常让三个涨、一个跌：

| 改动 | 会涨 | 会跌 |
|---|---|---|
| top-k 从 3 调到 10 | context recall | context precision、成本 |
| 加"只说上下文里有的"约束 | faithfulness | 覆盖率、可能 relevancy |
| 加重排 | context precision | 延迟 |
| 换更小的模型 | — | faithfulness、relevancy |

第二行是最常见的取舍：约束越紧，编造越少，该说而不敢说的也越多；只看忠实度会一路把约束加到模型不敢说话。第一行的代价在成本，top-k 翻三倍，输入 token 也接近翻三倍，召回只从零点五涨到零点九，值不值取决于问答单价，第 46 章的成本瀑布算的就是这个。所以一次改动的报告要把涨的、跌的、花多少放在一起。

## 五、评测集

评测集是数据，不是脚本的一部分，集合被改动的那一刻，跨版本比较就失效。`dataset_experiment.py` 是数据模型的演示脚本，用二十条用例组成一份 dataset，在同一份上跑两次 experiment。

```python
@dataclass
class Item:
    item_id: str
    case_id: str
    kind: str                 # 正例 / 负例 / 边界
    intent: str               # 退货 / 退款 / 运费 / 发票
    question: str
    expected: str             # 期望行为：答对 / 说不知道 / 拼接两条
    source: str               # 线上抽样 / 专家标注 / 合成
    retired: bool = False
    trace_id: str = ""        # 跑过之后回填


@dataclass
class Experiment:
    exp_id: str
    dataset_version: int
    prompt_version: int
    model: str
    passed: dict[str, bool] = field(default_factory=dict)
```

```
=== 1. dataset ds-returns-2026-10 v3（20 条，退役 0 条） ===
  kind    条数  期望行为      来源
  正例    11    答对          专家标注、合成、线上抽样
  负例    4     说不知道      专家标注、合成、线上抽样
  边界    5     拼接两条      专家标注、合成、线上抽样
```

这段说明了什么：一条 item 带 kind、期望行为、来源三层信息。它们不是备注，决定了这条样本怎么判、能不能外推、替代了线上哪一类问题。

### 5.1 四个对象

| 对象 | 是什么 | 键 |
|---|---|---|
| dataset | 一组用例，带版本号 | `dataset_id` + `version` |
| item | 一条用例 | `item_id`，业务上是 `case_id` |
| run | 一次跑批 | `run_id`，指向 dataset 的某个版本 |
| experiment | 一次带对比意图的 run | `experiment_id`，带基线与候选 |

`dataset_experiment.py` 里这四个对象的关系就是表里这几列。run 与 experiment 的区别在意图：run 是跑了一遍，experiment 是为比较而跑；前者可能只是冒烟测试，后者必须固定基线、固定样本、固定参数。混成一张表，分数变了就说不清。

同一份 dataset 上的两版 prompt，跑完直接给出按 experiment 的分数与按 kind 的分组：

```
=== 3. 两次 experiment ===
  exp-101  dataset v3  prompt v1  gpt-4.1-mini  通过 14/20 = 70%
  exp-102  dataset v3  prompt v2  gpt-4.1-mini  通过 16/20 = 80%

=== 4. 按 kind 分组 ===
  kind    v1            v2
  正例    9/11 = 82%    10/11 = 91%
  负例    3/4 = 75%     4/4 = 100%
  边界    2/5 = 40%     2/5 = 40%
```

这段说明了什么：总分从七成到八成，分组看是正例涨、负例涨、边界不动。改动影响的是答得对不对与敢不敢拒答，对拼接两条没有帮助，边界样本的修法在拼装。边界只有五条，任何一条翻转就是二十个百分点，小分组的比率比总比率更不稳，报告里要同时给条数。

逐条差异更说明问题，下面是谁从失败变通过、谁反过来：

```
=== 5. 逐条差异：谁从失败变通过，谁反过来 ===
  i06 正例 退款  退款多久到账？
    失败 -> 通过（答对）
  i13 负例 退款  退款能加急到 1 小时吗？
    失败 -> 通过（说不知道）
```

这段说明了什么：两条翻转各对应一个行为。i06 说明 v2 对到账时间这类高频问题答对了，i13 说明 v2 学会在知识库没有时说不知道；前者是质量问题，后者是安全问题，都值得写进发布说明，因为它们说明了改动为什么有效。出现通过变失败的那条要单独看，可能是新引入的回归，也可能只是采样波动，区分方法是重复跑，第 45 章会给区间。

### 5.2 版本化与退役

集合一变，跨版本比较就失效，所以样本集要像代码一样有版本，`dataset_experiment.py` 里用两条规则约束它：

| 规则 | 理由 |
|---|---|
| 只增不改 | 改一条样本等于改了尺子，历史数字不可比 |
| 删除要留墓碑 | 一条样本被删，历史报告里那个分母就对不上 |

第一条的实际做法是新样本追加到末尾、旧样本保持原样。一条样本因文档更新而过期时，不是改它，而是标成 `retired` 并补一条新的，这样三月的零点八三与次年三月的零点八六仍然可比。第二条是审计需求：事故复盘要能重现当时评测集里有哪些样本。集合版本号要写进评测报告，否则三个月后没人说得清那个数字是哪把尺子量出来的。

评测的键是 `case_id`，线上的键是 `trace_id`，跑过一次就回填：

```
=== 6. case_id 与 trace_id 的连接 ===
  i01  case_id=c001  trace_id=（尚未跑过）
  i02  case_id=c002  trace_id=（尚未跑过）
  i03  case_id=c003  trace_id=（尚未跑过）
  <- 跑过一次就回填 trace_id；没有这一列，评测报告与线上 trace 是两套世界
```

这段说明了什么：一条用例每跑一次多一个 `trace_id`，报告里点开一条失败就能进到那次运行的 span 树，看它拿到的上下文、走的工具、卡在哪一步；没有这一列，判错只是一个无法核对的结论。回填的 `trace_id` 还让线上抽样来的样本能对回原会话，看用户当时问了什么。

## 六、评测集怎么建

评测集的价值不在条数而在覆盖，`dataset_experiment.py` 用一张矩阵把覆盖算出来，全是正例的集合条数再多也测不出编造率：

覆盖矩阵按 intent 与 kind 两维统计条数，脚本里就是这段循环：

```python
intents = ["退货", "退款", "运费", "发票"]
kinds = ["正例", "负例", "边界"]
for it in intents:
    row = [sum(1 for i in items if i.intent == it and i.kind == k) for k in kinds]
    print("  " + pad(it, 8) + "".join(pad(str(c), 8) for c in row) + str(sum(row)))
```

```
=== 2. 覆盖矩阵：intent × kind 的条数 ===
  intent  正例    负例    边界    合计
  退货    5       2       2       9
  退款    3       1       1       5
  运费    2       0       2       4
  发票    1       1       0       2
  <- 这一格里的 0 就是测不到的部分：某类意图没有负例，编造率就测不出来
```

这段说明了什么：这张表比二十条样本的清单有用，它一眼给出两处缺口，运费的负例是零，发票的边界是零。前者意味着运费类问题被编造这件事测不出来，后者意味着发票与退货交叉这类需要拼接的问题也没覆盖。维度按业务定：意图、文档来源、问题长度、租户，原则是找出系统可能系统性变差的维度，两个维度通常够用。

### 6.1 三类样本的比例

| 类型 | 建议占比 | 少了会怎样 |
|---|---|---|
| 正例 | 50–60% | 指标虚高，边界问题看不见 |
| 负例 | 20–30% | 编造率测不出来 |
| 边界 | 20–30% | 版本、拼接类问题测不出来 |

第二行是成熟度错觉的来源：九成正例的评测集，任何模型都会得到九十分。第三行决定系统能不能处理真实文档，现实里的问答大量需要拼两段、或涉及新旧两个版本，只测单块可答等于只测了最容易的那一半。

### 6.2 样本从哪来

| 来源 | 成本 | 偏置 |
|---|---|---|
| 线上日志抽样 | 低，但要脱敏与标注 | 贴近真实分布 |
| 从知识库构造 | 中，出题成本高 | 偏"可答"，漏掉负例 |
| 人工编写 | 高 | 容易写得比真实问题更完整 |

第一行是首选，代价在脱敏与标注，好处是分布真实，半句话、指代、错别字都会自然出现。第二行的偏置很实际：从文档构造的问题天然是文档里有答案的，负例几乎为零，要用它必须单独补一批文档里没有的问题。第三行的偏置最隐蔽，人写问题时会下意识把话说完整，评测集里的用户比真实用户更礼貌，第 44 章的指代用例就是这个问题。可用的组合是线上抽样为主、知识库构造为辅、人工边界补缺，并按比例维护。

### 6.3 多少条够

评测集规模由要判的差异有多小决定：

| 差异 | 需要的样本量 | 理由 |
|---|---|---|
| 10 个百分点以上 | 几十条 | 小样本也能看出来 |
| 3 到 5 个点 | 两三百条 | 置信区间要窄到这个量级 |
| 1 个点 | 上千条 | 通常不值得，改动本身的风险更大 |

三行的数字来自第 45 章的区间公式：两百条样本、九成五通过率，区间宽度约正负五个点；想窄到正负一个点，样本要到千条量级。第二行是多数团队的落点，想证明提升四个点，两百多条加区间判定就够。第三行要停下来想想，为了一个点的提升维护上千条集合，成本往往超过那一个点的收益。

### 6.4 合成数据的用法与陷阱

合成数据能便宜地把集合从二十条扩到两百条，但它的分布与被评测系统同源，会系统性偏容易。做法是让强模型读文档出题、另一个模型或人筛。第一个陷阱是同源：同一族模型不会犯的错，它出的题也不会考。第二个是答案泄漏，把原文块直接放进问题，题目自带答案，检索层永远满分。第三个是难度分布，合成题大多落在单块可答这一档，负例与边界几乎为零，所以合成只能扩正例。对抗样本也没法靠合成，它要故意构造看起来该答、实际不该答的输入。

| 项 | 量级 | 说明 |
|---|---|---|
| 一条新样本的标注 | 几分钟到半小时 | 要写问题、标准答案、出处 |
| 一次文档大更新后的复核 | 一到两天 | 过期样本要重审或退役 |
| 一次跑批的模型调用 | 几元到几十元 | 乘以指标数与样本数 |

第二行是长期成本的大头：政策类知识库每季度改一次，两百条的集合每次复核约两成，一年四次就是一百六十条人工判断。这也解释了只增不改为什么要配合退役，不退役集合越来越旧、指标被过期样本拖低，退役不记录历史报告的分母就对不上。

## 七、RAGAS 的接口

框架解决的是批量跑、逐样本留结果、接进 CI，不解决指标可信；把框架当成结论来源，等于把判据外包给一个默认配置。本机未安装 `ragas` 与 `datasets`，`ragas_contract.py` 是契约核对脚本，会先自检并打印安装命令，然后做离线能做的三件事：核对四个指标的输入与依赖、给出与手算口径的差别、说明跑批链上框架做了什么。

```python
METRICS = [
    ("faithfulness", "answer + contexts", "LLM 判分（拆断言 + 逐条判是否被上下文支持）",
     "代理版用二元组重合；RAGAS 版会把断言改写成独立陈述再判"),
    ("answer relevancy", "question + answer", "LLM + 嵌入（反推问题后算相似度）",
     "代理版直接算问答字面 F1；RAGAS 版比较的是'反推问题'与原问题"),
    ("context precision", "question + contexts + reference", "LLM 判分（逐块判相关）",
     "代理版用人工 rel 标注；RAGAS 版让 LLM 判每块是否相关"),
    ("context recall", "reference + contexts", "LLM 判分（标准答案逐句归因到块）",
     "代理版用重合度覆盖；RAGAS 版按句子归因"),
]
```

```
=== 1. ragas 是否可用 ===
  ragas           未安装
  datasets        未安装
  langfuse        未安装
  opentelemetry   未安装
  安装：pip install ragas datasets
  <- 本章的四个指标用代理口径离线复算；接 RAGAS 时换成真实指标，
     评测集、分层归因、门禁这三层结构不变
```

这段说明了什么：缺依赖不是跳过示例，而是把能离线验证的部分与必须装的依赖分开。四个指标的口径可以离线讲清，具体分数不能伪造，所以示例给代理口径的逐项计算并标明代理，不假装跑过 RAGAS。

### 7.1 三个入口与四个依赖

| 入口 | 作用 |
|---|---|
| `SingleTurnSample` | 一条单轮样本：用户输入、检索上下文、回答、参考答案 |
| `EvaluationDataset` | 一组样本；可从文件或列表构造 |
| `evaluate` | 跑批入口：dataset + 指标列表，返回逐样本分与汇总分 |

这三个名字在本章写作时是 RAGAS 的稳定入口；指标的类名与构造参数跨大版本改过，所以正文不写它们，接入时以所装版本的文档为准。四个指标的依赖也值得记：忠实度、上下文精度、上下文召回都靠模型判分，答案相关度还多一个嵌入模型，一次跑批的模型调用量约等于样本数乘指标数。

### 7.2 与手算口径的差别

| 指标 | 手算版 | RAGAS 版 |
|---|---|---|
| 忠实度 | 断言与块的字面重合 | 断言改写后由模型判是否被支持 |
| 答案相关度 | 问答字面 F1 | 反推问题与原问题的相似度 |
| 上下文精度 | 人工 rel 标注 + 位置加权 | 模型逐块判相关 + 位置加权 |
| 上下文召回 | 标准答案句的字面覆盖 | 标准答案句归因到块 |

四行里只有位置加权这个聚合公式是一致的，分子怎么判两边完全不同：`ragas_four.py` 是手算版，可复现、便宜、偏字面；RAGAS 版更接近语义、更贵、有模型偏差。两者用途不同，手算版讲清这个数怎么来的，RAGAS 版适合批量跑。同一批样本两边都跑一次，差异本身就是字面口径与语义口径差多少的度量，差异很大说明样本里改写多，字面指标不可信。

跑批链上框架做与不做，`ragas_contract.py` 的输出把它分成四行：

```
=== 5. dataset -> evaluate -> 报告 -> CI：框架做与不做 ===
  环节            框架做的                                    仍要你做的
  dataset 构造    给 SingleTurnSample 的字段形状；从文件读    不替你决定样本从哪来、覆盖哪几类
  evaluate 跑批   并发、重试、把每个指标的中间结果留下来      不替你控成本：裁判也是一次次模型调用
  报告            按样本给分，可导出                          不替你判'这个差异算不算数'（区间与门禁仍是第 45 章）
  CI 接入         能被脚本调用，返回结构化结果                不替你定阈值，也不替你处理密钥与配额
```

这段说明了什么：框架省掉的是跑批的工程活，判断没有省。样本覆盖、成本控制、阈值、差异是否显著，四件仍在人这边。接入之后变得可做的三件事是批量跑几百条、逐样本留中间结果、把跑批接进 CI；它没让指标可信变得更容易。

### 7.3 接进 CI 的最小形态

| 步 | 做什么 | 产物 |
|---|---|---|
| 1 | 固定 dataset 版本与指标版本 | 报告头里的两个版本号 |
| 2 | 跑批，逐样本落结果 | 一份 CSV 或 JSONL |
| 3 | 汇总，按 kind 与 intent 分组 | 分组通过率 + 条数 |
| 4 | 与基线比，算差异与区间 | 门禁输入 |
| 5 | 判定：回归、改善、无变化 | 合并或阻止 |

第二步的逐样本结果是复查的基础：只留汇总数，三个月后回看当时为什么判它失败，只剩一个分数。第三步分组比总分有用，原因见报告那一段。第四步的区间是第 45 章的内容，这里只需知道差异必须带范围。

## 八、会怎么坏

**第一，只测端到端。** 报告里只有一列“准确率 62%”，无法回答该改检索还是改提示词。

**第二，把检索失败算成生成幻觉。** 忠实度掉了就改提示词，而真正缺的是知识。

**第三，用模型给自己标相关性。** 标注文件由模型生成，没有抽检。

**第四，覆盖率当成正确率。** 一个答反了的回答覆盖率百分之百，报告里没有一致性判断。

**第五，指标被当成承诺。** 有人拿“相关度 31%”去对客户承诺。

**第六，评测集不随文档更新。** 政策从十五天改成七天，样本里还是旧标准答案，文档一改指标集体跳水。

**第七，集合改过但报告没版本号。** 新增四十条难题，通过率掉八个点，团队去找代码问题。

**第八，四个指标合成一个总分。** 排序变好、召回变差，总分不变，报告显示无变化。

---

## 九、边界

**第一，分层评分要求相关性标注可信。** 标注错了归因就错，而且错得很像真的，相关性标注要有人负责并定期抽检。

**第二，四个指标都是代理。** 中文的改写、指代、省略都会让它们失真，适合版本比较，不适合单点判定。

**第三，本章不涉及多轮。** 多轮里“这个问题”指的是上一轮的对象，单轮指标全部失效，那是第 44 章的内容。

**第四，结论只在评测集分布内成立。** 用退货政策攒的集合不能证明系统在技术文档上也行。

**第五，指标与成本要一起看。** top-k 从三调到十，召回可能从零点五涨到零点九，同时输入 token 翻三倍。

**第六，分层还缺拼装这一环的独立指标。** 四槽位预算、压缩、顺序的失败表现为生成层指标下降，很难与模型本身不行区分。

**第七，RAGAS 的分数不能跨版本直接比。** 指标实现、提示词、裁判模型都可能变，比较前要固定这三样。

**第八，示例的数字是固定样本上的真实计算，不是线上实测。** 它证明公式与归因逻辑成立，不证明某个系统一定是这个比例。

**第九，诊断力依赖“标准答案只有一条”。** 同一个问题有多条正确回答时，句覆盖会低估系统，这类样本应拆成多条，或改用要点集合。

## 这一章建立的 6 件事

1. 一条坏回答有四种坏法（知识缺、排序差、没用上下文、编了），修法分别落在知识库、检索、拼装与生成约束上。不分层就只能得到"准确率 62%"这种无法行动的数字。
2. 分层的核心是两次比较：检索结果对标准答案出处、回答对检索内容。先判检索再判生成，因为检索失败时生成层指标没有意义。
3. 四个指标逐个算开：忠实度按断言计、上下文精度按位置加权、上下文召回按标准答案句覆盖、答案相关度用重合度代理（零点一七四这个数没有绝对值意义）。
4. 评测集是带版本的数据：dataset / item / run / experiment 四个对象，`case_id` 连 `trace_id`；只增不改、删除留墓碑。
5. 覆盖矩阵比条数有用：某个意图没有负例，编造率就测不出来；三类样本的比例决定指标会不会系统性虚高。
6. RAGAS 的三个入口（`SingleTurnSample`、`EvaluationDataset`、`evaluate`）省掉跑批的工程活，不省判据；本机未安装时用代理口径讲清公式，不伪造分数。

## 下一章

这一章评的是"答得对不对"，但 agent 还有两样东西要评：它是怎么走到那个答案的（轨迹），以及判它对错的那个裁判本身可不可信。

第 44 章讲 agent 评测的四层——结果、轨迹、稳定、成本，四条轨迹判据各拦什么，怎么用一个 kappa 证明裁判不是在乱说，以及单轮测不到的指代与审批状态该怎么进用例。
