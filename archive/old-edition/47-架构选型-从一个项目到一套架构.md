## 一、选型的五类事实

第 22 章讲完了一个 agent 内部三层怎么配，它明确不管四件事：多 agent 拆分、框架与技术栈、状态与持久化、部署与上线。所以读完 22 章，手里只有部件，没有把一个项目配成一套架构的方法。

| 事实 | 具体是什么 | 两天内怎么量 |
|---|---|---|
| 任务形状 | 一条请求需要几步（含工具调用与模型轮次） | 抽 30 条真实请求，数步数，取中位数与 P95 |
| 请求分布 | 简单请求与复杂请求各占多少 | 同一批 30 条按"一步能否答完"打标，算占比 |
| 错误代价 | 错了会怎样：能否回滚、是否涉及资金、是否要签字 | 列三个最坏后果，逐条回答是或否 |
| 预算 | 月度 token 上限、P95 延迟目标、月请求量 | 上月账单 ÷ 请求数；延迟从网关日志取 |
| 团队与存量 | 几个人、什么语言、什么合规要求 | 直接问，半天能问清 |

`cases.py` 里三个画像填完是这样：

```text
=== 1. 三个画像 ===
=== 客服工单 ===
    任务形状：中位 6 步，P95 11 步
    请求分布：简单 70% / 复杂 30%
    错误代价：高，可回滚=False，需审批=True
    预算：600M tokens/月，P95 8s，60000 次/月
    团队：4 人，Python + 内部工单系统，合规=审计留痕

=== 内部知识问答 ===
    任务形状：中位 1.5 步，P95 3 步
    请求分布：简单 90% / 复杂 10%
    错误代价：低，可回滚=True，需审批=False
    预算：220M tokens/月，P95 3s，120000 次/月
    团队：2 人，Python + 现有向量库，合规=无

=== 研究报告 ===
    任务形状：中位 25 步，P95 40 步
    请求分布：简单 20% / 复杂 80%
    错误代价：中，可回滚=True，需审批=False
    预算：300M tokens/月，P95 300s，4000 次/月
    团队：3 人，Python + 检索服务，合规=来源可追溯
```

注意三处细节，它们决定了后面所有推演。第一，步数用中位数与 P95 两个数，不用平均值：平均值会被长尾拉高，而形态决策关心的是典型请求几步与最慢的那批几步，前者决定形态，后者决定预算。第二，请求分布是形态决策的主要输入，不是任务形状：一个中位 6 步但九成请求一步能答完的系统，与一个中位 6 步且一半请求是复杂流程的系统，配置完全不同。第三，错误代价是判断题，不是打分：能否回滚只有是或否，是否涉及资金也只有是或否，它们不进任何复杂度评分。

这五类事实里，任务形状与请求分布会随业务变化，错误代价与合规要求相对稳定，预算是外部约束。变化速度不同，意味着复查频率不同：前两类每月复算，后三类每季度一次。

每一类事实都有一个看似量了、其实没量的版本。任务形状的假量法是用产品文档里的流程图数步数，流程图写的是理想路径，真实请求会走进查不到、权限不足这类异常分支。请求分布的假量法是按产品经理的预估分档，可信的量法是对同一批样本打标，且打标的人要看过真实处理过程。错误代价的假量法是拍一个高中低，可信的量法是回答三个具体问题：能不能撤销、会不会动钱、要不要人签字。预算的假量法是用上个月账单，可信的量法是单请求成本乘预计月请求量。团队的假量法是我们团队很强，可信的量法是列出三样：现有语言与框架、有没有评测集、有没有人能维护提示词与工具。

## 二、五层决策与三个可数的量

事实填完，接下来是五层，`plan.py` 按事实逐层推出配置：

| 层 | 决定什么 | 由哪类事实决定 |
|---|---|---|
| 形态 | 一次调用 / 单循环 / 工作流加路由 / 多 agent 图 | 步数与请求分布 |
| 编排 | 分派层、主体形态、校验层（第 22 章） | 复杂请求的占比、错误代价 |
| 供给 | RAG、工具、Skill 各上哪些 | 任务需要的知识与动作 |
| 可靠性 | 重试、幂等、审批、熔断、降级 | 错误代价与可逆性 |
| 交付 | 同步、流式、异步队列 | P95 延迟目标与月请求量 |

**层间不可替代。** 一层选错，不会因为另一层加码而变对：形态选成多 agent，编排层再怎么调分派规则也救不回多出来的交接成本；校验层缺裁判，可靠性层加多少重试都只是让错误重来几次；供给层缺工具，主体层再强也只能编。三张画像推出来的配置是：

```text
=== 1. 五层配置 ===
  [客服工单]
    形态：单循环（中位 6 步，不需要并行与隔离）
    编排：分派=规则 + 小模型两级；主体=ReAct；校验=外部裁判 + 人工审批
    供给：工具（工单/退款）+ 政策 RAG + 审批卡
    可靠性：幂等键 + 提交前审批 + 熔断 + 限流 + 降级三档
    交付：同步 + 超时降级（P95 目标 8 秒）

  [内部知识问答]
    形态：一次调用（中位 1.5 步、九成一步能答完）
    编排：分派=无（单次生成）；主体=单次调用 + 结构化输出；校验=schema + 拒答
    供给：RAG（现有向量库）+ 引用回链
    可靠性：重试 + 限流 + 缓存
    交付：同步 + 流式（首 token）

  [研究报告]
    形态：多 agent 图（中位 25 步，超出单循环的稳定范围）
    编排：分派=小模型 + 大模型两级；主体=计划-执行（P&E）；校验=schema + 抽样复核
    供给：RAG（多源）+ 检索工具 + Skill（报告模板）
    可靠性：重试（预算 + 抖动）+ 幂等 + 降级两档
    交付：异步队列 + 进度回调
```

三段配置里，每一行都能追溯到某条事实。客服的单循环来自 6 步；外部裁判加人工审批来自错误代价高且不可回滚；同步加超时降级来自 P95 目标。这张表的价值不在配置本身，而在于它能被反驳：有人不同意客服该用单循环，就必须指出 6 步这个数不对，或者指出错误代价没那么高。

五层为什么是五层？判据是每一层都有一个独立的选择，且选错之后不能靠别的层补：形态决定有没有循环，编排决定谁来决定下一步，供给决定能碰到什么，可靠性决定错了会怎样，交付决定用户多久看到。也不该再多一层：模型选型与提示词是编排层内部的参数，不是独立的一层，分开会制造两份互相矛盾的决定。

---


这一节把复杂换成三个数。它们各自可量，且量错会直接选错：

| 量 | 定义 | 量错会怎样 |
|---|---|---|
| 依赖步数 | 一条请求平均需要几次串行决策 | 低估 -> 单循环不够用；高估 -> 过度拆分 |
| 首次通过率 `p` | 不加修复、一次就通过裁判的比例 | 高估 -> 不加裁判；低估 -> 加了一堆没用的反思轮 |
| 请求分布 | 简单请求占比 | 低估 -> 不分派，简单请求也走全套；高估 -> 分派层误伤复杂请求 |

三个数的量法都在第 22、23、13 章讲过，这里只讲量错的方向与后果，因为选型时最常见的错误不是不会量，是量的对象错了。

依赖步数量错，最常见的形态是数模型轮次而不是数决策：一次回复里可能包含三次工具调用，那算三步；模型反复思考但只调用一次工具，只算一步。首次通过率量错，最常见的形态是用测试集上的通过率代替线上通过率，测试集的题目是挑过的，更可靠的量法是抽样线上请求、人工标注第一次输出对不对，样本量按第 45 章的区间判定。请求分布量错，最常见的形态是按用户意图分类，而不是按处理路径分类：查一下订单的意图是查询，但处理路径可能是查订单、发现异常、转人工。

三个数一起看，才能定位配置问题：步数高而 `p` 高、分布偏简单，说明形态可能过度，先加分派；步数低而 `p` 低，不是形态问题，是供给或提示词问题。这三个数还各有一个阈值形态，超过它就该换层：

| 数 | 常见阈值 | 超过之后该动哪一层 |
|---|---|---|
| 依赖步数中位 > 8 | 单循环的稳定范围上限 | 形态层（工作流或图） |
| 首次通过率 < 0.6 | 反思循环的成本超过收益 | 校验层（外部裁判） |
| 简单请求占比 > 0.7 | 分派的收益明确 | 编排层（分派） |

阈值不是绝对的，但每个都对应一个成本拐点：8 步以上单循环的上下文与失败重试成本开始非线性上升；`p` 低于 0.6 时，两轮反思的期望收益抵不过第二次调用的成本。

三个数还有一个合起来用的判据：如果步数乘以 `1-p` 超过 3，说明每条请求平均要花三轮以上才能做对，此时任何形态优化的收益都低于先把 `p` 提上去。

## 三、用预算反算

预算是硬约束，它可以直接反算架构的上界：每月可用 token 除以月请求数得到单请求 token 上限，再除以每次调用的 token，就是最多能走几步。`plan.py` 的反算就是这三步：

```text
=== 2. 成本与延迟 ===
    画像           tokens/任务      月度tokens     预算占比      月成本元    P95    目标
    客服工单              9300     558000000      93%      1116    13s    8s
    内部知识问答            1650     198000000      90%       396     4s    3s
    研究报告             66875     267500000      89%       535    48s  300s

=== 3. 预算反算 ===
    画像             单请求上限     最多步数      不带裁判结论
    客服工单           10000      6.5       8.1  预算够，可带裁判
    内部知识问答          1833      1.7       2.1  预算够，可带裁判
    研究报告           75000     28.0      35.0  预算够，可带裁判

=== 4. 超预算的画像怎么改 ===
    客服工单：已用 93%，没有余量做 A/B
    内部知识问答：已用 90%，没有余量做 A/B
    研究报告：已用 89%，没有余量做 A/B
```

第一段有三列要一起读。月度 tokens 是按当前配置全量跑的量，不是实际账单；预算占比接近 100% 说明没有余量。

第二段是反算。客服的单请求上限一万 token，除以每次调用一千三百六十，得到 6.5 步，恰好略高于中位步数；问答的上限是 1.7 步，比中位 1.5 步只多一点，它几乎没有空间做多轮修复，一旦第一次答错，重试一次就超预算，所以配置里没有反思循环；报告的上限是 28 步，中位 25 步，余量刚好够一次重规划，这与它降级两档的可靠性配置一致。

第三段是没有余量的警告：三个画像都在 90% 上下，意味着不能做 A/B 测试，因为 A/B 要同时跑两套。砍功能的次序也有讲究，从最不影响裁判的地方砍起：先砍锦上添花的检索扩展，再砍重复的反思轮，最后才砍步数，因为砍步数会改变形态。

延迟也要一起反算。客服的 P95 是 13 秒，目标是 8 秒，超了 5 秒，这不是靠优化能解决的，11 步串行就是 13 秒。预算与延迟的联合判据可以写成一句话：预算决定能走几步，延迟决定这几步能不能串行，两者都过配置才成立，有一个不过就要么并行、要么降级。

反算的完整用法是一次做四步，以客服为例：先算单请求上限，再算每次调用成本，再折成步数，最后得出的是超预算的那部分怎么处理，而不是把预算放大到覆盖 P95。三条出路各有代价：并行要改图与合并状态，降级要接受质量损失，砍功能要动产品。这套反算还有一个前提：每次调用的 token 与耗时是估的，结论要每个月用真实数据校准一次。

## 四、ADR 与迁移阶梯

一个架构决定要能被三个月后的人复盘，必须写成五段：背景事实、决定、落选方案与失效证据、代价、回滚点。为什么不选比选了什么重要：没有失效证据的取舍只是偏好，偏好无法在三个月后复盘，也无法在半年后迁移。`adr.py` 是校验这五段的脚本，一份完整的 ADR 长这样：

```text
# ADR：客服工单助手的形态与校验层

## 背景事实
- 中位 6 步、P95 11 步（30 条真实工单抽样）
- 简单请求 70%、复杂 30%
- 错误代价高：涉及退款金额，不可回滚，需审计留痕
- 预算 600M tokens/月，P95 目标 8 秒，60000 次/月
- 4 人团队，Python，已有工单系统与政策库

## 决定
- 形态：单循环（不进图，不做多 agent）
- 编排：规则 + 小模型两级分派；主体 ReAct；校验 = 外部裁判 + 提交前人工审批
- 供给：工具（工单/退款）+ 政策 RAG + 审批卡
- 可靠性：幂等键 + 审批 + 熔断 + 限流 + 降级三档
- 交付：同步 + 超时降级（P95 目标 8 秒）

## 落选方案与失效证据
- **一次调用直接答（不分派、不循环）**：30 条抽样里有 18 条需要查工单或政策库才能答，一次调用拿不到这些信息，只能编；而退款动作不可回滚，编错的代价是一笔错账
  - 坏在哪一层：供给层（缺工具）与校验层（无裁判）
  - 失效信号：答案里出现具体金额或时效，但轨迹里没有任何一次工具调用
- **多 agent 图（分派 + 退款 agent + 复核 agent）**：中位 6 步的任务拆成三个 agent，交接至少两次；按第 55 章的账，token 上升四成以上，而错误率不会下降——退款错误的主因是政策理解，不是上下文隔离
  - 坏在哪一层：形态层（过度拆分）
  - 失效信号：交接摘要长度接近子任务输入长度；子 agent 平均上下文小于摘要

## 代价
- 审批卡让人均处理时长增加约 12 秒，需要排班兜住峰值
- 政策 RAG 要每周同步一次，否则答错率回升
- 同步交付在 P95 超过 8 秒时要降级为'先答后补'

## 回滚点
- 回到：第 2 级（单循环，去掉分派层）
- 触发数：兜底率连续 7 天高于 15%，或审批驳回率高于 20%
- 回滚后先看：分派层的误判率与政策库的覆盖率
```

五段各有一个常见的敷衍写法，对照看：

| 段 | 敷衍写法 | 合格写法 |
|---|---|---|
| 背景事实 | "业务复杂，需求很多" | 五个可量的数，带样本量与时间 |
| 决定 | "采用先进的多 agent 架构" | 五层各一行，每行能追溯到某条事实 |
| 落选方案 | "也考虑过其他方案" | 每个落选方案有一条失效证据、一个失效层、一个可观测信号 |
| 代价 | "成本会有所增加" | 哪一项增加、增加多少、谁承担 |
| 回滚点 | "效果不好就回滚" | 回到第几级、由哪个数触发、回滚后先看什么 |

这张表右侧的每一格都能被检查，所以本章把检查写成代码，`adr.py` 的第二、三段给出的就是被拒的输出：

```text
=== 2. 落选方案没有失效证据（被拒） ===
    - 落选方案『单循环』没有失效证据（只是偏好）
    - 落选方案『单循环』没有可观测的失效信号
    - 回滚点没写由哪个数触发

=== 3. 回滚点写成'效果不好时'（被拒） ===
    - 回滚点『上一级』没写清是第几级
    - 回滚点触发条件『效果不好时』不可判：没有数或指标
```

第二段那份 ADR 只写了决定做多 agent，落选方案一栏只有方案名，没有证据。第三段那份更常见：回滚点写效果不好时，它不是回滚点，是一句表态。校验拦住的是一个具体问题：这个决定能不能在三个月后被复盘。

背景事实一段常被写成长篇背景介绍，这是另一种敷衍。合格的标准是每一条事实都能被反驳，且反驳之后决定会变：写业务增长快无法被反驳，也不会改变任何决定；写中位 6 步可以被反驳，一旦数变了，形态那一行就要重写。代价一段最容易空，合格的代价要回答三件事：增加了什么、增加多少、谁承担，写不出谁承担，说明这个代价还没有被真正接受。一份 ADR 的生命周期也要写：复查日期、复查时要看哪三个数、什么条件下它作废。

---


架构不是一次选定的，是一级一级走上去的。`migrate.py` 里五级各有形态与退出条件：

```text
=== 1. 五级阶梯 ===
    第 1 级  一次调用        单次生成 + 结构化输出            无循环、无工具
    第 2 级  单循环         ReAct + 四终止             有工具，无分派
    第 3 级  工作流 + 路由    分派层 + 固定阶段              按请求类型走不同路径
    第 4 级  P&E + 外部裁判  计划-执行 + 裁判循环            有重规划与验收
    第 5 级  多 agent 图   节点即循环 + 状态归并            上下文与权限隔离

=== 2. 升级触发：连续 7 天滚动均值 ===
    兜底率从 8% 涨到 24%；7 天均值首次超过 15% 是第 11 天
    首次通过率从 78% 降到 64%；7 天均值首次低于 70% 是第 16 天
    兜底率命中 -> 升级到第 3 级（加分派）；首次通过率再跌破 -> 加裁判（第 4 级的校验层）
    <- 单日值不触发：第 8 天单日 15% 只是擦线，7 天均值到第 11 天才稳定超过
```

第一段是形态阶梯，第二段是升级的触发条件，两个数字都是连续 7 天滚动均值：兜底率超过 15% 说明简单请求没被挡住，该加分派；首次通过率跌破 70% 说明一次做对的比例在下降，该加裁判。

为什么用 7 天而不是单日？单日值是噪声：第 8 天的兜底率是 15%，正好擦线，按单日触发，第 9 天回落到 14% 又要回滚，一周内会横跳两次。滚动均值的作用不是平滑数据，是让升级这件事有足够证据。

| 升级 | 触发（连续 7 天） | 代码动多少 | 评测集动多少 |
|---|---|---|---|
| 1 → 2 | 一步答完率 < 60% | 加循环、工具、四终止 | 加轨迹判定 |
| 2 → 3 | 兜底率 > 15% | 加分派与两套提示词 | 按路径各一套 |
| 3 → 4 | 首次通过率 < 70% | 加计划、裁判、重规划 | 加裁判一致性 |
| 4 → 5 | 单任务上下文超窗口，或需并行 | 加节点、状态归并、回边 | 加图级与节点级 |

第四行是唯一因为容量而不是因为质量触发的升级：前三级升级是效果不够，第五级常常是上下文装不下或必须并行，前者的代价可以靠指标衡量，后者的代价是重写，这笔账第 55 章算过。

反向也要写：回滚的触发数与升级的触发数不能是同一个数，否则会在阈值附近来回跳，升级用 15%，回滚用 10%，中间留 5 个点的缓冲带。

```text
=== 3. 升级前后的账（示例数字，按同一批 60000 次/月） ===
    升级前（第 2 级）：tokens/任务=11625  token 成本=1395 元  失败率=12%  失败成本=57600 元  失败点=3 个
    升级后（第 3 级）：tokens/任务=12145  token 成本=1457 元  失败率=7%  失败成本=33600 元  失败点=4 个
    净收益 ≈ 23938 元/月（失败成本下降 - token 成本上升）
```

升级后 token 成本涨了六十二元，失败成本降了两万四，净收益约两万三千九百元每月，这个账能算清的前提是失败成本有单价。失败点从 3 个变成 4 个，这一行不能省：多出来的是分派误判，它的概率不高，但一旦发生，修复成本比原来更高，因为要同时查分派与业务。最后一级的跳跃最贵，因为它要同时改形态、编排与状态，第 55 章的对照表里能看到这一跳的账。

```text
=== 5. 两级跳的代价（第 2 级直接到第 5 级） ===
    代码面：循环 + 分派 + 图 + 多套提示词，一次到位
    评测集：需要图级与节点级两层，且要先有单循环的基线才看得出图有没有用
    回滚点：一旦图不成立，没有'第 3 级'可退，只能整体重写
    <- 阶梯的意义不是渐进，是给每一步留一个可退回的位置
```

第三行是阶梯的真正价值：回滚点只有在上一级还在的时候才成立。从第 2 级直接跳到第 5 级，图不成立时没有第 3 级可退，只能整体重写；一级一级走，每一级都是一个可退回的位置。

## 五、两个反例与框架自研

两个反例从同一份项目事实出发，只改一个决定。

过度架构：一个三步任务，中位 3 步、九成简单、错误代价低，被配成了五节点图加一个复核 agent。形态从一次调用升到多 agent 图，按第 55 章的实测，token 从 69 涨到 127，再加一个 agent 至少再涨四成。判据不是图更难维护，是多花的钱买到了什么：这个例子买到的是每个节点可以单独重跑，而三步任务没有哪个节点需要单独重跑。

欠架构：同一个项目，形态停在一次调用，但错误代价被写成低，于是没有裁判、没有分派，兜底逻辑写成尽量答。兜底率没有监控，因为尽量答不是一个可观测的状态；复杂请求走同一条路径，出错率是简单请求的数倍，但混在总成功率里看不出来。欠架构的代价不是效果差一点，是失去了定位能力：没有分派就没有分层指标，没有裁判就没有失败分类，所有问题都只能归到模型不行。

两个反例的共同点是它们都不是技术错误，是决定与事实不匹配：过度架构把一个三步任务当成了二十五步，欠架构把高错误代价当成了低。它们的起点还都看起来合理：过度架构的起点常常是反正以后要扩展，于是提前把图、分派、复核都建好，而这些结构不是免费的；欠架构的起点常常是先把效果做上去再说，代价不在第一个月，在第三个月。这也解释了为什么本章把验收三个数放在选型之后：三个数要先有位置可落。

---


这一节不做框架排名，只给判据：什么时候框架是净收益，什么时候是负债。

净收益的三种情形：需要可观测与评测的现成接入，追踪、span 树、评测集回放这些能力自研要几周，框架是配置；需要生态里的现成部件，检索切块、解析、重排这些本来也要自己接；团队小、变动快，框架的默认值比自研的合理预设更省事。负债的三种情形：锁定在框架的状态模型上，状态字段、检查点语义、恢复行为都由框架定义，换框架等于重写；隐形状态，框架维护了没有声明的状态，它的危害不在运行期，在复盘期，出了问题无法从记录里还原；版本升级会改行为，升级一次就要重跑一遍评测集。

两者都对的三种情形：用框架做编排与观测、自研裁判与业务工具，前者是通用能力，后者是护城河；用框架做原型、自研生产路径；用框架的部件但不用它的状态模型。这三条有一个共同前提：框架的部件能单独引入，这要求模块边界清楚。

判据可以压成一句：框架替使用方做的决定，以后还能不能改？能改的是净收益，不能改的是负债。

框架的版本策略也要写进 ADR：锁定小版本、升级前跑一遍评测集、升级后对比三个数。没有评测集的团队用框架，等于把升级会不会坏交给运气，而这一条与框架无关，自研也一样。

## 六、验收三个数与画像推演

上线前要盯三个数，加一个回滚点：

| 数 | 口径 | 什么时候算坏 |
|---|---|---|
| 单任务成本 | tokens × 单价，按成功任务摊 | 超过预算反算的上限 |
| P95 延迟 | 端到端，含排队与重试 | 超过目标且降级没触发 |
| 外部裁判通过率 | 外部状态核对通过的比例 | 连续 7 天低于上一级基线 |

第三个数是本章特有的：它不看模型自评，也不看用户没投诉，只看外部状态。客服看工单是否正确关闭、退款金额是否对；问答看引用是否指向存在的文档；报告看来源是否可查。

回滚点写进 ADR，且要满足两个条件：回到第几级、由哪个数触发，缺一就只是表态。选对了不等于不用改，三个数的用途是发现选错了：成本超上限说明形态太重，延迟超目标说明串行步数太多，通过率下滑说明校验层不够。

三个数还要与上一级基线比，而不是与行业平均比，基线的取法是升级前那两周的同口径数据。回滚点的触发数应当比升级的触发数更保守，且回滚要能在一天内完成，超过一天的回滚实际上等于回不去。

---


同一张表推三遍，产出三套配置、三份 ADR、三行成本。

| 项 | 客服工单 | 内部知识问答 | 研究报告 |
|---|---|---|---|
| 形态 | 单循环 | 一次调用 | 多 agent 图 |
| 分派 | 规则 + 小模型 | 无 | 小模型 + 大模型 |
| 主体 | ReAct | 单次 + 结构化输出 | P&E |
| 校验 | 外部裁判 + 审批 | schema + 拒答 | schema + 抽样 |
| 交付 | 同步 + 降级 | 同步 + 流式 | 异步队列 |
| tokens/任务 | 9300 | 1650 | 66875 |
| 月成本 | 约 1116 元 | 约 396 元 | 约 535 元 |
| ADR 落选方案 | 一次调用、多 agent 图 | 加反思循环 | 单循环 |

三行成本都不到千元，这个量级说明三件事：token 在这个规模上不是主要成本；真正的成本是审批、维护与评测集；预算的约束力不在花不起，在没有余量做实验。

三份 ADR 的落选方案各不相同，这正是它们的价值：客服否定一次调用与多 agent 图，问答否定加反思循环，报告否定分派层。推演的次序也有讲究：先定形态，再定编排，再定供给，再确定可靠性，最后定交付，次序颠倒会返工。

最值得看的是同一个决定在不同画像下的结论相反：分派层在客服与问答上都是收益，在报告上却是成本，因为报告八成是复杂请求，分派层能挡住的只有两成。成本的三行数字也要看相对值：报告的单任务成本是问答的四十倍，但月成本只有一点三倍，因为它的请求量只有三十分之一。

## 七、会怎么坏

**第一，用复杂度评分代替三个数。** 打出一个 7.2 分，然后按分数选形态，分数是合成的，合成权重无法验证，最后没人知道 7.2 意味着什么。**第二，ADR 只有决定，没有落选。** 三个月后无法复盘，半年后无法迁移。**第三，预算按 P95 配。** 为了让最慢的请求也不超预算，把预算放大三倍，结果大多数请求的成本被浪费。

**第四，层间补偿。** 形态选重了想靠更强的模型救，校验缺了想靠更多重试救，信号是一次调优同时改了三层。**第五，迁移没有回滚点。** 从第 2 级跳到第 5 级，图不成立时只能整体重写。

**第六，评测集不随架构升级。** 架构从单循环升到图，评测集还是单循环那套，图级的失败测不到。**第七，把框架当成架构。** 选了框架就以为选型完成，五层里只填了框架这一格。

---

## 八、边界

**第一，本章不教新机制。** 五层里的每一层都在前文有专章，本章只回答怎么在一个具体项目上把它们配起来，因此它不能替代实现能力。**第二，三个画像是示例。** 它们的数字取自典型规模，不是任何真实项目的账单；量法在 `cases.py` 里，换成真实数字后所有推演可以复算。

**第三，选型不能替代实现。** 一份好 ADR 不会让系统自动变好，它只保证决定是可复盘的，实现质量仍然取决于第 54 章的循环与第 55 章的图。**第四，本章的两天量到有前提。** 前提是已经有线上流量或真实请求样本，全新项目只能先用假设值，并在 ADR 里标注待验证。

**第五，架构会随事实变化而过期。** 五类事实里任务形状与请求分布每月会变，ADR 要写复查日期，而不是长期有效。**第六，本章不管组织流程。** 谁签字、评审会怎么开、ADR 存哪里是流程问题，本章只规定 ADR 的内容必须包含什么。

---

## 这一章建立的 7 件事

1. 选型的输入是五类项目事实：任务形状、请求分布、错误代价、预算、团队与存量；每类都要有"两天内量到"的方法，量不到的不算事实。
2. 五层决策（形态、编排、供给、可靠性、交付）层间不可替代：一层选错，不会因为另一层加码而变对。
3. 把"复杂"换成三个可数的量：依赖步数、首次通过率、请求分布；量错的方向分别是低估步数、用测试集代替线上、按意图而非路径分类。
4. 用预算反算架构：预算决定能走几步，延迟决定这几步能不能串行；预算占比超过 90% 时，第一件事是谈预算或砍功能，不是调提示词。
5. **每一个架构决定都必须附一条落选方案的失效证据**——说不出"另一种会在什么条件下坏、坏在哪一层"，这个决定就还只是偏好，无法在三个月后复盘，也无法在半年后迁移。这是本章的结论。
6. 迁移是五级阶梯，每级要有升级触发（连续 7 天滚动均值）与回滚点（回到第几级、由哪个数触发）；阶梯的意义是给每一步留一个可退回的位置。
7. 验收看三个数：单任务成本、P95 延迟、外部裁判通过率；前两个说明成本与速度，第三个才说明做对了没有。
