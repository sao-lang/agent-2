## 一、检索质量的两种失效

第 17 章结束时，库能存能查了。剩下的问题是：查出来的东西不够好。

不够好有两种，修法完全不同：

| 失效 | 表现 | 该加什么 |
|---|---|---|
| 该找的没进候选 | 前 10 条里没有正确答案 | 混合检索、改写、扩大 k |
| 进了候选但排得靠后 | 前 10 条有，前 3 条没有 | 重排、RRF、调整权重 |

第一种是召回问题，第二种是排序问题，加错层的代价是白花一笔钱：给召回问题加重排，重排只能从已有的候选里挑，候选里没有正确项时它无能为力。判断方法很直接：拿一批带标注的查询，看正确答案在不在前 N 条里，在就是排序问题，不在才是召回问题，用第 14 章 pipeline.py 的记录就能算。

本章手段的顺序按先召回后排序：混合检索与改写解决召回，RRF 与重排解决排序，MMR 解决重复。这一章的数字都来自同一个 27 条语料与 10 条查询：绝对值会变，但哪种手段补哪类失效、代价在哪个量级，是可迁移的。

### 1.1 用两个数分开两类失效

具体怎么算：对每条查询，记下第一条正确结果的排名，然后统计两个数。

| 数 | 算法 | 含义 |
|---|---|---|
| 候选召回率 | 前 10 条里含正确结果的比例 | 召回够不够 |
| 首位正确率 | 第一条正确结果排第 1 的比例 | 排序好不好 |

如果候选召回率高、首位正确率低，问题在排序，重排与 RRF 有用；如果候选召回率本身就低，先补召回，加多少重排都没用。这两个数还能区分检索差与标注差：一条查询的正确答案在前 10 条里其实存在，只是标注时漏标了，这类假失败会让人去调一个没问题的环节，做法是抽查几条低分查询，看候选里有没有能回答的，第 14 章那套四步归因里的 `retrieved` 字段在这里同样能用。

## 二、稠密与稀疏互补

第 15 章讲过两者的强项：稠密擅长换说法，稀疏擅长精确词与编号。在同一批查询上跑一遍，差别是数量级的，实测来自 `code/knowledge/ch18_retrieval/retrieval_quality.py`：

```
=== 1. 三种检索在同一批查询上的指标（k=5）===
  稠密（bge-small）              recall@5 0.92   MRR@5 0.90   nDCG@5 0.85
  稀疏（BM25，未分词）               recall@5 0.10   MRR@5 0.10   nDCG@5 0.10
  稀疏（BM25，按字符切）              recall@5 0.95   MRR@5 0.90   nDCG@5 0.87
  混合 0.5/0.5                 recall@5 0.92   MRR@5 0.95   nDCG@5 0.88
  混合 0.8/0.2（偏稀疏）            recall@5 0.95   MRR@5 0.90   nDCG@5 0.87
  混合 0.2/0.8（偏稠密）            recall@5 0.92   MRR@5 0.90   nDCG@5 0.86
```

稀疏未分词那一行要单独看：BM25 的 recall 只有 0.10。原因不在 BM25，在分词，它默认按空格切词，中文没有空格，每句话成了一大 token，几乎匹配不上。示例里把 `preprocess_func` 设成 `list` 按字符切，绕开它，recall 立刻从 0.10 升到 0.95；生产里通常用 jieba 之类的分词器，效果更好，但要多维护一份词典。

对照第二、三行还有一个反直觉的结论：在这个语料上稀疏检索比稠密更好，政策文档的词高度重复，字面匹配几乎就够，稠密反而会被近似措辞带偏。第 15 章说过稠密对编号、型号不敏感，本章语料里恰好有 `A1001`、`99 元`、`7 天`、`24 小时` 这类精确内容，它们是稀疏的主场。

### 2.1 中文稀疏检索的三处难点

第一个是分词。前面那组 0.10 已经演示了后果：默认按空格切，中文整句变成一个 token。三种解法各有代价：

| 解法 | 做法 | 代价 |
|---|---|---|
| 按字符切 | `preprocess_func=list` | 召回够用，但词表大、语义粒度粗 |
| 分词器 | jieba 等，切完再拼空格 | 多一个依赖与一份词典 |
| 字 + 词混合 | 两种 token 都用 | 索引变大一倍 |

本章示例用第一种，因为它不引入依赖；生产里更常见的是第二种，粒度更接近语义。第二处是停用词：中文的"的""了""吗"每句都出现，按字符切之后权重被稀释但仍占位置。第三处是同义与简称：退款与退钱、运费与邮费字面不同，稀疏检索匹配不上，这正是稠密补位的地方，也是混合检索最实在的收益来源：不是两条路都试试，而是各自覆盖对方的盲区。

### 2.2 混合的两种实现

混合检索有两种做法，区别在怎么合并两路结果：

| 做法 | 合并方式 | 需要什么 |
|---|---|---|
| 分数融合 | 加权求和两路分数 | 两路分数要可比 |
| 排名融合（RRF） | 只用名次，不用分数 | 只需要两路都能排序 |

第一种在实现上最简单，问题在可比：余弦是 0 到 1，BM25 是 0 到几十，直接加权没有意义，必须先各自归一化；而归一化又引入新问题，同一路检索在不同查询上的分数分布不同，按查询归一化会让这一路整体不自信的信息丢失。第二种放弃分数的绝对值，只用名次，这就是 RRF。

### 2.3 混合检索多出来的维护成本

加一路检索不是多写十行代码，它带来三样要长期维护的东西。第一是索引：稀疏索引要随文档更新，向量要重算嵌入，稀疏只要重算词频，两套逻辑意味着两处可能不一致。第二是分词器版本：分词规则变了，倒排索引就要重建，这与第 16 章切法要跟索引版本一起记同构，任何影响 token 化的改动都是一次索引重建。第三是权重：两路权重与语料、查询分布绑在一起，如果没人负责，它会一直停在随手写的 0.5 上。三样加起来，混合检索的真实成本远高于多查一次。

## 三、RRF：只用名次融合

RRF 的公式很短，下面是示意：

```
score(d) = Σ_i  w_i / (c + rank_i(d))
```

`rank_i(d)` 是文档 `d` 在第 `i` 路检索里的名次（从 1 开始），`c` 是平滑常数（通常 60），`w_i` 是权重。名次越靠前贡献越大，`c` 让第一名与第二名的差距不至于过大。手写一遍，实现在 `code/knowledge/ch18_retrieval/retrieval_quality.py` 里：

```python
def rrf(rankings: list[list[str]], weights: list[float], c: int = 60) -> list[str]:
    """每条结果 1/(c + rank) 累加，与分数绝对值无关。"""
    scores: dict[str, float] = {}
    for ranking, w in zip(rankings, weights):
        for rank, doc_id in enumerate(ranking, 1):
            scores[doc_id] = scores.get(doc_id, 0.0) + w / (c + rank)
    return sorted(scores, key=lambda d: -scores[d])
```

同一批结果，两路排名与 RRF 的合并结果：

```
=== 2. 手写 RRF 与加权求和的差别 ===
  BM25 排名   ['d25', 'd15', 'd24', 'd6', 'd8']
  稠密排名    ['d15', 'd25', 'd10', 'd6', 'd1']
  RRF 等权    ['d25', 'd15', 'd6', 'd24', 'd10', 'd8', 'd1']
  RRF 偏稀疏  ['d25', 'd15', 'd6', 'd24', 'd8', 'd10', 'd1']
```

看第一、二行：两路的第一名不同，BM25 认为 d25 最相关，稠密认为 d15 最相关，而正确答案是 d15（`订单 A1001 已发货`），d25 是干扰项（`订单 A1000 已取消`）。RRF 等权的输出把 d25 排在了第一，两路各让一步，结果谁也没说服谁。

但 RRF 有一个别的做法没有的好处：它不需要两路分数可比。换一个嵌入模型、换一个 BM25 变体，分数分布全变，RRF 的结果不变，因为它只读名次，这让加一路检索变成低风险的事。

### 3.1 常数 c 与分数融合的对比

常数 `c` 控制名次的影响衰减得多快。`c=60` 是文献里的常用值，效果是第一名与第十名的贡献之比约是 `70/60 ≈ 1.2`，前十名之间的差距被压得很平；`c` 越小头部越重要，`c` 越大越接近只看有没有出现过。

| c | 第一名权重 | 第十名权重 | 效果 |
|---|---|---|---|
| 1 | 0.500 | 0.091 | 头名压倒性，后位几乎无贡献 |
| 10 | 0.091 | 0.050 | 头部明显更重要 |
| 60 | 0.016 | 0.014 | 头部略重要，整体平滑 |

`c=60` 之所以常用，是因为它让两路都排第 5 的文档能超过一路第 1、一路没出现的文档，这在多路融合里通常是想要的：一致的中等相关，比单路的高相关更可信。分数融合是另一种做法，写法更直接（示意）：

```python
def score_fusion(rankings, score_lists, weights):
    """先按各自的最大值归一化，再加权求和。"""
    merged = {}
    for ranking, scores, w in zip(rankings, score_lists, weights):
        top = max(scores) or 1.0
        for doc_id, s in zip(ranking, scores):
            merged[doc_id] = merged.get(doc_id, 0.0) + w * (s / top)
    return sorted(merged, key=lambda d: -merged[d])
```

它比 RRF 多一个假设：每一路的最高分代表这一路最可信的结果。当一路整体不自信时，归一化会把它的噪声放大成 1.0，这是分数融合最典型的失效。选择标准因此很清楚：分数没有共同尺度时用 RRF，有共同尺度时可以用分数融合，本章两路一个是 BM25 分、一个是余弦，必须用 RRF。

### 3.2 RRF 救不了的情况

RRF 有一个前提：两路的错误是独立的。本章第二节那组排名就是反例：BM25 把 d25 排第一，稠密把 d15 排第一，RRF 等权之后 d25 仍在第一位。根因不在融合算法，在两路都缺乏区分 A1000 与 A1001 的能力：BM25 按字符切之后两个编号高度重合，稠密则对编号不敏感。修法在更上游：把编号抽出来做精确过滤。混合检索能补的是表述差异，不能补信息缺失，问题需要精确匹配时，该加的是过滤器而不是第三路检索。两路的第一名经常是同一个错误答案时，问题不在融合，在表示。

### 3.3 权重怎么定

`weights` 决定两路的相对重要程度。本章实测里三组权重的 recall 都在 0.92 到 0.95 之间，差别不大，因为两路都还不错；权重真正起作用是在两路表现差距大的时候：

| 情况 | 该怎么配 |
|---|---|
| 查询里常有编号、型号 | 偏稀疏（0.6–0.8） |
| 查询多是口语化描述 | 偏稠密（0.2–0.4） |
| 两类混杂、无法预判 | 等权，或按查询特征动态调 |

第三行是实践中最常见的。一个可行的做法是按查询是否含数字、英文或编号动态调权：含编号的查询给稀疏更高权重，其余给等权，这比调一个固定权重稳，代价是多一条判断规则。

## 四、三个指标各自回答什么

本章所有对比都用三个数，它们不能互相替代：

| 指标 | 回答什么 | 取值 |
|---|---|---|
| recall@k | 该找的找到多少 | 0 到 1，越高越好 |
| MRR@k | 第一个正确答案排多前 | 0 到 1，越高越好 |
| nDCG@k | 所有正确答案的整体排名质量 | 0 到 1，越高越好 |

recall 管有没有，MRR 管第一个对不对，nDCG 管整体排得好不好。只报 recall 会漏掉排序问题：正确答案都在前 5 条里但每次排第 4 条，recall 是 1.00，体验却很差；只报 MRR 会漏掉多答案场景：一个查询有 3 条相关文档，只有 1 条被召回且排第一，MRR 是 1.00，recall 只有 0.33。三个一起看才有判断力，本章对比表里稠密加重排那一行是 recall 0.97、MRR 0.95、nDCG 0.89，三个都涨才算真的变好。

### 4.1 指标要按查询分组看

平均值会掩盖分布：十次查询里九次 recall 1.0、一次 0.0，平均 0.9 看起来不错，但那一次是彻底失败。除了均值还要看两个数：完全失败的查询条数，以及指标最低的五个查询。分组也可以按业务来：文档类型、查询类型、租户。一个整体 recall 0.9 的系统，可能在操作步骤类查询上只有 0.6。分组的价值在于把整体还行变成哪一块不行，有了分组才能针对性补语料、补规则。

### 4.2 指标之外还要看的两列

指标只能说明检索得准不准，不能说明值不值。任何一次加手段，都要在对比表里补上两列：

| 列 | 怎么量 | 为什么必须看 |
|---|---|---|
| 延迟 | 单次检索的 P50 与 P95 | 重排与改写都是数百毫秒级 |
| 成本 | 每次查询的 token 或算力 | 改写要调模型，重排要跑前向 |

把本章的两张表补成四列，结论会变得具体：

| 方案 | recall@5 | MRR@5 | 延迟 | 增量成本 |
|---|---|---|---|---|
| 稠密 | 0.92 | 0.90 | 几十 ms | 无 |
| 稠密 + 重排 | 0.97 | 0.95 | +几十到几百 ms | 一次前向 × 候选数 |
| 混合 | 0.92–0.95 | 0.90–0.95 | +几 ms | 一路索引 |
| 多查询 | 1.00（并集） | — | +一次模型调用 | 数百 ms |

第三行是这一章里性价比最高的：混合检索的增量成本只有几毫秒，因为它只是多查一次倒排索引，而重排的增量是数十到数百毫秒，所以在瓶颈不明确时先加混合再考虑重排。第四行的成本最高，收益却不一定：多查询的并集 recall 是 1.00，但直接拼接后 recall@5 掉到 0.67，必须再配一次融合才有意义。

### 4.3 评测集从哪儿来

本章的 10 条查询是手写的，规模够看出方向，不够支撑上线决策。真实评测集通常有三个来源：

| 来源 | 优点 | 缺点 |
|---|---|---|
| 人工编写 | 覆盖全、可控 | 慢，且容易写出"文档里的措辞" |
| 线上真实查询 + 标注 | 分布真实 | 需要标注人力，涉及隐私 |
| 线上日志反推 | 零成本 | 只能拿到"用户点了哪条"，噪声大 |

第二种是主力：从线上抽样几百条真实查询，让业务标出哪几条文档能回答它。第三种作为补充：用户点了哪个引用、看完有没有追问都是弱信号，能发现标注集覆盖不到的查询类型。

评测集要带版本，与索引版本一起记，第 16 章说过这一点：一份不知道对应哪版文档的评测集，跑出来的分数没有意义。

### 4.4 小样本差别是噪声

本章的 10 条查询，两条方案差 0.03 到 0.05 很常见：10 条里换对一条，recall 就变 0.1。判断改动是否有效要三个条件：查询数够多、方向在多数查询上一致、变化大于随机波动。最便宜的估法是换一批查询重跑，两个不相交的查询集上方向相同，结论才可信。调完参数指标涨了 0.02 这种结论经常复现不了，涨的那点来自某一条的运气。在几十条查询的规模上只应相信方向明确、差距大的结论，比如 recall 从 0.10 到 0.95 的分词效应。

### 4.5 指标要跟着答案走

检索指标衡量的是块有没有被找到，不是答案对不对。两者多数时候一致，但有两种情况会分叉：块被召回而模型没用时，检索指标好、答案是错的，问题在生成或拼装；召回了错误的块而模型靠常识答对时，检索指标差、答案是对的。所以检索指标只能用来判断检索层的改动。整条链路的验收在 RAG 评测一章，那里的指标是端到端的。

## 五、重排

重排是用更贵的模型对少量候选重新打分。第 17 章末尾说过，它的输入是已召回的候选，所以只解决排序问题。运行 `code/knowledge/ch18_retrieval/rerank_mmr.py` 的输出：

```
=== 2. 重排：先取 10 条，再用 cross-encoder 排前 5 ===
  稠密 top-5                   recall@5 0.92   MRR@5 0.90   nDCG@5 0.85
  稠密 + 重排                    recall@5 0.97   MRR@5 0.95   nDCG@5 0.89
```

三个指标都涨了。逐条看第一条正确结果的位置：

```
  生鲜坏了怎么退          重排前  2 -> 重排后  1  <- 改善
  换货要几天内申请         重排前  2 -> 重排后  2
  改善 1 条，变差 0 条，不变 9 条
```

改善 1 条、变差 0 条。这个比例说明语料对稠密来说偏简单，重排的空间不大：如果稠密的 MRR 已经是 0.95 以上，重排通常只能带来一两个点的提升，而延迟是数百毫秒。重排的代价要算清楚：

| 项 | 量级 |
|---|---|
| 延迟 | 每对（查询, 候选）一次前向，10 个候选约几十到几百毫秒 |
| 算力 | cross-encoder 参数量约为 bi-encoder 的 10 倍 |
| 输入长度 | 受模型窗口限制（bge-reranker-base 是 512 token） |
| 收益 | 取决于候选里"该在前面的排错了"的比例 |

第三行容易被忽略：被重排的候选如果很长会被截断，重排看到的是半个文本，这与第 15 章的截断是同一个问题，只是发生在另一个模型上。

### 5.1 重排该重排多少条

`top_n` 是重排后保留的条数，`fetch_k` 是候选数，两个数一起决定成本与效果：

| 候选数 | 重排成本 | 召回上限 |
|---|---|---|
| 5 | 低 | 低（候选里没有的救不回来） |
| 10 | 中 | 中 |
| 50 | 高 | 高（但延迟可能不可接受） |

重排的召回上限就是候选集的召回：候选集 recall@10 是 0.95，重排后 recall@5 最多 0.95，它不能凭空造出没召回的内容。所以先测候选集的 recall@k 再决定要不要加重排，候选集 recall 只有 0.6 时先补召回。

### 5.2 重排模型怎么选

重排模型有两类，差别在要不要一次性看查询与文档：

| 类型 | 例子 | 精度 | 延迟 |
|---|---|---|---|
| cross-encoder | bge-reranker-base | 高 | 每对一次前向 |
| 轻量 cross-encoder | MiniLM 系（英文为主） | 中 | 快一个量级 |
| 生成式打分 | 让模型输出 0-10 分 | 低且不稳 | 一次调用 |

本章用的是 `BAAI/bge-reranker-base`，512 token 窗口、约 1.1 GB，代价是加载与推理都更重。选择时看三个数：候选数乘单对延迟决定总延迟，窗口大小决定多长的块会被截断，中文支持决定它能不能用。

生成式打分不建议用在主路径：它把排序变成了生成，输出不稳定。

### 5.3 两级重排

候选很多时可以用两级重排：先用轻量模型或向量相似度从 100 条收到 20 条，再用重模型从 20 条收到 5 条。

| 方案 | 延迟 | 精度 |
|---|---|---|
| 只重排 100 条 | 高（100 次前向） | 高 |
| 两级：轻 100→20，重 20→5 | 中 | 接近 |
| 只重排 10 条 | 低 | 取决于候选质量 |

第二行的价值在于用便宜的模型砍掉大部分候选，前提是轻量模型的排序不能太差，它只要保证正确答案在前 20 里。代价是复杂度：两个模型、两套参数，除非候选数超过 50，否则不值得。

### 5.4 重排的截断

重排模型也有窗口。bge-reranker-base 是 512 token，一块 300 字的文档加上查询大约 400 token 勉强能放下，一块 800 字的文档会被截断。这与第 15 章的截断是同一个问题，但后果不同：嵌入截断让这块搜不到，重排截断让这块排名偏低，后者更隐蔽，因为块仍然被召回了。

判断方法是对比重排前后的排名变化与块长，长块排名普遍下降说明截断在起作用；处理方式是限制输入块长。

### 5.5 重排之后还有一步常被忘掉

重排输出的是排好序的候选，接下来要拼装（第 19 章）。这两步之间有一个接口问题：重排的分数要不要传给拼装？传的好处是拼装可以按分数截断，坏处是这个分数是 cross-encoder 的原始分；不传的好处是解耦，坏处是遇到全部低分的查询也会硬塞满。折中的做法是传两个值：名次，以及一个只在候选内部归一化的分数，后者足以回答这批候选里哪些明显更差。检索层的输出因此还包括这批结果的置信程度，第 14 章讲的拒绝回答，判断依据正来自这里。

## 六、MMR：解决"结果太像"

MMR 解决的是第三种失效：前 5 条内容几乎一样。运行 `code/knowledge/ch18_retrieval/rerank_mmr.py` 的对照：

```
=== 4. MMR：λ 不同，前 5 条的多样性不同 ===
  λ=1.0  前 5 条 ['d3', 'd12', 'd16', 'd17', 'd27']  recall@5 1.00
  λ=0.7  前 5 条 ['d3', 'd12', 'd16', 'd17', 'd25']  recall@5 1.00
  λ=0.3  前 5 条 ['d3', 'd25', 'd17', 'd2', 'd26']  recall@5 0.50
```

`lambda_mult` 是相关性与多样性的权重：1.0 只看相关性，0 只看多样性。λ 从 1.0 降到 0.3，前 5 条里出现了 d25、d26 这类不相关的项，多样性是以相关性为代价换来的，调得太低，检索就变成了找不一样的而不是找对的。什么时候用 MMR：一个查询需要多个角度时，或者库里有大量近似重复时；后者是数据问题，应该去重，不该靠 MMR 掩盖。

### 6.1 fetch_k 决定 MMR 有多少可选

MMR 先取 `fetch_k` 条候选，再在里面挑 `k` 条互不相似的。`fetch_k` 太小，可选的太少，多样性无从谈起；太大，计算量与召回成本都上升。

| fetch_k | 效果 |
|---|---|
| = k | MMR 退化成普通检索 |
| 2k–3k | 常见的折中 |
| 远大于 k | 多样性上限更高，但延迟与噪声上升 |

本章示例用 `fetch_k=10, k=5`。还有一个容易被忽略的细节：MMR 的相似度用的是块与块之间的距离，不是块与查询的，所以它需要访问所有候选的向量，这意味着 MMR 通常发生在应用侧，而不是数据库侧。

### 6.2 λ 的起点

从 0.7 开始试：它保留大部分相关性，同时给多样性留了空间。本章实测里 0.7 与 1.0 的结果几乎一样，说明这个语料上重复不是主要问题；λ 调到 0.3 时出现了不相关项，recall 掉到 0.50，这就是多样性过度的样子。

判断是否需要 MMR 的信号是前 5 条里有两三条讲同一件事，没有这个信号，加 MMR 只会损失相关性。

## 七、改写问题

查询改写发生在检索之前，用来解决用户的话与库里的写法对不上。运行 `code/knowledge/ch18_retrieval/retrieval_quality.py` 的多查询对照：

```
=== 5. 多查询：三条改写各查一次，取并集 ===
  原查询 '生鲜坏了怎么退' 单次召回 ['d27', 'd17', 'd4', 'd21', 'd5']
  多查询并集        ['d17', 'd27', 'd21', 'd4', 'd25', 'd5', 'd1']
  recall@5 单次 1.00 -> 多查询 0.67
```

这一组结果值得细看：多查询的并集里包含了所有正确项，但直接拼接之后前 5 条里只剩 3 个正确项，recall@5 从 1.00 掉到 0.67。并集不是融合：三路结果直接拼起来，等于把每一路的第一名按哪一路先跑的顺序排列，而不是按相关性。正确做法是把三路结果用 RRF 合并，或者用重排统一打分。拼接在代码上最简单，但不同来源的结果没有共同的尺度，合并必须有规则。改写本身还有两个代价：

| 代价 | 说明 |
|---|---|
| 一次额外调用 | 改写要调模型，延迟增加数百毫秒 |
| 改写可能跑偏 | 把"退货"改成"退款流程"，语义变了 |

第二行是改写特有的风险：它不是无损操作。一个把生鲜坏了怎么退改成生鲜商品退款政策的改写，可能让检索偏向政策条款而错过操作步骤。所以改写要么用固定的模板，要么在改写后保留原查询一起检索。

### 7.1 改写的两种做法

改写有两种实现，代价差一个数量级：

| 做法 | 例子 | 代价 | 稳定度 |
|---|---|---|---|
| 规则 | 同义词表、去掉"请问""一下" | 微秒级 | 高 |
| 模型 | 让模型生成 3 个改写 | 一次调用 | 中 |
| 混合 | 规则清洗后再交给模型 | 一次调用 | 中高 |

第一种能解决口语词、指代与同义词，它解决不了用户的说法与库里的说法完全不在一个词表里的情况，那需要模型。第三种是实践里的常客：先用规则去掉明显无关的词，再让模型做语义层改写，规则那层的价值是减少模型改写的自由度。

### 7.2 HyDE：把问题改写成答案

还有一种改写值得单独提：HyDE。它不改写问题，而是让模型先编一个假答案，再用这个假答案去检索。原理是问题与文档的表述方式不同，一个是疑问句，一个是陈述句，而假答案是陈述句，更接近文档的形态。代价与风险都很明显：

| 方面 | 说明 |
|---|---|
| 成本 | 一次生成调用，比普通改写更贵 |
| 风险 | 假答案可能编错，把检索带偏 |
| 适用 | 问题短、文档长、表述差异大 |

第三行是关键。用户问东西坏了能退吗，文档写质量问题退货、往返运费由商家承担，两者字面差异大，HyDE 生成的假答案与文档更接近。但它有一个无法消除的问题：假答案本身可能错。

HyDE 提高的是表述匹配度，不是事实正确性，所以它适合检索不到而非检索错的场景：候选召回率低、人工看候选又觉得这些文档其实能答时值得一试；选错了文档时，它只会错得更远。

### 7.3 改写要单独评测

改写是唯一一个输入被改了的手段，所以它不能只看最终指标，必须单独看改写后的查询是否还在问同一件事。一个便宜的做法是人工抽检：取 50 条改写前后的对照，标语义是否保持，但能发现一类严重问题：改写把否定改没了，或者把范围改了。

第二类问题的后果最大：把生鲜坏了怎么退改成商品坏了怎么退，检索会返回通用退货政策，答案看起来正确但漏掉生鲜的特殊条款，而端到端指标可能还是通过的。改写的评测要看两条曲线：检索指标的提升与语义保持率的下降。

## 八、什么时候不该加

每种手段都有代价，加之前先看当前的瓶颈在不在它解决的那一层：

| 手段 | 解决什么 | 代价 | 不该加的信号 |
|---|---|---|---|
| 混合检索 | 召回 | 多一路索引，写入变慢 | 稀疏分词都没做对 |
| 重排 | 排序 | 数百毫秒延迟 | 候选集 recall 已经很低 |
| 改写 | 召回 | 一次模型调用 | 查询本来就是规范表述 |
| MMR | 重复 | 相关性下降 | 重复来自数据而非算法 |

第一行最典型：分词没做对时加混合检索，等于把一路 0.10 的检索混进来。第四行是数据问题的误判：MMR 能让结果看起来多样，但库里仍存着重复数据，正确做法是按内容去重（第 21 章讲治理），MMR 只适合同一主题的多个侧面。

### 8.1 一次查询的延迟预算

把四层叠起来，延迟会累加。以一个典型的问答请求为例：

| 层 | 典型延迟 | 能不能砍 |
|---|---|---|
| 改写 | 200–800 ms（一次调用） | 能，只在召回差时开 |
| 混合检索 | 几 ms（BM25）+ 几十 ms（向量） | 不能，是主路径 |
| 重排 | 50–300 ms（10 条候选） | 能，`top_n` 调小 |
| 拼装 | 1 ms | 不能 |

四层加起来，检索阶段可能到一秒以上，而真正的生成只要几百毫秒，用户感知到的慢主要来自检索的附加层，不是模型。可行的做法是按查询特征分层：简单查询只走稠密，复杂查询才走改写加混合加重排。

第 13 章讲的分流之所以放在最前面，是因为它是唯一能在入口处省掉后面所有层成本的手段。

### 8.2 该先加哪一层

按每毫秒换多少指标排序，本章的结论是：

| 手段 | 增量延迟 | 增量指标 | 优先级 |
|---|---|---|---|
| 混合检索 | 几 ms | recall +0.03 | 高 |
| 重排 | 100 ms 量级 | recall +0.05 | 中 |
| 改写 | 300 ms 量级 | 取决于查询类型 | 低 |
| MMR | 几 ms（本地计算） | 多样性，相关性可能降 | 按需 |

第一行的性价比最高，所以顺序是：先把混合做对（包括分词），再看重排，最后才考虑改写。这个顺序与先召回后排序一致，也与工程实现的难易一致。

### 8.3 改动前先留一份基线

每个手段都要能回答加了它之后哪三个数变了，前提是有一份可复现的基线：同一批查询、同一批文档、同一套指标脚本，在加手段之前跑一遍并记下来。基线的三个要素容易被漏掉：随机性要固定种子，数据版本一变旧基线就失效，口径要写进脚本。

有了基线，加手段的决策就变成一个比较：指标涨了多少、延迟涨了多少、维护成本涨了多少，任何一个明显变差都要重新考虑。

## 九、组件与参数

副线要认的四个组件，每个对应一个手段：

| 手段 | 组件 | 关键参数 |
|---|---|---|
| 混合检索 | `EnsembleRetriever` + `BM25Retriever` | `weights`、`k`、`preprocess_func` |
| 重排 | `ContextualCompressionRetriever` + `CrossEncoderReranker` | `model`、`top_n`、`base_retriever` |
| 改写 | `MultiQueryRetriever` | `llm`、`include_original` |
| 多样性 | `store.as_retriever(search_type="mmr")` | `fetch_k`、`lambda_mult`、`k` |

四行里有三个包裹型组件：`EnsembleRetriever` 套两路检索，`ContextualCompressionRetriever` 套一个重排器，`MultiQueryRetriever` 套一个改写器。这种设计可以任意组合，坏处是延迟累加。

### 9.1 一个可用的组合

一个可用的组合是把两段检索包进压缩器，写法见 `code/knowledge/ch18_retrieval/rerank_mmr.py`：

```python
bm25 = BM25Retriever.from_documents(docs, k=10, preprocess_func=list)
dense = store.as_retriever(search_kwargs={"k": 10})
hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.5, 0.5], k=10)
reranked = ContextualCompressionRetriever(
    base_compressor=CrossEncoderReranker(model=hf_ce, top_n=5),
    base_retriever=hybrid,
)
```

两段拼接，`k` 从 10 收到 5。这个组合的延迟大致是 BM25 几毫秒加稠密几十毫秒加重排几十到几百毫秒，重排占了大头，所以它的 `top_n` 要小。

### 9.2 参数到结论的映射

| 结论 | 落到哪个参数 |
|---|---|
| 两路要能比 | `weights` 只在等权附近有意义，差距大时先修单路 |
| 重排救不了没召回的 | `base_retriever` 的 `k` 要大于 `top_n` |
| 改写要保留原查询 | `include_original=True` |
| 多样性不能过度 | `lambda_mult` 不要低于 0.5 |

第一条容易被误解为权重随便调。实际是：当两路指标差距大时（比如 0.3 对 0.9），加权平均救不了差的那一路，只会稀释好的那一路，这时该修的是差的那一路。

### 9.3 组合时的三个坑

把几个包裹组件叠起来，有三个问题几乎必然遇到。第一个是顺序：改写要在检索之前，重排要在检索之后，把重排放在改写前面，重排的是原查询的候选，改写的价值就消失了。第二个是重复：混合检索会让同一个块从两路都返回，两路 id 体系不同时合并会出现同一内容两条记录。第三个是分数方向：重排器的分数越大越相关，而某些库返回距离，方向错了结果完全反转，代码不会报错。

三个问题的共同点是它们都不产生异常，只产生看起来正常但结果不对。

## 十、边界

**先量再改。** 没有基线就加手段，无法判断收益。

**召回问题不能用排序手段修。** 候选里没有的，重排造不出来，`top_n` 再好也救不了候选集 recall 0.6 的情况。**RRF 不是万能的。** 两路在同一个干扰项上犯错时，融合会强化错误；它解决的是两路各自有理的情况，不是两路都缺信息的情况。**改写要保留原查询。** 改写是有损的，单独用它会把操作步骤类问题导向政策条款，`include_original=True` 是低成本的保险。**MMR 的多样性有价格。** λ 低于 0.5 时相关性明显下降，本章实测 recall 从 1.00 掉到 0.50，用之前先确认前几条是真的重复。**延迟是累加的。** 混合加重排加改写叠在一起，检索阶段可能从几十毫秒变成一秒以上，按查询特征分层是唯一能在入口处省掉这些成本的手段。**不要用检索指标验收整条链路。** recall 与 MRR 只说明块找到了没有，不说明答案对不对，召回了但模型没用、没召回但模型答对了，这两种分叉都会让检索指标与用户感受脱节。**任何加一层都要能单独关掉。** 重排超时、改写超时、混合的一路挂掉，都应该有降级路径：重排失败就用检索顺序，改写失败就用原查询，稀疏挂掉就只走稠密。

一条经验判断：如果关掉某一层之后指标几乎不变，那就该关掉它。每一层都在消耗延迟、算力与维护注意力，这条判断要定期重做。

## 这一章建立的 6 件事

1. 检索失效分两种：没召回（加混合、改写）与排得靠后（加重排、RRF），加错层等于白花钱。
2. 中文 BM25 不分词时 recall 只有 0.10，按字符切立刻到 0.95；混合检索前必须先把每一路单独调好。
3. RRF 只用名次不用分数，所以换模型、换实现都不影响它；但两路同时犯错时它会强化错误。
4. 三个指标各管一段：recall 管有没有、MRR 管第一个对不对、nDCG 管整体排序；只报一个都会漏。
5. 重排的收益受候选集召回限制，代价是数百毫秒；`top_n` 要小于候选数，否则重排没有意义。
6. 多查询的并集不是融合，直接拼接会打乱顺序（本章实测 recall@5 从 1.00 掉到 0.67），必须配 RRF 或重排。
