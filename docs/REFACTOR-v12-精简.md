# 方案 v12：正文精简（语言层，不动知识点）

> 目标读者反馈：每章概念多、读得慢、AI 味重（情绪化用词、不精炼）。
> 本方案只处理**语言的组织方式**，不动章节结构、知识点、代码、输出、表格。
> 生效后需同步修改 `docs/WRITING-SPEC.md` 第二节与 `docs/check_chapters.py` 的篇幅下限，否则改写会被生成器按旧口径补回去。

---

## 一、先说诊断：现在的"长"和"AI 味"从哪来

全书的量化基线（58 个正文文件，41.6 万汉字，不含代码与表格）：

| 指标 | 现状 | 说明 |
|---|---|---|
| 每章汉字数 | 9000–10500（中位 9300） | 贴着 `check_chapters.py` 的 9000 下限写 |
| 正文段落数 / 章 | 110–200 | 中位 128 |
| 平均段长 | 57.7 字（中位 52） | 一段普遍只有 1–2 句 |
| ≤20 字的段落 | 1244 个（占正文段 17%） | "短句成段"是节奏感的来源 |
| 解释性破折号 `——` | 1499 处 | 平均每章 26 处 |
| "不是 A，而是 B" | 247 处 | 平均每章 4.3 处 |
| 括号补充（≥6 字） | 1861 处 | 平均每章 32 处 |
| 第二人称"你" | 352 处 | 把读者拉进场景 |
| "这一节/本章/下面/前面" | 360 处 | 讲文章怎么组织，不讲内容 |
| 粗体占正文汉字 | 7.5%（3.1 万字） | 每章 24–130 处 |
| 情绪/评价类词 | 75 处（很贵、致命、灾难、坑…） | 集中但刺眼 |

这些数字对应四类可分离的毛病。**它们都不是"概念太多"，而是承载概念的句子出了问题。**

### 1.1 元话语：讲"这段很重要"，而不是讲"这件事是什么"

现状例（第 4 章）：

> **提示词缺项的代价不是"模型答得差"，而是"出错了归因不到提示词"。** 这句话决定了后面所有做法的意义：结构化的目的不只是让程序能读，更是让失败能被定位到一个具体的地方。

删掉"这句话决定了后面所有做法的意义"这类句子，读者不损失任何信息——它评论的是文章，不是系统。全书同类形态还有"这一条单独值得说""到这里可以把校验拆开看""下面这个脚本""注意这一条和上一条的区别"。

### 1.2 断面式句法：一个陈述 + 一个破折号补语

现状例（第 11 章）：

> 这段提示词的最后一个词是 `Introduce variation`——要求模型给出**有变化**的输出。

破折号后面的内容往往就是前半句的展开，合并成一个句子即可。1499 处破折号里，绝大多数属于这一类；少数是真正的插入语。

### 1.3 金句化：每段以一句粗体断言收尾

现状例（第 4 章）：

> **最容易发现的问题，往往最不重要。**

单看有力，连起来读就变成节拍器：讲一段、收一句、讲一段、收一句。读者感到"说得都对，但读完记不住"，原因在于**判断句太多、事实句太少**。粗体占正文 7.5% 是这一形态的量化标志。

### 1.4 情绪化与拟人化用词

现状例（第 14 章）：

> 噪声本身不致命，致命的是它挤占了预算、稀释了注意力。

"致命"是评价，不是事实；事实是"噪声挤占窗口预算、降低相关块的占比"。同类还有"很贵/很便宜"（应写"单次调用成本相差 N 倍"）、"坑""踩坑""烧钱""灾难性的第一步"。另有 195 处"兜住/兜底/接住/扛住"把系统写成了有身体的东西。

### 1.5 附带发现（先修，否则没有干净基线）

- 第 54、55 章文件缺失（`54-循环工程…`、`55-图工程…`），`check_nav.py` 因此失败并连带 4 处死链。
- 7 个文件的章内目录与正文 H2 不同步（`gen_book.py build` 可修）。
- 第 08 章 8861 字，低于 9000 下限，本来就没过检查。

## 二、目标口径（改完后要达到的数）

| 指标 | 目标 | 相对现状 |
|---|---|---|
| 散文汉字（读者真正读的部分，去掉代码/表格/标题/章首） | 4800–6250 | −27% 以上 |
| 章汉字数（`check_chapters.py` 口径，含不可改的章首与章末） | 6000–6800，下限 5500 | −25% ~ −30% |
| 平均段长 | 85–140 字 | 段落合并，约 −45% 段数 |
| 连续"≤20 字段落" | 不超过 2 段 | 消除碎片节奏 |
| 粗体占正文 | ≤3.5%，每章断言式粗体 ≤6 处 | 减半 |
| 破折号 `——` | ≤8 处/章 | −70% |
| "不是 A，而是 B" | ≤2 处/章 | 减半以上 |
| 括号补充 | ≤10 处/章 | −70% |
| 第二人称"你" | 0 | 全删 |
| "本节/本章/下面/前面" | ≤4 处/章（仅目录与导航保留） | −90% |
| 情绪/评价词 | 0 | 全删 |

阅读时间的口径：技术文本中文约 300–400 字/分钟，9000 字纯读 25–30 分钟，加上停下来看代码、自己想例子，一小时是正常损耗。降到 6000 字后，纯读 15–20 分钟，整章 35–40 分钟。

**为什么不是"删小节"**：章节结构是知识点的载体（`book.json` 与 `check_nav.py` 都在校验它）。删小节会连带破坏知识点追溯与目录。所以字数下降只能来自句子与段落层，H2/H3 标题一律保留。

## 三、不可触碰清单（硬约束）

改写只允许动**散文段落**。下列内容逐字保留，靠脚本而非自觉来保证：

| 内容 | 校验方式 |
|---|---|
| H1、H2、H3 标题（含编号） | 与原文逐字比对，集合相等、顺序相等 |
| 代码块 ``` | 提取全部 fence 内容，SHA-256 与原文一致 |
| 运行输出块（无语言标注的 fence） | 同上，逐字一致 |
| 表格 | 行数与每行内容一致；只允许改表格**外**的说明文字 |
| 章首 4 行（卷行/知识点/本章回答/示例目录/读完应当能回答） | 逐字一致（由 `book.json` 生成，本就不该动） |
| `## 这一章建立的 N 件事` 及其 N 个条目 | 逐字一致 |
| `## 下一章` 段落与导航行 | 逐字一致 |
| `第 N 章` 交叉引用、`code/knowledge/...` 路径、相对链接 | 出现次数不少于原文 |
| 知识点名词 | 每章按 `book.json` 的 points + 原 H3 标题生成词表，改写后每个词必须仍出现 |

## 四、改写规则（12 条，可机械执行也可机检）

每条都给出"判据 — 改法"，便于写进批量改写的提示词，也便于写成 lint 规则。

| # | 规则 | 判据（能搜到就改） | 改法 |
|---|---|---|---|
| R1 | 删元话语 | "这句话/这一条/这一点 + 决定/说明/值得/关键在于"；"本节/本章/下面/前面/到这里/接着看" | 整句删除；确实需要指路时合并进上一句 |
| R2 | 情绪词换事实 | 致命、灾难、很贵、很便宜、坑、烧钱、可怕、惊人、武器、硬伤、翻车 | 换成可测的后果："成本高 3 倍""记录为空""识别率降到 12%" |
| R3 | 去拟人 | 兜住、兜底、接住、扛住、撑住、看得见、记住、看见 | 换成对应代码对象："返回 None""跳过校验""上下文里保留 X" |
| R4 | 破折号补语合并 | `——` 后面是同位语或展开 | 改为逗号承接，或拆成独立句；每章最多留 8 处真插入语 |
| R5 | 段落合并 | 连续 2 段以上各只有 1–2 句，且讲同一个论点 | 合并成一段（90–130 字），保留原有的每一句事实 |
| R6 | "不是 A 而是 B" 降频 | 每章超过 2 处 | 保留最有力的一处，其余改为直接陈述 B |
| R7 | 粗体只标值 | 粗体内容是一个判断句、成语式短句 | 只保留字段名、数字、命令、错误信息；判断句去粗体 |
| R8 | 删重复结论 | 同一判断在章首、节末、章末各出现一次 | 只留信息量最大的一处 |
| R9 | 删第二人称场景 | "你""想象你是""你答不上来" | 改为无人称陈述："调用方无法判断""该值缺失" |
| R10 | 一句一事 | 一句里两个以上"的"链、三个以上分句 | 拆句；术语首次出现就地解释 |
| R11 | 括号补充去括号 | `（…）` 且 ≥6 字、非代码/非版本 | 并入正文，或独立成句；只保留极短的同位说明 |
| R12 | 压缩解释、保留因果 | 一节里"为什么"讲了两遍 | 保留"缺什么→成因→怎么补→会怎么坏"这条链，删掉同层的复述 |

**R12 是最容易做错的一条**：精简的目标是把"同一个原因说三遍"改成"说一遍"，不是把原因删掉。判定方法是逐节问：这一节删完后，读者还能不能自己回答"为什么要这一步"。

## 五、改前 / 改后对照（真实段落）

### 例 1（第 4 章，一、提示词的六项）

原文（381 字）：

> 先看坏的样子。同一段提示词，只删掉一句话，输出照样有内容、读起来也通顺，区别只有一处：程序解析不了。删的是"只输出一个 JSON 对象，不要任何其他文字"这一句。删掉之后，模型给了一段表格——人看完全没问题，`json.loads` 直接抛异常。
>
> 这类失效的共同点是：**输出看起来是正常的。** 没有报错、没有空回复、没有明显的错。写提示词时最容易只盯着"任务说清楚了没有"，而说清任务只是六项里的一项。
>
> 代价落在下游。解析失败的那一行抛异常，异常被上层接住、记一条日志、返回一个笼统的 500。到这一步，从用户看到的信息里已经看不出问题在哪——可能是检索没召回、可能是模型拒答、可能是解析失败，也可能只是某个字段的类型不对。**提示词缺项的代价不是"模型答得差"，而是"出错了归因不到提示词"。** 这句话决定了后面所有做法的意义：结构化的目的不只是让程序能读，更是让失败能被定位到一个具体的地方。

改写（214 字）：

> 同一段提示词只删掉"只输出一个 JSON 对象，不要任何其他文字"这一句，输出照样有内容、照样通顺，只是换成了一段表格，`json.loads` 直接抛异常。这类失效的共同点是输出看起来正常：没有报错、没有空回复、没有明显错误，写提示词时最容易只看"任务说清楚了没有"。
>
> 代价落在下游。异常被上层接住、记一条日志、返回一个笼统的 500，从用户看到的信息里已经分不出是检索没召回、模型拒答、解析失败，还是某个字段类型不对。所以结构化的作用不只是让程序能读，更是让失败能被定位到一个具体位置。

保留的事实：删句实验、失效表现、下游代价、四个可能的失败源、结构化的两个作用。
删掉的：开场指路句、"这句话决定了后面所有做法的意义"、两处破折号、一处判断式粗体。

### 例 2（第 14 章，噪声）

原文：

> **第二种是混进噪声。** 该找的找到了，同时还带进来一批不相关的块。噪声本身不致命，致命的是它挤占了预算、稀释了注意力。

改写：

> 第二种是混进噪声：该找的块找到了，同时带回一批不相关的块。噪声的代价不在内容错，而在它挤占窗口预算、稀释相关块在上下文中的占比。

## 六、批量执行流程

### 步骤 0：修基线（一次性）

```
python docs/gen_book.py build          # 同步 7 处章内目录
python docs/check_chapters.py --all
python docs/check_nav.py
git branch trim/v12 && git checkout trim/v12
```
第 54、55 章缺失单独处理（补写，或调整 `book.json` 的卷归属后再跑 build）。

### 步骤 1：新增两个脚本

**`docs/lint_prose.py`** —— 把第二节的目标口径做成机检，输出每章的违规清单与分数：

```
python docs/lint_prose.py --all
python docs/lint_prose.py 04-提示词工程-从规则到结构化输出.md
```
检查项：汉字数、平均段长、≤20 字段落连续数、粗体占比、破折号数、"不是…而是"数、括号补充数、第二人称、元话语短语、情绪词表命中。**它的意义是给"改没改到位"一个客观标准**，避免人工逐章判断风格。

**`docs/trim_verify.py`** —— 对比改前改后两个版本，核对第三节的不可触碰清单（fence 哈希、标题集合、表格、章首、章末、知识点词表、交叉引用数），任何一项不符即失败。

### 步骤 2：分章改写（每章一次调用）

把整章当作输入，按固定提示词改写，提示词骨架：

```
你是技术书编辑，任务是把这一章的正文压缩 30%，只改语言组织。

必须保留、逐字不动：
- 所有 # 标题行
- 所有 ``` 代码块与运行输出块（含其前后各一行说明的对应关系）
- 所有表格（不得改行）
- 形如 ⟦P3⟧ 的占位符（原样留在原位置）

可以改：段落文字、句子结构、标点。
按这 12 条规则改：<R1–R12 全文>

禁止：新增事实、新增数字、新增例子、新增概念、改变任何结论的方向。
禁止：删除任何"缺什么→成因→怎么补→会怎么坏"的因果环节；只允许把同一原因的多重复述并成一处。
目标：每章 6000–6800 汉字，平均段长 90–130 字。
```

**保护块回填**（关键安全机制）：改写前脚本把每章切成 `散文 / 受保护块` 交替序列，受保护块替换为 `⟦P1⟧…⟦Pn⟧`；模型只看到占位符；回填时按序号还原，哈希比对。这样代码与输出"物理上不可能"被改坏。

### 步骤 3：自动校验（每章，几秒）

```
python docs/trim_verify.py 04-*.md --base HEAD
python docs/lint_prose.py 04-*.md
python docs/check_chapters.py 04-*.md
```
三项全绿才进入人工复核。

### 步骤 4：人工复核（每章 5 分钟）

只看 `git diff --word-diff` 的删除侧，问三个问题：
1. 有没有删掉一个只有这一章讲过的判断？
2. 有没有把"为什么"改成"怎么做"？
3. 改写后的段落，换个场景还成立吗（说明讲的是原理，不是本章的代码）？

### 步骤 5：提交

一章一个 commit，message 形如 `trim: 第 4 章 −31%（9286→6412）`。任何一章出问题可单独 `git revert`。

### 步骤 6：全书收尾

改 `check_chapters.py` 的 `MIN_CHARS = 5500`、改 `WRITING-SPEC.md` 第二节口径 → 跑 `gen_book.py build` → `check_nav.py` → `check_chapters.py --all` → 更新 `docs/INDEX.md`（build 自动）。

## 八、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 压过头，判断句被删光 | 读起来像 API 文档，只剩陈述 | 每章强制保留 3–6 处粗体断言（R7 的下限） |
| 因果链被压缩成结论 | 读者知道怎么做，不知道为什么要做 | 每节字数不低于原文 45%；人工复核问题 2 |
| 代码与输出错位 | 输出块与代码不再配对 | 占位符回填 + 哈希校验 |
| 术语被同义替换 | `tool_calls` 变成"工具调用列表" | 不可触碰清单里的知识点词表校验 |
| 风格改写后各章不一致 | 有的狠有的松 | 固定提示词 + lint 阈值统一判定 |
| 生成器把字数补回去 | 下次 `build` 或再生成时反弹 | 同一批改动里更新 `WRITING-SPEC.md` 与 `MIN_CHARS` |

## 十、P0 结果：第 1 章已改完

工具已落地（都在 `docs/` 下）：

| 脚本 | 作用 |
|---|---|
| `lint_prose.py` | 按第二节口径机检，输出每章违规清单；`--all` 出全书面貌 |
