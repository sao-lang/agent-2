# 写作提示词（通用）

适用于全书任意一章。把 `=== 提示词 开始 ===` 到 `=== 提示词 结束 ===` 之间的内容整体复制到新会话的第一条消息。

**不需要为每一卷单独写提示词。** 各卷的差异只有知识点与代码落点，这些已在大纲里按卷列出，提示词负责指过去。

你在 c:\Users\30895\Desktop\agent-2 这个仓库里写一本技术书的章节。本次任务：写**下一章**。

## 第一步：读文件（不要跳过，不要凭记忆）

按顺序读。**`OUTLINE.md` 有 70 KB，不要整个读进来**，用 grep 定位后按段落读。

1. `.github/copilot-instructions.md` —— 入口与交付流程（很短，全读）
2. `docs/PROGRESS.md` —— 确认当前是哪一章、属于哪一卷（很短，全读）
3. `docs/CONTRACT.md` —— 已落地的接口签名（很短，全读）
4. `docs/WRITING-SPEC.md` —— 重点第零节、第三节、第四节（约 9 KB，全读）
5. `docs/CHAPTER-TEMPLATE.md` —— 骨架与清单（约 3 KB，全读）
6. `OUTLINE.md` —— **只读这六处**，用 grep 定位：
   - 第四节：本章的知识点编号与内容
   - 第五节 `### 5.7`、`### 5.8`（含 5.8.1–5.8.7）、`### 5.9`、`### 5.10`（组件契约，卷 2 起适用）
   - 第六节：本章所在卷的章节表，以及该卷末尾的**代码落点**说明
   - 第六节末的「各卷的代码落点汇总」表
   - 第九节：五段结构
   - 第十节：写作规则

读完用三句话复述：要写第几章、覆盖哪些知识点编号、要装哪些组件（或本章属于哪类内容）。**我确认后再动笔。**

> 若 `docs/CONTRACT.md` 状态表写着「当前无已落地契约」，说明本章是首批落地契约的章节。此时以 `OUTLINE.md` 5.7/5.8 的设计为准，写完后回填 CONTRACT。

## 第二步：写代码

**代码位置按章所属的卷查 `OUTLINE.md` 第六节的「各卷的代码落点汇总」表，不要写死路径。**

| 卷 | 位置 |
|---|---|
| 1 | `code/chNN_名称/`，每章独立 |
| 2–5 | `code/harness/`，逐章增加文件 |
| 6 | `code/framework/<框架名>/`，不改 `code/harness/` |
| 7 | `code/finetune/`、`code/harness/` 的扩展 |

硬性要求：

1. **离线可跑。** 不需要 API Key、不需要网络。需要模型的章节用 `ScriptedResponder`（见 5.8.1）。卷 6 起若必须联网，需在正文标注环境要求并提供离线替代。
2. **不改已有签名。** 已有函数名、参数、返回类型、数据字段一律不动。新字段加在末尾并给默认值。
3. **`loop.py` 只调 `actor.step()`。** 不直接调 `Tool.invoke()`，工具访问只经 `_call_tool(name, args)`（见 5.8.2）。
4. **步号由 `loop.py` 独家维护**，`Actor` 只读（见 5.8.3）。
5. **每章建立或补充 `tests/`**，用 pytest，不联网（见 5.8.6）。
6. **跑通再写正文。** 所有脚本与测试必须实际执行，输出逐字核对后贴进正文。

## 第三步：写正文

文件名 `NN-<章标题>.md`，标题与 `OUTLINE.md` 第六节完全一致（见 5.8.7）。

必须满足：

| 项 | 要求 |
|---|---|
| 章首 | 四行，顺序固定：知识点 → 交付 → 组件 → 读完应当能回答 |
| 结构 | 五段功能（是什么 / 为什么 / 怎么做 / 不适用 / 弄坏它）+ 小结 + 下一章 |
| 小节名 | 带本章章节号，如 `## 6.2 xxx`；编号连续不重复 |
| 必需小节 | `边界`、`这一章建立的 N 件事`、`复现`、`下一章` 四项缺一不可 |
| 交付 | 章首声明的交付类型，正文必须真的给出 |
| 代码块 | 只在交付物本身是代码/配置时用；其余指向代码文件 |

写作风格，三条最容易违反：

1. **不写虚构场景。** 不写"想象你是一个…""某天老板找你…"。直接讲内容。
2. **不随便用数据举证。** 正文每个数字必须能由 `code/` 下脚本跑出，并注明脚本路径。跑不出来的删掉。示例数据属代码输入，需在正文标注"非实测"。
3. **标题写对象或结论。** 不用比喻、不加引号强调、不用 emoji、不写"你必须知道的三个坑"。

另外：

- 每个概念讲透四件事：是什么、为什么、怎么做、什么情况不适用。
- 判断啰嗦：删掉一句话，读者还能否理解？能，就是多余的。
- 不写"本章产出 / 验收标准 / 章首术语表"，已废止。
- 术语第一次出现时就地解释。

## 第四步：跑检查（必须全绿）

```

python tools/check_style.py         # 标题、禁用语、主观词、数据出处、交付核对

```

任何一项报错都算没写完。

## 第五步：更新交接文件

2. **更新 `docs/PROGRESS.md`**：已完成表格加一行，改写"下一章"，勾掉已完成待办。

## 遇到分歧时

| 冲突 | 以谁为准 |
|---|---|
| 规范与大纲冲突 | `docs/WRITING-SPEC.md` |

## 用法

每次只写一章。把提示词原样发过去，它自己从 `PROGRESS.md` 读到当前是第几章。

若想指定章节，在末尾加一句：`本次写第 13 章。`

## 为什么不为每卷单独写一份

| 做法 | 问题 |
|---|---|
| 每卷一份 | 规则部分 90% 重复，改一次规则要改七份；容易不同步 |
| 一份通用 | 规则只维护一处；各卷差异交给大纲 |

各卷真正不同的只有两件事：**知识点范围**与**代码落点**。前者在 `OUTLINE.md` 第四节，后者在第六节的汇总表。提示词只负责指过去，不复制内容。

## 为什么这样设计

| 设计 | 原因 |
|---|---|
| 先复述再动笔 | 防止按印象写，写错了才发现 |
| 明确 CONTRACT > OUTLINE | 前者是实际，后者是计划，不一致时不能按计划写 |
| 指出 OUTLINE 有 70 KB | 不说明的话，会话会卡在读整个文件 |
| 代码位置指向汇总表 | 卷 2–5 用 `harness/`，卷 6 用 `framework/`，写死任一个都会错 |
| 四个命令必须全绿 | 覆盖单测、结构、引用、风格四类问题 |
| 强制写 CONTRACT | 唯一防止章与章接不上的机制 |
| 末尾"找不到就问" | 实测过，会话倾向自行发明缺失信息 |
