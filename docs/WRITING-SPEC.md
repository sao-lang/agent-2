# 写作规范

本文件是 `OUTLINE.md` 第 10 节的展开版。冲突时以本文件为准。

## 零、两条总要求

这两条覆盖后面所有细则。任何一章如果违反其中一条，即使其余规则都满足，也不算完成。

### 0.1 详细全面，但不啰嗦

**详细全面**指一个概念必须交代清楚四件事，缺一不可：

| 必须交代 | 具体含义 | 只讲一半的样子 |
|---|---|---|
| 是什么 | 定义、结构、组成部分 | 只给一句定义，不给组成 |
| 为什么 | 因果，不成立的后果 | 只说"很重要" |
| 怎么做 | 可操作的步骤或完整产物 | 只列要点，不给成品 |
| 什么情况不适用 | 边界与反例 | 只讲成功路径 |

这四件事是**内容要求，不是排版顺序**。不同的概念适合不同的展开方式：有的先给结论再解释，有的从一个具体现象切入，有的先描述失败再引出机制。四件事可以在一个小节内交代完，也可以分散在多个小节。**不要为了对齐这四件事而把每章切成固定的几块**，那样会把内容压成模板，读者读三章就会开始跳读。

判断内容是否讲透的标准是**读者能不能自己复现**，不是章节里有没有对应的小标题。

**不啰嗦**指不重复、不铺陈、不凑字数。以下都算啰嗦：

| 啰嗦的形态 | 例子 | 应改成 |
|---|---|---|
| 同一结论换说法重复 | 正文说一遍，小结再说一遍，下一章开头再说一遍 | 只在首次出现处说，小结只列条目不复述理由 |
| 无信息量的过渡 | "接下来我们来看看…""需要注意的是…" | 直接进入内容 |
| 为对称硬凑结构 | 三个例子实际上只有两个有意义 | 只给有意义的 |
| 解释已经解释过的术语 | 同一术语在不同小节反复定义 | 首次出现定义，后续直接使用 |
| 罗列不使用的选项 | 列五种做法，实际只讲一种 | 只列会用到或需要对比的 |

**判定方法**：删掉一句话，读者是否还能理解？如果能，就是多余的。整章删完后若逻辑仍然通顺，删掉的部分就是啰嗦。

### 0.2 只在需要处给完整成品

**问题背景**：只写"要素有哪些""要注意什么"，读者读完仍然拿不到能用的东西。但反过来，给每一章都硬塞一个示例，就成了凑内容，与 0.1 的"不啰嗦"冲突。

**正确的做法是按章的交付类型决定**，不是一律要求。每章必须在章首声明交付类型，检查器按声明核对。

| 交付类型 | 什么时候用 | 必须给出什么 | 典型章节 |
|---|---|---|---|
| **标准范式** | 这一章的核心是"某个东西应该长什么样" | 一份完整、可直接照抄使用的成品，不是要素清单。成品载体可以是提示词全文、配置全文、代码骨架、表单模板之一 | 提示词工程、章节结构 |
| **可运行脚本** | 这一章的核心是"某个机制怎么运行" | 正文引用真实存在、跑得通的脚本，输出与正文一致 | 调用链路、循环、计量 |
| **操作序列** | 这一章的核心是"按什么顺序做什么判断" | ≥3 条带判定条件的编号步骤 | 排查流程、选型判据 |
| **无** | 这一章是地图、索引或纯概念铺垫 | 不要求 | 目录章、术语章 |

**关键区别**：

- 第 4 章讲"提示词应该怎么写"，核心交付就是**一份标准提示词**。只列六要素、不给成品，这一章等于没写。
- 第 2 章讲"生成机制"，核心交付是**可运行的演示**。硬塞一份"标准提示词"反而是跑题。
- 第 1 章讲"调用链路"，核心交付是**可运行的记录器**。

**判断方法**：问这一章读完，读者手上应该多出什么，而不是问这一章该不该有代码。

**反例**：

- 为了通过检查，在纯概念章里塞一段与主题无关的代码 → 违反 0.1
- 在讲"该怎么做"的章里只给要素表 → 违反本节

**检查方式**：`tools/check_style.py` 读取章首的 `> **交付**：<类型>`，按类型核对。未声明、或声明了但没交付，均判不合格。

## 一、内容

### 1.1 不写多余场景

直接进入内容。不编造人物、对白、"某天你遇到"这类叙事。

| 禁止 | 应写成 |
|---|---|
| 想象你是一个电商工程师，某天老板找到你 | 在售后系统中，退款接口需要人工确认 |
| 你可能遇到过这种情况：明明代码没错，结果就是不对 | 请求成功、状态码 200，但返回的 `content` 不完整 |
| 这时候你一定会问：为什么？ | 原因有两层 |

### 1.2 不随便用数据举证

| 情况 | 做法 |
|---|---|
| 数字可由 `code/` 下的脚本跑出 | 引用，并在正文注明脚本路径 |
| 数字是估算或假设 | 不使用。改为说明判断依据，或删除 |
| 数量是结构事实（四类失控、六个环节） | 可使用，读者能自行数出 |

**禁止出现的写法**：

- "实测提升了 23.5%"
- "大约有 80% 的情况会…"
- "性能提升 3 倍"

如果确实要展示差异，必须给出可运行的脚本，并注明"运行 `xxx.py` 得到"。

**可接受的来源标注形式**：

| 形式 | 示例 |
|---|---|
| 小节开头注明脚本 | `运行 code/ch03_tokens/step1_estimate.py。`（该小节内后续数字视为有出处） |
| 数字所在行直接注明 | 表格上方一行：`以上比例由脚本在 2000 次采样下统计` |
| 行内引用 | `见 step1 的偏差列` |

检查脚本按"该行或上方 25 行内出现 `.py` 且提到运行/脚本"判定为有出处。不满足此条件的一律报错。

### 1.3 客观陈述

用事实和因果说明。不用评价性形容词。

| 禁止 | 应写成 |
|---|---|
| 这个设计非常糟糕 | 这个设计使 X 无法单独测试 |
| 这是最重要的一点 | 这一点决定了后续三种情况能否被区分 |
| 显然，应该… | 从 1.2 的数据可见… |

### 1.4 不带情绪

禁止感叹号、反问句、夸张、拟人。

| 禁止 | 应写成 |
|---|---|
| 结果会让你大吃一惊！ | 该实现返回空字符串 |
| 难道不应该先检查吗？ | 检查顺序如下 |
| 模型"想"要调工具 | 模型的输出中 `finish_reason` 为 `tool_calls` |

### 1.5 文义清晰

- 一句话只表达一件事。超过 40 字考虑拆分。
- 术语第一次出现时就地解释，不集中列表。
- 指代明确：不出现"它""这个"而没有明确先行词。

## 二、标题

### 2.1 三条要求

| 要求 | 说明 |
|---|---|
| 概括内容 | 读者只看标题就知道这一段讲什么 |
| 简单精炼 | 尽量短，不用完整的句子 |
| 不加修饰 | 无比喻、无引号强调、无 emoji、无形容词 |

### 2.2 写法

| 不推荐 | 推荐 |
|---|---|
| 补充说明 / 其他 / 小结 | 调用记录应包含的字段 |
| 上下文：那个看不见的隐形杀手 | 上下文窗口的容量限制 |
| 为什么现有手段不够 | （删除，改为正面陈述） |
| 你必须知道的三个坑 | 三种失败的差别 |
| chunk_size 的确定 | 切太碎会导致结果重复 |

**例外**：`下一章` 这类功能性小标题允许简短。

## 三、章节结构

结构由内容决定。本章讲什么，就按最容易讲清的顺序展开，不套固定段落。

章首四行元信息固定，顺序不变——它是给读者和后续会话看的元数据，不属于正文：

```markdown
> **知识点**：A1 调用链路，A2 `finish_reason`
> **交付**：可运行脚本
> **组件**：无（本章不涉及组件）
> **读完应当能回答**：一次调用会在哪些环节失败，每种失败在代码里表现为什么。
```

### 正文的编排

| 约束 | 说明 |
|---|---|
| 不预设段数 | 可以是 3 个小节，也可以是 12 个。按内容需要分 |
| 不预设段名 | 小节名写这一节讲的对象或结论，不写"为什么""怎么做"这类功能名 |
| 不预设顺序 | 先讲现象还是先讲机制，由哪种更容易讲清决定 |
| 不要求覆盖固定四段 | 0.1 的四件事是内容要求，用来说明是否讲透，不是排版模板 |
| 段落推进要有理由 | 每次切换话题，读者应能明白为什么要讲这个了。做不到就说明顺序该调 |

**反面例子**：每章都先定义、再讲动机、再给步骤、再列边界、再演示失败。这样写出来的五章，读者读完第一章就摸清了套路，后面四章会开始跳读。内容之间的真实关系被结构掩盖了。

**正面做法**：如果这一章的核心是一次失败，就从失败讲起，讲完再回头交代机制；如果这一章的核心是一个组件，就从它的输入输出讲起，边界放在讲到边界处，不必集中到最后。

### 必须保留的收尾

| 小节 | 作用 |
|---|---|
| `这一章建立的 N 件事` | 小结。列条目，不复述理由 |
| `下一章` | 与后文的衔接，说明下一章解决本章留下的什么问题 |

这两个小节的位置固定在正文之后。原因不是排版习惯：`这一章建立的` 是读者自查清单，`下一章` 是保持全书连续性的接口，后续会话靠它判断进度。

### 小节编号

| 约束 | 说明 |
|---|---|
| 小节名带章节号 | `## 3.2 成本结构`。这是为了让正文可以互相引用，也方便后续章节指回来 |
| 功能性小节可不带号 | `这一章建立的`、`下一章` |

编号连续与否不做强制检查：正文内容可能合并、拆分，只要引用能对上即可。

### 代码块的显示规则

正文中的代码块只用于两种情况：

1. 本章声明的交付物本身就是代码或配置（如 `标准范式`）
2. 需要展示一小段无法用文字替代的片段

其余实现放在 `code/` 下，正文用「运行 `code/chXX_xxx/stepN.py`」引用。**引用必须指向真实存在的文件。**

## 四、代码

| 规则 | 说明 |
|---|---|
| 离线可跑 | 不需要 API Key、不需要网络 |
| 目录（卷 1） | `code/chXX_名称/stepN_*.py`，每章独立 |
| 目录（卷 2 起） | `code/harness/`，一个可 import 的包，见 `OUTLINE.md` 5.9 |
| 可复现 | 固定随机种子；不依赖当前时间 |
| 估算须标注 | 代码注释与正文同时注明"非真实值" |
| 只往上加 | 卷 2 起，不改变已有函数签名与字段 |
| 契约同步 | 写完把实际签名写入 `docs/CONTRACT.md` |

**章节与目录的对应**：

- 第 1–4 章：`code/ch01_call_lifecycle/` … `code/ch04_prompt/`
- 第 5 章起：代码进入 `code/harness/`，章节内不再新建 `chXX_*` 目录

第 5 章起，正文引用代码写作 `code/harness/actor.py`，不再用 `code/ch05_*/stepN.py` 的形式。

## 五、术语

首次出现时用一句话解释，就近放置。例：

> `finish_reason` 是服务端返回的停止原因字段，决定 `content` 能否使用。

不在章首集中列术语表。

## 六、引用

| 类型 | 写法 |
|---|---|
| 引用其他章 | `第 3 章`（用中文数字前的阿拉伯数字，与文件名一致） |
| 引用代码 | `code/ch01_call_lifecycle/step1_call_lifecycle.py` |
| 引用小节 | `1.2`（本章内）或 `第 3 章 3.2`（跨章） |

所有引用必须指向真实存在的文件与小节。
