# 写作规范（WRITING-SPEC）

> **本文件与大纲的分工**：`OUTLINE.md`（索引）与 `outline/` 分册只负责**结构与内容边界**（知识点、章节划分、卷归属、代码落点、设计决定）。本文件负责**怎么写**（骨架、篇幅、示例、标题、内容规则、工程约束、协作流程、检查脚本）。
>
> 两者不得矛盾。修改本文件中任何会改变结构的内容时，必须同步更新 `outline/` 分册。

## 一、主线章节的固定骨架（"从缺什么讲起"）

主线每章必须按**因果链**展开，不按"定义—动机—步骤—边界"的并列结构展开：

```
① 缺什么   这一步要是不做，系统会在哪里坏？先给出坏的样子
② 成因     为什么会坏到那个程度？模型 / 网络 / 窗口 / 进程的哪个事实导致的
③ 怎么补   这个设计怎么补上那个事实；内部怎么工作
④ 做法对比 有多种做法时，逐一实现并给输出（这是硬要求，见 1.1）
⑤ 会怎么坏 这个设计自己的失效模式与信号
⑥ 边界     什么情况下不该用它 / 用它的代价上界
```

**这不是模板，是因果顺序。** 可以不分成六个小节，但六件事都要交代；顺序不能颠倒——先讲做法再讲为什么有这种做法，读者只会记住做法，换个场景就不会用。

**反例**：从字段名开始。"`tool_calls` 是一个数组，每个元素有 `id`、`type`、`function`……"。读者不知道它为什么存在，读完只能照抄。

**正例**：从缺什么开始。"模型最擅长的事是生成下一个 token。它没有手，碰不到文件、查不了库。所以它能做的只有一件事：在回复里**描述**它想做什么。`tool_calls` 就是这段描述的格式。"

### 1.1 代码示例的硬要求

**凡是讲做法的地方，正文必须出现三类内容：① 代码本身 ② 这段代码要说明什么 ③ 运行输出。**

三者缺一，读者就拿不到可以复现的东西。**只贴输出不贴代码，等于让读者相信一个没有依据的结论。**

| 要求 | 判定（逐节自查） | 反例 |
|---|---|---|
| **正文必须有代码** | 这一节是否只贴了缩进的运行输出，而没有可复制的代码？ | 只贴 `temperature=0.5 → 分布 A:0.83 ...` 而不给计算代码 |
| **代码必须完整** | 每段代码能不能单独 `compile()` 通过？有没有裸的 `return`、裸的循环体、`...` 省略？ | `for _ in range(20): return x`（`return` 悬空） |
| **代码必须被解释** | 代码前面说它要做什么，后面说哪一行是关键的、为什么 | 代码贴完直接进入下一段，不说关键行 |
| **必须贴真实输出** | 输出是跑出来的还是编的？贴之前有没有运行过？ | 手写一段"预期输出" |
| **有多种做法时逐一实现** | 每种做法是否都有自己的代码块和输出？ | 只给一种，其余一句"也可以用 X"带过 |
| **失败案例要贴失败输出** | 讲失效的那一节，是否贴了真实的报错或错误结果？ | 只描述"可能失败"，不贴失败的样子 |
| **模拟要标注** | 假后端、演示常数是否标明了"原理演示，不是实测"？ | 把演示数字当成实测结果 |

#### 代码块的最低形态

代码块必须是**可以整体复制走、直接运行**的最小单元。判断标准：

```python
# 合格：有函数签名、有返回值、能编译
def estimate_chars_div2(text: str) -> int:
    return len(text) // 2
```

```python
# 不合格：裸语句、return 悬空、依赖外部未定义的变量
for _ in range(20):
    reply = call_model(messages)
    if reply.is_final:
        return reply.content      # return outside function
```

```python
# 不合格：省略号函数体
def run():
    ...
```

#### 一个做法一个代码块

讲"N 种做法"时，读者要能把它们摆在一起比较。所以：

| 做法 | 必须有 | 不要求 |
|---|---|---|
| 每种做法 | 完整可运行的函数 + 真实输出 | 一套完整的工程实现 |
| 对比表 | 各做法在同一输入上的结果 | 各做法的性能基准 |

```python
def plain_extract(text: str) -> tuple[dict | None, str | None]:
    """纯文本 + 正则抽取。"""
    m = re.search(r"\{.*?\}", text, re.S)
    if not m:
        return None, "没有找到 JSON 片段"
    try:
        return json.loads(m.group(0)), None
    except json.JSONDecodeError as e:
        return None, f"JSON 解析失败：{e}"
```

代码后面必须紧跟它的输出，以及一句"这段说明了什么"：

```
JSON 解析失败：Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
```

这句话对应的是：模型返回了中文引号，正则抽得出来，但 `json.loads` 不认。**没有这一句，读者只知道失败了，不知道为什么。**

#### 提示词也是代码

提示词是这一行里最容易被写成"一段引用"的东西。它必须以代码块出现（标注 `text`），并满足：

| 要求 | 说明 |
|---|---|
| 段落分隔 | 用 `# 角色`、`# 任务` 这样的标题分段，让每一段的作用没有歧义 |
| 数据包住 | 输入数据用 `<<< >>>` 或 XML 标签包住，与指令分开 |
| 格式明确 | 写明"只输出 JSON，不要 markdown 包裹"这类可执行要求 |
| 约束可判 | 约束写成"信息不足时填 null"，而不是"尽量准确" |

```text
# 角色
你是电商客服，只处理退货相关问题。

# 任务
判断这笔订单是否符合退货条件，给出结论。

# 输入数据
<<<
订单号：A1001
签收时间：3 天前
商品状态：未拆封
>>>

# 输出格式
只输出一个 JSON 对象，不要任何其他文字：
{"eligible": true | false | null, "reason": "不超过 40 字"}
不要用 markdown 代码块包裹。

# 质量与约束
- 只依据上面的政策判断，不引用外部知识
- 信息不足时 eligible 为 null，并在 reason 里说明缺什么
```

#### 示例的技术栈

**判据：这一章的主题是不是某个库。** 是，就必须用那个库；不是，才允许手写。

| 章的类型 | 例子 | 允许的实现 |
|---|---|---|
| 原理类（主题是语义） | 循环的终止条件、状态机、SSE 帧格式 | 标准库手写；可加一句"框架里对应什么" |
| 库即主题 | 切块、嵌入、向量检索、MCP、RAG 评测、可观测 | **真实库**，不允许手写近似 |

三条硬规定：

1. **手写版与真实库版成对出现。** 手写版用来讲"这一步在做什么"，真实库版用来讲"工程里怎么做"。只有手写版，读者学不会落地；只有真实库版，读者看不懂原理。
2. **不许用代用品冒充实测。** 字符 n-gram 不是嵌入，字面重合不是 RAGAS 指标，正则不是 tokenizer。用代用品时必须在正文标注"代用品 + 换成真实库时方法不变"，并把它降级为对照，不能占据章节主位。
3. **一个示例最多尝试 3 次。** 仍跑不通时，加一段"环境限制"说明（缺什么、怎么装、替代方案），不得手写一段"预期输出"充数。

首次运行需要联网装依赖或下载模型时，在章首的示例目录后面注明（如"首次运行需下载 bge-small-zh，约 95MB"）。

#### 代码放在哪

| 位置 | 内容 |
|---|---|| 正文代码块 | 讲这一节要用的核心函数，可以只取相关部分，但必须能独立编译 |
| `code/knowledge/chNN_XXX/` | 完整可运行脚本，与本节的代码块一致 |
| 正文输出块 | 脚本的真实运行结果，逐字粘贴 |

**正文代码块与仓库脚本必须是同一份代码。** 允许正文只摘录相关函数，不允许写成另一套。

### 1.2 副线章节的固定骨架（卷 7）

```
① 这个设计的主线出处，以及当时为什么没做成部件
② 把它做成部件要冻结哪些契约
③ 实现（代码）
④ 替换实验：换掉它，证明只有一件事消失
⑤ 如果做错了会怎样（耦合的三种典型形态）
```

副线可以出现类名、模块名、契约定义，因为那是本章的主题。

### 1.3 框架卷章节的固定骨架（卷 6）

```
① 这个 API 的签名与参数表（逐个参数说明管什么）
② 最小可跑例子 + 真实输出
③ 它替代的是主线哪一章的做法（对照表里的一行）
④ 它的边界：做不到什么，什么时候不该用它
```

卷 6 与主线的关系是**对照**，不是"更好的做法"。所以每章至少要有一处明确的对照：

| 对照项 | 写法 |
|---|---|
| 替掉了哪段 | "这一段对应第 6 章的 30 行循环，框架里是一个 `create_agent` 调用" |
| 没替掉哪段 | "护栏仍然要自己写，框架只提供钩子" |
| 代价 | "参数从 30 行变成 12 个，可读性下降；版本升级会改这些参数" |

**卷 6 的正文可以出现 API 名、参数名、类名**，但每出现一个，都要能回答"主线第几章做过同一件事"。答不上来的 API 不写。

接入类章节（可观测、评测集、RAGAS、Agent 评测）多一条要求：**必须给出"用了它之后，哪三件事变得可做了"**，否则它只是一段安装说明。

### 1.4 固定的三处

| 位置 | 内容 | 作用 |
|---|---|---|
| 章首 | 引用块：卷行 + 四项列表（知识点 → 本章回答什么问题 → 示例在哪 → 读完应当能回答；可选：本章不负责） | 元数据，检查器据此核对 |
| 正文之后 | `这一章建立的 N 件事` | 读者自查清单 |
| 正文之后 | `下一章` + 一行机器导航 | 连续性接口 |

#### 章首与章末的生成方式

**这三处不由人写，由 `book.json` 生成。** 改完 `book.json` 跑：

```bash
python docs/gen_book.py build   # 重建 INDEX.md 与各章章首/章末
python docs/check_nav.py        # 校验是否一致
```

| 行 | 形态 | 为什么 |
|---|---|---|
| 卷 | `> **卷 5 · agent 进阶（第 22–26 章）**｜[全书目录](./INDEX.md#vol5)｜[本卷导读](./outline/vol05-agent进阶.md)` | 读者手里只有一章时，唯一能知道"这属于哪一卷、上下还有几章"的地方 |
| 知识点 | `> - **知识点**：B6 编排的三层 —— 分派、主体、校验各管一段，选型就是分别回答这三问（编号定义见 [知识点-B-运行层](./outline/12-知识点-B-运行层.md)）` | 编号是内部代号，读者不认识；**中文名 + 一句人话 + 可点的定义**三样缺一不可 |
| 章末导航 | `[← 第 21 章 · 知识治理](./…)　｜　[卷 5 目录](./INDEX.md#vol5)　｜　[第 23 章 · 反思… →](./…)` | `## 下一章` 是内容（讲下一章要解决什么），导航才是入口；两者不能互相替代 |

章首的完整形态：

```markdown
> **卷 5 · agent 进阶（第 22–26 章）**｜[全书目录](./INDEX.md#vol5)｜[本卷导读](./outline/vol05-agent进阶.md)
>
> - **知识点**：…
> - **本章回答**：…
> - **示例目录**：`code/knowledge/ch22_orchestration/`
> - **读完应当能回答**：…
```

四项必须写成引用块里的 `> - ` 列表项。连续写 `> **知识点**：…` 这类多行时，CommonMark 会把它们当作**同一段**，预览时软换行合并成一行；列表项之间才是真正的块级分隔。

下一章若尚未写出，导航指向该章的节级计划并标注"待写"，不给死链：

```markdown
第 33 章 · 拆分与协作：四种拓扑（卷 7，待写）→ [章节计划](./outline/40-编排架构章节计划.md)
```

**文件名规则**：文件名 = 章号 + 标题，空格与引号去掉，`：，、` 统一换成 `-`（例：`22-编排的三层-分派-主体-校验.md`）。标题改了，文件名必须一起改，`docs/check_nav.py` 会报出来。

### 1.5 一处必须自查的跑偏

**主线正文的主题是"为什么必须有这一步"，不是本章要写的代码，更不是 harness。**

判定方法一：把正文里所有类名、模块名、私有方法名删掉，再读一遍。读不懂说明讲的是实现。

判定方法二：搜索正文里的 "Harness"、"组件"、"插点"、"契约"、"loop 的第 N 个位置"。**在卷 1–5、7 出现即为跑偏。**

## 二、篇幅要求

**每章正文目标 10000 字符以上**（中文字符计，不含代码与表格）。这是篇幅的下限目标，不是配额。

| 情况 | 处理 |
|---|---|
| 内容需要更多篇幅 | 照写，不设上限 |
| 写满 10000 字符但仍有未讲透的点 | 说明本章知识点拆分有误，应回到 `outline/` 的知识点分册与卷章表调整章节归属，而不是继续堆文字 |
| 内容确实撑不到 10000 字符 | **不补。** 宁可短，也不许出现任何一种凑字数写法 |

**判定"是否真的不够"**：按第一节的六件事逐项自查。六件事都交代清楚了、每种做法都有一个可运行例子、例子输出都贴了，仍然不到 10000 字符——那就是这个知识点本身只有这么大，写短是对的。

**凑字数的典型形态（出现即返工）**：

| 形态 | 判定 |
|---|---|
| 复述 | 同一个结论在章首、章中、章末各说一遍，措辞略改 |
| 扩充背景 | 讲工具调用先花两千字讲大模型发展史 |
| 泛化举例 | 列举多个行业的同类场景，失效原因完全相同 |
| 场景叙事 | 编造人物、对话、时间点，用"会发生什么"代替"为什么必然发生" |
| 无源数字 | 用"提升 30%""快了 5 倍""几百行"填充段落 |
| 同义小节 | 把一段拆成"概述—详解—小结"三节，内容重复 |
| 代码注水 | 把 20 行能运行的例子拆成 200 行，加大量空行与注释 |

**篇幅的唯一合法来源**：把一个设计讲到读者能自己复现——它的历史成因、它替代了什么、它在什么情况下失效、它的实现细节为什么会是那个样子。

## 三、内容规则

**每条规则的"判定"列是写作完成后逐段过一遍的问题，"反例"只是形态示意，不是合规边界。** 撞不上反例不等于合规。

| 规则 | 判定（逐段自查） | 反例（仅示意形态） |
|---|---|---|
| **不写场景叙事** | 这一段里有没有一个具体的人、一次具体的对话、一个具体的时间点或时长？有就改成陈述 | "想象你是一个电商公司的工程师，某天老板找到你…"；"一个任务跑了二十分钟，对方关掉了浏览器" |
| **不用人的动作描述系统** | 这一段里有没有把系统说成有身体、眼睛、手、记忆、情绪？有就换成它在代码里对应的那个东西 | "系统扛住并发""模型看见结果""上下文记住了""你答不上来" |
| **不平均用力** | 并列的几条里，有没有一条明显更长、一条明显更短？全部等长等结构说明没有判断参与 | 六个条目，每条都是"两字标题 + 场景 + 反转 + 加粗金句" |
| **用论断不用画面** | 每一处结论后面有没有依据？只有画面没有依据的，补上"为什么必然如此" | "有人问提高多少，你答不上来" → 应写"单次对比无法区分改动有效与随机波动" |
| **不随便用数据举证** | 这个数字是哪跑出来的？说不出来源就删 | "实测准确率提升了 23.5%"；"大概是几百行" |
| **客观陈述** | 这一段有没有对设计的评价词？有就改成"它会导致 X" | "这个设计非常糟糕" |
| **文义清晰** | 有没有一句话塞了三件事？术语首次出现有没有就地解释？ | 长句嵌套三个从句 |
| **做法必须对比** | 有多种做法时，每种是否都实现并贴了输出？ | 只讲一种，其余一句话提及 |
| **抽象词不许当骨架** | 有没有一个抽象名词承担"读者靠它理解全书安排"的作用？有就换成具体因果 | 用"机制""本质""核心"统称所有设计 |
| **同一抽象词不许反复出现** | 同一抽象名词在本章出现超过 3 次？每次是否都带了定语？ | "这个机制""每个机制""从机制讲起" |
| **术语只用于具体物** | 这个术语能不能指出一个具体的东西？ | "续写机制"（指 token 逐字生成）合格；"这个机制"不合格 |
| **不许凑字数** | 这一段删掉后，读者会失去什么？说不出就删 | 同一结论换措辞说三遍 |

## 四、标题怎么取

**标题是给这一节的内容起名字，不是给这一节写摘要，也不是给它编代号。**

这一节讲怎么取名字。不是规则清单，是三个步骤加一组判据。

### 4.1 第一步：说出这一节在讲哪个东西

不要先想标题，先填空：

```
这一节讲的是 ______。
```

填出来的必须是一个**名词**——一个人、一样东西、一种情况、一个概念。如果填出来的是一件事或一个判断，说明这一节是在论证，标题应当写它论证的对象。

| 填出来的 | 判断 | 标题 |
|---|---|---|
| "请求里有哪些字段、响应里有哪些字段" | 是问题，不是东西 | 请求与响应的字段 |
| "只取 content 会出什么错" | 是判断，不是东西 | 只取 content 的写法 |
| "温度如何改变分布" | 是过程，不是东西 | 温度的作用点 |
| "四种取值分别怎么处理" | 是问题 | 四种取值的处理 |

### 4.2 第二步：检查这个名词在正文里出现了吗

**标题里的词，必须在正文里能找到对应的名词。** 找不到就说明是自造的分类名。

| 标题 | 正文里有这个词吗 | 结论 |
|---|---|---|
| 字段归属 | 没有 | 自造，改为"请求与响应的字段" |
| 产物类型分组 | 没有 | 自造，改为"产物类型" |
| 退出条件 | 有："循环的退出条件必须由调用方定义" | 合格 |
| 截断误判 | 有："`length` 就会走进成功路径" | 接近，可改为"截断被当成完整" |

这一条能挡掉大部分不知所云的标题，因为自造词在正文里必然对不上。

### 4.3 第三步：套用五种形态之一

名字可以长短不同，但都落在下面五种里。超出这五种，多半写成了摘要或口号。

| 这一节在做什么 | 标题形态 | 例子 |
|---|---|---|
| 定义或介绍一个概念 | 概念名，2–6 字 | 上下文窗口、指令自相矛盾 |
| 讲一种会出问题的情况 | 情况名，短陈述 | 参考资料太多、多步骤复杂流程 |
| 说明某个东西的某个属性 | 对象 + 限定 | 取值的来历、请求与响应的字段 |
| 列举几项并列的东西 | 顿号连接 | Zero-shot 与 Few-shot |
| 回答一个读者确实会问的问题 | 疑问式（仅当这一节就是回答它） | 为什么需要提示词 |

**最后一种要慎用。** 只有当这一节整节都在回答那个问题时才用；如果只是顺带提一句，改成陈述。

### 4.4 判据

写完标题后逐条过：

| 判据 | 通不过的表现 | 怎么改 |
|---|---|---|
| 是名词或名词短语吗 | 能单独作为一句话读 | 去掉谓语，留下对象 |
| 正文里有对应的名词吗 | 找不到 | 换成正文里实际使用的说法 |
| 只看标题能说出讲哪个东西吗 | 说不出来 | 补上缺的限定 |
| 不超过 12 字吗 | 超了 | 先看是不是讲了两个东西，是就拆节 |
| 有没有比喻、形容词、引号强调、emoji | 有 | 删 |
| 有没有"最""唯一""真正""关键"这类评价 | 有 | 删，写成对象 |
| 有没有把系统说成会看、会扛、会记 | 有 | 换成它对应的代码概念 |
| 本章标题是否句式一致到像模板 | 全部同一种 | 按每节的性质分别选形态 |

**最后一条最容易被忽略。** 一章里所有标题都写成"X 的 Y"或都写成"A 不是 B"，就说明没有按内容选，而是套了模板。人写的目录不会这么齐。

### 4.5 完整示例

拿第一卷的章节做示范，每一行的右边是推出来的标题：

| 这一节讲的是 | 正文里对应的说法 | 标题 |
|---|---|---|
| 请求和响应里各有哪些字段、由谁产生 | "请求里只有四类东西，全部由调用方决定" | 请求与响应的字段 |
| `finish_reason` 有哪几个取值 | "四个常见取值，对应四种不同的中止原因" | `finish_reason` 的四个取值 |
| `length` 之后怎么补 | "内容不完整，但可以补。补的方式有三种" | `length` 的三种补法 |
| 过滤为什么有两种 | "实际有两种来源，处理方式相反" | 过滤的两个来源 |
| 参数为什么是字符串 | "这是接口设计的结果，不是实现缺陷" | 参数的字符串形式 |
| 单次生成和整轮任务的区别 | "`finish_reason` 是单次生成的记录" | 单次生成与整轮任务 |

反过来，下面这些是同一批内容如果按摘要写会变成什么，以及为什么不合格：

| 摘要式标题 | 不合格原因 |
|---|---|
| 请求和响应里各有哪些字段、由谁产生 | 18 字，是句子 |
| 为什么过滤有两种来源 | 疑问式，但这一节不是回答"为什么" |
| 参数是字符串的三个理由 | 含数量词，正文没按"三个理由"组织 |
| 单次生成不等于整轮任务 | 是判断，标题该写对象 |
| 字段归属 | 自造词，正文没有 |

### 4.6 检查方法

标题的问题在正文里看不出来。写完一章后，把全章标题单独列成一张清单，附字数和形态，只看清单：

```
  7 字  ## 一、只取 content 的写法        [对象+限定]
  6 字  ### 2.1 四个取值                  [列举]
 11 字  ### 2.2 stop 的含义               [对象+限定]
 22 字  ### 3.7 同一输入两次结果不同       <- 句子，超长
 13 字  ### 7.3 过滤被误判为长度           <- 正文无"误判"一词
```

**句子、超长、自造词这三种问题在这个视图里一眼可见，混在正文里几乎发现不了。**

## 五、工程规则

| 规则 | 手段 |
|---|---|
| **三段代码分离** | `code/knowledge/`（主线）、`code/framework/`（卷 6）、`code/harness/`（卷 7）三者互不 import |
| **副线代码只往上加** | 卷 7 内一条连续骨架，每章新增部件，不改已有签名 |
| **框架示例要能对照** | 每个框架示例都要能指回它替代的主线章节；指不回去的不写 |
| **每个部件必带单测** | 无模型、无网络的离线测试；测不了说明耦合了 |
| **每个示例必须能跑** | `code/knowledge/chNN_*` 下每个入口文件单独运行即通过；卷 6 示例要求 `python code/framework/<名>/xxx.py` 可跑 |
| 引用永远有效 | `第 N 章` / `code/` 路径 / 相对链接由 `docs/check_nav.py` 校验 |
| **知识点可追溯** | 章首标注 A1–H10 中的哪几条，且带中文名与一句解释（由 `book.json` 生成） |
| **示例可追溯** | 每章开头标注示例目录 |
