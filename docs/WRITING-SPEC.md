# 写作规范

本文件是 `OUTLINE.md` 第 10 节的展开版。冲突时以本文件为准。

## 一、内容

### 1.1 不写多余场景

直接进入内容。不编造人物、对白、"某天你遇到"这类叙事。

| 禁止 | 应写成 |
|---|---|
| 想象你是一个电商工程师，某天老板找到你 | 在售后系统中，退款接口需要人工确认 |
| 你可能遇到过这种情况：明明代码没错，结果就是不对 | 请求成功、状态码 200，但返回的 `content` 不完整 |
| 这时候你一定会问：为什么？ | 原因有两层 |

### 1.2 不随便用数据举证

| 情况 | 做法 |
|---|---|
| 数字可由 `code/` 下的脚本跑出 | 引用，并在正文注明脚本路径 |
| 数字是估算或假设 | 不使用。改为说明判断依据，或删除 |
| 数量是结构事实（四类失控、六个环节） | 可使用，读者能自行数出 |

**禁止出现的写法**：

- "实测提升了 23.5%"
- "大约有 80% 的情况会…"
- "性能提升 3 倍"

如果确实要展示差异，必须给出可运行的脚本，并注明"运行 `xxx.py` 得到"。

**可接受的来源标注形式**：

| 形式 | 示例 |
|---|---|
| 小节开头注明脚本 | `运行 code/ch03_tokens/step1_estimate.py。`（该小节内后续数字视为有出处） |
| 数字所在行直接注明 | 表格上方一行：`以上比例由脚本在 2000 次采样下统计` |
| 行内引用 | `见 step1 的偏差列` |

检查脚本按"该行或上方 25 行内出现 `.py` 且提到运行/脚本"判定为有出处。不满足此条件的一律报错。

### 1.3 客观陈述

用事实和因果说明。不用评价性形容词。

| 禁止 | 应写成 |
|---|---|
| 这个设计非常糟糕 | 这个设计使 X 无法单独测试 |
| 这是最重要的一点 | 这一点决定了后续三种情况能否被区分 |
| 显然，应该… | 从 1.2 的数据可见… |

### 1.4 不带情绪

禁止感叹号、反问句、夸张、拟人。

| 禁止 | 应写成 |
|---|---|
| 结果会让你大吃一惊！ | 该实现返回空字符串 |
| 难道不应该先检查吗？ | 检查顺序如下 |
| 模型"想"要调工具 | 模型的输出中 `finish_reason` 为 `tool_calls` |

### 1.5 文义清晰

- 一句话只表达一件事。超过 40 字考虑拆分。
- 术语第一次出现时就地解释，不集中列表。
- 指代明确：不出现"它""这个"而没有明确先行词。

## 二、标题

### 2.1 三条要求

| 要求 | 说明 |
|---|---|
| 概括内容 | 读者只看标题就知道这一段讲什么 |
| 简单精炼 | 尽量短，不用完整的句子 |
| 不加修饰 | 无比喻、无引号强调、无 emoji、无形容词 |

### 2.2 写法

| 不推荐 | 推荐 |
|---|---|
| 补充说明 / 其他 / 小结 | 调用记录应包含的字段 |
| 上下文：那个看不见的隐形杀手 | 上下文窗口的容量限制 |
| 为什么现有手段不够 | （删除，改为正面陈述） |
| 你必须知道的三个坑 | 三种失败的差别 |
| chunk_size 的确定 | 切太碎会导致结果重复 |

**例外**：`边界`、`复现`、`下一章` 这类功能性小标题允许简短。

## 三、章节结构

固定五段，顺序不变：

```
1. 缺了它会怎样 —— 缺少该机制时的具体失效形式
2. 机制       —— 失效的原因
3. 实现       —— 代码，在前一章基础上增量添加
4. 边界       —— 适用条件与不适用情形
5. 复现       —— 构造并观察一次失效
```

章首元信息固定三行：

```markdown
> **知识点**：A1 调用链路，A2 `finish_reason`
> **组件**：无（本章不涉及组件）
> **读完应当能回答**：一次调用会在哪些环节失败，每种失败在代码里表现为什么。
```

## 四、代码

| 规则 | 说明 |
|---|---|
| 离线可跑 | 不需要 API Key、不需要网络 |
| 目录 | `code/chXX_名称/stepN_*.py` |
| 可复现 | 固定随机种子；不依赖当前时间 |
| 估算须标注 | 代码注释与正文同时注明"非真实值" |
| 只往上加 | 卷 2 起，每章在上一章代码基础上增量添加 |

## 五、术语

首次出现时用一句话解释，就近放置。例：

> `finish_reason` 是服务端返回的停止原因字段，决定 `content` 能否使用。

不在章首集中列术语表。

## 六、引用

| 类型 | 写法 |
|---|---|
| 引用其他章 | `第 3 章`（用中文数字前的阿拉伯数字，与文件名一致） |
| 引用代码 | `code/ch01_call_lifecycle/step1_call_lifecycle.py` |
| 引用小节 | `1.2`（本章内）或 `第 3 章 3.2`（跨章） |

所有引用必须指向真实存在的文件与小节。
