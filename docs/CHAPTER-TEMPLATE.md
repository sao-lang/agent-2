# 章节模板

本文件只规定**不可省的部分**：章首四行元信息、两个收尾小节。正文如何分节由内容决定，没有骨架可抄。

---

## 固定部分

### 章首四行

```markdown
# 第 [N] 章 [标题]

> **知识点**：[编号与名称]
> **交付**：[标准范式 | 可运行脚本 | 操作序列 | 无]
> **组件**：[组件名，或"无"]
> **读完应当能回答**：[一个具体问题]
```

顺序固定，不可增删。这四行是元数据：`知识点` 让后续会话知道覆盖范围，`交付` 被检查器核对，`组件` 用于追踪全书组件落地进度，`读完应当能回答` 约束本章的写作目标。

### 收尾两节

```markdown
## 这一章建立的 N 件事

1. [结论一]
2. [结论二]

## 下一章

[一句话衔接下一章要解决的问题。]
```

`这一章建立的` 是读者自查清单，列条目不复述理由。`下一章` 是全书连续性的接口，后续会话据此判断进度。

### 正文

正文从一级标题之后开始，到 `这一章建立的` 之前结束。中间怎么分节、分几节、先讲什么，没有模板。

判断标准只有一条：**读者能不能顺着读下去，并在读完时具备章首声明的那项能力。**

## 检查清单

### 可读性（最高优先级，未满足则整章不合格）

- [ ] **章首声明了交付类型**，且真的交付了该类型的内容（见 WRITING-SPEC 0.2）
- [ ] 交付类型与本章主题匹配：讲"长什么样"给标准范式，讲"怎么运行"给可运行脚本
- [ ] 没有为了通过检查而硬塞与主题无关的示例
- [ ] 内容是讲透的：是什么、为什么、怎么做、什么情况不适用，四件事都交代了（不要求写成四节）
- [ ] 没有换说法重复同一结论
- [ ] 删掉任意一句话都会损失信息（没有可删的多余句）
- [ ] 没有罗列实际不使用的选项
- [ ] **段落顺序有理由**：每次切换话题，读者都能明白为什么要讲这个
- [ ] **没有套用固定套路**：这一章的分节方式，与上一章不同

### 内容

- [ ] 没有虚构场景、人物、对白
- [ ] 每个数字都能由 `code/` 下的脚本跑出，或属于结构事实
- [ ] 没有估算数字未标注
- [ ] 没有评价性形容词（非常、极其、糟糕、关键、核心）
- [ ] 没有感叹号、反问句
- [ ] 「你」的出现次数为 0 或仅在必要处

### 标题

- [ ] 每个标题都是名词短语或结论句
- [ ] 没有比喻、引号强调、emoji
- [ ] 标题能概括该段内容
- [ ] 小节标题写对象或结论，不写"为什么""怎么做"这类功能名

### 结构

- [ ] 章首四行元信息齐全且顺序正确（知识点 -> 交付 -> 组件 -> 读完应当能回答）
- [ ] 有 `这一章建立的` 与 `下一章` 两节，位置在正文之后
- [ ] 知识点编号与 `OUTLINE.md` 一致
- [ ] 章号与文件名一致

### 代码

- [ ] 脚本已实际运行，输出与正文一致
- [ ] 离线可跑，不需要 API Key
- [ ] 估算值已在代码和正文两处标注
- [ ] 计算类脚本使用了固定种子

### 引用

- [ ] 所有 `第 N 章` 引用存在的章节
- [ ] 所有 `code/` 路径存在
- [ ] 跨章小节的引用准确
