# 章节重建作业书 v2（连贯优先）

> 适用于**第 1–26 章的重建**。与 v1（`TRIM-BRIEF.md`）的区别：v1 是在已压缩稿上继续改，v2 是**从原始稿重新压一遍**，并且把"前后文通顺"作为第一优先级。

## 零、为什么要重建

第一轮压缩只验了"代码/输出/表格逐字不变"和"字数落在区间"，没验"读完能不能接上"。结果是读者反馈：**上一句在讲 A，下一句突然说"后果是……"，而这个"后果"的成因在压缩时被删了。**

一个真实例子（第 8 章）：

- 原文有 §1.5「失控与'任务本身很难'的区别」，含一张对照表（步数 / 每步事实 / 回灌内容 / 修法），结论句是"只看步数无法区分——这正是'调小上限'常常无效的原因"。
- 压缩时整节被并掉，表格删了，只留下"…指纹永远不重复，只有上限能停。**后果是"换参数打转"会被当成"任务太复杂"**"。读者不知道"任务太复杂"是哪来的、和上文什么关系。

**所以本轮的第一判据不是字数，是"每一段都能被上一段接住"。**

## 一、来源：从原始稿重建，不从现稿改

每章的起点是 `627ddd9` 这个提交里的版本（压缩前的完整稿）：

```bash
git show 627ddd9:NN-*.md > .trim/NN.base.md     # 只读，不要 git add
```

然后用 `docs/trim_split.py` 处理 `.trim/NN.base.md`（它会生成 `.trim/NN.seg.json` 与 `.trim/NN.view.md`）。
**注意**：`trim_apply.py` 写回时用的是当前工作目录里的同名段表，所以第 1 步先把它 split 一次即可；回填后用 compare 确认代码块哈希与基线一致即可（`trim_verify --base 627ddd9` 就是干这个的）。

要求：
- **代码块、输出块、表格一律从原始稿原样保留**，不增不删不改。
- 章节标题（H1）与章首引用块、章末清单、导航：从**当前文件**取（它们已被 `gen_book.py build` 统一过，与 `book.json` 一致），不要用原始稿里那份。
- 受影响的知识点以原始稿为准（另一条工作线删掉过一些知识点，本轮不追究删得对错，但**这 26 章按原始稿的完整知识点重建**）。

## 二、保留什么（比 v1 更严）

| # | 必须保留 | 说明 |
|---|---|---|
| K1 | 每节的**第一段**（总起句/本节要回答的问题） | 删了它，后面的"因此/所以/后果是"全部悬空 |
| K2 | 每张表格**引出它的一句话**，以及**表格之后的判据句** | "下表/上表/后两行是判据"这类引用必须能指到东西 |
| K3 | **对照关系**（A 与 B 的差别、为什么这么分） | 这是读者理解"为什么要有这一步"的唯一来源 |
| K4 | 术语与说法的**首次定义** | 包括加引号的说法：`"任务太复杂"`、`"换参数打转"` 这类，第一次出现必须带解释 |
| K5 | **成因句**（为什么会这样） | 只留结论不留成因，就是"后果是……"没头没尾 |
| K6 | 每节末尾的**收束句**（这一节确立了哪条判据） | 它决定读者能不能带走一条规则 |

## 三、可以删的（与 v1 相同）

- 元话语（"这句话决定了…""值得注意的是""本节/下面"）
- 情绪词与拟人动词（致命、坑、兜住、接住）
- 第二人称场景（"你答不上来""想象你是"）
- 判断式粗体（粗体只留字段名、数字、命令、错误信息）
- 同一结论的重复表述（章首说过、节末又说、章末再说一遍——只留信息量最大的一处）
- 铺垫性的背景、不服务于本节结论的举例

## 四、结构

- 每节保持"缺什么 → 成因 → 怎么补 → 会怎么坏 → 边界"的因果顺序，**不许把两节的内容混进一段**。
- 节数不必强求合并。**如果合并会让某节的结论失去总起句，就不合并**（这是 v1 犯的错）。
- 允许保留原来的 H2/H3 划分；只在"两节讲同一件事、且合并后仍能保留各自的总起句与判据"时才并。

## 五、验收（六项）

```bash
python docs/lint_prose.py    NN-*.md      # 风格（现行口径 2800–4400 散文，见下）
python docs/check_chapters.py NN-*.md     # 结构
python docs/trim_verify.py   NN --base 627ddd9 [--restructure]   # 代码输出表格逐字、引用不减
python docs/check_reader.py  NN           # 锚点（代码来源/输出出处/并列项/术语）
python docs/check_flow.py    NN           # 连贯（孤儿指代/指向已删表格/空壳小节/未定义说法）
```

**散文长度**：现行 `lint_prose.py` 的口径是 **2800–4400**（比 v1 的 4800–6250 更短，是后续定下的标准）。若你判断压不到 4400 而又不想删知识点，**就停在 4400 附近并把理由写进报告**，不要为凑数删判据。

## 六、check_flow 的五类问题与修法

| 类 | 报的样子 | 修法 |
|---|---|---|
| F1 孤儿指代 | 段落以"这/那/它/该/前者/后者/后果/结果"开头，与上一段没有共同词 | 补回上一段的落点句，或把指代改成具体名词 |
| F2 指向已删表格 | "表格后两行/上表/第三行"但上方没有表格 | **把表格拿回来**（从原始稿），或删掉这句引用 |
| F3 指向已删小节 | "上一节…"但本节之前没有对应小节 | 改成具体节名，或补回那节 |
| F4 空壳小节 | `###` 标题下直接是代码块 | 补一句总起（"下面是这段做法的示意代码："） |
| F5 未定义说法 | 结论句里出现引号包住的、前文从未出现的说法 | 在首次出现处补一句解释，或把说法换成普通描述 |

F5 会有误报（像"有没有停"这种自解释的说法），**逐条看，能解释的就在报告里注明，不要硬改**。

## 七、交付

每章报告：

```
第 NN 章（基线 627ddd9）：散文 A→B（目标 2800–4400），章汉字 X→Y
  lint ✓ chapters ✓ verify ✓ reader ✓ flow ✓（F5 保留说明 n 条）
  结构：H2 a→b，H3 c→d（如未动写"未动"）
  保留的对照/表格：n 处；删掉的元话语：n 处
```

发现原稿硬伤（如标题数目与正文不符、节号断了）一并修，并在报告中单列。
