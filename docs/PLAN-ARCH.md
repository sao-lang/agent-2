## 二、五处共用的骨架

### 2.1 章首四行（可直接用）

```markdown
> **知识点**：B6 编排的三层——分派、主体、校验；三者的判据与成本结构
> **本章回答**：一个任务该用哪种推进方式，分派与校验各占多少成本
> **示例目录**：`code/knowledge/ch22_orchestration/`
> **读完应当能回答**：能对任意任务说出主体形态并给出理由；能算出一个带反思的循环贵多少；能说出分派层的四个契约
```

第 33、52 章按同样格式改知识点与示例目录。

### 2.2 每章开头必须有的总图

```
系统 = 拓扑 + N 个 agent
agent = 分派 + 主体 + 校验
```

第 22 章画全五层（含执行层并注明"不是架构"）；第 33 章只画拓扑层，并复述一句"拓扑是系统层，不是 agent 层"；第 52 章画"一个 `Agent` = 一次 `build()` + 一个 loop"，然后接四种拓扑。

### 2.3 名字的写法（防目录化）

- **先判据，后名字。** 每一节的第一句必须是判据或失效，不是定义。反例："ReAct 是一种将推理与行动交替进行的范式。"
- **每个名字第一次出现，必须写明它把决定权放在哪**（代码 / 模型每步 / 计划 / 人 / 板上的状态）。
- **不写优缺点列表。** 只写"成本记号"与"坏了长什么样"。
- **同一张对照表。** 凡讲多种形态，必须给一张表，列固定为：形态 / 决定权 / 模型调用次数 / 成本记号 / 失败信号。

### 2.4 示例的硬要求（沿用 `WRITING-SPEC` 1.1）

- 每种形态一个完整可运行函数，后面紧跟真实输出。
- 对照表里的每一个数都来自脚本打印，不许手填。
- 分派层与反思层各要一个"失败"输出（误分流、修了三轮仍在同一错上）。

## 五、验收

### 5.1 每章通用

- [ ] 章首四行齐全，知识点编号与 OUTLINE 一致
- [ ] 每节第一句是判据或失效，不是定义
- [ ] 每个形态都有代码 + 真实输出 + 一句"这段说明了什么"
- [ ] 对照表每个数都能从脚本复现
- [ ] `这一章建立的 N 件事` 与 `下一章` 都在
- [ ] 标题 ≤ 12 字、名词短语；本章标题不全是同一句式

### 5.2 架构特有

- [ ] 每个名字第一次出现都写明了"决定权在哪"
- [ ] 每种形态给了失效信号，且不同形态的失效不重复
- [ ] "架构"一词只用于分派/主体/校验/拓扑四层；协议、推理策略、集成策略不用这个词
- [ ] 第 33 章没有出现 A2A 的代码；第 38 章没有出现原理重讲

### 5.3 副线替换实验（第 52 章）

| 实验 | 断言 |
|---|---|
| `Supervisor` → `Handoff` | 结论一致；只有"控制权归属"改变 |

| `Supervisor` → 单 `Agent` | 只有"上下文隔离"消失 |
